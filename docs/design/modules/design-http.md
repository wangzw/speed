# http

## 职责

- 依据配置打开各监听端，在 `Serve` 阶段绑定地址并开始接受请求。
- 提供路由与中间件的登记面，写入闸门借用 `Migrate` 与 `Start` 阶段位，框住全局 `Init` 阶段。
- 按各中间件声明的约束与数值组装每个监听端的链，交给该端的 gin 引擎。
- 接住各登记层与 handler 抛出的 panic，收口一次响应并记一行日志（[ADR-http-recovery-2026-09-22](../../adr/adr-http-recovery-2026-09-22.md)）。
- 建立请求上下文，把日志模块的 logger 注入其中，供链上各层与 handler 取用。
- 停机时由 `Stop` 关闭各端的监听器，并等在途请求排空结束才返回（[ADR-http-shutdown-2026-09-14](../../adr/adr-http-shutdown-2026-09-14.md)）；排空开始时向不会自行结束的响应发出信号。
- 报告各监听端是否仍在接受请求。
- 定义资源类型 `Spec`，供模块声明自己的 OpenAPI 文档片段，并在启动时校验其形状。
- 定义默认的错误响应形状，经可选接缝接受定制，并提供写出它的入口，供各层与 handler 取用（[ADR-http-errors-2026-10-10](../../adr/adr-http-errors-2026-10-10.md)）。

登记面用 gin 的类型表达：路由的 handler 与中间件的 `Handler` 都是 `gin.HandlerFunc`。**本模块是 gin 的封装**（[ADR-http-surface-2026-09-14](../../adr/adr-http-surface-2026-09-14.md)、[ADR-module-packaging-2026-09-14](../../adr/adr-module-packaging-2026-09-14.md)）：路由匹配与路径的语法、中间件的调度、请求体的绑定与校验、响应的渲染都由 gin 提供，本模块不在其上另设一层，也不包装它们；它承担的是装配。取用本模块的宿主因而承受 gin 的依赖闭包。

### 非职责

- **不提供请求体绑定、校验与响应渲染。** 它们是 gin 的，handler 直接用 `gin.Context` 的方法；本模块不包装它们，也不提供替代品。
- **不改动 gin 绑定与校验器的进程级设置。** 那些设置对同一进程里的全部 gin 引擎生效，归宿主决定。
- **不认识任何具体功能。** 认证（[authn](design-authn.md)）、租户、限流是各自模块的事，本模块只按它们声明的约束排序，不知道任何一层做什么（[ADR-http-middleware-2026-09-14](../../adr/adr-http-middleware-2026-09-14.md)）。
- **不为 handler 自己写出的响应定形状。** 默认的错误响应形状只覆盖本模块写出的响应与经写出入口写出的响应（见外部接口契约）；handler 用 gin 自己写出的响应，本模块不拦截。
- **不决定哪些路由免于认证。** 路由的认证策略归实现认证的那个模块（[authn](design-authn.md)），它以中间件的形式接入。
- **不判定监听端是否健康。** 本模块报告它是否仍在接受请求，把这个事实解读成健康与否归读取方，本模块不定义健康的含义，也不提供探活路由。
- **不合并 OpenAPI 片段，也不发布它们。** 本模块保存各模块声明的片段并校验其形状，把它们合成一份完整规格、或挂一条路由把它提供出去，都归读取方。
- **不签发或轮换 TLS 证书。** 监听端的配置承载证书的位置，证书从哪里来、何时更换不在本模块范围内。
- **不承载运行期可变的参数。** 判据是该值是否在数据库可用之前就被需要；监听地址与超时在其列（[ADR-config-scope-2026-09-13](../../adr/adr-config-scope-2026-09-13.md)）。

## 外部接口契约

本模块交付一个功能，定义一种资源类型供其他模块声明，另有写出错误响应的入口与排空信号供 handler 与各层取用，另有一个供其他模块实现的可选接缝 `ErrorResponder`。

**交付的功能**。功能标识的元素类型必须是接口，取用写作 `core.Resolve[http.Router](reg)`：

```go
type Router interface {
    // Endpoint 取得一个已声明的监听端。任何阶段都可以调用。
    Endpoint(name string) (Endpoint, error)
    // Endpoints 返回已声明的全部端名，升序，每次调用返回一份新切片。
    // 任何阶段都可以调用。
    Endpoints() []string
}

// Endpoint 是一个监听端上的登记面。
type Endpoint interface {
    // Route 登记一条路由：method 是 HTTP 方法，path 取 gin 的写法，
    // handlers 依次运行，最后一个处理本次请求。
    Route(method, path string, handlers ...gin.HandlerFunc)
    Use(mw Middleware)
    Accepting() bool
}
```

`nethttp` 是 `net/http` 在本包内的别名——本包自身叫 `http`，引用标准库时要区分开；`gin` 是 `github.com/gin-gonic/gin`。

`Endpoint` 在端名未声明时返回错误，因为端的集合来自配置这份数据。`Endpoints` 不返回错误：它读的是同一份已声明的集合。`Route` 与 `Use` 不返回错误：登记不上的只有调用点的编程错误，它们当场 panic，与 `core` 对非法功能标识、对重名登记的处理同类（见 [core](design-core.md)）。`Handler` 为 `nil`、`Route` 没有 handler 或其中有 `nil`、`Provides`、`After` 与 `Before` 中出现非法的功能标识、不是 gin 规整后写法的路径、以及 gin 判为非法的方法或路径，都属于这一类——方法与路径是代码里写死的字符串，写错它们与数据无关。gin 接受 `nil` 的 handler 而要到请求到来时才崩，本模块因而在登记点拦下。登记时用一台独占的 gin 引擎单独试挂即可把非法的路径与冲突分开。

**路径须已是 gin 规整后的写法**：以 `/` 起头，不含多余的斜杠与 `.`、`..` 段，末尾的斜杠按原样保留。gin 把路径接到引擎的根上时会规整它，`c.FullPath()` 报出的是规整后的结果；登记的路径与它逐字相同，按（方法，`c.FullPath()`）与登记写法比对的层（认证的豁免、审计的匹配）才不会因为写法不同而永不命中。

**端的集合在本模块的配置里封闭，登记面按名取端，也列出全部端名。** 登记面的读方法是 `Endpoint` 与 `Endpoints`：`Endpoint` 按名取一个端，`Endpoints` 返回已声明的全部端名，按升序排列，调用方改动返回的切片不影响登记面（[ADR-http-enumeration-2026-10-10](../../adr/adr-http-enumeration-2026-10-10.md)）。列出的只是端名：一个端上登记了哪些路由与层，登记面不提供枚举。模块能把自己声明的端名清单与端的全集互相比对，也能对每个已声明的端登记同一层；比对不是登记面做的，也不会让缺失自动失败。一个模块只在自己清单点名的端上登记，漏写一个端，那个端上就不会出现它的任何一层，启动期既不失败，也没有一行诊断指向它，除非那个模块自己拿全集比对并报错。这一档与宿主在命令树上漏写一个模块同源，起于装配的决定而不是意外（见 [architecture](../architecture.md) 的可观测性）。察觉它靠 `Serve` 组装时逐端写出的链清单：每个已声明的端一行，行内按组装后的次序列出该端的各登记层，每一层连同它在 `Provides` 里声明的功能标识；不经登记面、也没有功能标识的那些层（请求体上限与请求上下文的建立、兜底层）同样列在这一行里，只有名字。功能标识是登记面能就「这一层代表什么」说出的唯一一件事，也是 `After` 与 `Before` 据以建图的那一样东西；`Middleware.Name` 只用于诊断，不是一个可被比对的标识，因而「某功能在这个端上的链里无人代表」只在这一行里读得出来。

同一个端上的路由**冲突**不属于这一类：登记只记录声明，两条路由是否冲突要到 `Serve` 组装、挂到该端的引擎上时才谈得上，那时 gin 以 panic 拒绝，本模块捕获它并报成启动失败。

功能标识是否合法，判据与 `core` 的同一条（元素类型必须是接口）。`core` 未导出它的判定，本模块自建一份，并以一条测试比对两者的结论——拿 `core` 的公开行为当基准，两份规则漂移时那条测试会红。

**`core` 不会导出这个判定**：它导出的包级函数受架构不变量约束，限于注册表的构造函数、进程级注册表变量、哨兵错误与需要类型参数的泛型封装，判定函数不在其中。本模块这份判定与那条比对测试因而是常设的，不是等上游补齐的临时措施。

本模块排他地交付 `(*Router)(nil)`：两个入口模块同时启用时，登记方无从知道自己登记到了哪一个，而"只能整体取出"对登记没有意义。本模块由根包在包初始化时登记，模块名是 `http`（导出为 `ModuleName`），**宿主在命令树上以这个名字点名它**：它排他交付，依赖闭包不替宿主挑，宿主没有写下的入口模块不进参与集，为它预置了实例的除外（见 [core](design-core.md)）。

**排他声明多数时候并不是冲突真正暴露的地方。** 另一个交付 `Router` 的模块若同样使用 `http` 这个配置命名空间，同名输入项在 `config` 收集清单时就会失败，走不到消解阶段；同名登记更早，`core.Register` 在 `init` 期即 panic。排他声明因而是一条契约陈述，它在两个入口模块各自声明了不相交输入项这种情形下才是实际的拦截点。

**登记面在借用自 `Migrate` 与 `Start` 的阶段窗口内接受写入**，窗口之外的写入一律 panic。窗口以本模块的 `Migrate` 回调为起点、`Start` 回调为终点：阶段逐个推进，全局 `Init` 阶段整体落在这个区间之内，区间两端还各含 `Migrate` 与 `Start` 阶段中本模块之外的回调（见阶段行为一节）。最终 handler 在 `Serve` 阶段组装一次，此后不变（[ADR-http-routing-2026-09-14](../../adr/adr-http-routing-2026-09-14.md)）。

读不受这道闸门限制：`Accepting` 报告该端此刻是否仍在接受请求，任何阶段都可以调用，绑定之前与停机之后都返回 `false`。

**中间件**。一层中间件连同它对自身位置的声明：

```go
type Middleware struct {
    Name     string          // 只用于诊断：panic 文本与启动时列出的链
    Provides []core.Token    // 本层在链上代表哪些功能，供他人指向
    After    []core.Token    // 本层位于这些功能的中间件之内
    Before   []core.Token    // 本层位于这些功能的中间件之外
    Order    int             // 约束未定之处的偏好，小者靠外
    Handler  gin.HandlerFunc // 本层本身：c.Next 交给其后各层，c.Abort 终止链
}
```

`After` 与 `Before` 是硬约束，`Order` 只在硬约束未定的自由度内起作用，两者因而不会冲突（[ADR-http-middleware-2026-09-14](../../adr/adr-http-middleware-2026-09-14.md)）。

**写出者携带的可选接口不得因包装而丢失。** gin 的链上，一层读响应的状态、是否已写出与已写出的字节数，用 `c.Writer` 的 `Status`、`Written` 与 `Size`，不必包装写出者；gin 的写出者本身携带 `Flusher`、`Hijacker` 与 `Unwrap`，`http.NewResponseController` 经它可用。替换 `c.Writer` 的层，以及本模块在 `net/http` 一级包住写出者的层（兜底层），都要把原来那个写出者携带的可选接口转发出去，或用 `Unwrap` 把它暴露出来，否则一个对这些接口做类型断言的处理器在该端点上静默失效——流式响应与协议升级随之失效，且不报错。这条要求归本模块，因为链的组装与写出者的归属都在这里；装配里任何一层包住写出者都受它约束。

**`Provides` 是约束能够落地的前提**：`After` 与 `Before` 指向功能，而链上哪一层代表哪个功能，只能由那一层自己声明。登记面拿不到登记方的身份——`Endpoint` 不带它，`core` 不提供「当前正在 `Init` 的模块」这样的查询，而本模块允许在协程里登记，调用栈也就不成立。`Provides` 为空是合法的，代价是无人能指向这一层。

**本模块不校验 `Provides` 与登记方描述符里 `Provides` 的一致性**，同样因为它不知道登记方是谁。一层因此可以声称代表一个它所属模块并不交付的功能。

声明写成：

```go
// 遥测模块：本层代表它交付的追踪与指标，位置靠外，不指向任何别的功能
ep.Use(http.Middleware{
    Name:     "observability",
    Provides: []core.Token{(*observability.TracerProvider)(nil), (*observability.MeterProvider)(nil)},
    Order:    -10,
    Handler:  instrument,
})

// 另一个模块的层：本层代表审计，示例把它排在遥测层之内
ep.Use(http.Middleware{
    Name:     "audit",
    Provides: []core.Token{(*audit.Audit)(nil)},
    After:    []core.Token{(*observability.TracerProvider)(nil)},
    Handler:  capture,
})
```

**路由引擎**。每个监听端由本模块建一台 gin 引擎，不带 gin 的默认中间件。引擎是本模块的内部，登记方经 `Endpoint` 登记，拿不到它。引擎有如下设定：

- **关闭尾斜杠重定向。** gin 默认把 `/x/` 重定向到 `/x`，而重定向发生在全局中间件之前，一个被重定向的请求不经过认证、限流、审计与遥测的任何一层。
- **开启对不允许的方法的识别。** 路径存在而方法不在其中时答 405 并带 `Allow` 头，不答 404。gin 在运行任何层之前就把 `Allow` 写进响应，一个在这条路径上先行拒绝的层（认证的 401、租户解析的 404、限流的 429）因而会把路径存在与它允许的方法带给没有凭据的调用方；引擎的第一个内部处理器把它摘下并留存，由方法不允许的处理器在各层放行之后写回。这个处理器不在登记面上，不参与排序，也不列入链清单。
- **开启上下文回落。** `*gin.Context` 作为 `context.Context` 使用时回落到请求上下文取值，`log.FromContext(c)` 与 `log.FromContext(c.Request.Context())` 取到同一个 logger。
- **无匹配路由与方法不允许经错误响应的入口写出**（见下）。两者与有匹配的请求一样经过全部登记层，认证因而在路径不存在时同样先于 404。
- **不信任任何代理头。** gin 默认采信任何来源发来的 `X-Forwarded-For`，`c.ClientIP()` 因而可以被客户端伪造；引擎不信任任何代理，`c.ClientIP()` 只返回连接的对端地址。
- **gin 处于发布模式，调试输出不写到标准输出。** 运行模式与输出是 gin 的进程级设置：路由登记时的调试打印不经日志模块，本模块因而在构造时把它们关掉。

**路由冲突在 `Serve` 组装时报成启动失败，并归因到一对路由。** gin 在挂载时以 panic 拒绝冲突：同一位置上的路径参数名不一致、同一方法同一路径重复登记、通配与静态段或参数并存都在其列；静态段与参数并存则被接受，不同方法上的同一路径互不冲突。本模块捕获这个 panic，点名被拒的那一条，以及已挂载的哪一条与它冲突。归因的做法是把已挂载的每一条与被拒的那条两两放到一台独占的引擎上复现，复现出拒绝的那一对即是。**归因不出来时错误要说明这一点，不退化成只点名被拒的那条**：一条只对部分冲突成立的诊断承诺，会在遇到它答不出的那一类时悄悄失效。gin 在挂载时拒绝、而已挂载的路由中没有任何一条能与被拒的那条复现出拒绝的情形——例如一条路由连同该端各层的 handler 总数超出 gin 一条链所能容纳的上限——同样报成路由冲突，错误文本说明归因失败。登记点的试挂在一台没有任何层的引擎上做，看不到这一类。

**API 声明资源**。模块声明自己那一份 OpenAPI 文档，本模块保存供查询：

```go
type Spec struct {
    Endpoint string // 这份文档描述哪个监听端上的 API
    Document []byte // OpenAPI 文档片段，JSON
}
```

`Document` 是片段而非完整的规格：它描述声明它的那个模块提供的 API，一个进程的完整规格由读取方把各片段合并得出。模块通常以 `//go:embed` 把自己的 `openapi.json` 读进来。

`Spec` 不参与路由。它供文档合并、网关配置与权限清单这些发生在装配之外的用途读取，与实际登记是两份各自维护的事实（[ADR-http-routing-2026-09-14](../../adr/adr-http-routing-2026-09-14.md)）。读取方用 `core.Resources[http.Spec](reg)` 取得全部片段，每一份都带着声明它的模块名，合并冲突因而能点到来源。

**取材域**（架构不变量 15）。本模块自己的形状校验取**可用集**：它只校验声明而不让声明生效，而畸形与否是静态事实，让一条声明因为本次没被纳入而漏检，会使同一个二进制在两条命令下给出不同的启动结论。它跑在 `Prepare` 里，此时启用结果尚未消解出来，只有启用集不可取（声明集与参与集在这之前就已确定，见 [core](design-core.md)）。**这个消费点不做减法**：形状校验只读声明、不让它生效，一个本次不运行的模块，其 `Spec` 的畸形仍是这个二进制的一份静态事实。**读取方的取材域由读取方自己裁定**：问"这个二进制提供哪些 API"取可用集，问"此刻这个进程在服务哪些 API"取启用集。本模块交出全部片段，不替读取方过滤——那是它对读取方的承诺，不是对取材域的规定。

一个 `Spec` 对应一个端，API 分布在多个端的模块把多个 `Spec` 放进自己的 `Resources`。`Spec.Endpoint` 指向一个未声明的端时本模块不报错：资源是静态声明，本模块只保存并供查询，不解释它描述的内容。

**本模块校验文档的形状，不校验它的内容。** 空的 `Document`、不是 UTF-8、不是合法 JSON、顶层不是 JSON 对象、顶层没有 `openapi` 字段，各是一类启动失败。完整的 OpenAPI 语法校验要引入解析库，本模块不引入它；这里挡住的是会让下游的合并在启动之后才崩掉的那一类。

**配置**。本模块以 `config.Schema` 资源声明自己的输入项。每个监听端各有地址、各项超时、请求体上限与可选的 TLS 证书位置；排空时限也按端配置，`Stop` 以它为界等待在途请求走完。端的集合由配置给出：一个端都没有声明时本模块无法启动，启动失败，错误点名缺的是监听端的声明。纳入本模块即承诺装配它，配好至少一个端因而不可省——无论由宿主在命令树上点名，还是不写命令树的调用方走 `Run` 入口。

**端名 `*` 是保留的。** 配置里写一个名为 `*` 的端，`Prepare` 即失败，错误点名该端与应改的键，与未知键、缺地址的判定同在读配置这一步。保留它，是为了让别的模块的端名清单能以 `*` 表示全部已声明的端，而不与某个真实端名相撞（[ADR-http-enumeration-2026-10-10](../../adr/adr-http-enumeration-2026-10-10.md)）。

**各项的默认值**：读取请求头的时限 10 秒，读取与写出的时限各 30 秒，空闲连接 120 秒，排空时限 30 秒，请求体上限 1 MiB。请求体上限对每个端无声地生效，超限的请求体在读到它的地方被截断，`0` 表示不设上限。

**端条目里的每个键都要是一个端认得的键，认不出即启动失败。** 端的集合是一个容器叶子，其内部的键不参与配置的未知键校验（见 [config](design-config.md)）：一个拼错的排空时限或请求体上限会被静默丢掉、默认值照样生效，而配置它的人以为这个端已按所写的生效。本模块因而自己查这些键，错误点名那个端、认不出的键与一个端可用的全部键。

**时长项的零值不统一，判据是关掉它的后果由谁承担。** 多数时长项显式 0 表示关闭该项，后果限于配置者自己那个端。两项例外，显式 0 一律拒绝并给出理由：读取请求头的时限关掉之后，一个不发完头部的连接可以无限占住资源；排空时限关掉之后 `Stop` 会无限等一个卡不动的在途请求，而此时 context 已被剥掉取消、注册表也不施加停机超时，宿主阻塞在驱动里再无可打断的途径——排空时限正是 [ADR-http-shutdown-2026-09-14](../../adr/adr-http-shutdown-2026-09-14.md) 指定用来满足「回调必须有界」的那一项。

**请求体与响应**。handler 里的请求体绑定、校验与响应渲染直接用 `gin.Context` 的方法，本模块不包装它们。请求体的大小上限由该端的配置在链最外层施加，对该端的每个 handler 一律生效；超限的请求体经 gin 的绑定以 `*nethttp.MaxBytesError` 返回，调用方用 `errors.As` 判别。

**错误响应**。本模块写出的错误响应有一个默认形状，可由一个可选接缝整体替换；供各层与 handler 写出错误响应的入口与它们共用同一处决定形状（[ADR-http-errors-2026-10-10](../../adr/adr-http-errors-2026-10-10.md)）：

```go
// Problem 是一次错误响应的内容，字段取自 RFC 9457。
type Problem struct {
    Type     string // 缺省为 "about:blank"
    Title    string // 缺省为状态码的标准说明，没有标准说明的状态码则省略
    Status   int
    Detail   string
    Instance string
    Cause    error // 不写入默认响应体，供定制的 ErrorResponder 读取
}

// ErrorResponder 决定本模块写出的全部错误响应的形状。
type ErrorResponder interface {
    RespondError(w nethttp.ResponseWriter, r *nethttp.Request, p Problem)
}

// Fail 把一次拒绝或失败写成错误响应，并中止其后的 handler。
func Fail(c *gin.Context, p Problem)
```

没有模块交付 `ErrorResponder` 时用默认形状：以 `Problem.Status` 为状态码，不在 200 至 599 之内时写 500——单独写出的 1xx 是信息性响应，不是最终状态；响应体是 `application/problem+json`，内容为 `Type`、`Title`、`Status`、`Detail` 与 `Instance` 中的非空字段，`Cause` 不写入。默认形状自己写出响应体，调用方在此之前设过的 `Content-Length` 与 `Content-Encoding` 描述的是另一份响应体，它丢弃这两个头，其余响应头保留。兜底层接住 panic 后写默认形状时，另外丢弃描述 handler 原打算写出的那份内容的头：`Content-Disposition`、`ETag`、`Last-Modified`、`Content-Range`、`Accept-Ranges`、`Cache-Control` 与 `Expires`——一条带着 handler 的 `Cache-Control: public` 的 500 会被缓存当作答案留下。交付者替换的是整个形状：它须按 `Problem.Status` 写出状态码，响应体与媒体类型由它决定，响应头一概不由本模块动。

**经这处决定形状的响应**是：`Fail` 写出的；兜底层接住 panic 后写出的，状态码 500，`Cause` 是一个包着 panic 值的错误；无匹配路由的 404；方法不允许的 405。handler 用 gin 自己写出的响应不经它。

**`Fail` 之前设置的响应头保留。** 认证层的 `WWW-Authenticate`、限流层的 `Retry-After` 由各层在调用 `Fail` 前设好，形状的决定者不丢弃它们。响应已经开始流出去时，`Fail` 不写入，只中止其后的 handler，已提交的状态码与响应体不被改写。`Fail` 对「已开始」的判据是 gin 的写出者认定的已写出（`c.Writer.Written()`），它比兜底层的判据宽：处理器强制写出了 1xx 的头、或在 HTTP/2 上接管连接失败之后，gin 已认作写出，`Fail` 因而不再写入，兜底层却仍会作答。

**写出入口取得的 `ErrorResponder` 由请求上下文的建立那一层放进请求上下文**，与 logger 同途，`Fail` 从 `c.Request.Context()` 取它。请求上下文里没有它时（没有经过本模块的链，例如测试里单独构造的上下文）用默认形状。

**排空信号**。不会自行结束的响应——服务端事件流、长轮询、被接管去跑别的协议的连接——要知道停机已经开始，才能自己收尾：

```go
// Draining 返回一个通道：ctx 所属请求的那个监听端停止接受请求、开始排空时，它被关闭。
func Draining(ctx context.Context) <-chan struct{}
```

**排空不取消在途请求的 context**：普通请求要能对着一个完整的系统走完，取消它的 context 会让它中途失败。只看自己 context 的长连接 handler 因而得不到任何通知，一直跑到排空时限把它切断，停机随之报排空超时；这个信号与请求的 context 分开，正是为此。它由监听端的服务器放进每个请求的上下文，不经登记面，也不占链上的位置。**不是派生自请求上下文的 context 取不到它**，返回 `nil`，一个永远不会就绪的通道。

## 依赖

`pkg/http` 根包 import `pkg/core`、`pkg/config`、`pkg/log` 与 gin：`core` 提供功能标识的类型与资源、实例的查询，`config` 用于声明输入项，`log` 提供可选依赖的功能标识与上下文存取，gin 提供登记面的 handler 类型与路由、绑定、渲染。接口面上除标准库与本包自己的类型之外，出现 `core` 的功能标识类型与 gin 的 `gin.HandlerFunc`、`*gin.Context`。

**本模块封装 gin，取用本模块的宿主因而承受 gin 的依赖闭包，另承受 `pkg/config` 的解析工具依赖。** 声明输入项与读取配置都经由 `pkg/config`，它解析配置所用的那些库因而落在本模块的传递闭包里，这是 [ADR-config-parsing-2026-09-20](../../adr/adr-config-parsing-2026-09-20.md) 记下的代价；gin 与它的传递依赖落在其中，是 [ADR-http-surface-2026-09-14](../../adr/adr-http-surface-2026-09-14.md) 记下的代价。守住的那一条是本模块不在其上新增：`pkg/http/deps_test.go` 以「标准库 ∪ 本仓库模块 ∪ `pkg/config` 的当前闭包 ∪ gin 的当前闭包」为预算扫描本模块的全部包，预算之外的一个包即失败，OpenAPI 解析库因而仍然进不来。

本模块声明对 `Logger` 功能的可选依赖：日志模块在场时注入它的 logger，不在场时不注入。可选依赖的缺失是一种合法配置，模块按文档所载的默认行为继续运行，这是架构允许的唯一降级形态（[ADR-dependency-resolution-2026-09-13](../../adr/adr-dependency-resolution-2026-09-13.md)）。**代价**：没有日志模块时，请求路径上的日志照常写出，但进的是进程根 logger 的目的地即标准输出，而不是配置的目的地，且这不产生任何失败信号（[ADR-log-context-2026-09-13](../../adr/adr-log-context-2026-09-13.md)）。

**这条代价在真实宿主里到得了。** 根包 import `pkg/log`，而它在包初始化时把自己注册进进程级注册表，于是凡 import 了本模块的宿主都传递地拿到一个**已登记**的日志模块。已登记不等于在场：取用只认已有的实例，一条只运行级纳入本模块与业务模块、没有列举 `log.ModuleName` 也没有预置日志实例的命令里，日志模块不进参与集、不构造，本模块也就真的取不到它。这一支的表现与手工构造注册表时相同——请求路径上的日志进进程根 logger 的目的地，而不是配置的目的地，且不产生失败信号。

本模块另声明对 `ErrorResponder` 功能的可选依赖：有模块交付它时，本模块写出的全部错误响应的形状由它决定；没有时用默认形状。这一项缺席不丢失信息，默认形状带着状态码与标题。多个模块交付它时取用以 `ErrAmbiguousProvider` 失败，启动随之失败。

方向满足架构不变量：本功能目录位于 `core` 与 `config` 之上、全部登记路由的模块之下，不 import 其中任何一个。中间件的相对位置以功能标识声明，标识由声明方给出，本模块因而不 import 任何贡献中间件的模块。

## 核心数据结构

登记面在登记窗口内积累的是声明，不是成品：每个监听端持有一张按登记先后排列的路由表与一张中间件表。路由表与登记层在 `Serve` 阶段挂到该端的 gin 引擎上；引擎之外还有不经登记面的层：兜底层与请求体上限、请求上下文的建立（见兜底层一节）。组装好的 handler 交给该端的服务器。

中间件表的每一项是一个 `Middleware` 值。`After` 与 `Before` 中的功能标识指代功能而非实例，与 `Requires` 中的写法一致（[ADR-capability-token-2026-09-13](../../adr/adr-capability-token-2026-09-13.md)）。本模块不解析这些标识的含义，只用它们建图。

## 核心算法与流程

### Serve 阶段的组装

每个监听端各组装一次，依次：

1. 中间件按下面的排序结果依次交给该端的 gin 引擎的 `Use`，因而每一层都作用于该端的全部路由，包括无匹配路由与方法不允许的响应。先于路由交给引擎是承重的：gin 在加入一条路由时才把引擎已有的 handler 并进它的链，路由挂上之后才交的层到不了它。
2. 该端的路由表挂到引擎上。同一个端上的路由冲突在此暴露，启动失败并点名冲突的两条路由与它们所在的监听端。是否冲突由 gin 判定，本模块不自己比对；冲突落在哪两条上，按路由引擎一节所述归因。
3. 兜底层包在引擎之外（见兜底层一节）。
4. 请求体上限与请求上下文的建立包在最外层，链上每一层与每个 handler 都能取到 logger，超限的请求体在任何一层读到它之前就被截断。

组装完成后绑定地址。组装与绑定都在 `Serve` 的同步部分完成，其中任何一步失败都是启动失败。

**TLS 端经 ALPN 同时提供 HTTP/2 与 HTTP/1.1**，与标准库自己的 TLS 路径相同。TLS 监听器由本模块自建，是为了让证书在 `Serve` 的同步部分装载、装载失败即启动失败，不为改变协议的选择；客户端只提供 HTTP/1.1 时照常走 HTTP/1.1。

**绑定之后逐端写一条记录，报出实际绑定的地址。** 记录带端名、套接字实际绑定的地址、配置给出的地址以及是否走 TLS。配置写 0 号端口时端口由操作系统挑选，这条记录是进程之外得知它的唯一途径；它在接受循环起来之前写出，而套接字此时已经绑定，读到它的客户端可以立即连接。

### 中间件的排序

每个监听端各算一次，输入是该端登记的中间件表。

各中间件按其声明的功能标识建图：一条 `After` 边把本层排在提供该功能的那些中间件之内，`Before` 边反之。引用的功能在该端上没有提供者时，该边不存在，约束自动满足；提供它的模块在进程里却不守这个端，也是这一档。

图按拓扑序展开，就绪集合中取出的次序由 `Order` 决定，小者先出、落在外层；`Order` 相同者按登记先后。`Order` 只在就绪集合内选择，因而选不出违反约束的位置。

复杂度为 O(V+E)，V 是该端的中间件数，E 是它们之间成立的约束数。这是启动期各端一次性的开销。

约束成环时排不出序，启动失败并点名环上各成员。

**未落到任何一层的约束要在启动诊断中列出。** 判据是这条约束有没有摆放任何东西：一条 `After` 或 `Before` 在跳过声明它的那一层之后若不再指向任何一层，它就无声地消失了——声明它的那一层以为自己有位置保证，实际没有。这不构成失败（功能缺席是合法配置），但它必须能被看见。

**诊断要分清两种原因，它们的修法不同。** 一种是该功能在本端无人代表：装配里缺了那个模块，或者它在进程里却不守这个端，或者它的层在这个端上却漏写了 `Provides`。另一种是该功能只由声明这条约束的那一层自己代表——自指的边按跳过自身丢掉，约束因而什么也没约束到，而这是声明本身写错了，不是谁不在场。**本层之外还有别的层代表该功能时不属于此列**：自指那部分被跳过，其余照常生效。

**诊断的级别随原因而定，判据是这次装配照原样能不能是对的。** 该功能在本端无人代表时，这一行记 Info：模块不在进程里、在进程里却不守这个端，都是合法配置，一个只在部分端上解析租户的宿主每次启动都会产生这样的行。把它记成警告，合法装配就带着一条永远消不掉的警告运行，运维学会跳过它之后，真正需要处理的那一条也随之被跳过。自指的那一种记 Warn：这条声明在任何装配下都摆放不了任何东西，没有哪种配置能让它成立。**代价**：漏写 `Provides` 在图上与模块缺席同形，登记面又不知道哪一层是谁登记的，它因而同样只记 Info，没有警告指向它（[ADR-http-middleware-2026-09-14](../../adr/adr-http-middleware-2026-09-14.md)）。约束成环不在此列，它是启动失败。

### 请求上下文的建立

本模块在中间件链之外、早于任何一层取得该端的 logger 并写入请求上下文，链上各层与 handler 此后从上下文取它。注入点的位置决定字段的覆盖范围，链外是唯一能让每一层都取到 logger 的位置。

首次注入归产生上下文的这一方，不归中间件：注入是产生上下文那一步的一部分，放进中间件意味着同一条路径上可能有多个模块各自认为自己该兜底，而它们注入的 logger 带的模块名各不相同（[ADR-log-context-2026-09-13](../../adr/adr-log-context-2026-09-13.md)）。

日志模块缺失时不注入，下游的 `log.FromContext` 回落到进程根 logger。

请求上下文里同时放着 `ErrorResponder`，写出错误响应的入口从那里取它（见外部接口契约）。

### 兜底层

**兜底层是 `net/http` 一级的一层，包在每端的 gin 引擎之外、请求体上限与请求上下文的建立那一层的内侧，每端唯一。** 登记层与路由的 handler 都在引擎之内，它接住的是它们抛出的 panic：接住之后当次请求结束，进程继续服务其余连接。请求上下文此时已经建立，被接住的那一次因而能在配置的目的地上写出一条记录；而它拿不到链上各层在内层绑定的关联字段——那些字段绑在派生出的上下文里，兜底层手里的是建链时的那一个（见并发与事务边界）。它不在登记面上：`Endpoint` 的方法集里没有它，它不参与中间件的排序，也不改任何一层的先后（[ADR-http-recovery-2026-09-22](../../adr/adr-http-recovery-2026-09-22.md)）。

**写出的响应经错误响应的接缝决定**（见外部接口契约）：状态码 500，`Problem.Cause` 是包着 panic 值的错误，默认形状不把它写进响应体。接住之后不再向下或向上传递；handler 已经写出部分输出的那一档状态码改不动，见错误与失败语义。

**panic 未发生时它原样转交**，不读请求也不碰响应；handler 正常产生输出时，任何结果都不经它改变。

**gin 自带的恢复中间件不装。** 它吞掉 `http.ErrAbortHandler`，响应以空体的 200 收口，一次有意的连接放弃于是读作成功（[ADR-http-recovery-2026-09-22](../../adr/adr-http-recovery-2026-09-22.md)）。引擎之内没有任何一层接 panic，panic 穿过引擎到达兜底层。

**它不覆盖跨协程的 panic。** 一个模块在自己起的协程里 panic，只有那个协程自己接得住；兜底层覆盖的是请求路径所在的这一次调用（同一条界限见 [authn](design-authn.md)）。

**handler 既没有返回、也没有抛出值时，它照样收口并记一行，但不称其为 panic。** 这是 handler 调用了 `runtime.Goexit`，或在 `GODEBUG=panicnil=1` 下 `panic(nil)`，两者在兜底层分不开；行内写明是这种情形与它的堆栈，`Problem.Cause` 是一个说明同一件事的错误值，不是 `nil`。`runtime.Goexit` 之后协程随即结束，那次响应到不了连接，协议层把连接关掉。

**`net/http` 的 `ErrAbortHandler` 不被它接住。** 那个值是处理器在请求放弃这条连接，不是缺陷：本层原样抛出，让协议层按既有处置关掉连接，既不写状态码也不记一行。答成一次响应，会给一条已被处理器判定为坏掉的连接写状态码，并为一次客户端中途离开记一条错误。被包装过的这个值同样放行，`net/http` 按普通 panic 处置它：关掉连接，并为它自己写一条带堆栈的记录。

**`net/http` 为它自己写的记录进本模块的日志出口。** 监听端的服务器把它的输出交给本模块的 logger，因而 `base` 自身与协议层产生的 panic、TLS 握手失败、以及它对一条连接的处置，都进配置的目的地；没有这一步它们落进标准库日志的默认出口即标准错误，那是本模块的配置管不到的地方。**接受的代价**：端口扫描与协议探测产生的握手失败也在其中，它们在配置的目的地里是一类可观的量，不经这一步时只落在标准错误上；日志模块不在场时这些记录落在标准输出，与请求路径上那些记录同途。那些记录的措辞是 `net/http` 的，本模块不改写。

**响应已经开始流出去时，兜底层不写入。** 兜底层交给其余请求路径的写出者会记下响应是否已开始：写出过 200 及以上的状态码、写出过一个字节、刷新过或接管了连接，都算已开始（1xx 的信息性响应除 101 外不算，它们之后还有最终状态）。状态码与接管都以底层写出者接受为准：`net/http` 拒绝的状态码、HTTP/2 上失败的接管，都不算已开始。只有底层写出者支持 HTTP/2 的服务器推送时，这个写出者才暴露 `Pusher`，否则 gin 交给 handler 的仍是 nil。已开始时，已提交的状态码与已写出的响应体原样保留，兜底层只写那一行记录，不调用 `ErrorResponder`，`net/http` 也就不会为一次迟到的状态码另写一条记录。这个写出者同样转发底层写出者携带的可选接口，见外部接口契约。

**它写出的那次响应不带归因。** 响应不区分崩的是哪一层、哪个模块；把一类 panic 归到具体某个后端或某条路径名下，仍由发现它的那一层自己做（见 [authn](design-authn.md)、[tenant](design-tenant.md)）。它记下的那一行则是另一回事：那一行带端名、panic 值与堆栈，读日志的人据此定位到崩溃的那一帧。响应不给归因与记录不给证据不是同一件事，这里要的是前者。

**头部已经提交、响应已经开始流出去时，这一次以「格式完好但内容截断」的形态结束。** 兜底层接住 panic 之后正常返回，协议层因而按正常结束补上分块的结尾；没有兜底层时 panic 一路逃到协议层，连接被直接关掉，客户端解析分块时看得出中断。带上这一层换来的是一次可读的记录与一个可预期的状态码，代价是这一档截断对客户端不再可分辨——需要分辨它的处理器得自己在流的中间处理失败。

### 阶段行为

| 阶段 | 行为 |
|---|---|
| `Prepare` | 读配置，校验各模块声明的 `Spec` 的形状；一个监听端都没有声明时启动失败，错误点名缺的是监听端的声明，端名取了保留的 `*` 时同样启动失败。 |
| `New` | 按配置构造各监听端的状态，不绑定地址。登记面此时尚不接受写入。 |
| `Migrate` | 打开登记面的写入闸门。 |
| `Init` | 登记面接受写入。本模块自身不在此阶段登记任何东西。 |
| `Start` | 关闭写入闸门。 |
| `Serve` | 逐端组装、绑定地址并写出实际绑定的地址、起接受循环的协程。 |
| `Stop` | 逐端关闭监听器，随后等待各端排空结束，以该端配置的排空时限为界。 |
| `Close` | 收拾 `Stop` 没有走到的端；生命周期自己的路径上无动作。 |

**宿主为本模块预置的实例不是本模块的产物时，从 `Migrate` 到 `Close` 的回调都不对它做任何事**：登记面的闸门不开合，`Serve` 不监听，`Stop` 与 `Close` 不排空也不释放；它怎样对外提供服务、持有的资源怎样释放，都由预置的一方负责，它放进来的在途请求也不在下文排空的界之内（[ADR-supplied-instance-2026-10-08](../../adr/adr-supplied-instance-2026-10-08.md)）。

**闸门借用 `Migrate` 与 `Start` 两个阶段位**，因为它要框住的是全局的 `Init` 窗口，而不是本模块自己的 `Init` 回调。阶段是逐个推进的：本模块的 `Migrate` 回调执行时全局尚未进入 `Init`，本模块的 `Start` 回调执行时全局的 `Init` 已经结束，两者恰好是该窗口的两侧。挂在本模块自己的 `Init` 与 `Serve` 上做不到这件事——那样排在本模块之前的模块在 `Init` 里的合法登记会撞上假的拒绝，而整个 `Start` 阶段里的登记又会静默成功。本模块不迁移任何东西，也没有自身的服务要启动，这两个阶段位没有别的用途。

**驱动深度决定这扇门的开合，而两者之间没有约束。** 浅于 `Migrate` 的驱动不打开它，也不推进到全局的 `Init`，因而没有登记发生：窗口的两侧同时缺席，结果自洽。**恰好止于 `Migrate` 的驱动则打开它而无人关上**——`Start` 不执行，闸门一直敞到进程结束。那种驱动下没有 `Init`、没有登记、也没有流量，敞开的闸门不被任何人看见，但"登记窗口有两侧"这条性质在那里确实不成立。回避的办法是那条命令不纳入本模块：以施加迁移为目的的命令本来就不需要对外入口。代价是这一点不体现在任何一方的声明里——本模块借用的是阶段位，而推进到哪个阶段由发起驱动的那条命令决定，两者之间没有一处可供检查的约束（[ADR-lifecycle-drive-2026-09-20](../../adr/adr-lifecycle-drive-2026-09-20.md)）。

`Serve` 的回调不阻塞：绑定地址同步完成，接受循环在独立协程中进行。绑定失败即启动失败，进程不会带着一个没有入口的监听端跑起来。

### 排空的界

`Stop` 与 `Close` 收到的 context 去掉取消、保留值：正常停止的触发就是宿主取消 `ctx`，原样递下去会让任何遵守 context 的排空立刻返回（见 [core](design-core.md)）。排空的界因而来自本模块配置的排空时限，不来自 context。

**本模块各端排空结束之前，停机不越过本模块的 `Stop`。** 在途请求可以触达进程内任何模块。注册表把入口——声明了 `Serve` 的模块，本模块即是——排在其余模块之前停止（见 [core](design-core.md) 的入口单独成一个阶段），但它给出的只是先后：本模块的 `Stop` 若在排空途中返回，其余模块随即收到 `Stop`、拒收在途请求的工作，全部 `Stop` 之后的 `Close` 又会释放在途请求正在用的东西。本模块的 `Stop` 因而等排空结束才返回，此前任何模块都收不到 `Close`，不声明 `Serve` 的模块也收不到 `Stop`。形态与理由见 [ADR-http-shutdown-2026-09-14](../../adr/adr-http-shutdown-2026-09-14.md)。

**这条保证不看一个模块构造在本模块的哪一侧。** 挂路由的业务模块、声明依赖本模块功能的模块与本模块可选依赖的那些提供者，只要不声明 `Serve`，都在本模块排空结束之后才收到 `Stop`，因而可以在自己的 `Stop` 里停止接收新工作。进程里的其他入口与本模块之间仍按逆依赖序逐个停止：排在本模块之前的入口在本模块仍接受请求时就已停止，排在本模块之后的入口要等本模块排空结束才开始停止，其间照常接受请求。

**被接管的连接同样算在途。** handler 接管连接之后（WebSocket 一类的协议升级即是如此），协议层不再跟踪那条连接，它的关停既不等它、也切不断它。本模块另按 handler 的调用计数等待：一次请求在它的 handler 返回之前都算在途，排空要等计数归零，以同一个排空时限为界，到期未归零同样是排空超时。这类连接与流式响应一样不会自行结束，它们的 handler 在 `Draining` 关闭时收尾，排空才能在时限之内走完（见外部接口契约）。**接受的代价**：时限到期时被接管的连接切不断，它归 handler 所有，本模块手里没有它；handler 把连接交给自己另起的协程后即返回的，那些协程不在排空的覆盖之内。

`Stop` 先关闭全部端的监听器，再逐端等待，各端的排空因而并行进行。一个端的排空超时不缩短其余端的等待，逐端的失败聚合后由 `Stop` 一并返回，每一端的失败只报一次。

**时限从该端关闭监听器起算**，即排空真正开始的那一刻。它限的是排空这件事本身，本模块关闭其余端监听器所花的时间不计入其中。

## 错误与失败语义

启动期的失败一律终止启动。本模块为自己判定出的每一类失败提供哨兵错误，调用方以 `errors.Is` 判别，错误文本承载定位所需的信息：端名未声明、同一个端上的路由冲突、中间件约束成环、`Spec` 的文档形状不合法、监听端绑定失败各是一类。包裹一律用 `%w`，底层的 `net` 错误链保持完好。

哨兵表对本模块自己产生的失败是封闭的：新判定出一类确定失败，要么并入既有哨兵，要么补一条。经由本模块返回的其他失败不在此列——handler 与中间件的失败由它们自己定义，本模块不为它们发明名字。

每一类启动期失败给出修复动作：端名未声明时点名可用的端，路由冲突时点名冲突的两条路由（方法与路径）与它们所在的端，约束成环时点名环上各成员并给出它们各自的声明，文档形状不合法时点名声明它的模块与不合法之处，绑定失败时带上地址与底层原因。

**冲突报错不点名登记者**：登记面不知道调用它的是谁，这一点与中间件的 `Provides` 同源。方法与路径本身是代码里写死的字符串，足以定位到登记它们的地方。

**TLS 证书装载失败并入监听端绑定失败**，不另设哨兵。判据是宿主的补救动作：证书路径写错与地址被占用，补救都是改配置重启，而具体原因由错误文本承载。

**`Handler` 为 `nil` 在登记时 panic**，`Route` 没有 handler 或其中有 `nil` 同样。gin 接受 `nil` 的 handler，要到请求到来时才崩，那时崩在请求路径上，已经没有启动失败这条路。

**运行期的失败由本模块自己定义行为**，启动期不降级这条规则到此为止。

- **接受循环异常退出**：记入日志，该端此后不再接受请求，`Accepting` 随之返回 `false`。绑定已在 `Serve` 的同步部分成功，此后的退出不再有终止启动这条路；`Run` 此刻阻塞等待宿主取消，本模块没有唤醒它的途径（[ADR-lifecycle-stages-2026-09-13](../../adr/adr-lifecycle-stages-2026-09-13.md)）。本模块不判定这是否构成不健康，那归读取 `Accepting` 的一方。**接受的代价**：进程活着但该端不再接受请求，察觉它要靠有人去读这个状态，而不是靠进程退出。
- **排空时限到期**：仍在途的请求被切断，失败在 `Stop` 阶段以 `ErrDrainTimeout` 报出。
- **错误响应的写出**：响应已经开始流出去时，`Fail` 不写入，只中止其后的 handler，已提交的状态码与响应体不被改写。
- **各登记层与 handler 的 panic**：兜底层接住它并记一行日志，该请求随后结束，同一进程的其余连接照常服务。响应那一侧分两档：handler 尚未写出任何输出时，经错误响应的接缝写出一次 500；头部已经提交之后再 panic 时状态码无法改写，该请求以已提交的形状结束，日志照写。

## 并发与事务边界

登记面在借用自 `Migrate` 与 `Start` 的阶段窗口内接受写入，`Serve` 之后只读。窗口以本模块的 `Migrate` 回调为起点、`Start` 回调为终点，全局 `Init` 阶段整体落在其中。写入侧有互斥保护：各阶段按依赖序逐个模块驱动，但登记方可以在自己的回调里起协程，本模块不假设写入来自单一协程。

组装好的链此后结构不变，可被多协程并发调用。每个请求的上下文各自派生，链上各层绑定的属性落在派生出的上下文里，不共享。

监听端的可变状态是它的监听与排空：绑定由 `Serve` 写入，关闭由 `Stop` 写入，排空结果由后台协程写入并经一个通道通知等待它的 `Stop`。`Accepting` 读的正是这份状态，调用可能来自任何协程、任何时刻，它与各写入点之间因而要有同步。`Stop` 可能在从未监听过的实例上被调用，也可能被重复调用，两者都不产生失败。

本模块不为 handler 与中间件的调用加锁，也不保证它们的调用来自单一协程：每个请求各占一个协程，这是 `net/http` 的形态。

gin 的 `*gin.Context` 只在它所属那次请求的处理期间有效：handler 把它交给自己另起的协程时要先 `Copy`。

## 扩展点

**错误响应的形状**经可选接缝接入：交付 `ErrorResponder` 的模块整体替换默认形状，不需要修改本模块（[ADR-http-errors-2026-10-10](../../adr/adr-http-errors-2026-10-10.md)）。

**中间件**由各模块自己贡献，经登记面接入。新增一种横切机制不修改本模块：它声明自己相对哪些功能的位置，本模块按声明排序而不认识它做什么。**本模块自带的兜底层是这条的一个例外**：它是内建行为，不是一次登记——它不加 `Endpoint` 的方法，不加配置键，也不出现在任何一层的位置声明里（[ADR-http-recovery-2026-09-22](../../adr/adr-http-recovery-2026-09-22.md)）。
