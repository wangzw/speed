# 通知

## 问题陈述

收件人需要在一个地方读到系统发给自己的消息、知道有多少条未读、按消息类型决定它走站内信、邮件还是短信，并在页面打开时尽快看到新消息。派发消息的业务模块需要一条不丢消息、不重复发送的投递承诺。本能力把这些行为固定为可从外部判定的要求。

## 范围

站内信收件箱的列出、分组过滤、分页、未读计数、单条与全部标记已读；按类型的渠道偏好矩阵与通知类型清单；派发按收件人的生效渠道集选择渠道；站内信的实时推送及其断线与重连表现；出站投递的至少一次承诺、按渠道的重试与跳过；收件人可见的空态、失败态与写入反馈。

### 不在范围内

- 非用户外部联系人的联系方式验证、按类型退订与平台级黑名单（同意台账）。
- 不属于任何租户的平台级广播。
- 同类消息的聚合与按收件人的发送限频；发送上限由宿主另行施加。
- 通知正文与文案的撰写；文案归声明该类型的业务模块。

## 参与者

- **收件人账户**：已登录的租户用户。以自己的身份读取本人收件箱、未读计数与渠道偏好，并维持一条实时连接。冒充期间以被冒充账户为生效身份。
- **通知派发方**：声明通知类型的业务模块。声明内容包括分组、默认渠道、是否可退订与收件人可见参数白名单；在业务事件发生时提交一次派发。
- **宿主**：装配本次部署，决定具备哪些渠道能力，对通知路由施加访问判定，并在分布式部署里保证各实例装配同样的渠道能力。

## 功能需求

### REQ-notifications-001

系统必须向收件人列出本人作为收件人的站内信，每行包含类型、分组、标题、正文、消息携带的参数、链接、接收时间与已读时刻。

- **验收**：账户甲请求列表，只看到收件人为甲的消息；每条可见行带齐类型、分组、标题、正文、参数、链接、接收时间与已读时刻，未读行的已读时刻为空；账户乙的消息不出现。
- **状态**：已实现
- **端到端测试**：`starters/demo/web/e2e/specs/journey-member-organization.spec.ts` `member-organization: a member receives, reads and configures notifications`

### REQ-notifications-013

系统必须在一条站内信的写入落在收件人实时连接所属的实例上时，向该连接推送一条提示；收件人无需手动刷新即可看到该消息。收件人是请求身份的生效账户，冒充期间为被冒充账户。写入落在其他实例时不承诺推送提示，该情形由 REQ-notifications-015 覆盖。

- **验收**：账户甲连上实时连接，从写入到判定之间不发起任何收件箱列表读取；业务在甲连接所属的实例上为甲写入一条站内信，甲的连接收到该消息的提示，随后读取列表时该消息出现且未读计数增加。账户乙在同一次派发期间同样不发起列表读取，其连接不收到提示；冒充期间该次派发只到达被冒充账户的连接。「不收到」一律以提示帧判定，不以列表内容代替；只靠轮询列表才看到该消息、连接上没有提示帧的判为不通过。
- **状态**：已实现
- **端到端测试**：未实现

### REQ-notifications-014

- **验收**：收到提示后解析其内容，其中只有消息标识与它所属的租户、收件人与类型；提示中没有正文或参数。
- **状态**：已实现
- **端到端测试**：未实现

### REQ-notifications-015

- **验收**：断开实时连接期间为收件人写入一条消息，重新连接并重新读取列表后可见；分布式部署里把同一条消息交由另一实例写入，本实例的连接没有收到提示，但重新读取列表后可见。
- **状态**：已实现
- **端到端测试**：未实现

### REQ-notifications-016

- **验收**：令连接连续断开，观察等待间隔依次增长，达到 30 秒后不再增长；在等待期间收到一条提示，随后的断开从 1 秒重新开始计时。

### REQ-notifications-019

### REQ-notifications-025

系统在读取收件箱或偏好失败时，必须把一般读取失败与准入拒绝分开呈现：一般失败呈现可重试的错误占位；准入拒绝呈现不可重试的「无法访问当前组织」空态，并说明该组织可能不存在、或请求者不是其成员。

- **验收**：令读取返回一般错误，界面出现可重试的错误占位，点击重试触发再次读取；令读取得到准入拒绝（不区分租户不存在、已停用与非成员），界面出现「无法访问当前组织」的空态且没有重试动作。
- **状态**：已实现
