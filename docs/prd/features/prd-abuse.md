# 防滥用

## 问题陈述

平台会代表请求方向第三方邮箱与手机号发送验证消息，也会按业务要求投递邮件与短信。发送量没有约束时，攻击者可以让平台对任意邮箱或手机号反复发信：受害者收到大量并非自己请求的消息，平台的发信通道、号码与发信声誉被消耗，平台本身成为攻击的发起者。本能力规定平台在这些出站消息上的约束。

## 范围

本能力覆盖所有由请求方触发、收件人由请求方指定的出站消息：登录与注册流程中的验证短信、账户自助中验证邮箱与手机号的邮件与短信、匿名口令重置的验证邮件与短信、以及业务通知的邮件与短信投递。它规定预算的层级、预算在并发下的一致性、按来源的约束、同一收件箱的别名归并、发送失败与预算耗尽时的可见结果，以及按发送面缺省开启、部署可按面关闭或更换机制的人机验证门槛。

### 不在范围内

- 站内信的列出、未读计数与偏好矩阵，归通知能力；本能力只规定其邮件与短信投递侧的预算。
- 管理面写入是否需要重新验证，归账户安全能力。
- 邮件与短信载体的选择、模板与注册，归相应的发送能力。

## 参与者

- **请求方**：触发一次发送的人。匿名访客在登录与注册流程中发码，已登录账户在自助验证中发码，业务模块按事件派发通知。
- **收件人**：接收消息的地址或号码的持有人。收件人没有请求该消息时，就是被攻击的一方。
- **平台运营者**：按发送面决定人机验证的机制或是否关闭，并调整各项预算的人。

## 功能需求

### REQ-abuse-001

系统必须对验证消息按目标地址或号码、按账户（请求方已认证时）与全局分别计数，并在任一预算用尽时拒绝继续发送。

- **验收**：对同一目标连续请求直到预算用尽，后续请求不发送消息并得到可重试的拒绝；换一个目标仍在预算内时可以发送；全局预算用尽时任何请求都不再发送。
- **状态**：已实现
- **端到端测试**：未实现

### REQ-abuse-002

并发请求不得越过本能力规定的任何一层预算。

- **验收**：对同一目标并发发起多于预算数量的请求，实际发出的消息数不超过预算；按账户与全局两层同样成立。
- **状态**：已实现
- **端到端测试**：未实现

### REQ-abuse-003

系统必须按请求来源对验证消息计数，覆盖每小时与每天的发送数、每小时与每天的不同目标数，以及每小时确定失败的次数，且不区分用途；没有可信来源的请求跳过这一层，其余各层预算照常适用。

- **验收**：同一来源对多个不同目标各请求一次，超过来源预算后不再发送；同一来源轮换目标仍受不同目标数预算约束；同一来源反复触发确定失败时受失败次数预算约束；该来源被拒绝时，其他来源仍可在预算内发送；请求没有可信来源时，来源层不计数，但其它预算照常可以拒绝它。
- **状态**：已实现
- **端到端测试**：未实现

### REQ-abuse-004

同一收件箱的不同地址写法必须共用同一份按目标预算。

- **验收**：对同一收件箱的加号别名与大小写不同的写法分别请求，累计超过预算后不再发送。
- **状态**：已实现
- **端到端测试**：未实现

### REQ-abuse-005

一次确定没有发出的验证邮件不得消耗发送预算；结果不确定的发送仍计入预算。

- **验收**：让一次邮件发送以确定失败（被拒绝或被限流）后重试，成功发送的次数仍可达到预算上限；一次结果不确定的发送照常占用预算。
- **状态**：已实现
- **端到端测试**：未实现

### REQ-abuse-006

预算用尽时，系统必须给出可重试的拒绝并标明建议的重试时间，不得报告服务不可用。

- **验收**：耗尽任一预算后，后续请求的应答带重试提示，且与发送后端故障的应答可区分。
- **状态**：已实现
- **端到端测试**：未实现

### REQ-abuse-007

系统必须按发送面提供人机验证，且默认开启：手机号面（短信登录、短信第二因素、手机登记、匿名短信重置）默认使用自托管的人机验证码，该验证码在图片与滑块拼图之间由服务端轮换，客户端不能指定这两种视觉形式，只能请求作为屏幕阅读器无障碍替代的音频形式，且音频形式的按来源签发上界比图片与滑块的轮换更严；其余面（匿名口令重置的邮箱分支、自助添加邮箱）默认使用自托管的工作量证明。部署可以显式关闭任一面，也可以把任一面换用外部机制（目前为 Turnstile，[REF-cloudflare-turnstile](../../references.md)）；选择外部机制而缺少其凭据时，启动失败，不得静默降级。

- **验收**：默认装配下，两个面都要求一份一次性的证明，证明由进程本身校验，不依赖第三方凭据；手机号面的自托管人机验证码在图片与滑块之间由服务端轮换，客户端只能请求音频形式，不能选择图片或滑块；同一来源达到音频形式的签发上限时，只有音频请求被可重试地拒绝，视觉挑战不受影响；删去某一面的模式键后，该面仍按其默认机制要求证明；显式关闭某一面后，只有该面不再要求证明，另一个面照常要求；选择 Turnstile 而缺少站点键、密钥、主机名或控件 action 时，启动失败并指出缺少的项。
- **状态**：已实现
- **端到端测试**：未实现

### REQ-abuse-008

某一发送面的闸开启时，该面上每一条发送验证消息的请求都必须先提交一份有效、只能使用一次的证明。手机号面的证明来自自托管的人机验证码：挑战形式由服务端在数字图片与可键盘操作的滑块拼图之间轮换，客户端不能指定这两种视觉形式，只能请求作为屏幕阅读器无障碍替代的音频挑战，且音频形式的按来源签发上界比图片与滑块的轮换更严；证明也可以来自显式选定的外部机制（目前为 Turnstile）。其余面的证明来自自托管的工作量证明，也可以来自显式选定的外部机制（目前为 Turnstile）。

- **验收**：逐个入口（短信登录、短信第二因素、手机登记、匿名短信重置、匿名口令重置的邮箱分支、自助添加邮箱）开启所属面的闸：提交缺少、无效、过期或重放的证明时都不发送消息，有效的一次性证明正常发送；服务端轮换到图片与滑块时都能完成一次发送，客户端请求音频时同样能完成一次发送，且一次性与有效期的语义相同；客户端不能选择图片或滑块；同一来源达到音频形式的签发上限时，只有音频请求被可重试地拒绝，视觉挑战不受影响。
- **状态**：已实现
- **端到端测试**：未实现

### REQ-abuse-009

业务通知的邮件与短信投递都必须受预算约束：短信与验证短信共用同一份台账与部署的跨渠道小时上界，邮件用自己的键值计数器计数、不占用短信台账；投递携带的收件地址必须属于该消息的收件人。

- **验收**：对同一收件人高频派发超过预算后不再投递；同一租户在一小时内向过多不同收件人派发时被拒绝；派发携带的收件地址不属于该收件人时，该次投递被拒绝；部署的跨渠道小时上界用尽时，同一小时内的验证短信也被拒绝。
- **状态**：已实现
- **端到端测试**：未实现

### REQ-abuse-010

一次确定没有发出的验证短信必须退还发送预算并使该验证码失效；一次确定失败的尝试仍计一次尝试预算；结果不确定的发送保留发送预算。

- **验收**：让一次短信发送以确定失败后重试，成功发送的次数仍可达到预算上限，且此前发出的验证码不再可用；该次确定失败仍消耗一次尝试预算；一次结果不确定的发送照常占用发送预算。
- **状态**：已实现
- **端到端测试**：未实现

### REQ-abuse-011

系统必须把匿名口令重置的验证消息纳入与其它验证消息相同的发送约束：按目标地址或号码、按来源与全局预算；短信分支把人机验证证明随发送带入发送入口，由该入口校验并消费；邮箱分支由重置路由校验并消费人机验证证明；对不合格的目标不投递消息。

- **验收**：连续向同一地址或号码请求重置直到预算用尽，后续请求不发送消息；部署开启人机验证时，短信分支把证明带入发送入口，由该入口校验并消费，缺少或无效证明的发送被拒绝；邮箱分支由重置路由校验并消费证明，缺少或无效证明的重置请求不发送；向不存在或未证明的地址或号码请求重置时不投递消息，可见应答与合格目标相同；被抑制的请求仍计入按目标与按来源的预算，全局预算只计真实发送。
- **状态**：已实现
- **端到端测试**：`starters/demo/web/e2e/specs/journey-password-reset-email.spec.ts` `password-reset-email: an addressed code resets the password and ends the old sessions`；`starters/demo/web/e2e/specs/journey-password-reset-sms.spec.ts` `password-reset-sms: a phone-code reset writes a new password and ends the old sessions`

### REQ-abuse-012

系统必须为发送尝试单独计数，与发送预算分开：认证侧的尝试预算只计确定失败的尝试，通知侧的尝试预算计每一次尝试。

- **验收**：一次确定失败的验证短信消耗一次认证尝试预算，发送成功的短信不消耗；通知侧每投递一次就消耗一次尝试预算；尝试预算用尽后拒绝新的尝试，即使发送预算仍有余额。
- **状态**：已实现
- **端到端测试**：未实现

### REQ-abuse-013

部署必须有一道跨渠道的小时上界，由两个短信发送渠道共用；它只计未退款且未被抑制的尝试，并在其它每一道短信预算之前先被检查。

- **验收**：一个渠道在一小时内用尽上界后，另一个渠道在同一小时内的短信发送也被拒绝；被退款或被抑制的尝试不占用上界；对一次发送，上界的判定先于按目标、按来源、按用途与尝试预算的判定。
- **状态**：已实现
- **端到端测试**：未实现

## 约束

- 开放匿名注册或放行可发送的短信号段之前，部署必须先具备 REQ-abuse-002 与 REQ-abuse-003 的预算。这两项未实现时，匿名者可以批量取得账户并轮换目标，平台可被用作轰炸的发起者。

### REQ-abuse-014

系统必须限制一个账户同时持有的活跃业务组织数量；达到上界时，新的自助创建被拒绝，且不建立组织。

- **验收**：一个账户持有的活跃业务组织达到上界后，再次自助创建得到冲突拒绝，名册不新增租户；该账户的个人租户、已停用的业务组织与已停用的成员关系不计入上界；平台运营者通过运行时设置调低上界后，同一账户的下一次创建按新上界拒绝。
- **状态**：已实现
- **端到端测试**：未实现

### REQ-abuse-015

系统必须限制一个账户每小时的自助创建次数；计数在通过全部前置校验后、建立组织之前发生，建立失败也消耗一次。

- **验收**：一个账户在一小时内达到次数上界后，再次创建得到可重试的拒绝并带有建议的重试时间；形状、资格、上界、锁与限流的前置拒绝不消耗次数；建立过程失败消耗一次；下一个小时开始新的窗口。
- **状态**：已实现
- **端到端测试**：未实现

### REQ-abuse-016

同一账户的并发自助创建请求必须串行：至多一个请求进入建立，其余请求得到“创建进行中”的拒绝。

- **验收**：对一个账户并发发起多于一个创建请求，只有一个请求建立组织，其余得到“创建进行中”的冲突拒绝；建立完成后，同一账户的新请求可以再次创建。
- **状态**：已实现
- **端到端测试**：未实现

### REQ-abuse-017

每一次进入建立的自助创建尝试必须留下审计记录；建立失败时补一条与成功行关联的失败记录，但被名册以标识或别名冲突拒绝的除外——那一次请求的强制行已经落下。

- **验收**：一次成功的创建在审计中留下一条记录，点明账户、组织与创建动作；一次因故障而失败的创建留下两条记录，结果分别为成功与失败，两条由同一个动作标识关联；被名册以标识或别名冲突拒绝的创建只留下那一条强制记录，不再补失败行；在前置校验处被拒绝的请求不留下审计记录。
- **状态**：已实现
- **端到端测试**：未实现
