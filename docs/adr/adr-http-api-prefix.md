# 全部 HTTP API 路径收进 `/api/v1` 命名空间

## 背景

模块的路由挂在各自的顶层命名空间下：认证与账户面在 `/auth`、授权管理面在 `/authz`、租户、设置、短信与审计管理面在 `/tenant`、`/settings`、`/sms`、`/audit`，特性文档在 `/features`，个人租户入口在 `/workspace`；通知则挂在 `/api/v1/notifications`。两类路径都符合端点的认领表，但对外契约 `contracts/api.json` 的根路径不统一：调用方要为每项能力分别记住它是否有前缀，生成的客户端也只能照抄两种形状。

`v1` 段没有版本策略支撑。平台不对路径版本化作任何承诺，也没有第二版的路由或迁移规则；带 `v1` 的路径因此读起来像一项不存在的保证，而不带的路径又不带这一段相同的含义。

路由路径是宿主可见面，外部系统按路径登记：企业 IdP 的回调地址、SAML 服务提供方元数据地址与 JWKS 地址都以路由路径拼出，改动它们要求部署方同步更新外部登记。

## 考虑过的选项

### 保持两种根路径，并在设计文档里写成文约定

对外契约维持现状，文档写明业务资源在 `/api/v1` 下、平台能力在顶层命名空间。

**否决**：调用方仍需按能力区分两类根路径，生成物与文档的示例因此保留两种形状；`v1` 在没有版本策略时仍被读成一项承诺。

### 业务资源留在 `/api` 下，去掉 `v1` 段

把 `/api/v1/notifications` 改为 `/api/notifications`。

**否决**：只修掉一段。`/api/...` 与 `/auth/...` 仍是两种根路径，契约的不统一没有消除。

### 全部收进 `/api/v1`

每项能力的路由改为 `/api/v1/<能力>/...`。业务端点认领 `/api`，账户端与管理端点在同一监听上按 `/api/v1/<能力>` 认领各自的子树，最长的认领胜出。

**采纳**，见「决策」。

## 决策

采纳：**模块挂载的每条 HTTP API 路径以 `/api/v1/<能力>` 为根。** ops 探针（`/health`、`/ready` 与 `/openapi.json`）留在 `ops` 监听的根上：它们是进程探针与 API 文档读取，不是对资源的操作。

## 后果

- 生成的契约、各模块的内嵌 OpenAPI 片段、宿主的端点认领表与前端开发代理清单都按同一套根路径书写。
- 认证挂载基路径的缺省值改为 `/api/v1/auth`；显式配置了 `authn.gate.mount.base-path` 的宿主保留自己的取值。
- 前端页面路径不受影响：页面表全部落在 `web` 端点的 `/` 兜底认领之下，与 `/api` 命名空间不相交。

**付出的代价：**

- 这是一次破坏性的宿主可见变更。已部署的客户端、企业 IdP 的回调地址、SAML 元数据地址与 JWKS 地址都要同步更新，更新之前这些流程在旧地址上失败。
- 账户端与管理端点从顶层命名空间改为 `/api/v1` 下的子树认领，端点认领表比按顶层段书写时更长，认领写漏会在启动时以 `ErrUnclaimedRoute` 失败。

## 失效条件

路径版本化若成为平台的真实承诺——出现第二版路由、迁移窗口或兼容层——`v1` 段就承载了本记录否认的含义，本决定需要重新裁定，重新定义版本段的语义。ops 探针若被要求挂在 API 命名空间之下，本记录对它们的例外同样需要重审。
