# Twilio 载体绑定官方 SDK，不自写 HTTP 客户端

## 状态

已接受

## 背景

Twilio 载体的发送走 Messages API，模板管理走 Content API：前者按内容 SID 与变量发送一条消息，后者把一条正文登记成内容资源、返回 SID，并在删除时释放它。两个 API 都以 HTTP Basic 认证（账户 SID 与认证令牌），错误以 HTTP 状态码加 Twilio 自己的错误码表达。

Content API 相对较新，它的资源形状（内容类型、语言、变量、审核）独立于 Messages API 演进。手写客户端意味着同时维护两套请求与响应结构、认证、分页、错误解码，并在 Twilio 改动任一处时跟着改。本能力已经把厂商 SDK 限制在载体叶子包内，根包与注册表不 import 任何 SDK，依赖闭包由 `deps_test.go` 守住；把官方 SDK 放进 Twilio 叶子包与这条封边一致。

约束如下：

- 载体不重试，SDK 的默认重试必须被关掉；一次 `Send` 对应一次厂商调用。
- 厂商类型不得越过载体的 `Open`，注册表与调用方只看到本能力的类型。
- 一个宿主不选 Twilio 时，仍然在 `pkg` 模块的依赖清单里背负这个 SDK；这是所有载体叶子包共有的代价，只能靠钉版与替换叶子包控制。

## 考虑过的选项

### 用 `net/http` 手写 Messages API 与 Content API 客户端

只依赖标准库，自己构造请求、解析响应、映射错误。

**否决**：要维护两套独立的资源结构，Content API 的形状还在演进，手写实现没有编译期契约，字段改名只能靠集成测试发现。认证、错误解码与分页都要重写一遍，而它们不是本能力要解决的问题。测试也只能按手抄的结构断言，等于把同一份维护成本再写一遍。

### 采用社区维护的 Twilio 客户端

使用第三方封装，避开官方 SDK 的依赖。

**否决**：社区客户端的维护频率与 API 覆盖都不如官方，Content API 这类较新的接口往往滞后；出问题时无法要求上游修复，最终仍要回到手写或官方 SDK。它没有带来比官方 SDK 更小的依赖，只带来了更小的确定性。

### 绑定官方 SDK `github.com/twilio/twilio-go`

用 `rest/api/v2010` 发送、`rest/content/v1` 创建与删除内容资源。

**采纳**，见决策。

## 决策

采纳：**Twilio 载体绑定官方 SDK `github.com/twilio/twilio-go`，只在其 `pkg/sms/twilio` 叶子包内 import。**

- **两个子包对应两个 API。** 发送用 `rest/api/v2010`，内容资源的创建与删除用 `rest/content/v1`。
- **SDK 被包在 `Product` 后面。** 厂商类型只出现在 `Open` 与载体内部，不越过接缝；注册表、管理面与调用方只看到 `sms` 包的类型。
- **关掉 SDK 的默认重试。** 载体强制一次尝试；SDK 若默认重试，必须显式覆盖，否则违反「载体从不重试」。
- **错误按 HTTP 边界归类。** 429 归 `ErrThrottled`，同步 4xx 归 `ErrRejected`，5xx、超时与网络错误归 `ErrUncertain`；没有已核实的错误码归入 `ErrUnroutable`。
- **依赖封边不变。** 根包与注册表不 import 该 SDK；`pkg/sms/deps_test.go` 把根包的传递闭包守在不含任何厂商 SDK 的一侧，并在 `pkg/go.mod` 里精确钉版。

## 后果

Twilio 的两套 API 由上游维护，载体只写映射与归类；Content API 的响应结构随 SDK 更新，不必在本仓库里同步。

**接受的代价：**

- **依赖进入每个宿主的 `go.sum`。** `twilio-go` 及其传递依赖随 `pkg` 模块解析，一个不选 Twilio 的宿主也背负它们。钉版与撤掉叶子包是回退手段；这与其余载体 SDK 的代价相同。
- **升级节奏由上游决定。** Content API 变更时，要等 SDK 发布对应版本；载体只能在一个版本内使用 SDK 已暴露的能力，未覆盖的接口在升级前不可用。
- **SDK 的默认行为需要逐项检查。** 重试、超时与错误包装的默认值可能与本能力的契约相反，载体必须在 `Open` 里显式设定；漏掉一处，例如默认重试，就会直接违反「载体从不重试」。
- **测试经过真实 SDK。** 适配层测试用回环 `httptest` 端点驱动 `Send` 与内容创建，断言请求形状与错误归类；没有真实凭据，SDK 的行为只能按它发出的请求与它解析的响应来验证。
- **一个 SDK 的依赖冲突可能波及工作区。** 若它的某个传递依赖与工作区其它模块冲突（阿里云 SDK 的 `genproto` 单体曾经如此），要用 `go.work` 的 `replace` 钉版或换用替代方案；这属于依赖管理成本，不是载体逻辑的成本。

## 失效条件

- 官方 SDK 停止维护，或长期不覆盖 Content API 的某个必要接口，使载体无法表达设计所需的行为。
- SDK 的依赖闭包与工作区其余模块发生无法用 `replace` 解决的冲突，且官方没有修复路径。此时应改用手写客户端或换一个可维护的封装。
