# 中间件的定位由固定的一组阶段给出，阶段内以约束与三值 Position 取舍

## 状态

已接受

## 背景

中间件由彼此独立的模块贡献，各自在链上占一层；层与层的先后影响正确性。入口模块不认识任何具体功能，新增一种横切机制不修改入口模块；登记面不带登记方身份，一层代表哪个功能只能由那一层自己说（[ADR-http-middleware-2026-09-14](adr-http-middleware-2026-09-14.md)）。

现行模型由三部分构成：层以 `Provides` 声明自己在链上代表哪些功能；另一层的 `After` 与 `Before` 指向这些功能作为硬约束；一个全局整数 `Order` 在约束留下的自由度内决定先后。

这套模型表达不了下面这些定位诉求，而它们正是中间件定位真正要用的：

- **对开放集合的全称约束。** “观测层在所有会拒绝请求的层之外”要求点名每一个会拒绝的层，可宿主的层和以后新增的模块事先点不了名。观测层现在靠一个很小的负值落在最外层，宿主写一个更小的值就把它挤到里面，且不产生任何信号。
- **框架内建层没有落点。** 兜底、请求体上限、访问日志要落在“观测之内、拒绝之外”，也就是模块层之间的位置。用边表达，要么入口模块点名具体能力（与“不认识任何功能”相悖），要么每个会拒绝的模块都记得写一条指向兜底的约束；漏写就静默落到错误的位置，默认值不安全。
- **丢边破坏传递性。** A 在 B 之内、B 在 C 之内，而 B 不在场时，A 与 C 之间就没有约束，改由数值决定，可能反过来。各层因此只能把所有锚点写全，注释里还专门解释数值的陷阱。
- **锚点按类型身份认，造成 import 耦合。** 写一条指向某能力的约束就得 import 那个包；反过来，要让观测层声明位于所有人之外，底层的观测模块就得 import 上层的全部模块。

`Order` 是一根没有语义的全局数轴：它的取值由各模块互相看着对方定下来，等于用另一种形式回到全局协调。按约束图排序的算法等价于在“就绪集合”里按优先级选取，而“我属于哪一类”这件事被隐含在取值里。

其他产品对中间件定位的做法：

| 产品 | 机制 | 数字与阶段的关系 |
|---|---|---|
| Spring Security | 框架给内建过滤器分配序号；自定义过滤器只写相对某个锚点的 `addFilterBefore`、`addFilterAfter`、`addFilterAt` | 数字由框架分配，使用者不写数字，只写锚点 |
| Micronaut | 命名的阶段（`ServerFilterPhase`），每个阶段带前后两个序号 | 阶段是槽位；数字只是阶段的编码，因为 Java 的 `Ordered` 只认一个整数 |
| Spring Boot | 整数加公开常量划分区段 | 数字就是全部依据，再由公开常量补上区段的含义 |
| Kong | 插件分阶段运行，插件自带静态优先级 | 阶段在先，优先级在阶段内比较；相对约束是后来补上的，且只作用于一个阶段 |

保留数字的产品，其数字要么由框架分配，要么只是阶段的编码，要么由一张公开的表做全局协调。speed 的 `Order` 不属于任何一种：数字由各模块自己挑，“我属于哪一类”被隐含在取值里，而数值又从属于约束图、不提供任何保证。

## 考虑过的选项

### 保留 Order，不引入阶段

维持现状：约束图加一个全局整数偏好。

**否决**：上面那些诉求一类都表达不了。最外层那一档尤其关系到正确性——宿主写一个更小的数就把观测层挤到会拒绝的层之内，而挤错时不产生任何信号。

### 只用名称或数值优先级排序，不引入阶段

去掉约束图，链按一列优先级整数（或一列名字）排列。

**否决**：与 [ADR-http-middleware-2026-09-14](adr-http-middleware-2026-09-14.md) 否决“只用数值优先级”和“只用功能标识声明的约束”同因。数值的含义来自全局协调，模块无从知道别人取了什么值；名字排序对“与任何具体功能都无关的位置诉求”没有可写的东西。跨类别的先后由谁决定仍然悬空。

### 阶段集合开放，模块可新增阶段

阶段作为可扩展的枚举，模块可以声明新的一类。

**否决**：开放的类别又回到“对开放集合的全称约束”那一类问题——框架无法为它没见过的类别规定先后。管线的通用类别多年不变，新增一类属于修改入口模块并另写记录，代价小。

### 用固定的一组阶段定位，阶段内以约束与三值 Position 取舍

框架定义一组命名的阶段并规定其先后；层声明自己属于哪个阶段，阶段之间的先后由框架决定；阶段之内 `After` 与 `Before` 是硬约束，`Position` 只在该阶段内取舍。

**采纳** —— 见决策。

## 决策

采纳：链的跨类别先后由一组固定的阶段给出，层的偏好用三值 `Position` 表达，`Order` 删除。

阶段是 HTTP 管线的通用类别，不是某个具体能力：观测、防护、鉴别、限流、记录、授权，按此顺序由外到内运行。它们固定在入口模块里，模块只声明自己属于哪一个，不能新增。`Stage` 是必填项，零值与未定义值在登记时 panic，不给默认值——漏填而落到某个默认阶段，等于让一层在没人选择的类别里运行。

阶段之间的先后由框架决定，因此一条跨阶段的 `After` 或 `Before` 是冗余的：与阶段顺序同向时它已被满足、不建边，记 Debug；反向时启动失败，返回 `ErrStageConflict`，点名两层的层名、阶段与这条约束。`After` 与 `Before` 只在同一阶段内建边，阶段内的图照旧做拓扑排序，成环返回 `ErrMiddlewareCycle`。不同阶段的边可以删掉，方向反了则不会静默降级。

`Position` 取 `PositionDefault`、`PositionFirst`、`PositionLast`。它不是一个整数，因为阶段之内剩下的诉求只有“排在本阶段的边缘”一种——CORS 要排在来源限流之外，429 才带得上 CORS 头——一个方向性的取值就够；整数偏好会把全局数轴原样搬进阶段，重新要求跨模块协调。`Position` 只在就绪集合里取舍，让位于阶段内的约束；两层声明同一边缘时由登记先后决定，并记一条 Info 诊断。结果确定：`(Position, 登记先后)` 是阶段内的全序，而登记先后由 `Init` 的依赖序线性化给出。

内建层不经登记面，也不出现在任何约束里：它们在组装时挂在各阶段之间，访问日志在观测阶段之外，兜底在观测之内、防护之外，请求体上限在防护之内、其下各阶段之外。这属于入口模块的实现，见 [ADR-http-recovery-2026-09-22](adr-http-recovery-2026-09-22.md)、[ADR-http-body-limit-2026-10-11](adr-http-body-limit-2026-10-11.md) 与 [ADR-http-access-log-2026-10-11](adr-http-access-log-2026-10-11.md)。

本记录取代 [ADR-http-middleware-2026-09-14](adr-http-middleware-2026-09-14.md)：那个记录的两条判据里，"层的先后由指向功能标识的硬约束决定"仍成立，只是被收进阶段之内；"数值只在约束未定之处起作用"被 `Position` 取代，数值本身连同那条全局数轴一并去掉。

## 后果

跨类别的定位不再需要 import 对方的包：一条跨阶段的边一律可以删除，方向反了则启动失败，老代码迁移时不会静默错位。阶段内的约束只剩下真正“我读你写入的东西”的那几条。

与具体功能无关的位置诉求由 `Position` 承担，声明它的层不必点名任何人。

组装结果是确定的、可读的：启动时逐端写出一条 `chain=` 行，标出阶段与各层声明的功能。

**接受的代价：**

- **阶段集合封闭。** 新增一类（例如请求解压或响应压缩）需要修改入口模块并另写一条记录。代价是这类需求被挡在门外，换来的是类别之间的先后始终由框架给出。
- **`Position` 仍是偏好，不是保证。** 两层声明同一边缘时，先后由登记先后决定，可能不是任何一方的本意；启动诊断点名这一并列，但不替它们决定。
- **与阶段顺序相反的一条跨阶段约束会让启动失败。** 迁移时旧的跨阶段边若方向与阶段相反，不会静默降级，而是报错要求改；这比静默错位好，但要求迁移方逐条核对锚点。
- **宿主不能按端覆盖顺序。** 链的先后只由阶段、阶段内约束与 `Position` 决定；真需要按端调整时，要另立机制。
- **兜底层在观测阶段之内，观测阶段自身的 panic 不由它应答。** 观测阶段的层抛出的 panic 越过兜底层抵达 `net/http`：`net/http` 关闭该连接，并经监听端配置的日志器写一条记录；调用方拿到的是连接中断，而不是一次 500。兜底层覆盖的是它之内各层与 handler 的 panic。
- **登记先后作为最终裁决，其确定性与 [ADR-http-middleware-2026-09-14](adr-http-middleware-2026-09-14.md) 相同**，来自 `Init` 的依赖序，不是入口模块对外承诺的契约。
- **同一模块在两个宿主里可能落在不同的层数上**，因为一层的最终位置取决于本次装配里有哪些别的层。

## 失效条件

本记录的前提是 HTTP 管线的通用类别很少变化。若实际装配里反复出现放不进现有阶段、又需要与现有阶段交叉排序的层，则阶段的划分过粗，需要重划或另立机制；若新的类别长期只增不改，封闭这一取舍成立。
