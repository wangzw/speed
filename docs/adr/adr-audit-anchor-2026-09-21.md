# 链上锚点用审计自己的接口类型，锚定方 import 接口包

## 状态

已接受

## 背景

入口模块的中间件排序按能力标识建图：一层用 `Provides` 声明它在链上代表什么，别的层用 `After` 或 `Before` 指向那个标识。图以接口的 `reflect.Type` 为键，匹配按类型的同一性，不按结构等价。

`pkg/http/AGENTS.md` 里的一段示例写的是另一回事：一个模块在本地声明 `type Audit interface{ audit() }`，注释说这样就不必 import 交付该功能的模块。该写法在机制上不成立——本地声明的接口与交付方的接口是两个不同的类型，`After` 约束落不到任何一层。同一份设计文档里的示例一律使用交付方限定的写法，写入方为别的模块定义接口不是本仓的做法。

## 考虑过的选项

### 锚定方在本地声明结构等价的接口

**否决**：匹配按类型同一性，本地声明的接口不指向任何一层。约束落空的表现是启动诊断里那一条「未落到任何一层的约束」，而声明方以为自己有位置保证。

### 由 `pkg/core` 承载一个公共的审计标识

**否决**：`core` 不认识任何功能，新增一种功能不修改它（架构不变量 2）。

### 审计自己的接口类型作为锚点，锚定方 import 接口包

**采纳**，见决策。

## 决策

采纳：**`(*Audit)(nil)` 是链上锚点，它与描述符里的交付标识取同一个值。** 要在链上相对审计排位的模块 import `pkg/audit` 接口包，写出 `After: []core.Token{(*audit.Audit)(nil)}`。

**这项导入的代价是该发布单元的依赖闭包。** Go 按模块解析依赖，import 接口包与 import 实现子包带来同一份构建图代价，把接口单独放在一个包里并不能免掉它。本仓的既有做法一致：一个模块为写出别人的令牌而 import 对方的接口包，就一并承担对方的闭包——租户的解析子包为锚定认证层而 import 认证的接口包即是一例。

## 后果

排序约束与交付声明共用同一个标识，取值不变。

**接受的代价：**

- **锚定方承担审计的整个依赖闭包**：数据库、GORM、事件总线、入口模块、认证、租户、日志。一个只想把自己的层排在审计之内的轻模块，为此付出一个数据库堆栈。
- **`pkg/http/AGENTS.md` 里的那段示例与本决策冲突。** 以本地声明接口的方式锚定审计，其 `After` 约束落不到任何一层，表现是启动诊断里的一行「未落到任何一层的约束」，而声明方以为自己有位置保证。

## 失效条件

若 Go 的依赖解析改为按包进行，则「锚定方承担整个发布单元的闭包」这条代价消失，接口包与实现子包的拆分也随之失去意义。
