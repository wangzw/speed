# 存在性进特性文档、取值与形状归拥有它的模块，条件特性由声明模块在 Init 中于决定该面的判定处报告

## 状态

已接受

## 背景

特性文档发布本进程服务的特性名，由装配决定，在 Start 冻结（[ADR-feature-document-2026-10-17](adr-feature-document-2026-10-17.md)）。模块之内还有许多开关与可选依赖决定用户看得见什么，它们的性质各不相同：

- 一些决定某个面是否成立。authn.login 有 `SMSCodes` 时才挂手机号自助路由；邮箱添加路由恒挂，其邮箱分支在没有 `EmailCodeSender` 时答 503。authn.admin 的会话、因素、密钥、SSO、SSO 元数据刷新、冒充记录各组路由，按对应功能是否在场挂载。notification.delivery 在构造期解析可选的 `mail.Sender`、`sms.Registry`、`sms.Sender`，一个渠道能否兑现由这些接缝决定；渠道列本身由 notification.preferences 恒挂的路由服务。
- 一些是取值集合或渲染形状，而且登录前就要用：登录方法描述符、注册开关、可登记的因素种类，由 authn 的匿名发现面 `GET /auth/methods` 发布（[ADR-authn-login-method-discovery-2026-10-16](adr-authn-login-method-discovery-2026-10-16.md)）。
- 一些只是参数（时长、上限、预算），违反时服务端逐次拒绝；一些的结果经流程应答送达——自动关联经 401 `link-required`，全局强制 MFA 经登录流程的登记步，租户级强度策略经 401 的 `WWW-Authenticate`；一些发布出去会暴露租户、IdP 或账户维度，例如 IdP 清单。

需求覆盖「模块装没装」与「模块内的配置开关」；按租户定制不在其内，但不得被堵死。

生命周期约束：注册表先按依赖序对全部模块执行 New，再从 Migrate 起逐阶段推进，一个阶段逐个模块执行。认证网关的登记窗口从 Migrate 开、到 Start 关，因而包含整个 Init 阶段，这是同类写入窗口的既有形状。

通知渠道是封闭的平台词汇；偏好按（类型，渠道）逐格存储，渠道的取值集不因宿主装配而增减（[ADR-notification-channels-2026-10-15](adr-notification-channels-2026-10-15.md)）。

## 考虑过的选项

### 全部并入一份统一文档

方法描述符、因素种类、注册开关与存在性事实合进同一份文档。

**否决**：与 `/auth/methods` 重复，正是登录发现记录所说的「两处必然漂移」；还会把匿名可读与需认证的内容混进同一份应答。

### 全部留在各模块自己的发现面

各所有者各开端点：authn 开 `GET /auth/identifiers/kinds`，通知类型端点的应答带 `channels`。

**否决**：导航与路由需要一个统一的存在性判定；前端要发多次读取，等待态成倍增加；对象存储这类模块本来没有发现面。`channels` 还要求 notification.preferences 再判一遍 notification.delivery 的可选依赖，同一条规则在 notification.preferences 与 notification.delivery 里各有一个读取点。

### 在 `feature.Spec` 里声明成立条件，由发布者求值

声明里写明条件特性依赖哪些功能，发布者在 Start 按功能是否在场求值。

**否决**：决定挂不挂的判定在模块里，条件又写在声明里，模块里的判定与声明里的条件决定同一件事；路由内分支的条件（邮箱分支取决于依赖结构里的一个字段）用功能标识表达不了。

### 逐请求求值的 `Source` 接口

条件特性由模块交付一个求值接口，发布者每次请求时调用。

**否决**：每个请求多一条错误路径；现有的条件全是 Init 期就定下的装配事实，没有需要逐请求求值的对象。按租户收窄另走独立的减法扩展，不借这个接口。

### `notification.Dispatcher` 加 `Channels()`

由投递接缝列举可兑现的渠道，偏好面据此渲染。

**否决**：Go 接口加方法属破坏性变更；notification.preferences 还要多一条对 `Dispatcher` 的可选依赖。

### 按维度分工，条件特性由声明模块在 Init 中于决定该面的判定处经 `Board.Post` 报告

**采纳**，见决策。

## 决策

采纳：**模块内开关按维度分归；条件特性由声明模块在决定该面是否成立的那一处判定里经 `feature.Board` 的 `Post` 报告，发布者在 Start 冻结。**

- **存在性**：前端已经带着代码的某个界面面（页面、区块、入口控件）是否成立；它是布尔值，只在登录后才需要。特性文档只承载这类事实，其中成立与否随装配变化的进特性文档；前端不经特性门控就直接依赖的模块，其恒挂的面不随装配变化，不立特性名。特性文档由装配决定、按进程成立、在 Start 冻结，与调用者身份无关。例：手机号自助、自助添加邮箱、邮件通知渠道、SSO 管理组。
- **取值与形状**：满足任一条即归拥有该事实的模块自己的发现面——它是取值集合或渲染形状而非布尔值；登录前就要用；需要逐请求求值而又不属于存在性。例：`/auth/methods` 的方法描述符、注册开关、因素种类。
- **不发布**：满足任一条即不进任何发现面——只是参数，违反时服务端逐次拒绝；结果经流程应答送达；发布会暴露租户、IdP 或账户维度。例：自动关联开关、手机号前缀允许集、IdP 清单。
- **同一事实只有一个发布点。** 例：可登记的因素种类只在 `/auth/methods`；特性文档里只有「MFA 区块存在」，不按因素种类分出名字。
- **条件特性的报告**：声明模块在 Init 中、在决定该面是否成立的同一处判定里调用 `feature.Board` 的 `Post`。面是路由的，在挂载该路由的分支里报告；面是路由内一个分支的，在与该分支同源的判定处报告——authn.login 的邮箱添加路由恒挂，`authn.identifiers.email` 在与邮箱分支答 503 同源的判定处报告；面由不挂路由的模块兑现的，在该模块据以决定能否兑现的判定处报告——notification.delivery 按构造期已存下的渠道接缝判定，`in_app` 恒在、不立名字。`Post` 的合法窗口从发布者的 Migrate 到它的 Start，窗口之外调用即 `panic`。Start 时，报告的名字若不是报告者声明的条件特性，启动失败。没有发布者的进程里（例如 `worker`），报告静默跳过。

## 后果

报告与决定该面的判定写在同一处，存在性不会与挂载或分支的判定漂移；集合在 Start 冻结，应答是预先算好的字节，请求期没有失败路径。存在性由一处、一次、原子地决定，取值与形状留在拥有它的模块。

**接受的代价：**

- 静态与条件的划分靠模块作者守住：一个随配置或装配而定的面若被声明为静态，发布者察觉不到，前端会显示一个不存在的面。这条约束写成架构不变量，由各模块断言「功能在场」「报告该名」「该组路由已登记」彼此一致的测试守住。
- 在 New 或 Migrate 中报告会落在窗口之外而 `panic`；按构造期解析的依赖判定的模块（notification.delivery）只能把判定所需的接缝存下，到 Init 再报告。
- 存在性按进程判定：notification.delivery 若被移到另一个进程，`serve` 进程与它的装配必须一致，渠道特性才与实际投递相符。宿主给 notification.delivery 预置实例时，它的生命周期回调不处理这个实例，渠道特性不报告，属失败即关的方向。
- 隐藏的渠道列不改变偏好的取值集，已存的偏好值不受影响；装配恢复该渠道后，原值照旧生效。
- 按进程成立的特性文档容纳不了逐请求求值的存在性事实；除按租户收窄这一类减法之外，这类事实没有落点。

## 失效条件

- 按租户收窄特性文档不构成失效：它是存在性维度上预留的减法扩展——取值放在设置的租户层，逐请求求值，只能从进程集里减，不受「按进程成立」这一限定约束。若需求变成按租户**增加**本进程未服务的面，减法扩展不再够用，本决策要重审。
- 出现必须在 Init 之后才能定下的存在性事实（例如运行期接入或摘除一个后端），「Init 中报告、Start 冻结」的机制不再成立。
- 某个面的成立条件在模块内找不到唯一的判定处（由多个模块的运行期状态共同决定），「报告与判定写在一处」不再可行，需要另立机制。
