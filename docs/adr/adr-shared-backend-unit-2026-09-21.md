# 两个实现子包共用一份第三方客户端构造

## 状态

已接受

## 背景

键值模块与事件模块各有一个 Redis 实现子包，两者都要做同一件事：读地址、口令、库序号与连接池大小，建一个客户端，并在停机时关闭它。两处代码的形状由同一个第三方客户端决定，差异只在配置项落在哪个命名空间。

旧实现把建客户端这一步推给宿主：`kv/redis` 与 `eventbus/redis` 的构造器都只收一个现成的客户端，宿主机自建后注入。新架构取消了这条路——模块之间取得产物的途径只有注册表，宿主向装配提供的声明一律经由模块机制（架构不变量 5、9）。建客户端因此推回模块自己，两个子包各写一遍。

写出的两份代码无法互相看见：跨发布单元的依赖一律指向对方的接口包，不 import 其他发布单元的实现子包。

## 考虑过的选项

### 两个实现子包各写各的

**否决**：两处的差别只有配置项的挂载路径。它们的正确性——口令为空时是否仍建池、地址不可达时是构造失败还是首次调用失败、关闭是否幂等——无法由同一套测试覆盖，一处修正不会传导到另一处，而两处的失效形态完全相同。

### 事件模块的 Redis 实现依赖键值模块的 Redis 实现子包

**否决**：违反依赖规则，实现子包不对外提供可被跨发布单元引用的面。它还会把两种功能耦合起来：键值模块调整自己的连接管理，事件模块随之改变，而两者在语义上毫无关系。

### 抽一个只封装第三方客户端的共享发布单元

把客户端类型、连接配置与构造、关闭收敛到一处，两个实现子包各自依赖它。

**采纳**，见决策。

## 决策

采纳：**两个实现子包共用一个发布单元，该发布单元封装第三方客户端，不登记模块、不交付功能、不参与生命周期。**

它的接口面是：被封装客户端的类型（原样暴露，不另造等价抽象，依据是架构不变量 11）、一个带配置标签的连接配置结构体、一个构造器与一个关闭函数。它的实现细节——重试、TLS、哨兵与集群拓扑——封在构造器内，调用方不感知。

两个实现子包**各自在自己的配置命名空间下挂载同一份连接配置结构体**，因此 `kv.redis.addr` 与 `event.redis.addr` 是两条独立的输入项路径。它们是两种不同功能各自的一个实现，路径本就不同，不触及"同一功能的互斥实现必须划分各自的输入项路径"这条判例。

**本发布单元的划分依据是被封装的后端，不是功能。** 术语表对发布单元的定义是"按功能划分"，且允许一个发布单元登记零个模块；本记录不修改那个定义，而是指出这一形态与它并存：它不承载功能，因此没有可划分的功能边界，它的边界就是那个第三方客户端。

## 后果

建客户端这件事只有一处实现，两个子包共用它，也共用它的测试。

依赖传染面不增加：引用本发布单元的只有本来就要承担那个客户端的实现子包。

`go.work` 多一个成员；发布与版本粒度多一个单元。

**接受的代价：**

- 连接配置结构体的改动同时影响使用它的键值模块与事件模块，且这条耦合边不受任何机制检查。它是有意保留的——两处配置本就该一致，不一致才是缺陷——但它意味着改一处要记得另一处。
- 本仓由此出现一个不交付功能的发布单元，"`pkg/` 下每个目录是一个发布单元，提供一种功能"这句话对它不成立，读架构文档的人会遇到一处例外。
- 只有一种功能使用某个后端时，抽它净亏：多一个发布单元、多一层间接，换来的只是"将来可能有第二个用它的模块"。本记录不预设将来是否真的出现，也不为尚未出现的后端预先建立这样的单元。

## 失效条件

若某个后端的客户端构造短到不值得共享——几行参数默认值加一次构造调用，没有 TLS、拓扑、重试可封——则抽取它的收益低于多一个发布单元的固定成本，那个后端应按各写各的处理。

若键值模块与事件模块对同一后端的连接要求出现实质分歧（例如其中一个需要专用连接池隔离），共享一份连接配置不再成立，该后端要为提出要求的那一个单独构造。
