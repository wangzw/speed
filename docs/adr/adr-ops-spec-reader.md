# ops 读取 http.Spec：取可用集、不做减法、冲突即启动失败

## 背景

`pkg/http` 的 `Spec` 是一份静态声明：一个模块把自己那份 OpenAPI（[REF-openapi](../references.md)）片段连同它描述的端名放进去，`http` 只保存、只校验结构，不让它生效。`Spec` 的文档明说合并与发布归读者，读取方用 `core.Resources[http.Spec](reg)` 取全部片段。谁来做这个读者、读哪些、撞车怎么办，`http` 留下一句话：「读取方的取材域由读取方自己裁定」（架构不变量 15）。

合并后的一份规格是运行期的产物：探针与网关按它工作，它描述的是这个二进制提供哪些 API。它可以有两种问法——这个二进制提供哪些 API，或此刻这个进程在服务哪些 API——两者取材域不同，得到的文档也不同。冲突的处理也有分歧：撞车的两份片段可以静默留一份，也可以让装配失败。这些必须在把读者落到某个模块之前定下来。

## 考虑过的选项

### 读取方取启用集，按运行发布

按「此刻这个进程在服务哪些 API」取材，只合并本次运行里被驱动的模块的片段。

**否决**：减法是给让声明生效的消费点的；合并的是一份静态事实——一组片段是不是这个二进制的一部分，比任何一次命令长寿。取启用集会让同一个二进制在两条命令下发布两份不同的规格，而声明本身没变：一个只被静态级纳入的模块，其 API 在一条命令下出现在文档里、在另一条下消失。

### 冲突静默保留一份

同一 operation 被多份片段声明时，先出现的胜出或后出现的覆盖，装配照常继续。

**否决**：发布出去的文档会描述一个不是正在服务的 API。这是唯一能把两份片段连回各自来源的地方；在这里丢掉一份，冲突就再没有一处会说出来。

### 冲突留到运行时判定

启动照常完成，首个请求触到撞车的 operation 时返回错误。

**否决**：撞车是两份静态声明之间的事实，与请求无关。`Init` 判得出就应在 `Init` 判出；留到首个请求返回 500，把一个装配缺陷伪装成一次运行故障，而它本该在启动期就挡住整个进程。

### 读取方取可用集、不做减法，冲突即启动失败

按「这个二进制提供哪些 API」取材，合并全部已登记模块的片段，撞车即启动失败。

**采纳** —— 见决策。

## 决策

采纳：`ops` 是 `http.Spec` 的读取方；合并的取材域取可用集且不做减法；撞车一律启动失败，**operation 撞车点名声明它的两个模块与各自的端，components 同名不同内容点名后一份声明它的模块与那个名字**（两份来源的名字前一份无从取得——`components` 的合并按节进行，撞上的那一份只带自己的模块名）。

## 后果

- 一个二进制发布一份与命令树无关的规格：任何一条纳入 `ops` 的命令，其 `/openapi.json` 是同一份文档，只随二进制变化。
- 撞车是一个二进制级的缺陷：只要二进制里有两份片段声明同一个 operation，任何一条纳入 `ops` 的命令都启动失败——包括本次不运行那两个模块里任何一个的命令。

**接受的代价：**

- 一个与本次运行无关的模块的片段可以与另一个模块撞车，并挡住整条命令的启动。挡住是有意的：撞车是二进制的静态事实，一条命令判得出，就没有理由让别的命令带着它跑。
- 运行时不再有按运行裁剪规格的手段；需要它时只能另写一个取启用集的读取方，而不是配置一个开关。
- `ops` 的取材域与 `http` 自己的结构校验同取可用集、同不做减法，两处判决绑在一起：把任一改成做减法，另一个仍按可用集取材，同一个二进制会在两条命令下给出不一致的启动结论。

## 失效条件

若「同一二进制在多条命令下发布不同规格」成为需求——例如一个只被静态级纳入的模块，其 API 不应出现在那条命令的文档里——取可用集的裁定不再成立，改由按运行取材的读取方承载。
