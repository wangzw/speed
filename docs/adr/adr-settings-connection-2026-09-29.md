# 设置的写入、删除与列举各经数据库模块的 Connection 取一条自己的连接，等待有界

## 状态

已接受

## 背景

`Set`、`Delete` 与 `List` 访问数据库，而读写面不收事务：本模块没有加入调用方事务的途径，每一次调用都从交付连接池里另取一条连接。写入还把事务的开启与提交放在调用方的取消之外，好让返回值与落库结果一致（见 [settings](../design/modules/design-settings.md) 的写入路径）。

数据库模块把只属于一条连接的 SQLite 定位符（内存库）交付成只开一条连接的连接池。调用方在交付句柄上开着事务时，这条连接由它占着，要到它自己的调用返回之后才放开；在这样的事务里调用 `Set`、`Delete` 或 `List`，等的是调用方自己。`database/sql` 取连接的等待只随上下文结束：上下文没有期限就一直等下去；写入的事务开启不随调用方取消，有期限也等不完。这期间这个库唯一的连接一直被占着，进程里其余每一条语句都排在它后面。走到这一步不需要反常的用法：进程内总线在发布方的协程上、带着发布方的上下文调用订阅方（[event](../design/modules/design-event.md) 的并发与事务边界），发布方在自己的事务里发布一个事件，订阅方在处理它时写一个设置，就是这种调用。

文件库上的同一次写入等的是调用方占着的写锁。SQLite 在驱动里等锁，由连接的忙等时限结束（驱动默认 5 秒，定位符可以改得更长），上下文结束打断不了这段等待。

数据库模块为替调用方发出语句的模块提供 `Connection`：在一个界内取连接，并把其上每一条语句的等锁收进同一个界，方言的设法留在实现子包里；模块自己的语句经它取连接，不各自设界（[ADR-db-waits-2026-09-29](adr-db-waits-2026-09-29.md)）。

本模块从交给它的上下文里读不出调用方持有的事务，Go 也不给出协程的身份：调用方自己的占用与别的写者的短暂占用，在它看来是同一回事。

## 考虑过的选项

### 取连接的等待只随调用方的上下文结束

写入先在调用方的取消下取连接，再在取到的连接上于取消之外开事务。

**否决**：调用方给了期限时这就够了，可没有期限的上下文仍然一直等下去，唯一的连接也一直被占着。进程内总线交给订阅方的是发布方的上下文，订阅方给不了它期限。

### 本模块自己限时取连接

本模块自己从交付连接池取连接，取连接的等待随调用方的上下文结束，也不超过一个固定的界。

**否决**：它只约束取连接；文件库上等锁那一段仍等满定位符的忙等时限，上下文结束不了它，要约束它得在本模块里按方言改写连接的忙等时限，正是数据库模块否决的由各模块自己设界（[ADR-db-waits-2026-09-29](adr-db-waits-2026-09-29.md)）。

### 读写面收调用方的事务

`Set` 另收一个 `*gorm.DB`，或从上下文里取出调用方放进去的事务，让写入与调用方的工作同进退。

**否决**：写入之后的重载与发布以「已提交」为前提。写在调用方的事务里，重载经别的连接读不到这一行，事件在提交之前发出，调用方一回滚，本副本与其余副本就会去服务一个从未落库的值。要保住这一前提，重载与发布只能等调用方提交之后再做，而这件收尾就落到了每一个调用点身上。接口签名也要改。

### 识别只开一条连接的库，调用时直接拒绝

连接池的上限为一、在用数为一时，判定调用方占着这条连接。

**否决**：在用的那一条也可能正被别的协程短暂占着，一次正常的写入会因此被拒；连接池开几条连接是数据库模块的交付细节，本模块据它判定，就依赖了一个不在契约面上的事实。

### 行为不变，只写进对宿主的要求

**否决**：漏了这条不报错，表现是整个进程无声地卡住，没有一处说出原因。进程内的订阅方正是会在发布方的事务里被调用的一方，而写这段代码的人未必知道它会在谁的事务里被调用。

### 经数据库模块的 `Connection` 取连接，界为五秒

**采纳**，见决策。

## 决策

采纳：**`Set`、`Delete` 与 `List` 各经数据库模块的 `Connection` 从交付连接池另取一条连接，不加入调用方的事务，界为五秒：取连接与这次调用每一条语句的等锁合计不超过五秒，取连接的等待还随调用方的上下文结束。** 过界即失败，这一行不改动：取不到连接的错误点明是在等连接，等不到锁的是引擎自己的错误。写入在取到的连接上开事务，事务的开启与提交仍在调用方的取消之外，它们等锁也在同一个界里。

五秒取驱动默认的忙等时限：文件库上的同一次写入不设界时等锁就等这么久；只开一条连接的库上，那条连接起的就是锁的作用，同一个引擎的两种库因而以同一种方式失败。

写入之后的重载不经这个界。它的触发方从不占着它要等的那条连接：调用方事务里的写入在重载之前已被拒绝，周期刷新不持有连接，本模块自己的变更事件在写入的连接归还之后才发布。写入先取连接，再等重载锁，因为一次在等别人连接的重载占着这把锁。

## 后果

只开一条连接的库上，在调用方的事务里写、删或列举设置，五秒内失败，进程不再卡住；文件库上等调用方占着的写锁同样在五秒内失败，不看定位符里的忙等时限。调用方的期限短于五秒时，取连接的等待随期限先结束，写入也不例外。本模块不写任何方言代码。

**接受的代价：**

- **连接池被占满、或表被锁住超过五秒时，写入、删除与列举失败。** 此前它们会一直等到有连接空出来、或等满忙等时限；现在调用方拿到一个错误，重试与否由它决定。
- **正常的调用也可能这样失败**：只开一条连接的库上，别的协程开着一个超过五秒的事务时，这次调用等不到连接。本模块分不出这种占用与调用方自己的占用。
- **写入不与调用方的事务同进退。** 调用方回滚自己的事务，撤销不了一次已经返回 `nil` 的写入；要让一个设置随一件工作一起成败，本模块做不到。
- **等待过界没有哨兵。** 取不到连接的错误包着 `context.DeadlineExceeded`，与调用方自己的期限到了是同一种判别，要分开二者，看调用方自己的上下文是否已经结束；等不到锁是引擎自己的错误，它不早于调用开始之后五秒到来。

## 失效条件

若出现必须与调用方的工作同进退的设置写入——例如开户时写下的设置必须随开户一起回滚——读写面不收事务的形态需要与这个需求重新比较。

若正常负载下取连接与等锁的时间普遍接近五秒，这个界要改成一个输入项。
