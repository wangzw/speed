# 设置的写入、删除与列举各经数据库模块的 Connection 取一条自己的连接，取连接的等待有界

## 状态

已接受

## 背景

`Set`、`Delete` 与 `List` 访问数据库，而读写面不收事务：本模块没有加入调用方事务的途径，每一次调用都从交付连接池里另取一条连接。写入还把事务的开启与提交放在调用方的取消之外，好让返回值与落库结果一致（见本模块设计文档的写入路径）。

数据库模块把只属于一条连接的 SQLite 定位符（内存库）交付成只开一条连接的连接池。调用方在交付句柄上开着事务时，这条连接由它占着，要到它自己的调用返回之后才放开；在这样的事务里调用 `Set`、`Delete` 或 `List`，等的是调用方自己。`database/sql` 取连接的等待只随上下文结束：上下文没有期限就一直等下去；写入的事务开启不随调用方取消，有期限也等不完。这期间这个库唯一的连接一直被占着，进程里其余每一条语句都排在它后面。走到这一步不需要反常的用法：进程内总线在发布方的协程上、带着发布方的上下文调用订阅方（`event` 设计文档的并发与事务边界），发布方在自己的事务里发布一个事件，订阅方在处理它时写一个设置，就是这种调用。

文件库上的同一次写入等的是调用方占着的锁：数据库模块默认以 `IMMEDIATE` 开启 SQLite 的事务，调用方不以 `DEFERRED` 开启的事务从开启起就占着写锁，读没读过、写没写过都一样；以 `DEFERRED` 开启的事务写过之后占着写锁，回滚日志模式下读过之后占着共享锁，写入的提交要等它读完（[ADR-db-waits-2026-09-29](adr-db-waits-2026-09-29.md)）。SQLite 在驱动里等锁，由连接的忙等时限结束（驱动默认 5 秒，定位符可以改），上下文结束打断不了这段等待，等满了写入就以 `SQLITE_BUSY` 失败。PostgreSQL 上写调用方写过的那一行，等的是调用方的事务，等到上下文结束，或由会话的 `lock_timeout`、`statement_timeout` 结束。

数据库模块为替调用方发出语句的模块提供 `Connection`：在一个界内取连接，等锁照引擎自己的设置；模块自己的语句经它取连接，不各自设界（[ADR-db-waits-2026-09-29](adr-db-waits-2026-09-29.md)）。

本模块从交给它的上下文里读不出调用方持有的事务，Go 也不给出协程的身份：调用方自己的占用与别的写者的短暂占用，在它看来是同一回事。

## 考虑过的选项

### 取连接的等待只随调用方的上下文结束

写入先在调用方的取消下取连接，再在取到的连接上于取消之外开事务。

**否决**：调用方给了期限时这就够了，可没有期限的上下文仍然一直等下去，唯一的连接也一直被占着。进程内总线交给订阅方的是发布方的上下文，订阅方给不了它期限。

### 本模块自己限时取连接

本模块自己从交付连接池取连接，取连接的等待随调用方的上下文结束，也不超过一个固定的界。

**否决**：它与数据库模块的 `Connection` 做的是同一件事，取连接、钉住会话、交还连接的代码在本模块里再写一份，失败的形状与交还时的处置随之与名册、审计各写的一份各自漂移，正是数据库模块否决的由各模块自己设界（[ADR-db-waits-2026-09-29](adr-db-waits-2026-09-29.md)）。

### 读写面收调用方的事务

`Set` 另收一个 `*gorm.DB`，或从上下文里取出调用方放进去的事务，让写入与调用方的工作同进退。

**否决**：写入之后的重载与发布以「已提交」为前提。写在调用方的事务里，重载经别的连接读不到这一行，事件在提交之前发出，调用方一回滚，本副本与其余副本就会去服务一个从未落库的值。要保住这一前提，重载与发布只能等调用方提交之后再做，而这件收尾就落到了每一个调用点身上。接口签名也要改。

### 识别只开一条连接的库，调用时直接拒绝

连接池的上限为一、在用数为一时，判定调用方占着这条连接。

**否决**：在用的那一条也可能正被别的协程短暂占着，一次正常的写入会因此被拒；连接池开几条连接是数据库模块的交付细节，本模块据它判定，就依赖了一个不在契约面上的事实。

### 行为不变，只写进对宿主的要求

**否决**：漏了这条不报错，表现是整个进程无声地卡住，没有一处说出原因。进程内的订阅方正是会在发布方的事务里被调用的一方，而写这段代码的人未必知道它会在谁的事务里被调用。

### 经数据库模块的 `Connection` 取连接，取连接的界为五秒

**采纳**，见决策。

## 决策

采纳：**`Set`、`Delete` 与 `List` 各经数据库模块的 `Connection` 从交付连接池另取一条连接，不加入调用方的事务，取连接的界为五秒，取连接的等待还随调用方的上下文结束。** 取不到连接即失败，错误点明是在等连接，这一行不改动。写入在取到的连接上开事务，事务的开启与提交仍在调用方的取消之外。每一条语句等锁照引擎自己的设置，引擎放弃等锁时以它自己的错误失败。

五秒与名册、审计模块自己写的行取同一个界：负载之下被占着的连接在一条语句的工夫里就会放开，远在界内。

写入之后的重载不经这个界。它的触发方从不占着它要等的那条连接：调用方事务里的写入在重载之前已被拒绝，周期刷新不持有连接，本模块自己的变更事件在写入的连接归还之后才发布。写入先取连接，再等重载锁，因为一次在等别人连接的重载占着这把锁。

## 后果

只开一条连接的库上，在调用方的事务里写、删或列举设置，五秒内失败，进程不再卡住。调用方的期限短于五秒时，取连接的等待随期限先结束，写入也不例外。本模块不写任何方言代码。

**接受的代价：**

- **连接池被占满超过五秒时，写入、删除与列举失败。** 调用方拿到一个错误，重试与否由它决定。
- **正常的调用也可能这样失败**：只开一条连接的库上，别的协程开着一个超过五秒的事务时，这次调用等不到连接。本模块分不出这种占用与调用方自己的占用。
- **等锁不在界内。** SQLite 文件库上，调用方的事务占着写锁时在里面写、删设置——不以 `DEFERRED` 开启的事务从开启起就占着，读没读过、写没写过都一样，以 `DEFERRED` 开启的写过之后才占着；回滚日志模式下调用方以 `DEFERRED` 开启的事务读过、占着共享锁时在里面写、删设置；或别的连接占着整个库时：每一条语句——写入的开启、那条语句、提交，列举的那一读——各等满连接的忙等时限才失败，定位符设得多长就等多长。PostgreSQL 上写调用方的事务写过的那一行，要等调用方的事务结束，而调用方在等这次写入返回：调用方的上下文没有期限、会话又没有 `lock_timeout` 与 `statement_timeout` 时，这次写入永远等下去。
- **写入不与调用方的事务同进退。** 调用方回滚自己的事务，撤销不了一次已经返回 `nil` 的写入；要让一个设置随一件工作一起成败，本模块做不到。
- **等待过界没有哨兵。** 取不到连接的错误包着 `context.DeadlineExceeded`，与调用方自己的期限到了是同一种判别，要分开二者，看调用方自己的上下文是否已经结束；等不到锁是引擎自己的错误。

## 失效条件

若出现必须与调用方的工作同进退的设置写入——例如开户时写下的设置必须随开户一起回滚——读写面不收事务的形态需要与这个需求重新比较。

若正常负载下取连接的时间普遍接近五秒，这个界要改成一个输入项。
