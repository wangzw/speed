# 通知类型是发出它的业务模块的资源声明，通知模块是消费点，取材域取可用集

## 背景

一条通知必须有类型。收件箱按类型分组与过滤，渠道偏好按（收件人，类型）记，投递按类型校验与去重。类型是业务词汇，形如 `billing.invoice_paid`，通知模块不认识 `billing` 与 `invoice_paid` 是什么。

一个类型的属性不止一个名字：

- **分组**，供收件箱按组过滤。
- **默认渠道**，业务模块对这类通知的渠道偏好起点。
- **可退订与否**：验证码一类不可退订。
- **收件人可见参数**的白名单：非 nil 时，只有列出的参数进得了载荷。

这些属性必须与类型名一起给出，且必须能被**偏好写入**与**投递**两处当校验参照。类型因此是**词汇**：同一个声明不能在这条命令下合法、在另一条下非法，否则宿主写一项偏好会在一条命令下被接受、在另一条下被拒。

约束如下：

- **模块以描述符上的 `Resources` 字段对外声明只读元数据。** 注册表原样保存并按类型提供查询（`core.Resources[T](reg) []core.Resource[T]`），`core` 不解释任何资源（[ADR-core-scope](adr-core-scope.md)）。
- **该查询遍历全部已登记模块，`core` 不代消费点过滤；取材域由消费点自行裁定**，并写在消费点所属模块的设计文档里（[ADR-module-resource-scope](adr-module-resource-scope.md)）。
- **模块描述符在驱动开始前已冻结**，「业务模块可以在通知模块之后才声明」因此平凡成立（[ADR-lifecycle-stages](adr-lifecycle-stages.md)、[ADR-dependency-resolution](adr-dependency-resolution.md)）。

## 考虑过的选项

### 进程级可变登记座

业务模块在运行期向一个进程级登记座注册自己的类型，通知模块从登记座读全部类型（旧树 `NotificationsSeat` 形态）。

**否决**：描述符在驱动开始前已冻结，一个模块能否参与装配在驱动开始时就已定下，「业务模块可以在通知模块之后才声明」因此平凡成立，不需要运行期登记去等它。可变登记座会造出第二个真相源——同一份类型集合在描述符里一份、在登记座里一份，两者不一致时无人裁定；而登记座的写入发生在 `Init`，一个未被本次命令纳入、也没有预置实例的模块没有 `Init`，它的声明静默不到场。

### 类型名常量加使用方配置项点名

发布方在自己包里声明类型名常量（字符串），通知模块用配置项逐项点名它要处理的类型（审计动作形态，[ADR-audit-reach](adr-audit-reach.md)）。

**否决**：一串类型名承载不了分组、默认渠道、可退订与否、收件人可见参数这些属性；把这些属性另找一处声明，就等于把一份类型声明拆成两处，两处可以不同步。配置项点名还与「同一个声明跨命令不变」直接相悖：一个类型在这条命令下被点名、在另一条下没有，词汇属性因此随命令变化。

### 由通知模块自己声明全部类型

通知模块列举并声明它支持的每一个类型。

**否决**：类型的归属是发出它的模块，通知模块不认识 `billing.invoice_paid` 一类的业务词汇，列举不出来，也只能靠猜；业务模块要新增一个类型，就得改通知模块，依赖方向反转。

### 类型是发出它的业务模块的资源声明，通知模块是消费点，取材域取可用集

**采纳**，见决策。

## 决策

采纳：**通知类型是发出它的那个业务模块的资源声明；通知模块是消费点；取材域取可用集，不做减法；不引入任何运行期可变的注册表。**

- **声明落在 `Resources` 上。** 业务模块把 `notification.TypeSpec` 值放进自己描述符的 `Resources`，与它声明别的只读元数据一致。
- **消费点有两处，各自在 `New` 收。** `notification.preferences` 与 `notification.delivery` 各在 `New` 里经 `core.Resources[notification.TypeSpec](reg)` 收齐全部已登记模块的类型声明。
- **取材域取可用集，不做减法。** 判据是类型为词汇：偏好写入与投递拿它当校验参照，同一个声明不能在这条命令下合法、在另一条下非法。消解落选的模块其声明也照收——一份类型声明是这个二进制的一份静态事实，不随一次运行存亡。
- **不引入运行期可变注册表。** 类型的全集在驱动开始前已由各模块的描述符定下，无需在运行期登记或变更。

## 后果

类型集合有一处定义（各业务模块的描述符）、两处消费（偏好模块与投递模块的 `New`）。一个类型的全部属性随它自己的声明一次给出，偏好写入与投递两处读的是同一份。

**接受的代价：**

- **业务模块要多一条 `pkg/notification` 接口包的依赖。** 一个只想发通知的业务模块，为了把 `notification.TypeSpec` 放进 `Resources`，要 import 通知的根包；这条依赖是构造期依赖，进它所在模块的依赖闭包。
- **一个未被本次命令纳入的模块，其类型声明照样进分类法。** 可用集不随命令变化：宿主在一条只装通知模块的命令上，仍看到全部已登记模块声明过的类型。
- **类型名一旦发布即跨模块的契约。** 业务模块改一个类型名，偏好矩阵里按该名记的行、使用方按该名的查询都随之失效，而编译器一处也拦不住。

## 失效条件

以下情形出现时，本决策需要重议：

- 若出现一种类型，其属性必须随一次运行而变（而非随二进制冻结），则「取可用集、不做减法」这条的前提（声明是静态词汇）改变。
- 若 `core` 开始提供按集合过滤的资源查询，则「消费点自定取材域」这条判据可能被 `core` 的查询承接（[ADR-module-resource-scope](adr-module-resource-scope.md)）。
