# 用户档案的自助功能与管理面分立

## 背景

显示名与账户属性集的写当前只有管理面一条口子：改它们的唯一对外路由是 `B/admin/accounts/:id`，它走管理面管线，每一步以权限点为前提（动作 `authn.account.update`，经 `Decider` 判定）。登录引擎的自助件在 `pkg/authn/login/internal/selfservice` 下，挂 `B/me` 的读、`B/me/preferences` 的语言与时区偏好写，以及改口令、手机号、删标识、解绑外部身份；它**不含显示名与通用属性的写**，且在 `internal` 下，只被登录引擎构造与调用，别的模块够不到。

一个已认证的用户因此改不了自己的显示名与通用属性：要改，得先有一条带管理权限点的路由。用户必须能自助读自己的档案，并写自己的显示名、语言、时区与颜色模式偏好（REQ-account-001、REQ-account-002、REQ-account-003、REQ-account-071）。改自己的档案是自助动作，其授权依据是“发起者就是这个账户”这条无须策略、authn 自己可以核对的事实，与改他人账户不是同一回事。

管理面的每条路由要求一个权限点，判定经 `Decider`；自助功能只要求一个已认证的身份。自助功能与管理面的信任级不同。把自助功能并进管理面，会让权限模型失去“自助动作不过 `Decider`”这条区分点。

## 考虑过的选项

### 扩 `pkg/authn/admin`，在其中加一条不带权限点的自助路由

在管理面模块内为档案的自读自写加路由，跳过 `Decider`。

**否决**：管理面的管线固定为“先冒充检查，再有 `Decider`，再格式与租户，再归属，再读对象，再问 `Decider`，再发起者强度，再强制审计，再调能力”。自助动作不要权限点、不问 `Decider`。并入后要么给这一条路由开一条穿过管线的旁路，模块内因此多出一套与管理面并行的授权路径；要么把自助动作也经 `Decider` 判定，给“改自己”要求一个权限点，没有 `Decider` 的装配里用户就改不了自己的档案。两种都让“自助不经过扩展点”这条判据失去落点。

### 复用 `authn.login` 的内部自助件

把档案的自读自写留在 `pkg/authn/login/internal/selfservice`。

**否决**：那个包在 `login/internal` 下，只被登录引擎构造与调用，别的模块与宿主 import 不到，档案接口因此继续绑死在登录引擎上；它不含显示名与通用属性的写，补上它们等于在登录模块里长出一份与管理面并行的档案写入接口。并且留着它，`B/me` 的读与它在这里、写在那里，同一份资源的主要部分分在两处。

### 档案路由把账户标识放进路径

档案路由以路径参数寻址账户，形如 `PATCH B/me/:id`，或复用 `B/admin/accounts/:id` 的格式。

**否决**：用户只读取、修改自己的档案，上下文里的身份已经点名了账户。路径再带一个标识，授权就退化成“比较客户端给的标识与身份”，多出一条越权路径，且与自助范围判据“发起者就是这个账户”重复。

### 新模块 `authn.profile`，挂 `GET B/me` 与 `PATCH B/me`

**采纳**，见决策。

## 决策

采纳：用户档案的自助功能是独立模块 `authn.profile`，挂 `GET B/me`、`PATCH B/me`，与管理面分立。

**判据是信任级。** 自助动作的授权依据是“发起者就是这个账户”，是 authn 自己可以核对的事实，不经 `Decider`、不要权限点；管理动作要权限点、经 `Decider` 判定。自助功能与管理面据此分立：`authn.profile` 挂自助的档案接口，`authn.admin` 挂管理面。

**读身份取自上下文，不取自路径。** 档案路由经 `authn.FromContext` 取发起者的身份，账户由身份给出；路径里不出现账户标识。授权是“发起者的账户就是被写账户”这条恒真的事实。

**自写字段集是封闭集：显示名、属性、语言、时区、颜色模式。** 这些字段经账户的既有写入接口 `AccountAdmin.SetDisplayName` 与 `AccountAdmin.SetAttributes` 写入；语言、时区与颜色模式是账户属性集里的具名用法（`i18n.locale`、`i18n.tz`、`presentation.color-mode`），不新持存储、不另造写入接口。

**不可自写：账户状态、标识符（邮箱、手机、用户名）、外部身份绑定。** 它们各有其路由与更强的认证要求，不在本接口范围内。

## 后果

宿主为档案接口纳入模块 `authn.profile`；不纳入时 `B/me` 不挂，账户的读改仍可经 Go 接口由宿主命令调用。

档案的自读自写与改动认证事实的自助路由不在同一个模块：档案接口在 `authn.profile`，改口令、手机、删标识、解绑在 `authn.login`。只挂其一、不挂另一的宿主得到一项不完整的自助功能。

**接受的代价：**

- 功能目录多一个模块，宿主多一个要纳入的名字；档案接口与登录自助功能不再属于同一个模块，“自助”不再是某一个模块的同义词。
- 可自写字段集封闭：新增一个可自写字段要有新的决定，不能在已接受的自助功能里直接加。
- “读身份不从路径取标识”把账户标识的唯一来源固定在上下文；想按标识寻址档案的调用方（例如管理界面代客读取）不能用这条路由，要走管理面。
- 复用账户既有写入接口意味着档案接口的校验边界跟着账户模块走：显示名上限、属性集边界一改，档案接口随之改。

## 失效条件

- 出现一种自助动作，其授权依据不是“发起者就是这个账户”而仍需策略：判据“信任级”不覆盖它，档案接口与授权接口的边界要重新裁定。
- 所有宿主总是同时纳入 `authn.profile` 与登录自助功能：`authn.profile` 与登录自助功能的分立不再带来装配上的选择，可合并为一个自助模块。
- 档案接口要自写的字段扩到标识符或外部身份绑定：它与管理面的分立随之减弱，字段集与路由需重新裁定。
