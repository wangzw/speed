# 管理员身份由租户成员关系承载，system 是名册中的真实租户

## 背景

租户即策略域，一次判定是（主体，域，资源，动作）的精确匹配，域取请求上下文里的租户标识，平台范围取保留值 `"system"`（[ADR-authz-model](adr-authz-model.md)）。名册里不得有标识为 `system` 的租户，启动期核对，有同名租户即终止启动。

现状的 `platform-admin` 角色在每个租户域各建一份并绑定给该租户的成员，使一个业务租户的成员同时持有该租户的全部租户级权限；个人租户另用 `owner` 角色。管理员身份与租户成员关系不相关联：一个账户持有管理员权限，不必是任何特定租户的成员。

需要成立的条件：

- 平台管理员的权限只在 `system` 内；不在 `system` 租户内的账户不能持有管理员权限。
- 每个租户有自己的租户管理员，负责该租户内的成员、邀请、身份提供方与角色。
- 租户机制不按租户种类分叉：`system`、业务租户与个人租户使用同一套角色与绑定。

## 考虑过的选项

### 维持现状：`platform-admin` 逐租户绑定，`owner` 管个人租户

管理员权限继续随每个租户各建一份，个人租户继续用允许集为空的 `owner`。**否决**：管理员身份与租户成员关系脱钩，「不在 `system` 租户内不得成为管理员」无法表达；同一个「租户内最高权限」的语义由 `platform-admin` 与 `owner` 两个名字承担。

### 只把 `platform-admin` 移出非 `system` 租户，保留 `owner`

业务租户不再持有平台角色，个人租户仍用 `owner`。**否决**：租户管理员仍按租户种类分成两个角色；且 `system` 没有名册行，无法承载「管理员必须是 `system` 成员」这条成员关系。

### 统一租户管理员角色，`system` 成为真实租户

每个租户内的最高权限用一个角色承担，`system` 进入名册，管理员资格由成员关系表达。**采纳**，见决策。

## 决策

采用：**管理员身份由租户成员关系承载，`system` 是名册中的真实租户，同时是平台策略域。**

- **`system` 进入名册。** 标识与平台域取值相同，是名册中的一行，别名 `system`，状态受保护：不可停用、不可删除。启动核对反转：名册里没有 `system` 即终止启动。名册的标识唯一性由 `tenant.Catalog` 保证，`system` 与其他租户没有区别。
- **每个租户一个 `tenant-admin` 角色。** 角色位于该租户域，持有该租户域内治理的租户级动作（[ADR-authz-tenant-management](adr-authz-tenant-management.md)）；判定仍按租户域进行，租户之间互不解析对方的绑定。
- **创建者是第一个 `tenant-admin`。** 创建租户、创建账户个人租户的动作，在同一个动作里为创建者写入成员关系与 `tenant-admin` 绑定。任何一类租户都不存在没有管理员的中间状态。
- **创建的钩子可以读账户行。** 账户模块在创建事务提交之后调用 `AccountCreated`；钩子这时读得到账户，重试读到已删除的账户时什么也不做。「实现不得读账户行」约束的是账户删除之后的收尾钩子，不是创建。
- **每个租户至少保留一个 `tenant-admin` 绑定。** 一个 `tenant-admin` 不能移除自己的绑定；移除他人时剩余的绑定数不得为零。这条约束由写入侧执行，不由读取侧解释。它只管显式的成员关系移除：删除账户时，该账户的成员关系与绑定随账户一起消失，删除不问成员守卫，也不经过这条约束；一个租户因此在账户删除之后可能没有租户管理员，直到有人写入一条新绑定。
- **`platform-admin` 只在 `system` 域存在。** 其他租户域不创建该角色。写入 `system` 域的角色绑定时，被绑定账户必须在 `system` 租户持有有效成员关系，不满足即拒绝；移除该成员关系时，撤销该账户在 `system` 域的全部绑定。成员资格由宿主提供的检查接缝回答；宿主可以对本部署自己配置的主体（静态凭据表的主体）答真，这类主体没有成员关系行，而配置主体与写下绑定的正是同一个部署。
- **平台能力在平台域判定，路径里的租户是数据。** 一个能力若属于平台运营而不是某个租户的治理，它的判定在平台域做出；请求路径或正文里的租户标识只说明它作用的数据，不构成策略域。声明这一性质的权限在 `authz.guard` 的 `Decider` 分派里固定为平台域，不按 `Decision.Tenant` 判定，也不回退到那个租户域。冒充的 `authn.impersonation.start`、`authn.impersonation.read`、`authn.impersonation.revoke` 是这类能力：平台管理员不必是目标租户的成员，只在目标租户持有 `tenant-admin` 的账户不通过；被冒充账户必须是该租户的有效成员，这条属于冒充的结构性限制，不由策略域承担。
- **不存在 `owner` 角色。** 个人租户的管理员是同一种 `tenant-admin`，允许集的差异由宿主按租户种类声明（见 [ADR-starters-personal-tenant](adr-starters-personal-tenant.md)）。租户种类本身也是宿主的策略：平台只收到租户标识，个人租户的识别（标识前缀）、写保护与成员删除的拒绝都由宿主按自己的约定判定。

## 后果

管理员资格可以从成员关系读出：不在 `system` 租户内的账户不可能持有 `platform-admin`，写入侧的成员校验使这条在数据上成立，而不只是约定。宿主自己配置的静态主体是这条的例外：它们没有成员关系行，成员核对按部署的配置答真。

平台管理员默认不能管理业务租户的成员、邀请与身份提供方。跨租户进入仍由 `authn.tenant.access` 的平台域回退放行，进入之后能做什么仍按该租户域判定；平台管理员要在某个业务租户内行使管理权，必须由该租户的 `tenant-admin` 授予，或由平台管理员显式写入一份 `tenant-admin` 绑定。冒充记录与冒充的发起不在此列：它们是平台能力，在平台域判定，平台管理员不必是目标租户的成员。

`system` 的 `tenant-admin` 决定谁进入 `system` 租户，因而能扩大平台管理员的候选池；把候选者变成平台管理员仍需 `system` 域的 `role.manage`。

**代价：**

- **创建路径承担首绑。** 创建租户与创建账户都要写第一条 `tenant-admin` 绑定；任何一条路径遗漏，留下的租户就没有管理员，而「至少一个」的写入侧检查只能在后续移除时生效，补不了这个洞。创建动作必须是原子的，或由重试补齐。
- **旧数据需要迁移。** 已存在的每个租户域 `platform-admin` 角色与绑定要撤销，个人租户的 `owner` 角色与绑定要迁移为 `tenant-admin`；`system` 名册行要在升级时建立。
- **`system` 不可删除。** 运营者不能通过删除租户来清理平台策略数据，只能清理该租户下的业务数据。
- **平台管理员不再默认可用。** 只持 `platform-admin` 的账户打开业务租户的管理页面会被拒，需要该租户的 `tenant-admin` 授权；冒充页除外，它按平台域判定，平台管理员不必是该租户的成员。部署要为走查准备这条绑定。
- **成员关系的写入口限制更严。** 移除 `system` 成员关系会连带撤销平台权限，这条联动必须与成员写在同一事务里，或由幂等重试补齐。
- **账户删除可以留下没有管理员的租户。** 删除不经过显式移除的守卫，一个租户的最后一名租户管理员被删除后，该租户没有租户管理员，直到有人写入一条新绑定。这是「至少一个」规则的明示例外。
- **宿主的 seed 对账管理员，但不覆盖运营者的成员决定。** `seed.tenants[].admins` 点名的账户在每次运行补齐缺失的成员关系与 `tenant-admin` 绑定；`seed.members` 只在本次运行创建该账户时写入，运营者经成员管理面做的增加、暂停、恢复与删除因此保留。
- **`serve` 依赖 `seed` 先建立 `system` 租户。** 名册里没有 `system` 租户时策略模块拒绝启动；`sqlite-memory` 栈的库只在进程内，`seed` 与 `serve` 要共享它就得指向同一个文件定位符，因此该栈同样必须先种入再启动。

## 失效条件

出现两个互不信任的平台管理团队，需要各自的平台域与各自的 `platform-admin` 集合时；或业务租户需要无需平台参与的自助创建，而创建者无法成为其 `tenant-admin` 时。
