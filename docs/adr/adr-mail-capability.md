# 邮件发送能力为顶层能力模块，投递载体为 SMTP，内容不模板化

## 背景

邮件的**发送**能力（载体接口与 SMTP 适配）是「发出一条已经渲染好的邮件」这件事，与短信的发送能力一样，是一项通用基础能力，与 `pkg/kv`、`pkg/event`、`pkg/sms` 同级，不属于任何功能目录。约束如下：

- **邮件的内容是自由文本，不是模板。** 邮件的 SMTP 载体没有国内短信厂商那样的模板约束：抄送、密送、回复地址、自定义主题与两份可替代的正文（纯文本与 HTML）都是接口点名的字段。发送接口因此以一条已渲染的消息为中心。
- **附件是不可变内容，可能很大。** 一封邮件带零到多个文件；把每个文件一次性读进内存的代价由每一封带附件的邮件承担。
- **发件人是有约束的身份。** 中继通常只接受它自己域内的发件人；一个进程默认以一个身份发信，接口要允许逐封覆盖，而配置要能收窄可用的发件人。
- **发送接口不幂等。** SMTP 事务重复一次会投递并计费第二封，超时之后调用方无从知道邮件是否已发出，重试会重复投递。
- **`net/smtp` 已被冻结，且不带上下文。** 走它就得自己实现 MIME 组装：多部分正文、附件编码、非 ASCII 头的编码字与点填充。
- **两家国内厂商的 OpenAPI 都够不着这封邮件的全部字段。** 腾讯云 SES（[REF-tencent-cloud-ses](../references.md)）的 OpenAPI 默认只能发模板邮件，它的自由文本参数 `Simple` 已被文档标记为 `Abandoned`，错误码是 `FailedOperation.WithOutPermission`；阿里云 DirectMail（[REF-aliyun-directmail](../references.md)）的 OpenAPI 没有抄送与密送。两家都提供覆盖全部信封字段的 SMTP 端点。
- **发送能力的形态在短信上已经定下**：根包接口与工厂、载体叶子排他交付、哨兵 `ErrThrottled`/`ErrRejected`/`ErrUncertain`/`ErrInvalidConfig`、无队列无重试（[ADR-sms-capability](adr-sms-capability.md)）。
- **共享单元必须能被两个功能目录取用。** `pkg/sms` 下的包不能 import `pkg/mail` 的 `internal` 包，`pkg/internal/dedupe` 与 `pkg/internal/configtest` 已被两个功能目录的载体取用。

## 考虑过的选项

### 另造一套接口与工厂，不仿 pkg/sms

为邮件定义一套与短信不同的结构：自己的消息类型、自己的工厂、自己的归类器，不与短信共用任何约定。

**否决**：邮件与短信的发送需求同为「同步、一次性、按厂商归类、无队列无重试」，差异只在消息结构与载体集合。另造一套会让本仓库同时维护两份功能几乎相同的工厂与归类器，形态上的差异不抵这份重复。采纳的是仿 `pkg/sms` 的形态，代价是两份近似重复的工厂与归类器并存。

### 邮件内容模板化，复用短信的模板声明

把正文做成模板：调用方给出模板名与参数，载体按语言到编号的映射渲染成邮件。

**否决**：邮件的内容是调用方已经渲染好的自由文本，SMTP 载体对它没有任何模板约束；模板约束是国内短信厂商独有的。把模板强加进来，会让调用方为每一封邮件预先登记一份模板，而 SMTP 没有这个要求。采纳自由文本，代价是语言与格式由调用方负责。

### 载体集合含厂商 OpenAPI 适配

除 SMTP 外，另写阿里云 DirectMail 与腾讯云 SES 的 OpenAPI 适配，作为各自的载体叶子。

**否决**：两家 OpenAPI 都够不着接口点名的字段——腾讯云的 OpenAPI 默认只收模板邮件，用自由文本要特殊授权；阿里云的 OpenAPI 没有抄送与密送。一个交付不了接口点名字段的载体不在这个接口之下。两家的 SMTP 端点覆盖全部信封字段，所以厂商适配经 SMTP 承载。采纳 SMTP-only，代价是 SMTP 之外的厂商专有接口够不着。

### 附件一次性读成字节，接口收 `[]byte`

用例程把附件一次性读成字节切片，随消息一并交出。

**否决**：附件可能很大，把每个文件读进内存的代价由每一封带附件的邮件承担，而发送本身只需要顺序读一遍。采纳 `io.Reader`，代价是该读取器在发送时被读到结尾、发送一次即耗尽，重试要重建它。

### SMTP 库手写 MIME，不使用第三方库

在 SMTP 载体叶子包内自己组装 MIME 报文与 SMTP 会话，不引入第三方库。

**否决**：`net/smtp` 已被冻结、且不带上下文；自己实现多部分正文、附件编码、非 ASCII 头的编码字与点填充，只会把这些细节的缺陷留给本仓库。采纳桥接 `github.com/wneessen/go-mail`（[REF-go-mail](../references.md)），代价是 `pkg/go.mod` 多一个第三方依赖，要固定版本并加封边守卫。

### 共享单元留在 pkg/sms 下，mail 从那里取用

把去重表与配置夹具继续留在 `pkg/sms` 下，mail 的载体从那里 import。

**否决**：Go 的 `internal` 规则禁止 `pkg/mail/**` import `pkg/sms/internal/**`。要共用就得把两个单元移到共享单元的位置，判据与当初把 `literal` 上移时相同：两个功能目录都需要它。采纳上移到 `pkg/internal/`，代价是 `pkg/sms` 的 import 与点名旧路径的文档跟随改动。

### 提供任意头透传

让 `Message` 携带一个任意的头字段映射，调用方自行填 `List-Unsubscribe` 之类的头。

**否决**：接口点名的字段要么被每个载体忠实交付、要么被拒绝，这是接口契约的可判性来源；一个任意头映射既没有判据，也让「载体忠实交付了什么」不可核对。SMTP 本身支持任意头，但支持不等于要把它暴露成接口。采纳不透传，代价是接口没有点名的头没有传出的通道。

## 决策

采纳：**邮件发送能力为顶层能力模块 `pkg/mail`，形态仿 `pkg/sms`，投递载体集合为 SMTP，内容不模板化。**

- **形态仿 pkg/sms。** `pkg/mail` 根包是接口包与工厂，不登记模块；它交付 `Sender`、`Message`、`Attachment`、`Receipt`，哨兵 `ErrThrottled`、`ErrRejected`、`ErrUncertain`、`ErrInvalidConfig`，以及工厂 `Spec`、`NewModule`。载体叶子包排他交付 `Sender`。不引入队列、工作池与重试。
- **内容不模板化。** 正文是调用方渲染好的自由文本（`Text` 与 `HTML` 两份可选），本模块不持模板、不渲染、不翻译。
- **投递载体集合为 SMTP，不含厂商 OpenAPI 适配。** 投递载体叶子包 `pkg/mail/smtp` 经 `github.com/wneessen/go-mail` 发信，覆盖两家厂商的 SMTP 端点与任意 SMTP 中继。另有一个不触中继的日志载体 `pkg/mail/log` 作为没有配置其它载体时的通道，由 `mail.carrier` 选择（[ADR-carrier-selection](adr-carrier-selection.md)）。
- **附件是 `io.Reader`。** 读取在发送时完成，一个 `Message` 值只发送一次；重试要重建读取器。
- **发件人是载体配置项加允许集，可被消息覆盖。** 载体配置给出一个缺省发件人与一组额外允许的发件人，`Message.From` 为空取缺省，非空须落在允许集里。核对需要载体的配置状态，因此落在载体、不落在无状态的 `Validate`。
- **`dedupe` 与 `configtest` 上移为 `pkg/internal/` 的共享单元。** 两个功能目录的载体都需要它们，判据与当初把 `literal` 上移时相同。
- **SMTP 库是桥接 `github.com/wneessen/go-mail` v0.8.1，不在叶子包内手写 MIME。**
- **不透传任意头。** 接口点名的字段要么被每个载体忠实交付、要么被拒绝；接口没有点名的头没有传出的通道。

## 后果

发信能力可被任何模块单独引入，不必背上整套认证，也与短信的发送能力形态一致。投递载体只用一个通用协议，一次覆盖多家厂商的中继；日志载体保证没有配置中继的部署仍有一条可用的邮件通道。

**接受的代价：**

- **两份近似重复的工厂与归类器并存。** `pkg/mail` 与 `pkg/sms` 各有一份形态相同的工厂与归类器；两处一起改的维护负担由此而来（[ADR-sms-capability](adr-sms-capability.md)）。
- **邮件的语言与格式由调用方负责。** 本模块不渲染、不翻译，也不认识语言；调用方要发多语言的邮件，就得自己渲染出多份正文。
- **SMTP 之外的厂商专有接口够不着。** 接口只表达 SMTP 能覆盖的信封与报文；一家厂商只在其 OpenAPI 上提供的功能没有通道。
- **带附件的邮件重试要重建读取器。** 附件的 `Data` 被读到结尾，一个 `Message` 值只发送一次；重试用一个新的 `DedupeID` 而没有重建读取器时，发出去的是一份空附件、没有错误可看。
- **一个进程默认以一个身份发信。** 除非配置额外列出允许的发件人，否则每封邮件都从配置的缺省发件人发出；发件人的核对因此从无状态的 `Validate` 移到需要载体配置状态的载体一侧。
- **`pkg/sms` 的 import 与文档跟随改动。** `dedupe` 与 `configtest` 的路径变化，引用它们的包与点名旧路径的文档都要改。
- **`pkg/go.mod` 多一个第三方依赖。** SMTP 库要精确固定版本，并加一条封边守卫把它挡在叶子包里。
- **接口没有点名的头没有通道。** 一个调用方需要发一个接口未点名的头（例如厂商专有头）时，只能改本模块的接口，不能绕过。

## 失效条件

以下情形出现时，本决策需要重议：

- 若某个厂商开始要求预先审核通过的正文模板（如今只对短信成立），则「内容不模板化」不再够用，需要重新引入模板声明，对照短信的形态。
- 若 `net/smtp` 被废弃的替代出现，或 `github.com/wneessen/go-mail` 停止维护，则桥接对象需要重选，甚至手写 MIME 重新成为代价可接受的一档。
- 若出现一封邮件必须携带接口未点名的头（例如某个普遍需要的厂商专有头），则「不透传任意头」这条规则需要重新权衡。
- 若出现一个使用方，它必须经某家厂商的 OpenAPI 才能发出（例如 SMTP 端点不可用），则「载体集合只有 SMTP」不再够用，需要为那家写一个 OpenAPI 载体。
