# 限流的装配级性质写成非保证

## 状态

已接受

## 背景

限流是一层普通中间件，它的强度取决于这次运行纳入了什么、链上还有谁、计数后端是哪一个。这些本模块大都观察不到：它读不到链的其余部分，也读不到副本数。入口模块的登记面能列出已声明的端名，本模块则不拿它与自己的清单比对：清单里没有的端是漏写还是有意收窄，名单本身分不出来。

认证与租户都把这一类性质写成非保证，判据是同一条：成立与否取决于这次运行纳入了什么，而模块既不持有那些信息，也没有能观察它们的接缝。认证考虑过在入口模块上增开接缝、把性质变成强制，并否决了那个做法——每一道为拦一条绕过路径加的接缝都造出下一个可被绕过的接缝，可被绕过的点因此只是挪到别处（[ADR-authn-guarantees-2026-09-20](adr-authn-guarantees-2026-09-20.md)）。

## 考虑过的选项

### 为每条性质加一道接缝，把它变成硬保证

**否决**：可被绕过的点会挪到别处而不消掉。本例尤其如此：本模块要拦的绕过路径几乎都在它之外——链上另一层的 `Order`、所选的键值实现——本模块没有一处能观察它们，为它们加的接缝只能加在别的模块上，而别的模块没有理由为一个它不认识的功能扩接口。端名清单是例外，接缝已经存在（[ADR-http-enumeration-2026-10-10](adr-http-enumeration-2026-10-10.md)），否决的理由换了一条：清单里没有某个端，可以是漏写，也可以是只守业务端、不守管理端的有意收窄，比对只能报出差集，判不出哪一种，把差集当作失败会拒绝合法的配置，因此它不能成为硬保证。

### 写成非保证，逐条列出

**采纳**，见决策。

## 决策

采纳：**本模块不以硬保证的形式承诺任何装配级性质**，把它们逐条写进模块文档的非保证一节。

哪些性质落在这一侧由判据定，不由清单定：一条性质若成立与否取决于这次运行纳入了什么，而本模块既不持有那些信息、也没有能观察它们的接缝，它就在这一侧。这条判据是充分条件：接缝存在、但比对只报得出差集而分不出合法配置与疏漏的性质，同样在这一侧，端名清单即是（[ADR-http-enumeration-2026-10-10](adr-http-enumeration-2026-10-10.md)）。

## 后果

一个部署要确认限流确实生效，只能靠运维侧的核对——逐端的链清单、那行标准错误、副本数与计数后端的对应关系。

**接受的代价：**

- 本模块不替任何部署保证限流一定拦得住。链上多一层、端名漏写一个、后端换成进程内实现，都会让限制变弱而不报错。
- 非保证一节随装配形态增多而变长，它是模块文档里最常被漏读的一节。
- 引入一条新的装配形态时，判断它落在哪一侧是本模块自己的事，别的模块不会替它问。
