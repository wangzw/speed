# 迁移以资源声明交付，按依赖序统一应用

## 背景

带表的模块各自携带自己的建表与改表语句。这些语句必须在全部产物构造完成之后、任何模块开始工作之前应用，`Migrate` 阶段就是这个时机（[ADR-lifecycle-stages](adr-lifecycle-stages.md)）。

模块的表之间存在引用：一个模块的外键指向另一个模块建的表。被引用的表要先存在。

可用集由 import 决定，其中包含宿主未必知情的模块：某个依赖 import 进来的模块同样带着它的表。

进程会反复启动，同一批语句因此会反复面对同一个库。

模块以描述符上的 `Resources` 字段对外声明只读元数据，注册表原样保存并提供按类型的查询，“带有哪些数据库迁移”是该机制列出的用例之一（[ADR-module-resources](adr-module-resources.md)）。

## 考虑过的选项

### 每个模块在自己的 `Migrate` 回调中应用自己的迁移

`Migrate` 阶段按依赖序逐个调用，顺序因此天然正确，模块各自对自己的库结构负责。

**否决**：幂等记录没有归宿。每个模块都要自己判断哪些语句已经施加过、自己写记录、自己处理中途失败，同一件事在每个带表的模块里各实现一遍。记录表本身的结构也没有定义者。迁移还因此不再是静态可查的：不启动数据库就无法回答“这个二进制里有哪些迁移”。

### 迁移按全局版本号排序

每条迁移带一个跨模块单调的版本号（时间戳一类），应用顺序由版本号决定，与模块依赖无关。

**否决**：版本号是一个跨模块的全局命名空间，而可用集由 import 决定。独立开发的两个模块会取到相同的版本号，且撞号双方未必知道对方存在。这与传统迁移工具的处境不同：那里全部迁移出自一个仓库，版本号有唯一的分配者。

### 模块之间的迁移彻底隔离

每个模块的迁移只能触及自己命名空间内的表，跨模块的外键与引用一律禁止，应用顺序因此不重要。

**否决**：跨模块的表引用在业务中常见，禁止它会把完整性约束从数据库赶到应用层，由各模块自己检查，而那正是数据库能够保证、应用层容易遗漏的一类约束。

### 同名迁移文件交给记录表去撞

同一模块的两条 `Migrations` 声明里出现同名文件时，不加检查，让记录表的主键在第二条施加时挡住它。

**否决**：记录表的主键是模块名与文件名两列的组合，第二条会被当成已施加而静默跳过：文件里的语句一条也不跑，而记录表看起来完整。被采纳的读法是收集阶段判 `ErrMigrationFailed` 并点名该文件，在任何一条迁移施加之前拒绝。

### 迁移以资源声明交付，数据库模块按依赖序统一应用

模块把自己的迁移集作为资源声明，数据库模块在 `Migrate` 阶段收齐全部声明并应用。

**采纳**，见决策。

## 决策

采纳：模块以资源声明交付自己的迁移集，数据库模块在 `Migrate` 阶段收齐并应用。

跨模块按依赖序，依据是各模块已有的依赖声明；模块内按迁移文件名的字典序。引用另一个模块的表，就要依赖那个模块的功能，没有这条声明则两者之间没有顺序保证。

幂等由一张记录表承担，记录已施加的模块名与文件名。该表自身用一条无条件可重入的建表语句创建，不经由任何模块的迁移集：应用迁移之前要先读它，它没有能被自己追踪的时机。

同一模块的两条声明里出现同名文件，在收集阶段判 `ErrMigrationFailed`，在任何一条迁移施加之前拒绝。记录表给不出这条保证：它的主键按模块名与文件名去重，撞上时表现为“已施加”而非冲突。

迁移集按本次命令的声明集收齐：不在声明集里的模块，其迁移不应用；在其中而被运行级纳入、又消解落选的，其迁移同样不应用。只被静态级纳入的模块没有表态，其迁移照常应用。

判据是库结构跟着这个二进制走，比一次运行长寿，所以取材域比启用集宽；而建哪些表仍是宿主写得出的一件事，所以取材域不是可用集。施加迁移的那条命令只运行级纳入引擎（带表的模块依赖引擎、引擎不依赖它们，依赖闭包够不到），因此那条命令要把它们静态级纳入（[ADR-command-tree-inclusion](adr-command-tree-inclusion.md)、[ADR-module-resource-scope](adr-module-resource-scope.md)）。按参与集过滤会让这条命令一张表都不建，而且成功退出、不报错。次序另有依据：依赖序在全部已注册模块上算出，与取材域无关，为的是同一批迁移无论由哪条命令施加，顺序都一样。

整个应用过程在一次跨进程互斥之下进行，互斥由方言实现提供。记录表给出的幂等只对先后发生的启动成立：多副本首次启动时各进程同时读到“未施加”，随后各自执行，先写入的那个之后，其余的建表语句因对象已存在而失败。

## 后果

带表的模块只声明，不执行：幂等、记录、失败处理都在数据库模块一处实现。

迁移集是静态的，不启动数据库即可回答这个二进制里有哪些迁移，由哪些模块带来。

跨模块的表引用合法，其顺序用模块已有的依赖声明表达，不引入第二套定序机制。

**接受的代价：**

- 依赖声明因此承担了两重含义：构造顺序，以及迁移顺序。一个模块仅仅为了让自己的表排在另一个模块之后而声明依赖，会连带改变构造顺序。
- 模块内的顺序取决于文件名，重命名一个已经施加过的迁移文件，记录表按新名字认为它没施加过。
- `Migrate` 中途失败会留下已施加的部分，这部分不在回滚范围内，也无法回滚。
- 本次命令运行级纳入了而消解落选的模块，其表不建，而一个已启用模块的迁移可能引用它们。这类引用在启动时表现为迁移失败，不在声明时暴露。
- 静态级纳入漏写一个带表模块、也没有为它预置实例时，它的表不建，而这件事不报错：未被本次命令纳入、也没有预置实例的模块不进启动诊断（[ADR-supplied-instance](adr-supplied-instance.md)）。“全部静态纳入”这项选择存在正是为了让宿主不必维护那份清单，用它则反过来会建起二进制里全部已登记模块的表，包括宿主 import 了却从未列举的模块：多出来的表没有写入方，代价是库里有空表。两条路各有各的代价，宿主必须选一条。
- 消解落选只在运行级纳入了该模块的那条命令下挡得住建表。同一个模块在提供服务那条命令下消解落选、而施加迁移那条命令只把它静态级纳入时，它的表仍然建出来。
- 不同命令可以收到不同的迁移集。一条深度越过 `Migrate` 而没有写静态级纳入的命令，其声明集等于参与集，它施加的迁移比专门施加迁移的那条少；记录表不记是哪条命令施加的，因而先跑前者再跑后者会把同一批迁移分两批施加，批与批之间的次序不再是依赖序：依赖序只在一次收集之内成立。深度越过 `Migrate` 的命令因此要与施加迁移那条写同一份静态级纳入。
- 出现在多副本部署中的方言必须能提供跨进程互斥，这是对实现子包的额外要求。提供不了的方言只适用于一个库一个进程的部署。

## 失效条件

若出现一个模块，其迁移必须在另一个模块之后应用而两者之间不存在构造期依赖，则“依赖序即迁移序”不再覆盖全部情形，迁移需要独立于依赖声明的定序手段。

若要支持一种不把 DDL 纳入事务的方言，则一条迁移的执行与它的记录不再原子，记录表给出的幂等失效，本记录对该方言不适用。

若同一个数据库上要跑两套彼此独立的装配，而它们的首次迁移不能相互排队，则固定的互斥标识不再适用，标识需要随装配自己的某个配置项派生。
