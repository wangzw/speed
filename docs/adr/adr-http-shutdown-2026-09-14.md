# Stop 关闭监听器并等在途请求排空结束

## 状态

已接受

## 背景

`Stop` 阶段的语义是停止接收新工作，逐个调用：入口——声明了 `Serve` 的模块——在前，其余模块在后，两组各按逆依赖序（[ADR-lifecycle-stages-2026-09-28](adr-lifecycle-stages-2026-09-28.md)）；`Close` 阶段释放资源，逆依赖序，在全部 `Stop` 走完之后才开始。注册表不对停机施加超时，这些回调必须自己保证有界（[ADR-lifecycle-stages-2026-09-13](adr-lifecycle-stages-2026-09-13.md)）。

`Stop` 与 `Close` 收到的 context 去掉取消、保留值，因而其中的排空不会因为宿主取消而立即返回。

在途请求可以触达进程内任何模块：它写的审计记录、它产生的跨度、它的 handler 经由的句柄与客户端。这些模块与入口之间没有构造期依赖——登记方在 `Init` 期取用登记面，不在 `Requires` 里声明它。注册表把入口的 `Stop` 排在它们之前，但排的只是回调的先后：入口的 `Stop` 一返回，其余模块随即逐个收到 `Stop`。在途请求触达的模块若已收到 `Stop`，它拒收这个请求的工作；若已收到 `Close`，它已释放这个请求正在用的东西。

各模块的 `Stop` 是逐个调用的：其中一个耗时多久，其后每一个就推迟多久。

## 考虑过的选项

### 分两拍：Stop 关闭监听器，Close 等待排空

入口在 `Stop` 里同步关闭监听器后返回，排空在后台进行，`Close` 等它结束。

**否决**：入口的 `Stop` 返回之后，其余每个模块都在排空期间收到 `Stop`，而 `Close` 阶段在全部 `Stop` 之后才开始；`Close` 又逐个调用，构造在入口之后的模块先于入口的 `Close` 被关闭。在途请求因而在排空中途失去它触达的模块：审计拒收它的记录，遥测不再导出它的跨度，handler 用着的句柄已被关闭。「排空期间其余模块尚未停止、仍在接收新工作」不是代价而是前提：在途请求要走完，它触达的模块就必须仍在接收它的工作。

### 关闭监听器与排空都放进后台协程

`Stop` 立即返回，关闭监听与排空都在协程中进行。

**否决**：`Stop` 返回即承诺不再接受新请求，而协程何时被调度不受调用方控制。承诺与事实之间因而有一段窗口，其中新请求会进入一个已经开始停止的系统。排空同样落在其余模块的 `Stop` 与 `Close` 之后，上一个选项的问题它全都有。

### Stop 关闭监听器并等待排空结束

`Stop` 同步关闭监听器，随后在调用协程内等待排空结束才返回。

**采纳**，见决策。

## 决策

采纳：`Stop` 在调用协程内关闭本模块全部监听端的监听器，随后等待各端排空结束，以各端配置的排空时限为界，然后返回；排空的失败由 `Stop` 报出。`Close` 只收拾 `Stop` 没有走到的端。

关闭监听器不放进排空协程：关闭之后，不再接受新请求这件事必须已经成立。全部监听器关闭之后才开始等待，各端的排空因而并行进行。

## 后果

本模块各端的在途请求排空结束之前，任何模块都没有收到 `Close`，不声明 `Serve` 的模块也都没有收到 `Stop`：先后由 [ADR-lifecycle-stages-2026-09-28](adr-lifecycle-stages-2026-09-28.md) 给出，排空由本记录的决策放进 `Stop`。

排空时限由本模块自己的配置承载，满足回调必须有界的要求。

**接受的代价：**

- 不声明 `Serve` 的模块，其「停止接收新工作」推迟到排空结束，推迟的时长至多为排空时限；这段时间里它们照常接收来自入口之外的工作。
- 排空时限到期时仍在途的请求被切断，调用方看到的是连接中断，失败在 `Stop` 阶段报出。
- 进程里另有一个入口、且它在本模块之后才收到 `Stop` 时，它的监听器要等本模块排空结束才关闭。
- 未曾绑定监听器的实例也会走 `Stop` 与 `Close`，两者都必须容忍一个从未监听过的实例。
