# 限流根包即实现，认证与租户只按上下文读

## 背景

本仓的模块有两种打包形态。一种是接口包加实现子包，接口与实现分开：认证按校验后端分，键值按存储后端分，租户按解析与名册分，审计的实现集中在一个子包里。另一种是根包即实现，设置采用这一种。

依赖形态上，认证与租户交付的是上下文读取，不是实例查询。把这类读取写成构造期取用，会让一个没有认证层的宿主启动失败，而那种装配是合法的（[ADR-authn-guarantees](adr-authn-guarantees.md) 记有不装认证模块的装配为合法）。

## 考虑过的选项

### 接口包加实现子包

**否决**：限流没有第二个实现，也没有第二条通路。拆出接口包只换来一个只有类型、没有行为的包，而它的唯一作用（让实现可替换）在本模块没有用途。

### 把认证与租户写成构造期取用

**否决**：没有认证层的装配是合法的，本模块在其中对取不到身份的请求放行。构造期取用会让那种装配启动失败，而这两处读取不发生实例查询，本来也不存在要排的序。

### 根包即实现，认证与租户只按上下文读

**采纳**，见决策。

## 决策

采纳：**根包即实现，不拆接口包与实现子包。** 入口模块、设置与键值三项在 `Init` 期经注册表取用，取不到即启动失败；认证与租户只按上下文读取，不进依赖声明。

交付的标识是 `(*ratelimit.Limiter)(nil)`，排他交付：一个进程里恰好一个判定接口生效。

## 后果

一个宿主只 import 本模块即得到完整的限流能力，没有实现子包要一并点名。

**接受的代价：**

- 本模块的接口与实现不分离。将来出现第二种实现（例如另一套计数维度），要先做一次拆包。
- 宿主不装认证或租户时，本模块照常构造，取不到的那两档在请求期分别按放行与全局层处置，构造期没有信号。
- 排他交付意味着两个限流实现同时表态启用时启动失败；本仓目前只有一个实现，这条约束要等到第二个出现才起作用。
