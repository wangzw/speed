# 本模块的句柄装上自己的 GORM logger，经日志模块写出，内容里不带语句的值

## 背景

本模块打开的每个句柄都携带一个 GORM（[REF-gorm](../references.md)） logger，交付的与 `Open` 自建的都是。GORM 的默认 logger 在一条语句失败、或慢于 200 毫秒时，经标准库 `log` 往标准输出写一行：语句的文本，绑定值按方言的引号规则填进占位符，失败时再加上语句的错误文本。一次被拒的插入因此把口令哈希、邮箱、联系人姓名这类值原样写到标准输出；`First` 查不到行也按失败写出，连同查找用的值；`Debug` 派生的会话写出每一条语句连同它的值。

错误文本同样可能带着值。PostgreSQL 拒绝一个格式不对的输入时，把输入写进消息：`invalid input syntax for type integer: "…"`。database/sql 扫描不了读出的一个值时，把那个值写进消息：`converting driver.Value type string ("…") to a int`。

句柄上的 logger 由每个模块的语句共用。宿主可以在自己发出的语句上以 `Session(&gorm.Session{Logger: …})` 换掉它；别的模块在同一个句柄上发出的语句——名册、设置、审计写的行——不经宿主，照样写出它们的值。交付之后改句柄上的 `Logger` 会与在途的语句竞争，本模块不支持。

GORM 给 logger 留的接缝是 `ParamsFilter` 与 `Trace`：`ParamsFilter` 在它把值填进文本之前问 logger 要哪些值，`Trace` 拿到填好的文本与语句的错误。GORM 的 logger 报出的调用点是调用栈上第一个不在 GORM 源码里的帧。

GORM 的终结方法 `DB.Scan` 是个例外。它在语句执行期间把句柄的 logger 换成 GORM 的记录器，记录器对 `ParamsFilter` 把值全数交回，方言于是把值填进文本，`Scan` 在语句执行完之后才把这段文本经 `Trace` 交给句柄原来的 logger：句柄上的 logger 在这条路上不被问到有哪些值要交，文本到手时值已在里面。

日志模块交付 `Logger` 功能，调用面是标准库的 `*slog.Logger`：记录经它的处理链写到装配配置的目的地，格式与级别由配置选定，登记的脱敏规则作用在每条记录的属性上。别的要写记录的模块——事件模块与入口模块即是——对这个功能声明可选依赖，装配没有交付它时回落到日志包的进程根 logger，那个 logger 固定写标准输出。

句柄上的 GORM logger 经标准库 `log` 往标准输出写时，写出的行不经日志模块的处理链，装配为日志配置的目的地、格式、级别与脱敏都管不到它。

## 考虑过的选项

### 维持 GORM 的默认 logger，写明它把值写到标准输出

**否决**：凭据与个人数据随每一次失败的写入落到标准输出，别的模块发出的语句宿主管不到；写明代价不给宿主任何避开它的途径。

### 用 GORM 自带 logger 的 `ParameterizedQueries`

语句不带值，其余照默认 logger。

**否决**：错误文本照样写出，PostgreSQL 与 database/sql 消息里的值跟着出去。在它外面包一层替换错误，调用点就报成包装层：包装层是第一个不在 GORM 源码里的帧，每一行都指向本模块的同一个文件。

### 用 GORM 自带的 slog logger

把日志模块的 `*slog.Logger` 交给 GORM 的 `logger.NewSlogLogger`，记录由 GORM 的实现构造并写出。

**否决**：它把失败语句的 `err.Error()` 原文写成 `error` 属性，错误文本里引用的值跟着出去；GORM 自己的消息，它把格式实参整个原样作为一个 `data` 属性交出，实参里的值不成为独立属性，落在脱敏的判定面之外（[ADR-log-redaction](adr-log-redaction.md)）。

### 靠日志模块的脱敏遮蔽语句里的值

语句照默认 logger 填好值写出，值交给日志模块的脱敏去遮。

**否决**：脱敏按登记的敏感键名与值形状改写属性，不判记录的消息（[ADR-log-redaction](adr-log-redaction.md)）；一条填了值的语句是一整段文本，里面的邮箱、姓名不在任何键下，也不是哪一种登记过的形状。值要遮得住，就不能先填进文本。

### 什么都不写

**否决**：失败与慢的语句在调用方之外不留下痕迹，慢语句的记录是宿主看得到一条语句慢的唯一途径。

### 把 logger 作为一项配置交出去

**否决**：默认值仍须不写值，旋钮只会多出一条把值写出去的路，要去掉的正是这条路。

### 一次性设置 GORM 的包级变量 `logger.RecorderParamsFilter`

GORM 的记录器问包级变量 `logger.RecorderParamsFilter` 里的函数要值，默认的函数把值原样交回；本模块打开句柄时把它换成不交回值的函数，`Scan` 的文本里便没有值，本模块的 logger 不必认出 `Scan`。

**否决**：包级变量对进程里的每个 GORM 句柄生效，宿主自己的句柄也在内，它们的 `Scan` 日志不再带值；宿主也设置同一个变量时，后设置的覆盖先设置的，本模块的保证无声地失效。

### 替换 GORM 的包级变量 `logger.Default`

GORM 的模式解析器直接用 `logger.Default` 报告解析不了的模型与签名不对的钩子；本模块打开句柄时把它换成经日志模块写出的 logger，这些行便进日志配置的目的地，经脱敏。

**否决**：包级变量对进程里的每个 GORM 句柄生效，宿主自己的句柄也在内，它们的消息改道；宿主也设置同一个变量时，后设置的覆盖先设置的，本模块无声地失效，或宿主的设置无声地被覆盖。迁移器在 `DryRun` 下自己用 `fmt.Println` 打印语句，不经这个变量，换了它也到不了。

### 维持 `Scan` 这条路的现状，把缺口写明

本模块的 logger 只处理 `ParamsFilter` 问到的语句，`DB.Scan` 执行的语句连值写出，缺口写在后果里。

**否决**：本记录要给的保证在一条常用的路上不成立：`pkg/settings` 与 `pkg/tenant/catalog` 的语句就经 `Scan` 发出。

### 维持经标准库 `log` 写标准输出

本模块的 logger 经标准库 `log` 往标准输出写，与 GORM 的默认 logger 同途：文本不带值，错误只写类别。

**否决**：这些行不经日志模块的处理链，装配为日志配置的目的地、格式、级别与脱敏都管不到它们：`outputs` 配到文件，它们仍落在标准输出。日志模块保证的只是经它的处理链写出的记录（[ADR-log-redaction](adr-log-redaction.md)）。

### 对日志功能声明硬依赖

`Requires` 里的 `Logger` 不标 `Optional`，装配里没有日志模块即启动失败。

**否决**：没有带日志的装配也要能启动，可选依赖的缺失是一种合法配置（[ADR-dependency-resolution](adr-dependency-resolution.md)）。日志模块排他交付 `Logger`，依赖闭包不展开排他的提供者，命令树上没有点名日志模块的命令因而没有它：示例宿主的 `migrate` 命令只点名数据库引擎，硬依赖会让它以缺提供者启动失败。

### 不声明依赖，装配后期再取

不在 `Requires` 里写 `Logger`，句柄交付之后——`Init` 或更晚的阶段——再取日志，设置与租户名册取用它即是这样。

**否决**：句柄上的 logger 在 `New` 里打开句柄时定下，交付之后改它会与在途的语句竞争，本模块不支持；在 `New` 里取，又要日志模块已经构造。没有依赖边时，构造次序由模块名的字典序决定，`db.postgres` 与 `db.sqlite` 都排在 `log` 之前，`New` 里的查找得到缺提供者，本模块按缺席回落到进程根 logger，装配带了日志也没有任何迹象。声明买下的是构造顺序。

### 从请求的上下文取 logger

GORM 把语句的上下文交给 `Trace`，本模块的 logger 用 `log.FromContext` 从中取 logger：注入过 logger 的请求路径上，语句的记录带着请求的关联字段。

**否决**：

- 要在有注入时用请求的 logger、没有时用本模块持有的 logger，就得分得出带注入的上下文与不带注入的上下文，公开接口分不出。上下文里没有注入过 logger 时，`FromContext` 交回进程根 logger（[ADR-log-context](adr-log-context.md)）；只经 `WithAttrs` 绑过属性的上下文交回的是从进程根 logger 派生的 logger，它不是进程根 logger，却仍在引导链上，写标准输出，按引导级别过滤。
- 注入的 logger 按原样取用，它绑定的 `module` 属性属于注入方，替换与撤下都够不到：语句的记录署的是注入方的模块名，不是本模块的。
- GORM 自己的消息里，回调注册表的移除、重复登记与替换，回调链编译失败，以及迁移器解析不了的模型，传给 logger 的是后台上下文，从中取到的总是进程根 logger。
- 同一个句柄上的记录因此分处配置的目的地与标准输出：带注入上下文的语句进配置的目的地，回调注册表的消息、回调链编译失败与迁移器解析不了的模型的消息，和没有注入的语句进标准输出。

### 本模块装上自己的 GORM logger，经日志模块写出：何时写照 GORM 的默认 logger，文本不带值，错误只写类别

**采纳**，见决策。

## 决策

采纳：本模块打开的每个句柄装上本模块自己的 GORM logger，经日志模块的 `*slog.Logger` 写出。

- 本模块对 `Logger` 功能声明可选依赖，`New` 在打开句柄之前取用它。日志模块交付了该功能时，取它按本模块名交出的 `Named` logger；装配没有交付它时，取日志包的进程根 logger 并盖上本模块名的 `module` 属性，因为记录的消息是通用的词，不盖戳的记录看不出出自哪个模块；查找以缺提供者之外的错误失败、或提供者没有交出 logger 时，启动失败。`Open` 建的句柄与交付的句柄共用这个 logger。
- GORM 的 Info、Warn、Error 与 slog 的同名级别一一对应：失败的语句写成 Error 记录，慢于 200 毫秒的语句写成 Warn 记录，`LogMode(logger.Info)` 下——`Debug` 即是——的每一条语句写成 Info 记录。
- 语句的文本与 GORM 自己的消息放在记录的属性里，不放进消息，因为脱敏判属性，不判消息。
- 记录的调用点与 GORM 的默认 logger 报的相同：记录自带这一帧，同时写成一个属性。
- 语句的文本在持有的 logger 表示会写这一级的记录之后才渲染。`DB.Scan` 除外：它让方言在询问 logger 之前就把语句连同值渲染成文本，不论记录写不写，随后把文本丢掉；值只在这一刻存在于内存里，不写到任何地方。

语句绑定的与读出的值不写：logger 对 `ParamsFilter` 不交回任何值，语句照 GORM 为日志渲染的文本写出，占位符不填。失败的语句不写错误文本，只写错误带着的、文本固定的类别：GORM 的查不到行、唯一约束与外键约束的哨兵，上下文的取消与到期，引擎给这次失败的代码——PostgreSQL 的 SQLSTATE、SQLite 的结果码；一个也不带时不写类别。本模块不为这个 logger 设配置项：记录写到哪里、从哪一级写、什么格式，是日志模块的配置。

GORM 的终结方法 `DB.Scan` 执行的语句不带文本写出：`Trace` 认出调用它的是 `DB.Scan`，这条路上的每条记录——失败的、慢的、`Debug` 会话里的——照写错误的类别、耗时、行数与调用点，语句的位置写一段固定的说明：语句因 GORM 在 logger 看到它之前已填入值而不写出。语句没有构造出来时，不写这段说明。认出在 `Trace` 之内完成，不设置 `logger.RecorderParamsFilter` 或 GORM 别的包级变量。只有这个终结方法在此列：`Row` 与 `Rows` 不换 logger，泛型接口 `gorm.G[T]` 的 `Scan` 方法是另一个函数，它们的语句经句柄的 logger 渲染，带占位符的文本写出。

## 后果

记录经日志模块的处理链写出：去向、格式与级别按装配的日志配置，登记的脱敏规则作用在记录的属性上。每个引擎上，本模块的 logger 为语句写的记录里没有一条语句绑定的或读出的值，接受的代价里写明的转手路径除外；GORM 自己的消息不在这项保证之内，也在接受的代价里写明。错误原样交给调用方，记不记、怎样脱敏由调用方决定。

**接受的代价：**

- 写出的格式是日志模块配置的记录格式，不是 GORM 默认 logger 的一行；PostgreSQL 的占位符照 GORM 的渲染写作 `$1$`。去向、级别与格式跟日志配置走：装配带着日志模块时，`outputs` 配成空表，这些记录不写到任何地方；级别高于 info 时 `Debug` 会话的语句不写，那些语句是 Info 记录；高于 warn 时慢语句也不写。
- 按记录解析标准输出的宿主会读到这些记录，它们的 `module` 属性是引擎的模块名，例如 `db.sqlite`。
- 语句的记录没有请求关联字段：本模块持有的 logger 不带请求的 logger 带的追踪标识、租户标识这类字段。带上它们的前提是日志模块先在公开接口上给出"上下文里有没有注入过 logger"的判断，这项决策不含这一步。
- `First`、`Take`、`Last` 查不到行按失败写出，连同整条语句，写成 Error 级别的记录，这类记录的量对告警可见。
- 导入 `pkg/db` 的每个宿主都带着已登记的日志模块，它在包初始化时把自己登记进进程级注册表。命令树宿主要在命令树上点名它才进参与集；不点名时，本模块的记录回落到进程根 logger，写标准输出，不产生失败信号，入口模块对日志功能的可选依赖有同一项代价。已登记对宿主还有这些后果：宿主向进程级注册表登记自己的名为 `log` 的模块，登记时因重名 panic；宿主的模块声明的输入项与日志模块声明的相同——`log.level`、`log.outputs`、旗标名 `log-level`——或其中一条路径的前缀或延伸，装配在收集清单时以 `ErrConfigConflict` 失败；配置文件里的 `log` 段，在没有别的途径带上 `pkg/log` 的宿主里会被当作没有模块声明的键拒绝，导入本模块之后被接受，而命令树不点名日志模块、入口又不取全部已登记模块时，它不被读取，写下的级别与目的地不起作用。
- 带了日志模块的装配里，日志模块先于本模块构造，停止与关闭的次序相反。没有依赖路径相连的模块之间的次序可能随这条边改变，这类次序本就不作保证（[ADR-lifecycle-shutdown-order](adr-lifecycle-shutdown-order.md)）。
- 可选依赖在对方在场时照常参与定序，于是交付 `Logger` 功能、自己又对 `db.Database` 声明依赖的模块——日志的目的地放在数据库里即是——经这条边与本模块成环，装配以 `core.ErrDependencyCycle` 启动失败，错误点名这个环。日志模块自己不依赖任何功能，本仓库里也没有这种形状的模块。
- 每条语句的记录写到日志配置的全部目的地，滚动的文件也在内；迁移文件的正文是语句文本，被写出的那条语句把它整份写进一条记录。
- 失败语句的错误文本不在日志里，它带着的被违反的约束名也不在；语句的文本在记录里，写着表名，`DB.Scan` 执行的语句除外，它的文本不写出。诊断要看调用方拿到的错误，记录里关于失败的原因只有类别，例如 `duplicated key not allowed, result code 2067`。
- `DB.Scan` 执行的语句不带文本写出：失败的、慢的与 `Debug` 会话里的那条记录只有类别、耗时、行数与调用点，语句要到调用点指的那一行去看。
- 语句文本里本来就有的东西——调用方写进 SQL 的字面量、拼进文本的值、迁移文件的正文——照写，`DB.Scan` 执行的语句除外：它整条不带文本。这些东西不是绑定值，本模块不解析 SQL，分不出文本里哪一段是值。
- GORM 自己的消息格式化成文本放进 `detail` 属性，脱敏的判定面只有这个属性；`detail` 里的细节是 GORM 自己的文本，数据已格式化在内，不受语句的记录所作保证的约束。这类消息按来源列举，这里只举例，不求穷尽：回调注册表的移除与重复登记（Warn）、替换（Info），回调链编译失败，迁移器解析不了的模型，`Row` 在 `DryRun` 下的不支持报告。GORM 报告的错误文本在 `detail` 里；迁移器解析失败的那一条还带着调用方交给它的那个模型值，字段取值连同失败的原因。没有绑定值或读出值、没有错误文本、没有 `DB.Scan` 的文本这几项保证属于语句的记录，不及于这些消息，脱敏链像判别别的属性那样判别 `detail`，不因它是 GORM 的消息而另有规则。
- 模型解析不了时，模式解析器自己往标准输出写报错的行，不经任何句柄的 logger，每次解析都写，一次迁移因而不止一行；到 `detail` 的只有迁移器随后的消息。受支持的用法里没有 `gorm info` 记录：回调注册表经根句柄的 logger 写日志，根句柄的 GORM 级别是 Warn，替换消息只有根句柄自己的 logger 被调到 Info 才写，那要改根句柄的配置，本模块不支持；`Debug` 与别的会话把级别调到 Info，回调注册表也不经它们。移除与重复登记是 `gorm warning` 记录。
- GORM 有几条路径不经任何句柄的 logger，日志配置的目的地、级别、置空的 `outputs` 与脱敏都管不到：模式解析器报告解析不了的模型与签名不对的钩子，经 GORM 包级的默认 logger，由标准库 `log` 写标准输出，文本写着失败的原因；`DB.Scan` 执行期间 GORM 的记录器顶替句柄，把 Warn、Error 交给 GORM 的默认 logger（它只写 Warn 及以上，Info 在那里被丢弃），期间经句柄的 logger 发出的 Warn 与 Error 因而落到标准输出，本仓库的代码走不到这里，只有宿主自己的回调经语句的 logger 写消息才会；`DryRun` 下的迁移器自己用 `fmt.Println` 打印每一条语句。
- 转手的 logger 在保证之外。GORM 的迁移器在 `DryRun` 下为一次迁移装上的 logger（`printSQLLogger`）内嵌 `logger.Interface`，不露出 `ParamsFilter`，把 `Trace` 转给原来的 logger，并自己用 `fmt.Println` 把语句的文本连同 GORM 填进去的值写到标准输出，不论有没有记录写出。宿主以 `Session(&gorm.Session{Logger: …})` 在自己的语句上装的包装，内嵌 `logger.Interface` 而不露出 `ParamsFilter` 的，在值的填入上与它相同。GORM 为这样的 logger 转手的每一条语句——不止 `Scan` 的——都先把值填进文本，本模块的 logger 收到的文本里就有值，`Scan` 之外的语句照写；转手若经包装自己定义的 `Trace`，`Scan` 的语句也认不出，同样连值写出。本仓库的代码不走这些路径。
- 语句的调用经过持有的 logger 背后的处理链：处理链里的 handler，或别的模块登记的形状匹配器，一旦 panic，就从语句的调用里 panic 出来，经 `Row` 或 `Rows` 发出的语句还会留下没有归还的连接。本模块不 recover 这样的 panic，别的模块经同一个 logger 写记录时也不 recover。
- 认出 `DB.Scan` 靠 GORM 内部一个函数的名字，GORM 把它改名或挪走，这条保护无声地失效，守着它的只有每个引擎上的日志用例。GORM 对 `logger.Interface` 或 `ParamsFilter` 的不兼容改动直达本模块。

## 失效条件

若 GORM 不再在把值填进文本之前询问 `ParamsFilter`，或把绑定值另经别的途径交给 logger，文本里的值要由本模块另想办法去掉。`DB.Scan` 就是这样一条途径，本模块认它靠的是调用 `Trace` 的函数名：GORM 把 `Scan` 改名或挪到别处，这条路上的语句就连值一起写出，除日志用例外没有哪一处报错；每个引擎上的日志用例经 `Scan` 发出绑定了值的语句，守着这个认出。GORM 让 `Scan` 也经 logger 的 `ParamsFilter` 渲染语句时，这个例外不再需要。

若日志模块的脱敏开始判定记录的消息，决策里把语句与 GORM 自己的消息放进属性而不放进消息所据的前提——脱敏只判属性——不再成立，要重新评估。若日志模块不再支持对它的功能的可选取用，本模块的可选依赖与回落随之失去依据。
