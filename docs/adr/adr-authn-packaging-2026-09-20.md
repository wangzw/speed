# 根包不登记模块，网关排他交付而校验后端并存

## 状态

已接受

## 背景

认证这个发布单元要同时容纳一个决定请求能否继续的网关（`Gate`），与任意多个各自绑定一种凭据来源的校验后端。既有产品的形态是并存而非替换：启用目录认证之后，内置口令表的登录仍然可用。网关与校验后端对排他性的诉求因此相反——一条中间件链上只容得下一个网关，校验后端有多少个都成立。

发布单元按功能划分，实现拆为子包，每个实现子包各登记一个模块（[ADR-module-packaging-2026-09-13](adr-module-packaging-2026-09-13.md)）。既有发布单元的各个实现子包是同一功能的互斥实现，都排他交付它，由消解选出本次生效的那一个。

排他是提供方对自身的声明，消解只针对排他交付（[ADR-module-enablement-2026-09-13](adr-module-enablement-2026-09-13.md)，架构不变量 10）。传播禁用那些声明排他且表态 `StateAuto` 的提供者，触发条件是该功能有提供者表态 `StateEnabled`；裁决看仍然启用的提供者里还有没有排他者。纯非排他的功能不进入消解，它的多个提供者照常并存。

登记随 import 发生，可用集是构建的产物（[ADR-module-registration-2026-09-13](adr-module-registration-2026-09-13.md)）。import 一个包即执行它的 `init`，该包登记的模块随之进入可用集。

宿主的依赖清单由它 import 的包精确决定。校验后端的外部依赖跟着凭据来源走，换一种来源就换一套：内置口令表只需一个口令哈希库，目录后端需要目录协议的客户端，自带凭据表的后端还要取用数据库功能。

配置输入项的清单收集自全部已注册模块，包含本次不会启用的那些；同一路径上的两份声明只要都被 import 就是冲突，且该冲突在收集阶段检出，早于排他消解。可能被同时 import 的多个实现因此必须各自划分输入项路径。

## 考虑过的选项

### 根包登记网关模块，后端子包各自登记

`pkg/authn` 既定义功能接口与身份类型，又登记网关模块；校验后端各住在子包，各登记一个模块。

**否决**：登记随 import 发生，而根包是每个后端子包与每一处读取身份的业务代码都要 import 的包——后端子包要实现根包定义的接口，业务代码要用根包的 `FromContext`。根包登记模块，这些 import 就都把一个 HTTP 入口层带进可用集，「本二进制有没有认证入口」不再由宿主自己的 import 决定。根包还要随之占用一个模块名与一个配置命名空间，而它是每个后端子包的编译前提，无从绕开。

### 网关与随发布单元交付的后端合成一个模块

一个模块同时承载网关与内置的校验后端，此外的后端另行登记。

**否决**：一个模块只有一份 `Requires`、一个配置命名空间与一次表态。自带凭据表的后端要取用数据库功能，与网关合成一个模块即让每一个要认证的宿主都必须装配数据库，该后端绑定的客户端库也一并落到每个宿主头上，与发布单元按功能划分、实现拆为子包相悖。表态只剩一次，也表达不出「这个后端的配置齐备、那个没有」。内置后端与其余后端的接入方式随之分成两条路，各自的表态、诊断与配置面都不同形。

### 每个校验后端各自排他交付网关功能

后端子包照既有发布单元的形状办：各自排他交付同一个功能，由消解选出本次生效的那一个。

**否决**：两个后端同时在场即为排他冲突，启动失败并点名双方。而多个校验后端并存是这个发布单元存在的前提，不是要被消解掉的冲突。

### 内置后端排他交付校验功能并表态 `StateAuto`

内置口令表声明排他并取默认表态，其余后端非排他且在配置齐备时表态 `StateEnabled`，借传播规则换取「配了目录认证，内置就让位」。

**否决**：并存形态需要的语义是「我是兜底的，别人来了我也继续在链上排最后」，而传播只表达得出「没人显式来我就独占，有人显式来我就整个退出」。这个折中实际的落法与意图不符。同侪显式启用时，内置被传播禁用，网关只看到其余后端，驱动照常推进、没有任何一处报错，唯一的信号是一行启动诊断——启用目录认证之后内置口令登录随之失效，与既有产品的形态相反。第三个后端同时在场时，只要仍然启用的提供者里没有一个表态 `StateEnabled`，传播就不触发，裁决随即因为其中混着一个排他声明而判 `ErrExclusiveViolated`，整组启动失败。让传播表达出「兜底提供者」这一档要改写消解算法，而那套算法是 [ADR-module-enablement-2026-09-13](adr-module-enablement-2026-09-13.md) 的决策本体，为一个发布单元的需要改它，代价落在全部模块头上。

### 根包不登记，网关排他交付而校验后端一律非排他

**采纳**，见决策。

## 决策

采纳：`pkg/authn` 根包是接口包，不登记模块，也不导出模块名常量；网关与每个校验后端各住在自己的子包，各登记一个模块，各导出自己的 `ModuleName` 常量。

网关的交付声明为 `Provides: []core.Provision{{Token: (*Gate)(nil), Exclusive: true}}`。校验后端交付 `Verifier`，`Exclusive` 一律留空。

该决定附带的约束是下面这些。

- 网关的表态只能是 `StateEnabled` 或 `StateDisabled`，不得为 `StateAuto`。
- 每个校验后端必须声明 `Prepare`。未声明 `Prepare` 的模块等同于表态 `StateAuto`，它对自己那份配置的第一次读取因此推迟到 `New`，而那时已经没有表态可退，缺配置的表现从安静退让变成启动失败。
- 每个校验后端各挂自己的 `authn.<后端>` 配置命名空间。
- 自带凭据表的后端自己声明对数据库功能的构造期依赖；接口包不依赖数据库。

## 后果

「本二进制有没有认证入口」由宿主是否 import 网关子包决定。读取身份的业务代码 import 接口包，不因此把任何模块带进可用集。

网关的唯一性由消解强制：两个模块都排他交付这个功能必定启动失败并点名双方，认证层自己不必再防这件事。

多个校验后端并存是正常形态，不需要任何人编排。消解对纯非排他的功能不做任何事——不禁用、不去重、不报错、不排序。

依赖清单按后端裁剪：只 import 内置口令表的宿主，依赖图里不出现目录协议的客户端，也不需要数据库功能的任何提供者。

每个后端有自己的模块名与配置命名空间，它在启动诊断与启用结果查询中的身份因此是唯一的，同时 import 多个后端也不会在输入项清单的收集阶段撞车。

**接受的代价：**

- **网关的表态不得为 `StateAuto`，而这条约束没有任何机制强制。** 排他加 `StateAuto` 正是传播要禁用的那一格：另一个模块交付同一个功能并表态 `StateEnabled` 时，网关被传播禁用，它的 `New` 与 `Init` 都不执行，驱动没有任何一处报错，整端无认证放行，唯一的信号是一行启动诊断。排他声明拦不住这件事——另一方同样声明排他时，被禁用的仍然是取默认表态的那一方；拦得住的是表态：网关显式表态 `StateEnabled` 之后，同一装配在消解阶段即失败于 `ErrExclusiveViolated` 并点名双方。「链上只有一层」在网关被顶掉之后仍然成立，不成立的是「那一层是网关」。
- 「后端子包的 `Exclusive` 必须留空」同样是一条纸面规则。任一后端写成 `true`，同侪取默认表态时整组启动失败，同侪显式启用时它自己被传播禁用而不报错。一个子包因此能单方面决定同一发布单元里其余后端的命运。
- 校验后端的在场性不由消解或依赖解析保证。非排他的功能有零个提供者不是错误，而网关不声明构造期依赖（[ADR-authn-wiring-2026-09-20](adr-authn-wiring-2026-09-20.md)），`Verifier` 因此不出现在任何 `Requires` 里，一个后端都没有纳入时机制一声不吭。判空落在网关自己身上。
- 后端之间没有机制赋予的次序，也没有机制赋予的身份。非排他的多个提供者只能整体取出，取回的实例不带模块名（架构不变量 9 与 10），谁认领哪些主体、一次认定该归给谁，要由功能接口自己回答（[ADR-authn-ownership-2026-09-20](adr-authn-ownership-2026-09-20.md)）。
- 一个发布单元登记多个模块，宿主要在命令树上逐个列举它们。未被本次命令纳入的模块（本记录据此推断它不进启动诊断，这是推断而不是引自架构文档的条文：诊断要写的原因——表态禁用，或消解落选——在一个连表态都没有的模块身上无从写起），启用结果查询也给不出结果——宿主 import 了某个后端却没有在命令树上列举它，机制一声不吭。自带凭据表的后端还必须被执行迁移的那条命令纳入、并在该命令下表态启用，它的表才建得出来；只在提供服务的那条命令里纳入不够，漏了不报错，表现为运行期的查询失败。

## 失效条件

若消解规则演进出「兜底提供者」这一档——声明排他的默认实现在别人显式启用之后仍然留在提供者集合里，而不是整个退出——则「校验后端一律非排他」不再必要，本记录对后端排他性的约束不再适用。
