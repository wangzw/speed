# 发送能力的载体由运行期选择项决定，日志载体是保底

## 背景

邮件与短信两个发送能力各有多个载体实现，而一个进程只能有一个生效的载体：两个同时发送会让调用方无从知道消息走了哪一家，也会把同一条消息投递两次。载体能不能启动取决于三件彼此独立的事：二进制里有没有它，这次部署有没有把它配置齐，这次运行有没有选中它。前两件已经由“编译期定上限、运行期模块自决”的启用机制承接（[ADR-module-enablement](adr-module-enablement.md)），第三件没有表达的地方。

约束如下：

- **编译期不挑选载体。** 用 build tag 决定哪个载体进二进制，会让构建矩阵随载体组合增长，并让本地走查需要一个与部署不同的二进制。
- **没有配置任何厂商载体时，通道仍要可用。** 一个刚拷贝出来、还没填 SMTP 或短信厂商凭据的部署，若邮件验证码或短信登录因此无法启动，装配就会停在“必须先有外部账号”上。
- **本地走查要从进程日志读验证码。** 这条通道不能只存在于为走查或测试另编的构建里，否则同一个能力在不同构建里的载体集合不同。
- **写错载体名、同时启用两个载体必须报错。** 一个拼错的 `mail.carrier` 若被当成“没有载体”，能力会安静地关掉，依赖它的模块随之关闭，排障只能从启动诊断里猜；两个载体同时启用若只报通用的排他冲突，读者还得自己找出是哪两个模块。
- **`Prepare` 阶段没有顺序，也读不到别的模块的表态。** 载体之间无法在 `Prepare` 里互相协调谁运行。

## 考虑过的选项

### 用 build tag 在编译期选载体

一种构建只含一个载体，由 tag 决定。

**否决**：构建矩阵随载体组合增长；本地走查用的日志载体只能进一个走查专用的构建，于是这个构建与部署构建的能力集合不同，正是“编译期是上限、运行期自决”要消除的差别。

### 每个载体只判自己的配置，没有显式选择项

一个载体配置齐了就运行，配置不齐就关闭，靠排他声明解决并存。

**否决**：无法表达“彻底不要这条通道”；一个拼错的未编入载体名和“没有配置”无法区分，都会安静地关掉能力；两个载体同时启用只能得到通用排他错误，错误不点明这是载体的选择出了问题。

### 由一个选择模块统一裁定，载体向它读结果

每个能力注册一个选择模块，持有选择项并在 `Prepare` 里决定哪个载体运行，载体从它取结论。

**否决**：`Prepare` 不保证顺序，也不暴露别的模块的 `Prepare` 结果；载体要拿到结论就得让每个载体重复计算同一份判断，或引入一个 `Prepare` 阶段尚不存在的实例。裁定点并没有消失，只是多了一层模块。

### 显式选择项加共享的载体名声明，保底交给排他消解

每个能力有一个选择项，每个载体声明自己的选择名；选择项为空时由载体自判配置，日志载体声明为可自行退出的保底提供者，由 core 的排他消解在另一载体显式启用时让它退下。

**采纳**，见决策。

## 决策

采纳：**邮件与短信各有一个显式选择项，日志载体编译进所有构建并在没有其它载体时保底运行。**

- **选择项是 `mail.carrier` 与 `sms.carrier`。** 取值是一个已编入载体的选择名，或 `none`，或空。空表示自动选择：配置齐的载体运行；没有配置齐的载体时日志载体保底。
- **每个载体声明自己的选择名。** 工厂把 `CarrierName{Name}` 作为资源挂到模块上，`Prepare` 由它得知这次二进制里编译了哪些载体。
- **`none` 彻底关闭能力。** 所有载体都关闭，日志载体也不保底；能力没有提供者，依赖它的模块在 `Prepare` 里读同一个选择项并自行关闭：邮件验证码、短信验证码状态机、模板注册表、管理面以及短信登录与短信第二因素。
- **未编入的载体名是错误。** 选择项给出一个没有任何已编入载体回答的名字时，每个载体的 `Prepare` 返回 `ErrInvalidConfig`，错误点名该名字、能力与这次二进制携带的载体名。
- **未配置与半配置分离。** 一个载体的配置项全都为空是“未配置”，载体以 `StateDisabled` 关闭并给出原因；一部分给了、一部分没给是“半配置”，`Prepare` 返回 `ErrInvalidConfig` 并点名缺的项。选择项点名某载体时，该载体必须可运行，否则同样是错误；未被点名的载体不判自己的配置。
- **两个载体同时启用是排他冲突。** 选择项为空而两个载体的配置都齐时，两者都显式启用，core 的排他消解失败并点名两个模块。日志载体以 `StateAuto` 参与，任何显式启用的载体都会让 core 把它搁下，所以保底只在没有其它载体时生效。
- **日志载体编入所有构建。** `mail.log` 与 `sms.log` 是普通能力模块，不是只为测试编译的支持代码；它们把消息写进进程日志并在启动时打一条警告，说明这条通道会把正文与验证码写进日志。选择项本身由日志载体声明，因为它保证出现在每次构建里。
- **配置层的 `Required` 不再用于载体身份项。** 未编入本次运行的载体也会参与配置清单与 `Prepare`，若身份项仍声明 `Required`，一个没配置的厂商载体会让整个装配失败。必填判断因此移进载体的 `Stance`，并按“全空 / 半空 / 齐全”三档处置。

## 后果

同一个二进制可以按部署配置选择载体、关闭整条通道，或在没有厂商配置时落在日志通道上。选择错误在启动期被点名，而不是表现为能力悄悄消失。

**接受的代价：**

- **日志载体把消息正文写进日志。** 这是它存在的目的，也是它必须在启动时告警的原因；一条验证码随日志采集或导出离开机器，是选择这条通道的部署接受的代价。
- **配置层的必填标记从载体身份项上消失。** 缺项不再由加载器统一拒绝，而由每个载体的表态逐个判断；新增一个载体要同时写好自己的三档判断。
- **选择项由日志载体声明。** 一个只 import 厂商载体、不 import 日志载体的二进制接受不了选择项，只能自动选择唯一配置齐的载体；要在配置里显式选择，就必须同时编入日志载体。
- **日志载体的选择名是保留的。** `log` 不能再用作厂商载体的选择名，否则两个载体回答同一个名字。
- **`Spec` 增加三个字段。** 载体的工厂规格多出选择名、保底标记与选择项声明标记，每个载体都要填写。

## 失效条件

若 core 将来提供一种“默认提供者”的一等声明，或启用机制能让模块在 `Prepare` 之前读到彼此的裁定，那么选择模块或保底标记的这套约定可以收回，改为机制本身承担。

若选择需要按租户、按目的地或按消息类型分流，而不是一个进程一个载体，那么单一选择项不再够用，需要重新设计路由。
