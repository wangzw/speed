# 通知能力做站内信收件箱、渠道偏好矩阵、类型分类法登记接口、出站投递流水线与实时推送，同意台账刻意后置且不声明权限点

## 背景

通知能力回答一件事：一个业务模块产生了一件值得告知某个用户的事，把它送到这个用户看得见的地方。这件事由几段互不相同的机制承接——站内信是写一行、出站渠道是调用外部厂商、实时推送是一条长连接——它们共享同一份类型词表与同一份渠道偏好，但不共享状态。

约束如下：

- **一条通知必须有类型。** 收件箱按类型分组与过滤，渠道偏好按类型记，投递按类型校验与去重。类型是业务词汇，由发出它的模块声明（[ADR-notification-taxonomy](adr-notification-taxonomy.md)）。
- **渠道是封闭的平台词汇。** 站内信、邮件、短信三值，业务模块只能从中挑选（[ADR-notification-channels](adr-notification-channels.md)）。
- **出站投递要异步、要能重试。** 邮件与短信的厂商调用慢、可能失败、超时之后无从知道是否已送达（[ADR-notification-delivery](adr-notification-delivery.md)）。
- **实时推送要低延迟，且它是延迟优化而非正确性依赖。** 收件箱是持久表，使用方回读即得（[ADR-notification-stream](adr-notification-stream.md)）。
- **有一类常与本能力并提的需求，其对象不是本系统的用户。** 向非用户的外部联系人发消息，要先取得并维护其同意：验证联系方式、记录按类型的退订、维护平台级黑名单。这类记录的主语是外部联系人，其取得、验证与合规生命周期与本能力的上表、状态机、路由都不同。
- **谁可读某个收件人的收件箱，是宿主侧对一个资源与动作的判定。** 本能力交付收件箱的内容与路由，不交付「谁可以问」的判定。

## 考虑过的选项

### 把非用户外部联系人的同意台账一并做

在同一能力内建 `verified_contacts` 表与 `contact_type_unsubscribes` 表、平台黑名单，并挂一组 `/contacts` 路由（声明、验证、重发、列表）。

**否决**：范围膨胀；同意台账的对象是外部联系人，一条联系方式的验证、一份按类型的退订、一条平台黑名单的合规维护，与收件箱的行、已读数、分组各自描述不同之物，两者不共享表、不共享状态机、不共享路由的授权语义。把它并进来会让本能力的每次改动都要同时回答两类生命周期各自的问题。

### 给路由声明自有权限点

本能力用 `authz.PermissionSpec` 声明自己的权限点，每条路由带一个自有的权限闸，判定「谁可读某个收件人的收件箱」。

**否决**：谁可读某人的收件箱是宿主侧的资源与动作判定，模块替宿主发明权限会让每个使用方都得为它编一条。同一个收件箱是否是「当前用户自己的」，取决于宿主如何把身份映射到收件人；本能力不持这份映射，也就无法给出一个跨宿主都成立的权限点。

### 做本能力的机制，同意台账刻意后置，不声明权限点

**采纳**，见决策。

## 决策

采纳：**本能力做站内信收件箱、渠道偏好矩阵、类型分类法登记接口、出站投递流水线与 SSE 实时推送；非用户外部联系人的同意台账刻意后置；本模块不声明任何权限点。**

- **站内信收件箱。** 一张 `in_app_messages` 表、写行、查、未读数、标记已读，以及其上的路由（`notification.inbox`）。
- **渠道偏好矩阵。** 一张 `notification_preferences` 表，按（收件人，类型）记渠道集；它同时是类型分类法的消费点（`notification.preferences`）。
- **类型分类法登记接口。** 类型由业务模块以资源声明，本能力经 `core.Resources` 收齐并把 `/types` 与 `/preferences` 暴露出来。
- **出站投递流水线。** `Dispatcher.Dispatch` 把这条投递入队为一条作业，消费时逐渠道发送、落账（`notification.delivery`）。
- **SSE 实时推送。** 每副本一个 Hub，订阅收件箱创建事件，经 `/stream` 推给已连接客户端（`notification.stream`）。
- **同意台账刻意后置。** `verified_contacts` 表、`contact_type_unsubscribes` 表、平台黑名单，以及 `POST /contacts`、`POST /contacts/:id/verify`、`POST /contacts/:id/resend`、`GET /contacts` 一组路由，本轮不落地。这一条是刻意的，不是漏项：`RecipientClass` 的 `external` 取值留在闭集里但本轮没有生产者，`notification.contact.*` 一组审计动作本轮不声明。
- **不声明权限点。** 本能力的路由不带自有权限闸；谁可以读某个收件人的收件箱由宿主侧的授权决定。

## 后果

范围可以从设计文档逐段读出：站内信收件箱、渠道偏好矩阵、类型分类法登记接口、出站投递流水线与实时推送各有自己的模块与表，同意台账的一组表与路由不在其中。

**接受的代价：**

- **后置的部分不落地，向外部联系人发消息的合规通路在本能力内不存在。** 需要它的宿主要在本能力之上另建一层，自行持有联系方式的验证与退订状态。
- **`RecipientClass` 的 `external` 与 `notification.contact.*` 一组审计动作是本轮的死取值。** 它们在契约里定义、没有生产者，读者要读本记录才知道它们为何在。
- **不声明权限点，接入的每个宿主各自落地「谁可读收件箱」的授权。** 两个宿主可以给出不一致的答案，本能力不提供统一判定，也不拦截一个缺乏授权的接入。
- **分组与过滤以类型词表为界，跨出该词表的通知不受本能力约束。** 一个不走类型分类法的通知没有可校验的类型，本能力无从记录它的偏好或去重。

## 失效条件

以下情形出现时，本决策需要重议：

- 若出现第二个需要向外部联系人发消息的宿主，且它要求的同意维护（联系方式的验证、按类型的退订）与本能力已有的渠道偏好结构相近，则「同意台账是独立能力」这一判据要重新检验。
- 若宿主侧的授权普遍表达不了「读自己的收件箱」这类资源与动作判定，则「权限归宿主」这条的前提改变。
