# 主体持有的权限由策略模块读出，并经一条自身路由回答

## 背景

授权引擎一次回答一个问题：某个主体在某个域里能否对某个（资源，动作）做某件事。宿主还需要另一个答案——这个调用方实际持有哪些权限——用来决定界面显示什么、哪些入口可用。没有这个读取时，宿主只能猜：演示程序把整个权限目录当作已持有，于是每个调用方都看见每一项权限，而目录回答的是「哪些权限可以被授予」，不是「谁持有什么」。

策略数据是（域，角色，资源，动作）的 grant 与（域，账户，角色）的 binding，权限名只是词表。要把一个主体持有的（资源，动作）对翻回权限名，需要目录的反向查找；要让宿主自己拼出这个答案，它要遍历目录、逐个问引擎，并在自己的代码里再维护一份反向映射。

这条读取属于调用方自身，因此任何已认证调用方都必须能读到，不能要求一项权限：要求权限的路由只能被已经持有该权限的调用方走到，而「是否持有」正是这条读取要回答的问题。

## 考虑过的选项

### 宿主侧逐个询问引擎

宿主枚举 `Catalog.Declared()`，对每个权限调用 `Enforcer.Allowed`，把为真的权限拼成答案。

**否决**：一次读取要跑与目录规模相同的判定次数，且每个宿主都要自己把权限名翻成（资源，动作），再反向判断结果；同一份逻辑会在每个宿主里各写一遍，写法稍有不同就得到不同的答案。引擎的隐式权限查询本来就返回主体持有的全部规则，逐个询问是把一次读拆成多次判定。

### 把目录当作已持有的权限集

把 `Catalog.Declared()` 直接当作调用方持有的权限回答。

**否决**：目录是词表，不是持有关系。它会把每一个已登记的权限都报成已持有，正是这套读取要修掉的错误；目录还刻意不按本进程运行哪些模块收窄，因此连没有服务入口的权限也会出现。

### 策略模块交付读取，自身路由只读

在根包新增 `SubjectPermissions`，由策略模块排他交付；`Held` 读判定所用的同一份内存快照，取引擎的隐式权限（主体绑定角色所持 grant 的并集），再经目录的反向查找映射回权限名。新增 `authz.self` 模块把它挂成 `GET /api/v1/authz/me/permissions`，返回平台域与请求所属租户域两个列表。

**采纳**，见决策。

## 决策

采纳策略模块交付的主体持有权限读取，以及把它暴露成 HTTP 的 `authz.self` 路由。

读取是根包的一条排他能力 `SubjectPermissions.Held(ctx, domain, subject)`；它读进程内快照，不做 IO，结果按权限名排序、去重，没有声明权限翻译到的（资源，动作）对略去。快照未装载或引擎报错是 `ErrPolicyUnavailable`，调用方按 503 处置，不视为空集。

路由 `GET /api/v1/authz/me/permissions` 要求已认证、不要求权限，在路由声明表上登记为开放；回答 `{ "platform": [], "tenant": [] }`，平台列表取平台域，租户列表取请求解析出的租户，没有租户时为空列表。它挂在配置 `authz.self.endpoints` 列出的端上。

## 后果

- 根包的接口新增 `SubjectPermissions`，策略模块的交付接口新增一项排他能力；第二个提供方使启动失败。
- 每条读取在平台域与请求租户域各查一次快照，两次都是内存读，不产生数据库访问。
- 回答是权限名的并集，不解释「为什么」：它不说某个权限来自哪个角色，也不按资源收窄；需要这些内容的读取是另一个决定。
- 一条 grant 的（资源，动作）对若没有被任何声明权限翻译到，它不会出现在回答里。写入方因此要先声明权限与翻译行，授权才读得回来。
- 路由本身不带权限判定。它必须挂在网关所守的端上；挂在没有网关的端上时，只剩下 handler 写出的无身份 401，任何已认证调用方都能读自己的权限——这正是这条读取的语义，不是缺口。
- 新增的路由与应答结构进入对外接口，生成的契约文档与客户端要随重新生成更新。
- 管理面之外多了一个读策略数据的 HTTP 接口；它的写入接口仍然只有 `Manager` 与管理面路由。

## 失效条件

宿主需要按资源收窄的权限列表，或需要说明一项权限来自哪个角色时，这条读取的回答不够用；届时它要么被扩展，要么被另一条读取取代，而本记录不再描述新增的形态。
