# 租户解析、租户名册与数据隔离同属一个发布单元，设置与权限另立

## 状态

已接受

## 背景

已落地的文档把若干判定推给一个尚未存在的模块，每一处给承接方起的名字都不一样，也没有一处说明承接它们的是一个发布单元还是几个。

数据库模块不认识租户，把租户隔离推给"租户模块"，并规定承接方定义自己的模型约定、声明自己的插件（[ADR-db-scope-2026-09-14](adr-db-scope-2026-09-14.md)）。日志模块规定关联字段由产生它的模块在自己的注入点绑定，并把租户标识点名为这样的字段之一（[ADR-log-context-2026-09-13](adr-log-context-2026-09-13.md)）。配置模块把按租户取值的参数一律判给设置一侧（[ADR-config-scope-2026-09-13](adr-config-scope-2026-09-13.md)）。入口模块把租户与认证、限流并列为各自模块的事，自己不内建任何一层（[ADR-http-middleware-2026-09-14](adr-http-middleware-2026-09-14.md)）。

中间件的排序把认证立为可被指向的功能，并规定按身份分支的层位于认证之后（[ADR-http-middleware-2026-09-14](adr-http-middleware-2026-09-14.md)）。租户解析是不是这样一层，此前没有任何一处裁过；这条空白在认证模块落定时被补上，它把租户解析点名为以认证为锚点的层，落在认证之内（[ADR-tenant-ordering-2026-09-21](adr-tenant-ordering-2026-09-21.md)）。

认定一个请求属于哪个租户，与让每一条语句都带上这个租户，与记住这个租户还在不在，所需的输入不同。解析要的是请求面，隔离要的是每一条语句的拦截点与模型的声明，名册要的是一张表与它上面的状态。发布单元按功能划分，是版本与发布的粒度；把一种能力升格为独立的发布单元需要举证，成立条件是它有独立的发布节奏，或者消费者会脱离它所属的发布单元单独取用它（[ADR-module-packaging-2026-09-13](adr-module-packaging-2026-09-13.md)）。

## 考虑过的选项

### 解析、名册与隔离各成一个发布单元

租户的认定、名册的维护与语句的过滤各由一个发布单元承载，三者之间经跨发布单元的功能接口取用。

**否决**：升格所需的举证不成立。隔离的输入是"当前租户"，而当前租户只由解析产生；名册的唯一读者是解析与隔离。把其中任何一个升格，都没有独立的发布节奏支撑，也没有一个消费者会脱离其余单独取用它。拆开还多出一种失败形态：隔离可以在一个没有任何解析层的进程里安装成功，声明方拿到的信号与生效时完全一样——插件的安装不看它依赖的东西在不在。

### 隔离并入数据库模块

数据库模块内建按租户过滤，模型带上约定的声明即自动生效。

**否决**（[ADR-db-scope-2026-09-14](adr-db-scope-2026-09-14.md)）：租户标识产生于依赖图上层的模块，数据库模块反向依赖它们会成环；把它下沉到数据库模块自己定义，则每一个需要租户标识而不访问数据库的模块都要为取得一个标识而 import 数据库模块；该选项还替每一个宿主决定了它是多租户的，单租户应用同样要带着这套概念和它施加的模型约定。

### 解析并入认证发布单元

租户的认定由 `pkg/authn` 一并交付，身份的认定与租户的认定在同一层里完成。

**否决**：认证的边界判据是判定所需的输入——只需凭据与主体来源的归它（[ADR-authn-scope-2026-09-20](adr-authn-scope-2026-09-20.md)）——而租户解析凭据与主体来源两样都不要。身份的类型字段不导出、只能由判决盖章产生，在它上面加一个租户字段等于要求每一个校验后端回答租户问题。认证的接口包自我约束不依赖 `pkg/db`（[ADR-authn-packaging-2026-09-20](adr-authn-packaging-2026-09-20.md)），而名册在库里，并进去就把数据库依赖推给每一个只要认证的宿主。豁免路由上没有身份，而登录、注册、探活这些最需要知道租户的路由恰恰走在豁免上。

### 租户与设置、权限同属一个发布单元

租户的认定与名册、按租户取值的参数、按租户的授权判定合在一个发布单元里。

**否决**：与认证模块拒绝与权限合并同源。权限判定要认识资源、动作与策略，设置要一套存储与一条变更通道，合并等于替每个只需要租户的宿主选定它们的约定与输入项，并让策略模型与设置形态的每次演进都推动租户的版本。

### 解析、名册与隔离同属一个发布单元，设置与权限另立

**采纳**，见决策。

## 决策

采纳：`pkg/tenant` 交付租户的认定、名册的维护与按租户的语句过滤；按租户取值的参数归设置模块，按租户的授权判定归权限模型，两者另立。

**判据是判定所需的输入。** 本发布单元回答"这条请求、这条语句属于哪个租户，以及这个租户还在不在"；回答"这个租户的这个参数取什么值""这个租户能不能做这件事"的归别处。

名册随解析与隔离同属，因为隔离判得出停用要读名册，而解析判得出一个名字是否有效也要读名册；名册不落地的形态下，两条路径各自去问一个由宿主实现的东西，停用的语义就散在各宿主那里。

本发布单元不从设置取任何值：它的每一项输入都在 `Prepare` 中被 `Decode`，而在那一刻数据库尚未可用（[ADR-config-scope-2026-09-13](adr-config-scope-2026-09-13.md)）。名册不在配置里：配置是启动时的快照，而租户的增删是运行期动作（[ADR-config-lifecycle-2026-09-13](adr-config-lifecycle-2026-09-13.md)）。

## 后果

推让有了同一个承接方。数据库模块的"租户模块"、日志模块点名的租户标识产生方、入口模块并列的租户一层，至此指同一个发布单元。

只需要请求面租户解析的宿主不存在：本发布单元带着名册，取用它就要落一张表。名册是隔离得以判定停用的前提，也是解析得以判定一个名字有效的依据，两者都离不开它。

设置与权限的演进不推动本发布单元的版本，本发布单元也不承受它们的约定与输入项。

**接受的代价：**

- 判据落在输入上，而新出现的判定未必一眼看得出落在哪边。一种判定先按租户实现、后来才发现它要读一份策略，改归属就是一次跨发布单元的搬迁。
- **"租户内的用户"与"租户"容易被混为一谈。** 用户是主体与它在租户内的身份，归认证的校验后端；租户是数据归属的单位，归本发布单元。误读的形态是把用户表建进本发布单元。
- 本发布单元同时出现在入口模块与数据库模块之上，它的登记单元因而跨两个接缝。这一条的减轻落在 [ADR-tenant-packaging-2026-09-21](adr-tenant-packaging-2026-09-21.md)。
- 名册使本发布单元依赖数据库功能，而数据库功能是可选的：一个只要租户认定、不落库的装配取不到本发布单元。

## 失效条件

若出现一种租户判定，它既不读请求面也不作用于语句，而是在进程启动之前就已经确定——例如按部署实例静态绑定的租户——则"解析要请求面"这一前提不再覆盖它，本发布单元的交付面需要重新裁定。
