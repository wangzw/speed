# 渠道是封闭的平台词汇，可用性由装配决定，接缝缺席时跳过而不失败

## 背景

一条通知经一个或多个渠道送出。站内信、邮件、短信这三类渠道的实现分属不同的能力：

- **站内信**由本能力自己写一行。
- **邮件**经邮件接缝发送（`pkg/mail` 的 `Sender`）。
- **短信**经短信能力发送（`pkg/sms` 的 `Registry` 与 `Sender`）。

收件人必须能按类型调整渠道偏好，以业务模块为该类型声明的默认渠道集为起点（REQ-notifications-009、REQ-notifications-010）；声明与调整都不决定「如何发一封邮件」。渠道词表因此由本能力定义，而渠道的实现由各能力交付。

约束如下：

- **装配不必装齐所有渠道。** 一个只装站内信的部署没有邮件与短信接缝，业务模块却仍会声明一个含 `email` 的默认渠道集，收件人也仍可能把它调成含 `email`。
- **偏好矩阵按（收件人，类型）记渠道集**，渠道取值来自业务模块的挑选与收件人的调整。
- **每条投递的结果要落账**（[ADR-notification-delivery](adr-notification-delivery.md)），账上的结果是封闭集 `succeeded` / `failed` / `skipped`。

## 考虑过的选项

### 把渠道做成开放的扩展点，让业务模块注册自己的渠道

本能力只定义「渠道」这一接口，业务模块各自实现并注册自己的渠道（例如某个业务自己的移动推送）。

**否决**：渠道的实现（邮件、短信）是平台能力，放开会把发送实现散到各处；渠道的可用性判定、去重键的构造、结果账的落法都要在模块之外定义，本能力无从保证它们一致。每新增一个渠道还要所有人重新编译并重新理解渠道词表。

### 把不可用渠道当作失败

一次投递遇到一条偏好里的渠道，而该渠道的接缝不在本次装配里时，记一条 `failed`。

**否决**：只装站内信的部署不该因为偏好里有一条 `email` 而把每次投递记成失败。失败会累积、会进账本与告警，而它表达的不是一次真实的发送失败，是一条本部署装不上的偏好；把两者记成同一种结果，运维从账上分不出「厂商拒了」与「本部署没有这个渠道」。

### 渠道是封闭的平台词汇，可用性由装配决定

**采纳**，见决策。

## 决策

采纳：**渠道是封闭的平台词汇；业务模块只能从中挑选，不能扩展；渠道的可用性由装配决定，接缝缺席时该渠道不可用，投递时跳过并落一条 `skipped` 结果，不当作失败。**

- **词表是闭集。** 渠道取值为 `in_app`、`email`、`sms`，由 `notification.Channel` 的闭集给出，`notification.KnownChannel` 判定取值是否在集内。加一个渠道是本能力自己的变更，不动业务模块。
- **可用性判据。** `in_app` 恒可用；`email` 要邮件接缝（`pkg/mail` 的 `Sender`）在场；`sms` 要短信注册表与发送接缝（`pkg/sms` 的 `Registry` 与 `Sender`）在场。判据取「本次装配是否取到该接缝」，不取「偏好里是否提到它」。
- **接缝缺席的处置。** 一条投递展开时，落在不可用渠道上的那一项不进入发送路径，落一条 `skipped`（`notification_sends` 的 `status` 取 `skipped`），发一条带有渠道名的提示。其余可用渠道照常发送。
- **偏好里出现一个取值不在词表内的渠道即拒绝**（`ErrUnknownChannel`），这发生在写入偏好时，与可用性无关。

## 后果

渠道的取值集不因宿主装配而增减：一份偏好在一个只装站内信的部署上、在装了邮件的部署上表达同一件事。落地结果因装配而异，而落地结果记在结果账上。

**接受的代价：**

- **新增一个渠道是本能力的变更。** 业务模块不能在通知模块之外加一个渠道；一个只对某个业务有意义的渠道，要么并入平台词表，要么在通知模块之外自行发送。
- **同一条偏好在不同装配上得到不同的落地结果。** 在一个只装站内信的部署上得到 `skipped`，在装了邮件的部署上得到一次真实发送；两个部署对同一条偏好的观察不同。
- **`skipped` 与 `succeeded`、`failed` 并列进结果账，消费方要多区分一种结果。** 一次投递里「本部署没有这个渠道」与「本部署有这个渠道、发成功了」在账上是两行不同结果。

## 失效条件

以下情形出现时，本决策需要重议：

- 若出现一种渠道，其实现既不是平台能力、又必须由某个业务模块提供（例如某个业务自己的移动推送），则「渠道是平台词汇」这条要重议。
- 若宿主需要「偏好里写了一个本部署永远装不上的渠道」在启动期失败，而不是每次投递落一条 `skipped`，则「可用性由装配决定、接缝缺席即跳过」这条要重议。
