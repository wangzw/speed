# 入口模块定义默认的错误响应结构，并经可选接口接受定制

## 背景

请求路径上的各层收口各自的拒绝：认证网关写 401，限流层写 429，租户解析层写 404 与 500，兜底层写 500。它们各自调用 `WriteHeader`，没有共用的响应结构，同一个 API 的客户端要为每一类拒绝分别处理。认证、租户、审计各自处理 panic 而口径互不一致，已在 [ADR-http-recovery](adr-http-recovery.md) 的背景里记过一次；错误响应是同一类分歧的另一处。

登记接口锚定 gin（[REF-gin](../references.md)）（[ADR-http-surface](adr-http-surface.md)）。gin 把错误交给 handler 自己写出，不定义统一的错误响应结构，也没有集中的错误处理接口。

兜底层是引擎上的一个 gin handler，手里有 `*gin.Context`。写出仍经同一个接口：`ErrorResponder` 的签名只取 `http.ResponseWriter` 与 `*http.Request`，结构因而不依赖 gin 的类型。

RFC 9457（[REF-rfc9457](../references.md)）是 HTTP API 错误响应的现成标准，规定了字段与 `application/problem+json` 媒体类型。

## 考虑过的选项

### 不定义结构，由各模块自己写出

各层照原样写自己的状态码与响应体。

**否决**：分歧已经发生，客户端无法对拒绝做统一处理，每新增一个会拒绝请求的层就要再写一遍。

### 入口模块只写状态码，结构由提供 API 的模块经接口决定

兜底层只写状态码、不写响应体，有交付者时才由它决定结构。

**否决**：它只覆盖兜底层写出的那一类。认证、限流、租户解析的拒绝与无匹配路由的响应仍然各写各的，而没有模块交付接口的装配里，全部错误都没有响应体。

### 入口模块定义自己选字段的默认结构

字段与媒体类型由入口模块自拟。

**否决**：那是另造一种客户端与现成工具都不认识的结构，而标准已经存在。

### 按错误类别分设多个接口

兜底、校验失败、认证拒绝等各有一个可替换的接口。

**否决**：同一个 API 的各类错误只该有一个结构，分设之后各接口各自漂移。

### 入口模块定义默认结构，取 RFC 9457，经一个可选接口整体替换

**采纳**，见决策。

## 决策

采纳：入口模块以 RFC 9457 的字段定义错误响应的内容，默认以 `application/problem+json` 写出；一个可选的功能接口允许交付它的模块整体替换这一结构。

入口模块自己写出的错误响应——兜底层写出的、无匹配路由的、方法不允许的——以及供其他层调用的写出入口，都经同一处决定结构。handler 自己用 gin 写出的响应不经它。

## 后果

客户端面对一种错误结构，认证、限流、租户解析的拒绝共用它。

默认结构用现成标准，不另造；整体替换让一个进程里的错误响应只有一个结构来源。

**接受的代价：**

- 结构成为入口模块接口的一部分：内容的字段与默认的媒体类型一变更，即构成不兼容变更。
- 不经写出入口的错误不在覆盖内。handler 自己写出的响应、某一层绕过写出入口直接写状态码，都会让结构再次不一致；统一取决于各层是否使用它。
- 一个进程里只有一个结构来源。同一进程的各端点需要不同结构时，由交付者按请求自行区分。
- 这一块是自造，不是桥接：gin 没有对应的接口，选 gin 即由入口模块自备（[ADR-http-surface](adr-http-surface.md)）。

## 失效条件

若在已发布的宿主上默认结构都被替换，即每一处都交付了自己的接口实现，则默认结构这一半可以去掉，让结构完全归交付方。

若 gin 提供了统一的错误响应结构与集中的错误处理接口，则本记录自造的部分应当改为桥接。
