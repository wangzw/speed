# 登录标识的自助添加：用户名直接写，邮箱经验证码证明所有权

## 背景

账户的登录标识此前只能由管理员写：管理面经 `AccountAdmin.AddIdentifier` 添加，登录自助面只删不加，账户设计的规则 A7 明说「邮箱只经 IdP 声明或管理员登记成为标识，没有自助添加邮箱的路由；用户名只由管理员添加」。已认证用户因此改不了自己的登录标识，只能找管理员。

标识的写入带一条 `verified_via`，取值是封闭集，分证明渠道（`sms-code`、`invite`、`idp:<提供方标识>`）与断言渠道（`admin`、`import-unverified`）。证明渠道是自动关联与企业 JIT 并入的依据；断言渠道只记事实、不作依据。自助添加一条标识，必须回答两个问题：这条标识能不能不经证明就写；若能，`verified_via` 由谁定、取什么值。

仓库不内置邮件发送通道：账户设计明说「没有邮件通道，没有忘记口令流程」。短信承载由 `authn.sms` 的状态机（挑战表、号码前缀表、预算、盲索引）提供，它绑定的是手机号。

## 考虑过的选项

### 维持现状：标识只由管理员添加

**否决**：已认证用户改不了自己的登录标识，账户设置页缺一块；改自己的标识是自助动作，其授权依据是「发起者就是这个账户」，与改他人账户不是同一回事。

### 邮箱与用户名都只经断言写入，不做所有权证明

把邮箱也当作一条可自陈的登录名，直接写 `verified_via = self` 一类断言渠道，省掉验证回路。

**否决**：邮箱是联系方式，未证明即写入，会让依赖「真实证明」的判据——`link-required` 的触发、自动关联（`authn.account.auto-link`）、企业 JIT 并入——对一条从未被兑现的地址作出判断。所有权必须有一条可走的证明路径。

### 复用邀请令牌做邮箱证明

自助添加时建一条指向该地址的邀请式令牌，兑现令牌即证明持有该地址，再写标识。

**否决**：邀请的兑现会建账户与成员关系，是另一件事的状态机；把它挪用进标识写面，会让两套状态在同一个写路径上纠缠。

### 复用 `SMSCodes` 发码到邮箱

经既有短信验证码接缝发送到邮箱地址。

**否决**：`SMSCodes` 是手机验证码的状态机，带号码前缀放行表、号码级预算、挑战表与号码盲索引，与邮箱承载无关；复用会把这些语义压进一个与它无关的接缝。

### 新接缝只做投递，验证回路落在登录自助件；用户名直接写

新增一个只负责把验证码投递到邮箱地址的宿主接缝，验证回路（码的产生、记录、比较、尝试上限、重发间隔）落在登录模块的自助件里；用户名不经验证一步写入。

**采纳**，见决策。

## 决策

采纳：自助面新增两条路由 `POST B/identifiers`（体 `{kind, value}`）与 `POST B/identifiers/verify`（体 `{code}`），与既有自助路由同族、同新鲜认证与冒充门控。

**`kind` 是封闭集：`username` 与 `email`。** 手机不在本口，仍走既有 `POST B/phone` 与 `POST B/phone/verify`。

**用户名是登录名，无所有权可证，一步写入。** 它写入时 `verified_via = self`，是断言渠道，与 `admin`、`import-unverified` 同类，不作自动关联或并入的依据。

**邮箱是联系方式，须证明所有权，两步写入。** 第一步把码投递给该地址（应答 `state = pending`），第二步提交码（`POST B/identifiers/verify`），匹配才写标识，写入时 `verified_via = email-code`，是证明渠道。

**`verified_via` 由写标识的那一步定，而非账户管理员自陈。** 管理面的写入以 `admin` 记管理员自陈；自助面由自助写的处理器按它走的路径定：经码证明的邮箱记 `email-code`，未证明的用户名记 `self`。两个值都新增进封闭集，`email-code` 归证明渠道，`self` 归断言渠道。

**投递是宿主的接缝，`pkg/authn` 根包不内置邮件通道。** 根包新增 `EmailCodeSender`（`SendCode(ctx, to, code, ttl, locale) error`），登录模块可选取用：未装配时邮箱分支答 503，用户名分支照常。邮件通道的有无由宿主部署决定：仓库提供 `pkg/mail` 的发送能力与 `pkg/authn/emailcode` 适配模块（`authn.emailcode`），后者把该接缝接到 `pkg/mail` 的 `Sender` 上，装配它们仍是宿主的选择；账户模块自身不带邮件通道，与账户设计一致。

**验证码的回路落在登录自助件里**：码是六位数字，按会话在 kv 里存一条记录（地址、码的摘要加会话盐、发出时刻、尝试次数），成功即写标识并删记录；一次记录最多五次尝试，用尽即作废；重发有最短间隔，间隔内的重发答 429。循环不另立模块。

## 后果

- `via` 封闭集扩大两个值：`email-code`（证明）、`self`（断言）。账户的 `Verification.Valid` 与 `Proves` 随之更新：`email-code` 计证明，`self` 计断言。以真实证明为前提的自动关联与企业并入据此继续成立。
- 宿主可见面新增接缝 `authn.EmailCodeSender`；不装配它的宿主不能用自助邮箱添加，用户名添加不受影响。这是宿主可见面的变更。
- 登录模块新增两项设置：`authn.login.email-code-ttl`（默认 10 分钟）与 `authn.login.email-resend-interval`（默认 60 秒）。
- 自助邮箱添加引入一条由宿主提供的邮件发送通道，替代了账户设计此前「没有邮件通道」的绝对表述——账户模块自身仍不带通道，通道由宿主按需装配。
- 自助添加一条标识会撤销该账户的其余会话（当前会话轮换令牌），与加手机一致：一条新的登录名是一条新的进入账户的途径。
- 「用户名只由管理员添加」的政策由本决定改写；一个账户至多一个用户名的唯一约束不变，自助写入受同一约束。

**接受的代价：**

- 未装配邮件通道的部署，自助邮箱添加答 503；客户端据该码文本提示「本部署不支持自助添加邮箱」。
- 验证码经邮件承载，其投递的不确定性与外泄面由宿主接缝负责；平台侧只能保证「非成功即 503」。
- 邮箱的规范化在自助处理器里按文档规则做一次轻量校验（ASCII、恰一个 `@`、至多 254 字节、折小写），权威规范化仍在账户模块的 `NormalizeIdentifier`；两处规则的边界若漂移，以账户模块为准。

## 失效条件

- 若一个自助场景需要不经任何宿主接缝即可添加邮箱（例如平台要自带邮件通道）：投递接缝的设计要重新裁定。
- 若 `self` 渠道被用作自动关联或企业 JIT 并入的依据：证明与断言的划分失守，判据要收紧。
- 若六位码加五次尝试的上限在实际流量下被证明不足或过度：码的长度与尝试上限是数值裁定，可再调。
