# 选库为 OpenTelemetry

## 背景

架构文档的不变量 11 与 [ADR-module-packaging](adr-module-packaging.md) 写到这一依赖时都不点名具体的库，只说“追踪的 API 包”。不变量 11 的末句把“接口包暴露了哪些第三方类型”交给本模块自己的设计文档交代，而封装的是哪一家的库决定那批类型。

划界的判据在 [ADR-module-packaging](adr-module-packaging.md)：模块封装该库时，用它的类型表达接口是正常形态；模块只是碰巧用到该库时，那是实现绑定，留在子包。本模块对追踪与指标两种信号都是封装关系，接口与扩展点因此都要用被封装库的类型表达。

## 考虑过的选项

### 换一个追踪库，例如某一家的客户端库

采纳它意味着接口包与装配器都暴露并使用那一家的客户端类型。

**否决**：换库换不来本模块需要的任何性质，换来的只是让语义约定（[REF-opentelemetry-semconv](../references.md)）失去唯一出处：属性名与单位由库自带，而它们正是看板与告警读的东西。

### 接口包只暴露 API 包的类型，SDK 导出器类型留在实现子包，接口包另定义一个薄的导出器接口

采纳它意味着接口上只有上游 API 包的类型，speed 另定义导出器接口，实现子包在两套类型之间转换。

**否决**：那个薄接口仍然要提上游 SDK 的具体类型：导出接口的入参是 SDK 的只读跨度；不提它，包装就得分片搬运属性，批量与时间性随之丢掉；提了它，接口就不比 SDK 的类型薄。两种走法都落到一层只在名字上不同的等价抽象，正是 [ADR-module-packaging](adr-module-packaging.md) 已否决的东西。

### 封装 OpenTelemetry，接口包以类型别名暴露它的 provider 与导出器接口

**采纳**：见决策。

## 决策

采纳：**OpenTelemetry（[REF-opentelemetry-go](../references.md)）是本模块封装的库。**

接口因此按封装关系用它的类型表达：以类型别名暴露追踪与指标各一个 provider 接口，以及 SDK 侧各一个导出器接口。导出器是本模块的扩展点，后端实现方要用上游的类型写出实现，把 SDK 的类型挡在接口包之外只会让它在两套类型之间来回转换（[ADR-module-packaging](adr-module-packaging.md)）。

## 后果

宿主与依赖方用上游的类型写 provider 与导出器的锚点，不经转换；新增一种导出目的地是新增一个实现子包，装配器不需要认识任何后端。

**接受的代价：**

- **传染。** 取用装配器即承受上游 API 与 SDK 的闭包：只想用追踪的宿主，其接口包闭包里同样带着指标一侧的类型。上游的破坏性升级直达接口，也直达每一个用这些类型写锚点的模块：它的一次不兼容升级就是本模块的一次不兼容升级，不能在实现子包内消化（[ADR-module-packaging](adr-module-packaging.md)）。
- **导出后端的更新由上游的接口演化触发。** 扩展点上交付的类型就是上游 SDK 的导出接口，上游在该接口上新增方法时，每一个导出后端子包都要跟着改才编译得过。
- **语义约定换版不在本模块手里。** 换版会改变属性名与单位，而属性名是看板与告警读的东西；一处改名要在下游多处同步，本模块单独升一次级换不来这件事。

## 失效条件

若上游库停止维护，或项目需要在完全不依赖它的前提下支持第二种遥测后端，本决策的取舍随之重估。
