# 认证模块的范围：交付身份系统，授权另立

## 背景

`pkg/authn` 要回答的问题是「调用方是谁」。入口模块把路由的准入策略推给认证（[ADR-http-stages](adr-http-stages.md)）；中间件排序以「认证」作为可被指向的功能，按身份分支的层声明自己位于认证之后，认证无人代表时该约束静默消失；数据库模块把「谁可以物理删除」判为权限问题，推给认识操作者的那一层（[ADR-db-plugin-scope](adr-db-plugin-scope.md)）。这些推让各自用不同的名字指向承接方，承接方是一个功能目录还是几个，需要一处记录来定。

宿主要交付的认证能力超出对 `Authorization` 头逐请求校验：浏览器用户要登录并持有会话，服务调用方要换取令牌，部分账户要求第二因素，企业租户要接自己的 IdP，运营人员要在受限范围内冒充用户。这些能力共享同一份状态：账户、已验证标识、外部身份绑定、口令凭据、会话、令牌、因素与冒充记录。分散到多个功能目录，意味着同一个账户在几处各有一份存储，停用与删除要在它们之间协调。

账户全局，可属多个租户。「这个账户是不是这个租户的成员」是一条身份层面的事实，需要一张表来承载；请求期据此拒绝非成员，则要同时读身份与租户上下文。`pkg/tenant` 位于 `pkg/authn` 之上，`tenant/resolve` 已经 import `pkg/authn` 根包；authn 的子包反向 import `pkg/tenant` 会使两个目录互相依赖（[ADR-tenant-admission](adr-tenant-admission.md)）。

登录与令牌签发的路由由 authn 自己交付，对外与被保护的业务路由同一个端点、同一条监听、同一个地址。一条监听是一个具名地址，端点是挂在它上面的一条链（[ADR-http-listener-endpoint-split](adr-http-listener-endpoint-split.md)）；登记的层作用于该端点的全部路由，只对一部分路由生效的处理链由路由登记时带上的 handler 承担（[ADR-http-surface](adr-http-surface.md)）。登录路由免于认证而同端点的业务路由受认证，两者的访问级别因此要在同一个端点上逐路由区分。

判定凭据对应哪一个主体，与判定这个主体能不能做这件事，所需的输入不同。认定身份要的是凭据、账户与会话等认证事实；裁定权限还要资源、动作与一份策略，而资源与动作是应用自己的领域概念，策略的模型形态同样由应用决定，角色、属性与能力列表都是其中一种。

冒充要求宿主回答「谁可以冒充谁」，这是一个授权问题，而冒充的发起、记录、期限与审计是身份层面的事实。判定接缝默认全拒：没有任何模块交付它时，每次冒充请求都被拒。宿主的判定拒绝时，处理函数必须回答点什么：401 表示凭据缺失或强度不够，调用方已认证，不适用；404 表示隐瞒资源存在，而不是转述一次策略拒绝。

功能按包划分，版本与发布的粒度是 `pkg` 这个 Go module（[ADR-module-layout](adr-module-layout.md)）。一个子包所绑的第三方库只有 import 它的宿主才背负，功能目录变大不会把库带给不用它的宿主。

## 考虑过的选项

### 前置身份代理作整体方案

登录、会话、令牌、多因素、企业 SSO 与账户存储交给独立部署的身份服务（Ory Kratos、Dex、Keycloak 一类）。`pkg/authn` 缩成一个校验后端，校验该服务签发的令牌或会话。

**否决**：

- speed 以库的形式交付，宿主把模块编译进自己的二进制；整体方案要求每个宿主另部署并运维一个身份服务，改变的是交付形态而不是某个模块的实现。
- 账户、成员关系、会话与冒充记录要和 speed 自己的事务、租户、审计与事件在同一进程内协作。冒充要求审计在动作之前写成功、写不成则动作不执行；账户停用要同步撤销会话；请求期的成员判定要读成员关系。外置之后这些都要跨进程，失败方向（依赖不可用时拒绝）由部署而不是由模块决定。
- 这类服务各自有自己的租户或域模型，与 speed 的租户模型是两套；账户与租户的映射、成员关系与租户级强度策略要另行同步，同步的滞后落在放宽一侧。
- 模块的取向是现成库与 speed 之间的桥；独立的身份服务不是库，没有可桥接的接口，登录流程、账户存储与成员关系表仍要自写，代理只替掉其中一部分。

这一否决只针对整体方案。Dex、Keycloak 一类服务作为企业租户的上游 IdP，经企业 OIDC 接入，不受影响（[ADR-authn-sso](adr-authn-sso.md)）。

### 认证与授权同属一个功能目录，`pkg/authn` import 授权

`pkg/authn` 交付从凭据到「这个请求可不可以继续」的整条判定，授权模块被 authn 的管理面与冒充直接调用。

**否决**：

- 权限的判定要认识资源与动作，策略的模型形态由应用决定；合并进来等于替每个宿主选定一种，只需要认证的宿主也要一并承受它的约定与输入项。
- 授权要消费账户标识、成员关系与变更事件，这些是 authn 的数据；授权模块 import authn 根包并实现其中的接缝，与 `tenant/resolve` import `pkg/authn` 同形。反过来让 authn import 授权，两个目录互相依赖，authn 根包的形状要由它所依赖的授权模块决定，而授权的形状随应用的策略模型而变。
- 两者的输入来源与变更节奏不同：认证随凭据与登录方式增减而变，策略随应用的领域模型而变（[ADR-module-layout](adr-module-layout.md)）。

### 所有拒绝都答 404

`Decider` 的拒绝、被关闭的登录方式、账户不可用、冒充发起的限制一律写成 404，网关之外再没有 403。

**否决**：404 是隐瞒资源存在。对 authn 自己的资源，调用方已经认证、资源确实存在，管理员与调用方因此分不清「没有权限」与「没有这个资源」，排障与客户端的错误提示都失去依据。404 只用于存在本身需要保密的场合：非成员访问租户、冒充的范围与请求所在租户不符，这些场合由 `tenant.admission` 以同一形状的 404 回答，不泄露租户是否存在。

### 拒绝一律答 401

保持「`pkg/authn` 从不写 403」的原句，`Decider` 等策略拒绝改用 401 加挑战头。

**否决**：401 的语义是凭据缺失或强度不够，客户端据此重新登录或加强认证。策略拒绝时凭据本身有效，重新认证不改变结果，客户端会在 401 与重试之间循环。

### 豁免归入口模块，或另设独立功能目录

入口模块在登记路由时接受「这条不需要认证」的标注，或提供路由查询面；或豁免表由独立功能目录承载，作出认证判决的层在判决之前向它查询。

**否决**：「这条路由不需要认证」是认证概念，落进登记面要求入口模块认识认证，而它不认识任何具体功能（[ADR-http-stages](adr-http-stages.md)）；登记面不带登记方身份，无从判断提出标注的与作出判决的是不是同一方。独立目录下豁免表只有一个读取方，没有独立于认证的发布节奏，也没有脱离认证单独取用它的消费者，升格所需的举证不成立；拆开还多出一种失败形态：豁免登记可以在没有任何一层作出认证判决的进程里成功完成，登记方拿到的信号与生效时完全一样。

### 免认证路由分到另一个端点

沿用入口模块对「只对一部分路由生效的层」给出的既有答案，把登录与令牌签发路由挪到不挂认证的端点。

**否决**：登录与令牌签发路由与被保护的路由同一条监听、同一个地址对外，这是 API 的形状，不是装配的自由度。挪到另一个端点上，它们要么仍在这条监听上（地址不变，却多出一条链），要么落到另一条监听上（客户端于是要对登录与业务使用不同的地址），API 的形状随装配而变。

### 认证与路由豁免同属一个功能目录，范围覆盖身份系统，授权另立

**采纳**，见决策。

## 决策

采纳：`pkg/authn` 交付身份系统，授权另立。

**判据是判定所需的输入与事实的性质**：只需要凭据、账户、标识、会话、令牌、因素、IdP 配置与冒充记录这类认证事实的归 `pkg/authn`；还需要资源、动作与策略的归授权。

在这条判据之下，`pkg/authn` 当前交付的范围是（例举，随新增的认证事实与登录方式增长，归属以判据为准）：

- 登录，含多种登录方式；
- 登录会话；
- 访问令牌与刷新令牌的签发与校验；
- 多因素认证；
- 企业 SSO；
- 冒充：发起、记录、期限与结构性限制；
- 账户、外部身份绑定与成员关系表；
- 路由访问级别的登记：豁免、可选认证、可冒充。

**授权是独立模块，`pkg/authn` 不 import 它。** authn 只在根包留接缝，依赖方向是授权模块与宿主 import authn 根包。接缝按提供方分为两组（例举，完整清单见设计文档 `design-authn-admin`）：

- 由宿主或授权模块交付：
  - `Decider`：判定接缝，缺席时对他人账户与租户级资源的管理面动作、对冒充一律拒绝；
  - `AccountLifecycle`：账户停用与删除的清理钩子，授权模块按需选择实现；
- 由 authn 交付并向授权承诺：
  - 身份字段：只回答「谁」，不含角色与权限，由网关盖章；
  - `Memberships`：成员关系的只读面，由 `authn.account` 实现；
  - 事件：账户、成员关系与会话撤销的变更通知，授权据此清理自己的绑定与缓存。

**成员关系的事实归 `pkg/authn`，请求期的成员判定放在 tenant 目录**（模块 `tenant.admission`）。`pkg/authn` 的子包不 import `pkg/tenant`；两个目录之间的边界只由根包的 `ScopeGuard` 与 `Memberships` 接口维持。

**冒充按身份层面的事实与策略拆开**：谁、在哪个租户、多久、有没有被审计，由 `pkg/authn` 结构性地强制；「谁有权冒充谁」经 `Decider` 判定，`Decider` 只能在结构性限制之上进一步收紧。

**「`pkg/authn` 从不写 403」收窄为：做认定的层，即网关，从不写 403。** `pkg/authn` 自己的路由处理器作为自己资源的所有者，只在转述认证之外的策略拒绝时写 403，这一集合是封闭集，成员与状态码的完整对应见设计文档 `design-authn-failure`，处理器一侧的分工见 `design-authn-admin`。除此之外，「强度不够」凡重新认证能解的都是 401 加强认证挑战（[ADR-authn-verdict](adr-authn-verdict.md)）；重新认证解不了的只有一种：冒充发起与管理员重置时，发起者名下没有启用已满规定时长的非短信因素，它归 403 `factor-not-seasoned`，因为 401 的挑战对它指不出出路，调用方会在挑战与重试之间循环。`tenant.admission` 不写 403：非成员与冒充范围不符答 404，认证强度不足答 401。通过认证的请求继续沿链向内，是否还有一层拦它不由 `pkg/authn` 的网关决定，网关也不知道有没有那一层。

**登录与令牌签发路由与被保护的路由同址。** 它们由 `pkg/authn` 自己交付，访问级别经网关的公开登记面与路由成对登记（[ADR-authn-exemption](adr-authn-exemption.md)）。路由豁免因此承担 authn 自己整个路由面的访问级别声明；豁免与认证判决同属一个功能目录的判据在此成立：登记时机、冻结时机与命中判据在同一份代码里一起变更。登记的来源与匹配规则由 [ADR-authn-exemption](adr-authn-exemption.md) 裁定。

## 后果

承接方有了同一个名字：入口模块推让的认证，数据库推让的权限，分别落在 `pkg/authn` 与授权。「位于认证之后」这条中间件约束有了落点（[ADR-http-stages](adr-http-stages.md)）。

账户只有一份存储，停用、删除与撤销在同一个功能目录里有单一的权威表，跨模块的清理走钩子与事件（[ADR-authn-account-lifecycle](adr-authn-account-lifecycle.md)）。

只需要认证的宿主不承受授权模型的约定与输入项。每个子包所绑的库只由 import 它的宿主背负，目录变大不改变宿主的依赖面（[ADR-authn-packaging](adr-authn-packaging.md)）。

调用方能从状态码读出拒绝的性质：401 表示凭据缺失或强度不够，应重新认证；403 表示已认证而被策略拒绝，重试无效；404 表示对该调用方而言资源不存在。

**接受的代价：**

- `pkg/authn` 目录变大：模块、迁移集、第三方库与威胁面都随登录、会话、令牌、多因素、SSO 与冒充一同进来。账户全局，登录面与账户存储的缺陷同时波及全部租户。
- `pkg/authn` 与 `pkg/tenant` 的边界靠根包的 `ScopeGuard` 与 `Memberships` 接口维持。这些接口的形状变更，同时牵动 authn 一侧的实现与 `tenant.admission` 一侧的消费；`pkg/authn` 在编译期也无从得知准入层是否装配，冒充模块把 `ScopeGuard` 当必需依赖，装配里没有准入层即启动失败，以此代替编译期的保证。
- 装配了认证而没有装配授权模型的进程里，凡通过认证且通过准入层的主体都能到达每一条不豁免的路由。网关不写 403，也不知道链上有没有人写；未被本次命令纳入、也没有预置实例的模块不进启动诊断，理由是诊断要写的原因只有消解落选，而它在一个连表态都没有的模块身上无从写起。缺一个授权模型因而不产生任何主动信号，按名查询答得出它未被纳入，但那要宿主自己去问。
- 认证与授权之间的接缝只由 `pkg/authn` 一侧定义。身份的形状、账户标识的性质与成员关系的读法由 authn 根包先行固定，授权模块若要求另一种形状，改的是一个已经被其他模块 import 的接口包。
- authn 处理器的 403 集合是封闭集：新增一种策略拒绝要重新裁定它归 403、401 还是 404，不能在处理器里直接选用。网关与准入层不写 403，调用方读到的 403 可能来自 authn 自己的处理器，也可能来自链上的授权层或宿主的 handler，仅凭状态码区分不了来源。
- 豁免与作出判决的那一层一同在场或一同缺席：那一层不在本次命令的参与集里时，豁免登记整体不发生，而缺席时的净效果是放行不是拒绝（[ADR-authn-guarantees](adr-authn-guarantees.md)）。
- 归属的判据落在输入与事实的性质上，而新出现的判定未必一眼看得出落在哪边。一种判定先按认证实现、后来才发现它要读一份策略，改归属就是一次跨功能目录的搬迁；冒充与管理面经 `Decider` 拆出策略部分，是对这一风险的既有处理，不是对它的消除。

## 失效条件

- 出现一种不经 HTTP 的入口同样需要认证与豁免：豁免以 HTTP 的方法与路径表达，那种入口没有方法与路径，`pkg/authn` 的交付面需要重新裁定。
- 授权模块的设计要求一种身份字段、成员关系读法或事件载荷无法由现有接缝提供的形状：本记录假设授权只消费 authn 根包的接口，不要求 authn 反向依赖它；该假设不成立时，接缝与归属需要重新裁定。
- 出现无法拆出策略部分的认证判定，即判定本身必须读一份应用的策略才能给出认定结果：判据「所需输入与事实的性质」没有覆盖它，归属需要重新裁定。
- 出现要求账户存储与登录由宿主之外的身份服务承担的部署要求：前置身份代理的整体方案需要在那个部署约束下重新评估。
- `pkg/tenant` 不再位于 `pkg/authn` 之上：准入层放在 tenant 目录并只经 `Memberships` 与 `ScopeGuard` 读 authn 的前提不再成立。
