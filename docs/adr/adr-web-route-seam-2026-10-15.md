# 路由与导航独立成包，壳不做导航

## 状态

已接受

## 背景

前端由若干包组成。壳（`web/packages/product-shell/src/index.ts` 的 `ProductShell`）是一条三分支视图机：它渲染一帧界面——页头、抽屉导航、内容区——但它不做导航，不解析 URL，导航条目由宿主算好、连同选中态一起传入：`ProductShell` 经它本地的 `AppShellChromeProps`（`Pick<AppShellProps, …>`，`web/packages/product-shell/src/components/ProductShell.tsx`）把 `navItems` 等框架 prop 原样转给 layout-kit 的 `AppShell`。这是壳的既定契约。

一个产品要有页面、路径、深链接与选中态，这些决定今天没有任何一处承载：宿主各自发明。参考应用里就有一条宿主本地的路由器，每个产品会再写一遍，路径形状与选中态各不相同。

后端已有一条对称的机制：命令树点名模块，纳入沿命令路径继承，一个程序由哪些模块组成写在一处（[ADR-command-tree-2026-09-20](adr-command-tree-2026-09-20.md)、[ADR-command-tree-2026-09-21](adr-command-tree-2026-09-21.md)）。前端缺一条对应的接缝：一个产品由哪些页面组成、各占哪些路径，没有一处可写。

## 考虑过的选项

### 把路由并入壳 product-shell

**否决**：壳是一条与登录渠道无关的视图机，它今天不解析 URL、不认路由表。并入路由会把路径形状这一产品决定绑进一个本应无意见的壳；一个不经 URL 渲染的消费者（嵌入式视图）也一并背上路由依赖。这推翻壳"不做导航"的既定契约。

### 让每个业务模块自带走路由库与路径约定

**否决**：路径形状、选中态、链接构造与路径冲突检测会按模块数各写一遍。参考应用与各产品各自的写法印证了这一点，深链接与选中态在各处不一致，收敛不到一处。

### 由独立包 route-kit 持有路由与导航，业务模块经声明式注册面接入

**采纳**，见决策。

## 决策

采纳：**路由与导航独立成包 `route-kit`，壳保持不做导航，业务模块经声明式注册面接入。**

- `route-kit` 是独立包，不被壳 import；壳继续只渲染宿主算好的导航条目，契约不变。
- 一个产品经一份声明式注册面登记它要占的路径与页面：每条登记是「路径 pattern 加页面」，产品在一处点名它由哪些页面组成——与后端命令树点名模块对称。
- 选中态、链接构造、深链接解析与未命中回退由 `route-kit` 一处承担。
- 路径与权限之间的关系不由 `route-kit` 建立：授权仍是宿主在内容区里的组合，`route-kit` 只按登记面匹配路径。
- 路径匹配、历史导航与链接构造**建在一个既有的第三方路由器之上**（`react-router-dom` 作为本包的 peer 依赖），产品不直接 import 它：本包是一个现成库的桥，另造一层等价的路径匹配与历史栈只会让产品在两套地址模型之间转换。今天的反例正是参考应用里那条手写的地址读写——每个产品再写一遍。

## 后果

一个产品的页面组成写在一处，每个业务模块不再各带一套路径约定；壳保持无路由依赖，无 URL 形态的宿主照常只用壳。

**接受的代价：**

- **新增一个必须与壳、与各页面族一起演进的包。** `route-kit` 是产品页面装配的唯一入口，它一坏，整页的导航与深链接一起坏。
- **登记面的形状成为宿主可见面。** 发布之后改登记面是破坏性变更，须随发布对账。
- **一个第三方路由器成为整条前端链的必需依赖。** `react-router-dom` 进入每个采用本包的产品，它的主版本升级由本包承担；本包因此不能在没有它的情况下单独交付，也不能替产品换一个地址模型。
- **路径与权限没有编译期联系。** `route-kit` 不校验一个页面占的路径与它所需的权限；把两者接错（一个页面渲染了它无权取的资源）不在路由层被拦下，授权仍靠宿主在内容区里喂给 `RouteGuard` 的状态。

## 失效条件

- 若产品的普遍形态是无 URL 的嵌入式渲染——没有深链接，没有可分享的地址——声明式注册面的价值随之下降，路由应退回各宿主自己的形态。
- 若各产品最终只在栈顶有一条视图、路径从不分叉，登记面比需要的更重，应重新评估它的形状。
