# 租户列存服务端生成的不可变标识，请求侧与界面只出现创建时确定、此后不可变的别名

## 背景

受租户约束的每一张表都有一列记住这一行属于哪个租户（[ADR-tenant-isolation](adr-tenant-isolation.md)）。那一列里存什么，与请求侧出现什么，此前没有出处。

两个位置上的约束不同。请求侧出现的是取法读到的那个串：子域名的合法字符集、路径段的合法字符集与请求头的取值三者并不相同，而用哪一种由配置选定（[ADR-tenant-resolution](adr-tenant-resolution.md)）。库里那一列的取值不在任何 URL 的语法之下，它的读者只有本模块、日志与排查的人。

租户的对外名字在创建时确定，此后不随租户内的资料或状态变化；受约束表里那一列存的是稳定、不可变的值。

请求侧的名字还要与用户名共处。个人租户的别名就是账户的用户名；一个业务组织的别名与一个账户的用户名出现在同一个地址空间里。两个名字各自唯一，不等于它们之间的互斥自动成立；如果它们在两处分别登记，同一个串可以同时是一个组织的别名和一个账户的用户名，请求侧无法判断它指谁。

标识还会出现在日志与启动诊断里，那些场合的读者是排查的人；界面、错误 detail 与确认文案面向操作者，读到的东西要能直接认出是哪个租户，因此写别名（或显示名），不写标识。

## 考虑过的选项

### 请求侧那个串直接入列

取法读到的名字就是库里那个取值，省掉一次解析。

**否决**：库的约束会跟着取法的字符集走：换一种取法就换一套合法字符，而已入库的取值不跟着变——同一份数据在两次部署之间可用的名字不同。URL 的语法约束因此变成库的约束，而两者管辖的范围本不相同。

### 数值自增主键入列

名册用一个自增整数做主键，受约束表存那个整数。

**否决**：跨库搬迁与合并时撞号，而这两个动作在多租户系统里是常规运维。它在日志、启动诊断与错误文本里读不出是谁，每次排查都要回查名册，而租户标识的读者是人，读到就要认出是哪个租户。可读性是租户标识自己的要求；账户标识的取舍另有依据，见 [ADR-authn-accounts](adr-authn-accounts.md)。

### 不可变标识入列，别名可改

名册的一行携带一个不可变标识与一个可改的别名，受约束表存标识，请求侧出现别名，解析即别名换标识；改名只写名册一行。

**否决**：别名是组织的公开地址，改名让已经发出的书签、链接、缓存与客户端里的地址指向新组织；别名释放之后还可以被另一个组织登记，旧地址于是把访问者带到另一个租户。组织需要改的是显示名，显示名不承担寻址。

### 不可变标识入列，别名不可改，用户名与别名分两个命名空间

名册存不可变标识与不可改的别名；用户名仍在账户的标识表里，两者各自唯一。

**否决**：个人租户的别名就是用户名，两个命名空间在个人租户上重合；要让“组织别名不撞用户名”成立，需要一条从账户模块到租户模块的跨表检查，或反过来的一条。两个唯一约束各管一半，中间的窗口仍可以让同一个串在两边登记。

### 不可变标识入列，别名不可改，用户名与别名共用一个命名空间

名册存不可变标识与不可改的别名；别名在创建时由用户输入，落在 `tenants.alias` 的单列唯一约束上；个人租户的别名直接取用户名，业务组织的别名因此与用户名在同一张表上互斥。

**采纳**，见决策。

## 决策

采纳：租户列存不可变标识；请求侧出现的名字是名册上的别名，创建时由用户输入，全局唯一，创建后不可改；别名与用户名共用一个命名空间。

```go
// ID 是一个租户的不可变标识。
type ID string
```

**标识是一个不透明的字符串，由服务端生成，创建路径不接收它。** 平台登记与自助创建都只收别名与资料，标识在服务端铸出（`org-` 加一个随机 UUID），宿主导入既有租户时可以直接写它持有的租户号。标识不在任何视图、路径、界面文本或错误 detail 里出现，因而它不需要可读性；个人租户的标识仍按账户标识派生，那是内部事实，不对外。本模块校验它的格式——非空、不含空白与控制字符——生成器负责唯一性。

**别名由建立租户的一方给出，唯一，不可改。** 别名的字符集是统一的 slug：三到六十三个小写字母、数字与连字符，以字母或数字开头。它与用户名的规则相同，因为个人租户的别名就是用户名。别名不得等于任何租户的标识：标识可以由宿主导入为任意字符串，别名与它重合会让请求侧的名字与内部键撞在一起，维持两者互斥的代价远低于事后分辨。名册没有改名写：`Put` 的别名必须与既有别名一致，否则拒绝。

**用户名与别名共用 `tenants.alias` 的单列唯一约束。** 个人租户的别名取账户的用户名；一个业务组织的别名因此与一个已存在的用户名互斥，反过来，一个新用户名等于一个业务组织的别名时，账户创建事务在写个人租户行处失败并整体回滚。并发的竞争由该唯一约束仲裁，不靠两张表之间的检查。

**保留字取用户名保留集与别名保留字的并集，含 `personal-` 前缀。** 一个名字在任一命名空间里被系统保留，就不能在另一个命名空间里被登记。

**解析是别名到标识的一次换名**，写进请求上下文的是标识。日志与启动诊断写标识，需要人能认出来的场合另外带上别名；**面向人的界面、错误 detail 与确认文案写别名（或显示名），不写标识**。别名不改，但作为请求侧的名字仍不承担任何判定，资料里的显示名承担展示。

## 后果

跨库搬迁与合并时标识保持原样，合并的冲突落在别名上，而那是人读得出的一类冲突。受约束表一行都不用动，因为别名从来不进那些表。

受约束表的那一列与请求侧出现的东西从此是两个概念，链条是：取法读出别名 → 名册换成标识 → 上下文携带标识 → 插件按标识加条件 → 日志与诊断写标识。

**接受的代价：**

- **每个请求要把别名换成标识，因而必须读名册。** 换名的结果要有缓存与失效途径，租户名册从此位于请求的关键路径上；它答不了时请求收口而不是放行。
- **标识与别名两个概念并存，两个场合各写哪一个要各自明确。** 写错一处的形态是排查时对不上号：日志里是标识，而操作者手上是别名。
- **别名不可改，写错的地址不能修正。** 组织改名要改的是显示名；一个必须换地址的组织只能新建一个租户，旧租户按删除处理。这是用地址的稳定性换掉的。
- **别名不可回收。** 删除把租户写成墓碑，别名随行保留，同一个别名不能被另一个组织再次登记；旧地址因此不会指向新组织。标识与别名一起不可复用。
- **用户名不可复用。** 个人租户的墓碑保留用户名，同一个用户名不能被另一个账户再次登记；这与账户标识不可复用的语义一致。
- **标识不可变，因而它不能承担任何随租户而变的信息。** 把区域、分级一类东西编进标识的宿主，改它们时要面对一次数据迁移，而本模块不提供。
- **标识不需要可读性，也不能被操作者引用。** 出问题的租户只能按别名来指认；日志里是标识而操作者手上是别名，两处对照要经名册。这是把请求侧与内部存储分开换来的一条代价。
- **宿主导入既有租户时仍可写自己的标识。** 服务端生成的是本模块创建路径的规则，导入路径不受它约束；标识的长度由那一列与宿主的取值决定，不另立一个判据。

## 失效条件

若产品需要组织在成立之后更换请求侧地址，则“别名不可改”这一条要重新比较：地址的稳定性与改名后的旧地址处置之间，权衡的结论可能相反。

若出现一种部署形态，其中同一个租户在不同端点上必须由不同的名字到达，且这些名字不能同时是别名，则「别名唯一」这一条不再够用，名册的键要重新裁定。若产品的运营流程普遍要求修正已发布的别名，则「创建后不可改」要重新比较，代价是每个请求多一层重定向或旧名的长期保留。

若出现一种部署形态，其中用户名不必与租户别名共用命名空间，则单列唯一约束不再是互斥的仲裁者，两个命名空间要重新裁定。

若宿主普遍需要本模块生成标识，则“不生成”这条要重新比较：多一套生成器与长期并存两套编号之间，权衡的结论可能相反。
