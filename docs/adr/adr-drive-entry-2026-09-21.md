# 注册表有两个驱动入口，`Run` 是 `Drive` 的一种取值

## 状态

已接受

## 背景

一次驱动要三个参数：推进到哪个阶段、纳入哪些模块、到达之后做什么（[ADR-lifecycle-drive-2026-09-20](adr-lifecycle-drive-2026-09-20.md)）。写出命令树的宿主把运行级纳入的模块写在命令树上，注册表据此展开依赖闭包（[ADR-command-tree-2026-09-20](adr-command-tree-2026-09-20.md)、[ADR-command-tree-2026-09-21](adr-command-tree-2026-09-21.md)）。

不写命令树的调用方同样存在。包外测试手工登记一小组模块，它的意图是这批模块全部跑起来；嵌入式宿主把 speed 接进一个已有入口的更大程序，不需要 speed 的命令树，意图同样是已登记的模块全部跑起来。

注册表已持有登记名单：`Modules` 给出描述符全集，登记的顺序也在它手里。只留一个接清单的入口时，这类调用方要自己取出全部名字、拼成参与集，并写明深度与动作。这份改写每个调用点各写一遍，而其中的名字清单是注册表自己的事实——调用方复制它，就是维护一份与登记失配时不会被任何一层拦下的副本。

## 考虑过的选项

### 只保留接清单的入口

不写命令树的调用方从 `Modules` 取出全部名字填入参与集，深度写 `StageServe`，动作留空。

**否决**：把注册表自己已经知道的事实复制到每个调用点。"全部已登记模块"因此从注册表的性质退化为一处调用方的约定，漏列一个名字是静默的——那个模块不运行，而没有任何一层会说出来。

### `Run` 接一份参与集清单

`Run(ctx, names)` 与 `Drive` 一样收清单，区别只在深度固定为 `StageServe`、动作固定为空。

**否决**：不解决上一条。不写命令树的调用方仍要自己拼那份"全部"清单；省下的只有深度与动作，代价最高的那一半原样留着。

### 两个入口各自实现推进

`Run` 独立实现一条从 `Prepare` 到 `StageServe` 的推进路径，与 `Drive` 分开维护。

**否决**：推进的规则要在两处实现并保持一致——浅驱动的跳过、失败后的回滚、`Stop` 与 `Close` 的两拍。两处实现迟早分叉，而分叉的后果落在资源释放上。

### `Run` 是 `Drive` 的一种取值

`Run` 在注册表内部取出登记名单，填成一次 `Drive` 调用：纳入全部已登记模块、推进到 `StageServe`、没有动作。推进路径只有 `Drive` 一条。

**采纳**，见决策。

## 决策

采纳：**注册表暴露两个驱动入口，`Run` 是 `Drive` 的一种取值。**

`Drive(ctx, Drive{...})` 收一份字面清单、一个深度与一个动作，都由调用方给出，服务于写出命令树的宿主。清单列的是运行级纳入的模块，由命令树的执行展开依赖闭包后带进驱动；预置了实例的模块不必列入，驱动开始时由注册表并入参与集（[ADR-supplied-instance-2026-10-08](adr-supplied-instance-2026-10-08.md)）。

`Run(ctx)` 服务于不写命令树的调用方——包外测试与嵌入式宿主。它纳入全部已登记模块、没有静态级纳入、没有动作、推进到 `StageServe`，因而阻塞到 `ctx` 取消后关闭。它在注册表内部展开成一次 `Drive` 调用，推进路径因此只有一条。

**两个入口共用驱动的一切性质。** 一次驱动的不可分割性、`Stop` 与 `Close` 的必执行、一个注册表只驱动一次，对两者同样成立（[ADR-lifecycle-drive-2026-09-20](adr-lifecycle-drive-2026-09-20.md)）。

## 后果

不写命令树的调用方不必维护那份名单，也不必自己判断深度。

`Run` 下的集合关系退化：参与集是全部已登记模块，声明集等于参与集，静态级纳入为空。`Run` 下没有未被纳入的已登记模块，也没有只被静态级纳入的模块。

**接受的代价：**

- `Run` 下没有命令树的执行，因而没有配置加载这一步：配置读取面不会被预置。`config` 模块一经登记便在 `Run` 的参与集里，而它没有 `New`，调用方不自己预置读取面就启动失败：有模块在轮到 `config` 模块构造之前取用读取面时报 `ErrMissingProvider`，否则轮到它构造时报 `ErrUndeliveredCapability`（[ADR-supplied-instance-2026-10-08](adr-supplied-instance-2026-10-08.md)）。注册表里没有登记 `config` 模块，且登记的模块也都不读配置时，不受此限。这个入口服务于嵌在别处的宿主与测试，不服务于装配整个应用的宿主。
- `Run` 下参与集是注册表里已登记的每一个模块，模块是否参与不取决于命令，宿主无须指明哪条命令用得上哪些功能。一个 import 了某模块、却不想在本次运行中跑它的二进制，用 `Run` 表达不出来，只能用 `Drive` 给出清单。
- `Run` 纳入注册表里已登记的每一个模块，因而对一个同一排他功能在场多个实现的二进制不可用：那些实现全在参与集里、都必须启动，必然以排他冲突终止启动。`Run` 的适用面因此比不写命令树更窄一层——不写命令树只说明调用方不给出清单，`Run` 另要求这个二进制里每个排他功能只有一个在场实现（[ADR-dependency-resolution-2026-09-13](adr-dependency-resolution-2026-09-13.md)）。
- "一个注册表只驱动一次"在调用点上表现为两个方法名，把 `Run` 与 `Drive` 各调一次，得到的是 panic 而不是第二次驱动。

## 失效条件

若命令树的装配能力被拆出一个不依赖 `pkg/config` 的最小入口，"不写命令树的调用方自己预置读取面"这条代价随之减弱，`Run` 与那个入口的分工需要重新裁定。

若不写命令树的调用方普遍要的并非"全部已登记模块"，`Run` 固定的取值覆盖不了它们，它们只能用 `Drive` 给出清单——那时 `Run` 存在与否不再影响任何调用点能写出什么。
