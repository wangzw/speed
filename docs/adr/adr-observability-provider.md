# provider 经注册表交付，不装成上游的全局，也不装进程级的错误处理器

## 背景

上游遥测库 `go.opentelemetry.io/otel`（[REF-opentelemetry-go](../references.md)）自带进程级单例：`otel.SetTracerProvider` 与 `otel.SetMeterProvider` 装入的 provider，`otel.SetErrorHandler` 装入的错误处理器，都挂在进程上。未装 provider 时全局给出空实现，跨度与指标照常被调用、什么都不产生；未装错误处理器时上游把内部错误记到标准错误。两者都不随注册表走。

模块之间只按功能取用彼此，不使用全局变量传递实例（架构不变量 9）。该条约束的是取得另一个模块实例的途径：凡是由注册表持有的模块实例，无论由模块在 `New` 中构造还是由宿主预置，一律经 `core.Resolve` 取得。

一个进程里可以并存多个注册表，各自驱动自己那一组模块：`Run` 入口服务于不写命令树的调用方（包外测试、嵌入式宿主）。上游的全局挂在进程上，不属于任何一个注册表，第二个装配一出现就覆盖第一个。

## 考虑过的选项

### 调用上游的全局设置函数把两个 provider 装进去

装配器在 `New` 中调用 `otel.SetTracerProvider` 与 `otel.SetMeterProvider`，本模块的 provider 成为进程级单例，任何一处 `otel.Tracer` 与 `otel.Meter` 调用都落到它上面，provider 不必穿过每一处调用点。

**否决**：架构不变量 9 排除这条途径。同进程的第二个装配会覆盖第一个：被覆盖的那个注册表里，经 `core.Resolve` 取到的仍是它自己那一个，经上游全局取到的却是后装的那一个，两侧从此不一致，而没有任何一层报出这件事。

### 额外安装一个进程级错误处理器把上游的内部错误接进日志

装配器调用 `otel.SetErrorHandler`，把上游 SDK 的内部错误（导出失败、批处理器异常）导向本模块配置的 logger。

**否决**：它与全局 provider 同属进程级单例，同样被第二个装配覆盖，而错误处理器没有注册表可挂，本模块没有一条随注册表走的途径去装它。本模块需要的那条信息（导出失败）由转发包装自己给出，不经进程级状态（见设计文档）。

### 两个 provider 只经注册表交付，消费方 `core.Resolve` 取得

装配器返回同时实现两个 provider 接口的产物，由注册表持有；取用它的调用点按功能标识查询，与取得任何别的模块实例是同一条途径。

**采纳** — 见决策。

## 决策

采纳：**本模块不调用上游的全局设置函数，不安装进程级的错误处理器。** 两个 provider 只经注册表交付，消费方经 `core.Resolve` 取得（[ADR-dependency-resolution](adr-dependency-resolution.md)）。

## 后果

一处要产生跨度或指标的调用点，必须持有经注册表取到的 provider。`otel.Tracer` 与 `otel.Meter` 这两个包级入口在本模块的装配下取到的是上游的空实现，写进去的信号不落到任何目的地。

**接受的代价：**

- **依赖上游全局 provider 的第三方自动插桩库取不到本模块的 provider。** 那些库按 `otel.GetTracerProvider` 取全局，本模块不装全局，它们因而拿到空实现，其产生的跨度不进入本模块的导出链路。这条缺失没有任何一层会报出来——库照常工作，跨度照常创建，只是不导出。撞上它的是引入这类库的宿主：插桩看起来生效，信号却缺席。
- **没有 provider 与 provider 在工作但没采到东西，在调用点观察相同。** 前者拿走的是上游的默认实现，它是空转；两者都表现为调用成功而无产出。本模块把这一条写进装配级性质，不由异常表达，调用点不会因此收到错误。撞上它的是排查信号为什么是空的运维者：要区分两者只能回到装配与配置，取用点给不出线索。
- **上游交给进程级错误处理器的内部错误照上游默认写标准错误。** 导出失败不在此列：转发包装写完它的日志行即把错误吸收，不交回上游（见设计文档的转发包装）。其余的内部错误——上游在构造批处理器、读数器或仪表时自己判出的那些——仍由上游默认的处理器写到标准错误，绕开日志链与脱敏层。撞上它的是读标准错误的运维者：这几行与启动诊断同流，格式却是上游自己的。
- **每一处要发信号的调用点自己取用并传递 provider。** 装一次全局换来的是处处可见，本决策放弃了这一条：新增一个上报指标的模块要显式声明依赖并取用它，漏掉依赖的表现为启动失败（`core.ErrMissingProvider`），不是静默取到别人的 provider。撞上它的是新增上报点的模块作者。

## 失效条件

本决策据以否决全局安装的那条冲突，前提是同一进程可以并存多个注册表、后一个装配覆盖前一个。若进程被限制为只有一个注册表，或上游库取消进程级全局，装全局不再产生两个装配之间的不一致，本决策要重新检验。
