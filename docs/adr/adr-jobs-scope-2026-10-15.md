# 作业能力只承载必须跨副本收敛的触发，进程内循环归各模块自己的 ticker

## 状态

已接受

## 背景

需要一处受理三类触发：在某个时刻执行一次、按周期重复执行、把一件耗时的事交给后台异步执行。它们的共同点是效果必须在多副本部署里收敛——一次触发不因副本数增加而重复发生。单副本进程内的循环表达不了这一点。

本仓既有的循环分工是「循环属于需要它的那个模块」，没有任何一处把循环交付给别的模块。这些循环的用途与所在模块是：

| 用途 | 模块 |
|---|---|
| 刷新进程内快照 | `pkg/authz/policy`、`pkg/settings`、`pkg/tenant/catalog`、`pkg/sms/registry` |
| 清扫过期行 | `pkg/authn/session`、`pkg/authn/token`、`pkg/authn/account`、`pkg/authn/mfa`、`pkg/authn/sms`、`pkg/authn/sso` |
| 轮转日志文件 | `pkg/log` |
| 轮询外部状态 | `pkg/sms/registry`（厂商审核） |

它们的统一形态是：间隔 ≤ 0 即关掉循环、失败只记一条 Warn、各处循环各自持有停机制约。

判据在于，「要不要跑一个循环」与「效果要不要跨副本收敛」是两件事。「跑一个循环」各模块已经能做，「跨副本收敛」单副本的循环做不到。

## 考虑过的选项

### 把既有各模块的 ticker 一并收编进一个通用定时框架

每个模块把自己的循环注册进作业能力，由它统一驱动与停止。

**否决**：这些循环不需要跨副本收敛。刷新进程内快照刷的是每个副本自己的内存，多副本各刷各的正是需求而非重复；清扫过期行与轮转日志文件的效果本就按副本计。收编让它们凭空背上一次数据库往返、一次作业行的写入与一次认领，为的是解决它们没有的问题。收编还会把循环的启停从模块自己的 `Start`/`Stop` 挪进一个统一框架，模块失去对自身循环的直接停机制约，而现状正是每处循环各自持有停机制约。

### 把能力边界写成「任何异步执行」而不加跨副本收敛这一判据

凡事不在当前请求的协程里完成的执行都进本能力，包括进程内的后台协程与内存队列。

**否决**：去掉跨副本收敛这条判据，本能力就与「起一个 goroutine」无异。于是每一个需要后台执行的模块都要连数据库、建表、走认领，而要解决的问题——多副本下的重复执行——在单副本装配里根本不存在。判据不是「异步与否」，是「效果是否必须跨副本收敛」；一个提交即返回、效果只在本进程存在的执行，归调用方自己起协程。

### 只受理必须跨副本收敛的触发

**采纳**，见决策。

## 决策

采纳：**作业能力只承载必须跨副本收敛的触发——定时一次、周期、异步三类；单个进程内的循环触发归各模块自己的 ticker。**

- 本能力受理的触发：在某个时刻执行一次（`jobs.WithScheduledAt`／`jobs.WithDelay`）、按周期重复执行（`jobs.Schedule` 声明）、把一件耗时的事交给后台异步执行（`jobs.Queue.Enqueue` 提交后立即返回）。
- 三类触发共用一条判据：效果必须跨副本收敛——多副本部署里一次触发至多产生一个作业，执行在副本之间分摊，不因副本数增加而重复。收敛靠一张持久作业表与有时限的认领达成（[ADR-jobs-claim-2026-10-15](adr-jobs-claim-2026-10-15.md)），不靠进程内的一致性。
- 单个进程内的循环触发不进本能力：刷新进程内快照、清扫过期行、轮转日志文件、轮询外部状态各归需要它的模块自己的 ticker，形态维持现状。
- 三类触发在提交侧共用同一个 `jobs.Queue`，区别只在 `jobs.EnqueueOption`：延迟或定时用 `jobs.WithDelay`／`jobs.WithScheduledAt`，异步用无延迟的 `Enqueue`，周期由 `jobs.Schedule` 声明。

## 后果

必须跨副本收敛的触发有一处受理点，多副本部署里一次触发不再每个副本各做一遍。各模块自己不需要跨副本收敛的循环留在原地，不必连数据库。

**接受的代价：**

- 能力的边界靠一条判据——效果是否必须跨副本收敛——划定，不靠一份名单。一个新需求该不该进本能力，要按这条判据判，不能按它「像不像定时任务」来判。
- 三类触发共用一套作业模型：一张表、认领、退避与终态。一件只执行一次的异步作业与一件按周期重复的作业走同一条路径，各自特有的性质靠选项表达，模型本身不为它们分叉。
- 单个进程内的循环维持分散形态，本能力不为它们提供统一驱动，也不统一它们的间隔、失败与停机语义。
- 一个效果只在单副本成立、而部署又可能起多副本的循环，仍留在调用方一侧；本能力不替调用方判断这样的循环在多副本下会不会重复。

## 失效条件

若某处进程内循环出现了必须跨副本收敛的新需求——例如它写的不再是本副本的内存而是共享状态——该循环应由本能力承载，判据对它的答案随之改变。

若作业能力开始受理效果只在本进程存在的执行，则「跨副本收敛」这条判据已被放弃，本记录不再描述它的边界。
