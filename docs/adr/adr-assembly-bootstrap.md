# 配置在装配开始之前由宿主加载

## 背景

每个模块都需要先取得自己的配置才能构造，而配置由配置模块提供。配置模块若与其他模块同等对待，就要求它在自己被构造之前就已经可用。

配置的来源之一是命令行。命令行同时承载子命令，而子命令决定这次运行装配哪些模块（[ADR-command-tree](adr-command-tree.md)）。因此命令行的解析必须早于装配的任何一步：装配要装什么，答案在命令行里。把配置的收集放在装配流程内部，无论放得多靠前，都晚于需要它的那个决定。

保持配置模块与普通模块同构有实际价值：同一个注册表、同一份描述符、同一条“import 决定可用集”的规则，使得配置源可以像其他功能一样按需引入，不必为它另建一套加载与选择机制。

## 考虑过的选项

### 注册表先行构造配置模块

配置模块与普通模块共用注册表与描述符，不需要任何标记。注册表在 `Prepare` 阶段最先构造它，识别依据是约定的模块名，由它完成命令行与环境变量的收集、配置源的读取与全局校验。

**否决**：该时机在装配流程内部，而子命令要在装配开始之前就决定装配哪些模块。命令行解析因此无法安排在这里。这一条同时是 `core` 中唯一一处按名称识别的特例，取消它一并消除了那个先例。

### 配置加载内建于 core

配置加载不再是模块，直接实现在 `core` 中，在模块机制启动之前就已就位。

**否决**：`core` 被每一个模块 import，不含第三方依赖是它的架构不变量，而配置解析要取用成熟的解析库。配置源的可插拔性也需要在模块机制之外另建一套注册与选择机制，同一件事在项目里会有两种做法。

### 两阶段启动

先用一份最小的内置配置构造出配置模块，再由它加载完整配置驱动其余模块。

**否决**：引入了“最小内置配置从何而来”这一新问题，且启动流程需要完整运行两遍，其中第一遍的语义与第二遍不同。

### 描述符中的引导期标记

在描述符中增加一个字段，声明该模块先于配置而构造。任何模块都可以声明它，代价是放弃依赖与配置。

**否决**：为一个只有配置模块会用到的时机增加一个所有模块都看得见的字段，扩大了描述符这一对外接口的范围；泛化的形式也暗示会有第二个声明者，而实际上不会有。

### 宿主在装配开始之前加载配置

配置的加载由 `main` 发起并在装配开始之前完成：收集各模块声明的输入项，组装命令行，解析命令行、环境变量与配置源，产出读取接口。读取接口随即作为 `config` 模块的实例预置到注册表，装配开始时它已经在那里。

**采纳**，见决策。

## 决策

采纳：配置的加载由宿主在装配开始之前发起并完成，`core` 不再按名称识别配置模块。

- 加载的入口在 `main` 中显式调用，不是装配流程的一个阶段。宿主因而看得见配置何时就位，也看得见命令行在何处被解析。
- **产出的读取接口是 `config` 模块的预置实例**（[ADR-supplied-instance](adr-supplied-instance.md)）。`pkg/config` 根包登记这个只声明交付读取接口的模块，它没有 `New`，实例由宿主在装配开始之前生成并预置，读取接口因此不由任何模块的 `New` 构造。它自预置起就存在，第一个模块的 `Prepare` 之前已经可以取用，注册表不必为它另设次序。命令树的执行预置它时指名这个模块，名字取自 `pkg/config` 导出的模块名常量；注册表按名字找到登记项，与指名预置任何别的模块走同一条路径，不知道那是配置。
- 配置源与格式仍是模块机制中的资源，按 import 引入。加载发生在 `init` 之后，注册表此时已经完整，资源查询照常可用。

## 后果

循环断开的方式从“在装配内部开一个后门”变为“把加载移到装配之前”，启动流程只需运行一遍。

`core` 中不再有任何按名称识别的模块，描述符也不因这个时机增加字段。取而代之的是一个不认识配置的通用入口：注册表收下一个预置实例，把它归给一个已登记的模块，不知道那是什么（[ADR-supplied-instance](adr-supplied-instance.md)）。

命令行的解析先于装配，子命令因而能够决定装配哪些模块。

配置源作为子包按需引入：未被 import 的源，其第三方依赖不进宿主的 `go.mod`，宿主的 `go.sum` 与实际下载则会经被 import 包的测试闭包带上它们，只有读整图的操作会看到全部实现所绑的库（[ADR-module-layout](adr-module-layout.md)）。

**接受的代价：**

- 宿主的 `main` 从一次驱动调用变为显式的加载与驱动两步，最小宿主的代码量随之增加。框架对宿主的要求不再是“只写一句”。
- 读取接口只能出自宿主：`config` 模块没有 `New`，它进入参与集而宿主漏掉预置时，取用读取接口的模块得到提供者缺失的错误，推进到构造阶段的驱动轮到构造它时同样失败。不经命令树的执行发起驱动的宿主，这一步要自己做（[ADR-drive-entry](adr-drive-entry.md)）；手工搭建的注册表还要先登记 `config` 模块，才能预置读取接口（[ADR-supplied-instance](adr-supplied-instance.md)）。
- 加载无法通过 `Requires` 取得任何东西：它跑在一切构造之前。它所需的传输与格式因此经资源通道取得。
- 加载期的失败发生在日志模块构造之前，其诊断只能直接写到标准错误，无法借助装配起来的任何设施。

## 失效条件

若宿主不再需要在装配之前知道命令行的内容（例如子命令不再决定装配哪些模块），加载移到装配之前的理由随之消失，此时把它放回装配流程内部可以让宿主的 `main` 重新收缩为一次调用。
