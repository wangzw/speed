# 命令行与配置的解析委托给成熟库

## 背景

配置模块的价值在于收集各模块声明的输入项、把它们交给解析工具，并向其余模块提供统一的读取面。解析本身——切分命令行、按层叠加、把文本转换成目标类型、渲染帮助——不是这个价值的一部分。

命令行是人机界面。使用者对它的预期来自其他命令行程序：短名可以聚合，`--` 之后的内容不再当作参数解析，帮助的排布是惯见的那种。为某一处语法论证出一个"更合理"的取舍，得到的是一套只在本项目成立的方言，使用者要为它单独学习一次。

配置层叠的形态——默认值、主配置源、环境变量、命令行自低向高单向覆盖（[ADR-config-source](adr-config-source.md)）——与通行配置库的优先级模型一致，不是本项目独有的结构。

## 考虑过的选项

### 继续自建

命令行解析、类型强制与帮助渲染留在本模块内，换取根包不引入第三方依赖。

**否决**：自建的语法偏离通行约定，使用者要为本项目单独记一套规则；帮助渲染、类型强制的每一处边界都要自行维护并自行测试，而这些都是已被反复实现过的部分。根包零依赖是这笔交换的收益，代价是持续的维护面。

### 标准库 flag

不引入任何第三方依赖，用标准库完成命令行解析。

**否决**：它不区分长短名，`-verbose` 与 `--verbose` 等价，无法表达"长名双横线、短名单字符"的分工；遇到第一个非参数的词即停止解析，其后的参数被静默收进剩余参数而不报错；遇到未知参数时自行向输出写 usage。三者都与本模块需要的行为相抵。

### urfave/cli

另一套主流的命令行框架，自带命令树。

**否决**：它不使用 pflag（[REF-pflag](../references.md)），与所选配置库之间没有现成的绑定，两侧的参数定义要各写一遍并保持同步。

### kong 与 go-flags

以结构体标签声明参数，形式紧凑。

**否决**：输入项清单在运行期从注册表收集，不是编译期写定的结构体，标签驱动的形式在这里用不上。两者的使用面也明显小于所选方案。

### koanf

模块化的配置库，解析器与来源按需引入，依赖面比 viper（[REF-viper](../references.md)）小。

**否决**：依赖面的差别不足以抵消使用面的差别。选择解析工具的判据是它是否为使用者与维护者所熟悉，而不是它引入多少个包。

### viper 与 pflag

命令行解析用 pflag，命令树用 cobra（[REF-cobra](../references.md)），配置源与层叠用 viper，类型转换用 viper 自带的 mapstructure（[REF-mapstructure](../references.md)）；环境变量层除外，见决策。

**采纳**，见决策。

### 格式解析合并为一个子包

JSON 与 YAML 的解析共用一个子包。

**否决**：YAML 解析器也能解析 JSON，合并会让只用 JSON 的宿主背上 YAML 解析库，而按需引入正是子包划分的用途。

## 决策

采纳：命令行与配置的解析委托给 pflag、cobra、viper 与 mapstructure，本模块不再自行实现解析。

- **命令行语法以 pflag 的 POSIX 约定为准。** 短名聚合、`--` 终止符及其余通行行为一律照其语义，本模块不为任何一处另立规则。
- **层叠模型不变。** 自低向高为默认值、主配置源、环境变量、命令行，与既有决策一致；viper 的优先级顺序与之同构，是该决策的一个实现而非对它的修改。
- **环境变量层不经 viper 读取。** viper 每次取值都重新读一遍进程环境，而配置是启动时的快照（[ADR-config-lifecycle](adr-config-lifecycle.md)）：交给它的话，运行期改动进程环境会改变一个再次 `Decode` 的模块读到的值。本模块在加载开始时取下一份进程环境，环境变量层从这份快照里读，位置不变——主配置源之上，命令行之下。
- **本模块保留的部分**：输入项清单的收集与展开、同一命名空间内的冲突判定、每个输入项声明自己接受哪些来源、配置定位符与传输扩展点，以及供其余模块按路径取值的读取面。

## 后果

命令行的行为与通行的命令行程序一致，使用者不需要为本项目单独学习语法。

帮助输出、shell 补全、子命令的组织由命令行库提供，不必自行实现。

解析的边界情形由被广泛使用的实现承担，本模块的维护面收缩到清单与读取面。

格式解析按格式分为 `json` 与 `yaml` 两个子包。

**接受的代价：**

- 配置模块的根包不再是零第三方依赖。声明了配置的模块都 import 它，这些依赖因而落到它们各自的下游。以此换取的是上述维护面的收缩，这笔交换是明确做出的。
- 解析失败的文本由库给出。本模块只能把它归类到自己的哨兵之下，无法再逐条给出针对本项目概念的诊断。
- 帮助输出的排布由命令行库决定。分组与敏感项默认值的遮蔽不是它提供的能力，需要另行处理或放弃。
- viper 不公开"某个键的值来自哪一层"。必填判定依赖"是否有来源给出过值"这一事实，只能由主配置源、环境、命令行与宿主默认文档四处查询组合重建；默认值层中只有原型那一半不算给出，文档那一半算，这一点因而是本模块自己维持的，不是库的保证。
- 环境变量层是本模块自己读的一层。变量名的查找、空变量也算给出值，都由本模块落实，不是库的行为；层叠顺序因而写在两处——viper 的优先级，以及本模块在命令行没有给出时让环境变量压过主配置源的那一步——两处要保持一致。

## 失效条件

若所选库的语法与本模块需要的行为出现无法通过配置调和的冲突，或其维护停止，委托的前提不再成立，届时需要重新评估解析的归属。
