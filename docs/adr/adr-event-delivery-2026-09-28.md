# 事件携带发布时赋予的标识，作为消费方去重的键

## 状态

已接受

## 背景

总线不承诺投递次数（[ADR-event-delivery-2026-09-21](adr-event-delivery-2026-09-21.md)）。同一个事件因此可能到达一个订阅者不止一次，而且这是常规形态而非故障：经传输投递的实现把每个事件广播给每个副本，一次发布在 N 个副本上各被处理一次；后端可以重投一个未被确认的条目——订阅方一侧的确认在链接断开期间发出时不被客户端排队待发，条目留在未确认状态，到确认等待之后被交还持久消费者；发布方在一次读不出结果的失败之后（连接在写入之后、应答之前断开）会再发一次。

后果落在那些效果不止于本副本的订阅者身上：审计的事件路径每个副本各写一行，同一个领域事实在共享的库里留下 N 行；投影与对外回调同样被执行 N 次。它们要做到"一个事件只处理一次"，就要能认出第二次到达的是同一个事件，而事件上只有类型、租户与不透明的载荷，没有一样能认出它。

载荷由发布方决定形状，订阅方按字段名读取（[ADR-event-scope-2026-09-21](adr-event-scope-2026-09-21.md)）；横切的订阅方——审计、可观测性——不认识任何一个发布方，读不出每个发布方各自约定的字段。

## 考虑过的选项

### 不提供标识，需要去重的发布方在载荷里携带自己的键

**否决**：键的字段名与形状由每个发布方各自约定，横切订阅方要去重就得认识每一个发布方，那正是总线要消除的耦合。发布方还可能不带键，这时订阅方连"是否重复"都判断不了。租户标识放在事件上而不是载荷里，是同一个理由。

### 以后端自己的条目标识充当事件标识

Redis 的流条目标识、JetStream 的流序号、PostgreSQL 发件箱的行号，各自在本后端内唯一，订阅时可以取到。

**否决**：进程内实现没有这样的东西；各后端的形状互不相同，换后端即换了键的形状与取值，已经按旧键存下的去重记录全部失效。发布方重发一次，后端写下的是新条目、新标识，重发恰恰认不出来。发布方也无从在发布之前知道它，因而没法把它与自己的写入记在一起。

### `Publish` 返回它赋予的标识

**否决**：改变 `Bus` 的方法签名，每个实现与每个发布点都要跟着改。需要知道标识的发布方只是少数，它们在发布之前自己设一个即可，接口不必为此变形。

### 事件携带标识，发布方留空时由 `Publish` 赋予

**采纳**，见决策。

## 决策

采纳：**事件携带一个字符串标识，它是幂等消费方去重的键。**

- 发布方留空时，`Publish` 在事件离开发布调用之前赋予一个：RFC 9562 第 7 版 UUID 的规范文本形式，由本模块以标准库生成。
- 发布方设了非空值时，`Publish` 原样携带，不检查它的形状。
- 同一个事件的每个订阅者——同一副本的，其他副本的，任何一种实现下的——收到的是同一个值；后端重投的条目带着同一个值。两个标识相同的事件，在订阅方看来就是同一个事件投递了两次。
- 需要在发布之前知道标识的发布方，自己设它：用本模块导出的生成函数，或自己的键。

## 后果

幂等消费方有了一个与发布方、与后端都无关的键：审计的事件路径、投影、对外回调按它去重，就能在广播、重投与重发之下只处理一次。

**接受的代价：**

- 去重本身归消费方。本模块不记录见过的标识，不按标识拦截重复投递，也不规定去重记录保留多久；一个不去重的订阅者照旧处理每一次到达。
- 由 `Publish` 赋予的标识，发布方拿不到。一个需要把标识与自己的写入记在一起、或者要在失败后重发同一事件的发布方，必须自己设；忘了设的，重发出去的是一个新事件。
- 唯一性只对本模块赋予的标识成立。发布方自设的，唯一性由发布方负责：两个不同的事件被设成同一个值，去重的订阅方会把后一个当作重复丢掉，而这件事哪一方都看不到。
- 标识不校验形状，订阅方不能假设每个标识都是 UUID；要把它存进 UUID 类型列的消费方，得先确认发布方都用本模块的生成函数或留空。
- 每个事件在每个后端条目里多一段文本；PostgreSQL 实现的发件箱为此多一列，此前建成的表在启动时补上这一列。

## 失效条件

若接口改为承诺恰好一次投递，订阅方不再需要自己去重，标识作为去重键的用途随之消失，本记录应被取代。
