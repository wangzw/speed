# 回跳失败时把用户代理落回产品，机器码经 URL 片段携带

## 背景

社交与企业登录的回跳是用户代理的顶层导航：提供方把浏览器送回 `GET B/callback/:provider`。这条路径上的失败一律答 `application/problem+json`，这是本模块对全部失败的通则；通则没有区分导航与 API 调用，于是一个浏览器在登录被拒之后停在问题文档上，页面上只有一段 JSON，没有任何回到应用的入口。

真实发生的一例：GitHub 登录的邮箱命中一个既有账户，引擎按威胁模型答 `401 link-required`，用户看到的是 `{"type":"urn:speed:authn:link-required",...}`。登录回跳被拒时不得把用户代理留在问题文档上（REQ-signin-028）；任何回跳失败都落在同一形状上。

约束：

- 机器码的封闭词汇与语义不变，问题文档对 API 客户端仍然是唯一形状。
- 产品文案与排版归前端与 i18n 资源，服务端不渲染页面。
- 一次登录的失败不得因此多暴露超出定位所需的事实：码本身已是既有封闭集合；`link-required` 只发给已被提供方证明拥有该邮箱（企业 JIT 为其域）的调用方，且片段里附带的冲突地址由服务端掩码到首位字符与域名。
- 落地地址必须受控，不能成为开放重定向。

## 考虑过的选项

### 服务端渲染一张 HTML 错误页

引擎直接答 `text/html`，页面上有双语说明与「返回登录」链接。

**否决**：产品文案与版式归前端与 i18n 资源（[ADR-i18n-rendering-ownership](adr-i18n-rendering-ownership.md)），引擎要多一套模板、一套双语文案和一套样式，且与宿主的前端外观脱节；同一段说明会在前后端各写一次。

### 保持问题文档，由前端补救

**否决**：浏览器已经离开 SPA，落在 API 的路径上，前端没有任何执行机会。

### 落到 `return_to`

成功与失败都落到流程记录的 `return_to`。

**否决**：`return_to` 是登录成功后的目标页，不是登录面；未认证的用户被送到那里只会被准入层再拒一次，或者看到一个与自己处境无关的页面。

### 落在失败落地页，码经 URL 片段携带

回调在导航请求上答 `303` 到产品内的一个页面，把问题码放进片段；`link-required` 点名了冲突地址时，同一片段再带其掩码：`<落地页>#authn_error=<码>[&authn_email=<掩码地址>]`。

**采纳**，见决策。

## 决策

采纳：**回跳是顶层导航且登录被拒时，回调答 `303` 到产品内的失败落地页，问题码以 `authn_error` 为键放进 URL 片段；`link-required` 且拒绝点名了冲突地址时，以 `authn_email` 为键附带其掩码。API 请求的失败形状不变。**

- 判据是请求本身：只对 `Sec-Fetch-Mode: navigate` 生效，没有该头的请求照旧得到问题文档。
- 落地页按目的取：`login` 落到设置 `authn.login.callback-error-return-to`（缺省 `/`）；`link`、`step-up`、`enroll` 落到该流程记录的 `return_to`，即发起它的页面。两个来源都按 `return_to` 的既有规则校验。
- 码取问题类型 `urn:speed:authn:<码>` 的 `<码>` 一段，是既有的封闭词汇；不带码的 500 落成 `unavailable`。
- 片段而非查询串：片段不随请求发往服务器，码与掩码地址都不进访问日志，也不进页面能发出的 `Referer`。
- 落地页读不出或不合规时退回问题文档：把用户代理送到一个未经校验的地址，比留在 JSON 上更糟。
- 客户端把码按 api-client 的推导归一到 `authn.<码>`（连字符换下划线），交给登录面的内联错误渲染；白名单之外的码落通用文案。登录面为此多一个宿主注入的 `initialError` 属性，它自己不读 URL；`link-required` 的掩码地址另以 `initialErrorEmail` 注入，登录面只在码为 `authn.link_required` 时把它渲染进同一条内联错误横幅，与拒绝句一起被播报。

## 后果

- 回跳失败不再把用户留在裸 JSON 上；`link-required` 这类需要「先用原方式登录再绑定」的拒绝，现在随登录面一起出现，并给出下一步；拒绝点名了冲突地址时，登录面在拒绝句下方显示其掩码，用户由此认出是哪个地址。
- 码与 `link-required` 的掩码地址进入浏览器历史与地址栏。码属于既有封闭词汇；掩码地址只在 `link-required` 时出现，由服务端掩到首位字符与域名，且只发给已被提供方证明拥有该地址（企业 JIT 为其域）的调用方，因此它只多告诉调用方「冲突的是自己哪个地址」，不构成对陌生人的新事实暴露。两者都可以被复制与分享，这在按码排查问题的同时是接受的代价。
- 登录、邀请、控制台三处复用同一个登录面，因此都得到这条落地；宿主只需读片段并清除。
- 配置面多一个设置项 `authn.login.callback-error-return-to`。
- 不保留原目标：流程在失败时已作废，`return_to` 随之消失，重新登录后落到默认目标。为失败保留目标需要一条跨流程的载体，本记录不做。
- `link-required` 的自助解除通道（先以自己的登录方式登录，再在账户面显式绑定该提供方）不在本记录内，另议；本记录只把拒绝呈现清楚。
