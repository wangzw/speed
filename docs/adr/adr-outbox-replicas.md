# 各副本的中继以有时限的认领分摊一张暂存表，发布在事务之外

## 背景

事务发件箱的暂存表在交付的库里，多副本部署中每个副本都运行一个中继，读的是同一张表（[ADR-outbox-scope](adr-outbox-scope.md)）。约束有这几条：

- **同一行通常不应被发布两次。** 使用方按事件标识去重兜得住偶发的重复，每个副本各发一遍则是把重复变成常态。
- **副本会在持有工作时终止。** 被强行终止的副本来不及交还什么，它手里的行必须由别的副本接手。
- **一次发布可能很慢，也可能很久不返回**：后端卡住、网络断开。
- **进程内总线在 `Publish` 里同步调用订阅者**，订阅者常常经交付句柄读写库；数据库功能接受只开一条连接的库，那时持有连接的中继与要连接的订阅者会互相等待。
- **SQLite 一次只有一个写者**，持有写锁的事务让其余写者忙等。
- **副本的时钟各不相同。**

## 考虑过的选项

### 每个副本各自读表发布，不认领

**否决**：每个事件被发布的次数等于副本数，这是常规形态而不是故障；多个副本还会在删除同一行上相互竞争。

### 选出一个副本，只有它的中继工作

以会话级咨询锁选主，持锁的副本发布，其余等待。

**否决**：会话级的锁要一条长期占着的连接，只开一条连接的库上中继会占掉唯一的那条；主副本卡住而不断开时锁一直不放，其余副本无从接手，要另写一套活性检测与交接。SQLite 没有咨询锁。

### 在一个事务里锁住行、发布、删除、提交

`SELECT … FOR UPDATE SKIP LOCKED` 取一批行，逐个发布，删除之后提交；行锁在发布期间一直持有。

**否决**：发布期间持有一个事务与一条连接。进程内总线的订阅者在发布里经交付句柄写库，只开一条连接的库上等中继，中继等订阅者，一直等到上下文期限；SQLite 上这个事务持有写锁，其余写者在整个发布期间忙等；一次慢的发布让锁与连接被占用同样久。副本终止时事务随连接回滚，这一点是它的长处，而有时限的认领靠到期达到同样的效果。

### 有时限的认领，发布在事务之外

一条短语句认领一批到期的行，写下认领者与到期时刻；事务之外逐个发布；总线接受即删除，拒收即退回并延迟；到期仍未结清的行由别的中继认领。

**采纳**，见决策。

## 决策

采纳：**各副本的中继以有时限的认领分摊暂存表，发布时不持有事务与连接。**

- 认领是一条自动提交的语句，把到期的行标为本中继所有，到期时刻为 2 分钟之后，并交回这些行。
- PostgreSQL 上认领对它取的行加锁，并跳过另一个认领正锁着的行：两个认领同时进行时，行锁决定哪一行归谁，第二个认领既不取、也不等第一个正在取的行。SQLite 上不另加锁，一次一个写者使认领本身即原子。
- 时刻一律取数据库的时钟，各副本对认领是否到期的判断出自同一个时钟。
- 一次发布至多 1 分钟；一行只在它的认领剩余时间还比一次发布的上界长时才交给总线，否则剩下的行交还，重新认领。
- 停止时，中继把自己持有而未发布的行交还，立即可被认领。

## 后果

多个副本同时发布一张表时，每一行通常只被发布一次；副本终止留下的行在认领到期之后被接手；发布期间库上没有被占着的连接与锁，订阅者在只开一条连接的库上也不会等中继。

**接受的代价：**

- **终止的副本手里的行至多晚一个认领的时长才被发布。** 副本被强行终止时它认领的行要等 2 分钟；正常停止时交还，没有这段等待。
- **认领到期而发布仍在进行时，同一行可能被发布两次。** 上界让中继在认领剩下的时间不够时不再开始发布，挡住了常见的情形；一个不理会上下文期限、超出上界仍未返回的总线实现挡不住，那时另一个中继接手，使用方按标识去重。
- **数据库时钟的跳变直接作用在认领上。** 时钟向前跳，认领提前到期；向后跳，认领推迟到期。
- **每一行至少要两条语句**：认领分摊到一批，结清一行一条。

## 失效条件

若一次发布的正常时长接近认领的时长（比如一个总线后端的写入通常需要几十秒），认领到期而被接手就不再是偶发情形，重复发布会变成常态，认领的时长与发布的上界要随之重新定。
