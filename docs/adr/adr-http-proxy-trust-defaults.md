# 可信代理设置以模块级默认下发，端点可覆盖

## 背景

入口模块的可信代理网段与来源地址头名此前只能按端点声明，缺省不信任任何代理。部署在反向代理之后的装配因此要在配置里把同一对取值重复写进每个端点；漏写一个端点，那个端点上的 `c.ClientIP()` 取到的是代理的地址，按来源地址计数的层把全站算作一个来源，会话记录里的来源地址也只是代理地址。

一份部署的代理拓扑是整份配置共享的事实，不是逐端点的决定。逐端点声明让同一事实有多个副本，彼此漂移时没有信号。代理之后的来源地址还要求头名按部署选择：不同反向代理的转发头各不相同，gin（[REF-gin](../references.md)）的内建头序不覆盖每一种。

## 考虑过的选项

### 只在端点级声明

维持现状：每个端点各自写可信代理网段与来源地址头名。

**否决**：同一份部署的代理拓扑要在每个端点上重复，一处漏写只影响那个端点，启动不失败，也没有诊断指向它；新增一个端点时最自然的写法是不写，于是它默默退回到不信任任何代理。

### 默认信任全部来源

保留 gin 的默认行为，采信任何来源发来的转发头。

**否决**：`c.ClientIP()` 于是可以被任何直连客户端伪造，按来源地址计数的层与会话记录里的来源地址都失去意义；信任边界退化成「任何调用方都能声明自己的来源地址」，而入口模块无法区分代理与客户端。

### 自动探测可信代理

按连接的来源地址与常见内网段推断哪些对端是代理。

**否决**：推断出来的网段不受部署控制，与代理共用网段的主机因此获得伪造来源地址的能力；探测结果随部署环境变化，配置与运行行为不再一一对应。

### 模块级默认，端点级覆盖

配置在监听集合与端点集合之外增加一对模块级项，所有端点默认继承；端点写同名项即覆盖。

**采纳**，见「决策」。

## 决策

入口模块的配置增加两个模块级项：`trusted-proxies`（可信代理网段）与 `remote-ip-headers`（来源地址头名）。

- 端点省略同名项时继承模块级取值。
- 端点写同名项时覆盖模块级取值。写空列表也是覆盖：`trusted-proxies: []` 让该端点回到不信任任何代理，`remote-ip-headers: []` 让该端点使用 gin 内建的头序。
- 两个模块级项只从主配置源取值，与端点集合的其余键同源。
- 模块级的网段在启动时校验一次，写错即启动失败，错误点名该键与出错的那条取值。

## 后果

- 一份部署文件写一次代理拓扑，所有端点共享；新增端点默认得到与其余端点相同的取值。
- 一个端点可以单独回到不信任任何代理，用于不经过代理的流量。
- 缺省仍是空：不写这两项时不信任任何代理，与逐端点声明时的缺省一致。
- 信任名单是地址来源的过滤器，不是认证边界：列在其中的对端可以写出任意来源地址，与代理共用网段的其他主机同样能伪造来源地址。部署要只列代理独占的网段。
- 来源地址在代理正确覆盖转发头时才是客户端地址；代理采信客户端自带的头时，按该地址计数的层与展示该地址的界面承受这一代价。
- 配置新增两个模块级键，读取它们的一方获得代理拓扑，不读取的一方不受影响。

## 失效条件

- 部署中出现按请求选择代理、或代理网段变化到无法写进静态配置时，基于固定网段的信任不再成立，需要重议信任名单的来源。
