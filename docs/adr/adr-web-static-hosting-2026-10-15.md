# 静态托管与 SPA 回退独立成一个模块

## 状态

已接受

## 背景

本仓的入口模块拥有一台 gin 引擎与各监听端的链，但它不提供静态托管：一份构建好的前端产物要经 HTTP 交出，只能由宿主自己写一遍。每个要托管前端的宿主因此各自实现同样的东西——读一个目录、配缓存头、对未知路径做回退、把请求路径钉在目录之内。

前端构建产物的形状是稳定的：一个入口文档，加一棵按内容命名的资源子树。客户端路由在浏览器里，一个深链接要求服务端对未知路径回退到入口文档。

入口模块的引擎已经有一个「无匹配路由」的答复槽（`pkg/http/assemble.go` 的 `NoRoute`），它答一份 404 的 `application/problem+json`：这是 API 的未命中形状，不是 SPA 回退。

部署的常见形态：前端与后端在同一个进程里（产物内嵌进二进制，或从磁盘读），或前端另由静态主机（CDN、nginx）托管、后端只做 API。这些形态消费同一份构建产物。

## 考虑过的选项

### 把静态托管并入入口模块

**否决**：入口模块是 gin 的封装与装配面，它不承载任何具体产物，也不该知道前端构建的形状——入口文档叫什么、资源子树在哪、缓存口径是什么。把它做进入口模块，会让每个只跑 API 的宿主也背上静态托管的配置面与依赖，而它们用不到这份能力。

### 并入运行面

**否决**：运行面（`ops`：探针路由与合并后的 API 规格）回答进程自身状态——存活、就绪、这个二进制提供哪些 API；静态资源是一份构建产物的交付。两者只在都经 HTTP 暴露这一点上相交，其余没有共同职责。并且它们在同一端上并存不了：运行面登记具体路由，静态托管登记一条覆盖全端路径空间的通配路由，两者挂到同一个端上会以路由冲突启动失败。合成一个模块，只会把一个生命周期与两个互相排斥的登记面绑在一起。

### 让宿主各写各的

**否决**：缓存口径、回退语义与路径限定是会出缺陷的地方——路径限定出的是安全缺陷，陈旧资源被缓存钉住出的是运维缺陷。让每个宿主重复发明这几件事，等于把这些缺陷按宿主数复制一遍，而它们本可以被定在一处。

### 静态托管与 SPA 回退独立成一个模块

**采纳**，见决策。

## 决策

采纳：**静态托管与 SPA 回退独立成一个模块。**

- 模块以 `fs.FS` 接收构建产物，由装配方提供——内嵌部署传 `embed.FS`，从磁盘部署传 `os.DirFS(dir)`。模块不认识任何具体应用的产物。
- 模块 `Requires` 入口模块的 `Router`，在配置点名的端上登记一条覆盖该端路径空间的 `GET` 与 `HEAD` 通配路由。
- 回退语义与缓存口径是这条决策引出的设计，落在 design-webui，本条不重述。
- 入口模块的无匹配路由答复保持不变。它是 404 的问题文档写出器，不承载 SPA 回退。

## 后果

宿主只要给它一个 `fs.FS`，就能在进程内托管前端。同一个模块在内嵌拓扑与分离拓扑下都成立：内嵌拓扑里它把产物答出去，分离拓扑里同一份产物交给静态主机、后端进程不纳入本模块。

路径限定与回退语义只实现一处，宿主不再各自发明。

**接受的代价：**

- **静态托管独占它点名的端。** 该端上不能同时登记别的路由：gin 的路由树拒绝一条通配路由与任何具体路由并存，宿主把两者挂到同一个端上是启动失败（`http.ErrRouteConflict`），而不是静默地让其中一个失效。要在同一个端上同时给出 API 与前端，只能把它们分到不同的端，或在前面放一个反向代理。
- **模块对产物的目录形状有约定。** 入口文档名与内容寻址子树的目录名是约定的（子树的目录名由配置项给出，缺省 `assets`）。构建工具改了它们的名字或布局，装配方要在配置里跟上。
- **不压缩、不指纹。** 本模块不认识产物内容，因而不能替宿主做压缩或指纹；压缩与指纹是构建工具的职责，宿主若要在传输时压缩，要在前面放一层。
- **从磁盘装配的产物随进程启动时点而定。** `os.DirFS` 下每次请求读盘，产物在启动后补齐或替换能被看到；`embed.FS` 下的内容固定在二进制里，重新构建前端要重新构建二进制。这些拓扑对「前端热更新」的支持因此不同，这一点随所选拓扑而来，不是可配置项。

## 失效条件

- 入口模块的路由机制若能让「先匹配具体路由、再回退」不必要求通配路由独占一个端，则「独占一个端」这条代价随之消失，本决策要重新评估。
- 前端产物若不再呈现「入口文档加内容寻址子树」的形状——例如改为服务端渲染、或改为另一套命名与分片——回退与缓存口径的约定要重订。
