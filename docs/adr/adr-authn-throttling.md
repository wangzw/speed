# 认证前的失败退避与枚举防护：db 的 Throttle，账户级静默，口令表进程内

## 背景

登录、因素校验、短信验证码与服务账户的令牌换取都在调用方尚未被认定之前接受输入，口令与验证码是低熵秘密，次数不受约束就等于任由暴力破解与撞库。要约束次数，先要定下计数落在哪里、计数的键是什么、约束生效时调用方看到什么。

**现成的限流用不上。** `pkg/ratelimit` 排在认证之内，取不到身份的请求一律放行，计数维度只有租户与责任键，`Limiter` 只是别的层据以定序的标识、不可调用（见限流的设计文档）。认证前的请求没有身份，登录请求不带租户。取向也相反：计数后端不可达时限流放行，且被明说不是架构的安全边界（[ADR-ratelimit-failure](adr-ratelimit-failure.md)、[ADR-ratelimit-boundary](adr-ratelimit-boundary.md)）。登录退避约束的正是口令猜测次数，它的计数一旦读不到，放行即放宽上限。

**计数的存放由状态放置的判据决定。** 丢失会放宽校验的状态进 db（[ADR-authn-state-placement](adr-authn-state-placement.md)）。退避计数归零等于恢复攻击者的全部尝试额度，属于这一类；它要在重启之后保留，在多副本之间一致。

**枚举防护约束计数的键与应答。**

- 凡可能泄露账户、标识或号码是否存在的分支，应答的形状与耗时须同形。分支的列举是例举，判据是该分支的差别可被调用方观察到；未知标识、错口令、停用、退避中都在其内。
- 429 与 401 的差别本身就是存在性的信号。
- 键若取「账户」，未知标识没有账户可计，已知与未知标识就走不同的计数路径。
- 口令校验是内存与时间密集的派生；未知标识若不做等价派生，耗时差同样暴露存在性（口令条目的格式与派生参数见 [ADR-authn-password-hash](adr-authn-password-hash.md)）。

**口令表有自己的约束。** `authn.static` 认领 `Basic`（[ADR-authn-credential-dispatch](adr-authn-credential-dispatch.md)），表在配置里，是 db 故障时的运维后路。它的主体名（例如 `ops`）与账户的登录名可以重名。它的口令逐请求出示，每个请求都是一次认证，成功与失败都以请求的速率发生。

**入口模块默认不信任任何代理头**：端及其继承的模块级默认都未列出可信代理时，`ClientIP()` 是连接的对端地址（design-http）。按来源地址计数的任何层，在这样的代理之后把全站看作一个来源。

## 考虑过的选项

### 复用 `pkg/ratelimit` 做认证前限流，口令表同样复用

在限流模块里加认证前的维度，或让登录路径调用它。

**否决**：限流在链上排在认证之内，要让它在认证之前生效，整条链要重排，而它的责任键维度对没有身份的请求无从取值。`Limiter` 不可调用，登录引擎拿不到按调用传入键的入口。取向与退避相反：限流在后端不可达时放行，退避要求读不到计数就不放行校验。口令表的 `Basic` 失败发生在身份产生之前，同样没有责任键可计。

### 退避按账户计，对外返回 429

计数键取已解析出的账户，到阈值后对该账户的请求答 429。

**否决**：已知账户得 429，未知标识永远得 401，匿名攻击者据此区分账户存在与否。未知标识没有账户，也无从计数，这等于对未知标识不设次数约束。

### 只按提交的标识字符串计，没有账户级

键只取提交内容的规范化形式，不再按账户累计。

**否决**：同一个账户可由多种拼写指到（登录名、已验证邮箱、已验证手机号与各自的规范化变体）。攻击者轮换拼写，每种拼写各得一份尝试额度，有效次数随拼写数倍增。它也不消除自我拒绝服务：攻击者对受害者的某一种拼写连续失败，该拼写照样被退避。

### 退避期内照常派生，再按结果放行或返回 429

退避期内仍对提交的口令做派生与比对。

**否决**：比对为真即放行，则退避不约束猜测次数；比对为真仍拒绝，则攻击者在退避期内继续驱动每次内存密集的派生，退避起不到减负作用。

### 退避计数放 kv，或放进进程内

计数用 kv 的原子递增加过期，或每个副本在内存里自己算。

**否决**：kv 的淘汰、重启与实现的丢键行为都使计数归零，归零是放宽（[ADR-authn-state-placement](adr-authn-state-placement.md)）；进程内则每个副本各算一份，重启清零，有效尝试次数随副本数放大。kv 与进程内都不满足「重启保留、多副本一致」。

### 口令表沿用账户后端的写法：成功时清零

口令表的退避与账户后端同形：失败时记一次，成功时把计数清零。

**否决**：口令表的口令逐请求出示，每个请求都是一次认证，成功因此频繁发生，而且不由攻击者独占：持有共用该键的另一条条目的口令的人（键折叠大小写与空白，只在大小写上不同的主体名共用一个键），以及该主体合法使用者的日常请求，都能在两次猜测之间产生一次成功。每次成功把计数拉回零，攻击者把猜测夹在其间，计数到不了自由次数，退避永不生效。账户后端没有这个问题：登录是换会话或令牌的流程，成功之后的请求带的是会话或令牌，不再出示口令。

### 检查、派生与记失败分开执行

先检查是否在等待，再派生，派生之后才记失败。

**否决**：检查、派生与记失败之间没有原子性：并发到来的错误口令在第一次失败写入之前都通过检查，每一个都去派生，免费的尝试数的上界是派生的并发宽度，不是自由次数；并发宽度为 64 时，64 次错误口令全部派生。

### 成功只衰减，不清零

成功校验把该键的失败计数减去一格，或按比例缩小，不归零。

**否决**：成功仍然是一根可以拉动的杆。减去的量不小于一次失败时，每一次成功抵消一次猜测，计数不再增长，退避同样不生效；小于一次失败时，也只是把抵消一次猜测所需的成功次数乘以一个常数。成功的来源不由攻击者独占，口令表的缓存又使命中的成功不付派生成本，猜测的速率因此始终与成功的速率挂钩，不被自由次数封顶。失败才记数、时间才衰减，这条规则没有可以调节的参数。

### 清零前要求真实派生且距上次失败已过一个窗口

成功只在这次成功来自一次真实的派生而不是缓存命中、且距该键最近一次失败已过一个窗口时清零。

**否决**：「距最近一次失败已过一个窗口」这个条件使清零什么也没有清。键没有在等待时才可能有成功，而窗口已过、该计数赚得的等待也已走完时，计数按时间老化本来就归零，成功清不清零不改变任何结果；窗口之内条件不满足，成功不起作用，与采纳的做法等价。留下的只有一份要维护的额外判定：区分真实派生与缓存命中，以及一次与老化规则重复的窗口比较。

### 命中校验缓存的口令也预占一次尝试

口令表里每一个到达的口令，包括缓存里记着的，都在检查的同时预占一次尝试，通过之后退还。

**否决**：缓存里只有已经真实派生通过的口令，命中的不是猜测，预占对它没有防护价值。预占使同名的在飞尝试互相计数，同名的命中请求并行度越过自由次数之后，持续出示正确口令的客户端被退避拒绝，而这些请求没有猜测任何东西。命中的口令仍要过一次只读的等待检查，一个因失败而在等待的名字不因口令正确就被放行。

### 退避键加对端地址

退避键由主体字符串的摘要加上连接的对端地址组成。

**否决**：未配置可信代理时 `ClientIP()` 是对端地址，代理之后所有调用方共用一个对端，键里加地址等于没加；配置了可信代理时来源地址来自请求头，攻击者每换一个来源地址就得到一份新的自由次数，有效次数随其可用的地址数倍增，而来源地址可以成段获得，例如一个 IPv6 前缀。键含地址还使「表里主体的键是固定键」无法成立：固定键要在建表时就知道全部键，含地址的键空间没有上界，喷洒不同地址即可把表内主体的计数挤出。

### 诱饵 PHC 在进程启动时生成一次

标识不存在时，对启动时固定下来的一条诱饵条目做派生。

**否决**：运行期改了哈希参数之后，已知账户按新参数派生、诱饵停在旧参数，耗时差随之出现，暴露账户存在。

### 来源地址限流缺省开启，并作为主要防线

登录入口按对端地址计数，缺省生效。

**否决**：未配置可信代理时 `ClientIP()` 是对端地址，开启后在代理之后的全站共用一个桶，一个来源的失败使所有人受限，是对自己的拒绝服务。作为主要防线还要求计数后端恒可用，而它在 kv 里，丢失会放宽。

### `authn.static` 在 db 在场时改用 db 的 `Throttle`

口令表与账户后端共用同一套退避实现与参数。

**否决**：db 不可用时 `Throttle` 读不到状态，登录路径整体 503，运维后路随 db 一起不可用；`ops` 与账户的登录名落在同一键空间，互相触发退避；`Throttle` 不接收按调用的参数，口令表与账户各有一组参数时，哪一组生效没有定义。

### db 的 `Throttle`，键取提交内容的摘要，账户级静默，口令表恒用进程内退避

**采纳**，见决策。

## 决策

采纳：认证前的失败退避由 authn 自备，不经 `pkg/ratelimit`；账户后端的退避状态放 db，口令表的退避恒在进程内。算法与表的细节由 design-authn-login 与 design-authn-account 承载，设置键与取值域由 design-authn-config 承载，本记录只定判据。

**计数的键。** 账户后端的退避按提交内容规范化形式的摘要计数，与账户是否存在无关：未知标识与已知标识走同一条计数路径。成功使计数清零，并发的失败不丢计数；口令表的写法不同，见下。

**退避期内不派生。** 退避期内的尝试不派生、不比对，直接拒绝。

**可见度按键的来源划分。**

- 标识级退避（键是提交的字符串）对调用方可见：429，带 `Retry-After`。
- 账户级退避（键是已知账户，不论提交了哪种拼写）静默：到阈值后仍照常做诱饵派生，返回统一的 `ErrInvalidCredentials`，不返回 429。账户级计数只在账户已知时累计。

**枚举防护的同形措施。**

- 标识不存在时，对一条诱饵 PHC（[REF-phc-string-format](../references.md)）做一次等价派生。诱饵的参数始终跟随当前的哈希设置，设置变更之后重建，不在启动时固定。
- 统一失败的适用范围是例举，判据是分支的差别可被调用方观察到：口令、验证码、因素、断言不成立，以及账户不存在、无口令、已停用，都在其内；新增的失败分支按同一判据归入统一失败。

**来源地址的前置减负**放 kv，按来源地址限制每分钟发出的验证消息数，缺省 60 条，改到 0 时关闭并在启动诊断里点出。检查在请求入口、调用方法之前做，计数由调用报出的发送条数累加，因此超限的请求不会发出消息。它是权威退避之前的一层粗粒度减负，不承担防线：kv 不可用时跳过该层并留 Warn 与计数，权威退避在 db，放宽的上界是自由次数。

**口令表。** `authn.static` 的退避恒用进程内实现，不取 db 版 `Throttle`。键是出示的主体字符串规范化形式的摘要，与存在与否无关，键空间与账户的标识范围分开；参数与账户后端的参数各自生效、互不影响。

- 并发到来的尝试互相计数：免费的尝试数由自由次数封顶，与派生的并发宽度无关，所以检查与记账不得分作互不原子的几步。
- 只有猜测计入失败：没有给出答案的派生，以及命中校验缓存的口令（缓存里只有已经通过的口令），不留失败，也不与别的尝试互相计数。
- 成功不抵消失败：此前的失败只随时间老化，窗口与退避曲线沿用账户后端的形状。
- 进程内的表有容量上界，口令表里主体的键不被挤出。

**依赖不可用时的方向。** 账户后端读不到退避状态时，登录路径拒绝、不校验；口令表不受 db 影响（失败语义的全表见 design-authn-failure）。

**表行数有界回收。** 退避状态的键与账户是否存在无关，匿名攻击者用随机用户名即可使每个失败请求多出一行；`authn.account` 因此持有有界的后台清扫，回收已衰减、且未处于锁定期内的行，多副本并行运行互不冲突。缓解措施是 `ratelimit` 的地址盾（按来源地址限制单位时间内的请求数，在身份确定之前生效）、入口层限流与这一清扫；登录路径的前置减负按发出的验证消息计数，不约束不发送的请求的速率，不给这一项上界。行数上界写为非保证（[ADR-authn-guarantees](adr-authn-guarantees.md)）。清扫的条件与批量见 design-authn-account。

## 后果

退避状态在重启之后保留，多副本一致；已知与未知标识的计数路径、应答形状与派生耗时同形；口令表的运维后路不随 db 一起不可用。

**接受的代价：**

- **自我拒绝服务。** 匿名攻击者对任一已知标识连续失败，可使该账户的口令登录不可用的时长至多为退避上限，上界有限、不是永久锁定。换一种标识拼写不能绕开账户级那一层，所以换拼写不是缓解；运维主体同样受影响（`static.ops` 受口令表自己的进程内退避约束）。受害者仍可用短信、社交、SSO、通行密钥登录。账户级计数正是挡「轮换拼写以放大尝试次数」的那一层，这一代价与枚举防护同源，不可分开取舍。
- 账户级退避静默，被退避的合法用户看到的是普通的登录失败，不知道原因，只能等候；察觉途径是退避开始时发布的事件、日志与计数器（design-authn-events）。
- 登录尝试不经人机验证：人机验证闸的是发送，闸不到开始登录流程（[ADR-authn-human-verification](adr-authn-human-verification.md)）；开始登录流程不要求凭据，入口层面的限流是宿主的部署责任。
- 缺省下按来源地址限制每分钟发出的验证消息数（`authn.login.ip-limit` 为 60），它计数的是发出的消息，不约束不发送的请求的速率；匿名洪泛的请求速率只受退避与入口层限流约束。未配置可信代理时，代理之后全站共用一个桶，一个来源用尽额度会使该桶内的请求在本窗口内被拒。
- 随机标识洪泛使退避状态的行数随失败请求速率增长，到清扫回收之前一直占用存储。
- 已知账户的哈希参数弱于当前设置、尚未随登录升级时，派生比诱饵快；诱饵的重建随设置变更传播，传播之前诱饵停在旧参数。这一耗时差存在于设置变更之后到账户下次登录（或诱饵重建）之前，上界是新旧参数之差。改哈希参数是受控变更，这一窗口写为非保证。
- 口令表的成功不清零：越过自由次数的名字，即便随后出示正确口令，也要等失败老化之后才通过，与账户后端不同；一个被持续猜测的主体，它的合法使用者在这段时间里同样被拒。
- 要派生的尝试在同一名字上互相计数：同时在飞的数目越过自由次数之后，超出的尝试以退避拒绝，即使它们出示的口令都对。并行发请求的口令表客户端在缓存未命中、需要派生时可能触到这个上限；命中缓存的尝试不预占，不受它影响。
- 口令表的失败计数表满时，被挤出的非固定键丢掉它的计数：喷洒足够多别的名字的调用方，可以让一个不在表里的名字重新得到自由次数；表里主体的键是固定键，不受影响。
- 口令表在多副本下的退避每副本各算一份，有效尝试次数放大为副本数倍；口令表的用户名因对不在表里的名字快速拒绝而可被枚举，这是口令表一直接受的代价（[ADR-authn-credential-dispatch](adr-authn-credential-dispatch.md)）。
- 账户后端与口令表各有一组退避参数，运维要分别调整。
- db 不可用时账户后端的登录整体 503，不因退避状态读不到而放行。

## 失效条件

- 部署在代理之后的装配普遍配置了可信代理、`ClientIP()` 反映真实来源成为常态时，来源地址前置减负取 60 这一缺省值所依赖的「共享出口留有余量」不再需要，需重议其缺省与定位；口令表的退避键是否加对端地址的否决理由随之失效，要一并重议。
- 部署要求受害者能自助解除退避、或要求登录本身经人机验证作为强制步骤时，静默账户级加有界退避的形状不足，需要重议；自我拒绝服务的上界（退避上限）被部署判为不可接受时同样重议。
- 口令表需要在多副本间共享失败计数时，进程内退避不足，需要另立一份计数落点，并重新核对「口令表不随 db 不可用」这一前提。
- 部署判定口令表主体在被猜测期间合法使用者被拒不可接受时，成功不清零的形状不够，需要重议；区分来源的做法要先配置可信代理，让来源地址可信，见「退避键加对端地址」的否决。
- 假设：并发错误口令的免费尝试数由自由次数封顶。守住它的是同一名字上并发宽度大于自由次数的错误口令测试，被派生的次数与并发宽度无关；该测试失败即回到本决策重议预占的写法。
- 假设：缓存里记着的正确口令不被同名在飞的尝试拒绝。守住它的是同一名字上并发宽度大于自由次数的命中缓存的测试，全部通过；该测试失败即回到本决策重议命中缓存的口令是否预占。
- 假设：单语句原子递增在各个方言下对并发失败不丢计数。守住它的是并发失败的测试，该测试失败即回到本决策重议计数的写法。
- 假设：随机标识洪泛之后，清扫能把退避状态的行数回收到洪泛前的量级。守住它的是洪泛后回收的测试；清扫速度长期跟不上失败请求速率时，行数上界需要改为硬性约束。
- 假设：账户级阈值触发之后，另一种拼写加正确口令的结果与同一拼写一致，仍被拒。守住它的是该场景的测试。
- 假设：设置变更之后诱饵确实被重建，已知账户与未知标识的派生耗时不随运行期改参而分叉。守住它的是改参前后已知账户与未知标识的耗时比较测试。
