# 遥测模块只装配上游 SDK 的 provider，不定义信号语义

## 背景

运行期的日志、指标与追踪不由 `pkg/core` 提供，它们是各自模块的事，其中只有日志指给了具体模块（架构文档的跨切面设计一节）。`pkg/log` 的非职责一节写明它只承担日志这一种信号，不提供追踪与指标（`log` 的设计文档）。指标与追踪在权威文档里没有归属。

命令树的记录写到遥测的用途，也没有指给谁：它的背景把遥测举成「子命令决定装配哪些模块」的例子，迁移不需要遥测，不该因为遥测的某个必填项没给而启动不起来（[ADR-command-tree](adr-command-tree.md)）。这条预设下，遥测自带必填项与参数，且只为纳入它的命令付代价。

上游遥测库已经定义了跨度、属性、仪表、采样器与传播格式。本模块与这些类型的关系，以及它交付到哪一步，是本记录要定的。

## 考虑过的选项

### 自持信号语义

本模块自己定义跨度、属性、仪表、采样器与传播格式的接口，上游库退为实现子包。

**否决**：架构不变量 11 已经把「遥测模块之于追踪的 API 包」写成既定的封装范例，理由是另造一层等价抽象只会让依赖方在两套类型之间来回转换（架构文档）。打包决策里的「接口包另造一层等价抽象」同样被否决，判据同源：抽象与被封装库的能力一一对应时，它不隔离任何东西，只给同一组概念起第二套名字，还要随被封装库的演进同步扩张（[ADR-module-packaging](adr-module-packaging.md)）。

### 把日志一并纳入，做成一个「三信号」模块

三种信号由同一个模块交付。

**否决**：日志已经是一个独立功能目录，已有实现，已有一批模块声明对它的依赖。合并会把日志的全部既有契约推到一次重写上——格式与目的地、脱敏、上下文关联字段、写入者去重与引用计数（`log` 的设计文档）；而两者没有任何共享的装配接口，日志的形态是处理链，追踪与指标的形态是 provider 加导出器，合并只让一个配置命名空间变大。

### 只做追踪，指标留给以后

本模块先交付追踪，指标留作下一步。

**否决**：指标在权威文档里本就没有归属，留到以后等于把它继续悬空。

### 交付上游库的 provider 加上本模块自己的采集

本模块交付上游遥测库的 provider、请求路径的采集与一条出站注入工具，信号的语义本体仍由上游库定义。

**采纳**，见决策。

## 决策

采纳：**遥测模块只装配上游 SDK 的 provider，不定义信号语义。** 交付范围与排除范围见本模块设计文档的职责一节。

## 后果

依赖方直接用上游库的类型取用追踪与指标，上游生态——它的插件、扩展点与围绕它的既有代码——不经转换即可使用。

**接受的代价：**

- **覆盖面止于既有扩展点够得着的地方。** 数据库的语句级跨度、拉取式指标端点与性能剖析都要新的扩展点才谈得上，本模块不提供它们，不提供意味着这些方面继续没有任何信号。一个要按语句定位慢查询的宿主从本模块拿不到东西，要等一个包装 `database/sql` 驱动接口的实现子包；一个要让既有监控系统抓取指标的宿主只拿到推的途径，不拿到可挂到路由上的处理器。
- **模块的职责边界随上游库的能力走。** 上游能表达的信号本模块可以装配，上游表达不了的——例如跨进程序列化格式之外的关联手段——本模块也造不出来。上游库的一次破坏性升级因而同时改变本模块能装配的集合与对外接口的类型，这一层无法在模块内部消化。
- **信号的命名与形态没有承接者。** 属性取什么名、仪表怎么聚合、业务指标叫什么，由产生信号的模块与上游库给出，请求路径的采集产出的计量与跨度属性取自上游采集库，本模块不持有一份自己的属性表（[ADR-observability-instruments](adr-observability-instruments.md)）。两个模块对同一个业务概念取不同的指标名，没有一层会拦下；要一份全进程一致的指标目录，本模块给不出。
