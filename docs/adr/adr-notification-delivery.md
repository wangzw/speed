# 出站投递经持久队列异步进行，逐渠道一个去重键，notification_sends 是幂等与结果账，短信预算与认证共用台账，邮件预算留在键值计数器

## 背景

一条通知经一个或多个渠道送出。每个出站渠道是一次外部调用：邮件经 `pkg/mail` 的 `Sender`，短信经 `pkg/sms` 的 `Sender`。这类调用具有下列性质：

- **慢。** 一次厂商调用可能耗时数秒，也可能挂住到上下文到期。
- **可能失败。** 通知投递失败时的重试要求见（REQ-notifications-020）。
- **不幂等。** 厂商的发送接口不按调用方标识去重，超时之后无从知道是否已送达（与 `pkg/sms`、`pkg/mail` 的 `ErrUncertain` 同一条判据）。

约束如下：

- **站内信是写一行**，不依赖任何外部厂商；写行之后投递流水线发一条收件箱创建事件（[ADR-notification-stream](adr-notification-stream.md)）。
- **一次投递里各渠道的结果要分别可见。** 站内信成功、短信失败是寻常情形，两者不能挤到一个结果里。
- **多副本要收敛。** 投递作业分散在各副本上执行，崩溃后由别的副本接手，同一条作业可能被执行不止一次（[ADR-jobs-claim](adr-jobs-claim.md)）。
- **去重键按渠道派生。** `idempotency_key = hex(sha256(canonicalJSON{tenant, type_key, recipient_class, user_id, channel, locale, occurrence_id, params}))`，逐渠道各一个；同一逻辑事件的重发共用同一个 `occurrence_id`。
- **短信预算要约束部署的总发送量。** 通知投递的短信与认证的验证码花的是同一个部署的同一份短信容量。一个只按通知渠道计的键值计数器答不了两者之和，厂商却按总和计费（[ADR-authn-sms](adr-authn-sms.md)）。
- **一次发送的预算要先占用、后发送。** 投递是异步的，发送发生在消费者里；预算若在消费时才计，一个超限的生产者仍可无限入队，队列本身没有上界。
- **通知侧的发送也会确定失败。** 接缝缺席、模板或参数不成立、载体限流、拒绝或送不到，都说明消息没有离开进程或没有进入厂商管线；这些情形应退还发送预算。

## 考虑过的选项

### 在请求路径上同步发送

业务模块的提交面调用直接把各渠道发出去，厂商返回后再返回给调用方。

**否决**：一个慢厂商会把请求拖住，请求耗时因此取决于最慢的一个外部厂商；失败没有重试的落点，一次请求失败即一条通知丢失，或要调用方自行重试——而重试会重复投递一个不幂等的渠道。

### 站内信也经队列

站内信不在投递流水线里写，也经一条投递作业完成，由消费作业的一方写行。

**否决**：站内信是写一行，队列只值一个通知——它换不来重试、换不来去重，因为写一行本就可以在一个已提交的事务里完成。收件箱行落库之后再发 `notification.inbox.created` 事件，已经给出站内信的延迟下界；再经一次队列只增加延迟而不增加任何保证。

### 不落账，只靠队列的幂等键

投递结果不写自己的表，去重与结果都靠 `pkg/jobs` 的作业行作答。

**否决**：跨渠道的结果要分别可见，而作业行答的是「这条作业的结果」，答不出「这条作业里这个渠道这一次的结果」；且渠道调用不幂等，超时后无从知道是否已送达，作业行的状态表达不了「这一渠道已调用过、结果未知」。落账因此是本能力自己的事。

### 保留键值计数器，另加一条共享的跨渠道上界

按收件人与按租户的预算继续走键值计数器，跨渠道上界从共享台账读。

**否决**：同一次发送要在两处计数，两个来源对「这次发送算不算」给出不同答案；退还一次确定失败的发送时，键值计数器与台账各退一次，任何一边漏退还使两边不一致。跨渠道上界也只能由台账回答，键值计数器提供的第二个上界只增加一处会漂移的状态。

### 键值计数器与共享台账双写

通知保留已有的键值预算，同时把同一次发送写进共享台账。

**否决**：双写不产生单一事实来源；漏写、重写与退款不同步都会让两个数分叉，而排障的人读不出哪一个对。

### 把邮件预算也移进共享短信台账

邮件与短信共用一套台账与计数，`kv.KV` 整体退役。

**否决**：共享台账是短信尝试的账，它的跨渠道上界约束的是部署的短信容量；把邮件投递写进去会把邮件算成短信发送，既占用短信厂商的额度，也让两个渠道的退款与抑制语义相互干扰。邮件没有需要与认证合并的容量，它的按收件人与按部署预算留在键值计数器上即可，同一条邮件投递不会同时记在台账与计数器两处，不存在两个事实来源。

### 在消费者里计预算，不在提交面计

投递入队时不占预算，作业被消费、真正要调用载体时才计。

**否决**：提交面是唯一的生产者入口，入队不计数就使队列本身没有上界；一个超限的调用方可以先把队列灌满，预算只在消费者里拦住发送，队列与存储仍被占满。预算计在提交面，与入队同一个动作。

### 通知的尝试预算只计确定失败，与认证同一条判据

通知的按租户尝试预算只计载体确定没有收下的发送；认证的尝试预算正是这样计的。

**否决**：认证的尝试预算计的是猜码的人，成功的那一次不该记在攻击者名下，所以只计事后退款的行。通知的调用方是生产者本身，尝试预算防的是它陷入重试循环：一次重试风暴里的尝试可能每一次都被载体接受，也可能每一次都确定失败并退还发送预算，只计确定失败会让风暴在尝试窗口里消失。通知的尝试预算因此计每一次尝试，不论载体是否接受、发送预算是否已退还。

### 出站投递经持久队列异步进行，逐渠道一个去重键，落 notification_sends 账，短信预算写共享台账

**采纳**，见决策。

## 决策

采纳：**出站投递经 `pkg/jobs` 的持久队列异步进行；逐渠道派生一个去重键；`notification_sends` 是幂等与结果账；短信发送预算写进与认证共享的台账，并读同一条跨渠道上界；邮件发送预算留在键值计数器的固定窗口上。**

- **`Dispatcher.Dispatch` 只校验、计预算、入队。** 它校验一条 `Dispatch` 的类型在分类法内、载荷参数在类型的白名单内，核对派发携带的目的地属于收件人，在有效渠道里含邮件且本装配能发邮件时计一次邮件预算，含短信且本装配能发短信时计一次短信预算并写一行台账，然后把这条投递入队为一条作业；自己不写 `notification_sends`，不渲染、不发送。
- **投递消费作业。** 投递模块登记一个 `jobs.Handler`，消费作业时逐渠道发送；站内信写一行，邮件与短信经各自接缝发送。作业载荷携带提交面写入的台账行标识。
- **逐渠道去重。** 每次发送前按该渠道的去重键查 `notification_sends`，命中 `succeeded` 或 `skipped` 行即返回既有结果、不再调用接缝，命中 `failed` 行则这一次重新发送。唯一索引 `(tenant_id, idempotency_key)` 使同一去重键至多落一行。
- **落账。** 每次发送的结果连同耗时、错误、厂商回执标识落一行，`status` 取闭集 `succeeded` / `failed` / `skipped` 之一。
- **站内信与出站渠道在同一流水线里分叉。** 一次投递里，站内信那一项写 `in_app_messages` 行，创建事件由收件箱在提交那一行之后发布；出站渠道那一项走接缝。
- **短信预算写共享台账。** 台账是 `sms.budget` 交付的 `budget.Store`，表 `sms_budget_events`，与认证共用。一次短信尝试写一行：渠道 `notification`，用途取通知类型键，目的地取（租户，收件人标识）的摘要，租户取上下文里的租户，账户取收件人标识，结局在提交时写 `pending`。来源没有可信值，不写来源摘要，也不计来源维度。
- **预算维度与判据。** 部署的跨渠道小时上界 `sms.ceiling-hourly` 先于其余每一项；然后依次是每收件人小时、每收件人每日、每租户不同目的地小时与每租户尝试小时。跨渠道上界与收件人、租户的发送窗口只计未退款、未抑制的行；每租户尝试窗口计每一次尝试，退款与否都计。通知侧不产生抑制行。
- **先占后发、确定未发就退还。** 提交面在入队之前计预算并写台账行；入队失败或载荷编码失败即退还该行。消费者在接缝缺席、本站拒绝（缺模板、参数或目的地、模板解不出）以及载体确定未收下（限流、拒绝、送不到）时退还该行；结果不确定与闭集之外的错误保留，因为消息可能已经发出。
- **跨渠道上界与认证共用一把锁。** 提交面在计跨渠道上界与写台账行时取 `sms.budget:lock:ceiling`，认证侧在同一个键上取同一把事务级咨询锁；两个渠道因此不会同时读到上界以下、再各写一行。SQLite 在数据库层串行化写者，不取这把锁。
- **短信预算只走共享台账，邮件预算只走键值计数器。** 短信预算计在 `sms.budget` 的共享台账上，不读键值计数器，也不把旧计数写进台账；短信的跨渠道上界由 `sms.ceiling-hourly` 给出，没有数据迁移。邮件预算计在 `kv.KV` 的固定窗口计数器上：按收件人小时、按收件人每日与按部署小时，`notification.delivery.global-hourly` 由它读取，`kv.KV` 因此是本模块的硬依赖。
- **设置。** 本模块在 `notification.delivery` 命名空间下声明每收件人小时、每收件人每日、部署范围小时、每租户不同目的地小时与每租户尝试小时；前三个约束邮件的键值计数器，每收件人小时与每日同时约束短信台账，两个渠道各用各的计数；跨渠道上界由台账模块在 `sms` 命名空间下声明一处。这些设置读不出或越出取值域时回落到声明缺省，方向仍是一个上界。

## 后果

一次投递的每个渠道各有一个可查的结果与一个稳定的去重键。同一条投递作业被执行不止一次时，已成功的渠道不再重复发送；一个渠道超时、结果未知时，账上留下一行带 `failed` 的记录，重试由队列按退避进行。短信的发送预算与认证数同一批行，部署的跨渠道上界约束两者之和；一次确定未发出的短信退还发送窗口，却仍计一次尝试。

**接受的代价：**

- **投递延迟从一次请求的往返变成一次队列的轮询周期。** 站内信因此不在请求返回时就已经在收件箱里，而在投递流水线取到作业并写行之后。
- **投递模块依赖 `pkg/jobs`，其正确性受作业队列的至少一次语义约束。** 同一条投递作业可能被消费多次，幂等落在 `notification_sends` 的唯一索引上；少了这张账，重复消费会造成重复投递一个不幂等的渠道。
- **`notification_sends` 随投递量增长。** 本能力不设清理策略，这张表要么由宿主清理，要么一直增长。
- **去重键包含载荷参数。** 同一逻辑事件若用不同的参数重发，会被当作两次投递；要收敛成一次，发布方要对重发使用同一个 `occurrence_id` 与同一份参数。
- **一个渠道的结果未知时账上记 `failed`。** 超时不代表没送达，消费者读到 `failed` 不能断言那次发送没有生效。
- **预算按一次 `Dispatch` 调用计，不按一个逻辑事件计。** 重复入队的同一次逻辑事件在入队之前各自占一次预算；能调用提交面的调用方本就可以改 `occurrence_id` 造出不同作业，约束是预算本身，去重不承担这个职责。
- **短信预算的占用早于发送。** 一次投递在提交时占一行；作业在队列里等待期间，这一行已计入发送窗口与跨渠道上界。队列积压因此也会消耗预算，这是「入队不计数会使队列没有上界」的代价。
- **跨渠道上界把认证与通知绑在一起。** 一次通知投递的爆发可以耗尽部署的小时上界，使同一小时内的认证短信一并得 429；拆回两条上界就失去了这条约束。
- **通知的尝试预算计每一次尝试，与认证不同。** 认证只计确定失败，通知计每一次尝试：它防的是一个陷入重试循环的生产者，而风暴里的尝试可能每一次都被载体接受，也可能每一次都确定失败并退还发送预算。一个持续重试的生产者因此会先耗尽租户的尝试窗口，即便它的每次发送都被载体接受或都已退款。
- **台账或计数器不可读即拒绝。** 读不出跨渠道上界、任一短信计数，或写不进邮件计数器时，提交面以不可用拒绝，不入队；计不了数的预算不能让消息通过。
- **短信预算的设置面是宿主可见的。** 短信预算由共享台账的窗口与 `sms.ceiling-hourly` 给出，旧键值计数器不参与短信计数；邮件预算设置不变，按收件人的键与 `notification.delivery.global-hourly` 由邮件读取。
- **邮件预算与短信预算各记各的账。** 邮件的固定窗口预算留在键值计数器上，短信的预算在共享台账上；两者共用每收件人小时与每日的一对设置值，部署小时窗口归邮件、每租户窗口与跨渠道上界归短信，互不占用对方额度。同一次投递若同时走两个渠道，两边的计数各自加一，这不是双写：台账只记短信尝试，计数器只记邮件投递，各自回答自己渠道的问题。
- **台账没有内置的保留清扫。** 每一次通知短信尝试都留下一行；台账模块提供按时间删除行的接口，但不运行定时任务，没有宿主接上清扫时表随发送量增长。

## 失效条件

以下情形出现时，本决策需要重议：

- 若 `pkg/jobs` 不再交付持久队列（例如它退化为进程内队列），则「投递经持久队列异步进行」这条的前提改变。
- 若渠道厂商开始提供可按调用方标识去重的发送接口，则「逐渠道一个去重键、超时归 `failed`」这条的价值下降，超时后的处置可以简化。
- 若通知投递不再经短信发送，或认证与通知不再共享部署的短信容量，则共享台账与跨渠道上界的前提消失，通知侧可以退回自己的预算。
- 若提交面不再是唯一的生产者入口（例如队列接受别的写入方），则「预算计在提交面」不再给队列一个上界，预算需要移到消费端或由队列自身给出容量。
