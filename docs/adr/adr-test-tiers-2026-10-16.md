# 外部测试后端由 compose 提供，测试按是否依赖它分为单元与集成

## 状态

已接受

## 背景

`pkg` 下多个模块的用例要跑在真服务器上：PostgreSQL 用于数据库、键值与事件的 postgres 实现，Redis 用于键值与事件的 redis 实现，NATS 用于两者的 nats 实现，Memcached 用于键值模块的 memcached 实现。这些服务器都不是被测代码的一部分，而是测试环境：被测的是模块在这类后端上的行为（PostgreSQL 事务内的 DDL、Redis 的流消费组与 `SET` 的 `KEEPTTL`、JetStream 的 compare-and-swap 与拉取消费、Memcached 的 compare-and-swap），换掉后端就是换掉被测对象。

约束来自两处。

**提交门禁必须在任何装了 Go 工具链的机器上跑。** 门禁是每次提交的判据，而 `docker` 及其 compose 插件不在 `.mise.toml` 提供的工具链里。

**多个测试二进制并行。** `go test` 并行跑一个模块的包，`make check` 又跑两条腿，同一台机器上还可能有多个检出；同一时刻可能有几十个用例各自要一块隔离的数据。

**同一台机器上的默认端口可能已被占用。** 占用者可能是未受本仓库编排的服务，也可能是同一仓库另一个检出的栈；本机端口是否空闲不由本仓库决定。

## 考虑过的选项

### 夹具用 `os/exec` 驱动 docker CLI

夹具自己 `docker run` 一个同名容器、用临时端口发布、`docker port` 读回端口，并在两个二进制同时创建同名容器时等待胜者。

**否决**：容器生命周期不是被测对象，夹具却要为它承担代码与覆盖——两个专门测这场创建竞态的测试文件即由此而来。临时端口使「哪台服务器」无法从用例读出来；`docker run` 成功与服务器就绪是两件事，容器起来而服务器仍在初始化时只拨 TCP 的检查会放过它，表现为冷启动首批用例偶发连接失败。

### 用测试容器库

以 testcontainers 一类库管理容器。

**否决**：一个只被测试用到的依赖仍会进入模块的依赖清单，而它替夹具做的只是「起容器、读端口」。

### 用例内嵌等价实现

用进程内的替代物替换这些后端。

**否决**：见背景——被测的正是这些后端的行为，替换即取消被测对象。

### 外部后端由 compose 栈提供，用例按是否依赖它分两层

后端由 `compose.yaml` 声明、由 compose 起停；夹具只连不管，连不上即失败；需要后端的用例带构建标签，与不需要的用例分开执行。

**采纳**——见决策。

## 决策

采纳：**仓库根的 `compose.yaml` 声明 PostgreSQL、Redis、NATS 与 Memcached 四个服务，`docker compose up -d --wait` 是把它们起来的唯一方式，也是唯一管它们的东西。** 每个服务自带 healthcheck，`--wait` 因此返回即就绪。

**一套栈属于一个检出，端口按需分配。** 每个服务的宿主端口由 `SPEED_TEST_PG_PORT`、`SPEED_TEST_REDIS_PORT`、`SPEED_TEST_NATS_PORT`、`SPEED_TEST_MEMCACHED_PORT` 指定，变量缺省时取 5432、6379、4222、11211。`make deps-up` 调用 `tools/backends.py up`：项目名由检出根路径的散列派生（`speed-test-<12 位十六进制>`，同一检出稳定、不同检出不同），脚本在 `127.0.0.1` 上绑定 :0 取四个互不相同的空闲端口，把项目名与端口写入仓库根的 `.cache/test-backends.env`，再以该项目名执行 `docker compose up -d --wait`。状态文件存在且该项目的容器全部健康时直接复用；`up` 失败时重新取端口重试，至多三次，最终失败删掉状态文件并报出最后一次完整输出。`make deps-down` 只按状态文件里的项目名取下这一套栈，随后删除状态文件。直接执行 `docker compose up` 仍按默认端口起栈。

**测试夹具只连不管。** 夹具的地址来自 `SPEED_TEST_PG_ADDR`、`SPEED_TEST_REDIS_ADDR`、`SPEED_TEST_NATS_URL`、`SPEED_TEST_MEMCACHED_ADDR`，变量缺省时回落到固定的回环地址。夹具只做协议层的事：每用例一个 PostgreSQL 库、一个 Redis 库序号租约、一个 Memcached 键空间前缀、一个 NATS bucket 或 stream 名。**后端不可达时用例失败，不跳过。**

**用例分为单元与集成两类。** 依赖外部后端的用例带 `integration` 构建标签，其余的构成单元层。**提交门禁只跑单元层**，不需要 docker；集成层由 `make test-integration` 单独跑，在 CI 上由定时任务触发。

**同一用例跨方言（SQLite 与 PostgreSQL）各跑一遍时，方言集合与每个方言的打开方式都由使用它的包自己持有，PostgreSQL 那一条只存在于集成构建。** 它由一个带 `integration` 标签的文件在 `init` 里追加进集合，因此单元构建里 PostgreSQL 不在集合中，而不是被跳过。参数化用例的 SQLite 腿因此留在单元门禁里。

## 后果

单元门禁不再要求 docker，在任何装了 Go 工具链的机器上跑到绿；集成层是它的补集。

方言矩阵的分类落在构建标签上，而非运行期判断：单元构建里 PostgreSQL 不在集合中，不是被跳过。

**接受的代价：**

- **提交门禁不再覆盖跨进程行为。** PostgreSQL 迁移互斥、副本选举一类只在集成层跑，因此只在定时腿上报红，而不再挡在提交前面。
- **栈的端口不再固定。** 夹具与任何直接连后端的工具都必须读 `SPEED_TEST_*`；只认 5432 一类默认地址的调用方在一套分配了其他端口的栈上会连错服务器或连不上。直接 `docker compose up` 的默认用法仍然成立。
- **一个检出一套栈。** 同一台机器上的多个检出各自起四个容器；隔离从按进程扩大到按检出，代价是同时运行的容器更多。
- **集成层多了 docker 与 Python 3.11 以上两个前提**（`tools/backends.py`）。两者都不在提交门禁里，因此不影响单元层。
- **状态文件可能过期。** 容器被外部删除后状态文件仍指向旧端口；`make deps-up` 发现该项目的容器没有全部健康会重新分配，而不是复用。
- **分配失败最多重试三次。** 之后删掉状态文件、按 compose 最后一次完整输出报告；没有状态文件时 `make test-integration` 直接失败，不回落到默认端口。
- **骨架自带的 `starters/demo/compose.yaml` 仍用固定端口。** 它与一套按默认端口直接起的栈争端口；与脚本分配了端口的栈可以并存。
- **后端的镜像与版本集中在 compose 文件里**，改一处同时影响所有用例。
- 本地跑集成层要先跑 `make deps-up`（`make test-integration` 会自己跑）；集成层的唯一常规执行点是定时任务。

## 失效条件

- 若某个后端出现纯 Go 的等价实现，且用例断言的性质在它上面同样成立，则该后端的分层前提不再存在，它应回到单元层。
- 若一台机器无法为每个检出承担四个容器（内存、端口或镜像拉取成为新的阻塞），按检出独立起栈不再成立；替代方案是全机一套栈、各检出把状态文件指向它，或按项目名共享。
- 若 `bind(127.0.0.1:0)` 得到的端口与容器引擎实际能发布的端口长期不一致，三次重试仍不足以让两套栈共存，则需要改为不发布宿主端口、让夹具经容器网络访问。
- 若跨进程行为的缺陷多次只在定时腿上被发现且代价可观，则需要把集成层移进提交门禁或提高其执行频率。
