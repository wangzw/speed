# 写入的结果由每个反馈作用域的一个槽承载，同页至多一条结果、以最后落定的为准，成功确认为默认

## 背景

前端各包用同一组积木报告写入的结果：ui-kit 的 `InlineError`（`role="alert"` 横幅，文案由各包绑定的错误码解析器给出）、`InlineSuccess`（始终挂载的 `role="status"` 区域）、`AsyncSection`（读的四态）与 `ConfirmDialog`。积木统一，用法不统一，表现为：

- 管理后台的页面把多个 mutation 的错误拼成「数组里第一个非空」的一条页底横幅（`firstErrorCode` 在邀请、账户、权限、SSO、短信各页各有一份）。旧错误只在同一个 mutation 再次触发时才清掉，因此旧错误遮住另一个 mutation 的新错误，或与后一次写入的成功文案并存。
- 设置页的批量保存在同步循环里对同一个 mutation 观察者连续调用 `mutate`，页面只反映最后一次：更早的某一项失败，最后一项成功时仍显示「设置已保存」。
- 有成功文案的页面与没有的页面并存：租户名册、设置、会话、权限有；账户创建、SSO、短信、邀请、冒充、租户详情的重命名与启停没有，只剩表单清空或列表重读这类对读屏不可闻的隐含变化。account-ui 的档案、口令、手机、标识与会话几节手写了与 `InlineSuccess` 相同的 `Alert`。
- `PermissionsPage` 的角色删除失败时确认对话框保持打开，失败横幅落在被 `aria-hidden` 的背后页面里，操作者在取消之前读不到它。
- 已有缓存数据时刷新失败，旧行保持原样且没有任何提示：`AsyncSection` 只在没有数据时进入失败占位。
- 一次性值的展示块没有 live region。邀请的接受链接与 SSO 的域名认领令牌是页面层的普通文字，不标明所属的租户（邀请的文案只点名受邀人），切换租户后继续显示，因而可能被读成属于新选的租户；服务密钥的展示块在以所选账户为键的详情组件内，文案不点名账户，选择另一个账户或收起详情即被丢弃，唯一的一份就此丢失。

前端没有 Snackbar 或 toast，没有全局 `onError`；编码规范（`.claude/skills/frontend-coding-standards/SKILL.md`）没有点名这些积木，也没有「落定的操作要确认」的规则。同层的前端包不能互相 import，共享只能经 ui-kit。

## 考虑过的选项

### 维持现状，各页各自拼状态

**否决**：上列表现都出自这一做法。结果的归属（哪个控件组、哪个槽）、清除的时机与成功确认是否存在，在每个页面里各自决定，并已漂移：`firstErrorCode` 在多个页面各有一份副本，成功文案的有无按页面碰巧而定。

### 全局 toast 或 Snackbar，由 provider 统一承载

**否决**：失败要停留在被重试的控件近旁，toast 的自动消失不照顾读得慢的操作者，也不照顾读屏用户错过的那一次播报；成功文案本来就要由发起写入的宿主翻译、点名对象，provider 只能转运文本，不能决定它。树里没有可供依托的 provider，新建一个等于在页面区域模型之外再造一条反馈通道，而页面区域（先挂空区域、再填文本）已是 `InlineSuccess` 的验证过的无障碍做法。

### 在 QueryClient 的 `MutationCache` 里统一处理

**否决**：全局处理器看到的是一次 mutation，不是反馈作用域，不知道结果该落在哪个区域；批量保存这类一个动作含多次请求的尝试，在 mutation 粒度上无法表达为一次结果，上传一次尝试跨多个 mutation 同理。它还把 ui-kit 与页面的反馈绑到 react-query（[REF-tanstack-query](../references.md)）上，而反馈契约要对不以单个 mutation 为界的写入（跑在 auth-core 流程上的登录）同样成立。

### 每个包复制一份本地 hook

**否决**：同层包互不 import，共享只能放进 ui-kit；各包各留一份，就是 `firstErrorCode` 已有的多页副本再按包数复制，并且副本之间会继续漂移。

### 确认对话框保持打开到写入落定，失败渲染在对话框内

**否决**：侧边面板与步进对话框就是这样做的，但它们本来就是带表单或流程的模态，自带可承载失败的区域；`ConfirmDialog` 的内容是一段说明，要承载失败就要给它增加失败槽与重试语义，扩大它的契约范围，而成功文案仍要落在对话框之外的区域，结果因此分居两处。让对话框在写入落定时关闭、失败与成功都落在发起控件组的区域，只有一个结果落点。

### 新的写入发生时清空同页其他作用域的旧结果

**采纳（经页面级协调，见决策）**：同页并列时，扫读的人可能把一条结果读成另一件事的结果，区域各落在自己的控件组下方也不足以消除这种误读。因此同页至多展示一条结果，以最后落定者为准。协调由宿主挂载的可选 provider 承担：它只接收各作用域登记的清除回调，不持有槽、不渲染界面；槽的状态仍属于持有它的宿主，没有 provider 时各作用域互不影响。代价是操作者没做那件事、它的确认却会消失，一条失败也可能被同页后续的任意写入（包括成功）冲掉。

### 由 ui-kit 提供单槽 hook 与渲染区域，成功确认为默认

**采纳**，见决策。

## 决策

采纳：**一次写入的结果落在一个反馈作用域里，作用域持有至多一个结果、以最后落定的结果为准；ui-kit 提供 `useWriteFeedback`（槽的状态、在途计数与一次尝试的 `run`）与 `WriteFeedbackRegion`（把槽渲染为成功与失败的区域），各包用自己的错误码解析器绑定区域；每个由操作者发起、落定且无一失败的动作都落一条成功文案；不引入 toast 或全局处理器。**

- 一个动作是一次尝试：含多次请求的动作以一次 `run` 结算，部分落地的批量以失败结算。
- 同页至多一条结果：宿主挂一次 `WriteFeedbackPageProvider`，任一作用域的 `run` 开始、`succeed` 或 `fail` 落定先清空同页其它作用域的槽，`reset` 只清自己；没有 provider 时各作用域的槽互不影响。
- 写入在途时，发起控件与改变作用域上下文的控件禁用；被步进不足拒绝的写由提权门控接管，不落失败。
- `ConfirmDialog` 至迟在写入落定时关闭，失败落在关闭之后的区域；自带表单或流程的模态把失败渲染在模态之内。
- 已有数据时的刷新失败以 `AsyncSection` 的 `staleState` 标明。
- 一次性值的展示面板由宿主自持，与区域并列、不进槽。
- 一组并发、互相独立的逐项传输（上传队列）每行自成一个槽。
- 作用域的划分、各条款的细节与读取刷新失败的标明方式，由 ui-kit 的设计文档给出，本记录不重述；编码规范新增对应的条款，使这一用法成为评审可裁决的规则。

## 后果

同一类缺陷（旧错误遮新错误、成功与失败并存、批量保存的假成功、失败落在被隐藏的区域）由槽与一次尝试的语义排除，而不靠每个页面各自记得清除。成功确认从个别页面的做法变成默认，读屏用户与看得见的用户得到同样的确认。`firstErrorCode` 的副本与 account-ui 里手写的成功 `Alert` 随迁移消失。

**接受的代价：**

- **ui-kit 获得一个自己持有状态的 hook。** ui-kit 的组件不持有业务状态与写入结果，hook 的状态属于调用它的宿主组件；已导出的 hook（`useAppThemeMode`）只读 provider 的上下文，`useWriteFeedback` 是第一个自己持有状态的导出 hook，契约需要明确这条界线。
- **各页面要重新划分作用域，改动面覆盖所有有写入的页面。** 页底的聚合横幅被拆成每个控件组一个区域，页面的结构、测试与文案键随之变化；迁移不是原子的，所有页面迁完之前，两种反馈做法并存。
- **同页至多一条结果，一条确认或失败会被同页的另一次写入冲掉。** 任一作用域的 `run` 开始、`succeed` 或 `fail` 落定都会清空同页其它作用域的槽；这是产品明确接受的取舍——同页只看最近一次写入的结果，而不是把多条结果并列交给读者分辨。操作者没做那件事、它的确认却消失，也在取舍之内。
- **一个作用域一个槽，重叠的尝试以后落定者为准。** 同一作用域内两次写入几乎同时落定时，先落定的结果被后落定的结果替换；改变上下文的控件在作用域有写入在途时禁用，使 `reset` 之后不会有先前上下文发起的尝试落定，代价是这些控件在写入在途的短暂窗口内不可操作。
- **部分落地的批量只报第一个失败。** 批量保存里有多项失败时，槽里只有提交顺序中第一个失败项的码；其余失败项靠保留的草稿与待保存计数被发现。
- **确认对话框关闭后，重试要重新打开并确认。** 失败落在对话框之外的区域，操作者重试时再点一次触发控件、再确认一次。
- **通行密钥仪式（[REF-webauthn](../references.md)）的失败是槽之外的第二个失败来源。** 它源于客户端、不带 API 码，与槽里的失败横幅的互斥靠显式的互相清除，而不由槽的语义保证。
- **成功文案是译文快照。** 成功文案在 `succeed` 的时刻译好，之后的语言切换不更新它，直到下一次尝试替换它；失败码则随活动语言重新渲染。
- **新的成功文案要双语。** 每个需要新增确认的动作都要有 zh-CN 与 en-US 两条文案，每条都点名被改动的对象。
- **读屏用户听到更多播报。** 每个落定无失败的动作都会触发一次 `role="status"` 的更新。
- **结果不自动消失。** 成功文案一直留到下一次尝试或上下文变化，页面上可能停着一条已无关的确认，由 `reset` 的调用点（尝试开始、上下文变化）负责清除。

## 失效条件

- 出现一个控件组里需要多个并发、互相独立的结果、又没有逐项单元可各自成槽的界面：作用域要再细分，或槽要改为按键的集合；上传队列的每行一个槽是已采用的细分。
- 实测显示读屏用户被成功确认的播报频率困扰：成功确认需要按动作的分量分级，而不是对「每个落定无失败的动作」一律播报。
