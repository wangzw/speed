# 关联模式的语句按键填租户那一半，多对多关联的连接表按所连模型写进它的租户列判定

## 状态

已接受

## 背景

隔离插件按来源识别受约束模型，按结构体主键寻址的更新与删除由插件把主键里租户那一半填成上下文的标识（[ADR-tenant-isolation-2026-09-21](adr-tenant-isolation-2026-09-21.md)）。宿主据此按标识的其余部分寻址一行，租户那一半留给插件。

GORM 的关联模式（`Association` 的 `Find`、`Count`、`Append`、`Replace`、`Delete`、`Clear`）不经这条路。它在任何回调之前就把属主与所给记录的整个主键读出来，写进语句的条件：一个对键的各列取 `IN` 的条件，或一条列上的等值。宿主留空的租户那一半因而作为空标识写进条件，标识拒绝以空值被绑定，语句以"上下文里没有租户"失败，而上下文明明带着租户。同一个按键寻址，在模型自己的删除上可用，在关联的删除上不可用。

多对多关联还要经过一张连接表。GORM 给没有 `SetupJoinTable` 点名模型的关联自己构造一个连接表模型，那个模型不内嵌任何东西；`SetupJoinTable` 点名的模型也可以不内嵌约定。这样的连接表在插件看来是全局表：没有租户条件，也不拒绝没有租户的语句，一次在没有租户的上下文里对别的租户的属主做的 `Clear` 删掉了那个租户的关联行。连接表的内容是租户的数据——哪个商机关联了哪些联系人——而它的行只经关联模式写入与删除。

关联模式的 `Find` 与 `Count` 读的是另一侧的模型，连接表经 FROM 子句按表名联接进来：ON 把连接表的列与另一侧的键列相等，并以一个 `IN` 带上属主的键。这条读里没有连接表的模型，插件能看到的只有 ON 里的条件。

## 考虑过的选项

### 写明哪些关联写法要先加载记录，报错点名真正的原因

宿主在调用关联模式之前把属主与目标记录读出来，租户那一半因而是读出的值；关联模式遇到空的租户那一半时，错误文本改为说明要加载记录。

**否决**：同一个按键寻址在普通的写上可用、在关联语句上不可用，宿主要记住两套规矩，而宿主的规则要求租户那一半留给插件。`Delete` 的目标同样按键给出，每删一条关联先读一次它所指的记录。读出来的记录在别处不需要，这次读只为绕过一个插件填得了的空。

### 在 GORM 把键写进条件之前替它填结构体

插件在关联模式读取键之前把属主与记录的租户那一半填上，与按结构体主键寻址的写同样处理。

**否决**：`Association` 是 `*gorm.DB` 上的方法，读键发生在它自己的代码里，早于任何回调链；插件没有更早的挂点，模型的钩子也不在那里被调用。

### 条件里所有空的标识类型取值一律填成上下文的标识

不看它写在哪一列上，条件里凡是空的 `tenant.ID` 都替换成上下文的标识。

**否决**：一个以标识类型声明、却不是租户列的列——例如一行记录它指向的另一个租户——上的条件会被改写成另一个意思；写语句还要据它拒绝写了别的租户的键，那会把合法的语句拒掉。关联模式写键时列名是确定的，填的只该是写在那条语句自己的租户列上的那一段。

### 连接表一律按它自己的模型认，要求它内嵌约定

与任何模型一样，连接表内嵌了约定才受约束，宿主为每个多对多关联用 `SetupJoinTable` 点名一个内嵌约定的连接表模型。

**否决**：GORM 自己构造的连接表模型不内嵌任何东西，漏写一次 `SetupJoinTable` 的关联静默成为全局表，正是要挡的那一类。按表名联接连接表的读看不到它的模型，只看得到键，同一张表在两处的判据因而不一致：连接表模型内嵌了约定、而两侧的键把租户写在另一列上时，它自己的语句按一列加条件，联接它的读按另一列。

### 连接表当全局表放行，写进非保证

插件不认连接表，宿主自己守住它。

**否决**：连接表的行是租户的数据，而写它、删它、预加载时读它的语句都经过插件，插件认得出它是哪个关联的连接表；认得出却放行，等于把一个查得出的缺陷交给评审，证据里一次没有租户的 `Clear` 已经删掉了别的租户的关联行。

### GORM 默认构造的两个租户列都加条件、都填列

两个受约束模型之间不写 `joinForeignKey` 与 `joinReferences` 时，连接表里每一侧各有一个租户列；两列都按上下文加条件、填列、核对。

**否决**：插件的每一档——填列、核对、主键里租户那一半、条件——都按一个租户列设计，两列要处处各做一遍。更要紧的是一行关联写得下两个租户，库里没有约束让两列相等，要靠插件在每一条语句上维持，漏一处就是一行跨租户的关联；让两侧的键把租户写进同一列，这种行从 schema 上就不存在。

### 取不出一个租户列的连接表另立一个哨兵

**否决**：它与内嵌了约定却取不出一个租户列的模型同类，经它的语句到不了任何一个租户，`ErrNoTenantInContext` 已经承担这一类（[ADR-tenant-isolation-2026-09-21](adr-tenant-isolation-2026-09-21.md)）。修复在关联的声明上，错误文本点名连接表、关联与缘由即可。

### 按表名联接的读一律当成以 SQL 文本写出的联接

FROM 子句里按表名写出的联接与 `Joins("JOIN ...")` 同类，被联接的那一侧不加条件，写进非保证。

**否决**：关联模式的 `Find` 与 `Count` 正是这种形状，放行它们，连接表的读路径就是全局的。ON 是 GORM 按关联的键写出的条件，插件读得出其中连接表的哪一列带着租户。

### 按键写进它的租户所在的列认定连接表的租户列，关联语句的键在条件里补上租户那一半

**采纳**，见决策。

## 决策

采纳：关联模式写进条件的键，租户那一半按上下文填；多对多关联的连接表按所连受约束模型的键把租户写进哪一列来认定租户列，取不出一个租户列的连接表一律拒绝。

- **条件里的键。** 受约束模型的语句在上下文带租户时，条件里写在这条语句自己租户列上的键——对各列取 `IN` 的元组中租户那一位，或租户列上的等值——空的租户那一半填成上下文的标识，调用方的条件原样保留，同一条语句再次执行时按新的上下文重新填。租户那一半写了别的租户的：写语句以 `ErrExplicitTenantMismatch` 拒绝，与按结构体主键寻址的写相同；读语句照原样，读不到任何行。
- **连接表的租户列按来源认。** 一个多对多关联里受约束的一侧以含租户列的键参与关联时，它的租户写进连接表的某一列，那一列就是连接表的租户列，不论连接表的模型是谁构造的、内不内嵌约定。受约束的一侧只以键的其余部分参与关联时，它不往连接表里写租户，读写它的行的语句由它自己的模型加条件。连接表的每一条语句照受约束模型的规矩加条件、填列与核对。
- **三种声明取不出一个租户列，经这样的连接表的每一条语句都被拒绝**，不论上下文，配 `ErrNoTenantInContext`：至少一侧受约束而没有一侧往连接表里写租户；两侧把租户写进两列；连接表的模型内嵌了约定，落在另一列上。
- **按表名联接连接表的读，从 ON 里认它的租户列。** ON 在被联接表的某一列上绑定了标识类型的取值（属主键里租户那一半），或把那一列与这条读自己的租户列相等，那一列即是租户列：插件填上键里空的租户那一半，并在 ON 里加上那一列等于上下文标识的条件，这条读因而与受约束模型的读一样要求上下文里有租户。ON 显示被联接的表把租户放在两列上，或受约束的这一侧只按键的其余部分与一张看不出租户列的表联接，那条读被拒绝，理由与连接表自己的那三种相同。

## 后果

宿主按标识的其余部分寻址关联的属主与目标，与寻址普通的写一样，不必先读出记录。两个受约束模型之间的多对多关联，用 `joinForeignKey` 与 `joinReferences` 把两侧键里的租户那一半写进同一列，连接表模型可以由 GORM 构造，也可以是宿主点名的、不内嵌约定的模型。

**接受的代价：**

- **GORM 默认的多对多写法在两个受约束模型之间被拒绝。** 不写那两个标签时，连接表每一侧各有一个租户列，经它的每一条语句都失败，第一条语句上就摆出修复。
- **外键含租户列的一对多、一对一与属于关系，解除关联被拒绝。** GORM 把记录从属主上取下的做法是把外键的每一列写成 NULL，租户列在其中，这条更新把租户列写空，在租户之下以 `ErrExplicitTenantMismatch` 失败。要解除就用 `Unscoped` 的关联删除（删掉那一行），或自己写更新只置空外键的其余列。
- **只把属主的租户写进连接表的关联，跨租户读时另一侧按键的其余部分匹配。** 一行关联属于属主的租户，在租户之下它指的是那个租户里的行；跨租户的读不加条件，另一侧每一个持有那个键的租户的行都被读到。
- **属主只以键的其余部分参与、另一侧是全局模型的连接表，按表名联接的读判定不了。** 这张连接表自己的语句被拒绝，经插件写不进任何一行；联接它的读看不出租户列，读的是绕过插件写进去的行。这一条写进非保证。
- **判据读 GORM 写出的条件形状。** 条件里的键认的是 `IN` 与等值这两种 GORM 用来写键的表达式；按表名联接的读认的是 ON 里标识类型的取值与列之间的等值。调用方自己以这些形状写出的条件照同样的规矩判定。
- **每一条语句多走一遍 schema 上的关系**，看它的模型是不是某个多对多关联的连接表；每一条带 FROM 联接的读另把 ON 走一遍。

## 失效条件

若 GORM 的关联模式改为在回调之后才把键写进条件，或为它提供一个早于读键的挂点，条件里的填补可以换成在结构体上填，与按结构体主键寻址的写合成一处。

若 GORM 在按表名联接连接表的读上带出连接表的 schema，从 ON 里认租户列的那一步可以换成与连接表自己的语句同一个判据，属主只以键的其余部分参与、另一侧是全局模型的那一格随之可判。
