# 上下文无租户时受约束模型的语句拒绝执行，跨租户必须在调用点字面写出

## 状态

已接受

## 背景

插件对每一条针对受约束模型的语句作判定（[ADR-tenant-isolation-2026-09-21](adr-tenant-isolation-2026-09-21.md)），而"上下文里没有租户"这一档必须有确定的读法。**插件不认识名册**，因而不区分一个标识是从未存在、已经停用，还是只是没有被放进上下文——这三者到达它时是同一个样子：上下文里没有标识。

发出语句的路径不止一条。HTTP 请求经过解析层，上下文里一定有标识或一定没有；后台任务、管理面、迁移与宿主的自检代码则可能在一个与请求无关的上下文里访问受约束表，而它们恰恰是最需要跨租户读的地方。

数据库模块把物理删除留给 `Unscoped().Delete`，理由是"谁可以物理删除是权限问题"（见 `db` 设计文档的非职责）。`Unscoped` 是 GORM 为软删除提供的开关，它在 `Statement` 上是一个可读的字段。

认证为零值判决立过同一条防线：判决的零值读作"没答"而非"通过"，导出注入口等于让链上任何一层改写身份（[ADR-authn-verdict-2026-09-20](adr-authn-verdict-2026-09-20.md)、[ADR-authn-packaging-2026-09-20](adr-authn-packaging-2026-09-20.md)）。本记录是这条防线在数据一侧的对应物。

## 考虑过的选项

### 无租户即不过滤

上下文里没有标识时，语句原样发出。

**否决**：这是跨租户读出的完整形态，且不报错——一次忘了注入的后台任务、一条没经解析层的内部调用，都会读出全部租户的行。

### 无租户即过滤成空集

没有标识时加一个恒假条件，语句答出零行。

**否决**：读安全而写不安全——插入语句的租户列会落成空值，而空值不属于任何租户，它留下的行此后没有任何一条查询能再看到。它还把"没有数据"与"没有注入"在调用点变成同一个观察，排查时分不出是哪种。

### 各模型自己声明无租户时怎么办

约定里多一项，模型逐个声明它没有租户。

**否决**：把一条安全默认摊成每个模型各写一遍，漏写一个的形态是静默，而"漏一条就失效"正是这类能力被划进插件的理由（[ADR-db-scope-2026-09-14](adr-db-scope-2026-09-14.md)）。它同时取消了插件识别受约束模型这条规则的单值性：模型的声明与它是否内嵌约定会成为两份可以对不上的事实。

### 跟随 `Unscoped()`

`Unscoped()` 同时解除软删除条件与租户条件。

**否决**：`Unscoped()` 最常见的书写理由就是物理删除，而它一旦同时解除租户条件，一次针对本租户某一行的物理删除会打到全部租户的同 id 行上——一个破坏性的动作由一个与租户无关的开关触发。它还把跨租户这件事从具名变成匿名：一条语句是否故意跨租户，在代码上读不出来。

### 无租户即拒绝，解除作用域必须在调用点字面写出

**采纳**，见决策。

## 决策

采纳：插件判定的第四档是语句失败并配本模块自己的哨兵；跨租户的唯一途径是一个具名的上下文函数，写在调用点上。

跨租户函数的确切签名写在设计文档的外部接口契约里。

**`Unscoped()` 不解除租户条件。** 插件不读 `Statement` 上那个字段：它在 GORM 里表达的是软删除的范围，把它当成解隔离的开关，等于让一个与租户无关的动作拥有解除租户作用域的效果。

**跨租户是一个上下文事实，不是一个语句事实。** 带上标记的上下文可以在一个函数的入口处建立，此后的每一条语句都落在跨租户之下，调用点因而读得出这次操作整段的意图；语句级的开关则要求每一处各写一次，而漏写一处就退回拒绝，失效方向是隐性的。

**带标记的上下文不属于任何租户。** 建立标记之后上下文里没有标识可读：`FromContext` 在它里面答没有租户，logger 上绑的租户字段也一并撤下，一个从请求上下文里建立标记的调用点把它那条请求的租户一并交出。跨租户的语句不属于任何租户，把它记成某一个租户的，等于给一条不受约束的语句安上一个它没有的作用域。

**一条写语句显式给出的租户列取值必须与上下文里的标识一致，不同即失败。** 跨租户既然只有一条途径，在语句上另写一个租户就是把同一条规则开出第二个入口，而那个入口不带任何意图标记——一次复制粘贴改出来的写会静默落进另一个租户，不报错，也触发不了任何哨兵。

**标记是唯一的途径，而这条途径一旦存在就可被滥用。** 本模块提供它，不判定调用点该不该用它。它的名字要能在评审里被认出来，这是选择具名函数而不是布尔参数或字符串键的理由——后两者在调用点读起来都像别的东西。

## 后果

"没有租户就发出语句"这件事在本模块的判定里不存在：上下文里没有标识即失败，失效方向是拒绝而不是放行。一个标识指向的租户是否存在、是否停用，插件判不了也不去判——那是解析层的判定，而经请求面到达的语句在那一层就被拦下了。

后台任务、管理面与运维脚本要么显式写出跨租户标记，要么经名册进入它们为之做事的那一个租户（[ADR-tenant-scoping-2026-09-28](adr-tenant-scoping-2026-09-28.md)）；两者都写在调用点上，写出来这件事本身成为一处可评审的事实。**名册自己的读写不在此列**：名册表不内嵌受租户约束的模型约定，读写它的语句根本不经插件（[ADR-tenant-isolation-2026-09-21](adr-tenant-isolation-2026-09-21.md)），给它加标记不改变任何行为。

**接受的代价：**

- **漏写标记的形态从"静默读出别人的数据"变成"这条语句报错"**，但暴露在运行期而非启动期：本模块无从在启动时知道哪些代码路径没有租户。
- **每条针对受约束模型的语句多一次上下文读取与一次模型判定。** 判定走的是 GORM 已经解析好的 schema，代价与一次映射查找同阶。
- **一条语句在两个租户之间做关联查询表达不出来**，除非整条语句落在跨租户之下，于是最需要谨慎的那类查询恰好走在最宽的那条路上。
- **跨租户标记不带理由。** 谁在什么情况下解除了作用域，只有调用点的代码说得出，本模块不记它。留下这条痕要调用点显式调用审计的记录接缝，把用途与操作一起交给它；不调用就没有痕，而本模块无从知道哪个调用点该调用（[ADR-audit-scope-2026-09-21](adr-audit-scope-2026-09-21.md)）。
- **一个被停用的租户，其标识仍然在受约束表里。** 停用只让它不再被解析出来，数据留在原处；跨租户路径读得到它，这是本记录有意保留的形态。

## 失效条件

若 GORM 获得一种语句级的、可被评审认出来的作用域开关，且它与软删除的开关是两件事，则"跨租户是上下文事实"这一条要与它重新比较，判据是调用点读不读得出意图。
