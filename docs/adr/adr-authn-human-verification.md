# 人机验证是缺省关闭的发送前闸，机制由部署选定

## 背景

发送验证消息的滥用——短信轰炸、流量泵与向任意地址发码的邮件轰炸——在预算之内仍然成立：预算按收件人、来源、账户与用途给出上界，不区分一次发送背后是人还是自动化脚本（REQ-abuse-007、REQ-abuse-008）。产品要求提供人机验证，缺省关闭，由部署决定是否启用，且每次发送都要先出示一份有效、一次性的证明。

既有装配不能因为新能力改变发送路径：客户端还没有取得证明的控件，部署也可能不持有任何第三方凭据。证明的校验又要先于发送预算，使一次被拒绝的请求不浪费额度。证明的一次性由哪个部件保证，决定了接缝的形状。

## 考虑过的选项

### 缺省打开，内置一个第三方提供方

每次发送都经提供方的站点校验，部署无需选择。

**否决**：部署无法自托管时，发送路径就挂在第三方的可用性上；没有凭据的既有装配会直接停止发送；客户端也要被迫渲染一个它不认识的控件。这与「部署可以启用」相悖。

### 只靠预算，不引入证明

把预算调紧，用号码、来源、账户与用途四个维度限制发送量。

**否决**：预算限制的是总量，不验证发送者是不是人。攻击者可以在预算之内持续消耗，预算耗尽后合法用户同样被拒；需求明确要求每次发送先出示证明。

### 缺省关闭，接缝加上自托管与第三方两个机制

交付 `authn.HumanVerifier` 接缝，缺省模式 `off`；内置自托管的工作量证明与 Cloudflare Turnstile，部署按配置选一个，也可以自带实现。

**采纳**，见决策。

### 由认证模块自己保存证明的已用记录

接缝只负责验证，`authn` 自己记下已经出示过的证明。

**否决**：证明的有效期、格式与一次性都由机制定义，模块保存已用记录会把同一份状态复制一份到不认识该机制的一侧；无状态的提供方也因此无法接入。

## 决策

采纳：人机验证是 `authn.humanverify` 排他交付的 `authn.HumanVerifier` 接缝，缺省模式 `off`，内置自托管的工作量证明（`pow`）与 Cloudflare Turnstile（`turnstile`）两个机制，部署用 `authn.humanverify.mode` 选定。

- **每次发送都验，注册不验。** 登录短信、短信第二因素、添加手机与自助添加邮箱的每一条发送路径，都先向接缝出示 `HumanProof`。注册不发送消息，因此不经该闸。
- **先验证明，再花预算。** 证明在任何发送预算被消耗之前核对，被拒绝的请求不占额度、不写流程、不发送。
- **一次性归提供方。** 接缝只承诺一份被接受的证明不能再次通过；`pow` 用挑战的比较并交换兑现它，`turnstile` 依赖站点校验对重复令牌的拒绝。
- **离场的答案分三档。** 缺失、无效、过期或重放答 403 `human-verification-required`；过长的证明答 400；提供方或它的存储不可用答 503，发送不发生，也不降级为放行。
- **关闭时不多问。** `off` 模式下 `Required` 为假、`Verify` 接受任何证明，客户端不必取得证明，装配不必交付键值存储或路由挂载口。
- **换机制就换实现。** 接缝排他交付，部署想要别的机制时自带 `authn.HumanVerifier` 并把本模块从命令树上撤下，两个实现在一次运行里不能并存。

## 后果

证明把「能不能发」从一个只由预算回答的问题，改成先回答「这次请求背后有没有人」。部署打开它之后，一次发送要等证明取得并校验完成；部署关闭它时，发送路径与没有这项能力时相同。

**接受的代价：**

- **关闭时残余风险原样成立。** 缺省 `off`，每一处依赖证明的防护都不在场；短信与邮件轰炸仍只受预算与退避约束，威胁模型把它们记为接受的残余风险。
- **打开后提供方进入发送路径。** 提供方或其存储不可用时，发送答 503 而不是照常发送；这是拒绝方向，不因故障放宽。
- **客户端要取得证明。** 打开 `pow` 的客户端要解一道工作量证明，打开 `turnstile` 的要渲染控件；不这样做的客户端在闸打开时发不出验证消息。
- **装配多出依赖。** `pow` 需要键值存储与路由挂载口，`turnstile` 需要站点键、密钥与主机名，密钥还要登记为日志的字面量脱敏规则；这些依赖只在对应模式下必需，关闭时都不在场。
- **证明不替代预算。** 闸不计数、不设额度，也不感知用途；预算仍是发送量的上界，证明只抬高单次发送的代价。
- **注册仍是滥用面。** 注册不发送消息，因此不受该闸保护；批量注册的上界仍由注册预算与退避给出。

## 失效条件

- 需求改为人机验证缺省开启，或要求注册也经该闸；此时「部署选择」与「注册不验」的前提不再成立。
- 部署的客户端无法取得任何证明（例如没有脚本能力），使闸打开时合法用户一律发不出验证消息；接缝需要增加不依赖客户端控件的机制。
- 提供方不能再保证证明的一次性，或站点校验不再报告令牌重复；接缝必须自己保存已用证明，`turnstile` 机制随之重议。
