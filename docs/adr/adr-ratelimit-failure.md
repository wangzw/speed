# 计数后端不可达时限流放行

## 背景

计数经键值原语，后端可能是远程的。原语不可达即操作失败，它不重试也不降级。限流要在后端失败时给出一个行为，而两条路都有代价。

审计模块对写失败取 fail-open，但它的判据是记录与业务是不是一件工作：审计写失败不改变业务结果。限流的前提相反：它在请求之前介入，它的判定就是改不改变这个请求。

日志链与指标功能都是装配里可以缺席的：日志模块可以不纳入，指标功能是可选取用的功能。一条失败信号不能只靠其中任何一条，要能被人在日志链之外看见。

## 考虑过的选项

### 拒绝（fail-closed）

**否决**：计数后端抖动会让全部受守的端一并不可用。限流是防滥用一侧，不是数据越权一侧；把一次后端故障放大成全端拒绝，代价大于那段时间限流失效。

### 回退到进程内计数

**否决**：多副本下每个副本各算一份，实际额度随副本数放大，而这条失效是无声的：它看起来像限流在正常工作。这与计数经共享原语这条原则相悖。

### 放行并报信号

**采纳**，见决策。

## 决策

采纳：**计数后端不可达时放行该请求，并把这件事单独报出。** 第一次失败与随后的恢复各写一行到标准错误，不经日志链；此后的失败只计数不写行。

信号不进日志链的理由与日志模块报告自身失败、审计模块报告写失败时相同：报告链自身可能缺席，也可能被整条关掉。

## 后果

**接受的代价：**

- 后端不可达期间限流不生效，而这段时间与所有请求都在额度之内在外部不可区分，察觉途径只有那行标准错误。
- 一次故障只写两行，中间的失败次数只在进程内计数，不对外暴露。只落在一部分请求上的故障同样只写两行，因而恢复那一行要等这一类静默持续一段时间之后才写出。
- 一个持续不可达的后端不会让进程停止服务，故障因而可能被长时间忽略。

## 失效条件

若限流在某个部署里承担的是数据安全边界（例如它是某个高价值接口的唯一防线），放行的代价会超过拒绝，这条记录需要重新检验。
