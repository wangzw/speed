# 成员关系删除的清理是同步接口，事件只作崩溃窗口补偿

## 背景

成员关系删除在认证模块自己的事务里提交。别的模块按这条成员关系持有数据：平台域的绑定在成员关系成立时才允许写入，成员关系被移除后，残留的绑定会替一个已不属于平台租户的账户继续判定平台权限。这些表不在认证模块的事务里，删除提交与它们的清理之间没有原子性。

需要成立的条件：

- 成员关系删除提交之后，平台域的绑定必须随即撤销，不能只等一个异步事件。
- 删除已经生效而清理失败时，调用方要能知道这一点，并能以同一个调用重试；重试必须幂等，第二次不写任何东西也不报错。
- 进程在提交与清理之间崩掉时，不能留下一条继续授予权限的绑定。
- 账户删除是账户的终态抹除，不能被“租户至少保留一名管理员”这类守卫挡住。
- 同一租户上两次并发删除不能都通过“最后一名租户管理员”检查之后各自提交。
- 事件总线是可选依赖：有的装配没有总线，事件的投递是异步的、至少一次，送达时间不受删除方控制。

## 考虑过的选项

### 只靠 `authn.membership.changed` 事件级联清理

成员关系删除只发布事件，由持有数据的模块订阅并清理。

**否决**：没有事件总线的装配里清理根本不会发生；即使有总线，清理也滞后于提交，删除的调用方既不能得知清理失败，也没有可重试的返回路径。事件送达的延迟与删除的完成时间脱钩，这正是该条件要排除的窗口。

### 在删除的事务里完成跨模块清理

把别的模块的清理写进成员关系删除的同一个事务，提交即全部生效。

**否决**：跨模块的表不在同一个事务边界内，认证模块也不持有别的模块的表。要这样做，认证模块得知道每个持有数据的模块的表结构与写入口，模块依赖会反转，新的持有方也无法接入。

### 只有同步生命周期钩子

删除提交之后同步调用持有方的清理钩子，不发布事件。

**否决**：进程恰在提交与钩子之间崩掉时，没有任何机制会重试这段清理；残留的绑定继续授予权限，而调用方已经不在了。同步调用保证正常路径，但不覆盖崩溃窗口。

### 同步生命周期钩子为正常路径，事件为崩溃窗口的补偿

删除提交之后同步调用全部钩子，失败以可重试的错误返回；同一事件仍然发布，只用于补偿崩溃与未执行删除的副本。

**采纳**，见决策。

## 决策

**采用同步接口为正常清理路径，`authn.membership.changed` 只作崩溃窗口补偿。**

- **删除提交之后同步调用全部 `MembershipLifecycle.MembershipRemoved`。** 任一钩子失败使本次调用返回 `ErrCleanupIncomplete`，删除保持生效；重试同一个调用幂等地补完，钩子第二次执行不写任何东西也不报错。钩子在删除事务之外、租户锁释放之后运行，一次慢清理不阻塞同租户的后续删除，只延迟本次调用的应答。
- **`authn.membership.changed` 保留，只作补偿。** 它覆盖进程在提交与钩子之间崩溃以及另一个副本没有执行这次删除的情形。正常路径不依赖它；处理器与钩子执行同一段幂等清理，重复投递不产生任何写入。
- **账户删除是明示例外。** 账户删除不询问 `MembershipGuard`，也不调用 `MembershipLifecycle`：它的收尾经 `MembershipCleanup.RemoveMembershipForDeletion` 删除管理员加进来的成员关系行，抹除本身就是这一路的清理。这些行仍然发布事件，订阅者照常收到。账户删除因此可以让一个仍在服务的租户没有租户管理员绑定，直到有人写入一条新绑定。
- **判定的两条路径取同一把按租户的锁，锁归授权模块。** `Manager.DeleteBinding` 在数最后一条租户管理员绑定之前取 `authz.TenantLock`，提交之后释放；成员关系删除在问守卫之前取同一个对象，`MembershipGuard.Lock` 委托给它。宿主不装配时用进程内按租户的默认实现，单实例无需配置即正确；多副本的串行改由宿主用数据库级锁承担：PostgreSQL 上是会话级 advisory lock，SQLite 仍是进程内。不共享数据库的副本之间不保证串行。锁不可重入：账户删除的收尾与成员关系删除的级联走**不取锁的清理路径**（`ClearAccountBindings`，或模块内部同等的直接删除）；不得经 `DeleteBinding`，那会重入同一把锁而死锁。锁取不到即返回 `ErrUnavailable`，删除不发生，绝不按放行处理。

## 后果

正常路径的清理与删除同一次调用完成，失败对调用方可见并可重试；崩溃窗口由事件补偿，重复投递幂等。租户的“最后一名管理员”检查与删除提交被同一把租户锁串起来，同一租户的两次并发删除不会都通过检查。

**代价：**

- **每个按成员关系持有数据的模块都要实现钩子并保持幂等。** 一个只实现事件订阅的持有方在正常路径上不会及时清理，它的数据要等下一个事件或一次补偿才被撤销。
- **钩子与订阅者必须共用同一段幂等清理。** 两条路径各写一份，迟早给出不同的结果；其中一条的修复不会到达另一条。
- **没有事件总线的装配没有崩溃窗口补偿。** 提交与钩子之间的进程崩溃会留下指向已离开成员的绑定，直到下一次显式删除或一次人工清理。
- **账户删除可以留下没有租户管理员的租户。** 它是“至少保留一名管理员”规则的明示例外，补齐要由一条新绑定完成。
- **租户锁只在共享数据库的副本之间串行。** 不共享数据库的副本可能各自通过检查，而对方刚删掉的是最后一条管理员绑定；这是装配级非保证。
- **每个持有中的数据库锁占一条池化连接，删除事务再占一条。** N 个并发管理员删除因此至少要 2N+1 条连接；低于这个数时取锁等待，等到上下文结束答 503。进程内默认实现不额外占连接。连接数由宿主的装配给出，不是本模块能替它选的值。
- **事件路径带来至少一次的重复投递。** 它不产生错误，但每个订阅者都必须按幂等处理。

## 失效条件

事件投递同时具备调用方可见的同步失败回执与无总线时的清理保证时，同步接口失去理由；或者部署保证进程不会在提交与钩子之间崩溃（单进程且停机路径同步排空）时，事件补偿不再需要。任一条件成立，删除的清理可以改由事件承担。
