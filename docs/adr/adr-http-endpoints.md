# 一个入口模块承载多个具名端点

## 背景

业务流量与管理流量要分别暴露。健康检查、指标与诊断面向运维网络，业务 API 面向外部调用方，两者的可达范围不同，因而要落在不同的端点上，并进而可以落在不同的监听上。

模块名在进程内唯一，同名登记是登记那一刻就暴露的冲突（见 `core` 的设计文档）。

模块之间不按名称取用（架构不变量 9）。该条约束的是取得另一个模块实例的途径。

每个端点有自己的中间件链，认证与限流各自按端登记；地址与超时不在端点上，而在端点挂靠的监听上（[ADR-http-listener-endpoint-split](adr-http-listener-endpoint-split.md)）。管理端是否经过它们，取决于登记这两层的模块怎样选端：限流只在自己的配置点名的端上登记；认证默认守入口模块声明的全部端，只守业务端要靠显式的端名清单收窄，或由挂路由的模块对个别路由登记免认证（[ADR-authn-exemption](adr-authn-exemption.md)，端名读口见 [ADR-http-enumeration](adr-http-enumeration.md)）。

## 考虑过的选项

### 一个模块一个端点，管理面另立模块

入口模块只管一个端点，管理端由另一个模块自己监听。

**否决**：管理面模块要把监听、排空、链组装与登记接口重复实现一遍。两套实现此后各自演化，而停机时序与链组装正是最不应该有两个版本的部分。

### 每个端点一个模块实例

同一个入口模块登记多次，每个实例持有一个端点。

**否决**：模块名进程内唯一，同一个模块登记两次即重名冲突，要为此引入工厂式登记；多个实例交付同一功能，还要面对排他消解，而它们本不冲突。

### 一个模块多个具名端点

一份配置中声明多个具名端点，登记时指定落在哪一个。

**采纳**，见决策。

## 决策

采纳：入口模块在一份配置中声明多个具名端点，每个有自己的中间件链，并按名挂在一条由配置声明的监听上；登记路由与中间件时指定端名。

端名是本模块配置内的标识，不是模块名。取用本模块的功能仍然只经功能标识，架构不变量 9 约束的是取得另一个模块实例的途径，端名不是那个途径。

登记到未声明的端名即启动失败，不回退到任何默认端。

## 后果

管理面与业务面共用同一套监听、排空与链组装，只有一份实现。

每个端有自己的中间件链，认证与限流各自按端登记，两者都可以只登记在业务端。

管理端要留在认证之外，做法限于以下两种（封闭集）：认证的端名清单写成收窄后的显式清单，或对管理端上的个别路由登记免认证。

端名错写在启动时暴露，而不是表现为一条访问不到的路由。

**接受的代价：**

- 登记接口上多出一个端名参数，只用一个端的宿主同样要面对它。
- 宿主没有想到的端也被认证守住。探活、指标与运维端上的请求缺省要出示凭据，宿主必须显式处理这些端；只想让认证守业务端的宿主要写出端名清单。
- 端名是字符串，登记方与配置之间的对应靠启动期校验建立，编译器不参与。
- 全部端点与监听共享本模块的生命周期：任一条监听绑定失败即整体启动失败，已绑定的其余监听随之释放。
