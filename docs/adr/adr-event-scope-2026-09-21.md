# 事件载荷结构化读取，总线内置租户标识

## 状态

已接受

## 背景

横切能力需要拿到业务模块产生的领域事实：审计要记下谁在何时改了什么，可观测性要按租户与业务类型切分。目前能拿到这类事实的途径只有一个——数据库模块的插件扩展点，它作用于每一条语句。那条途径覆盖数据库写操作，覆盖不到未产生写操作的领域事实，也覆盖不到写操作与业务动作之间的对应（一次业务动作可能不产生写，一次写也可能对应多个业务动作的组合）。

另一条途径是让每个横切模块各自找到发布那些事实的业务模块。它要求业务模块认识审计与可观测性，或者反过来，在依赖图的下层向上引用。

发布与订阅之间有一个本仓特有的约束：订阅方通常不能 import 发布方的包。跨模块 import 一个具体类型会把依赖方向倒转，发布方与订阅方之间因而不能共享载荷的静态类型。

## 考虑过的选项

### 不引入事件总线，领域事实只能经数据库插件取得

**否决**：它把一类事实永久排除在外。审计与可观测性要么只覆盖写操作，要么各自耦合每一个业务模块——耦合每一个业务模块把横切能力反向推进业务模块的依赖里，而这正是把这些能力做成独立模块要消除的东西。

### 引入总线，发布方与订阅方共享载荷的静态类型

**否决**：订阅方 import 发布方的类型即产生反向依赖，两者之间还要有共同的依赖，否则发布方与订阅方无法引用同一个类型。载荷因此只能由第三方包定义，而那个包会被每一个发布事件的模块依赖——一个纯粹为了承载数据类型而存在、不含任何功能的发布单元。

### 引入总线，载荷结构化读取，租户标识内置

**采纳**，见决策。

## 决策

采纳：**模块交付事件总线功能。发布方按类型名发布一个事件，订阅方按类型名订阅；事件携带一个不透明的载荷与一个租户标识。**

**载荷由订阅方结构化读取，不做类型断言。** 同进程投递时订阅方拿到的是发布方自己的具体值，经传输投递时拿到的是传输解出来的结构；两种形状下，订阅方按字段名经序列化往返读取它需要的字段，而不依赖任何一个静态类型。这条约束是订阅方不能 import 发布方类型的直接结果，不是风格选择。

**事件携带租户标识，它的类型是字符串。** 租户是这些事件在横切能力那一侧的切分维度，让每个发布方自行把它塞进载荷，等于要求每一个发布方都记得，且字段名靠各自约定；审计要按租户切分时就只能猜。

**标识不取租户模块的那个标识类型。** 它虽然只是一个字符串的具名类型，但 Go 的依赖解析按模块进行：import 租户模块的接口包，会让本模块以及每一个使用本模块的宿主，在构建图里带上租户模块的全部依赖——数据库、GORM、SQLite 驱动、HTTP 入口、认证。接口包自身的代码不 import 它们，挡不住这件事，因为决定构建图的是模块的依赖声明而不是包内的 import。本模块与键值模块同处依赖图底层，接受这条边等于让每一个只想发布事件的宿主承担一个数据库堆栈。

**事件类型名是发布方与订阅方之间的约定字符串，不做校验。** 订阅即登记：一个传入了类型名与处理函数的订阅，就是本进程对该类型到场的事实的全部记录。本模块不提供类型名的注册面，也不在启动期校验一个类型名有没有发布方——发布方可以在运行期的任意时刻出现。

## 后果

审计与可观测性只要订阅总线即可拿到领域事实，不必认识任何一个业务模块，业务模块也不必认识它们。

事件类型名成为跨模块的隐式契约：发布方写下一个字符串，订阅方写下同一个字符串，两者之间没有编译期检查，改名会静默断开订阅。

**接受的代价：**

- 订阅方读不到载荷时会静默丢弃这条事件。它不能 import 发布方的类型，也就没有一处能靠编译发现字段改名。这条契约的维持靠约定与测试，不靠类型系统。
- 事件类型名没有校验，"订阅了一个从不发布的类型"与"发布了一个无人订阅的类型"都不报错。发布了一个无人订阅的类型，意味着发布方的意图落空而无人知晓。
- 租户标识在本模块是字符串，与租户模块的标识类型之间没有编译期联系。两者的取值集合是否一致，由使用它们的代码各自保证，本模块校验不了。
- 载荷经序列化往返，因而必须是可序列化的。一个含有不可序列化字段的值在发布时才失败，发布方写下发布语句时看不出这一点。

## 失效条件

若订阅方需要的载荷结构复杂到结构化探测无法可靠表达——多层嵌套、多态、随类型名变化的形状——则"按字段名读取"不再够用，那时需要在载荷之外另有一处携带其形状的落点。

若出现一个需要拿到领域事实的消费方，它与发布方之间可以共享静态类型且不产生反向依赖（例如发布方与消费方同属一个发布单元），则那一条通路不必经总线，本决策不排除它。
