# 入口模块定义默认的错误响应形状，并经可选接缝接受定制

## 状态

已接受

## 背景

请求路径上的各层各自收口自己的拒绝：认证网关写 401，限流层写 429，租户解析层写 404 与 500，兜底层写 500。它们各自调用 `WriteHeader`，没有共用的响应形状，同一个 API 的客户端要为每一类拒绝分别处理。认证、租户、审计各自处理 panic 而口径互不一致，已在 [ADR-http-recovery-2026-09-22](adr-http-recovery-2026-09-22.md) 的背景里记过一次；错误响应是同一类分歧的另一处。

登记面锚定 gin（[ADR-http-surface-2026-09-14](adr-http-surface-2026-09-14.md)）。gin 把错误交给 handler 自己写出，不定义统一的错误响应形状，也没有集中的错误处理接缝。

兜底层是引擎上的一个 gin handler，手里有 `*gin.Context`。写出仍经同一处接缝：`ErrorResponder` 的签名只取 `http.ResponseWriter` 与 `*http.Request`，形状因而不依赖 gin 的类型。

RFC 9457 是 HTTP API 错误响应的现成标准，规定了字段与 `application/problem+json` 媒体类型。

## 考虑过的选项

### 不定义形状，由各模块自己写出

各层照原样写自己的状态码与响应体。

**否决**：分歧已经发生，客户端无法对拒绝做统一处理，每新增一个会拒绝请求的层就要再写一遍。

### 入口模块只写状态码，形状由提供 API 的模块经接缝决定

兜底层只写状态码、不写响应体，有交付者时才由它决定形状。

**否决**：它只覆盖兜底层写出的那一类。认证、限流、租户解析的拒绝与无匹配路由的响应仍然各写各的，而没有模块交付接缝的装配里，全部错误都没有响应体。

### 入口模块定义自己选字段的默认形状

字段与媒体类型由入口模块自拟。

**否决**：那是另造一套客户端与现成工具都不认识的形状，而标准已经存在。

### 按错误类别分设多个接缝

兜底、校验失败、认证拒绝等各有一个可替换的接缝。

**否决**：同一个 API 的各类错误只该有一个形状，分设之后各接缝各自漂移。

### 入口模块定义默认形状，取 RFC 9457，经一个可选接缝整体替换

**采纳**，见决策。

## 决策

采纳：入口模块以 RFC 9457 的字段定义错误响应的内容，默认以 `application/problem+json` 写出；一个可选的功能接口允许交付它的模块整体替换这一形状。

入口模块自己写出的错误响应——兜底层写出的、无匹配路由的、方法不允许的——以及供其他层调用的写出入口，都经同一处决定形状。handler 自己用 gin 写出的响应不经它。

## 后果

客户端面对一种错误形状，认证、限流、租户解析的拒绝共用它。

默认形状用现成标准，不另造；整体替换让一个进程里的错误响应只有一个形状来源。

**接受的代价：**

- 形状成为入口模块接口面的一部分：内容的字段与默认的媒体类型变更即不兼容变更。
- 不经写出入口的错误不在覆盖内。handler 自己写出的响应、某一层绕过写出入口直接写状态码，都会让形状再次不一致；统一取决于各层是否使用它。
- 一个进程里只有一个形状来源。同一进程的各监听端需要不同形状时，由交付者按请求自行区分。
- 这一块是自造，不是桥接：gin 没有对应的接缝，选 gin 即由入口模块自备（[ADR-http-surface-2026-09-14](adr-http-surface-2026-09-14.md)）。

## 失效条件

若在已发布的宿主上默认形状都被替换，即每一处都交付了自己的接缝实现，则默认形状这一半可以去掉，让形状完全归交付方。

若 gin 提供了统一的错误响应形状与集中的错误处理接缝，则本记录自造的部分应当改为桥接。
