# 隔离落在共享表加租户列，过滤经 GORM 插件，模型按约定声明自己受约束

## 背景

数据库模块把需要上层概念的横切能力推到插件扩展点，并规定租户隔离由租户模块实现、由它定义自己的模型约定（[ADR-db-plugin-scope](adr-db-plugin-scope.md)）。插件的安装取启用集：一个本次不运行的模块，它声明的插件不安装（[ADR-module-resource-scope](adr-module-resource-scope.md)）。

隔离的物理形态此前没有出处。可选的有共享表加一列、每租户一个库、每租户一个 schema、数据库自带的行级安全，以及不经插件、由各仓储手写条件。

几条既成事实收窄了范围。经模块机制交付的库只有一个——配置给出的，或宿主预置的——额外的连接由调用方经接口自建，不进装配范围、不施加迁移（[ADR-db-multiplicity](adr-db-multiplicity.md)）。迁移按声明集一次性施加（[ADR-db-migration](adr-db-migration.md)）。方言是一个封闭集合，SQLite 在其中（见 `db` 设计文档的扩展点）。

**插件实例在 `init` 期随描述符冻结，而数据库模块在自己的 `New` 中安装它。** 名册子包声明对数据库功能的依赖，因而排在数据库模块之后构造：插件的 `Initialize` 在它所属模块的 `New` 之前就被调用了，插件实例不可能持有那个模块在后来的任何阶段算出的东西——不论是 `New`、`Init`，还是名册快照的装载。而一个进程要执行两条命令就建两个注册表，两个装配共用描述符上那一个实例。这两件事合起来，把「插件能持有随运行而变的状态」这条路封死。

## 考虑过的选项

### 每租户一个库

隔离落在物理边界上，每个租户一个数据库。

**否决**：迁移要在一个运行期才知道的集合上施加多次，而迁移按声明集一次性施加。采纳它要同时推翻三条已接受的记录。连接池另按库各算一份，租户数成为连接数的乘数，而连接数有上界。

### 每租户一个 schema

隔离落在命名空间上，一个库里按 schema 分租户。

**否决**：迁移要施加多次这一条与上一个选项相同。另加，schema 的选定落在物理连接的会话状态上，而句柄从池里借连接：让隔离取决于连接怎么配，正是迁移互斥拒绝让标识随会话状态派生时给出的理由（[ADR-db-migration](adr-db-migration.md)）。

### 数据库自带的行级安全

隔离落在数据库自己的策略机制上。

**否决**：方言是封闭集合而 SQLite 在其中，SQLite 没有这套机制；采纳它等于让隔离只在一种方言下成立。它同样要求在每条语句之前于同一条物理连接上设好会话变量，与池化句柄不相容。

### 不经插件，由各仓储手写条件

每个查询自己带上租户条件。

**否决**：漏一条就是跨租户读出，且不会在该条语句上显形——这正是数据库模块把这类能力判为「必须作用于每一条语句」的判据（[ADR-db-plugin-scope](adr-db-plugin-scope.md)），而插件是该记录裁定的唯一途径。

### 模型实现一个标记接口

约定做成一个标记接口，模型实现它的方法即声明受约束，那一列另按各自的迁移文件加。

**否决**：声明与那一列成为两份可以对不上的事实。写下一个空方法就算声明了，而列可以不存在、可以写错名字、可以不是非空；三种不一致没有一种会在声明处显形，它们都表现为运行期的同一类失败——插件认为该过滤而语句报列不存在，或者插件认为不该过滤而语句照常读出全部租户。内嵌一个结构体把声明与那一列合成一个动作，这类不一致因而从状态空间里去掉。数据库模块的后果段把承担方的交付形态写成「模型约定与标记接口」（[ADR-db-plugin-scope](adr-db-plugin-scope.md)）；本模块交付的是模型约定，标记接口是约定与那一列分成两处时的一种形态，不是约定本身。

### 租户列只带索引，不进键

那一列是一个普通列，模型自己的键自己声明，两个租户的同一业务标识各自唯一。

**否决**：唯一约束不以租户列打头的表，`Save` 与 `OnConflict` 产生的插入会碰到**另一个租户**的行并把它改成写入方的租户。语句里没有任何一处写了别的租户——写入方写的是它自己的标识——插件因而没有可拒绝的东西，这一档也不是逐条判定关得掉的：它来自键的结构。把租户列放进键里，这个结构从 schema 上就不存在。代价是模型的键成了复合键，一个想用全局生成标识做主键的宿主表达不出来，而那正是会产生这个洞的结构。

### 为只读另设一个约定类型

读别的模块的表时内嵌另一个只用于读的约定类型，插件据它给读加条件，并拒绝经它发出的每一条写。

**否决**：约定成为两个类型，识别、联接与子查询的判定都要对两个类型各做一遍，对外接口上多出一个类型。它挡住的写，是一个模块写另一个模块的表，而那条边界由「表归声明它的模块写」划出，不由约定的类型划出：一个不内嵌任何约定的模型、一条原生 SQL 照样写得进那张表。

### 读别的模块的表时整段跨租户，自己写租户条件

**否决**：与由各仓储手写条件是同一个形态，漏一条就是跨租户读出，理由见上。

### 按约定的字段名找到那一列，填列与核对作用于约定自己的字段

在 schema 上按约定的字段名查找，命中且出自约定类型即为受约束，插件填的、核对的都是约定自己的那个字段。

**否决**：GORM（[REF-gorm](../references.md)）把每一列绑到一个字段上——路径最短的那一个，同样短的取先声明的——读写只经它，按字段名查找找到的也是它。模型在约定旁边声明一个同名字段，或经另一处先于约定的内嵌带上同一列，按名字找到的就不是约定的字段，模型被当成全局表：没有租户的读读出全部租户，写不填也不核对，而模型明明内嵌了约定。另起名字、标着那一列的字段不被名字找到，找到的仍是约定的字段，而 GORM 从不写它：填列落空，核对的是一个到不了表里的值，GORM 写下的那个字段反倒没人判。

### 内嵌约定、又在那一列上另声明字段的模型一律拒绝

认出约定而那一列绑在别的字段上时，经这个模型的每一条语句都失败。

**否决**：这样的模型读写形态是确定的——GORM 读写绑在那一列上的那个字段——插件照它加条件、填列、核对，租户约束照样落在表上。拒绝挡掉的是隔离照样成立的模型：只读模型给租户字段换一个接得住 NULL 的类型，以便跨租户读出不属于任何租户的行，就是这种形态。拒绝给出的修复只有一种，回到约定原本的结构，那个结构又恰好表达不了可空的读。

### 按约定声明的列名找租户列

在 schema 上取 GORM 绑到约定标签里那个列名 `tenant_id` 上的字段，再确认模型内嵌了约定。

**否决**：内嵌前缀改掉了那一列的名字——具名字段 `Owner tenant.Model` 标了 `embedded;embeddedPrefix:owner_` 时，约定的字段落在 `owner_tenant_id` 上——按 `tenant_id` 找不到任何字段，模型被当成全局表：没有租户的读读出全部租户，读、改、删都跨租户，插入不填也不核对。列名不是约定的来源，约定的字段才是。

### 把 GORM 不读的内嵌当成全局表

约定放进未导出的基类、未导出的字段或标了 `-` 的字段时，GORM 的 schema 上没有那一列，插件照 schema 把模型当成全局表，写进非保证。

**否决**：这样的模型内嵌了约定，写它的人要的是受约束，当成全局表的结局是静默的跨租户读写，正是隔离要挡的那一类。插件从模型的类型上认得出这种内嵌，认得出却放行，等于把一个查得出的缺陷交给评审。

### GORM 不读的内嵌照约定声明的列名加条件，只拒绝插入

读、改、删照约定声明的列名加租户条件，GORM 不写那一列的插入按插入行不带租户列拒绝。

**否决**：插件手里没有 GORM 绑到那一列上的字段，填列、主键里租户那一半、赋值的核对都无处落脚。同一个声明落出三种结局：读得通，以结构体插入一律失败，以 map 插入又能写进去。修复只有一种——把约定放到 GORM 读得到的地方——整个模型被拒绝，这个修复在第一条语句上就摆出来。

### 约定内嵌两次、落在两个列上时取其中一个

按 GORM 解析的先后取第一个约定字段的列作租户列，另一个当普通列。

**否决**：取哪一个是在猜声明方的意图，猜错时读按一个列限定，另一个列上写什么都不核对，两处都不报错。一行只属于一个租户，两列的声明本身就是缺陷。

### 取不出租户列的模型另立一个哨兵

为约定放在 GORM 不读的地方、约定落在两个列上这两种声明另立一个哨兵。

**否决**：这样的模型上没有一处承载得了租户，经它的语句到不了任何一个租户，与插入行不带租户列、跨租户的写把租户列写空同属「一行到不了一个租户」这一类，那一类的哨兵已经有了。调用方对它没有运行期的处置：这样的模型第一条语句就失败，修复在模型的声明上，错误文本点名模型与缘由即可。另立一个名字，不给调用方多出任何一种可写的分支。

### 插入的选列漏掉租户列时由插件把它补进去

GORM 构造出的插入行不带租户列时，插件把那一列加进选列，让填进去的值到达表里。

**否决**：行不带租户列有三种来由：选列没有点名它、省列点了它、绑在它上面的字段不在插入时写出。后两种是调用方与模型显式写下的，补进去就是改写调用方的语句与模型的声明；只补第一种，同一类行在三种写法下有两种结局。拒绝时语句不到达数据库，调用方把租户列点名进选列即可。

### 核对模型上每一个落在租户列上的字段

插入时模型上凡是写到的列被数据库读成租户列的字段，不论 GORM 写不写它，都按它的取值核对。

**否决**：经内嵌重复了某一列、GORM 又不写的字段，它的取值到不了表里，按它拒绝，拒绝的是一条照常落进上下文租户的插入——没写那个字段时它是空串，于是每一次插入都被拒绝。核对的对象应当是会写进表里的值。

### 共享表加租户列，过滤经插件，模型按约定声明

**采纳**，见决策。

## 决策

采纳：隔离落在共享表加一列上；过滤经一条 GORM 插件作用于每一条针对受约束模型的语句；模型按本模块定义的约定声明自己受约束。

```go
// Model 是受租户约束的模型内嵌的约定。它同时是那一列的定义与声明。
type Model struct {
    TenantID ID `gorm:"column:tenant_id;not null;primaryKey"`
}
```

**约定是内嵌一个结构体。** 声明与那一列由同一个动作给出：内嵌它就有了那一列，也就声明了受约束。把两者分成两处的形态被否决了，理由见考虑过的选项。

**插件按来源识别受约束模型与它的租户列**：GORM 从约定的字段解析出的那一列就是租户列——直接内嵌、经公共基类嵌套、以指针内嵌与标了 `embedded` 的字段都算，内嵌前缀改过名的那一列照样是它。判据是模型上有一个出自约定类型的字段，而不是模型上有一个同名的字段，不是按约定的字段名找到的那一个，也不是约定声明的列名上绑着的那一个。识别读的是 GORM 首次遇到该模型时解析并缓存的结果；schema 上没有约定字段的模型，插件另沿模型类型上的内嵌走一遍，找 GORM 不读的那种内嵌。

**内嵌了约定却取不出一个租户列的模型，经它的每一条语句都失败**，不论上下文是否带租户、是否跨租户。这样的声明有两种：约定放在 GORM 不读的地方——未导出的类型或字段、标了 `-` 的字段——那一列因而不在模型上，GORM 既不读它也不写它；约定内嵌两次、落在两个列上，而一行只属于一个租户。失败配 `ErrNoTenantInContext`，错误文本点名模型与缘由：这样的模型上没有一处承载得了上下文里的租户，经它的语句到不了任何一个租户，与插入行不带租户列同属一类。

**插件填列与核对的是 GORM 写出的值。** 那一列的值取自 GORM 绑到那一列上的字段：模型在约定那一列上另声明了字段时，它取代约定的字段，GORM 只读写它。插入时核对的另一种写法，限于 GORM 会写出的字段。

**模型是否声明了约定，本模块验不了。** 一个本该受约束却没有内嵌约定的模型，表现为一张全局表：它的语句不带条件、插入不带值，而没有任何一处会说出来。这一条写进非保证。

**约定的义务落在建表并写入那张表的一方。** 迁移里的键与模型声明的键一致、租户列非空，这两条挡的是写：键不以租户列打头时，一次写经冲突改写另一个租户的行；租户列可空时，写得下一行不属于任何租户的数据。**只为按租户读另一个模块的表而内嵌约定的模型是认可的形态**，称为只读模型：那张表的键与租户列由它的声明方决定，插件照样给只读模型的每一条读加租户条件，租户列为 NULL 的行在任何一个租户下都读不到；只读模型不发写语句，那两条义务因而不约束它。

**名册子包在自己的描述符上声明一条 `db.Plugin` 资源。** 声明它的是名册子包而不是解析子包：隔离与名册是本功能目录在数据库一侧的两件事，由同一次纳入决定去留——插件取启用集，名册表取声明集，拆成两个模块只换来命令树上多一个名字，而漏写它的失效形态与漏写名册完全相同（[ADR-tenant-packaging](adr-tenant-packaging.md)）。**资源声明没有排他这一说**：`Exclusive` 是交付声明的标注，资源只是按类型被收集的元数据（[ADR-module-resources](adr-module-resources.md)）。另一个启用模块因而可以声明自己的 `db.Plugin` 并照样装上，两条插件各加各的条件、各填各的列，没有一处会报出「两份隔离」。

**插件不持有任何随运行而变的状态。** 判据全部来自两处：语句经过的模型——GORM 解析好的 schema 与模型的类型，二者只取决于模型的声明——以及每一条语句的上下文。这不是省事，而是没有别的可能：插件实例随描述符在 `init` 期冻结，而一个进程要执行两条命令就建两个注册表，两个装配共用那一个实例；插件的 `Initialize` 又由数据库模块在自己的 `New` 中调用，早于名册子包的 `New`，也早于任何一次快照装载。把快照或配置装进插件实例的写法在第二个注册表上会覆盖第一个，先建的那个装配此后每条语句都按后者的取值判定。

**读名册因而只发生在解析层。** 插件不认识名册，既不知道一个租户是否存在，也不知道它是否停用。

**插件对每一条语句的判定是四档**，前三档的顺序即定序：

1. 模型没有内嵌约定——不动作，语句原样发出；内嵌了约定却取不出一个租户列——语句失败，不论上下文，配本模块自己的哨兵，点名模型。
2. 上下文带着跨租户的标记——不加条件、不填列，语句照调用方写的发出；只有写进租户列的取值仍要核对，写空的拒绝（[ADR-tenant-scoping](adr-tenant-scoping.md)）。
3. 上下文里有标识——读语句加上条件，写语句把那一列填成这个标识。
4. 没有标识——语句失败，配本模块自己的哨兵，点名模型。

**停用的生效点因而在写进标识的那一步，不在语句级。** 经请求侧到达的语句在解析层就被拦下，经名册的 `Enter` 进入租户的后台路径在进入时就被拦下（[ADR-tenant-scoping-jobs](adr-tenant-scoping-jobs.md)），停用期间仍属于那个租户的工作经名册的另一个进入方法有意进入它（[ADR-tenant-suspension-access](adr-tenant-suspension-access.md)）；一条跨租户的路径不经名册，照常读得到那个租户的数据。这一条写进非保证。

**写语句要填列，不只是加条件**：条件管得住读，管不住插入。插件缺席时租户列没人填，而没被填过的那一列里是空串，非空约束挡不住它；插入之所以失败，靠的是标识类型拒绝以空值被绑定进语句，这是本设计里少数几处 fail-loud 之一。**填进去的值要到得了表**：GORM 构造出的插入行不带租户列的，插件拒绝那次插入，上下文跨不跨租户都如此，与跨租户的插入没写租户列用同一个哨兵。

**插件建议可被多次 `Initialize`。** 数据库模块的 `Open` 自建连接时复用同一批插件实例，GORM 对每个句柄各调一次 `Initialize`；把首个 `*gorm.DB` 捕获进闭包的写法在第二个句柄上安装成功而不生效。数据库模块把这条写成建议（[ADR-db-plugin-scope](adr-db-plugin-scope.md)），本模块接受它并对自己的插件负责。

## 后果

不装配本模块的宿主不承受任何租户概念：模型不必内嵌约定，那一列不存在，语句与被装配之前一字不差（[ADR-db-plugin-scope](adr-db-plugin-scope.md)）。

受约束表的每一个索引以租户列打头，单租户的查询因而不扫全表。这是声明方写迁移文件时的义务，写在设计文档的约定一节。

**接受的代价：**

- **隔离是一条条件，不是一道物理边界。** 条件只加在插件认得出的语句上。原生 SQL 读得到别的租户，而这是 GORM 的结构决定的，不是选择：语句预先填好了 SQL 文本时整段子句构造被跳过。建迁移记录表的那几条语句走的正是这条路，因而不受本插件影响。以 SQL 文本写出的联接只给主表加条件，被联接的表名在插件不解析的文本里；不经受约束模型发出的语句——只写表名、目标是 map 或另一个未内嵌约定的类型——插件认不出它受约束。
- **受约束表的其余索引要以租户列为前缀**，漏了不报错，表现为规模上去之后变慢。主键那一段由约定给出，其余索引仍是声明方写迁移文件时的义务，本模块验不了。
- **一个租户的数据量影响其余租户的查询计划**，共享表下这是同一条表上的事实。按租户导出、删除与搬迁都要自己写，库级工具给不了。
- **插件之间的相对次序依据由数据库模块裁定**（见 `db` 设计文档的插件的安装），本模块只留下那条结论与它的副作用：需要排在租户过滤之后的插件，其所属模块要声明对名册功能的构造期依赖，而那条声明不会把名册模块拉进那条命令的参与集：名册排他交付，依赖闭包不替宿主挑排他的提供者，它的缺席在依赖解析处以缺提供者终止启动，那条命令因而必须点名名册模块，或由宿主为它预置实例。
- **「只有一条租户过滤插件」不是本模块能保证的。** 任何启用模块都能声明自己的 `db.Plugin`，两条插件会被一并装到同一批句柄上，各自加条件、各自填列。排他不是资源能表达的属性，而交付声明管的是功能，不是插件。
- **一个本该受约束却没有内嵌约定的模型静默成为全局表**，没有任何一处会说出来。内嵌约定的模型要么带那一列，要么经它的每一条语句都失败，反过来的方向本模块验不了。
- **内嵌了约定却取不出一个租户列的模型，每一条语句都失败，跨租户的语句也不例外。** 把约定放进未导出公共基类的模型，要把基类导出才发得出语句；约定内嵌两次、落在两个列上的模型，要只留一个。
- **每一条语句都把模型的字段走一遍找约定的字段**，经全局模型的语句也是；schema 上没有约定字段的模型另走一遍类型上的内嵌。代价与字段数成正比，与 GORM 为同一条语句构造子句时的遍历同阶。
- **在约定那一列上另声明字段的模型，约定随它那个字段带来的两道防线要由取代它的字段自己声明。** 主键里租户那一半，只在那个字段标了 `primaryKey` 时才有，否则按键的 upsert 以模型自己的键为冲突目标；以空值被绑定时的拒绝，只在那个字段的类型是标识类型时才有，否则插件缺席的句柄上，一次没填租户列的插入把那个字段的零值原样绑定进去。插件在场时条件、填列与核对照常作用于它。
- **插入的选列要点名租户列。** 只点名别的列的 `Select`、省掉租户列的 `Omit`，在受约束模型上一律被拒绝，即便那张表的租户列带着数据库自己的默认值。
- **只读模型发出的写本模块拦不住。** 插件分不出只读模型与受约束模型，经它发出的写照样被填列与核对，而那张表的键不以租户列打头，一次按键的 upsert 碰得到另一个租户的行。只读模型只发读语句，靠评审守住。
- **本模块不为「哪些模型应当受约束」提供清单。** 表的属性属于声明它的模块，本模块不读别的模块的模型。
- **`Statement.Settings` 一类按语句传递的旁路对任何插件开放**，跨租户标记所依赖的机制挡不住别人猜到它。

## 失效条件

若 GORM 的回调链接口不再允许在写语句上填列——例如插入语句在回调之前就已绑定参数——则「写语句填列」这一档要改为经模型的钩子达成，那会要求约定额外内嵌一个钩子实现，本决策随之改变。

若方言集合扩展到一种既有共享表又提供行级安全的数据库，且它在受支持的部署形态里占多数，则物理形态要与行级安全重新比较。
