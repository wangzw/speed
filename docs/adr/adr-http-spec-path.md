# OpenAPI 片段以相对路径声明，端点前缀与版本段由 Spec 承载

## 背景

模块以 `http.Spec` 声明自己的 OpenAPI 片段。片段里的每条 path 都写着完整路径 `/api/v1/<能力>/...`，而 `Spec` 只带一个逻辑端名 `Endpoint`。由此产生的后果：

- 端点前缀 `/api` 与版本段 `v1` 没有各自的声明点。它们只出现在每条 path 的字面文本里，读不出「这是端点属性」与「这是版本号」的区别，也无法按模块单独声明版本。
- 每份片段把同一段根重复写进每条 path；一个模块升级 API 版本、或一个端点改前缀，要改的是该片段里的每一条 path。
- 端点认领表（宿主配置）与片段路径是两份各自维护的事实，而片段这一侧把认领前缀抄进了每一个 operation。

片段是生成客户端与契约的唯一来源，路径写法属于对外接口面；改它是一次宿主可见的变更。

## 考虑过的选项

### 片段继续写完整路径

维持现状，只在文档里写明根路径的约定。

**否决**：版本与端点前缀仍然没有声明点；版本升级与端点改前缀仍要遍历每条 path。

### 只在 Spec 上声明 Version，端点前缀由配置在合并时拼入

片段路径相对版本，`/api` 由合并方从宿主配置的认领表取。

**否决**：`Spec` 是静态声明，而合并函数是纯函数、不读配置（构建工具在没有任何模块实例时调它）。把端点前缀挪进配置会让构建期与运行期读不到同一份输入；`/api` 又是端点属性，模块声明自己所在端点更自然。

### Prefix 与 Version 都进 Spec，片段路径相对

模块在 `Spec` 上声明 `Prefix: "api"` 与 `Version: "v1"`，两者都是裸段；片段里写 `/auth/me`。读取方把非空部分拼成 `/api/v1` 再接片段路径。

**采纳**，见「决策」。

## 决策

采纳：**`Spec` 增加 `Prefix` 与 `Version` 两个字段，承载端点的路径前缀与该模块服务的 API 版本段；片段里的 paths 写成相对路径，由读取方拼出完整路径。** 两者都写作裸段，斜杠由读取方插入。端点服务在根上时两者皆空，此时片段路径即完整路径。

## 后果

- 一份片段只写自己那一段路径；升级版本是换掉 `Version` 并声明新片段的对应关系，不再遍历每条 path。
- 合并、片段与路由的一致性核对、宿主自己的应用操作标记都经 `Spec.ResolvePath` 拼路径，规则只有一处。
- 形状校验新增三类拒绝：`Prefix` 带首尾斜杠、`Version` 不是一个字面段、某条 path 已经带着拼出的根（会被拼两次）。
- 合并后的契约逐字节不变：这次改动只改变声明的写法，不改变对外路径。

**付出的代价：**

- `Spec` 是对外类型，新增字段是对宿主可见的接口面扩展。
- `Prefix` 与宿主配置的认领前缀仍是两份各自维护的事实，可以互相矛盾；框架不核对二者一致，只有示范的认领测试在文档与配置这一侧兜底。
- 每份片段都必须以相对路径书写，一次迁移涉及全部片段与所有读取片段路径的测试。

## 失效条件

一个模块需要在多个端点前缀上服务同一份片段时，单一的 `Prefix` 不再够用，这条决策需要重新考虑（届时可能需要按端点分别声明）。版本段若获得协商或迁移语义，`Version` 就不再是一个静态段，同样要重审。
