# 短信验证码：挑战状态机归 SMSCodes，发送归顶层能力 sms.Sender

## 状态

已接受

## 背景

短信验证码在认证目录里按用途区分，用途取值是封闭集：`login`（作第一因素）、`mfa`（作第二因素）、`enroll`（登记手机或短信因素时证明号码归属）。各用途对挑战的要求相同：一次性消费、尝试次数上限、失败计数、发送预算。

约束与威胁：

- 验证码空间只有百万量级，不带密钥的摘要等于明文；库一旦被转储，在途挑战即可被直接还原。
- 每条短信有真实成本，短信轰炸专打特定国家与高价号段。匿名流量能触发的发送，上界只能由服务端预算给出。
- 号码是否已登记不得对外暴露（REQ-signin-014）。任何一个预算、应答形态或耗时在已登记与未登记号码之间不同，请求方就能把发送接口当作枚举预言机（枚举防护的总体规则见 [ADR-authn-throttling-2026-10-10](adr-authn-throttling-2026-10-10.md)）。
- 认证选用的国内厂商（阿里云、腾讯云）只收预先审核通过的签名加模板，不收自由文本；模板按语言分别审核，语言因此是模板的一个维度。这是载体侧的性质，不是短信能力的普遍前提：AWS Pinpoint 与 Twilio 不做逐模板审核，接受按模板声明的正文（[ADR-sms-template-review-is-carrier-capability-2026-10-22](adr-sms-template-review-is-carrier-capability-2026-10-22.md)）。
- 厂商发送接口不保证幂等：阿里云接口注释明说不幂等，超时之后调用方无从知道短信是否已发出。
- 厂商 SDK 各自绑定不同的依赖闭包，宿主只应为自己选用的厂商付出依赖（[ADR-authn-packaging-2026-10-10](adr-authn-packaging-2026-10-10.md)）。
- 预算由挑战行的行数得出，行丢失会使预算被放宽，所以挑战行按状态放置的判据进 db（[ADR-authn-state-placement-2026-10-10](adr-authn-state-placement-2026-10-10.md)）。
- 登录由流程引擎驱动，流程记录里的 `sends` 是每流程发送次数的载体（[ADR-authn-login-flow-2026-10-10](adr-authn-login-flow-2026-10-10.md)）。

## 考虑过的选项

### 厂商托管的验证码接口作主路径

由阿里云 `dypnsapi` 一类的托管接口生成、发送、校验验证码，本模块只转发。

**否决**：尝试次数、重放、失败计数是否因重发清零、跨租户的节流如何做，都由厂商决定，且各厂商的规则互不一致，`sms.Sender` 无法立一份统一契约；规则落在厂商一侧，也使「重发不清零失败计数」「抑制行与真实行同路径计数」无法由本模块保证。

### 单一全局预算，且未登记号码不写挑战行

预算只按号码与一个全局值计；未登记且注册关闭的号码直接拒绝，不留任何记录。

**否决**：已登记号码的第二次请求触发重发间隔得到 429，未登记号码因为没有记录永远得不到 429，请求方连发两次即可判断号码是否登记。登录、第二因素与登记共用一个全局预算，则匿名流量耗尽它之后，只有短信因素的用户在已通过口令的情况下也发不出验证码，被锁在第二因素之外。

### `signup` 开放时，对未登记号码的首次发送单设更低的小时预算

意图是限制开放注册带来的发送成本。

**否决**：该预算耗尽时只有未登记号码被拒。攻击者先耗尽它，再探测某个号码：得到 503 的是未登记号码，得到成功的是已登记号码，预算本身成为枚举预言机。注册开放时已登记与未登记号码本来都真实发送，没有需要隐藏的差别，单设预算只制造差别。

### 登录用途也按账户计每小时上限

对所有用途一视同仁，按账户限制每小时发送条数。

**否决**：登录用途的账户要由手机号推出，已登记号码有账户可计、未登记号码没有，两者的应答随之不同，又一次暴露号码是否登记。`mfa` 与 `enroll` 用途的账户由第一因素或会话确定，不经手机号推出，按账户计不泄露这个事实。

### 登录方式与短信因素各自持有挑战状态

短信登录与短信因素各写各的挑战行、各算各的预算。

**否决**：同一号码的重发间隔、小时与日上限、失败退避要跨用途累计；状态分在两处，换一个用途就能绕开另一处的上限，失败计数也无法跨用途不被重发清零。

### 验证码存明文或不带密钥的摘要

挑战行存验证码的明文，或存其 SHA-256。

**否决**：百万量级的空间下，不带密钥的摘要可被穷举还原，与明文无异。

### 适配器遇到超时自行重试

适配层在厂商调用超时或网络错误时重发，以提高到达率。

**否决**：厂商接口不幂等，超时时短信可能已发出，重试会向用户重复投递并重复计费；适配器重试也绕开了引擎的预算计数。

### 挑战状态归 SMSCodes、发送方可插拔、预算同路径计数

SMSCodes 排他持有挑战状态机，`sms.Sender` 作排他的可插拔发送方；预算由挑战行得出，已登记与未登记号码走同一条计数路径；厂商适配只做请求构造、调用与错误归类。

**采纳**，见决策。

## 决策

采纳：短信验证码的全部状态归 `authn.sms` 引擎，发送归可插拔的厂商适配模块；所有预算按同一条计数路径得出，已登记与未登记号码不可区分。

- **能力归属。** `SMSCodes` 由 `authn.sms` 排他交付，持有挑战的全部状态机：写挑战行、预算、尝试次数、消费、入队与发送；验证码明文从不离开引擎。`login.sms` 与 `mfa.sms` 是 `SMSCodes` 的使用方，不持有挑战状态。`sms.Sender` 由 `pkg/sms` 下的载体叶子包（`sms.aliyun`、`sms.tencent`）排他交付，宿主在命令树上选定一个。
- **验证码的存放与校验。** 挑战行只存带密钥摘要，摘要的密钥由 db 根密钥派生；缺根密钥时启动失败，不降级为无密钥摘要。校验以尝试次数的条件递增与一次性消费为准，失败统一返回 `ErrInvalidCredentials`，不区分成因。计算与校验的步骤见 design-authn-sms。
- **重发。** 重发写新挑战行并作废旧行，**不清零失败计数**；手机号维度（`ScopePhone`）的退避键与登录共用同一套退避，不因重发重置。
- **发送语义。** 发送交给有界工作池，`Send` 立即返回，响应时间与厂商延迟无关。`sms.Sender` 的失败只归入 design-authn-failure 登记的发送哨兵。发送后不知是否送达的哨兵当作已发送，**不盲目重发**，用户重新请求时才再发，且计入预算。适配器从不自行重试。
- **预算的判据。** 预算全由 `authn_challenges` 的行数得出，已登记与未登记的号码走同一条计数路径。预算维度、取值与配置键由 design-authn-sms 与 design-authn-config 给全，本记录不复述。判据如下：
  - 全局预算**按用途分设**：匿名登录流量耗尽自己的预算，不挤占已通过口令的第二因素与登记的发送。
  - 按账户计的上限**只对 `mfa` 与 `enroll` 计**，判据是账户不得由手机号推出。
  - 号码前缀必须在放行表里，**放行表缺省为空，空即一律拒绝**；判据是不明确放行就不发。
- **抑制行。** 号码未登记且注册关闭时，照样写一行 `suppressed` 的挑战行：不入队、不发送，但计入全部预算；对外应答与「已发送」同形，随后的答复一律按 `login-failed` 失败，并经一次诱饵比对。号码已验证且账户启用、或注册开放，才真正入队。判据是真实发送与否是已登记与未登记号码之间唯一的差别，且不可从应答观察到。
- **模板与语言。** 模板按（模板，语言）映射到厂商模板编号，缺任何一个组合即 `ErrInvalidConfig`；语言是模板的维度，语言的取得与映射见 design-authn-sms。模板由顶层发送能力 **`pkg/sms`** 做成一等声明，认证所需的模板键是 `authn.code.login`、`authn.code.mfa`、`authn.code.enroll`，覆盖由认证在启动期核对自己所需。
- **厂商适配。** 发送能力抽为顶层能力模块 **`pkg/sms`**，厂商适配是其下的叶子包（`pkg/sms/aliyun`、`pkg/sms/tencent`），各自一个模块；认证经 `pkg/sms` 根包的 `Sender` 发送，不再持有发送方接缝。适配只做构造请求、调用、把响应与错误归入发送哨兵；整个叶子包可以撤掉而不影响其他模块。适配层没有真实凭据无法在线验证，只用 `httptest` 起假端点验请求形状。具体厂商与包路径见 design-sms（[ADR-sms-capability-2026-10-13](adr-sms-capability-2026-10-13.md)）。
- **排他性。** `sms.Sender` 排他交付，多个厂商适配同时纳入在消解阶段失败；排他的消解规则见 design-core，该处的通知功能举例是虚构的，与 `sms.Sender` 无关。

## 后果

挑战行、预算与抑制行共用一张表、一条计数路径，枚举面只剩应答与耗时，由统一应答与诱饵比对守住。登录的预算被耗尽时，第二因素与登记仍可发送。厂商的差别收在适配叶子包内，引擎与上层不感知厂商。

**接受的代价：**

- **「已受理」的统一应答隐藏失败。** 号码未登记、厂商故障、队列满时，用户都看不到失败，只能重试。
- **抑制行把写放大交给匿名请求。** 未登记号码也写一行，匿名流量因此能增长挑战表；增长上界由前述预算给出。
- **号码级预算可被用来拒绝服务。** 对任一已知号码连续请求即可耗尽它的小时与日预算，使该号码在窗口内收到 429；受害者可改用口令、社交、SSO 或通行密钥登录。
- **全局预算耗尽即拒绝该用途的合法用户。** 注册开放且前缀放行时，攻击者可向任意放行前缀的号码触发发送，上界是各用途的全局预算；预算耗尽后，该用途的合法请求得 503。分设使各用途互不挤占，不使各自的耗尽消失。
- **注册开放时未知号码也真实发送。** 此时已登记与未登记号码没有可隐藏的差别，枚举防护靠的是不存在差别，成本由预算承担。
- **不确定即视为已发送的代价。** 超时而实际未发出时，用户要等重发间隔，并为这次重发占用预算。适配器不重试，瞬时网络错误也让用户多点一次重发。
- **缺省拒绝使短信开箱不可用。** 宿主没有配置放行前缀，短信登录与短信因素一律不发送。放行表是可在运行期改的设置，改到更宽松时写一行警告并记一条尽力档审计，事前不拦（[ADR-authn-settings-and-secrets-2026-10-10](adr-authn-settings-and-secrets-2026-10-10.md)）。
- **短信是受限认证器。** SIM 劫持与号码携转使短信登录与短信因素弱于 TOTP 与通行密钥，号码被回收后新持有者可用短信登录旧账户；发送前的风险信号检查不做，因素层面的限制见 [ADR-authn-mfa-2026-10-10](adr-authn-mfa-2026-10-10.md)。
- **厂商 SDK 进入 `pkg` 的依赖。** 叶子包随 `pkg` 模块一并解析，宿主的 `go.sum` 带上未选用厂商的依赖；撤掉叶子包是回退办法。

## 失效条件

以下情形出现时，本决策需要重议：

- 厂商托管验证码接口的规则收敛到可以立统一契约：尝试次数、重放、失败计数不随重发清零，并且节流可由调用方控制。此时「厂商托管接口作主路径」的否决理由消失。
- 抑制行与真实行的应答在观察上可区分（状态码、响应体、头、耗时任一项）。此时统一应答的前提失效，预算统一路径不再足以防枚举。
- 厂商接口提供幂等键，使适配器可以安全重试。此时「不盲目重发」的约束可放宽到适配层。

以下行为是未经运行核实的假设，依赖它们的断言以对应的测试守住，测试失败即视为本决策的前提不成立：

- 假设阿里云各错误码都可归入发送哨兵之一，且超时一类错误只归「不确定」一类。适配层测试用 `httptest` 起假端点，对照 SDK 与厂商文档逐个错误码断言归类，未列出的错误码断言落入「不确定」一类。
- 假设腾讯云 `LimitExceeded.*` 错误码全部是按号码的限流，归 `sms.ErrThrottled` 不会误吞其他含义的限流。适配层测试逐码断言归类。
- 假设阿里云与腾讯云的 SDK 与 TOTP、WebAuthn、SAML、go-oidc 的库在同一个 `pkg` 模块里编译兼容。构建检查把全部厂商适配叶子包与那些库一起编译。
- 假设已登记号码、未登记且注册关闭的号码，其 `Send` 应答在状态码、响应体与头上相同，预算计数的增量相同。契约测试对已登记与抑制两种号码各发一轮，断言应答同形、`authn_challenges` 的计数路径一致；耗时只能证否，不能证真，对照不出差别不构成证明。
