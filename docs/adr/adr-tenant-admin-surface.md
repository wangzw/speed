# 管理面分两档：平台管理面在 /admin，工作区管理面在 /workspace/admin 的租户外壳内

## 背景

平台管理面是平台员工的管理界面，入口固定在 `/admin`。管理面合计有三类端点，判定域与路径前缀各不相同，三者不合并：

- **平台资产**：`/api/v1/system/...`，在平台域判定。
- **平台管理面中按租户寻址的页面**：邀请与成员、SSO，路径在 `/api/v1/tenants/{tenant}/...`，在该租户域判定。持有 `platform-admin` 本身不放行这些路径；调用方要在该租户另有一份绑定，通常经该租户的 `tenant-admin` 治理集取得所需权限。
- **工作区管理面**：`/api/v1/tenants/{tenant}/...`，作用于当前租户，在该租户域判定。

租户内的管理动作——角色、权限与设置——没有租户侧的界面；租户管理员要改自己租户的策略只能走 API，或由平台员工代劳。产品要求租户管理员在自己的租户内自助管理这三类对象。

平台管理面与工作区管理面的作用对象与判定域不同：平台资产跨租户，判定在平台域；按租户寻址的页面与工作区管理面都作用于一个租户，判定在该租户域。路径前缀由作用域决定：平台资产在 `/api/v1/system/...`，按租户寻址的页面与工作区管理面在 `/api/v1/tenants/{tenant}/...`（[ADR-http-api-path-scopes](adr-http-api-path-scopes.md)）。

租户面还受下列既有事实约束：会话的权限集按域分开，租户域集合取当前租户（[ADR-web-tenant-query-key](adr-web-tenant-query-key.md)）；冒充期间生效账户是被冒充账户，管理入口按权限集出现（[ADR-web-impersonation-shell](adr-web-impersonation-shell.md)）；`system` 是名册中的真实租户，个人租户是宿主策略（[ADR-tenant-administration](adr-tenant-administration.md)、[ADR-starters-personal-tenant](adr-starters-personal-tenant.md)）。

## 考虑过的选项

### 为租户管理面另起一个前端包

`tenant-admin-ui` 与 admin-ui 并列，各有一份页面与操作束。

**否决**：两类面的页面——角色列表与编辑、权限授予、绑定、设置——形状与交互高度重合，另起一包要把它们复制一份，两份随后各自漂移；admin-ui 已有的页面与操作束因此无法复用。

### 把租户管理页面并入平台管理面的导航

平台管理面的导航同时列出平台页与租户页，租户页按当前租户取数。

**否决**：平台管理面的入口按 `/admin` 前缀与平台权限集出现，租户页只作用于当前租户、按租户权限集出现。两者放进同一个壳，权限集与当前租户在同一个导航里有两个含义，平台员工看到不属于自己的租户页，租户管理员看到平台页。作用域段所建立的地址分界也随之消失。

### 只做租户侧的 API，不做界面

**否决**：产品要求租户管理员自助管理；只有 API 不构成可用面，每一处管理都要回到平台员工代劳。

### admin-ui 同时承载两个面，页面与操作共用，外壳与入口分立

**采纳**，见决策。

## 决策

采纳：**管理面分两档。平台管理面在 `/admin`，其平台资产读平台域权限集 `permissionSets.system`，按租户寻址的页面在该租户域判定；工作区管理面在 `/workspace/admin`，渲染在 `ProductShell` 内，作用于当前租户，读 `permissionSets.tenant`。两个面共用 admin-ui 的页面与操作束，外壳与入口分立。**

- **admin-ui 的边界。** admin-ui 同时承载两个面的页面与操作。页面与操作束是共用的，外壳与入口各属一面：平台面保留 `AdminShell` 与 `AdminProvider`，工作区面由宿主的 `ProductShell` 承载。
- **数据来源由注入给出。** 共用页面不直接读平台权限集、平台名册或当前租户；租户、权限集、操作实现与导航回调都经入参注入。页面因此能在两个外壳里取各自域的数据，不把平台读带进租户面。
- **路径与请求前缀。** 平台管理面的平台资产在 `/admin` 下，请求落在 `/api/v1/system/...`；平台管理面中按租户寻址的页面（邀请与成员、SSO）请求落在 `/api/v1/tenants/{tenant}/...`，判定在该租户域，持有 `platform-admin` 不因此放行；工作区管理面在 `/workspace/admin` 下，请求落在 `/api/v1/tenants/{tenant}/...`，作用于当前租户。按租户寻址的每条请求都带租户路径段，路径里的租户必须等于请求解析出的租户的别名。
- **入口、导航与首页卡片。** 工作区管理面有独立的导航父项与首页卡片；平台管理面的入口与导航不变。工作区管理面的导航父项只在下列条件全部成立时出现：已认证、当前租户已落定、当前租户不是 `system`、当前租户不是个人租户、会话不在冒充中、当前租户的权限集至少含该面所需的一项权限。页面各自再按权限码做显能判断。
- **页面级回退。** 一条声明所需的权限码未持有，或收窄后没有任何可进入页面时，宿主把请求转到当前可进入的第一条工作区管理页；一条也没有时转到当前租户首页。冒充中、个人租户与 `system` 租户的直达访问都转到当前租户首页。回退只决定落点；宿主的权限守卫仍按精确命中的声明判定，服务端也判定每一条请求。
- **切换语义。** 租户面的权限集绑定到当前租户：切换租户时先同步清空租户域权限集，再按新租户重读；租户面以租户标识为重挂载键，上一租户的页面状态与在途请求不跨到新租户；查询缓存按租户 query key 逐出（[ADR-web-tenant-query-key](adr-web-tenant-query-key.md)）。
- **排除的租户与状态。** 冒充期间不出现工作区管理入口，也不渲染工作区管理页面：冒充会话展示的是被冒充者看到的产品体验，管理动作不放在这条体验里；服务端的判定仍按被冒充账户的权限执行，这条是界面的取舍，不是安全的边界。`system` 租户不出现工作区管理面，它由平台管理面管理。个人租户不出现工作区管理面，个人租户的成员与角色由宿主自己的策略管理。冒充中、个人租户与 `system` 租户的直达访问都转到当前租户首页。
- **页面与操作的分层归设计文档。** 页面清单、操作束形状与导航分组在 admin-ui 与示范宿主的设计文档里，本记录不重述。

## 后果

两个管理面共用一个前端包，页面与操作不重复实现；外壳与入口分属两面，平台权限集与当前租户不在同一个壳里争用含义。租户管理员在自己的租户内有了可用的管理面；平台管理面继续携带平台资产，以及按租户寻址的邀请、成员与 SSO 页面。

**接受的代价：**

- **admin-ui 的公开面同时服务两个面。** 页面与操作束的行为变化同时影响平台面与工作区面，一处改动要在两个装配里验证。
- **页面必须经注入取数。** 任何页面直接读平台权限集、平台名册或当前租户，都会在另一面读出错误的域；这条靠代码审查与测试守住，没有类型强制。
- **租户面多一层重挂载。** 切换租户会丢弃页面内状态并重发当前的读；这是不把上一租户的状态带进新租户的代价。
- **平台员工在按租户寻址的页面上需要该租户的绑定。** 持有 `platform-admin` 不使调用方通过该租户的邀请、成员或 SSO 页面；平台员工要在该租户另行持有相应权限，通常经该租户的 `tenant-admin`。这是平台域判定与租户域判定分开的代价。
- **两类租户没有管理面。** `system` 与个人租户的管理仍由平台员工或宿主策略承担；产品若要求这两类租户自助管理，要另立一条面。
- **冒充期间租户面不可达。** 冒充者不能以被冒充账户的身份进入工作区管理面；要看工作区管理面，要先结束冒充。

## 失效条件

- 两个面的页面不再重合，或租户面需要一套与平台面不同的交互原语：共用 admin-ui 的理由减弱，拆包要重新比较。
- 租户面需要平台管理面没有的全局导航或跨租户视图：`ProductShell` 作为租户面外壳的选择要重新裁定。
- 个人租户或 `system` 租户被要求拥有工作区管理面：本条的两类排除要重议。
