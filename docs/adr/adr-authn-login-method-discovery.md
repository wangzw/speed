# 登录方式的发现：渠道来源是后端发现端点，方法自带描述符

## 背景

前端要「后端提供什么登录途径就渲染什么」，不硬编码名字到界面的映射。它需要的不只是方法的名单，而是每个方法怎么画：直接渲染表单起流程（口令、短信），还是渲染一个按钮，起流程后拿回跳步（社交），还是先输邮箱、由后端 discover 出 IdP（企业 OIDC 与 SAML），还是通行密钥的仪式。它还需要知道当前部署是否开放注册、有哪些第二因素种类可选。

约束如下：

- 第一因素方法是并立的叶子包，各自交付 `LoginMethod` 接缝；引擎不 import 任何方法，方法集合由 `core.ResolveAll` 汇总（[ADR-authn-login-flow](adr-authn-login-flow.md)）。任何方法专属的知识（名字、品牌、首步字段）都只能由方法自己持有。
- 方法名属于对外接口面，但它出现的地方是路由、流程记录与指标属性，不是渲染契约；名字本身不告诉前端该画表单还是画按钮。
- 首步字段是对交互的事实：方法在 `Begin` 以空字段调用时无副作用地返回首个 prompt，字段取自那里。
- 注册开关 `authn.account.signup` 是部署级闭集开关；一个方法能否为未知标识开户是各方法自己的事实，彼此不同：短信与社交在未知标识上开户，口令对未知标识直接拒绝（REQ-signup-012、REQ-signup-048、REQ-signup-049、REQ-signin-007）（[ADR-authn-accounts](adr-authn-accounts.md)）。
- 可用因素种类是装配收到的（部署级，谁可选），与账户级「本人已登记因素」是两回事。
- 企业 SSO 的提供方清单刻意不公开：它按邮箱域 discover，不泄露账户存在性（[ADR-authn-sso](adr-authn-sso.md)）。发现端点不得成为它的旁路。

`GET B/methods` 当前只答方法名数组（`{"methods":["github", ...]}`），不含上述任何一条。

## 考虑过的选项

### 维持名字数组，前端硬编码名字到界面的映射

发现端点继续只答方法名。

**否决**：前端要与后端方法集合同步维护一张名字到界面的表，新增或停用一个方法都要改前端；名字不是给前端渲染用的对外接口面，把渲染知识建立在其上，等于让两处各自维护同一套方法世界的视图，缓慢漂移。品牌标签与 i18n 也各存一份。

### 复刻 legacy 的公开配置端点

把登录途径、注册开关等做成一份公开的部署配置文档，前端读它。

**否决**：要在方法与配置之间再维护一份形状相同的数据源，与方法自报的字段重复，两处必然漂移；配置端点面向的是部署参数，不是「每个方法怎么画」这层逐方法形状，硬塞进去会让两者互相牵制。

### 前端逐一调用每个方法的探测接口

每个方法各挂一个公开探测路由，前端逐方法问。

**否决**：N 个方法就是 N 次往返；每个方法都要新增一个公开只读路由，方法与其渲染探测耦合，新增方法就新增一处公开面。

### 发现端点发布方法描述符，方法经接缝自报

`LoginMethod` 增一个 `Describe()`，方法自报名字、渲染类别、线协议、品牌标签、首步字段与是否可开户；发现端点把它们连同注册开关与部署级因素种类一起发布。

**采纳**，见决策。

## 决策

采纳：登录渠道的来源是后端发现端点 `GET B/methods`，它发布每个方法自报的描述符，外加注册开关与部署级可用因素种类。

- `LoginMethod` 增 `Describe() MethodDescriptor`，方法自报其描述符。它是纯常量：不读存储、不读配置，不携带任何一次登录会带的值。
- 描述符的取值域：`kind` 是渲染类别闭集（`form`、`redirect`、`enterprise`、`webauthn`）；`protocol` 是 `redirect` 与 `enterprise` 类方法所讲的线协议（`oauth2`、`oidc`、`saml`）；`label` 是品牌名，缺失时前端按方法名查 i18n 回退；`fields` 是首步字段预览，取自 `Begin` 以空字段调用时所答的首个 prompt，仅 `form` 类给出；`opens_account` 是该法能否在首登为未知标识开户；`binding_providers` 是该方法 link 流程把绑定存下的提供方取值或命名空间前缀（`google`、`github`、`wechat`、`wechat-openid:`、`oidc:`、`saml:`），为空表示绑定落在方法名下。
- 字段知识留在各方法模块，不在引擎层重抄。
- 应答并发布注册开关（由 `authn.account.signup` 派生）与可用因素种类（装配收到的 `MFA.Kinds()`）。前者是部署级闭集开关，后者是部署级可选因素，与账户级 `GET B/factors` 语义不同。
- 企业 SSO 的提供方清单不进此应答，仍走 `POST B/sso/discover`；oidc 与 saml 只作 `enterprise` 类别的方法描述符。
- 该应答的形状升级为对象数组，是破坏性变更：`AuthnLoginMethods.methods` 由 `string[]` 变为对象数组，`auth-core` 的 `listMethods()` 返回类型随之改变。

## 后果

前端只需读发现端点即可渲染部署提供的登录途径，新增或停用一个方法只改后端，前端不动。每个方法模块持有并自报自己的渲染知识，引擎层不重抄字段，方法的描述符与其首步行为由方法自己的测试钉在一起。品牌名不翻译（`Google`、`WeChat`），缺失时回退到按方法名的 i18n。

**接受的代价：**

- `Describe()` 是方法接缝上新增的一个方法，每个方法作者要多实现一个纯常量方法；通行密钥登录方法也在此列。
- 描述符是方法自报的事实，可能与 `Begin` 的实际首步漂移；靠每个方法模块对 `Describe()` 的表驱动断言钉住。
- 发现端点是破坏性升级：返回类型改变，前端迁移随后进行。
- 发现端点新增一类公开只读面：方法集合与其渲染类别对未认证调用者可见。这正是它要发布的信息，不构成账户枚举（它不含账户维度）。

## 失效条件

- 前端仍要按方法名硬编码某些行为，说明描述符的取材不足以覆盖渲染所需，扩描述符而不是回到硬编码。
- 部署出现无邮箱域可 discover 的企业 SSO，或企业 SSO 需要把提供方清单并入发现，则「清单不进发现端点」这一条要重审。
- 方法在 `Begin` 以空字段调用开始产生副作用（写状态、发短信），则「首步字段取自 Begin」不再成立，字段预览需另设来源。
