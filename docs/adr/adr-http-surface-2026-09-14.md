# 入口模块的登记面锚定 gin

## 状态

已接受

## 背景

入口模块交付路由与中间件的登记面。登记面上的类型跨模块流动：业务模块在这里绑定自己的 handler，横切模块在这里贡献自己的中间件，这些类型因而出现在每一个带 API 的模块的接口上。

接口包可以暴露它所封装的第三方库，划界依据是模块与该库的关系——模块封装该库时用它的类型表达接口是正常形态，模块只是碰巧用到该库时那是实现绑定（[ADR-module-packaging-2026-09-14](adr-module-packaging-2026-09-14.md)）。判据不看模块在库之上是否另有装配：数据库模块在 GORM 之上安装各模块声明的插件、收齐迁移集并按依赖序应用，仍是 GORM 的封装（数据库模块的设计文档称它为 GORM 的封装）。

入口模块的功能面分两部分。一部分是装配：多个具名端点、路由与中间件的登记、中间件的跨模块排序、与生命周期各阶段的接驳，这些概念都不出自任何 HTTP 框架。另一部分是请求处理：路由匹配、中间件调度、请求体绑定与校验、响应渲染、panic 恢复，这些由 HTTP 框架提供，而且每个带 API 的模块都要用到。

配置模块选择解析工具的判据是它是否为使用者与维护者所熟悉，不看引入多少依赖（[ADR-config-parsing-2026-09-20](adr-config-parsing-2026-09-20.md)）。

关联字段经 `context.Context` 传递，请求路径上的日志调用从上下文取 logger（[ADR-log-context-2026-09-13](adr-log-context-2026-09-13.md)）。

架构把 HTTP 与 gRPC 并列为入口形态，二者都是模块，都在入口阶段开始监听（[ADR-core-scope-2026-09-13](adr-core-scope-2026-09-13.md)）。

## 考虑过的选项

### 锚定标准库 net/http

登记面用 `net/http` 的 `Handler`、`ResponseWriter` 与 `Request` 表达，中间件写作 `func(http.Handler) http.Handler`；路由引擎由实现子包绑定，请求体解码、校验与响应写出由入口模块另备工具。

**否决**：请求处理的那一半没有交给任何现成的库，由入口模块自造：解码只认 JSON，没有内容协商，没有声明式的校验，没有统一的错误响应，panic 恢复自备。自造部分的覆盖面窄于框架自带的，每个宿主的 handler 要为缺口各自补齐，补法互不一致。它的收益有两样：以 `net/http` 为形状的中间件可直接登记，这一点在锚定框架后靠适配保留；框架依赖不传染给取用入口模块的宿主，这一点的范围只及于取用入口模块的宿主，而这样的宿主本来就要路由与请求处理。

### 保留 net/http 登记面，请求处理的各项分别桥接现成的库

登记面与路由引擎不变；校验、表单与多部分解析、错误响应形状各取一个现成的库桥接。

**否决**：各个库之间没有共同的上下文类型，绑定、校验、渲染要在入口模块里再接一次线，而这一整套正是框架已经接好的。路由器与中间件调度仍是自备的一半，登记面的类型也没有因此得到任何现成生态。

### 锚定 chi

登记面用 chi 的路由与 `func(http.Handler) http.Handler` 中间件表达。

**否决**：chi 的核心只提供路由与中间件，不提供请求体绑定、校验、响应渲染与错误响应，请求处理的缺口原样留在入口模块。它的中间件形状与标准库相同，改锚点几乎不改登记面，等于把路由引擎换成另一个实现，解决不了上面的缺口。

### 锚定 echo

登记面用 echo 的 `HandlerFunc` 与 `MiddlewareFunc` 表达，绑定、校验与集中的错误处理接缝由 echo 提供。

**否决**：判据取使用者与维护者的熟悉程度（同 [ADR-config-parsing-2026-09-20](adr-config-parsing-2026-09-20.md)），熟悉程度以 pkg.go.dev 上引用该模块的包数衡量：gin 约 19 万，echo v4 约 3.2 万、fiber v2 约 3.1 万、chi v5 约 1.7 万，echo v5 约 1600，gin 在候选的 HTTP 框架中居首。echo v5 带有集中的错误处理接缝，v5.4.0 起另有 RFC 9457 的响应形状（`ProblemDetailsHTTPErrorHandler`），gin 两者都没有，选 gin 即由入口模块自备这一块（[ADR-http-errors-2026-10-10](adr-http-errors-2026-10-10.md)）；这笔代价已计入，没有因此改变判据。

### 锚定 fasthttp 系的框架

登记面用 fiber 这类不基于 `net/http` 的框架表达。

**否决**：这类框架不以标准的 `context.Context` 承载请求范围的值，而关联字段的传递正建立在它之上（[ADR-log-context-2026-09-13](adr-log-context-2026-09-13.md)）。追踪标识与租户标识在这样的入口下到不了下游的日志调用。

### 把接口定义推向 protobuf 优先

登记面以 connect-go 这类方案表达，模块的 API 由 protobuf 定义，同一个端点同时服务 gRPC 与 HTTP。

**否决**：这是模块如何定义自己 API 的范式决定，作用范围远大于入口模块，应当单独裁定。它也不构成本记录的替代项——connect-go 本身以 `http.Handler` 收口，采纳本记录不妨碍把它的处理器经 gin 的适配挂进某个端点。

### 锚定 gin

登记面用 gin 的 `gin.HandlerFunc` 表达路由的 handler 与中间件，入口模块是 gin 的封装。

**采纳**，见决策。

## 决策

采纳：登记面用 gin 的类型表达，路由的 handler 与中间件都是 `gin.HandlerFunc`。路由匹配与路由模式的语法、中间件的调度、请求体的绑定与校验、响应的渲染都由 gin 提供，入口模块不在其上另设一层。

入口模块承担装配：具名监听与端点、写入闸门、中间件按功能标识的跨模块排序、请求上下文的建立、排空，以及 gin 不提供的那部分请求处理——默认的错误响应形状（[ADR-http-errors-2026-10-10](adr-http-errors-2026-10-10.md)）与兜底层（[ADR-http-recovery-2026-09-22](adr-http-recovery-2026-09-22.md)）。

路由引擎不是可换的实现选项，入口模块没有实现子包。

## 后果

业务模块与横切模块用 gin 的绑定、校验、渲染写 handler，不经转换；gin 生态的中间件可直接登记。

同一条路由可以带多个 handler，由 gin 按序调用，路由级的处理链不需要入口模块另行提供。

入口模块不提供自造的请求体解码、校验与 JSON 响应工具，也没有路由引擎接缝与实现子包。

**接受的代价：**

- gin 传染给每一个取用入口模块的宿主：宿主的 `go.mod` 与依赖闭包随之带上它，它对 Go 版本的要求成为入口模块的要求。
- gin 的破坏性变更直达接口面：它的一次不兼容升级就是入口模块的一次不兼容升级，无法在实现内部消化（[ADR-module-packaging-2026-09-14](adr-module-packaging-2026-09-14.md)）。
- 登记面的类型绑定 gin 的私有上下文 `*gin.Context`。以 `net/http` 为形状写成的既有中间件与 handler 不能原样登记，要在外面包一层适配。
- gin 不清理请求路径里的空段：`/accounts//contacts/x` 匹配 `/accounts/:id/contacts/:cid`，`:id` 是空串；标准库 `ServeMux` 会先清理路径并重定向。handler 要自己处理为空的路径参数，尤其是把参数直接当作查询条件的写法。
- 路由的路径语法是 gin 的，不是标准库 `ServeMux` 的：参数写 `:name`，通配写 `*name`，按方法分别登记。已匹配的路由在链上经 `c.FullPath()` 可读，按登记的方法与路径判断请求的层与它逐字比对，不自持匹配器；与登记写法逐字不同的条目永不命中，这种写错不产生任何信号。
- gin 不把 `HEAD` 请求派给只登记了 `GET` 的路由，这样的请求得到 405；标准库 `ServeMux` 让 `GET` 的路由同时服务 `HEAD`。用 `HEAD` 探活的调用方要路由登记 `HEAD`。
- 请求体解码按 gin 的绑定器：未知字段被接受，成员名大小写不敏感，同名成员取后者，第一个值之后的内容被忽略，不认识的 `Content-Type` 落到表单绑定。客户端把字段名拼错时，请求看起来成功而该字段没有传进来；入口模块没有工具拦住这类失效形态，需要更严格的 handler 自行设置 gin 的解码选项或另行检查。
- gin 的若干设置是进程级的：运行模式、调试输出、绑定的解码选项与校验器。它们对同一进程里的全部 gin 引擎生效，入口模块只能为整个进程选取一个取值。
- gin 自带的 panic 恢复吞掉 `http.ErrAbortHandler` 并让响应以空的 200 收口，入口模块因而不用它，自备兜底层（[ADR-http-recovery-2026-09-22](adr-http-recovery-2026-09-22.md)）。
- gin 不定义统一的错误响应形状，也没有集中的错误处理接缝，入口模块为此自备默认形状与定制接缝，这一块不是桥接而是自造（[ADR-http-errors-2026-10-10](adr-http-errors-2026-10-10.md)）。
- 某个框架成为事实标准时，登记面不会因此自动跟进；改换锚点是入口模块接口面的一次不兼容变更。

## 失效条件

若 gin 的维护停止，或它的破坏性变更频繁到入口模块的接口面无法保持稳定，则本记录的锚点需要重新裁定。

若业务模块普遍绕过登记面、各自持有自己的 gin 引擎并只把一棵子树挂进来，则登记面没有起到装配作用，本记录的锚点需要重新裁定。
