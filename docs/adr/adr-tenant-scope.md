# 租户解析、租户名册与数据隔离同属一个功能目录，设置与授权另立

## 背景

数据库、日志、配置与入口各模块把租户相关的判定交给“租户模块”，需要有一处裁定承接这些判定的是一个功能目录还是几个。

数据库模块不认识租户，把租户隔离推给"租户模块"，并规定承接方定义自己的模型约定、声明自己的插件（[ADR-db-plugin-scope](adr-db-plugin-scope.md)）。日志模块规定关联字段由产生它的模块在自己的注入点绑定，并把租户标识点名为这样的字段之一（[ADR-log-context](adr-log-context.md)）。配置模块把按租户取值的参数一律判给设置一侧（[ADR-config-scope](adr-config-scope.md)）。入口模块把租户与认证、限流并列为各自模块的事，不为它们内建任何一层（[ADR-http-stages](adr-http-stages.md)）。

中间件的排序把认证立为可被指向的功能，并规定按身份分支的层位于认证之后（[ADR-http-stages](adr-http-stages.md)）。租户解析是以认证为锚点的一层，落在认证之后（[ADR-tenant-ordering](adr-tenant-ordering.md)）。

认定一个请求属于哪个租户，与让每一条语句都带上这个租户，与记住这个租户还在不在，所需的输入不同。解析要的是请求面，隔离要的是每一条语句的拦截点与模型的声明，名册要的是一张表与它上面的状态。功能按包划分，而 Go module 是版本与发布的粒度；把一种能力拆成独立的 Go module 需要举证，成立条件是它有独立的发布节奏，或者消费者会脱离其余功能单独取用它（[ADR-module-layout](adr-module-layout.md)）。

## 考虑过的选项

### 解析、名册与隔离各成一个 Go module

租户的认定、名册的维护与语句的过滤各由一个 Go module 承载，三者之间经跨 Go module 的功能接口取用。

**否决**：升格所需的举证不成立。隔离的输入是"当前租户"，而当前租户只由解析产生；名册的唯一读者是解析与隔离。把其中任何一个升格，都没有独立的发布节奏支撑，也没有一个消费者会脱离其余单独取用它。拆开还多出一种失败形态：隔离可以在一个没有任何解析层的进程里安装成功，声明方拿到的信号与生效时完全一样——插件的安装不看它依赖的东西在不在。

### 隔离并入数据库模块

数据库模块内建按租户过滤，模型带上约定的声明即自动生效。

**否决**（[ADR-db-plugin-scope](adr-db-plugin-scope.md)）：租户标识产生于依赖图上层的模块，数据库模块反向依赖它们会成环；把它下沉到数据库模块自己定义，则每一个需要租户标识而不访问数据库的模块都要为取得一个标识而 import 数据库模块；该选项还替每一个宿主决定了它是多租户的，单租户应用同样要带着这套概念和它施加的模型约定。

### 解析并入认证

租户的认定由 `pkg/authn` 一并交付，身份的认定与租户的认定在同一层里完成。

**否决**：认证的边界判据是判定所需的输入与事实的性质——只需凭据、账户与会话这类认证事实的归它（[ADR-authn-scope](adr-authn-scope.md)）——而租户解析凭据与账户两样都不要，它的输入是请求面。账户全局、可属多个租户，身份因此不带租户（冒充范围除外）：身份的类型字段不导出、只能由判决盖章产生，在它上面加一个租户字段等于要求每一个校验后端回答租户问题。账户与租户的成员关系是认证的账户模块持有的一张表；请求期依据它判定的准入层要同时读身份与租户上下文，而认证的子包不 import `pkg/tenant`，准入层因此放在本功能目录（[ADR-tenant-admission](adr-tenant-admission.md)）。认证的接口包自我约束不依赖 `pkg/db`（[ADR-authn-packaging](adr-authn-packaging.md)），而名册在库里，并进去就把数据库依赖推给每一个只要认证的宿主。豁免路由与无凭据的可选认证路由上没有身份，租户解析却要在这些路由上同样工作。

### 租户与设置、授权同属一个功能目录

租户的认定与名册、按租户取值的参数、按租户的授权判定合在一个功能目录里。

**否决**：与认证模块拒绝与授权合并同源。授权判定要认识资源、动作与策略，设置要一套存储与一条变更通道，合并等于替每个只需要租户的宿主选定它们的约定与输入项。

### 解析、名册与隔离同属一个功能目录，设置与授权另立

**采纳**，见决策。

## 决策

采纳：`pkg/tenant` 交付租户的认定、名册的维护与按租户的语句过滤，请求期的成员判定由本功能目录里的准入层承担；按租户取值的参数归设置模块，按租户的授权判定归授权，两者另立。

**判据是判定所需的输入。** 本功能目录回答"这条请求、这条语句属于哪个租户，这个租户还在不在，以及发出请求的账户是不是这个租户的成员"；回答"这个租户的这个参数取什么值""这个租户能不能做这件事"的归别处。

名册随解析与隔离同属：解析判得出一个名字是否有效、那个租户是否被服务，要读名册；隔离自己不读名册，它依据的是写进上下文的那个标识，而那个标识经过名册才写得进去（[ADR-tenant-isolation](adr-tenant-isolation.md)）。名册不落地的形态下，写进标识的那一步要去问一个由宿主实现的东西，停用的语义就散在各宿主那里。

本功能目录不从设置取任何值：它的每一项输入都在 `Prepare` 中被 `Decode`，而在那一刻数据库尚未可用（[ADR-config-scope](adr-config-scope.md)）。名册不在配置里：配置是启动时的快照，而租户的增删是运行期动作（[ADR-config-lifecycle](adr-config-lifecycle.md)）。

## 后果

数据库模块的“租户模块”、日志模块点名的租户标识产生方、入口模块并列的租户一层，均指 `pkg/tenant`。

只需要请求面租户解析的宿主不存在：本功能目录带着名册，取用它就要落一张表。名册是隔离得以判定停用的前提，也是解析得以判定一个名字有效的依据，两者都离不开它。

设置与授权的演进不改变本功能目录的判定面，本功能目录也不承受它们的约定与输入项。

**接受的代价：**

- 判据落在输入上，而新出现的判定未必一眼看得出落在哪边。一种判定先按租户实现、后来才发现它要读一份策略，改归属就是一次跨功能目录的搬迁。
- **"租户内的用户"与"租户"容易被混为一谈。** 账户全局、可属多个租户；账户与它在租户内的成员关系归认证的账户模块，租户是数据归属的单位，归本功能目录。请求期"这个账户是不是这个租户的成员"的判定由本功能目录的准入层承担，它读认证提供的成员关系，自己不存账户与成员关系。误读的形态是把账户表或成员关系表建进本功能目录。
- 本功能目录同时出现在入口模块与数据库模块之上，它的登记单元因而跨两个接缝。这一条的减轻落在 [ADR-tenant-packaging](adr-tenant-packaging.md)。
- 名册使本功能目录依赖数据库功能，而数据库功能是可选的：一个只要租户认定、不落库的装配取不到本功能目录。

## 失效条件

若出现一种租户判定，它既不读请求面也不作用于语句，而是在进程启动之前就已经确定——例如按部署实例静态绑定的租户——则"解析要请求面"这一前提不再覆盖它，本功能目录的交付面需要重新裁定。
