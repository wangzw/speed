# 重发在同一条邀请上换令牌

## 背景

邀请发出之后，投递可能失败，受邀人可能没收到，链接也可能临近过期。管理员需要一个动作把链接再送一次，而不改变这条邀请本身。接受令牌只以摘要保存，原链接发出后取不回来，所以重发不可能把同一个链接原样再发一遍。

## 考虑过的选项

### 可还原令牌

保存令牌明文或可逆加密的令牌，重发时把原链接再发一遍。采用它意味着任何读到邀请表的人都能兑现任意一条邀请，链接在多次投递之间保持不变。

**否决**：只存摘要是邀请凭据的安全前提；为“同一个链接”把令牌降为可还原，等于把全部的兑现能力交给能读表的人。重发的目的是把一条仍有效的邀请再送一次，不是让链接可被找回。

### 新行取代

重发时以同一地址新建一条邀请，旧行按新签发的取代规则退出。采用它意味着同一地址在多次重发后留下多条历史行，重发与首次签发共用同一路径。

**否决**：重发是重新投递同一条邀请。新建行会改变邀请标识与到期时间，列表与审计把一次投递记成一条新邀请，“已重发几次”也只能靠多行计数得到。历史行与它在审计里的对象因此不再稳定。

### 原行换令牌

在同一条邀请上写一枚新令牌，保留邀请标识、地址与期限。采用它意味着一条邀请的标识稳定，重发只改变令牌、最近发送时间与发送次数，旧令牌在写入时立即失效。

**采纳**，见决策。

## 决策

重发按邀请标识作用在同一条邀请上：条件写要求该行状态仍为待接受且未过期，命中时只写新的 `token_digest`、`last_sent_at`、`send_count + 1` 与 `updated_at`。邀请标识、租户、地址与到期时间不变；旧令牌随即失效，按旧令牌读取答 404。终态不接受重发，已接受、已过期与已撤销都答 409 `invitation-terminal`；邀请标识不指向任何一条邀请答 404。重发与签发共用同一地址的发送预算、通知与令牌交出规则。

## 后果

- 一条邀请只有一个标识，重发不新增行；`send_count` 与 `last_sent_at` 记发送次数与最近发送时间。
- 到期时间不因重发改变；要更长的有效期只能撤销后重新签发。
- 旧令牌在条件写提交时失效，新令牌只在重发应答与通知里出现一次。
- 重发计入发送预算，同一地址的窗口额度不因重发另开一档。

## 失效条件

若邀请必须能在不触达存储的前提下离线重发同一条链接，原行换令牌不成立，届时需要可离线验证或可还原的凭据，并承担相应的密钥或明文存储代价。
