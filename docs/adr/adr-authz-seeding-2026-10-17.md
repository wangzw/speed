# 种入面：独立于 Manager 的 Seeder 能力

## 状态

已接受

## 背景

内置角色对管理面固定：不可删除、不可改写、不可改其授权。这条冻结保护的是运营者的全部权限——删掉或掏空该角色会让管理员被锁在控制台之外，且没有命令能把角色放回去。

宿主同时必须能重复种入自己的策略数据。进程新声明一条权限后，管理员要在下一次 `seed` 时自动拿到它，命令要零错误地跑完。冻结与重跑在这条路径上相遇：经 `Manager` 的写全被 `ErrBuiltinRole` 拒绝，种入于是只有两个坏结局——命令失败退出，或管理员静默地少一条权限。

管理面（`authz.admin` 的 HTTP 路由）与宿主种入是两个信任面：前者由一个持有 `authz.role.manage` 的请求驱动，后者是宿主自己的部署步骤。冻结约束的是前者，不应该约束后者。要把两者分开，写入口的可见性就必须在类型上分开，而不是靠 handler 里「不要调用它」的约定。

## 考虑过的选项

### 在 `Manager` 上新增种入方法

采纳它意味着 `Manager` 增加 `SeedGrants` 一类的方法，种入命令与其它写共用同一个接口。

**否决**：`authz.admin` 取用的正是 `Manager`。管理面的模块声明里没有第二个 token，但同一个接口同时装着管理写与种入写，墙就只存在于 handler 的调用约定里——一个未来的路由或一次重构即可越过，审查也只看得到「它持有 Manager」。这与「管理面不能绕过」这条判据冲突。

### 收窄冻结语义：`PutGrant` 只拒绝删改，允许新增

采纳它意味着 `builtin` 从「整角色冻结」改为「冻结到一批已声明的授权」：角色行需要记录冻结集，`PutGrant` 对已冻结的授权拒绝删改、对新的授权放行。

**否决**：管理面的 `PUT /api/v1/authz/admin/tenants/:tenant/roles/:role/grants/:permission` 走的正是 `PutGrant`。放宽它等于让管理面可以直接给内置角色增补授权，与本决策要守住的第一条判据相反。此外冻结集要落进角色行，表结构与公开记录形状都要改，代价大于收益。

### 让种入绕过 `Manager`：直接写库，或经管理面 HTTP 路由

采纳它意味着 `seed` 自己开事务写 `authz_grants`，或把权限授予伪装成管理面调用。

**否决**：直接写库绕过薄 adapter 的租户核对与行形状，也绕过提交后的快照换指针与 `authz.policy.changed` 发布，本副本在下次重载前会继续按旧策略判定。走管理面则要求 `role.manage`，而管理面本身对内置角色返回 409，等于用被拒绝的路径做种入。

### 独立于 `Manager` 的 `Seeder` 能力

**采纳**，见决策。

## 决策

采纳：种入写入口是独立于 `Manager` 的 `authz.Seeder` 能力，由 `authz.policy` 排他交付，与 `Manager` 并列。`Seeder` 只声明 `SeedGrants(ctx, tenant, role, grants)`：给一个已存在的角色添加它尚未持有的（资源，动作）对，返回本次实际写入的行数。它只增——不删除、不改写、不重写时间戳——且幂等：已持有的授予不写、不报错、不计数。

`authz.admin` 只取用 `Manager`，不取用 `Seeder`，因此 `/api/v1/authz/admin/*` 下的任何写路由在类型上都够不到种入路径。管理面对内置角色的写继续以 `ErrBuiltinRole` 拒绝，映射为 409。

机制在设计文档 [design-authz](../design/modules/design-authz.md) 的「种入面」一节。

## 后果

宿主的重跑与内置角色的冻结不再互斥：声明集未变时种入返回零、不写行、不发事件；进程新增一条权限时，下一次种入把它补进内置角色，管理员自动拿到，命令不再失败。管理面与内置角色之间的墙由模块持有的能力决定，而不是由 handler 的分支约定维持。

**接受的代价：**

- **公开接口面增加一个接口、一个方法和一个输入类型**（`Seeder`、`SeedGrants`、`Grant`）。这是兼容性新增，不破坏既有实现；取用 `Manager` 的宿主不受影响。
- **做种入的宿主必须解析两个能力。** 只取用 `Manager` 的命令写不了内置角色的授权，这是分离的代价，也是分离的意义。
- **`Seeder` 不核对权限目录。** 它接受任何（资源，动作）对，种入面是宿主 Go 代码的信任边界；管理面则先经目录与翻译核对，两者不是同一类调用方。宿主的种入步骤只写入目录翻译出的对。
- **表述要按新的语义读。** 「内置角色不可改授权」的管理面含义不变，但不再是全称：宿主的种入面可以增补。凡把两者混为一谈的文档与注释都要按这条收窄。

## 失效条件

- 若管理面被要求让运营者给内置角色增补授权，独立种入面的墙与本决策同时失效，需要重新裁定写入口的用途约束。
- 若宿主种入需要在写入前核对权限目录或租户名册，`Seeder` 的「不核对目录」这一条与当前签名都要重新评估。
