# 限流交付速率限制，不承载配额

## 状态

已接受

## 背景

本仓多处把限流当作一个独立成模块的链上层来引用：入口模块的中间件设计把它与追踪、认证、租户、恢复并列为各自一个模块，并规定按身份分支的层位于认证之后；租户模块明确不做配额、计费与限流。它的额度归设置一侧，计数原语由键值模块交付。设计结论没有一处定过它到底限制什么。

一个值属于设置还是配置的判据是它是否在数据库可用之前就被需要（[ADR-config-scope-2026-09-13](adr-config-scope-2026-09-13.md)），限流的额度落在设置一侧。它因而按租户取值，并在请求路径上按内存快照读（[ADR-settings-propagation-2026-09-21](adr-settings-propagation-2026-09-21.md)）。

## 考虑过的选项

### 同时承载配额与速率

把一段时间内的总量与单位时间内的频次并入同一个判定。

**否决**：配额要读受约束表里每个租户的数据量，租户模块已把这类动作判为应用自己的领域。两者单位不同，一个以量为界、一个以频次为界，合在一个判定里没有共同的比较基准，调用方拿到的拒绝也分不出是哪一种。

### 只交付配额

**否决**：配额要有一处权威的用量账，而本仓没有这样一个账本。把账建在限流里，等于让它去读它不该读的业务表。

### 交付请求速率限制

**采纳**，见决策。

## 决策

采纳：**模块交付请求速率限制，不承载配额与计费。** 判定回答的问题是一个主体此刻是不是发得太快，不回答它一共发了多少。

## 后果

限流的判定只依赖请求本身、设置里的两个参数与计数后端，不需要读任何业务表。

**接受的代价：**

- 需要总量限制的部署要在应用侧另做一处落点，本模块不承接。
- 计费、套餐这类以量计价的形态建不在本模块上。
- 用量账不由本模块保存，跨窗口的历史用量无处可查。

## 失效条件

若出现一种部署，它要求单位时间内的频次与周期内的总量在同一个判定里一起生效，且两者共用一份用量账，则这条边界需要重新检验。
