# 超限以 429 与 Retry-After 收口

## 背景

入口模块定义默认的错误响应形状，并提供写出入口 `Fail` 供各层写出拒绝，形状可经可选接缝整体替换（[ADR-http-errors](adr-http-errors.md)）。本仓没有任何一处裁过限流超限时对外回什么。

认证模块对 401 与 503 的区分给出过一条对照：以 401 为键的那些设施只认 401，服务暂时不可用是另一个码。限流的拒绝要落在它自己那一个。

## 考虑过的选项

### 只返回错误，状态码由上层映射

**否决**：限流在 handler 之前介入，超限时没有上层可言——请求要么被这一层写出响应并终止，要么交给更内层的层。写不出响应的中间件只能放行，那等于不限。

### 503

**否决**：503 说的是本服务暂时不可用，而超限说的是这个调用方发得太快、服务本身好着。混在同一个码上，按 503 聚合的运维告警会被正常限流打满，而调用方也拿不到等一会儿再来这个正确的提示。

### 429 不带 Retry-After

**否决**：调用方拿不到等多久，只能盲目重试，而重试又撞在同一道闸门上。

### 本层自己写响应体

限流层自拟响应体的内容与媒体类型。

**否决**：同一个 API 的各类拒绝只该有一个形状，限流层自拟形状会让它与认证、租户解析的拒绝各写各的，这正是入口模块定义默认形状要消除的分歧（[ADR-http-errors](adr-http-errors.md)）。

### 429 只带状态码，不带问题类型

拒绝只写状态码与 `Retry-After`，不带 `Problem.Type`。

**否决**：同一个部署里别处也答 429，例如认证模块的退避；客户端按状态分支时无法把限流的超限与那些超限分开，只能按同一种处置。本模块的两层共用同一个判定，写同一个码，客户端因而只需认一个码。

### 429 带 Retry-After，经入口模块的写出入口写出

**采纳**，见决策。

## 决策

采纳：**超限经入口模块的写出入口 `Fail` 写出 429；`Retry-After` 由本层在调用 `Fail` 之前设好，给出当前窗口的剩余秒数，向上取整且不小于一。拒绝的 `Problem.Type` 取 `urn:speed:ratelimit:throttled`，配额层与地址防护层写同一个码；响应体的其余形状由入口模块决定，本层不写。**

## 后果

`Retry-After` 给出当前窗口的剩余秒数，它不指示调用方何时一定能通过。前一窗口的计数按权重仍计入估计值，跨过窗口边界之后那个权重接近一，因而一个在前一窗口打满额度的调用方在那时仍会被拒。这个头的用途是让调用方知道本层的记账周期，退避多久由它按自己的业务判断。

**接受的代价：**

- 响应体的形状不由本模块决定：它是入口模块的默认形状，或交付了 `ErrorResponder` 的模块给出的形状。本模块不能为限流单独定制。
- 拒绝的问题类型是客户端据以分支的对外接口面；改前缀或码要连同每一处按它分支的客户端一起改。
- `Retry-After` 由本副本的时钟与窗口编号算出，多副本下两个副本对同一个调用方给出的秒数可能不同。
- 429 只是对调用方的一条建议，本模块没有任何机制强制它等过那段时间。
