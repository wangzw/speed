# 租户名册的管理面由框架提供一个平台域的模块

## 背景

租户能力带的是接口与实现：名册的写入是它唯一的运维动作，而它不提供配套的 HTTP 管理面。一个想要管理面的宿主得自己写——项目的评估宿主就写了一遍：列租户、开租户、停用、启用、建账户、授成员，同一组路由与同一套判定在宿主里各写一遍。

一个租户管理面要处理的事，都与租户业务无关，却每个宿主都会重复：

- **谁可以问。** 名册是平台资产，不是某个租户的：读取要求平台域的组织读取权限，写入要求平台域的组织管理权限（REQ-tenancy-006）。判定若按请求解析出的租户做，一个在某租户获授权的调用方就能靠一个请求头触到整个名册。租户是一个策略域，跨租户的操作在保留的平台域里持角色（[ADR-authz-model](adr-authz-model.md)）。
- **每次写留痕。** 开租户、改资料、转移所有者、停用与删除是组织生命周期的写，要有一行在动作之前落下、写不进就不做的审计。
- **一个已被持有的标识不能被静默覆盖**（REQ-tenancy-001）。开一个租户与改一个租户是不同的事：登记只插入，改写才覆盖既有行。

这些落在一处还是散在每个宿主里，是本记录要定的。

## 考虑过的选项

### 管理面留给宿主自建

宿主自己写路由，自己做平台域判定，自己写审计前置。

**否决**：同一组路由、同一套判定与同一条审计前置会在每个宿主里重复一遍，重复的每一份都可能判错域或漏掉审计，而这两种错都是安全性质的——判错域让一个租户的授权伸到整个名册，漏掉审计让一次平台写不留痕。把安全性质的判定留给每个宿主各写一遍，正是这份重复要消掉的东西；评估宿主里那份手写实现就是这份重复的证据。

### 把管理面放进租户能力本身

把路由直接挂进 `pkg/tenant`，让租户能力自带一个管理面。

**否决**：`pkg/tenant` 是接口、数据类型与约定，自身不注册模块，且只依赖标准库。路由落在这里，会让它 import `pkg/authz`、`pkg/authn`、`pkg/audit`、`pkg/http`——一整套管理面的依赖闭合——并给这个能力一套与「这条请求属于哪个租户」无关的接口。租户能力的立场不变：它交的是扩展点，不是 HTTP 接口。

### 枚举当作一次跨租户读

把「列出全部租户」做成一次跨租户读，要求跨租户的标记与一条跨租户的权限。

**否决**：名册表不是受租户约束的表，它本就在过滤之外。给它一个跨租户标记是一句不实的陈述——没有租户在被跨越——而它会把租户能力的定序接口拉进管理面的依赖里。枚举是一次平台域的读，不是跨租户读。

### 一个独立的管理面模块，判定落在平台域

新建管理面模块 `tenant.admin`，宿主按需纳入；路由在中间件的声明表里登记为开放，handler 经 `authz.guard` 在平台域判定，每次写强制档审计。

**采纳**，见决策。

## 决策

采纳：**租户名册的管理面由框架提供一个独立的模块 `tenant.admin`，判定落在平台域。**

- **归属。** 管理面是 `tenant.admin` 模块，挂在固定基路径 `/api/v1/system/tenants`，宿主把它写进命令树即挂上，不写即不挂。它不交付任何功能接口，读与资料、状态写各是一次 `tenant.Catalog` 调用，所有者转移与组织删除经 `tenant.OrganizationWriter`；模块自己不持数据、不持规则。租户能力本身的立场不变：它仍不提供管理面。
- **权限与域。** 模块声明它的权限——读 `tenant.read`、写 `tenant.manage`——经 `authz.PermissionSpec` 进进程目录、经 `authz.TranslationSpec` 进进程翻译。判定在保留的平台域 `authz.PlatformDomain` 做出，调用方要持平台域的授予；判定不随请求解析出的租户走。
- **枚举是平台操作。** 列出全部租户读的是名册表，它在过滤之外，所以枚举是一次平台域的读、要平台域的 `tenant.read`，不建跨租户上下文。
- **登记不覆盖。** `POST /tenants` 写 `Create`：一个已被持有的标识以 `tenant.ErrTenantExists` 拒绝，答成 409。开一个租户只插入；此后资料、所有者、状态与删除各有自己的写路径。创建者成为组织所有者与首任租户管理员。
- **别名创建后不可改。** 管理面没有改名路由，`Catalog` 也没有只改别名的写：别名在创建时给定，`Put` 的别名必须与既有别名一致。
- **所有者转移与组织删除由平台管理面提供。** `PUT /tenants/:tenant/owner` 要求平台域的 `tenant.manage`；`DELETE /tenants/:tenant` 接受平台员工或组织所有者，不新增 `tenant.delete` 权限码。两者由 `tenant.OrganizationWriter` 在一条事务里写名册、策略与成员关系；删除写墓碑并清除核心关系。
- **写留痕在动作之前。** 每次写在调名册或组织写之前落一行强制档审计，写不进即 503 且动作不执行。

## 后果

框架有了它的第一个租户运维接口：一个想要名册管理面的宿主纳入 `tenant.admin` 即可，不必重写这组路由、这条判定与这条审计前置。名册的读写语义仍只在名册一处定义，管理面只是它的一个调用方。

**接受的代价：**

- **一个宿主可见的新接口。** 新模块名 `tenant.admin`、新配置键 `tenant.admin.endpoints`（必填、只收具体端名）、新的一组路由、新的权限（`tenant.read`、`tenant.manage`）与新的 `Problem.Type` 前缀 `urn:speed:tenant:`。这些都是宿主可见的接口。
- **管理面把一整套依赖带进租户能力目录的一个叶子。** `tenant.admin` import `pkg/authz`、`pkg/authn`、`pkg/audit`、`pkg/http`，是租户能力目录里唯一这样做的一层。它可撤掉，名册与解析不因它背上这些依赖，但一个纳入它的宿主的依赖闭合里就有了这套东西。
- **权限进入进程目录与权限选择器。** 它们占用（资源，动作）对 `(tenant, read)` 与 `(tenant, manage)`，这两对（资源，动作）因此不能被别的权限复用。
- **宿主断言平台域的授予。** 一个调用方要操作名册，得在平台域持 `tenant.read` 或 `tenant.manage` 的授予；部署要为用户或角色备好这条平台域授予，否则管理面对所有调用方都答 403。
- **组织写的事件是两条权限之外的第二个依赖。** 管理面要求 `tenant.OrganizationWriter`；只用名册管理面而不装配组织写的命令在依赖解析处失败。转移与删除的事务跨越名册、策略与成员关系，宿主因而必须装配这三者的写面。
- **删除的核心关系清理是管理面的动作，不是名册的。** 名册的 `Delete` 仍只写墓碑；不装配管理面的宿主若要删除组织，要自己清成员关系、绑定、角色与授予，或经 `tenant.OrganizationWriter` 调用。

## 失效条件

以下情形出现时，本决策需要重议：

- **若名册增长出一个面向租户自己的自助功能**（一个租户在自己的域内管理自己的东西），则「判定在平台域」不再覆盖它，那是另一条决策。
- **若宿主普遍需要一套与平台域不同的授权结构**（例如把租户读写拆给不同的角色，或按命名空间分权），则权限与平台域判定的结构要重议。
- **若产品重新允许别名修改**，则本记录与 [ADR-tenant-identifier](adr-tenant-identifier.md) 要一起重议：名册要新增一个只改别名的写，管理面要新增改名路由，受约束表里的地址稳定性随之改变。
