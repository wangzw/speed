# 跨模块边界的语言用 BCP 47 字符串，语言匹配库关在实现子包内

## 状态

已接受

## 背景

语言要在多处跨模块传递：经 context 传给下游，作为接口方法与值类型的字段，以及作为模块声明消息目录时的依据。

`golang.org/x/text/language` 提供语言的解析与匹配（`language.Tag`、`MatchStrings`）。它的解析能力要有一处用到，但把它放到接口面上，它的依赖闭包就落到每一个消费方：一个只想读一个语言并把它传给下一层、自己不匹配任何东西的模块，也要承受这个库。

**实测前提：`golang.org/x/text` 已经在 gin 的依赖闭包内。** gin 经 `go-playground/validator/v10` 传递地依赖 `golang.org/x/text`，`gin` 的 `go.mod` 把它列为间接依赖。入口模块的 `pkg/http/deps_test.go` 以「标准库 ∪ 本仓库模块 ∪ `pkg/config` 的当前闭包 ∪ gin 的当前闭包」为预算扫描本模块的包，`x/text/language` 因而已在预算之内，本能力目录引入它不使该预算增长。本能力目录的子包位于 `pkg/i18n/**` 下，不在 `pkg/http/**` 的扫描范围内，也就不参与那次扫描。

## 考虑过的选项

### 接口面、context 与资源声明用 `language.Tag`

`language.Tag` 作为跨模块传递语言的类型。

**否决**：不透明的结构体类型进了接口面，每个消费方与每个 context 携带它，都要 import `x/text`；接口包与 context 存取因而不再只依赖标准库。它也不适合作为资源声明的字段：一份声明是数据，`Tag` 不是可序列化的书面形式。

### 各模块各自 import `x/text`，在边界上各自解析

不引入共享的语言类型，每个需要匹配的模块自己解析。

**否决**：解析与匹配的规则（大小写、下划线对连字符、q 值协商、回退）会在每处重写一遍且各写各的，匹配结果因消费点而异；这正是一条规则需要一处承载、而不是多次复制的情形。

### 边界用 BCP 47 字符串 `i18n.Locale`，匹配库关在实现子包内

跨模块只传字符串，`x/text/language` 只在需要匹配的实现子包（引擎与入口接线）内出现。

**采纳**，见决策。

## 决策

采纳：跨模块边界上的语言是 BCP 47 字符串，类型为 `i18n.Locale`（底层是 `string`）。它穿过 context、接口方法与值类型的字段、以及模块声明消息目录的依据。

`golang.org/x/text/language` 只在需要匹配的实现子包里出现——引擎（收集目录并按请求语言匹配）与入口接线（把请求头落成一个 locale）。`i18n` 根包只依赖标准库，因此一个只读一个 locale 并把语言往下传的模块 import 它时不承受任何第三方库。

`language.Tag` 不进接口、不进 context、不进资源声明。

## 后果

跨模块只传字符串，消费方只依赖标准库与本能力目录的根包；匹配集中在一处，各消费点看到的是同一套结果。

`pkg/http` 的依赖预算不因这条决策增长：本能力目录不 import `pkg/http`，`pkg/http` 也不 import 本能力目录，而 `x/text/language` 已因 gin 落在预算内。

**接受的代价：**

- 字符串本身不校验良构。良构的校验（`ValidLocaleTag`）只在写入点应用，一个拼错的语言在渲染时回退到默认而不是当场报错。
- 匹配行为只在引擎里可见。一个消费方若要自己判断两个语言是否等价，得不到 `x/text` 的等价判断，只能做字面比较或以字符串传下去交给引擎。
- `x/text/language` 进入本仓库直接依赖的 `go.mod`，`go.sum` 随之变动；它在 gin 的闭包内这一事实是被依赖的前提，不是本仓库的承诺。

## 失效条件

本记录依赖「`x/text/language` 在 gin 的闭包内」。若 gin 换掉 `validator` 或 `validator` 去掉对 `x/text` 的依赖，该库便不再因 gin 落在 `pkg/http` 的预算内；此时若 `pkg/http` 仍不 import 本能力目录，预算不受影响，但「本库已在预算内」这条论据本身失效，需要重新核对入口模块的依赖声明。

若某消费方在边界外就能确定需要语言的等价判断（不只是传递），则字符串类型放不住，边界类型要重新考虑。
