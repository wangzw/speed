# 请求侧只产一个时长直方图，属性只取方法与状态码；服务端跨度以方法与路由模板定名

## 状态

已接受

## 背景

`http` 设计文档的「Serve 阶段的组装」一节写明，登记层按排序结果依次交给该端 gin 引擎的 `Use`，每一层作用于该端的全部路由，包括无匹配路由与方法不允许的响应。层在引擎之内、路由匹配之后运行。

已匹配的路由在链上可读：`c.FullPath()` 返回已匹配路由的完整路径写法，与登记方传给 `Endpoint.Route` 的 `path` 相同，没有匹配的路由时为空串。登记面锚定 gin（[ADR-http-surface-2026-09-14](adr-http-surface-2026-09-14.md)），`c.FullPath()` 给出的是路由模板（`/orders/:id`），不是请求的实际路径（`/orders/7`）：模板的取值个数以登记的路由数为上界，不随流量增长。路由属性在这里取得到，要决定的是它进不进直方图的属性面，以及进不进服务端跨度。

属性是闭集还是开放集合，决定它日后改不改得动。含标识的维度一旦被宿主的看板与告警引用，改名与去留都要连带改那些引用；认证把这条代价写在自己的后果一节（[ADR-authn-verdict-2026-09-20](adr-authn-verdict-2026-09-20.md)：「未表态」作为可观测面上的一类计数，名字一旦被看板与告警引用就改不动）。属性表因此是一条决策，不是实现的细节。

租户是另一个候选维度。它的取值与租户一一对应，取值集合随租户数增长。

## 考虑过的选项

### 带上路由属性

采纳它意味着直方图按已匹配的路由切分，请求量、错误率与延迟落到一条具体的 API 上，指标侧不必依赖跨度侧。

**否决**：属性是闭集还是开放集合，决定它日后改不改得动（见背景）。路由属性的取值随宿主登记的路由集合而增长，不由本模块限定；它一旦被看板与告警引用，路由的改名与去留都要连带改那些引用。放宽属性面容易，收回不行，因而本记录取窄的属性面。

### 服务端跨度以方法与路由模板定名，带上路由与端名

采纳它意味着服务端跨度的名称为「方法 路由模板」，属性带 `http.route`；没有匹配的路由时名称只取方法、不带 `http.route`。端名由属性 `speed.endpoint.name` 承载，取值是配置里的端名。

**采纳** — 见决策。「带上路由属性」一项的否决理由针对直方图：维度被看板与告警读过就收不回。跨度的名称与属性不属于直方图的名字、单位、桶边界与属性构成的对外面，那条理由到不了它；跨度一侧要守的是基数不随流量增长，路由模板满足这一条（见背景）。名称的形式照上游语义约定给服务端跨度定的「方法 路由」，没有低基数的路由时只取方法。名称里的方法取折叠后的值，与直方图一致：九种标准方法与上游写法相同，其余方法写作 `_OTHER`，上游约定对它不认识的方法在名称里写作 `HTTP`；上游已列为开发中取值的 `QUERY` 不在九种之内，同样折叠，上游的名称里写作 `QUERY`。没有匹配路由的请求，路径由调用方任意写下，不进名称也不进属性。

### 服务端跨度以端名与方法定名

采纳它意味着跨度名为「端名 方法」，路由不进名称也不进属性。

**否决**：一个端上全部路由的跨度同名，追踪后端按名称索引与聚合时分不出是哪条 API；路由模板的基数不随流量增长，排除它换不来什么。

### 服务端跨度以端名、方法与路由模板定名

采纳它意味着跨度名为「端名 方法 路由模板」，端名同时留在名称里。

**否决**：名称偏离上游语义约定给服务端跨度定的「方法 路由」形式；同一追踪后端里，遵循该约定的其他服务以标准方法产出的服务端跨度是「方法 路由」形式，两种命名在每一条路由上并存，按名称写的查询与告警要分别写。端名作为属性同样可筛选，放进名称不增加可查询的信息。

### 带上租户属性

采纳它意味着请求指标按租户切分，多租户宿主在指标侧直接得到每租户的延迟与错误率。

**否决**：基数与租户数同阶；把它放进请求指标的属性里，等于把一个高基数维度放到最热的信号上。

### 另立一个请求计数器

采纳它意味着请求量由一个计数器承载，直方图只负责时长。

**否决**：直方图自身带计数，请求量从它的计数读出；另立一个计数器会让同一个事实有两个来源，两者在采样与重试上的口径还会不一致。

### 只产一个时长直方图，属性取方法与状态码

采纳它意味着请求侧只有一个计量，属性面收得最窄。

**采纳** — 见决策。

## 决策

采纳：**采集层对每个请求记一次时长直方图，携带的属性只有请求方法与响应状态码；方法取九种标准方法之一，其余一律折叠为一个固定值；不携带路由，不携带租户。服务端跨度以折叠后的方法与路由模板定名，带 `http.route` 与 `speed.endpoint.name`；没有匹配的路由时只以方法定名，不带 `http.route`。**

## 后果

请求侧只产生这一种计量，宿主拿到一张「方法 × 状态码 × 时长」的表，不需要在多个计量之间对齐口径。

**接受的代价：**

- **按路由聚合不在请求指标里。** 本记录选择不纳入这条维度，要按 API 切分的指标看板在本模块的装配下没有依据；按路由的切分只在追踪一侧，由跨度名与 `http.route` 承载。
- **跨度名不含端名。** 换来的是标准方法的跨度名与上游语义约定的服务端跨度形式一致；同一路由模板登记在两个端上时两端的跨度同名，按端区分要读 `speed.endpoint.name`。
- **非标准方法的跨度名与上游不同。** 名称里的方法取折叠值 `_OTHER`，与直方图的方法取值一致；上游约定对它不认识的方法在名称里写作 `HTTP`，对开发中的 `QUERY` 写作 `QUERY`，同一追踪后端里这类跨度两种命名并存，按名称写的查询要分别写。
- **按租户聚合在指标侧同样没有。** 多租户宿主做租户级延迟与错误率时，本模块产出的信号里没有这个维度（[ADR-observability-events-2026-09-22](adr-observability-events-2026-09-22.md)）。
- **非标准方法分不开。** 自定义动词与扩展方法连同真正未知的方法全部落进同一个固定取值，按方法排查时它们在指标上无法彼此区分。

## 失效条件

若在已发布的宿主上，按 API 切分的请求指标是普遍的需要——看板与告警普遍要按路由读请求量、错误率与延迟——则属性面应当放宽到纳入路由属性。
