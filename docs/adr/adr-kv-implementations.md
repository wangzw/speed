# 部署前提由各实现自己声明，不满足即启动失败

## 背景

键值模块有多种实现，它们不同构：

- 内存实现把值放在本进程的映射里。多副本部署下每个副本各持一份，互相看不见对方写了什么，而每一次读写都成功返回。
- Memcached 实现共享一台服务端，多副本可见彼此的值，但服务端不持久化：进程重启、滚动升级、内存压力下的正常淘汰都会让它无声丢光全部数据。
- Redis、PostgreSQL、NATS JetStream（[REF-nats](../references.md)）既跨副本又持久。

旧实现用一组能力位处理这件事：每个实现声明自己满足哪些位（多副本安全、跨重启存活、无状态），装配阶段拿它与宿主声明的部署模式对账，不满足即启动失败，有状态却不持久的打一条横幅警告。

新架构没有部署模式，也没有装配期校验的位置：宿主在命令树上列举模块，模块的判断只能落在自己那份配置上，`core` 不解释任何东西，也认不出哪一种声明该按哪个集合裁断。

## 考虑过的选项

### 引入能力位与装配期校验

**否决**：它需要一个新的装配机制——谁声明要求、谁在哪个阶段校验、对账的取值域是什么——而这套机制的形态与"部署模式"这一概念绑定，新架构里没有它。它还与本仓既有用词冲突：`capability` 在本仓指"功能"，即模块之间相互取用的单位，再拿它指实现的能力位会让同一个词在一份文档里指两种东西。最后，校验的基准本身无处来：没有一处声明过"本次运行是多副本"。

### 不声明前提，只在文档里写明各实现的边界

**否决**：把"内存实现当跨副本共享存储用"这类配置错误全部留给运行期，而它的表现是静默的——两个副本各写各的，每次调用都成功，没有任何一层会报出不一致。这类失败的察觉成本远高于拦住它的成本。

### 每个实现自己在配置面下声明部署前提，不满足时启动失败

**采纳**，见决策。

## 决策

采纳：**每一个实现可以在自己的配置命名空间下声明描述其部署前提的输入项；前提不满足时，启动失败，错误点名缺的是哪一项。**

报故障走的是既有机制：实现在 `Prepare` 中 `Decode` 自己那份配置，读出前提输入项，判断与自己的性质是否相容，不相容即报故障，启动终止。不新增阶段、不新增字段、不新增取值域。

**判断依据由各实现自己给出，没有统一的取值域。** 内存实现关心副本数，Memcached 实现关心数据是否需要跨重启存活，持久实现不需要声明任何前提。设计文档逐个列出前提、默认值，以及前提不满足时错误要点名的输入项。

## 后果

一个把内存实现用在多副本部署下的装配会在启动时失败，错误点名副本数这一项，而不是运行起来后各副本各写各的。

**接受的代价：**

- 前提判断分散在每一个实现里，没有一处能回答"当前装配缺了哪一档保证"。宿主读到的是某个实现自己的错误文本，不是一个统一的对照表。
- 前提是宿主主动声明的。宿主不声明那个输入项时实现按默认值走，默认值取"前提成立"，因此漏声明等于放行。
- 每个实现要自己写一遍判断与措辞，且只能拦到自己。各模块各自声明的前提之间没有一致性保证。
- 前提输入项落在各实现自己的命名空间下，没有统一的键名。同一次部署里要让两个实现都知道"这是多副本部署"，宿主要在各自的命名空间下分别声明。

## 失效条件

若出现一种装配期的事实需要被多个模块共同对账——例如某个横切能力要求参与它的每一个模块都满足同一档保证，而任一模块不满足即无效——则各实现在自己的命名空间下各自判断不再够用，那时需要一处集中的声明与一处集中的校验。
