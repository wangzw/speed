# 启用分两期，运行期的取舍归模块自己

## 背景

一个二进制中被编译进来的模块未必都该在本次运行中跑起来。一个模块能不能运行由两层事实决定：二进制里有没有它——build tag 与 import 决定，是编译期的事实；这次部署有没有把它配置齐——输入项由模块自己解释，是运行期的事实。

判断一个模块能否运行所需的知识分布在模块自己手里：它清楚自己需要哪些输入项、哪些可以缺省、哪些缺了就不能工作。这份知识不在宿主手里，也不在注册表手里；宿主替它重写一遍，就复制了一份会随模块改配置而失配的判断。

运行级纳入是宿主在命令树上写下的意图，但它决定的是"模块进入参与集、有机会表态"，不是"模块一定能运行"。同一份命令树在配置不同的两次部署上装配出不同的功能集，这是运行期启用要表达的正常状态；差别必须能被看见。

## 考虑过的选项

### 由 `core` 读配置并判断哪些模块启用

`core` 读取每个模块的配置，替它决定跑不跑。

**否决**：判断依据是每个模块各自的配置语义，`core` 要为它认识的每个模块重写一遍，每次模块改配置都要同步；`core` 不认识任何配置接口，也不该认识。

### 只在编译期决定

模块被 import 即运行，配置不齐即启动失败。

**否决**：同一二进制里所有部署跑同一组模块，可选功能无法按部署关闭；一个只想用内存实现的部署，因为二进制里同时编进了远程实现，就必须把远程后端配置齐。为每种功能组合出一份 build tag 会让构建矩阵随组合增长，而运行期本就拿得到这份信息。

### 只在运行期决定，配置不齐即启动失败

不引入运行期关闭，凡是模块配置不齐就终止启动。

**否决**：可缺省的配置被当成启动故障，可选功能实际上无法缺席；模块知道自己缺了某项配置能不能照常工作，却被迫一律报错。

### 模块自行关闭，由 `core` 解释原因并判断关闭是否合法

模块表态 `StateDisabled`，`core` 按原因文本或某种分类判断这个关闭是否可信。

**否决**：关闭是否合法取决于模块的配置语义，`core` 没有解释它的知识；按原因文本判断会让一次文案修订改变装配行为。

### 测试控制也编入默认构建

把审查装配的测试控制与回环守卫同能力一起编进每一次构建，靠运行期开关决定它们是否生效。

**否决**：测试控制不是产品能力，部署二进制不应带有为本地走查开的控制路由；它们能否被调用取决于部署的信任边界，而不是配置。默认构建因此不含它们，`review` 构建标签只增加这一部分，不改变能力名册。

### 编译期定上限，运行期由模块表态，`core` 只传播事实

**采纳**，见决策。

## 决策

采纳：**启用分两期。** 编译期决定二进制里有哪些模块，是本次运行的功能上限；运行期由模块在 `Prepare` 中依据自己的配置决定是否正常运行。`core` 只提供机制，不做判断。

**编译期是功能上限。** 未被 import 的模块不在可用集里，运行期没有任何途径能让它启用；build tag 与 import 决定这个二进制能装配哪些功能。全部产品能力默认编入每一次构建，不为功能取舍增设构建变体；唯一的例外是审查装配的测试控制与回环守卫，它们只在 `review` 标签下编译，因为部署二进制不应带有测试用的控制路由。这个例外只增删测试控制，不改变能力名册。

**运行期由模块表态。** 参与集的模块在 `Prepare` 中返回三态之一：`StateAuto` 与 `StateEnabled` 表达它在排他交付上如何与他人相让，`StateDisabled` 表达它本次不运行并给出原因。模块对自身配置的取舍落在后两种结局的选择上：

- 缺的是可以缺席的项，模块照常工作的其余部分仍应生效，它表态 `StateDisabled` 并给出原因；
- 缺的是不可缺省的项，模块无法运行，它从 `Prepare` 返回错误，启动终止。

两种结局在机制上分开：关闭是一次预期的缺席，随启动诊断报告；错误是一次启动故障，终止驱动并回滚。某项配置属于哪一类由模块自己判断，`core` 只按模块给出的返回值处置。

**`core` 只传播事实。** 一个模块以什么原因关闭，`core` 原样记入启用结果、写进启动诊断，并在依赖方失败时原样转述。`core` 不解释原因，不区分"预期内的缺席"与"意外"，也不根据原因文本做任何决定。关闭必须给出原因，因为原因正是诊断与依赖方失败要转述的那件事。

**被关闭的模块从启用集移除。** 它不构造，不执行其后的任何阶段，它声明的功能不在本次运行交付，它的排他主张也进入不了消解。

**依赖一个被关闭模块的模块失败并点名它。** 构造期依赖解析在任何模块构造之前完成；必需功能的提供者在启用集里零个即 `ErrMissingProvider`，错误文本点名该提供者、它被关闭的原因，以及是哪个模块在要求它。依赖方不能运行，这个失败是错误，不是又一次预期的缺席。

**关闭一个模块不影响其它不依赖它的模块。** 启用集是参与集减去被关闭的模块，剩余模块照常构造、接线与启动，直到某个模块的 `Requires` 落空。

## 后果

同一二进制可以在不同部署上装配出不同的功能集。可选功能未配置时启动成功，缺席由启动诊断与启用结果查询报告，原因由模块自己给出。

模块不再被迫把可缺席的配置当成启动故障，也不必由宿主在命令树上替它表达"这次要不要它"。

**接受的代价：**

- 一次成功的启动不再意味着参与集的每个模块都在运行。要保证某个模块必须运行，得让它在缺配置时返回错误，或在部署上保证它的配置齐备；机制不提供"这个模块必须启用"的额外声明。
- 功能集随配置漂移，差别只在启动诊断与启用结果查询里可见。漏读诊断的部署与功能齐全的部署在退出码上无从分辨；诊断与查询因而是发现途径，不是可有可无的附带输出。
- 关闭一个提供者可能让某个功能在启用集里失去全部提供者，依赖它的模块随之启动失败。关闭的代价落在依赖方，而不是静默留下一个残缺的装配。
- 一个模块的关闭原因只对写它的人和读诊断的人有意义：`core` 不解读它，所有按状态判断的代码只能看 `StateDisabled`，不能比对原因文本。
- 编译期上限不可越过：部署无法运行一个没有被 import 的模块，即便配置齐备。

## 失效条件

若可选功能的缺席频繁发生而诊断无人读取，功能集的实际形态与宿主的预期长期不一致，则需要在模块描述符上增加一份显式的"必须启用"声明，让机制而不是诊断承担这项保证。

若一个模块的缺席普遍会拖住依赖它的模块，而这类依赖链足以覆盖大部分装配，则运行期关闭带来的"可选功能可以缺席"在实践中收益有限，取舍要回到宿主在命令树上精确列举模块的方式。
