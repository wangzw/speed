# 被纳入的模块必须启动，不能启动即故障

## 背景

一个二进制中被 import 进来的模块未必都该在本次运行中跑起来：连接信息没有配置的后端跑不起来，同一功能的多个实现之间只能有一个生效。决定一个模块能否运行所需的知识分布在模块自己手里——它清楚自己需要哪些配置、齐备到什么程度，这份知识不在宿主手里，也不在注册表手里。

运行级纳入是宿主在命令树上写下的意图。只被静态级纳入的模块不构造、不表态，它的缺席可以从命令树上读出；运行级纳入的模块不同，写下一个名字就是这条命令要它运行。

一条退让的通路使这条意图失去约束力：模块在 `Prepare` 中表态禁用并给出原因，即退出本次运行，启动照常成功。同一份命令树于是在配置不同的两次部署上装配出不同的功能集，两次的退出码都是零，差别只在启动诊断的几行。

依赖缺失与排他冲突表现为启动失败（[ADR-dependency-resolution](adr-dependency-resolution.md)）；配置缺失却留下一档退让，同一类"装不起来"在两处的处置不同。

资源声明的取材域把"表态禁用"读作本次装配给出的否定（[ADR-module-resource-scope](adr-module-resource-scope.md)）；那条减法成立的前提，正是退让是模块可以合法作出的动作。

## 考虑过的选项

### 保留表态禁用，只加强它的可观测性

表态禁用仍是合法结局，要求给出原因，并保证它进启动诊断。

**否决**：诊断是事后察觉，不是启动期的判定。启动本身仍然成功，命令树上写下的纳入仍然不是保证；一次漏看诊断的部署与一次成功的装配在退出码上无从分辨。加强可观测性改善的是排查成本，不是那份缺席本身。

### 由宿主判断启用

宿主读取配置，自行判断哪些模块跑得起来，只把那些模块纳入命令树。

**否决**：判断依据是每个模块各自的配置语义，宿主要为它使用的每个模块重写一遍这套判断；而"依据配置决定它能否运行"正是模块自己掌握的知识，搬到宿主头上等于把它复制一份，并随模块改配置而失配。

### 模块报告自己起不来，注册表记录并跳过它

模块在 `Prepare` 中报告自己起不来，注册表记录它并让它退出本次运行，启动继续。

**否决**：被跳过的模块仍然不进启用集，功能仍然缺席，只是换了一条记录路径。这与退让是同一件事——把缺席的原因从模块的表态换成模块的错误，装配出的功能集仍随配置漂移。

### 被运行级纳入的模块必须启动

模块不能启动时——配置缺失、依赖不满足、部署前提不具备——`Prepare` 报故障，启动终止。

**采纳**，见决策。

## 决策

采纳：**被运行级纳入的模块必须启动。** 它不能启动时，`Prepare` 报故障，启动终止；那是一次必须在部署上解决的失败，不是一个可以被启动吸收的运行期选择。「表态禁用」不是一档合法的表态。

`Prepare` 的表态取值域因此只剩 `StateAuto` 与 `StateEnabled` 两项，两者只表达模块与他人的排他主张如何相让，不表达跑不跑。`StateDisabled` 不是模块可作的表态，它只由注册表在消解中给出，以及启用结果查询对不在参与集里的模块给出。

**运行级纳入的含义是「必须启动」。** 宿主写下一个名字，就是承诺这个进程装配它；经依赖闭包拉进参与集的模块同样必须启动，因而一个未被配置的依赖不因提供者自己会让开而被消化。

**声明因此减无可减。** 被纳入的模块一律进入启用集，它的每一份声明都在本次运行生效；不是不做减法，而是不存在「退让」这一档可以减法。

**排他交付的消解不因本记录改变。** 消解仍只针对排他交付，传播与裁决两步照旧；多个排他提供者留到裁决时选择失败，而非任选其一或全部禁用——任选会让启动结果不确定，全部禁用把失败推迟到某个依赖它的模块。

## 后果

一个被运行级纳入的模块要么真的运行，要么启动失败。"启动起来了却缺一部分功能"没有一条由模块自己打开的静默通路，可退的只有排他消解裁决出的那几个，而它们随启动诊断输出。

命令树成为装配结果的可靠来源：装配成功即本次运行启用了它运行级纳入的每一个模块，例外只有消解退让的那几个；命令树之外进入装配的，只有预置了实例的模块；预置只由宿主与测试在驱动之前发起，这一点靠评审维持，机制拦不住（[ADR-supplied-instance](adr-supplied-instance.md)）。

配置缺失在启动时即暴露，早于任何构造；预置了实例的模块除外，它的 `Prepare` 不执行（[ADR-supplied-instance](adr-supplied-instance.md)）。

**接受的代价：**

- 部署前提不具备的模块不能被跳过。只想用内存实现而不配置远程后端的进程，在命令树上只点名内存实现即可——远程实现排他交付该功能，依赖闭包不为它自动纳入提供者，未点名、也没有预置实例就不进参与集，其前提无须配齐（[ADR-dependency-resolution](adr-dependency-resolution.md)）；而被点名的模块必须配齐前提，配不齐即启动失败。非排他功能的提供者经依赖闭包照常纳入参与集，未点名也无处回避，要么配齐它的前提，要么改依赖，要么为它预置实例——预置时它的 `Prepare` 不执行。「不把远程实现写进命令树」的回避只对写命令树的调用方成立：不写命令树的调用方经 `Run` 纳入全部已登记模块，登记即纳入，排除不掉其中任何一个（[ADR-drive-entry](adr-drive-entry.md)）。
- 一个功能的两份实现各自带着"配置齐备才跑"的判断时，这份判断不能表达成退让，取舍必须由宿主作出：在命令树上点名其一，或为其一预置实例。
- 模块没有自行关闭的余地："这次不跑它"只有一条途径——不纳入它，也不为它预置实例（[ADR-supplied-instance](adr-supplied-instance.md)）。「不纳入它」只对写命令树的调用方构成途径：不写命令树的调用方经 `Run` 纳入全部已登记模块，没有把某个已登记模块排除在外的动作（[ADR-drive-entry](adr-drive-entry.md)）。
- 互斥实现之间的取舍回到宿主手里。一个二进制可以同时 import 多个实现，那是编译期的常态；未被点名的提供者不进参与集（[ADR-dependency-resolution](adr-dependency-resolution.md)），宿主为它预置了实例的除外；运行时生效的是命令树点名的那一个，或宿主为其预置了实例的那一个，点名的实现与预置了实例的实现并存时按消解的普通规则处置（[ADR-supplied-instance](adr-supplied-instance.md)）。模块没有读出配置后自行退让这一档，取舍因而由宿主的点名与预置承担，而不是由模块自己让位：这不留下一处静默通路，代价是宿主必须知道自己用的是哪个实现。
- 配置缺失与配置错误不可分辨：两者同形，都是启动失败，诊断要从错误文本里区分。
- 退让的唯一来源是排他消解，而它不读配置、只看提供者是否显式启用。同一功能的两份实现若要在同时在场时择一，让位的那一方必须声明排他。

## 失效条件

若实践中大量模块的 `Prepare` 退化为"配置齐全则启用、否则报错"，而这份判断在模块之间重复且口径不一，则判断该由一份声明式的必填项清单承载，而不是每个模块各写一遍。

若一个模块的部署前提无法在启动时判定、只能在运行期发现，则"装不起来即故障"对它不成立，它需要一条启动之后的表达途径。
