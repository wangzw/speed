# 模块自己在交付库上发出的语句经本模块取连接，取连接与等锁都有界

## 状态

已接受

## 背景

本模块交付的句柄底下是 database/sql 的连接池。一条语句执行之前可能先等池里的一条连接，再等别的连接占着的锁。等连接由语句的上下文界定，没有期限就一直等。

只属于单条连接的库（SQLite 的内存库与临时库）上，本模块只开一条连接，永不替换：池里每条连接打开的会是各自的库。调用方在交付句柄上开着事务、或迭代着一个结果集时，那条连接由它占着；池大于一条时，每条连接都被这样占着，处境相同。

这时发出语句的不只有调用方自己，还有替它做事的模块：写自己那一行的插件，在发布方的协程里同步执行的订阅方，经交付句柄读表作答的调用。它们在调用方的事务里被调到，去池里取连接，等的是调用方，而调用方在等它们返回：等到上下文到期，没有期限就永远等下去。Go 不给出协程的身份，这种占用从语句所在的会话上与别的调用方的短暂占用分不开。

等锁那一段两个引擎不同。SQLite 在驱动里等锁，按连接上的忙等时限反复重试，驱动给每条连接设 5 秒，定位符里的 `_pragma=busy_timeout(n)` 可以改；上下文结束时驱动发出的中断到不了这段重试。上下文 300 毫秒到期的一条写入，在另一条连接占着写锁时仍等满 5 秒才以 `SQLITE_BUSY` 失败，定位符设 2 秒时等满 2 秒。PostgreSQL 的等锁随上下文结束，会话级的 `lock_timeout` 另给一个界。两个引擎都按一条语句开始时连接上的设置给它设界，PostgreSQL 上是那条语句等的每一把锁各按那个设置。

SQLite 的共享缓存模式（`file:` URI 带 `cache=shared`）另成一格：同一个缓存里一条连接写着的时候，另一条连接要读写它的表，驱动经 `sqlite3_unlock_notify` 一直等到写的那条连接的事务结束，不看忙等时限，也不随上下文结束：另一条连接的事务写着一张表、3 秒后提交时，读这张表的语句即便上下文 500 毫秒到期、忙等时限设为 300 毫秒，也要等满这 3 秒。本模块照常交付这种定位符，给它开配置的连接池。

给这两段等待设界，要的知识一半是 database/sql 的，一半是方言的。方言的那一半按本模块的边界落在实现子包里，其上的模块只拿得到句柄与 `Dialect`。

## 考虑过的选项

### 只写明这些事实，由各模块自己设界

**否决**：取连接那一段各模块照 database/sql 写得出，等锁那一段写不出——在 SQLite 上从上下文设不上界，要按方言分支、在取到的连接上改写忙等时限并在交还前放回，本模块之上的每个模块各写一遍方言代码。只按上下文设界的模块在 SQLite 上等锁仍等满忙等时限，自己看不出来；两个引擎上的界随各模块的写法各自漂移。

### 在只开一条连接的句柄上，由本模块给每一条语句的取连接设界

包装句柄的连接池，每条语句先在界内取连接，再在它上面执行。

**否决**：它改变这类句柄上的每一条语句，另一条语句正常的长时间占用也会让排在后面的语句失败，而那种排队原本是这种句柄的正常形态。GORM 自己的 `Connection` 与预编译语句的路径直接取底下的池，绕过包装。池大于一条而被占满的句柄、以及等锁那一段，都不在它的范围里。

### 内存库改用共享缓存，让连接池开多条连接

**否决**：共享缓存按表加锁，一个写着某张表的事务让并发读写它的连接一直等到它提交，忙等时限与上下文都结束不了这段等待；替调用方发出的语句在调用方的事务之外取了另一条连接，就永远等下去，这正是要消除的等待，只是换成了等锁。临时库无法共享。

### 让上下文结束 SQLite 的等锁

**否决**：驱动不交出挂接忙等回调的途径，它在上下文结束时发出的中断到不了忙等的重试，也到不了共享缓存里对 `sqlite3_unlock_notify` 的等待，要做到只能分叉驱动。

### 作为 `Database` 的方法

**否决**：插件在回调里拿到的只有会话，`OpenedFrom` 交回的也是句柄，拿不到 `Database`；接口多一个方法，会打破它在仓库内外的每一个实现与测试替身。

### 等锁的界在取到连接时设一次

**否决**：引擎按一条语句开始时的设置给它设界，只设一次，`fn` 的每一条语句都各等满剩下的时间：一个读失败之后再读一次以说明原因的调用，等锁的时长是界的两倍、三倍，调用方的期限也拦不住它。

### 共享缓存的定位符照常交付，写明其上的等待没有界

**否决**：那里没有任何一方收得住这段等待——本模块设不上界，其上的模块也设不上，调用方给的期限同样不起作用；写明它只是把一次整个进程无声卡住的故障交给宿主自己去撞。

### 共享缓存的定位符只开一条连接

与只属于单条连接的库同样处置，交付的池内不再有第二条连接，等表锁变成等连接，`Connection` 管得住。

**否决**：同一个缓存照样够得着——`Open` 以同一个名字自建的连接、同一进程里另一次装配、宿主自己开的池都在那个缓存里，它们与交付的那条连接之间的等锁仍旧没有界。收成一条连接之后，它提供的也只剩 `:memory:` 已经提供的东西。

### 本模块提供包级的 `Connection`，方言的设界经 `Spec` 给出，等锁的界在每条语句之前按剩下的时间重设，SQLite 实现拒绝共享缓存的定位符

**采纳**，见决策。

## 决策

采纳：本模块提供包级函数 `Connection(ctx, handle, wait, fn)`。它在 `wait` 之内从句柄背后的池里取一条连接，把这条连接上等锁的时限设为取到时 `wait` 剩下的时间，在钉住这条连接的会话上运行 `fn`；`fn` 此后的每一条语句——事务的开启与提交也算——开始之前，只要又过去了整一毫秒，就按那时剩下的时间重设，剩下的时间向上取整到毫秒。`fn` 返回后把等锁的设置放回取到时的原值再交还连接，放不回就关掉这条连接。取不到连接时返回的错误包着 `context.DeadlineExceeded`。

在一条连接上限定等锁时长的办法由实现子包经 `Spec.BoundLockWait` 给出，这一项必填：SQLite 用连接的忙等时限，PostgreSQL 用会话的 `lock_timeout`。本模块打开的每个句柄都在插件表里带着它背后的池与这项办法，由它派生的每个会话都找得到。

SQLite 实现不打开把连接放进共享缓存模式的定位符，交付的与 `Open` 自建的都一样：它的 `Dialector` 认出这种定位符，初始化即失败。认法照驱动交给 SQLite 的样子、照 SQLite 解析 URI 的方式：`#` 结束 URI，`%HH` 先解码，转义出的 NUL 截断它所在的部分，名字为空的参数连同取值跳过，同名参数取最后一个。

模块自己在交付库上发出、可能在调用方的事务里被调到的语句，经 `Connection` 取连接。

## 后果

两个引擎上界的含义相同：取连接与 `fn` 的全部等锁合计不超过 `wait`，界到了语句失败而不是一直等；本模块交付的每一种库上都是如此，界管不住的形态不交付。界截断的一次等锁不早于调用开始之后 `wait` 结束，调用方由此认得出失败是不是界到了。方言知识留在实现子包里，其上的模块不再按方言分支。插件只拿着一个会话也调得到它。

**接受的代价：**

- 界是失败而不是答案。界到了那条语句失败，要让它成功，得先由调用方放开它占着的连接：提交事务、关掉结果集。只开一条连接的库上、调用方的事务里，这样一条语句等满 `wait` 才失败，这段时间里调用方的事务与那条连接都被占着；一次本可以据表作答的调用得到的是一个既不是答案、也不是拒绝的失败。
- 等锁到界时报的是引擎自己的错误，SQLite 的 `SQLITE_BUSY`、PostgreSQL 的 `lock_not_available`，本模块不给它分类。它与界无关的同类失败——SQLite 为避开死锁立即报的 `SQLITE_BUSY`，PostgreSQL 的 `NOWAIT`——从错误上分不开，只能看它来得早晚。
- 界只约束经 `Connection` 发出的语句。宿主直接在外层句柄上发的语句照旧等到上下文结束，只开一条连接的库上事务里的语句要走事务句柄，这一条不变。
- 每取一次连接多出读、设、放回等锁设置的几条语句；`fn` 的一条语句开始时离上一次设界又过了一毫秒以上，它之前再多读、设两条。在 PostgreSQL 上各是一次往返。
- `fn` 返回时要已经关掉它的结果集、结束它的事务；还开着的结果集让交还那一步等它关闭。`fn` 的会话钉在一个包装了那条连接的连接池上，`Statement.ConnPool` 不是 `*sql.Conn`。
- `Spec` 多了一个必填字段，仓库之外实现方言的代码要补上它；它在一次 `Connection` 里被调用不止一次，事务开着时也会。
- SQLite 的共享缓存定位符不再可用，交付与 `Open` 都以 `ErrConnectFailed` 失败。只属于进程自己的内存库改写 `:memory:`，多条连接共用的库改用文件。

## 失效条件

若驱动交出了随上下文结束 SQLite 等锁的途径，等锁那一段可以改由上下文界定，`Spec.BoundLockWait` 随之可以去掉。

若驱动对共享缓存表锁的等待也受忙等时限或上下文约束，拒绝共享缓存的定位符可以撤回。
