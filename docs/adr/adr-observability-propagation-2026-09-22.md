# 传播器单点定义，入站提取在采集层、出站注入由调用点选用的工具承载

## 状态

已接受

## 背景

跨进程的链路要在两侧都做：服务端不提取父上下文，调用方的跨度就接不上；客户端不注入，下游就看不到这条链路。

上游库的默认复合传播器是空的：进程的默认传递器是一个零委托的复合传播器（`propagation.NewCompositeTextMapPropagator`，`go.opentelemetry.io/otel/internal/global` 的 noop 委托），注入与提取都静默空转，不报错。

`pkg/http` 只有入站侧：它组装每个端点的链（`http.Endpoint.Use` 逐端登记中间件），没有出站客户端的概念；出站请求由各调用点自己构造。

`ADR-log-context-2026-09-13` 确立了关联字段由产生它的模块绑定、经上下文传递的形态：产生字段的模块在自己的注入点绑定，下游从上下文取用，根包不认识任何字段（[ADR-log-context-2026-09-13](adr-log-context-2026-09-13.md)）。跨度上下文属同一形态，本记录定的是它的构造位置，以及两侧各由谁承载。

## 考虑过的选项

### 只做入站提取，出站交给调用点自己写

**否决**：每个调用点都要自己取出跨度、自己拼头部，写错一个字段名不报错、只是链路断掉；把这件重复的事收进一个包装，是把「漏一条就失效」的能力从调用点拿回来。

### 包装进程默认的传输，让所有出站自动注入

**否决**：那是一个包级全局，改动它影响进程内每一处 HTTP 调用，包括不属于本应用的客户端；且它被改写之后没有任何一层能察觉。

### 要求入口模块或数据库模块提供出站接缝

**否决**：把依赖推到别的模块身上，而它们都不持有出站客户端的构造点；本模块的两个工具只用标准库与上游 API，不需要任何模块配合。

### 传播器在追踪上下文之外一并承载 baggage

采纳它意味着传播器是追踪上下文与 baggage 的复合，入站的 baggage 随父跨度一起提取进请求上下文，出站时随追踪头部一起注入。

**否决**：采集层的提取发生在认证之前，入站的 baggage 是任何调用方都能写下的内容；提取之后它留在请求上下文里，传输包装再以本服务的身份把它转发给这次请求调用的每一个第三方。接续一条追踪只需要跨度上下文，baggage 换来的是一条把不受信的输入带过信任边界的通道。

### 传播器定义在接口包，入站提取在采集层、出站注入由调用点选用的工具承载

**采纳**，见决策。

## 决策

采纳：传播器由接口包构造一次并作为本模块自己的值使用（`observability.Propagator`），不写上游的全局传递器，它只承载 W3C 追踪上下文，不承载 baggage；入站侧的父跨度提取落在采集层，出站侧的注入由接口包给出的一个传输包装承载（`observability.Transport`），且不自动接管任何客户端——套上与否由调用点选择。

## 后果

出站注入这件「每个调用点各写一份、漏一处静默失效」的事收在一处，调用点只决定要不要套上这个包装。

**接受的代价：**

- **注入靠调用点自觉。** 出站注入不自动接管任何客户端，漏掉一处包装，该客户端发出的请求就不带传播头部，链路从客户端一侧断开；套没套、套在哪个客户端上，任何一层都不校验，断开也不产生失败信号。
- **进程之间的业务上下文不经本模块传递。** baggage 在两个方向上都不被读写：上游服务写下的 baggage 到本进程为止，本进程调用的下游也收不到它。需要跨进程携带业务上下文的宿主，自己选择载体，也自己决定信任谁写的内容。
- **传播格式不是配置项。** 需要另一种上游传播格式的部署，在配置面上没有可写的地方：格式的选择落在本模块的实现里，改动它要改这个接口包。
- **本模块不接管上游的全局传递器，进程内直接使用上游全局 API 的代码不被覆盖。** 这类代码的注入与提取沿用上游的空复合传播器，与本模块的采集层、传输包装并存于同一进程时，两条取向不同且都不报错。
