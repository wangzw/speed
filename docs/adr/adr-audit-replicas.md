# 事件级审计行按事件标识去重，由表上的唯一约束裁定

## 背景

多副本部署里每个副本各跑一份审计实现，写的是同一个库里的同一张审计表。语句级、请求级与接口级的事实只发生在一个副本上，各留一行；事件级不同。总线不承诺投递次数（[ADR-event-delivery](adr-event-delivery.md)）：经传输投递的实现把每个事件广播给每个副本的订阅，后端还可能重投一个未被确认的条目。每个副本的订阅各写一行，一个领域事实在表里留下副本数那么多行，读表方分不出这是几件事。

事件携带一个标识，它在每个副本、每种实现、每次重投上都是同一个值，是效果不止于本副本的订阅方去重的键（[ADR-event-identity](adr-event-identity.md)）。审计的事件级订阅正是这样的订阅方：它的效果落在共享的库里。

## 考虑过的选项

### 各副本共用一个消费者名或消费组，让一个事件只投给其中一个副本

**否决**：消费者名与消费组是总线实例的设置，作用于这个实例上的每一个订阅者，不只是审计。设置模块靠广播让每个副本重载快照（[ADR-settings-propagation](adr-settings-propagation.md)），改成负载均衡之后，没收到那条事件的副本继续用旧值，直到下一次周期刷新。进程内总线也没有这个设置。

### 读表时去重

**否决**：行上没有能认出同一事件的东西，两个内容相同的事件与一个事件投了两次在表上无法区分；而且每个读表方都要各做一遍，漏做的那一方拿到的行数是错的。

### 写入之前先查这个标识在不在

**否决**：两个副本同时查，都查不到，各写一行；查与写之间没有原子性，重复只是从必然变成了偶发。

### 只让一个副本订阅

**否决**：要在副本之间选出一个，而本模块没有、也不为此引入副本间的协调；那个副本不可用的时间里事件行全部丢失，失败还不进任何一个副本的失败信号。

### 行带事件标识，标识列唯一，插入遇到已有的标识什么也不做

**采纳**，见决策。

## 决策

采纳：**事件级审计行带上事件的标识，审计表对这一列有唯一约束，插入遇到已有的标识什么也不做。** 先到的那次投递写下这一行；其余投递照常成功，不写行，也不进失败信号：事实已经在表里，那正是它们要写的。

**标识为空的事件不去重**，每次投递各留一行，行上不带标识。总线在发布时补上标识，只有不补的实现会走到这一格；把空值当作一个标识，会把所有不带标识的事件并成第一条。

其余三条通路的行不带事件标识，不受这条约束影响。

## 后果

一个事件在表里恰好留一行，不论副本数与重投次数；行上的标识也让读表方把一行对回它记的那条事件。

**接受的代价：**

- **审计表多一个唯一索引。** 每次写入都要维护它，在没有事件级行的部署里也一样。
- **留下的是先到的那次投递。** 行上的时间是那一次的受理时间，其余投递什么痕迹都不留。
- **去重的正确性依赖事件标识的承诺。** 发布方用同一个标识发出的两个不同事实，后一个不留行：对订阅方而言两个标识相同的事件就是同一个事件。
- **滚动发布期间不去重。** 还在旧版本上的副本写的事件行不带标识，与新版本写下的那一行各自留存。
- **已部署的表经一条新增的迁移改造。** 加列之后建唯一索引，PostgreSQL 建索引期间阻塞对这张表的写入，语句级捕获的每一条模型写语句随之等待；表越大等得越久。迁移在事务里执行，不能改用不阻塞写入的建法。

## 失效条件

若事件总线不再保证同一个事件在每个副本、每次重投上带同一个标识，按标识去重即失效，要重新裁定。
