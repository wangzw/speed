# 模块自己发出的语句经本模块在有界的等待内取连接，SQLite 的事务在开启时就等写锁

## 背景

本模块交付的句柄底下是 database/sql 的连接池。一条语句执行之前可能先等池里的一条连接，再等别的连接占着的锁。等连接由语句的上下文界定，没有期限就一直等。

只属于单条连接的库（SQLite 的内存库与临时库）上，本模块只开一条连接，永不替换：池里每条连接打开的会是各自的库。调用方在交付句柄上开着事务、或迭代着一个结果集时，那条连接由它占着；池大于一条时，每条连接都被这样占着，处境相同。

这时发出语句的不只有调用方自己，还有替它做事的模块：写自己那一行的插件，在发布方的协程里同步执行的订阅方，经交付句柄读表作答的调用。它们在调用方的事务里被调到，去池里取连接，等的是调用方，而调用方在等它们返回：等到上下文到期，没有期限就永远等下去。Go 不给出协程的身份，这种占用从语句所在的会话上与别的调用方的短暂占用分不开。

等锁那一段两个引擎不同，界都来自连接上的设置，而设置来自定位符或服务端。SQLite 在驱动里等锁，按连接上的忙等时限反复重试，驱动给每条连接设 5 秒，定位符里的 `_pragma=busy_timeout(n)` 可以改；上下文结束时驱动发出的中断到不了这段重试。上下文 300 毫秒到期的一条写入，在另一条连接占着写锁时仍等满 5 秒才以 `SQLITE_BUSY` 失败，定位符设 2 秒时等满 2 秒。忙等时限按一条语句计：一条语句先等写者的锁、提交时再等读者的锁，合起来仍在一个忙等时限之内。PostgreSQL 的等锁随上下文结束；会话的 `lock_timeout` 按一条语句等的每一把锁各计一次，一条先后等几把锁的语句可以等到它的几倍；`statement_timeout` 给整条语句一个界。服务端默认两者都不设。

SQLite 的事务照它自己的默认以 `DEFERRED` 开启：开启时不取锁，第一次读取时取共享锁，第一次写入时才要写锁。一个已经读过的事务去要写锁、而写锁在另一条连接手里时，SQLite 不等，当即以 `SQLITE_BUSY` 拒绝它——两个都持有共享锁又都要写锁的事务互相等下去就是死锁。以 `IMMEDIATE` 开启的事务在开启时就要写锁，那时它什么也没读过，照忙等时限等。先读后写是最常见的事务：交付的文件库上十六个这样的事务同时运行，默认的开启方式下十三个当即失败，WAL 日志模式下同样如此；PostgreSQL 上同样的十六个互相等待，全部提交。驱动接受 `_txlock` 参数改变开启方式，但定位符同时带 `_time_format` 时它不读 `_txlock`。连接写不了库的定位符——只读副本、别的系统交出的只读文件——上，事务不写，SQLite 对开启方式的反应分两种：它以只读方式打开的库（`mode=ro`、`immutable=1`、进程没有写权限的文件）上，`IMMEDIATE` 与 `EXCLUSIVE` 的开启被当作读事务开启；`query_only` 开着的连接上，SQLite 拒绝这两种开启，报的是库只读，驱动默认的 `DEFERRED` 开启照常成功。`query_only` 可以由定位符的 `_pragma` 在每条连接上打开，也可以由一条语句在池里的某一条连接上打开或关掉。

SQLite 的共享缓存模式（`file:` URI 带 `cache=shared`）另成一格：同一个缓存里一条连接写着的时候，另一条连接要读写它的表，驱动经 `sqlite3_unlock_notify` 一直等到写的那条连接的事务结束，不看忙等时限，也不随上下文结束：另一条连接的事务写着一张表、3 秒后提交时，读这张表的语句即便上下文 500 毫秒到期、忙等时限设为 300 毫秒，也要等满这 3 秒。

给等连接设界，要的只是 database/sql 的知识；给等锁设界，要在取到的连接上按方言改写设置并在交还前放回，这一半按本模块的边界只能落在实现子包里，其上的模块只拿得到句柄与 `Dialect`。

## 考虑过的选项

### 只写明这些事实，由各模块自己给取连接设界

**否决**：每个模块各写一份取连接、钉住会话、交还连接的代码，失败的形状随各自的写法漂移，调用方从错误上分不出界到了与自己的取消；交还那一步最容易写错——`fn` 留下没结束的事务、在上下文不结束时 panic，连接就永远还不回去。插件手里只有一个会话，要自己从会话上找回背后的池。

### 在只开一条连接的句柄上，由本模块给每一条语句的取连接设界

包装句柄的连接池，每条语句先在界内取连接，再在它上面执行。

**否决**：它改变这类句柄上的每一条语句，另一条语句正常的长时间占用也会让排在后面的语句失败，而那种排队原本是这种句柄的正常形态。GORM 自己的 `Connection` 与预编译语句的路径直接取底下的池，绕过包装。池大于一条而被占满的句柄不在它的范围里。

### 内存库改用共享缓存，让连接池开多条连接

**否决**：共享缓存按表加锁，一个写着某张表的事务让并发读写它的连接一直等到它提交，忙等时限与上下文都结束不了这段等待；替调用方发出的语句在调用方的事务之外取了另一条连接，就永远等下去，这正是要消除的等待，只是换成了等锁。临时库无法共享。

### 让上下文结束 SQLite 的等锁

**否决**：驱动不交出挂接忙等回调的途径，它在上下文结束时发出的中断到不了忙等的重试，也到不了共享缓存里对 `sqlite3_unlock_notify` 的等待，要做到只能分叉驱动。

### 作为 `Database` 的方法

**否决**：插件在回调里拿到的只有会话，`OpenedFrom` 交回的也是句柄，拿不到 `Database`；接口多一个方法，会打破它在仓库内外的每一个实现与测试替身。

### 等锁也收进界里：取到连接时按剩下的时间设等锁时限，此后每条语句之前重设，方言的设法经 `Spec` 给出

SQLite 改写连接的忙等时限，PostgreSQL 改写会话的 `lock_timeout`，`fn` 返回后放回原值；只在取到连接时设一次的话，`fn` 的每一条语句都各等满一遍，所以每条语句之前按剩下的时间重设。

**否决**：界在 PostgreSQL 上仍守不住——`lock_timeout` 按每一把锁各计，一条语句先后等几把锁，就等到剩余时间的几倍，1 秒的界实测 1.8 秒、2.4 秒才让语句结束。每一条语句前多出读、设等锁设置的往返，审计自己写的每一行在 PostgreSQL 上慢到约 1.8 倍，而那一行就在每个被审计的请求路径上。PostgreSQL 的事务里一条语句失败之后只接受回滚，排在 `ROLLBACK TO SAVEPOINT` 之前的重设先失败，GORM 嵌套事务回滚到保存点随之失效，外层事务就此作废。改写设置要先认得出句柄的方言，本模块之外打开的句柄只能拒绝，宿主自建的句柄与测试替身就用不了依赖它的模块。

### 共享缓存的定位符照常交付，写明其上的等待没有界

**否决**：那里没有任何一方收得住这段等待——忙等时限与上下文都结束不了它，调用方给的期限同样不起作用；写明它只是把一次整个进程无声卡住的故障交给宿主自己去撞。

### 共享缓存的定位符只开一条连接

与只属于单条连接的库同样处置，交付的池内不再有第二条连接，等表锁变成等连接，`Connection` 管得住。

**否决**：同一个缓存照样够得着——`Open` 以同一个名字自建的连接、同一进程里另一次装配、宿主自己开的池都在那个缓存里，它们与交付的那条连接之间的等锁仍旧没有界。收成一条连接之后，它提供的也只剩 `:memory:` 已经提供的东西。

### SQLite 的事务照驱动的默认开启，写明先读后写的事务在别的连接写着时当即失败，要它等待的宿主在定位符里写 `_txlock=immediate`

**否决**：同一个事务在一个引擎上等待、在另一个引擎上当即失败，而那正是最常见的事务。本模块之上的模块在自己的事务里先读后写——名册的写入、设置的写入都是——每个用 SQLite 的宿主都得知道去写一个驱动参数，它们才不在任何并发写者之下当即失败；定位符同时带 `_time_format` 时驱动丢掉这个参数，写了也不生效，没有任何信号。

### 本模块在定位符上补 `_txlock=immediate`，由驱动照它开启事务

**否决**：驱动在定位符带 `_time_format` 时不读 `_txlock`，补上的默认值与宿主自己写的值都在那种定位符上静默失效；补参数还改写了 `file:` URI 交给 SQLite 的那段文本。

### 事务因 `SQLITE_BUSY` 失败时由本模块重跑

**否决**：事务的内容是调用方的代码，可能已经做了库以外的事；GORM 的 `Transaction` 没有重跑的接缝，重跑与否也不是本模块能替调用方定的。

### 交付的库默认改用 WAL 日志模式

**否决**：WAL 下读过的 `DEFERRED` 事务再去写，写锁在别的连接手里时同样当即以 `SQLITE_BUSY` 失败，这种失败没有消除；它还在库文件旁多出两个文件，改的是库在磁盘上的形态。

### SQLite 的事务默认以 `EXCLUSIVE` 开启

**否决**：回滚日志模式下它在开启时就挡住别的连接的读，而消除这种失败要的只是在开启时拿到写锁。

### `query_only` 开着的连接照样以 `IMMEDIATE` 开启，写明其上的事务开启即失败，要事务的宿主在定位符里写 `_txlock=deferred`

**否决**：驱动的默认开启下照常运行的只读定位符，每一个事务都在开启时失败，报的是库只读，不提开启方式；宿主要先知道这个驱动参数，而定位符带 `_time_format` 时驱动还丢掉它。

### 打开时拒绝打开 `query_only` 的定位符，点明它与 `IMMEDIATE` 的冲突

**否决**：这样的连接上每个事务都只读，`DEFERRED` 正是适合它们的开启方式，冲突由本实现自己化解得了，拒绝只是把一个绕行办法交给宿主；一条语句在一条连接上打开的 `query_only`，打开时的检查也看不见。

### 从定位符里读出 `query_only`，按它选开启方式

**否决**：`_pragma` 的取值是交给 SQLite 的一段 PRAGMA 文本，写法很多——`query_only(1)`、`QUERY_ONLY=true`、`query_only = on`——照 SQLite 的布尔规则读它是在复制 SQLite；语句在单条连接上打开或关掉的 `query_only`，定位符上读不出。

### 每个事务开启之前先问连接的 `query_only`

**否决**：每条连接上的每个事务都多出一条语句，为的是少数定位符才有的形态；开启被拒之后再问，写得了库的连接上一条也不多。

### 本模块提供包级的 `Connection`，只给取连接设界，等锁照引擎自己的设置；SQLite 实现拒绝共享缓存的定位符，以 `IMMEDIATE` 开启事务，定位符的 `_txlock` 可改，开启因 `query_only` 被拒时改以 `DEFERRED` 开启

**采纳**，见决策。

## 决策

采纳：本模块提供包级函数 `Connection(ctx, handle, wait, fn)`。它在 `wait` 之内从句柄背后的连接池里取一条连接，在钉住这条连接的会话上、在调用方的 `ctx` 下运行 `fn`；取不到连接时返回的错误包着 `context.DeadlineExceeded`。它不读、不设、不放回任何等锁设置，`fn` 的语句按连接上引擎自己的设置等锁。

句柄底下是连接池的，不论是否由本模块打开，都从那个池里取；句柄已经在一条连接上——一个事务，一个已钉住的会话——时，`fn` 就在这个句柄上运行，什么也不等。`fn` 返回或 panic 之后，它在那条连接上开着的事务在那条连接上回滚、开着的结果集关掉，连接回到池里，panic 照旧向上传。

SQLite 实现不打开把连接放进共享缓存模式的定位符，交付的与 `Open` 自建的都一样：它的 `Dialector` 认出这种定位符，初始化即失败。认法照驱动交给 SQLite 的样子、照 SQLite 解析 URI 的方式：`#` 结束 URI，`%HH` 先解码，转义出的 NUL 截断它所在的部分，名字为空的参数连同取值跳过，同名参数取最后一个。

SQLite 实现自己开启每一个事务，不经驱动的开启：以 `IMMEDIATE` 开启，在开启时就在忙等时限之内等写锁。定位符的 `_txlock` 参数指明别的开启方式时照它，读法与驱动的文档相同——取第一个，`deferred`、`immediate`、`exclusive` 不分大小写，不认得的值拒绝打开——不论定位符还带着什么。以只读方式开启的事务，以及最后一个 `mode` 参数为 `ro`、又没写 `_txlock` 的定位符上的事务，以 `DEFERRED` 开启：它们不写，在开启时取锁只会挡住别的写者——写得了的库上取的是写锁，只读打开的库上 SQLite 把 `IMMEDIATE` 当作读事务开启，取的是读锁，回滚日志模式下它同样挡住别的连接提交。开启被 SQLite 拒绝时，实现问这条连接的 `query_only`，开着就改以 `DEFERRED` 开启，不论定位符写的是哪种方式；没开着，拒绝原样交给调用方。

模块自己在交付库上发出、可能在调用方的事务里被调到的语句，经 `Connection` 取连接。

## 后果

取连接这一段在本模块交付的每一种库上都有界，界到了调用失败而不是一直等，调用方从错误上把界到了与自己的取消分开。等锁照引擎自己的规矩，不收进这个界：SQLite 上每一条语句至多等一个忙等时限；PostgreSQL 上等到上下文结束，或由 `lock_timeout`、`statement_timeout` 结束。SQLite 上先读后写的事务在别的连接写着时，在开启时照忙等时限等写锁，与 PostgreSQL 上同样的事务一样等待，而不是当即失败。方言知识不进本模块之上的模块。插件只拿着一个会话、宿主拿着自建的句柄，都调得到它。经 `Connection` 写出的一行与直接经句柄写出的一行发出的语句相同。

**接受的代价：**

- 界是失败而不是答案。界到了那次调用失败，要让它成功，得先由调用方放开它占着的连接：提交事务、关掉结果集。只开一条连接的库上、调用方的事务里，这样一次调用等满 `wait` 才失败，这段时间里调用方的事务与那条连接都被占着；一次本可以据表作答的调用得到的是一个既不是答案、也不是拒绝的失败。
- 等锁不在界内。调用方的事务占着的是锁而不是连接时——文件库上不以 `DEFERRED` 开启的事务从开启起、以 `DEFERRED` 开启的事务写过之后占着写锁，回滚日志模式下以 `DEFERRED` 开启、读过的事务占着共享锁，写入的提交要等它读完；PostgreSQL 上它写过某一行之后——经 `Connection` 的语句等的仍是调用方：SQLite 上等满忙等时限才失败，替调用方写的事务在开启时就等调用方占着的写锁；PostgreSQL 上写调用方写过的那一行，等到调用方的事务结束，而调用方在等它返回，上下文没有期限、会话又没有 `lock_timeout` 与 `statement_timeout` 时就永远等下去。要这一段也有界，宿主在定位符里给出等锁的设置，或给调用一个期限。
- 一次调用的等锁不合计。`fn` 的每一条语句各按连接上的设置等，一次为说明失败原因再读几次的调用，等锁的时长是一条语句的几倍；PostgreSQL 上一条语句先后等几把锁，同样各等一个 `lock_timeout`。
- 等锁到时报的是引擎自己的错误，SQLite 的 `SQLITE_BUSY`、PostgreSQL 的 `lock_not_available` 或语句超时，本模块不给它分类。它与等锁无关的同类失败——以 `DEFERRED` 开启、读过之后再写的事务当即收到的 `SQLITE_BUSY`，PostgreSQL 的 `NOWAIT`——从错误上分不开，只能看它来得早晚。
- SQLite 上以 `IMMEDIATE` 开启的事务——不以只读方式开启、定位符又没写别的开启方式时的默认——在开启时就占住写锁，只读不写的也一样：同一个文件库上两个这样的事务不再同时运行，后一个在开启时等前一个结束，等满忙等时限就失败。只读的工作以只读方式开启事务，或者不开事务。
- `query_only` 开着的连接上，每个事务的开启多出一次被拒的开启与一次对 `query_only` 的读；定位符在那里写的 `_txlock=immediate` 或 `exclusive` 不起作用，事务以 `DEFERRED` 开启。
- 定位符写 `_txlock=deferred` 的宿主拿回 SQLite 的默认，连同先读后写的事务当即失败这一格。开启事务的语句由本实现发出，驱动日后对开启方式的改动到不了这里。带 `_time_format`、`_txlock` 又写了驱动不认得的值的定位符，驱动照常打开，本实现拒绝打开。
- 界只约束经 `Connection` 取连接的语句。宿主直接在外层句柄上发的语句照旧等到上下文结束，只开一条连接的库上事务里的语句要走事务句柄，这一条不变。
- `fn` 返回时它开着的事务一律回滚，没关的结果集一律关掉；`fn` 要提交的事务得在返回之前提交。`fn` 的会话钉在一个包装了那条连接的连接池上，`Statement.ConnPool` 不是 `*sql.Conn`。
- SQLite 的共享缓存定位符不再可用，交付与 `Open` 都以 `ErrConnectFailed` 失败。只属于进程自己的内存库改写 `:memory:`，多条连接共用的库改用文件。

## 失效条件

若正常负载下经 `Connection` 的语句普遍因为等锁过久而失败或挂住，等锁需要由本模块设界，届时要的是一个在两个引擎上都守得住的办法：PostgreSQL 上按一条语句而不是按一把锁计。

若驱动对共享缓存表锁的等待也受忙等时限或上下文约束，拒绝共享缓存的定位符可以撤回。

若驱动在任何定位符上都照 `_txlock` 开启事务，开启事务的语句可以交还驱动，默认的开启方式经它的参数给出。
