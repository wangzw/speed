# 默认语言是配置项 i18n.default-locale，i18n 与 authn 取同一个

## 背景

认证模块的短信发送与 i18n 能力各需要一种「一个什么都没指名的请求解析到的语言」。它是协商取不到、账户偏好也没有时的兜底（[ADR-i18n-locale-resolution](adr-i18n-locale-resolution.md)），短信一侧它还是未声明语言时选哪种模板的依据。

认证模块此前把这个默认写进代码：`LocaleOf` 把一个不含语言的值读作 `zh-CN`，`zh-CN` 与 `en-US` 是短信模板的封闭集。默认的来源本身另有一条决策（[ADR-i18n-language-set](adr-i18n-language-set.md)）；本记录约束的是它由谁持有、有几个。

## 考虑过的选项

### 默认由两个模块各持一份

i18n 引擎有自己的默认，认证模块有自己的默认。

**否决**：同一个请求在错误响应与短信两处得到不同语言，除非每一处都显式传语言；两个默认的边界不在任何一处显现，改动其一会让两处悄悄分叉。

### i18n 缺席时认证模块退回另一个默认

装配了 i18n 引擎用一个默认，没有它时认证模块退回另一个。

**否决**：默认随装配是否存在而变化，同一份请求在两个装配里得到不同语言；一份二进制在有无该引擎时有不同行为，而这一差异不产生任何信号。

### 默认是一个配置项，两个模块读同一项

默认语言是配置项 `i18n.default-locale`，未设置时为 `en-US`；i18n 引擎与认证的短信模块读同一个项，一处声明同时服务两个能力目录。

**采纳**，见决策。

## 决策

采纳：默认语言是配置项 `i18n.default-locale`，取值是一个 BCP 47 标签，未设置时为 `en-US`。它是 i18n 引擎的 `Resolver.Default` 报告的语言，也是短信模块在请求语言为空或解析不到时的落点；一处配置同时决定错误文本与未声明语言时短信发的是哪种模板。

两个能力目录读的是同一项。命名空间与项名由 `pkg/i18n` 根包导出为 `ConfigNamespace` 与 `DefaultLocaleItem`，短信模块经 `reader.Decode(i18n.ConfigNamespace, &cfg)` 读它；该项在短信一侧预置为 `en-US`，因而一个没有纳入 i18n 引擎、也就没有该命名空间的装配读到的仍是英文，与那个引擎自己会读的默认一致。

## 后果

未协商、无账户偏好的请求，其错误文本与通知类文本按 `i18n.default-locale` 渲染；登录短信在请求语言解析不到时按该语言的模板。改默认只有一处。

**接受的代价：**

- 默认语言是启动期输入，取值不是 BCP 47 标签时启动失败，不再有一个恒定的编译期兜底。
- 这个项住在 i18n 命名空间，却由认证的短信模块读取；两个能力因此共用一个配置名，它成为跨模块的配置契约，改名会让两处静默各读一份。
- 默认语言的改动连带改变任何依赖默认的错误文本、通知文本与短信模板语言，影响面不止一处。
- 升级前默认发中文短信的部署，若不设该项，升级后默认发英文；让厂商侧提供 `en-US` 模板成为这个部署的一项工作。

## 失效条件

若产品的目标语言按租户或按区域而异、一个进程级的默认不够用，则「一个进程一个默认」不再成立，默认要下移到设置或租户级配置；本记录随之改为一处声明多个来源的回落次序。

若认证模块不再需要一种默认语言（例如短信语言完全由调用方指定、缺失即拒绝发送），则「两个模块读同一项」这条判据失去载体，只剩 i18n 一侧的默认。
