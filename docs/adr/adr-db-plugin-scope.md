# 数据库模块承担自足的横切能力，需要上层概念的经插件扩展点接入

## 背景

数据库之上有一批横切能力：软删除、字段级加密、按租户过滤、审计。它们的共同点是必须作用于每一条语句——遗漏一条，它要防的事情就发生了，且不会在该条语句上显形。

这些能力需要语句级的拦截点：知道这条语句作用于哪个模型、要读还是要写、条件里已经有什么。GORM 的回调链与字段序列化机制提供了这个拦截点，而数据库模块封装 GORM，它交付的句柄就是 `*gorm.DB`（[ADR-module-packaging](adr-module-packaging.md)）。

它们对语句之外的东西的需求并不相同。软删除要的是一个删除时间列，字段级加密要的是一份密钥，两者都不必知道是谁在发这条语句、为了什么；按租户过滤要知道当前是哪个租户，审计要知道是谁在执行变更、记录写到哪里去。

租户标识与执行变更的一方的身份产生于依赖图上层的模块。数据库模块被每一个访问库的模块依赖，位于它们之下。

密钥不能存放在它所保护的那个库里——那样要先有密钥才读得出密钥。它因而只能在数据库之外给出，按配置与设置的划界判据落在配置一侧（[ADR-config-scope](adr-config-scope.md)）。

## 考虑过的选项

### 数据库模块承担全部横切能力

模块内建按租户过滤与审计，模型带上本模块约定的声明即自动生效。

**否决**：租户标识与执行变更的一方的身份产生于依赖图上层的模块，数据库模块反向依赖它们会成环；把它们下沉到数据库模块自己定义，则每一个需要租户标识而不访问数据库的模块——注入点、认证、日志——都要为取得一个标识而 import 数据库模块。该选项还替每一个宿主决定了它是多租户的，单租户应用同样要带着这套概念和它施加的模型约定。

### 横切能力一律由上层模块经扩展点接入

数据库模块只交付连接与迁移，每种横切能力各由一个模块承担，声明自己的插件。

**否决**：软删除与字段级加密不需要任何上层概念，把它们推到模块外面，每个项目要各自重做一遍——而它们恰恰属于"漏一条就失效"的那类能力，分散实现正是漏的来源。软删除更是 GORM 自己就提供的，在外面重做一遍还要绕过它已有的机制。

### 声明即生效，不看声明它的模块是否启用

插件资源照 `core.Resources` 的字面收集：那个查询遍历全部已注册模块，不看启用结果，因此一个消解落选、从未构造的模块所声明的插件照样安装。

**否决**：那会让一个没有运行的模块的声明仍然生效，在"没启用就不生效"上开一个洞，且这个洞不报错——插件安装成功，没有任何一处会说它来自一个没有启用的模块。被采纳的读法是同一个查询加上启用过滤。迁移集另有自己的判据（[ADR-module-resource-scope](adr-module-resource-scope.md)）：插件只对这一次运行发出的语句起作用，判据因而是这个模块属不属于这一次运行；迁移改的是跨命令共享的库结构，判据因而不是。

### 按是否需要上层概念划分

不需要的由数据库模块承担，需要的经插件扩展点接入。

**采纳**，见决策。

## 决策

采纳：数据库模块承担不需要认识上层概念的横切能力；需要上层概念的经插件扩展点接入。

**判据是：除了这条语句本身，该能力还需不需要一个产生于依赖图上层的概念。**

不需要的由数据库模块承担。软删除只需要一个删除时间列，字段级加密只需要一份来自配置的密钥，两者都在数据库模块自己够得着的范围内。

需要的经扩展点接入：模块以资源声明交付自己的 GORM 插件，数据库模块在建立连接后、交付实例之前安装。按租户过滤要知道当前租户，审计要知道执行变更的一方与记录的去向，两者都产生于数据库模块之上。

插件只对这一次运行发出的语句起作用，而库结构跨命令共享。插件声明的取材域因而是这一次运行的启用集，迁移集的取材域不同（[ADR-module-resource-scope](adr-module-resource-scope.md)）。启用集的划界与安装次序见 design-db 的插件的安装。

数据库模块不解释插件的内容，也不认识任何一种插件所实现的能力。

## 后果

软删除与字段级加密是取用数据库功能就得到的东西，模型按约定声明即生效，不需要额外装配一个模块。

租户隔离由租户模块实现，它定义自己的模型约定并声明自己的插件；数据库模块不认识租户。审计同理。

不装配这些上层模块的宿主不承受它们的约定：模型不必带租户标识列，也不必带上它们的约定。

数据库模块自己构造的实例，插件在交付之前全部装好，取用方不存在拿到这类实例而插件未装的路径。宿主预置的数据库实例不经这次驱动里数据库模块的 `New`（[ADR-supplied-instance](adr-supplied-instance.md)），数据库模块怎样对待它，见 [ADR-db-supplied-instance-refusal](adr-db-supplied-instance-refusal.md)。

**接受的代价：**

- 判据依赖"产生于上层的概念"这一区分，而新出现的能力未必一眼看得出落在哪边。一种能力先按自足实现、后来才发现它需要知道是谁在执行变更，或需要账户是否已停用，改归属就是一次跨模块的搬迁：执行变更的一方的身份与账户的停用状态都产生于数据库之上的模块，按判据属于经扩展点接入的一侧。
- 插件之间的相互顺序要由声明它们的模块用依赖声明表达。注册到 GORM 同一个处理器的多个插件，回调链次序取决于安装次序，而这一点在各自的插件代码里看不出来。
- 数据库模块无法校验插件装对了。它不认识插件的内容，一个声明了却对某类模型不生效的插件，在这里表现为安装成功。
- 未进入启用集的模块，其插件声明不安装。一个只声明插件、自己不访问库的模块落在启用集之外时，它提供的横切能力静默消失，依赖方随后发出的语句在无人过滤、无人审计的状态下照常执行。这是“没启用就不生效”的应有之义，不是缺陷。
- 插件建议可被多次 `Initialize`，不写成要求：插件是外部类型，数据库模块没有可观察面判断它是否可重复初始化。不满足建议的插件在自建连接的句柄上安装成功而不生效，失效形态静默，判定留在声明该插件的模块那一侧。
- 宿主预置的数据库实例上，插件不由本记录的安装时机保证。数据库模块在 `Migrate` 拒收不出自它的 `New` 的实例，而拒收之前的取用不经这道检查，出自它的 `New` 而插件与本次运行的启用集不一致的实例照样通过：经这样的实例的句柄发出的语句可能缺某个插件，也可能经过一个本次不启用的模块的插件，没有任何一层拦下（[ADR-db-supplied-instance-refusal](adr-db-supplied-instance-refusal.md)）。
- 按租户过滤在框架层没有机制保证。承担它的模块不被装配，或宿主预置的数据库实例落在拒收管不到的情形里时（[ADR-db-supplied-instance-refusal](adr-db-supplied-instance-refusal.md)），遗漏过滤不会被任何一层拦下。

## 失效条件

若出现一种横切能力，其拦截需求 GORM 的回调链与字段序列化机制都表达不了，则该能力既不能由数据库模块承担，也无法经本记录的扩展点接入，数据库模块的交付面需要重新裁定。
