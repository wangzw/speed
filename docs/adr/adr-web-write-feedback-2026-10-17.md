# 写入的结果由每个反馈作用域的一个槽承载，最近一次尝试为准，成功确认为默认

## 状态

已接受

## 背景

前端各包用同一组积木报告写入的结果：ui-kit 的 `InlineError`（`role="alert"` 横幅，文案由各包绑定的错误码解析器给出）、`InlineSuccess`（始终挂载的 `role="status"` 区域）、`AsyncSection`（读的四态）与 `ConfirmDialog`。积木统一，用法不统一，核对全部包的写入后可观察到下列后果：

- 控制台的页面把多个 mutation 的错误拼成「数组里第一个非空」的一条页底横幅（`firstErrorCode` 在邀请、账户、权限、SSO、短信各页各有一份）。旧错误只在同一个 mutation 再次触发时才清掉，因此旧错误遮住另一个 mutation 的新错误，或与后一次写入的成功文案并存。
- 设置页的批量保存在同步循环里对同一个 mutation 观察者连续调用 `mutate`，页面只反映最后一次：更早的某一项失败，最后一项成功时仍显示「设置已保存」。
- 有成功文案的页面与没有的页面并存：租户名册、设置、会话、权限有；账户创建、SSO、短信、邀请、冒充、租户详情的重命名与启停没有，只剩表单清空或列表重读这类对读屏不可闻的隐含变化。account-ui 的档案、口令、手机、标识与会话几节手写了与 `InlineSuccess` 相同的 `Alert`。
- `PermissionsPage` 的角色删除失败时确认对话框保持打开，失败横幅落在被 `aria-hidden` 的背后页面里，操作者在取消之前读不到它。
- 已有缓存数据时刷新失败，旧行保持原样且没有任何提示：`AsyncSection` 只在没有数据时进入失败占位。
- 一次性值（邀请的接受链接、SSO 的域名认领令牌、服务密钥）的展示块是没有 live region 的普通文字，不标明所属的租户或账户，且切换上下文后继续显示。

前端没有 Snackbar 或 toast，没有全局 `onError`；编码规范（`.claude/skills/frontend-coding-standards/SKILL.md`）没有点名这些积木，也没有「落地的写入要确认」的规则。同层的前端包不能互相 import，共享只能经 ui-kit。

## 考虑过的选项

### 维持现状，各页各自拼状态

**否决**：上列后果都出自这一做法。结果的归属（哪个控件组、哪个槽）、清除的时机与成功确认是否存在，在每个页面里各自决定，并已漂移：`firstErrorCode` 在多个页面各有一份副本，成功文案的有无按页面碰巧而定。

### 全局 toast 或 Snackbar，由 provider 统一承载

**否决**：失败要停留在被重试的控件近旁，toast 的自动消失不照顾读得慢的操作者，也不照顾读屏用户错过的那一次播报；成功与失败文案本来就要由发起写入的宿主翻译、点名对象，provider 只能转运文本，不能决定它。树里没有可建立其上的 provider，新建一个等于在页面区域模型之外再造一条反馈通道，而页面区域（先挂空区域、再填文本）已是 `InlineSuccess` 的验证过的无障碍做法。

### 在 QueryClient 的 `MutationCache` 里统一处理

**否决**：全局处理器看到的是一次 mutation，不是反馈作用域，不知道结果该落在哪个区域；批量保存这类一个动作含多次请求的尝试，在 mutation 粒度上无法表达为一次结果。它还把 ui-kit 与页面的反馈绑到 react-query 上，而反馈契约要对不经 react-query 的写入（登录流程、上传）同样成立。

### 每个包复制一份本地 hook

**否决**：同层包互不 import，共享只能放进 ui-kit；各包各留一份，就是 `firstErrorCode` 已有的多页副本再按包数复制，并且副本之间会继续漂移。

### 由 ui-kit 提供单槽 hook 与渲染区域，成功确认为默认

**采纳**，见决策。

## 决策

采纳：**一次写入的结果落在一个反馈作用域里，作用域持有至多一个结果、以最近一次尝试为准；ui-kit 提供 `useWriteFeedback`（槽的状态）与 `WriteFeedbackRegion`（把槽渲染为成功与失败的区域），各包用自己的错误码解析器绑定区域；每个落地的写入都落一条成功文案；不引入 toast 或全局处理器。**

- 作用域的划分、尝试的界定、成功文案的要求、对话框与区域的先后、读的刷新失败如何标明，由 ui-kit 的设计文档给出，本记录不重述。
- 编码规范新增对应的条款，使这一用法成为评审可裁决的规则。

## 后果

同一类缺陷（旧错误遮新错误、成功与失败并存、批量保存的假成功、失败落在被隐藏的区域）由槽的语义一处排除，不再靠每个页面各自记得清除。成功确认从个别页面的做法变成默认，读屏用户与看得见的用户得到同样的确认。`firstErrorCode` 的副本与 account-ui 里手写的成功 `Alert` 随迁移消失。

**接受的代价：**

- **ui-kit 获得一个带状态的 hook。** ui-kit 的组件不持有状态，hook 的状态属于调用它的宿主组件；契约需要明确这条界线，而 ui-kit 此前交付的只有无状态的原语。
- **各页面要重新划分作用域，改动面覆盖所有有写入的页面。** 页底的聚合横幅被拆成每个控件组一个区域，页面的结构、测试与文案键随之变化；迁移不是原子的，所有页面迁完之前，两种反馈做法并存。
- **一个作用域一个槽，重叠的尝试以后落定者为准。** 同一作用域内两次写入几乎同时落定时，先落定者的结果被后者替换；发起控件在进行中处于忙态只能减少、不能消除这种重叠。
- **新的成功文案要双语。** 每个此前没有确认的写入都要新增 zh-CN 与 en-US 两条文案，每条都点名被改动的对象。
- **读屏用户听到更多播报。** 每个落地的写入都会触发一次 `role="status"` 的更新。
- **结果不自动消失。** 成功文案一直留到下一次尝试或上下文切换，页面上可能停着一条已无关的确认，由 `reset` 的调用点（尝试开始、上下文切换）负责清除。

## 失效条件

- 出现一个控件组里需要多个并发、互相独立的结果的界面：作用域要再细分，或槽要改为按键的集合。
- 实测显示读屏用户被成功确认的播报频率困扰：成功确认需要按写入的分量分级，不再「每个落地的写入」一律播报。
