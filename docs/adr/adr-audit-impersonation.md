# 冒充的明细键只由审计模块写入，非冒充行上的同名键被剥掉

## 背景

冒充行的“替谁、限定在哪个租户、在哪个登录会话里”存在于明细的 `on_behalf_of`、`impersonation_scope` 与 `session` 里；审计表没有对应的列，行主体列记的是真正动手的人（[ADR-authn-identity](adr-authn-identity.md)）。

明细是各条通路共用的通用通道：记录接口的调用方自选键名，事件级通路把载荷的标量字段原样变成明细键，载荷的字段名由发布方决定。读审计表的一方要靠这些键回答“这一行是不是冒充，替谁”，键在即冒充。

冒充身份带会话与冒充范围，由网关的出口检查守住；审计模块只从上下文里的身份读这些值。

## 考虑过的选项

### 非冒充行原样保留调用方放进明细的同名键

**否决**：键在即冒充的读法在一行普通操作上失效：一个字段叫 `session` 的事件载荷，或一个明细里写了 `on_behalf_of` 的调用点，会留下一行看起来是冒充，或带着不属于该请求的会话的审计行。冒充行上本模块覆盖这些键，碰撞在冒充时被消除，其余时候无声地留在表里，所以问题只在读表的一方按键判断时才暴露。

### 非冒充行上带这些键的明细令整行被拒

**否决**：事件级与语句级通路没有可回传错误的调用方，拒绝等于丢掉一行本该留痕的事实；丢掉一个键的损失小于丢掉一整行。

### 审计模块写的键改用保留前缀，调用方的同名键不再碰撞

**否决**：这些键名已在认证模块的明细闭集里，改名要同时改认证文档与读表一方，而碰撞换成了前缀的约定，调用方仍可以自行写出带前缀的键。

## 决策

采纳：**`on_behalf_of`、`impersonation_scope`、`session` 只由 `audit.journal` 在冒充行上写入；非冒充行上，包括上下文里没有身份的行，调用方放进明细的同名键一律剥掉。**

- 冒充行上这些键取自上下文里的身份，不取自调用方。
- 判据是上下文里的身份是否是冒充身份，与来源通路无关。
- 调用方的其余明细键不受影响，调用方交来的映射不被改动。

## 后果

读审计表的一方可以只凭这些键的存在判断一行是不是冒充，并信任它们的值出自网关盖章的身份。

**接受的代价：**

- **记录接口对这些键名有损耗。** 任何模块的明细里叫 `session` 或 `on_behalf_of` 的键在非冒充行上被静默丢掉，没有错误也没有日志；要记会话标识的调用方改用别的键名（认证模块自己用 `sid`）。
- **事件载荷里同名字段在非冒充行上被丢掉。** 发布方不知道这条规则，字段名撞上时事件级的行少一个键，发布方与订阅方都不会得到通知。
- **键名是约定，不是类型。** 明细是字符串映射，没有一处在编译期拦下调用方写这些名字。

## 失效条件

若审计表为被冒充者加专用列，这些键转为列，明细键名的保留不再需要。
