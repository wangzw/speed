# 驱动深度由命令决定，释放责任不随之转移

## 状态

已接受

## 背景

生命周期分为八个阶段，由注册表按固定顺序推进（[ADR-lifecycle-stages-2026-09-13](adr-lifecycle-stages-2026-09-13.md)）。推进这件事此前只有一种形态：从头推到 `Serve`，然后阻塞等待宿主取消，取消后关停。

子命令要求的形态不止一种（[ADR-command-tree-2026-09-20](adr-command-tree-2026-09-20.md)）。应用迁移需要全部产物构造完成，但不需要任何对外入口开始监听，执行完即退出；打印版本不需要装配任何模块；启动并提供服务才是推到底并阻塞的那一种。

推到底的形态有一条性质必须保住：进去一次，出来一次，释放资源不依赖宿主记得调用第二个方法。把推进拆成若干个可分别调用的操作会直接破坏它——宿主一旦可以只调前半段，就可以忘记调后半段，而忘记的后果是资源不释放。

## 考虑过的选项

### 每个子命令都完整驱动一遍

不区分深度，任何子命令都推到 `Serve`，命令的动作在推进完成之后执行。

**否决**：迁移会让对外入口开始监听端口、让后台任务开始运行，而这次运行的目的只是改一次库结构。一个以退出为终点的动作被迫先把整个服务跑起来。

### 用配置关掉不需要的模块

深度不变，靠配置决定本次不纳入哪些模块。

**否决**：把命令的意图编码成一串配置上的否定，同一个程序因而需要为每种运行方式各维护一份配置。而"这次不要监听"本来就不是配置要表达的东西，它是这次运行是什么的直接结果。

### 为每种深度提供一个独立入口

注册表为每种运行形态各提供一个方法，例如推进到构造完成、推进到服务就绪。

**否决**：深度取值来自阶段序列，穷举入口会随阶段的增减而变动，且两个入口之间共享的推进逻辑没有地方安放。

### 把推进拆成可分别调用的分段操作

注册表暴露若干个分段方法，宿主按需依次调用。

**否决**：破坏上述那条性质。宿主可以只调用前半段，资源随之泄漏，而这个错误在正常路径上不显形。

### 深度作为驱动的参数

推进仍是一次调用，调用时指明这次要推进到哪个阶段，以及推进完成之后执行什么动作。释放由这次调用负责，与推进到哪个阶段无关。

**采纳**，见决策。

## 决策

采纳：驱动的深度是一次驱动调用的参数，不是一组可分别调用的操作。

- 一次驱动指明推进到哪个阶段为止，以及到达之后执行什么。推到 `Serve` 并阻塞等待取消是其中一种取值，不再是唯一的形态。
- **已构造的实例由这次驱动负责释放，无论推进到了哪个阶段、也无论中途是否失败。** 释放的责任不因深度可选而转移给宿主，原有的进出成对性质完整保留。
- 未被推进到的阶段，其回调不执行。模块不因此需要知道自己运行在哪种深度下。

## 后果

以退出为终点的运行方式不必先把服务跑起来。

阶段集合保持不变，模块作者面对的阶段契约没有增减。

释放资源仍然只依赖一次调用，宿主没有可以遗忘的第二步。

**接受的代价：**

- 一个阶段是否执行，现在取决于这次驱动的深度。把只应执行一次的动作放在靠后的阶段，会让它在浅驱动下被跳过，而这种跳过不会报错。
- 阶段位被借用来表达"全体就绪"的地方，其两侧的时机随深度变化。入口模块用 `Migrate` 与 `Start` 两个阶段位围出登记窗口，浅于该深度的驱动不会打开这个窗口；该深度下也没有登记发生，因而自洽，但这个耦合不体现在任何一方的声明里。
- 宿主看得见深度这个概念，需要为每个命令判断它要推进到哪里。

深度由命令选定并不是唯一的形态：入口 `Run` 不接命令，深度由该入口本身固定为 `StageServe`，不经命令选定；它与 `Drive` 的分工见 [ADR-drive-entry-2026-09-21](adr-drive-entry-2026-09-21.md)。

## 失效条件

若出现一个无论驱动到哪个深度都必须执行的动作，"未被推进到的阶段不执行"不再成立，届时这类动作需要一个独立于阶段序列的表达形式。
