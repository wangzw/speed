# 微信登录自写薄客户端，网站应用与公众号拆成两个模块

## 背景

微信的浏览器端授权入口是网站应用扫码登录（授权范围 `snsapi_login`）与公众号网页授权（授权范围 `snsapi_userinfo`），入口集合以这两项为限。两个入口的授权地址、授权范围与应用凭据各自独立，宿主可以只用其中一个。登录方式的总体取舍见 [ADR-authn-login-flow](adr-authn-login-flow.md)，流程与配置键见 design-authn-login 与 design-authn-config，本记录只决定微信一侧的实现来源与模块切分。

下列事实限定了可选范围。

- 微信换令牌的接口是带 `appid`、`secret`、`code`、`grant_type` 的 `GET`，`secret` 在查询串里。失败以 HTTP 200 返回，响应体带非零 `errcode`，状态码不区分成败。
- 微信的授权协议没有 PKCE、没有 `nonce`、没有 ID 令牌。授权回跳的 CSRF 防线只有 `state` 与流程绑定，比 Google、GitHub 与企业 OIDC 少一层（[ADR-authn-oauth-flow](adr-authn-oauth-flow.md)）。
- 微信不提供邮箱。外部身份的主体取 `unionid`，没有则取按应用区分的 `openid`（[ADR-authn-external-binding](adr-authn-external-binding.md)）。
- Go 的 `*url.Error` 的文本带完整请求 URL。`secret` 在查询串里，任何把出站错误原样记入日志、写入响应或转交调用方的路径都会泄露它。
- 认证模块取现成库与 speed 之间的桥，自写需要现成库承担不了的理由（[ADR-authn-scope](adr-authn-scope.md)）。社交与企业 OIDC 的校验已取 `go-oidc` 加 `x/oauth2`。
- 一个模块只有一个实例，一个实例只报一个登录方式名；每个模块依据自己那份应用凭据决定是否运行——两项凭据都空时自行关闭，只给一项时是半配置（[ADR-authn-packaging](adr-authn-packaging.md)、[ADR-module-enablement](adr-module-enablement.md)）。
- 日志脱敏由规则登记提供，持有秘密的模块在 `New` 里先于日志器绑定登记（[ADR-log-redaction](adr-log-redaction.md)、[ADR-authn-wiring](adr-authn-wiring.md)）。

## 考虑过的选项

### 以 x/oauth2 为桥，自定义微信的端点

用 `oauth2.Config` 配一个微信的 `Endpoint`，授权码交换与令牌解析交给 `x/oauth2`，与 Google、GitHub 的实现同形。

**否决**：`x/oauth2` 的约定与微信的接口在下列各点上不一致。前两点各自使该库无法直接承担这一步；第三点未经核实，不构成否决理由。清单是已确认的不一致，不是两者差异的全集。

- 参数名：库发 `client_id` 与 `client_secret`，微信要 `appid` 与 `secret`。
- 错误形状：微信以 HTTP 200 加 `errcode` 返回失败，库只会报缺少 `access_token`，`errcode` 被丢掉，授权码过期、重复使用与应用凭据错误无法区分。
- 请求方法：库的令牌请求固定为 `POST`，微信的换令牌接口是 `GET`。`POST` 在成功路径上是否被接受未经核实。

### 桥接 goth 的微信提供方

经 `goth` 取微信登录，由它产出用户信息。

**否决**：`goth` 的微信提供方为外部身份引入下列与已定规则相悖的行为。它合成形如 `<openid>@wechat.com` 的邮箱，下游会把合成值当作提供方断言的邮箱；邮箱既不作绑定键，也不写入账户或用于识别账户，微信也没有邮箱（[ADR-authn-external-binding](adr-authn-external-binding.md)、[ADR-authn-contact-and-login-ways](adr-authn-contact-and-login-ways.md)）。它丢掉 `unionid`，`openid` 按应用区分，同一个人在网站应用与公众号下得到不同的主体，绑定键因而分裂。它把 `secret` 放在 URL 里，错误净化落在不受本项目控制的库内部。`goth` 作为整体的其余缺陷见 [ADR-authn-oauth-flow](adr-authn-oauth-flow.md)。

### 桥接 silenceper/wechat/v2 的公众号网页授权包

宿主取 `silenceper/wechat/v2` 的 `officialaccount/oauth`，由它换令牌，自己净化错误并自生成 `state`。

**否决**：该库在下列各点上不能直接承载这一步。清单是已核实的项，不是该库问题的全集。

- HTTP 客户端是进程全局的、无超时的包级变量，没有逐实例注入的口。桥接要改写这个包级变量，同进程内别的使用者随之受影响，影响范围未经核实；不改写则出站调用没有超时。
- `state` 不转义。
- 非 200 响应时，错误文本带含 `secret` 的完整请求 URI。
- 构造要整个公众号上下文，只为换一个授权码而装配公众号的全部能力。
- 带入另一个 Redis 客户端主版本（`go-redis/redis/v8`），仓库使用 v9。

净化错误与自生成 `state` 是桥接方案自己要补的两块，补完之后留给库的只剩一次 `GET` 与对响应体的解码，而这一步又要绕开它的全局 HTTP 客户端。`chanxuehong/wechat`、`PowerWeChat` 一类整套微信 SDK 与它同属为公众号运营而设的整体，依赖足迹与适配成本同样大，按同一理由不取。

### 一个模块交付两个入口

网站应用与公众号放进同一个模块，由它报告两个登录方式名，共用一份配置。

**否决**：一个实例只能报一个 `Name()`。让登录方式接缝改为返回方法列表，会使每个取用登录方式的消费方都多一层展开，换来的只有这一个提供方的便利（[ADR-authn-packaging](adr-authn-packaging.md)）。两个入口各有自己的应用凭据，宿主常常只用其一；合并成一个模块后，一个入口的凭据只给一半就使整个模块启动失败，连带另一个本可运行的入口，而拆开时两者各自判定。

### 两个模块各自带一份客户端

入口按模块拆开，各自在自己的包里实现一份换令牌与错误处理。

**否决**：出站错误剥去 URL、`errcode` 判定、`secret` 的日志脱敏登记与主体选取是该客户端的全部风险所在，两份实现意味着每处净化各写两遍，漏净化一处即泄露，两份实现之间的差异也无人察觉。

### 自写薄客户端，两个入口各一个模块并共用内部包

不引任何微信 SDK 与 `goth`，换令牌、`errcode` 判定、错误净化与主体选取写成一个内部客户端包，两个入口各一个模块，分别持有自己的配置。

**采纳**，见决策。

## 决策

采纳：微信登录自写薄客户端，不引任何微信 SDK 与 `goth`；网站应用与公众号拆成两个模块，共用同一个内部客户端包。

- **自造的判据。** `x/oauth2` 与各整套 SDK 在参数名、错误形状、HTTP 客户端的注入与错误文本的净化上，没有一项能不经绕开而直接承担；桥接方案要补的部分与自写相当，补完之后留给库的只剩一次 `GET` 与响应体解码。以上是本项目破例自写而不取桥的理由，适用范围限于微信这一个提供方，不推广到其他提供方。
- **两个模块。** 网站应用与公众号各是一个模块，分别交付登录方式名 `wechat.web` 与 `wechat.mp`。每个模块有自己的一份配置与必填校验，缺必填项即以配置不合法失败，两个模块之间没有联合判定。宿主在命令树上点名哪个模块，哪个入口就存在、哪份配置就必填。模块名、配置键与哨兵由 design-authn-config 与 design-authn-failure 承载。
- **共用客户端。** 两个模块共用登录目录内部的同一个微信客户端包。换令牌的请求、`errcode` 判定、错误净化与主体选取只在这一个包里有一份实现。HTTP 200 加非零 `errcode` 一律按失败。身份只取 `unionid` 或 `openid` 命名空间的键，不合成邮箱，昵称与头像不是授权依据。流程细节见 design-authn-login。
- **`secret` 的处置。** 判据是：携带 `secret` 的 URL 不得以任何形式离开客户端包。客户端的出站错误在返回前剥去 URL。客户端套 `observability.Transport(log.Transport(...))`：外层注入追踪头，内层为每次换令牌写一条记录，只取方法、主机、不含 query 的路径、对端状态、`outcome` 与耗时，无应答时取 `url.Error` 之下的底层成因；query 里的 `secret` 与授权码既不进跨度属性也不进记录。配置里的应用密钥值登记为日志脱敏的字面量匹配器，登记发生在模块的 `New` 里、先于日志器绑定。登记与「永不记录」的范围见 design-authn-events 与 [ADR-authn-events-and-audit](adr-authn-events-and-audit.md)，应用密钥作为敏感配置项的存放见 [ADR-authn-settings-and-secrets](adr-authn-settings-and-secrets.md)。
- **CSRF 的残余风险。** 协议没有 PKCE 与 `nonce`，微信入口的回跳防线只有 `state` 与流程绑定。该风险写入威胁模型的残余风险栏并接受，不为它在客户端之外另造一层防线（design-authn-threats）。

## 后果

微信的错误语义、`secret` 的去向与外部身份的主体选取由 speed 自己持有。进程内没有被改写的全局 HTTP 客户端，模块图里也没有另一个 Redis 客户端主版本。两个入口按纳入与否各自判必填，只用其一的宿主不必为另一个入口配置凭据。微信出站调用经 `observability.Transport(log.Transport(...))` 带追踪头，换令牌的每次调用另留一条不含 query 与 `secret` 的记录：不套 `observability.Transport` 的例外曾以「`Transport` 是否会把请求 URL 带进跨度属性未经核实」为理由设立，并附带「核实它不触及 URL 即取消例外」的条件；`pkg/observability/transport.go` 的 `Transport` 只向请求的副本注入追踪头，不读取也不记录 URL，条件成立，该例外取消。

**接受的代价：**

- **自己维护客户端。** 微信接口变化时，换令牌、错误码与授权地址的调整都由本项目跟进，没有上游库代为兼容。
- **漏净化一处即泄露。** `secret` 在查询串里，客户端内任何一条把底层错误原样带出的路径都会泄露它。守住这一点靠测试而不是靠类型，新增的出站路径必须补同样的断言。
- **CSRF 防线比其他提供方少一层。** 微信入口没有 PKCE 与 `nonce`，授权码被注入或回跳被伪造时，`state` 与流程绑定是唯一的防线。
- **只能对模拟服务端测试。** 真实的微信接口需要真实应用凭据，开发与自动化测试都对模拟的服务端进行，模拟与真实服务之间的差异只能在带真实凭据的环境里暴露。
- **宿主要用两个入口时点名两个模块、写两份配置。**
- **破例自写要在每次被问起时重新举证。** 自造的理由限定在微信这一个提供方，别的提供方不能援引。

## 失效条件

下列情形出现时，本决策需要重议：

- 出现满足下列条件的桥：把标准 OAuth2 库接到微信，处理参数名、请求方法与 200 加 `errcode` 的错误形状，HTTP 客户端可逐实例注入且有超时，错误文本不带 `secret`，`state` 的生成与转义可由调用方掌握，依赖足迹与仓库已有版本相容。此时自写的前提不成立，应改为桥接。
- 桥接某个微信 SDK 所需补的部分（设置该库的包级 HTTP 客户端、净化库的错误文本、自生成 `state`）的维护成本，低于维护本客户端的成本。此时自写的前提不成立，应改为桥接。
- 微信的授权协议加入 PKCE、`nonce` 或 ID 令牌。残余风险一节的前提不再成立，客户端与威胁模型随之重议。

以下行为是未经运行核实的假设，依赖它们的断言以对应的测试守住，测试失败即视为本决策的前提不成立：

- 假设微信换令牌接口以 HTTP 200 加非零 `errcode` 返回失败（已有实测依据，需带真实凭据复核）。模拟的微信服务端驱动「200 加 `errcode`」「非 200」「畸形响应体」「网络错误与超时」，断言每种情形都以登录失败结束，且失败原因能区分授权码失效与凭据错误。
- 假设 `secret` 没有任何出口。对客户端的每条错误路径与每条日志路径，配置里放哨兵值作为应用密钥，断言返回的错误文本、日志输出与响应体里既不含该值，也不含携带它的 URL。新增出站路径时同步增加该断言。
- 假设两个入口的必填校验互不牵连。装配测试只纳入其中一个模块并只给它配置，断言构造成功；缺该模块自己的必填项则以配置不合法失败。
