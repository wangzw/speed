# 租户的停用来源记在名册行上，账户联动只撤销它自己造成的那一次

## 背景

账户停用要停用它的个人租户，账户恢复要恢复那个租户，但运营者主动停用的租户不得因账户恢复而重新启用（REQ-tenancy-044）。名册行只记启用与停用两个状态，一次停用是谁造成的读不出来；恢复路径拿不到这个事实，就只能选择全部恢复或全部不动，前者推翻运营者的决定，后者让账户恢复失效。

一条账户造成的停用与一条运营者造成的停用在库里的形状完全相同：同一个状态取值，同一行。名册之外的任何一方也记不住它——宿主没有自己的持久状态，进程重启与多副本之间不共享，每个宿主各记一份还会各自漂移。

写入方在名册之外：运营者经 [tenant.admin](../design/modules/tenant/design-tenant-admin.md) 改状态，宿主经账户生命周期钩子联动（[ADR-authn-account-restoration](adr-authn-account-restoration.md)）。"运营者的决定不被推翻"是租户这一层的性质，不是某一个宿主的策略；只在一个宿主的钩子里判，第二个宿主就得把同一条判据再写一遍。

`Status` 的零值读作停用，落在拒绝的一侧。来源的零值同样不得落在能自动恢复的一侧。

## 考虑过的选项

### 恢复时按账户状态推断来源

账户恢复时，宿主查账户是不是启用，是就把租户重新启用。

**否决**：账户启用说明不了这个租户为什么停用。运营者在账户正常时停用的租户，会在任何一次账户状态迁移之后被打开。判据要回答的是"这条停用是不是账户造成的"，而账户状态答的是另一个问题。

### 宿主自己记住它停用过哪些租户

每个宿主在进程内保存自己造成的停用，恢复时按这份记录决定。

**否决**：进程重启之后这份记录就没有了，跨副本又各记一份；一次重启之后的账户恢复不会恢复租户，一次多副本之间的迁移会得出两个答案。宿主为这件事新增一张表，等于把名册的一部分搬到一个它并不拥有的地方。

### 行上两个来源标记，租户在任一标记成立时不被服务

名册行分别记"运营者要它停用"与"账户要它停用"，两个都为假才在册。

**否决**：租户的在册与否会变成两列状态的函数，而运营者的每一次显式启用都要回答"另一个标记还在时启不启用"。产品要的是运营者的决定优先，单列最后一次决定直接表达这条规则；两列表达的是另一条规则，即运营者不能在账户停用时启用租户。

### 行上一个停用来源，名册按来源约束状态迁移

名册行新增一列来源，值是一个封闭集合；运营者的写与账户的写各走一条迁移，来源由迁移写入，恢复只在来源是账户时发生。

**采纳**，见决策。

## 决策

采纳：名册行新增停用来源 `DisabledBy`，`Tenant` 携带它；来源的取值是一个封闭集合，`DisabledByOperator` 是零值，`DisabledByAccount` 是另一个取值。

**零值读作运营者停用。** 一行没有写过来源，或写入了本版本不认识的取值，都读作运营者停用：一次原因不明的停用不得被任何自动路径撤销。既有的停用行只有运营者一个来源，零值对它们是准确的。

**运营者的路径是 `SetStatus`，它记来源。** 写停用时把来源写成 `DisabledByOperator`，即便那一行已经是停用——运营者重新声明了一次决定，来源随之归运营者；写启用时把来源清回零值。已删除的行以 `ErrTenantDeleted` 拒绝（[ADR-tenant-deletion](adr-tenant-deletion.md)）。

**账户联动的路径是 `SetStatusByAccount`，它只在来源允许时写。** 写停用只在那一行在册时生效，来源写 `DisabledByAccount`；写启用只在那一行停用且来源是 `DisabledByAccount` 时生效，来源清回零值。其余情形什么也不写，返回 nil：运营者造成的停用原样留着，重复的调用不改变任何东西。已删除的行同样以 `ErrTenantDeleted` 拒绝。

**来源只能由状态迁移写。** `Put` 与 `Create` 接受零值与 `DisabledByOperator`，遇到 `DisabledByAccount` 以 `ErrInvalidTenant` 拒绝：账户造成的停用只能经 `SetStatusByAccount` 记下，否则一个登记入口就能造出一条自动恢复的停用。

**判据在名册里。** 宿主调 `SetStatusByAccount` 就能得到这条性质，不必自己先读状态、再决定写什么；第二个宿主重复的是调用，不是规则。

**管理面的视图渲染来源。** 停用的租户在视图里带 `disabledBy`（`operator` 或 `account`），其余状态不带（[tenant.admin](../design/modules/tenant/design-tenant-admin.md)）。

## 后果

- **名册的状态迁移从一个方法变成两个。** 宿主用错一个不报错：运营者的路径会把一次账户造成的停用变成运营者停用，账户恢复从此不再撤销它；账户的路径写不动一条运营者停用的租户，宿主据此以为恢复已经发生。
- **名册表多一列。** 迁移要改表，既有行读作运营者停用，不需要回填。
- **一次没有改状态的运营者停用没有状态上的痕迹。** 运营者对一个已停用的租户再点一次停用，来源换成运营者，其余不变；能看出这次动作的是管理面自己写的强制档审计行。
- **`SetStatusByAccount` 的 nil 分不出"撤销了"与"没有可撤销的"。** 钩子不需要这个区分，但一个想报告结果的调用方要另读那一行。
- **来源只回答"谁要它停用"，不回答"为什么"。** 运营者为什么停用，由动作记录与审计行回答。

## 失效条件

若产品后来要求"账户停用期间运营者也不能启用租户"，单列来源表达不了这条规则，要与两列标记重新比较。判据是运营者的启用是否必须看另一条停用是否还在。
