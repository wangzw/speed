# 用户名一经写入不可删除、不可更换

## 背景

用户名是账户持有并用于口令登录的名字，写入时只按断言渠道记账，没有邮箱或手机那样的所有权证明（[ADR-authn-selfservice-identifier](adr-authn-selfservice-identifier.md)）。每个用户账户在建立时即持有用户名（REQ-account-060），一个账户至多持有一个用户名（REQ-account-037），用户名因此是账户在人群中的可读标识。服务账户以服务密钥登录，不受用户名的要求；本记录只约束用户账户的用户名。

用户名没有所有权可证。一旦被释放，任何能经写入面写用户名的人都可以取用同一个字符串，系统无法区分后来取用它的人与原来的持有人。对外部引用、人对人的识别与支持记录而言，同一个用户名先后属于两个不同的人，就是把两段历史接到一起。

删除标识的现有规则只保护最后一个登录名：带口令凭据的账户删除后仍须保留至少一个登录名，口令才不会失去可用的登录对象（REQ-account-044，[ADR-authn-login-identifier](adr-authn-login-identifier.md)）。账户还有另一个登录名时，这条规则不阻止删除用户名，用户名随即释放。改名因此只能是先删除再添加，删除与添加之间账户没有用户名，旧名在删除之后即可被别的账户占用。

需要成立的条件：

- **可读标识在账户存续期内稳定。** 人群与外部系统按用户名识别一个账户；账户还在时，这个名字不能换到另一个人身上。
- **写入面不能留下空档。** 删除与添加是两次写入；直接调用 API、并发请求与客户端中断都能停在两者之间。
- **账户整体删除是既有终态。** 删除账户抹除个人数据、删除标识并留下墓碑，账户标识在生命周期内稳定（[ADR-authn-accounts](adr-authn-accounts.md)）；这是结束一个账户的既有操作。
- **显示名另有出口。** 显示名可改，昵称式的自我呈现不必落在用户名上。
- **管理面与账户面共用删除接缝。** 两面都经 `pkg/authn/account/admin.go` 的 `RemoveIdentifier` 删标识，拒绝的形状必须一致。

## 考虑过的选项

### 删除后再添加实现换名

允许账户先删除用户名，再写入一个新用户名；删除受最后登录名保护约束，添加走现有的规范化、保留用户名与唯一性规则。

**否决**：删除与添加之间用户名不存在，账户重新落回「没有用户名」的状态；直接调用 API、并发请求与客户端中断都能把这个中间状态留下，每一处读取与写入面又要为没有用户名的账户保留分支。旧名在删除后立即释放，别的账户可以取用，对外引用与人际识别随之从原持有人转到新持有人，而系统无法分辨两者。

### 新增显式改名操作

在账户面与管理面提供改名，服务端在一个事务里把旧用户名换成新用户名。

**否决**：改名后的旧字符串要么释放，要么永久保留为别名。释放与删除后再添加有同一后果：旧名可被别的账户取用，引用转移。永久保留别名，即允许一个账户持有多个名字，与「至多一个用户名」冲突；每次按用户名查找都要解析别名，别名集合只增不减，用户名作为可读标识的唯一性随之消失。用户名没有所有权证明，改名也无法证明新名字仍属于同一个人。

### 只保护最后一个登录名，允许在还有别的登录名时删除用户名

沿用现有的登录名数量规则，只在删除后账户不再剩下任何登录名时拒绝。

**否决**：账户只要还有一个选作登录方式的邮箱，就可以删掉用户名，用户名在账户存续期内仍然可移除、可释放、可被别的账户取用，本决定要成立的性质不再成立。删除后再添加的换名路径对还有另一个登录名的账户照常打开，其中的空档与引用转移一并回来。

### 只允许管理面删除或改写用户名作为运维补救

账户面无此操作，管理面保留删除用户名或在建号后修正用户名的能力。

**否决**：管理面改写的后果与用户改名相同：释放旧名可被别的账户取用，保留别名则与「至多一个用户名」冲突。把例外留给管理面，使「用户名不可变」变成取决于调用方身份的条件，而不是账户的性质；新增一条只对运维开放的改写面，还要在审计、界面与测试上各维护一份。拼写错误与不当用户名的补救是删除账户后重建，预置账户在首次使用前即可以这样做。

### 用户名一经写入即不可删除、不可更换

**采纳**，见决策。

## 决策

采纳：**用户名一经写入，在账户存续期内不可删除、不可更换。删除用户名在账户面与管理面都返回 `authn.ErrUsernameImmutable`，对外答 409 `username-immutable`，删除不生效。没有改名操作。删除账户是唯一的退出路径，不受此限。**

- **删除被拒。** `pkg/authn/account/admin.go` 的 `RemoveIdentifier` 删到用户名时，在事务内返回 `pkg/authn/errors.go` 的 `ErrUsernameImmutable`，删除回滚；账户面与管理面把该哨兵映射为同一个 409 `username-immutable`。该拒绝先于最后登录名规则（REQ-account-044），与其他标识删除的拒绝码可区分。
- **没有改名面。** 账户面不提供删除用户名或换用户名的入口，管理面不提供改用户名的操作；两面的标识列表照常列出用户名，但不给出可删除或可改写的操作。
- **全部写入面适用同一约束。** 自助注册、首登开户、邀请受理、管理面预置、初始装配与导入写入的用户名，在写入之后都不能由任何一面删除或替换；用户名只写一次。
- **账户删除不受此限。** 删除账户照常抹除个人数据与标识、留下墓碑，不经过用户名不可变的判定。
- **显示名承担可改的自我呈现。** 昵称、称呼一类可改的名字落在显示名上，不落在用户名上。
- 错误码的映射、路由与界面文案由账户、认证与管理面的设计文档承载，本记录不重述。

## 后果

用户名在账户存续期内是可读且稳定的标识：外部引用与人对人的识别不会指向另一个账户；账户不会经正常写入停在「没有用户名」的状态，读取面不必为用户名的缺失保留分支。删除标识的接口只有一条路径会因用户名而拒绝，判据是标识的类型，不是账户还剩几个登录名。

最后登录名保护保留，现在只有选作登录方式的邮箱可能触发它：正常写入的账户总有用户名，删掉邮箱后用户名仍是登录名。规则只在绕过写入面、账户没有用户名的行上触发，覆盖不到普通路径（REQ-account-044）。

**接受的代价：**

- **用户选错名字无法更换。** 用户名在写入时即定型，拼写错误、误用他人名字或不再喜欢的名字都无法由持有人改正；改名需求只能通过删除账户满足。删除账户是终态，个人数据与标识被抹除，会话、因素、成员关系与外部绑定一并清除，为换一个名字付出整个账户。
- **用户名作为永久公开标识，昵称式改名只能落在显示名上。** 界面不提供修改用户名的入口；经直接请求修改仍得到 409 `username-immutable`，界面要把它说明为用户名不可更换，而不是取值冲突。每一个会开户的写入面都必须在写入之前说明这一点。显示名是可改的，但它是另一项资料，不是登录名。
- **管理面也不能就地修正。** 管理员不能改正拼写错误或不当用户名；补救是删除账户后重建，预置账户在首次使用前可以这样做。按先删除再添加实现换名的运维脚本与本规则冲突，要改为删除后重建。
- **删除账户释放用户名。** 删除账户抹除标识行，墓碑只保留账户标识；用户名不再被任何账户持有，新账户可以取用同一个字符串，人群记得的旧名可能指向新的持有人。系统的稳定性承诺绑定在账户标识上，不绑定在用户名上；已删除账户的用户名不被永久保留。
- **最后登录名规则退回纵深防御。** 正常写入的账户不可能通过删除邮箱触发该规则，也不可能通过删除用户名触发；它只在绕过写入面的行上生效，测试与文档需要写明它覆盖的不是普通路径，否则会被误读为普通账户的约束。
- **每条写入路径都要在前端去掉删除与改名的入口。** 账户页与管理页不能再渲染用户名的删除操作，改名一类的表单不出现；前后端各自维护这份判断，前端漏一处就给出必然失败的入口，后端仍是权威拒绝。
- **拒绝码多一类。** 客户端要把 409 `username-immutable` 与 `username-taken`、`username-reserved`、`username-invalid` 及 `login-identifier-required` 分开呈现，它说明的是操作不被允许，不是取值冲突或缺少登录名。

## 失效条件

- 用户名被用作需要可回收或可改写的寻址键，例如按用户名路由的对外地址，且改名后旧地址仍须可用；永久标识与可改写寻址不能同时由「存续期内不可更换」满足，需要改为别名或重定向。
- 出现一种无需删除账户就能证明新用户名与旧用户名属于同一个人的机制，使释放旧名不会把引用转移给他人；删除后再添加与显式改名要重新与不可变比较。
- 账户删除不再抹除标识、用户名随墓碑永久保留；「删除账户释放用户名」的代价消失，但删除也只是把释放换成了永久别名，本决定与别名选项要重新权衡。
- 用户名获得所有权证明，例如引入与邮箱验证码相当的所有权核验；释放与改名所依赖的风险模型改变，不可变的依据要重新裁定。
