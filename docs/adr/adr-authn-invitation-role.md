# 邀请授予一个角色，接受与角色绑定同处一个事务

## 背景

邀请已经是一条待兑现的成员关系授予（REQ-tenancy-011、[ADR-authn-invitation](adr-authn-invitation.md)）。新成员加入组织后通常还需要一个角色，而这条授予没有携带角色的位置：管理员只能先让人接受邀请，再在成员面板里绑定角色。两次动作之间，受邀人已是成员却没有角色，而第二次动作可能失败、可能被遗忘。

角色不是管理员可以任意发放的值。租户管理面的绑定写受一条防提权规则约束：调用方只能授予自己持有的权限（[design-authz](../design/modules/design-authz.md)）。邀请是另一条发放角色的路径，若它不受同一条规则约束，租户管理员可以借一条邀请把高于自己的角色发给别人，绑定路由的约束形同虚设。邀请的签发者与接受者分处两个信任级，角色因此在签发时判定、在接受时复核。

邀请模块不 import 授权功能目录：它不知道角色、授予与绑定的表，也不该知道。角色的判定与绑定写必须由授权模块交付，而邀请模块只能经根包声明的接口取用。

一次接受要同时写下邀请的占用、成员关系与角色绑定，而这三张表分属邀请、账户与授权三个模块。三个写必须共享接受自己开的同一个事务：邀请行由本模块占用，成员关系经账户模块的事务内接口写，角色绑定经授权模块的事务内接口写。数据库是单写库，角色的复核读策略表，因此它在事务之外完成。

## 考虑过的选项

### 邀请只授成员，角色由接受后的另一次绑定写入

接受成功后，前端或管理员再调用一次绑定接口。采用它意味着邀请的状态机不变，角色的判定完全留在绑定路由。代价是邀请的兑现与角色成为两次独立动作：接受完成而绑定失败时，受邀人在组织里没有角色，界面无法把这两件事当成一次授予；管理员还要在成员面板里找到刚加入的人再操作一次。

**否决**：邀请要表达的是“以什么身份加入”，成员关系与角色是同一个授予的两半；拆成两次动作使其中一半可以单独失败，而且失败之后没有任何东西记得还欠这一半。

### 角色只记在邀请上，接受仍只写成员关系

邀请携带角色，但接受只写成员行，角色留给后续一次读或一次任务去补。采用它意味着接受路径不变，角色成为一个可以延迟兑现的字段。代价是“邀请已接受”与“角色已绑定”之间有一个窗口，窗口里受邀人看到的是没有角色的成员；补写失败时没有第二次机会，因为邀请已经终态。

**否决**：把角色放进邀请却不随接受兑现，只是把两次动作换成了一次动作加一个后台补偿，中间态仍然存在，而且更难观察。

### 在两次事务的补偿链上追加角色绑定

接受可以先用一个事务占用邀请行，再在另一个事务里写成员关系，成员关系失败时撤销邀请：这是不共享事务的两个模块之间的结算方式。把角色绑定追加到这条链上，意味着一次接受由三个阶段组成，失败可以落在“邀请已接受、成员关系未写”“成员关系已写、角色绑定未写”“角色绑定已写、邀请未回写”等不止一种中间态，每种中间态都要条件写与状态检查兜底，而角色可能已经绑给了一个邀请最终没有兑现的账户。

**否决**：中间态的数量随写入的次数增长，补偿链无法把一个授予表达成一次事实；防提权判定与绑定写在同一次接受里，拆分后没有任何东西记得还欠后半段。

### 邀请模块直接写策略表

邀请模块在自己的事务里直接插入绑定行。采用它意味着接受天然是一个事务，不需要新的接口。代价是邀请模块要 import 授权功能目录的策略实现，复制角色的存在性、保留角色与平台域的拒绝规则，并且跳过 `Manager` 与 `TxManager` 对绑定写的检查；两处写绑定的代码会各自漂移。

**否决**：邀请模块与授权目录之间的依赖方向是固定的，认证不 import 授权；策略行的写入只有一处实现，邀请不能成为第二个写入口。

### 在邀请模块里复制一条子集规则

邀请模块自己读角色与授予，按调用方的持有集比较。采用它意味着不需要新的判定接口。代价是同一规则在租户管理面的绑定写与邀请里各有一份实现；角色的映射、无法映射的授予与读取失败的处理稍有不同，两条路径就会对“同一个角色能不能授予”给出不同答案。

**否决**：防提权规则必须只有一处实现。邀请经根包声明的判定接口取用，判定与绑定写都由授权模块交付。

### 邀请带一个角色，判定经根包接口，接受在一个事务里写三件事

一条邀请至多携带一个角色，空串表示不带。签发时，角色判定由根包声明的 `authn.InviteRolePolicy` 回答：调用方持有租户角色管理权限、角色存在、角色不是平台管理员、每条授予都在调用方的持有集内、宿主写保护放行；任一不满足即在写行之前拒绝。宿主命令签发时没有调用方账户，判定收窄为角色存在、不是平台管理员、写保护放行，因为宿主本就可以直接写绑定。接受时，同一个接口按邀请人此刻的成员关系与持有集复核角色的可授予条件，邀请人的账户状态另读一次；任一不满足即撤销邀请并拒绝接受，读取账户失败不撤销而答 503。宿主命令签发的邀请没有邀请人可复核，只核对角色仍存在；静态主体与宿主命令一样跳过账户状态检查，但仍走角色的可授予复核。接受在一个事务里占用邀请行、经账户模块的事务内接口写成员关系、经授权模块的事务内接口写角色绑定；三件事一起提交或一起回滚。每次接受写一条强制审计行。

**采纳**，见决策。

## 决策

**邀请可以携带一个角色，且只携带一个。** 角色是邀请行上的一个字段，空串表示不带；重发沿用原角色，待接受邀请的角色不可修改。不携带角色的邀请与既有行为完全一致。

**签发时的角色判定是防提权规则的复用。** 角色判定由 `authn.InviteRolePolicy.Grantable` 回答，由 `authz.policy` 实现并交付。判定包含租户管理面绑定写的全部规则：角色不是 `platform-admin`、调用方持有 `authz.tenant.role.manage`、角色在该租户存在、角色的每条授予都在调用方的持有集内、宿主 `WriteGuard` 放行。权限先于角色名判定，所以没有角色管理权限的调用方对存在与不存在的角色得到同一答案，无法借两种应答探出角色名。子集规则只有一处实现（`Manager.RoleSubsetHeld`），绑定路由与邀请共用它。签发者不持有角色管理权限答 403 `forbidden`，角色不存在答 400 `invitation-role-unknown`，其余越权答 403 `invitation-role-protected`。宿主命令没有调用方账户，判定收窄为角色存在、不是 `platform-admin`、写保护放行；宿主本就可以直接绑定角色，经邀请发放同一种授予不改变它的权限。不带角色的签发不需要该能力；带角色而装配没有它时，签发失败关闭。

**接受时的角色复核判实际的可授予条件。** `authn.InviteRolePolicy.StillGrantable` 回答邀请人此刻是否仍是该租户的活跃成员、是否仍持有 `authz.tenant.role.manage`、是否仍持有角色的每条授予，以及角色是否仍存在、是否仍不是 `platform-admin`。成员关系要单独读：成员被停用后绑定保留，只看持有集会漏掉邀请人已经离开。邀请人的账户状态另读一次：账户被停用或已不存在时同样撤销，因为账户级停用保留成员关系与绑定，只有账户状态能看见；读邀请人账户失败不是拒绝，邀请保持待接受，接受答 503。静态主体（`static.` 前缀，部署配置的凭据表账户）跳过账户状态检查但仍走角色的可授予复核：它的权限来自部署配置，移除须改配置并重启，按账户库判定会把它签发的邀请全部误撤销。宿主写保护不在复核之内：它约束管理员发起的绑定写，接受兑现的是签发时已经放行的授予。任一不满足即撤销邀请并答终态拒绝，成员关系与绑定都不写，撤销本身写一条审计行；宿主命令签发、没有邀请人的邀请只核对角色存在。复核在事务之前完成，因为它读策略表的另一条连接，单写库上会等一个不属于它的事务。

**接受是一个事务，跨三个模块。** 邀请行由本模块的条件写占用（状态仍为待接受、未过期、令牌摘要仍是所呈令牌的），成员关系经 `provisioning.MembershipWriter.PutJoiningTx` 写，角色绑定经 `provisioning.RoleBinder.BindRoleTx` 写，三者共享接受自己开的 `*gorm.DB`。任一步失败整体回滚：邀请仍是待接受，成员关系与绑定都不写。两个事务内写交回的成员关系事件与策略快照重读，在接受提交之后由本模块运行。接受只有这一条写路径，事务之外没有补偿步骤。

**每次接受写一条强制审计行。** `authn.invitation.accept` 在事务之前写入，明细带租户、角色（有就写）与邀请人；审计行写不进即不接受。签发审计的明细也带角色。

## 后果

- 邀请可以在一次动作里表达“以某个角色加入”，接受成功后受邀人的成员关系与角色同时成立；管理端与受邀人页面只需读邀请的角色字段。
- 角色的判定与绑定写只有一处实现。`Manager` 的接口增加 `RoleSubsetHeld`，租户管理面的绑定写与邀请的角色判定共用它；两个调用方各自把拒绝映射成自己的问题码。
- 邀请模块与授权目录之间的依赖方向不变：邀请经根包声明的两个接口取用能力，不 import 授权目录；装配没有授权模块时，不带角色的邀请照常工作，带角色的邀请失败关闭。
- 接受的事务跨越三张表，由接受的一方拥有。数据库必须支持这三张表上的同一事务；单写库上，角色的复核必须在事务之外完成，否则会等待自己。
- 角色在签发之后可以被删除或被削弱。接受时复核失败会把邀请撤销，受邀人看到的是“邀请已撤销”而不是一个带残缺角色的成员关系；邀请人需要重新签发。
- 邀请人失去一条授予之后，已经发出的邀请不能再被兑现，即使受邀人已经证明地址并持有链接。这是防提权的代价：角色的可授予性以接受那一刻的持有集为准，不以签发时为准。
- 宿主命令可以签发带角色的邀请，判定只覆盖角色自身与写保护；这类邀请没有邀请人可复核，接受时只核对角色仍存在。宿主因此可以把一条邀请发出去，而角色在签发之后被删除时这张邀请会在接受时被撤销。
- 静态主体的权限来自部署配置，移除须改配置并重启，所以它的邀请跳过账户状态检查；被移出配置的静态主体此前签发的待接受邀请仍可授出角色，直到过期或被手动撤销。demo 的 `(*tenancyProduct).IsMember`（`starters/demo/server/tenancy.go`）对任何 `static.` 主体答真，同一个理由。
- 接受的三次写共享一个事务，成员关系写永久失败时邀请保持待接受，每次重试都会再失败一次；没有后台补偿把它收尾，邀请人只能撤销后重新签发。
- 每次接受多一条强制审计行，复核失败触发的撤销另写一条尽力档撤销审计行；审计不可用时接受不可用，这是既有强制档动作的一致规则。

## 失效条件

若一条邀请需要同时授予多个角色，或角色需要在签发时冻结其授予集而不是在接受时复核，本决策不成立：前者要把角色字段改成集合，后者要给角色一个版本并在接受时按版本判定，接受的事务里也要多一次版本核对。

若接受不能再跨模块共享一个事务（例如策略数据迁到另一个不接受同一事务的存储），本决策不成立：届时需要一条可重试的补偿协议，并接受“邀请已接受、绑定未写”的中间态，而不是把三件事当成一个授予。
