# 邀请以自持状态与不透明令牌成立

## 背景

成员关系已经声明邀请这一个来源：`Membership.Source` 的取值域是 `admin`、`jit:<提供方标识>`、`invite`、`import`（`pkg/authn/internal/model/directory.go` `Membership.Source`），而没有任何地方生成 `invite`。一条成员授予由管理员发起、经被邀请人接受后才成立（REQ-tenancy-011、REQ-tenancy-017）；这条路径没有落点。

账户写入接口接不住它。`AccountAdmin.Create` 要求地址「已经过验证」，且它的模型里没有可放待验证行的行（`pkg/authn/account.go` `AccountAdmin`、`pkg/authn/internal/model/directory.go` `CreateAccount`）：一个账户要么已经成立，要么不存在，没有「已记下、等某人来认领」的中间态。

接受一侧的身份不等于被邀请地址的归属。被邀请人可以是任何已登录账户，签发者管理员同样持有那枚令牌；只凭令牌出示，无法区分「受邀人本人」与「拿到同一链接的其他人」。接受因此需要一个已登录账户，并且该账户自己证明被邀请地址属于自己。邀请的签发端是已授权、已认证的管理动作，接受端是一个必须自己完成邮箱证明的普通账户，两端分处不同的信任级。

接受链接的落点由宿主的前端提供，不在接受路由上。签发进程不知道宿主把接受页放在哪个来源，也不该从一次请求的 `Host` 推出它：那个值由代理与客户端决定，而被邀请人点开的必须是宿主部署的落地页。链接因此需要一个配置给出的绝对来源。

投递与签发分属两个关注点。签发已经完成时，链接已经在应答里交出；一次通知发不出去，不能让一条已经成立的邀请变成一次失败的签发。反过来，投递也不该把签发拖进一条队列：签发路径要立即回答这条邀请是否成立。

## 考虑过的选项

### 待接受态落在账户表里

把一条邀请表示成账户表里的一行，状态为「待接受」，接受时把它激活。采用它意味着账户表同时承载身份与授予，且 `CreateAccount` 的验证前提被一条新的中间态绕过。

**否决**：`AccountAdmin.Create` 没有待验证态，是账户模型自洽的一部分——账户的地址一经存在就是已验证的。为邀请在账户表里开一个中间态，会把「等某人来认领的授予」混进身份存储，并使账户表的每一处读写都要区分这两种行。

### 署名令牌作接受凭据

接受令牌取 `pkg/authn/token` 的署名令牌形态（JWT，[REF-rfc7519](../references.md)，签名密钥与 JWKS 已就位，[REF-rfc7517](../references.md)），把邀请标识与租户写进声明，接受时验签读出。采用它意味着接受不需要为读凭据而查库。

**否决**：署名令牌的密钥集是身份令牌的密钥集，其公钥经 JWKS 公开；一个署名邀请因此可被任何持有公钥者验签，而撤销一条邀请仍要落库改状态——验签省不掉那次查库，签名却引入一条密钥依赖，并把「邀请」这一用途塞进身份令牌的密钥。邀请的凭据只在签发它的那一处有效，不需要一个可离线验证的全局签名。

### 自持一张表与一枚不透明令牌，接受要求已登录账户自己证明被邀请地址

一条邀请是 `authn_invitations` 里的一行，带自己的状态与期限；接受令牌是 256 位随机串，只以 SHA-256 落表。签发、列表与撤销是一次管理动作：发起者是已认证的管理员，判定经根包的判定接口，动作与成员关系管理取同一个（`authn.membership.manage`）。接受要求一个已登录的账户，该账户必须持有一条与被邀请地址相同的已证明邮箱（规范化后比较）；令牌只授予加入，不证明地址归属，也不为任何人开户。自持的状态使签发与接受分处两个信任级，接受端的证明由账户自己的邮箱验证路径完成。

**采纳**，见决策。

### 投递只由签发者或宿主承担

邀请签发之后把链接交给签发者，本能力不发送任何消息。采用它意味着每条邀请都要由管理员复制链接、经自己的渠道转交，接受路径本身不受影响；已签发的邀请也没有「已送达」这一事实。

**否决**：邀请的常规动作是「发出邀请」，把每次都留给人工转交使这条能力在界面上的主路径不完整；链接仍由应答交出，自动通知不改变邀请的状态机，也不替签发者决定把谁拉进租户。投递因此做成可选的一段，而不是把通知并进邀请的状态机。

### 经发件箱异步投递

签发只落邀请行，另由一名后台消费者从发件箱取通知发送。采用它意味着投递可重试、签发路径不被载体延迟拖慢，并能记录投递尝试。

**否决**：邀请在签发时已经有效，链接已经在应答里；引入队列、消费者与重试记录是为一个不影响邀请成立的动作增加一条运行期依赖，而签发应答再也不能告诉调用方这次通知的结果。通知失败本来就只影响操作者是否还要手工转交，不构成重试的理由。

### 签发路径上同步、有界的可选通知

签发成功后，本模块经可选接口 `authn.InviteNotifier` 请一次通知，限时五秒；结果作为 `sent`、`failed` 或 `not_configured` 随签发应答交出。没有通知接口的装配答 `not_configured`；失败只记日志与一条尽力档审计，邀请照常成立、令牌照常交出。

**采纳**，见决策。渲染与投递由 `authn.invitemail` 承担：它把租户、接受链接与期限渲染成消息，交给 `pkg/mail.Sender` 的一个载体。绑定一个上限而不是重试，使一次坏载体最多让签发应答晚五秒。

### 从请求的 Host 推出接受落点

通知里的链接取当前请求的 scheme 与 `Host`，拼上接受页的路径。

**否决**：接受页是宿主前端的路由，不是签发 API 的来源；`Host` 可被客户端指定，也会被反向代理改写，照它生成链接会把被邀请人送到一个签发进程不认识的地方，而且这是一条可被请求头影响的安全面。落点因此是一个显式配置项。

### 由配置给出接受落点的绝对来源

配置项 `authn.invitemail.accept-base-url` 给出接受页所在的绝对 http/https 来源；通知的链接是 `<accept-base-url>/invitations/<令牌>`。值必须在启动时通过校验（绝对 URL、有主机、无查询与片段），末尾的 `/` 归一化掉；空值表示本部署不发邀请邮件。

**采纳**，见决策。路径由模块拼接、令牌按单个路径段转义，配置改不了接受路由的形状。

## 决策

邀请以一张自持状态与期限的表 `authn_invitations` 成立，接受凭一枚只以摘要留存的不透明一次性令牌兑现；待接受态不落账户表。签发、列表与撤销是一次管理动作，接受是已登录账户的动作，两者分处两个信任级；接受落下的成员行，`Membership.Source` 取 `invite`。

**令牌授予加入，不证明地址归属。** 接受要求一个已登录的账户，且该账户持有一条与被邀请地址规范化后相等的已证明邮箱标识；证明渠道必须是 `Verification.Proves` 为真的那一类（`email-code`、`sms-code`、`idp:<提供方标识>`），`invite`、`admin`、`import-unverified` 与 `self` 都不算。被邀请地址不必是该账户的登录方式，也不因接受而成为登录方式或默认联系地址。没有这条证明的账户得到 403 `invitation-email-unproved`，邀请保持待接受。接受从不新建账户，也不写标识；地址尚无账户时，当事人先登录并证明地址，再回到链接接受。签发者持有同一枚令牌，因此签发者单独不能完成一次接受。

**成员被停用或移除时，其待接受邀请被撤销。** 本模块订阅 `authn.membership.changed`：在 `suspended` 或 `removed` 发生时，把这个账户的邮箱在该租户下的待接受邀请置为已撤销，条件是状态仍为待接受。接受本身遇到停用的成员关系也答 409 `membership-inactive` 并撤销该行，所以事件漏掉的一条活令牌也不能复用。

签发成功后，本模块经可选接口 `authn.InviteNotifier` 请一次接受通知，限时五秒，把结果以 `sent`、`failed` 或 `not_configured` 随签发应答交出。投递失败不撤销邀请，也不改变 HTTP 状态；失败记日志并写一条尽力档 `authn.invitation.deliver` 审计行。**投递成功时应答不交出令牌**：收件地址已经握有链接，再交出明文只是多一份持有者；只有 `failed` 与 `not_configured` 两种结果让签发者仍需转交，应答才带一次令牌。通知的渲染与投递由 `authn.invitemail` 承担，它把租户、接受链接与期限渲染成消息后交给 `pkg/mail.Sender`。接受页的来源由配置项 `authn.invitemail.accept-base-url` 给出，空值表示本部署不发邀请邮件。令牌明文在签发或重发的应答里至多出现一次，落表的是摘要。

接口 `Invites` 与它的值类型、哨兵定义在 `pkg/authn/invite`，不随根包里其余认证接口放进 `pkg/authn`：根包已以 `Issued` 命名会话签发的结果，邀请签发的结果占不住同一个名字；`pkg/authn/invite` 与根包同属一个 Go module，取用者的依赖闭包不因此变化。

## 后果

- 邀请的状态机与期限由本能力持有，与账户的生命周期解耦；账户表不新增行态，接受也不走开户路径。
- 接受是一枚随机令牌的摘要查找，加一次身份与已证明邮箱的核对，加一次成员行写入；撤销是改状态，无需密钥轮换。
- `Membership.Source` 的 `invite` 取值自此有生成方；`authn.membership.changed` 事件携带该来源，停用与移除也经同一事件撤销待接受邀请。

**接受的代价：**

- **`invite` 不能作为地址归属的证明。** `Verification` 的封闭集保留 `invite` 这个取值（`pkg/authn/internal/model/directory.go` `VerifiedViaInvite`），但 `Verification.Proves` 对它为假：签发者持有同一枚令牌，令牌被出示不能说明邮箱属于接受人。接受因此依赖账户自己已有的 `email-code`、`sms-code` 或 `idp:<提供方标识>` 证明，邀请路径不再为任何人补写标识。
- **接受要求一个已登录账户。** 没有账户、或账户尚未证明被邀请地址时，接受不会替当事人开户，也不会代为证明；当事人必须先完成登录与邮箱验证。这把「收到链接就能加入」改成「收到链接并证明地址才能加入」。
- **投递成功时签发应答不交出令牌。** 收件地址已经握有链接，再在应答里交出明文就多一份持有者；代价是签发者无法从界面复制一条已经发出的链接，只能依赖通知或重发。
- **接受按不透明令牌做一次不带租户谓词的查找。** 接受者还没有该租户的成员归属，这一步是邀请模块唯一不按租户过滤的查询。
- **签发应答最多被通知拖慢五秒。** 通知在签发路径上同步调用，超时即按失败作答；签发因此不会无限期等一个不回应的载体。
- **投递结果是尽力而为，不是送达证明。** `sent` 只表示载体接受了这条消息，不表示收件箱收到、被打开或地址可达；`failed` 不撤销邀请，应答仍带令牌供签发者转交。没有重试、没有排队，一次失败就是这次通知的结局。
- **通知不是邀请成立的条件。** 没有通知接口、没有配置接受来源或载体失败时，邀请都照常成立；后两种情况下应答带一次令牌，`not_configured` 是这类部署的正常回答，不是错误。
- **接受来源是部署的事实。** `authn.invitemail.accept-base-url` 配错会把被邀请人送到错误的来源；模块只校验它是不是一个绝对 http/https URL，不核对那个来源是否真的提供接受页。
- **链接只存在于签发或重发的那一次应答与那封通知里。** 令牌明文至多出现一次，落表的是摘要，所以历史行没有可复制的链接；重发以一条新邀请取代旧行，旧链接立即失效，新链接只在新应答与新通知里出现。
- **转发链接不等于转让加入能力。** 第三人拿到链接仍然必须证明被邀请地址；邮箱被共享、被转发或被回收时，能证明该地址的账户就是受邀人，这是邮箱归属作为判据的边界。

## 失效条件

若接受需要在不再触达存储的前提下离线验证一条邀请（例如跨宿主、无共享存储地兑现），不透明令牌的摘要查找不成立，届时需要改回可验证的署名形态，并承担一条与身份令牌分开的密钥。

若邀请必须保证送达、可重试或可审计每一次投递尝试，签发路径上的同步尽力通知不成立，届时需要发件箱与消费者，签发应答也不再能给出这次投递的最终结果。

若部署无法事先知道接受页的来源（例如同一进程按请求服务多个前端来源），固定配置的 `accept-base-url` 不成立，届时需要一个受信任的来源清单或按租户配置的来源，而不是从请求头推导。

若接受必须在没有已登录账户、也没有被邀请地址证明的前提下完成（例如由宿主代办加入），本决策不成立，届时需要一条与令牌强度相称的带外身份凭据，而不是把令牌本身当作地址归属的证明。
