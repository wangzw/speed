# 所有者转移在目标确认后生效

## 背景

组织所有者把一个组织交给另一个成员，是一次不可轻易撤回的治理动作。若一次请求立即改写名册的所有者列，主动权完全在发起方：目标可能已经离开组织、账户已被停用，或根本不同意接手，而组织已经换主。原所有者保留成员关系与全部绑定，所以损失不是数据，而是「谁对组织负责」这件事被单方面改变。

这条动作同时跨三个存储：名册的所有者列、策略里的 tenant-admin 绑定、成员关系里的目标资格。三者必须一起成立或一起保持不变，而当前所有者与目标成员分属两个身份：发起者与接收者。平台员工也可能代表组织发起，但它不是所有者，不能代替目标答应。

本记录要定的是：所有权在什么时刻改变，待处理状态记在哪里，目标凭什么身份处理它，以及通知走哪条渠道。

## 考虑过的选项

### 保持即刻转移

调用方一发起就写所有者列，目标没有拒绝的机会。

**否决**：目标可能已不是活跃成员、账户已停用或不愿接手，而组织已经换主；原所有者用过期页面继续写入的竞态只能靠预期所有者字段补，补不了「目标没同意」这件事。治理动作的主动权应当落在接收者一侧。

### 邀请式一次性令牌

给目标发一个一次性链接，点开即接受，待处理状态由令牌本身承载。

**否决**：令牌要落库、要过期、要撤销，等于再造一张与请求同构的表；而目标的身份已经由会话给出，链接不增加任何保证，只增加一条可被转发的凭证。目标页需要列出多条请求、显示终态，令牌模型回答不了「我名下有哪些待处理请求」。

### 纯事件驱动

发起时只发一个事件，由消费者在事件里完成转移。

**否决**：事件是提交之后的异步补偿，不能承载「目标确认」这一步；把转移写成事件消费者，会把一条需要同步校验（请求者仍是所有者、目标仍是活跃成员）的事务拆到没有事务边界的地方。

### 待处理记录归 `tenant.ownership`，目标面是账户级接口

新建 `tenant_owner_transfers` 表记录待处理与已结束的请求；发起只写这张表，确认在一条事务里重新校验并写所有者列；目标凭自己的身份在 `/api/v1/auth/me` 下处理；通知走站内信。

**采纳**，见决策。

## 决策

采纳：**所有权转移在目标确认后生效，待处理记录归 `tenant.ownership`，目标面是账户级接口，通知只走站内信。**

- **只有一个写路径改变所有权。** 名册 `owner_account` 的公开写入路径是确认事务。平台与租户两个面的转移入口是 `POST .../owner/requests`，请求侧由 `OrganizationWriter` 承担，确认由 `OwnershipTarget.ConfirmTransfer` 承担。
- **待处理记录是一张表。** `tenant_owner_transfers` 归 `tenant.ownership`，是该模块唯一持有的表；HTTP 面仍全部留在 `tenant.admin`。状态是闭集：pending、confirmed、declined、cancelled、expired。同一组织同时最多一条 pending，由部分唯一索引仲裁，不做「后来者覆盖」。
- **确认是唯一写所有者列的事务。** 确认在租户锁内重读请求，校验请求者仍是所有者、目标仍是活跃成员，授予 tenant-admin、写所有者列、把请求标为 confirmed；任一步失败整条回滚。原所有者保留成员关系与全部绑定。
- **目标是账户级接口。** 目标只需要自己的身份，不要求组织资料读取权限，也不要求当前租户就是该组织。非目标账户与不存在的请求得到相同的不存在结果。
- **到期是派生的。** 固定窗口过后由读写路径用条件更新结算为 expired，不新增定时任务；到期、拒绝与取消都不改变所有权。组织删除在同一事务里取消待处理请求。
- **表不内嵌租户模型。** 这张表是组织生命周期的元数据，目标的确认请求没有租户上下文；代之以「存储的每个方法都显式携带租户或目标谓词，不提供无谓词列出全部」的硬约束。
- **通知只走站内信。** `in_app` 恒可用，目标不保证有已验证邮箱；目标页是权威入口，站内信只是提示。首版不发送邮件。

## 后果

所有权转移的主动权落在接收者一侧：目标不确认，组织不换主；拒绝、取消与到期都留下组织原样。发起方仍能看到待处理状态并取消，平台员工仍能发起与取消，但都不能替目标答应。

**接受的代价：**

- **一次破坏性接缝变更。** `OrganizationWriter` 的方法集是 `RequestTransfer`、`CancelTransfer` 与 `PendingTransfer`；`OwnershipTarget` 的方法集是 `ConfirmTransfer`、`DeclineTransfer`、`PendingTransfersFor` 与 `TransferFor`。平台与租户两个面的转移入口是 `POST .../owner/requests`，目标面在 `/api/v1/auth/me/owner-transfer-requests` 下。宿主自实现的接缝要补齐这些方法，生成物（OpenAPI 片段、合并契约、前端 SDK）按新 operation 同批重生成。
- **多一张表与一套迁移。** `tenant.ownership` 从「不持表」变为「恰好持一张表」，SQLite 与 PostgreSQL 各有一份迁移；这张表不随租户过滤，谓词由存储方法自己保证。
- **目标需要一个入口。** 目标页 `/transfer-requests` 是账户级路由，宿主要在账户菜单提供入口并把通知的 `link` 导航过去；收件箱行属于组织所在租户，目标在别的租户时看不到站内信，只能走目标页。
- **一个固定窗口。** 七天内不确认即到期，窗口是模块常量，不可配置；需要更长的窗口要改代码。
- **通知是 best effort。** 派发面缺席或派发失败只记 Warn，不阻止请求或确认；首版不发送到期通知。
- **确认需要已验证账户。** 未证明邮箱的自助注册账户不能接手组织，答 403 `contact-required`；拒绝不受这条限制。

## 失效条件

以下情形出现时，本决策需要重议：

- **若产品要求转移在发起后立即生效、目标事后追认**，则确认事务与待处理表都要重做，主动权回到发起方。
- **若目标必须在多个组织之间批量处理请求**，则账户级列表的分页、筛选与批量动作要成为设计的一部分。
- **若通知需要邮件或短信渠道**，应新增独立类型并规定目标地址解析与「无地址则跳过」的规则，而不是把渠道塞进当前类型。
- **若平台员工需要代替目标确认**，则「确认只凭目标身份」的前提不再成立，权限与审计口径要一起重议。
