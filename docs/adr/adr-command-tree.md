# 命令树由宿主静态定义，模块按层纳入

## 背景

一个服务端程序需要子命令：应用迁移、初始化工作目录、打印版本，都是与「启动并提供服务」并列的运行方式，而不是它的一部分。

子命令不只是命令行上多一个词。它决定这次运行装配哪些模块：迁移不要求遥测后端可达（REQ-deployment-016），它的帮助输出不展示遥测的参数，也不会因为遥测的某个必填项没给而启动不起来。因此子命令同时决定了命令行的样子和配置的校验范围。

这与「装配由配置驱动」并不冲突：子命令本身就是一个配置值，来源是命令行。命令行上的一个词决定这次运行纳入哪些模块，配置则决定这些模块各自拿到什么输入。

`main` 开始之后、模块装配开始之前存在一段无人认领的位置。没有子命令时它是空的——宿主只需驱动一次生命周期；有子命令之后，「这次运行执行什么动作、装配哪些模块」必须在这里被决定。

## 考虑过的选项

### 模块贡献自己的子命令

模块以资源声明它支持的子命令，注册表收集后组装成命令树。迁移命令由数据库模块贡献，实现因而留在它所属的模块里。

**否决**：模块是被装配的对象，而命令树决定装配如何被发起，让模块填这个位置是倒因为果。更实际的风险是，可用集由 import 决定而不由宿主声明，宿主的某个间接依赖引入的模块同样会进入可用集、宿主未必知情；命令树是人机界面，它有什么不该由 import 图决定。

### 独立的命令行包

命令树的组装独立成一个包，与配置分开。

**否决**：命令行参数是配置的最高覆盖层，输入项清单收集一次同时供给命令行与配置源的解析。拆成两个包会把一件事切成两半，中间还要维持一个接口。若进一步做成模块，则需要注册表为它开第二处特殊时机。

### 命令树由配置文件定义

命令与它纳入的模块写在配置文件里，宿主不写命令树。

**否决**：配置定位符本身来自命令行，命令行的解析因而早于配置文件的读取；而配置文件的校验范围又由选中的命令决定。两者互为前提。

### 命令声明所需能力，由框架计算依赖闭包

命令不列举模块，只声明它需要哪些功能，框架按功能的提供者与依赖关系算出参与的模块集。

**否决**：一项功能的提供者有多个实现，选中哪个由宿主在命令树上点名，而点名的结果又决定配置的校验范围。按静态声明而非启用结果计算闭包可以打破这个循环，但得到的集合与显式列举相比并不更小，却让「这次装配了什么」不再能从宿主代码上直接读出。

### 宿主静态定义命令树，每个节点列举纳入的模块

`main` 写出命令树，并为每个命令节点列举该层纳入哪些模块。模块不知道命令的存在。

**采纳**，见决策。

## 决策

采纳：命令树由宿主在 `main` 中静态定义，命令树的每个节点列举该层纳入的模块；模块不声明、也无从知道自己出现在哪些命令下。

- **设计哪些子命令是宿主的事。** 需要某个模块的能力的命令，由宿主在它的执行路径里取用该能力；模块只导出可被取用的东西。
- **每个节点列举该层纳入的模块，纳入时一并引入它们的依赖。** 宿主也可以指定纳入全部可用模块。
- **纳入即进入参与集，不保证启动。** 被纳入的模块一律进入参与集、有资格表态；它是否进入启用集，由模块在 `Prepare` 中依据自己的配置决定，退让也可来自排他消解（[ADR-module-enablement](adr-module-enablement.md)）。
- **解析按命令树逐层推进，不是单一阶段。** 每一层纳入该层的模块、收集它们的输入项、解析该层的命令行，得到下一级子命令；子命令可以再有子命令。递归终止于叶子节点，此时命令树决定的参与集才完整；预置了实例的模块在驱动开始时并入参与集（[ADR-supplied-instance](adr-supplied-instance.md)）。
- **表态、启用消解、依赖校验与配置校验都发生在叶子节点**，且只对参与集内的模块进行。
- **配置源的 Schema 只有一份，不按命令切分。** 按命令切分的是校验的时机与范围，不是 Schema 本身。语法层面的失败当场报告；未知键的校验推迟到叶子节点。必填与类型不在那里扫描，而是各模块 `Decode` 自己那份配置时判定——扫描一遍完整清单会连这条命令没有纳入的模块一并判失败，而它们的必填项与这条命令无关。

每一层纳入哪些模块写在宿主代码里，因而整棵命令树连同各层的输入项在解析开始之前就是确定的，不存在运行期才出现的命令或参数。

## 后果

子命令成为一等概念，「启动并提供服务」只是其中一种运行方式。

一次运行的帮助输出、可用参数与必填项，都收敛到这条命令路径实际纳入的模块，与它无关的模块不出现、也不参与校验。

装配由配置驱动这一点没有被削弱：子命令是命令行给出的配置值，它扩大了配置的来源。**互斥的多个实现里用哪一个，由宿主决定：在命令树上点名，或为其中一个预置实例**，不由配置推断（[ADR-dependency-resolution](adr-dependency-resolution.md)、[ADR-supplied-instance](adr-supplied-instance.md)）。

**接受的代价：**

- 宿主要写出命令树并为每个节点列举模块，这部分样板随命令数量增长。**列举即承诺：写下的模块必须启动，配置不齐即启动失败，点名缺的是哪一项**（[ADR-module-enablement](adr-module-enablement.md)）。框架对宿主的要求因此比只驱动一次生命周期时高。
- 哪些模块支撑哪个命令，这项知识从模块转移到了宿主。新增一个模块若要参与某个既有命令，改的是宿主代码而不是模块自己。
- 配置源的未知键按完整 Schema 判定，而命令行参数与必填项按命令树决定的参与集判定，两者范围不同。这个不对称是有意的——一份配置源由各命令共用，按参与集判会让它在任何一个命令下都成为未知键——但它是这套规则中最容易被实现反的一处。
- 一项功能有多个候选实现时，帮助输出会列出全部候选的参数，尽管最终只有一个被启用。
- **「纳入全部可用模块」这一项让命令树决定的参与集重新成为 import 图的函数**，其中可能含有宿主并不知情的模块，而它决定帮助输出、可用参数与必填范围，全是人机界面。这与上面否决模块贡献命令时给出的理由同源。两者的区别在于它是宿主写下的一行明确选择，而不是一件它看不见的事；能不能接受由宿主自己判断，代价仍然记在这里。**纳入分级让它又重了一层**：被拉进参与集的模块必须启动，配置不齐即启动失败——一条 `IncludeAll` 的迁移命令因此启动不起来，而只纳入引擎的那条照常建立它该建的表（[ADR-command-tree-inclusion](adr-command-tree-inclusion.md)）。

## 失效条件

若某个命令所纳入的模块集合无法从宿主代码上静态写出——例如需要根据配置源的内容来决定装配哪些模块，而该配置源又只能在命令选定之后才知道位置——静态定义的前提不再成立，届时需要一种在解析过程中扩展命令树的形式。
