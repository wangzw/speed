# 语句级的记录跟着那条语句成败，请求级与事件级按 fail-open 处置，接缝返回错误

## 状态

已接受

## 背景

四条捕获通路里，三条挂在别人的路径上：请求级在请求路径上、事件级在订阅回调里、接缝级在调用方手里。它们与业务之间没有一层可以共同成败的东西——审计存储的一次故障若向上传播，审计存储的可用性就成了入口与总线的可用性，而那两处并不共享一件工作。

语句级不同：它挂在一条写语句上，而那条语句本身可能就在一件工作里。它可以另开一条连接把自己报出去，也可以写在那条语句的会话上、跟着它成败。这个选择决定了两件事——审计存储的故障会落到哪里，以及一个只允许单写者的引擎上会不会争锁。

语句级还有一格要单独回答。数据库模块经 `Open` 建出的额外连接装着同一批插件，却不施加迁移，它连着的库的 schema 由调用方保证，可以是只读副本、另一个系统的库或一次性的数据来源（[ADR-db-multiplicity-2026-09-14](adr-db-multiplicity-2026-09-14.md)）。那条连接上的写语句所在的库通常没有审计表，它与交付连接那个库之间也没有共同的事务。

## 考虑过的选项

### 三条通路一律另开连接、一律 fail-open

**否决**：语句级那一条会与调用方自开的事务争锁。本仓为两个方言写迁移，其中 SQLite 只有一个写者：业务写被拖住，审计写入以忙错失败，而它按 fail-open 被吞掉——审计行丢失且只有一行标准错误。别的引擎上不争锁，但一次随后回滚的业务写入已经留下了一条结果一列为成功值的审计行，即记下了一件没有发生的事。

### 四条通路一律 fail-closed

**否决**：请求级与事件级挂在别人的路径上，把审计存储的可用性变成入口与总线的可用性；而它们没有「同一条连接、同一件工作」这层关系可用，失败只能抛给一个与审计无关的调用方。

### 由宿主逐条通路、逐种情形配置

**否决**：组合数是通路与档位的乘积，每一格都要各自测试，而「这一条通路这一档、那一条通路那一档」在评审里说不清。

### 语句级跟着那条语句成败，其余三条 fail-open

**采纳**，见决策。

### 额外连接上的语句写进那个库自己的审计表

**否决**：审计轨迹劈成几处，哪一行落在哪个库不是任何东西能回答的——这与一次装配里不允许两个审计实现是同一个理由（[ADR-audit-packaging-2026-09-21](adr-audit-packaging-2026-09-21.md)）。那个库的 schema 归调用方，它可能属于另一个系统；缺表时那条连接上的每一条模型写语句都失败，宿主只剩绕开模型路径一条路。

### 额外连接上的语句不捕获

**否决**：那些写入确实发生了，不留痕也不报错，正是「以为有审计而实际没有」。

### 额外连接上的语句在提交之后写进交付库的审计表，按 fail-open 处置

**否决**：写入已经提交，审计行却可能写不进去，只留一行标准错误；「写不进记录的模型写入不发生」在额外连接上就此失守，而它是语句级区别于另外三条通路的那一条。

### 额外连接上的语句在提交之前写进交付库的审计表，写不进去令那条语句失败

**采纳**，见决策。

## 决策

采纳：**语句级那条通路的记录与那条语句是一件工作。** 写在那条语句自己的会话上：写审计表失败令那条语句失败，那条语句回滚也把那行一起带走——记下的因此是确实发生过的事，且只存在一条连接。

**额外连接上的语句，审计行写进交付连接那个库里的审计表**，经交付连接写出，写在那条语句提交之前；写不进去令那条语句失败，与交付连接上的语句同一个方向。它与那条语句不在一件工作里，两个库之间没有共同的事务可用。

**请求级与事件级按 fail-open 处置。** 写失败不进业务路径的返回值，业务照常完成。

**记录接缝返回错误。** 接缝是给调用方用的，一个愿意把自己的操作与审计写入绑在一起的调用方可以据返回值终止自己的操作。

**失败信号不经日志链。** 第一次写失败与随后的恢复各写一行标准错误，此后同一个故障不再写行；理由与日志模块报告自身失败时相同——报告链自身缺席或出问题时仍然可用。经日志链报的写法被否决：输出列表为空是合法配置，那条链可以整条不启用，而本模块最需要被看见的时刻正是一次写入失败。

## 后果

记录与它所记录的事实在语句级那条通路上同生共死；其余通路的失效方向不扩大业务的故障面。

**接受的代价：**

- **一次审计存储故障会让全部写语句失败。** 这是语句级那条选择的直接代价，也是它与另外三条的差别所在：宿主在有写流量的命令上装本模块，等于把那张表的可用性放进了写路径。
- **请求级与事件级有静默缺口。** 审计存储不可用期间它们照常放行；缺口只在那一行标准错误里可见，没有人会被自动通知。
- **信号只到标准错误，且一个故障只留两行。** 中间的过程无从得知；这两行不进任何日志目的地。
- **两处对同一次写入的读法不同。** 接缝返回的错误在一处是终止条件、在驱动的那两条通路上是可继续的信号。
- **失败的判定不区分原因。** 表不存在、连接断开、约束冲突都进同一处信号，宿主看不出该怎么修。
- **额外连接上的一条语句随后回滚时，它的审计行留在交付库里。** 记下的是一件没有发生的事——交付连接上那条选择要避开的正是它，而在两个库之间无从避开。
- **额外连接与交付连接指向同一个 SQLite 库时，那条语句的审计写入要等它自己持有的写锁**，等到驱动的忙等时限后令那条语句失败。
- **插件要分得出交付连接与额外连接，而它自己回答不了。** 插件实例在进程内被多个注册表共用、不持有状态，从一个句柄上读不出这个句柄的来历；回答要由建出额外连接的数据库模块给出。

## 失效条件

若出现一条合规要求规定审计不可用时业务必须全部停止，则驱动的那两条通路的 fail-open 不再成立，它们要与语句级取同一个方向。
