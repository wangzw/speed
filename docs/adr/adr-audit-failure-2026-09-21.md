# 语句级的记录跟着那条语句成败，请求级与事件级按 fail-open 处置，接缝返回错误

## 状态

已接受

## 背景

四条捕获通路里，三条挂在别人的路径上：请求级在请求路径上、事件级在订阅回调里、接缝级在调用方手里。它们与业务之间没有一层可以共同成败的东西——审计存储的一次故障若向上传播，审计存储的可用性就成了入口与总线的可用性，而那两处并不共享一件工作。

语句级不同：它挂在一条写语句上，而那条语句本身可能就在一件工作里。它可以另开一条连接把自己报出去，也可以写在那条语句的会话上、跟着它成败。这个选择决定了两件事——审计存储的故障会落到哪里，以及一个只允许单写者的引擎上会不会争锁。

语句级还有一格要单独回答。数据库模块经 `Open` 建出的额外连接装着同一批插件，却不施加迁移，它连着的库的 schema 由调用方保证，可以是只读副本、另一个系统的库或一次性的数据来源（[ADR-db-multiplicity-2026-09-14](adr-db-multiplicity-2026-09-14.md)）。那条连接上的写语句所在的库通常没有审计表，它与交付连接那个库之间也没有共同的事务。

额外连接也可能就连着交付库：同一个 SQLite 文件，或同一台 PostgreSQL 服务器上的同一个库。这时两者之间有共同的事务，语句自己的会话够得着交付库那张审计表。定位符说不准是不是这种情形：同一个库有多种写法——相对路径与绝对路径、链接、主机名与地址——而定位符的读法归数据库模块与驱动。引擎说得准：SQLite 答得出一条连接的主库放在哪个文件里（链接已解析），PostgreSQL 答得出服务器这一次启动的时刻、当前的库，以及一个表名在这条连接的搜索路径下解析到哪个关系。同一个库里，搜索路径不同的两条连接可以把同一个表名解析成两张表。

经交付连接写出的那一行，要另占交付连接池里的一条连接，单写者引擎上还要交付库的写锁，而它等的时候那条语句自己在另一个库上的事务还开着。调用方在交付句柄上开着一个占着写锁的事务——数据库模块默认以 `IMMEDIATE` 开启 SQLite 的事务，不以 `DEFERRED` 开启的事务从开启起就占着，读没读过、写没写过都一样——又在里面经额外连接写入时，这两样都由调用方自己占着，要到那条语句返回之后才放开；只开一条连接的库（内存库）上，连那条连接也取不到。额外连接指向交付库本身时，占着写锁的是那条语句自己。本模块另占一条连接写出的其余几行——接缝、事件级、请求级——在调用方的事务里调用或发布时处境相同，事件级与请求级还不随上下文取消。一行审计从交付给回调的会话上读不出调用方在别处持有的事务，Go 也不给出协程的身份：这种占用与别的写者的短暂占用，在它看来是同一回事。SQLite 的等锁发生在驱动里，由连接上的忙等时限决定，上下文结束打断不了它。数据库模块为这类另占连接的语句提供 `Connection`，在一个界内取连接，等锁照引擎自己的设置；它不打开 SQLite 共享缓存模式的定位符，那里的表锁等待连忙等时限也不看（[ADR-db-waits-2026-09-29](adr-db-waits-2026-09-29.md)）。

## 考虑过的选项

### 三条通路一律另开连接、一律 fail-open

**否决**：语句级那一条会与调用方自开的事务争锁。本仓为两个方言写迁移，其中 SQLite 只有一个写者：业务写被拖住，审计写入以忙错失败，而它按 fail-open 被吞掉——审计行丢失且只有一行标准错误。别的引擎上不争锁，但一次随后回滚的业务写入已经留下了一条结果一列为成功值的审计行，即记下了一件没有发生的事。

### 四条通路一律 fail-closed

**否决**：请求级与事件级挂在别人的路径上，把审计存储的可用性变成入口与总线的可用性；而它们没有「同一条连接、同一件工作」这层关系可用，失败只能抛给一个与审计无关的调用方。

### 由宿主逐条通路、逐种情形配置

**否决**：组合数是通路与档位的乘积，每一格都要各自测试，而「这一条通路这一档、那一条通路那一档」在评审里说不清。

### 语句级跟着那条语句成败，其余三条 fail-open

**采纳**，见决策。

### 额外连接上的语句写进那个库自己的审计表

**否决**：审计轨迹劈成几处，哪一行落在哪个库不是任何东西能回答的——这与一次装配里不允许两个审计实现是同一个理由（[ADR-audit-packaging-2026-09-21](adr-audit-packaging-2026-09-21.md)）。那个库的 schema 归调用方，它可能属于另一个系统；缺表时那条连接上的每一条模型写语句都失败，宿主只剩绕开模型路径一条路。

### 额外连接上的语句不捕获

**否决**：那些写入确实发生了，不留痕也不报错，正是「以为有审计而实际没有」。

### 额外连接上的语句在提交之后写进交付库的审计表，按 fail-open 处置

**否决**：写入已经提交，审计行却可能写不进去，只留一行标准错误；「写不进记录的模型写入不发生」在额外连接上就此失守，而它是语句级区别于另外三条通路的那一条。

### 额外连接上的语句在提交之前写进交付库的审计表，写不进去令那条语句失败

**采纳**，见决策。

### 额外连接连着交付库时，照样经交付连接写出

**否决**：单写者引擎上，那一行等的是那条语句自己占着的写锁，每一次这样的写入都等满界再失败，而写锁在界之后照样不会放开；另一个引擎上，那一行不在语句的事务里，语句回滚时留在表里——而这时两者本有共同的事务可用。

### 按定位符判定额外连接是否连着交付库

**否决**：同一个库有多种写法，按字面比较会漏认；要比得准，就得在本模块重写数据库模块与驱动对定位符的读法，两份读法随后各自演进。定位符也答不出表：PostgreSQL 上同一个库里，搜索路径决定同一个表名落在哪张表上。

### 额外连接上有审计表就写在语句自己的会话上

**否决**：有这张表不等于它就是交付库那张。一份拷贝、另一次运行的交付库都有它，行落进去，审计轨迹就劈成几处，与否决「额外连接上的语句写进那个库自己的审计表」是同一个理由。

### 由数据库模块在 `Open` 时认出交付库，让 `OpenedFrom` 不作答

**否决**：要回答的是这一行会落进哪张表，那张表与它的名字是本模块的；数据库模块只能回答连着哪个库，而同一个库里的同名表可以是两张。

### 问两条连接背后的引擎，连着的是同一张审计表时写在语句自己的会话上

**采纳**，见决策。

### 另占一条连接写出的行一直等到交付库收下

**否决**：在调用方的事务里写出的那一行等的是调用方自己。文件库上等满驱动的忙等时限才失败；只开一条连接的库上一直等到上下文结束，没有期限就永远等下去；事件级丢掉了发布方上下文的取消，连期限也救不了它。

### 交付库不能立刻收下就失败

**否决**：别的写者的短暂占用同样让它失败。单写者引擎上任何一次并发写入都能让额外连接上的一条写入失败、让一行请求级审计丢失，宿主只能自己重试。

### 认出调用方自己持有的交付事务，只在那时失败

**否决**：认不出。GORM 交给回调的会话与调用方在交付句柄上开的事务之间没有任何联系，调用方交给两者的上下文也未必是同一个；Go 不给出协程身份。

### 额外连接上的那一行交给另一个协程，在语句之后写

**否决**：写不进记录的模型写入就此发生，失败只进信号，与否决提交之后写进交付库是同一个理由。

### 本模块自己写的行与额外连接上的那一行取同一个界

**否决**：请求级与事件级在负载下排队等那一条连接的时间可能超过额外连接那一行的界，同一个界会让它们在一个繁忙但正常的库上丢行；额外连接那一行的界之所以短，是因为它等的时候另一个库上那条语句的事务还开着，本模块自己写的行没有这一层。

### 本模块自己给另占的连接设界

本模块自己从交付连接池限时取连接，在 SQLite 上改写取到的那条连接的忙等时限，写完放回。

**否决**：那是数据库模块否决的由各模块自己设界（[ADR-db-waits-2026-09-29](adr-db-waits-2026-09-29.md)）——方言代码写在本模块里，与名册、设置各写的一份各自漂移；每一行还多出改写与放回设置的往返，PostgreSQL 上按每一把锁计的 `lock_timeout` 也守不住一个合计的界。

### 取连接的等待设界，过界即失败

**采纳**，见决策。

## 决策

采纳：**语句级那条通路的记录与那条语句是一件工作。** 写在那条语句自己的会话上：写审计表失败令那条语句失败，那条语句回滚也把那行一起带走——记下的因此是确实发生过的事，且只存在一条连接。

**额外连接上的语句，审计行写进交付连接那个库里的审计表**，经交付连接写出，写在那条语句提交之前；写不进去令那条语句失败，与交付连接上的语句同一个方向。它与那条语句不在一件工作里，两个库之间没有共同的事务可用。

**额外连接连着的就是交付库那张审计表时，它与交付连接无异**：行写在那条语句自己的会话上，在它自己的事务里。认出它问的是两条连接背后的引擎，不看定位符：SQLite 上比两条连接的主库文件，引擎解析出的路径相同或文件系统认作同一个文件即是；PostgreSQL 上比服务器这一次启动的时刻、当前的库，以及审计表的表名在两条连接上各自解析到的关系。没有文件的 SQLite 库不被认作交付库，引擎答不出的情形照其余额外连接处理。

**另占一条连接写出的行，取连接的等待有界，界由数据库模块的 `Connection` 给出。** 额外连接上的语句，那一行的界为一秒，过界令那条语句以 `ErrWriteFailed` 失败并点明是在等；认出额外连接连着哪张表的那一问不等锁。本模块自己写的行（接缝、事件级、请求级）的界为五秒。插入的等锁与插入本身照旧只受数据库自己的设置约束：SQLite 的忙等时限，PostgreSQL 的 `lock_timeout` 与 `statement_timeout`。经 `Connection` 写出的一行，发出的语句与直接经交付句柄写出的相同。

**请求级与事件级按 fail-open 处置。** 写失败不进业务路径的返回值，业务照常完成。

**记录接缝返回错误。** 接缝是给调用方用的，一个愿意把自己的操作与审计写入绑在一起的调用方可以据返回值终止自己的操作。

**失败信号不经日志链。** 第一次写失败与随后的恢复各写一行标准错误，此后同一个故障不再写行；理由与日志模块报告自身失败时相同——报告链自身缺席或出问题时仍然可用。经日志链报的写法被否决：输出列表为空是合法配置，那条链可以整条不启用，而本模块最需要被看见的时刻正是一次写入失败。

## 后果

记录与它所记录的事实在语句级那条通路上同生共死；其余通路的失效方向不扩大业务的故障面。

**接受的代价：**

- **一次审计存储故障会让全部写语句失败。** 这是语句级那条选择的直接代价，也是它与另外三条的差别所在：宿主在有写流量的命令上装本模块，等于把那张表的可用性放进了写路径。
- **请求级与事件级有静默缺口。** 审计存储不可用期间它们照常放行；缺口只在那一行标准错误里可见，没有人会被自动通知。
- **信号只到标准错误，且一个故障只留两行。** 中间的过程无从得知；这两行不进任何日志目的地。
- **两处对同一次写入的读法不同。** 接缝返回的错误在一处是终止条件、在驱动的那两条通路上是可继续的信号。
- **失败的判定不区分原因。** 表不存在、连接断开、约束冲突都进同一处信号，宿主看不出该怎么修。
- **额外连接上的一条语句随后回滚时，它的审计行留在交付库里。** 记下的是一件没有发生的事——交付连接上那条选择要避开的正是它，而在两个库之间无从避开。连着交付库那张表的额外连接不在此列。
- **额外连接上的每一条写语句，在写出那一行之外多一到两次查询。** 一次在语句自己的连接上；它答出一个文件或那张表时，再在交付连接池取来的那条连接上问一次。取交付连接本身不发语句。
- **额外连接连着交付库本身时，认出它也要一条交付连接。** 交付池只开一条连接而被调用方占着时，那条写入一秒后失败，即便行本可以写在它自己的会话上。
- **单写者引擎与只开一条连接的库上，在交付句柄上开着的事务里经额外连接写入时，那条写入失败。** 只开一条连接的库上一秒后失败；文件库上这个事务占着写锁时——不以 `DEFERRED` 开启的从开启起就占着，读没读过、写没写过都一样，以 `DEFERRED` 开启的写过之后才占着——那一行等这把写锁，等满交付连接的忙等时限后失败；回滚日志模式下以 `DEFERRED` 开启、读过的事务让那一行的提交等它读完，同样失败。界替代不了识别：等的是调用方自己时，等多久都等不到；宿主要把这类写入挪到交付句柄的事务提交之后。
- **交付连接池被别的调用方占满超过一秒时，额外连接上的写入同样失败；交付库被别的写者占着超过交付连接的忙等时限时也失败。** 界分不出等的是谁，比这更长的占用只能由调用方重试。
- **本模块自己写的行，在交付连接池五秒给不出连接时失败，SQLite 上等交付库的写锁等满忙等时限时失败。** 接缝返回错误，事件级与请求级丢这一行、只进信号；在调用方的事务里调用接缝或发布事件时，调用方要等满这段时间。PostgreSQL 上审计表被锁住、会话又没有 `lock_timeout` 与 `statement_timeout` 时，不随上下文取消的事件级与请求级一直等到锁放开。
- **插件要分得出交付连接与额外连接，而它自己回答不了。** 插件实例在进程内被多个注册表共用、不持有状态，从一个句柄上读不出这个句柄的来历；回答要由建出额外连接的数据库模块给出。

## 失效条件

若出现一条合规要求规定审计不可用时业务必须全部停止，则驱动的那两条通路的 fail-open 不再成立，它们要与语句级取同一个方向。
