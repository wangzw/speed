# 发送身份的登记在带外完成，一个进程只挂一个载体且不做跨厂商路由

## 背景

短信到达目的地国家依赖发送方身份在当地已完成登记。美国要求 10DLC（[REF-us-a2p-10dlc](../references.md)）的品牌与活动登记，未登记的流量被运营商拦截；印度要求 DLT（[REF-trai-tcccpr](../references.md)）的实体与模板登记，发送时按目标国家参数带上登记编号；免费号码要验证、短号码要租用、逐国家的发送方 ID 要在当地申请。这些过程是合同与监管流程，状态由厂商门户与运营商持有，会独立于本进程改变。

本能力只做一件事：把一条已声明的消息交给一个载体发出去。载体在一份 `CarrierModel` 里声明它有哪些发送身份（签名、发送方 ID、长号码、短号码、免费号码、号码池、消息服务）以及这些身份覆盖哪些国家。一个进程里恰好一个载体生效。

约束如下：

- 身份的可达性不由本进程决定。一个身份今天在某个国家可用，明天可能因为登记过期而不可用，本进程没有可靠来源知道这件事。
- 发送接口不幂等。一次超时之后调用方无从知道短信是否已发出，重发会重复投递并重复计费。
- 模板的两类形态（厂商编号与本地正文）与审核方式（逐模板与不审核）按载体不同，跨载体切换一条模板需要重新声明，不是换一个地址。
- 一个进程只挂一个载体，是排他交付的直接结果：两个发送接口同时在场，消解阶段即失败。

## 考虑过的选项

### 在本能力内管理登记的生命周期

把品牌、活动、DLT 实体、模板登记、号码验证都做成可提交、可查询、可续期的资源，本能力跟踪它们的状态并在发送前检查。

**否决**：这些状态由厂商门户与运营商持有，本能力只能重复存储一份无法核实的副本。登记状态是监管与合同事实，不是本能力拥有的 API；一份陈旧的副本会让一条实际可用的身份被判为不可用，或相反，让一条已被撤销的身份继续发送。维护这份副本的成本与它带来的错误都高于让登记留在带外。

### 按目的地跨多个载体路由，并做故障转移

一个进程同时挂多个载体，按号码的国家选择最便宜或最可达的一个；一个载体失败时换另一个重发。

**否决**：多载体同时在场直接违反排他交付与单一 `Provider` 的前提；各载体的模板模型不同，同一条消息在不同载体上不是同一份声明；发送不幂等，故障转移中的“重发”在超时场景下会重复投递并重复计费；跨厂商还要求每个厂商各有一套合同、身份与登记，成本翻倍。故障转移看起来提高到达率，实际把“结果不确定”放大成“可能重复”。

### 声明身份与覆盖国家，登记留在带外，一个进程一个载体

载体声明可用身份与可送达国家，本能力不跟踪任何登记状态；一条消息只交给一个载体，不做跨厂商路由或故障转移。

**采纳**，见决策。

## 决策

采纳：**发送身份的登记在带外完成；本能力只声明身份与覆盖国家；一个进程只挂一个载体，不做跨厂商路由或故障转移。**

- **身份是声明。** `CarrierModel.Identities` 给出每个身份的名字、种类、值与覆盖国家，`Countries` 给出载体可送达的国家。这些是配置写下的声明，不随运行期改变，也不带登记状态。
- **身份的选择在 `Send`。** `Message.Originator` 点名一个身份，空值取载体的缺省身份。点名一个不存在的身份是 `ErrRejected`（调用方带了本部署没有的身份）；身份存在但覆盖不了目的地国家是 `ErrUnroutable`（部署缺口，消息本身没有缺陷）。
- **登记缺口归 `ErrUnroutable`。** 厂商明确表示缺权限、资源不存在、配额不足或身份不能服务目的地时，载体归 `ErrUnroutable`；一个归类不了的失败仍归 `ErrUncertain`，不当作确定结果。
- **不路由，不故障转移。** `Message` 与 `Resolved` 上没有任何选路键；一条消息只对应一个载体的一次调用。载体不重试，调用方也不从本能力得到“换一个厂商”的入口。
- **一张数据库只服务一个载体。** 运行期模板按 `carrier` 列隔离；第一次对着一张带旧行的数据库启动的载体收养旧行并写下所有权标记，此后一个不同的载体对同一数据库启动即失败，而不是静默接管。

## 后果

发送路径只有一条：声明身份、选择身份、交给一个载体、把厂商的答案归入封闭的哨兵集合。运维知道登记在厂商门户里，代码里不出现第二份无法核实的状态。

**接受的代价：**

- **未登记的身份可能产生非预期的发送结果。** 一个未登记的发送方 ID 可能被厂商改写成一个随机的长号码，也可能收到一条 `NOTICE` 或以其他形式被拒，具体表现按厂商与国家而异。本能力只把厂商明确表达的失败归入哨兵；厂商“接受”了一条最终被运营商拦截的消息时，同步答案看起来是成功的。
- **美国 10DLC 的流量在品牌与活动登记完成前被拦截。** 运营商拦截不产生本能力可归类的错误，运维必须在厂商门户里完成登记才能改变结果。
- **印度 DLT 的登记缺失表现为发送失败。** 模板的 `IN_TEMPLATE_ID` 与身份的 `IN_ENTITY_ID` 是声明，不是登记；登记本身仍在厂商侧。
- **一个厂商不可用就是一次不可用。** 没有故障转移，调用方只能等厂商恢复；自行重发要自己承担重复投递与重复计费，本能力不提供安全的跨厂商重发。
- **换厂商是一次迁移。** 模板按 `carrier` 隔离，身份、编号与登记都属于原厂商；换载体要重新声明模板与身份，并处理旧行的所有权标记，不是改一个配置值。
- **身份清单是配置。** 增加或撤下一个身份要改配置并重启，不能在运行期热加；本能力不提供身份的管理面。
- **身份视图不含登记状态。** 管理面的载体路由报告身份与覆盖国家，不报告它们是否已登记；运维要知道一条身份能不能用，仍要查厂商门户。

## 失效条件

- 厂商提供可靠的登记状态接口，使本能力可以在不重复存储的情况下读到一个可核实的登记结论。此时“登记留在带外”的理由减弱，可以评估只读的登记视图。
- 出现必须按目的地选择不同厂商的产品需求（例如逐国家的合同或价格差异）。此时“一个进程一个载体”的前提改变，跨载体路由需要重新设计，并同时解决模板模型差异与不幂等重发。
