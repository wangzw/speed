# 两个实现子包共用一份第三方客户端构造与测试夹具

## 背景

键值模块与事件模块各有一个 Redis 实现子包，两者都要做同一件事：读地址、口令、库序号与连接池大小，建一个客户端，并在停机时关闭它。两处代码的形状由同一个第三方客户端决定，差异只在配置项落在哪个命名空间。

旧实现把建客户端这一步推给宿主：`kv/redis` 与 `eventbus/redis` 的构造器都只收一个现成的客户端，宿主机自建后注入。新架构取消了这条路——模块之间取得实例的途径只有注册表，宿主向装配提供的声明一律经由模块机制（架构不变量 5、9）。建客户端因此推回模块自己，两个子包各写一遍。

写出的两份代码无法互相看见：跨功能目录的依赖一律指向对方的接口包，不 import 其他功能目录的实现子包。

## 考虑过的选项

### 两个实现子包各写各的

**否决**：两处的差别只有配置项的挂载路径。它们的正确性——口令为空时是否仍建池、地址不可达时是构造失败还是首次调用失败、关闭是否幂等——无法由同一套测试覆盖，一处修正不会传导到另一处，而两处的失效形态完全相同。

### 事件模块的 Redis 实现依赖键值模块的 Redis 实现子包

**否决**：违反依赖规则，实现子包不对外提供可被跨功能目录引用的面。它还会把两种功能耦合起来：键值模块调整自己的连接管理，事件模块随之改变，而两者在语义上毫无关系。

### 抽一个只封装第三方客户端的共享单元

把客户端类型、连接配置与构造、关闭收敛到一处，两个实现子包各自依赖它。

**采纳**，见决策。

## 决策

采纳：**两个实现子包共用一个共享单元，该共享单元封装第三方客户端，不登记模块、不交付功能、不参与生命周期。**

它的接口面是：被封装客户端的类型（原样暴露，不另造等价抽象，依据是架构不变量 11）、一个带配置标签的连接配置结构体、一个构造器与一个关闭函数。它的实现细节——重试、TLS、哨兵与集群拓扑——封在构造器内，调用方不感知。

两个实现子包**各自在自己的配置命名空间下挂载同一份连接配置结构体**，因此 `kv.redis.addr` 与 `event.redis.addr` 是两条独立的输入项路径。它们是两种不同功能各自的一个实现，路径本就不同，不触及"同一功能的互斥实现必须划分各自的输入项路径"这条判例。

**本共享单元的划分依据是被封装的后端，不是功能。** `pkg` 下的目录按功能划分，且允许一个目录不承载功能；本记录不修改那条划分，而是指出这一形态与它并存：它不承载功能，因此没有可划分的功能边界，它的边界就是那个第三方客户端。

**共享单元也承载测试夹具。** 各实现子包自己的集成用例要跑在真服务器上，"给每份用例一块隔离的库"这件事因此同样要有唯一的一份：两份副本会各自演进到行为不同的服务器上，而失配的表现是一个用例在两个模块里给出不同答案——与被测代码无关，也最难归因；本仓为此付过一次代价，两处 PostgreSQL 夹具的副本丢掉了另一处已经实装的并发恢复。夹具与客户端构造同为共享单元，落点也一致：封装某个客户端的共享单元，其夹具就是这个单元目录下的一个子包（`pkg/internal/pgpool/pgtest`、`pkg/internal/redis/redistest`）；没有对应封装包的夹具自成单元（`pkg/internal/natstest`）。整个共享单元子树落在 `pkg` 这个 Go module 根目录的 `internal/` 下，而不是各单元自己的 `internal/`：internal 规则只放行 `internal` 父目录子树内的引用方，PostgreSQL 夹具被键值、事件与数据库三个实现子包引用，落在任何一个单元自己的 `internal/` 下，另外两个都取不到；落在 `pkg` 的 `internal/` 下，`pkg` 内的引用方都取得到，`pkg` 之外的包取不到——夹具只被测试使用，不属于任何模块的公开面，宿主因而取不到它们。共享的理由不同：客户端构造是两份代码的逐字重复，夹具是多个模块的测试不可互证。PostgreSQL 夹具（`pkg/internal/pgpool/pgtest`）服务键值、事件与数据库三个实现子包，Redis 夹具（`pkg/internal/redis/redistest`）与 NATS（[REF-nats](../references.md)）夹具（`pkg/internal/natstest`）各服务键值与事件两个；数据库模块自带的 PostgreSQL 夹具并入前者：同一个后端的夹具只该有一份。

## 后果

建客户端这件事只有一处实现，两个子包共用它，也共用它的测试。

依赖面不因抽取而扩大：引用本共享单元的只有本来就要承担那个客户端的实现子包；宿主的 `go.mod` 干净，但 Go 的完整模块图（`go list -m all`、`go mod download all`）会看到这个客户端。

`pkg/internal/` 下多一个目录；它与使用它的实现子包同属 `pkg` 这一个 Go module。

**接受的代价：**

- 连接配置结构体的改动同时影响使用它的键值模块与事件模块，且这条耦合边不受任何机制检查。它是有意保留的——两处配置本就该一致，不一致才是缺陷——但它意味着改一处要记得另一处。
- 本仓由此出现一个不交付功能的共享单元，"`pkg/` 下每个目录提供一种功能"这句话对它不成立，读架构文档的人会遇到一处例外。
- 只有一种功能使用某个后端时，抽它净亏：多一个共享单元、多一层间接，换来的只是"将来可能有第二个用它的模块"。本记录不预设将来是否真的出现，也不为尚未出现的后端预先建立这样的单元。

## 失效条件

若某个后端的客户端构造短到不值得共享——几行参数默认值加一次构造调用，**且两处并不逐字相同**（各自已在演进，分歧是要保留的）——则抽取它的收益低于多一个共享单元的固定成本，那个后端应按各写各的处理。判据因此不是构造的长短，而是两份代码是否逐字冗余：短而逐字相同的构造照样共享（两处同时改的成本是确定的，而两份并存的漂移已经付过一次代价），短而各自演进的不共享。

若键值模块与事件模块对同一后端的连接要求出现实质分歧（例如其中一个需要专用连接池隔离），共享一份连接配置不再成立，该后端要为提出要求的那一个单独构造。
