# 作业能力根包是接口包，队列与登记面由 jobs.db 排他交付，调度器单列一个模块

## 背景

作业能力要被任何要交活的模块取用：一个提交作业的模块只应依赖提交面，不应依赖队列后端的实现。这与短信能力同形——根包是接口包，绑定后端的实现子包各登记一个模块（[ADR-sms-capability](adr-sms-capability.md)）。

队列与「登记谁来执行某类作业」落在同一个后端上：一个后端持有作业表、执行循环与认领，队列（接受作业）与登记面（告诉执行循环某类作业由谁执行）是它的两面，共享同一张表与同一个循环。

周期调度与执行是两件不同的事。一个只执行作业、不接受任何周期声明的部署（或周期作业由别处产生的部署）与一个只产生周期作业、不执行任何作业的调度进程都存在。调度面必需 `(*jobs.Queue)(nil)`、`(*jobs.Handlers)(nil)` 与 `(*tenant.Catalog)(nil)`，不需要数据库；执行面在此外另需 `(*db.Database)(nil)`，执行面与调度面的构造期依赖因此不同。

## 考虑过的选项

### 队列与登记面拆成两个模块

`jobs.db` 交付队列、另一个模块交付登记面，各是一份排他交付。

**否决**：队列与登记面是同一个后端的两面，都读同一张作业表、都在同一个执行循环里。拆开会让交付一份可用后端的实现方两份都要实现，两份的排他性也各要维护一次，而它们共享同一张表与同一个循环，拆开不产生任何独立的变化点。

### 把调度器并进 jobs.db

周期声明的展开与 tick 位于 `jobs.db` 模块内，不单列。

**否决**：只入队、不调度的部署不该跟着 tick。一个只执行作业、不接受任何周期声明的部署纳入 `jobs.db` 是为了跑作业，调度器并进去会迫使它起一个 ticker、读一份周期声明、按租户展开——这些都是它不需要的。反过来，一个只产生周期作业的调度进程应能只纳入调度面而不纳入执行面。

### 根包登记为一个模块

`pkg/jobs` 根包既做接口包又登记模块，把队列或登记面的一个默认实现放在根包里。

**否决**：根包被每一个要提交作业的模块 import，它一登记模块，提交方就会把一个后端实现与它绑定的第三方库（数据库驱动）一并拖进自己的闭包。接口包不绑定后端是既有形态（[ADR-module-layout](adr-module-layout.md)）。

### 根包作接口包、jobs.db 交付两面、调度器单列

**采纳**，见决策。

## 决策

采纳：**作业能力的根包是接口包、不登记模块；`jobs.db` 排他交付队列与登记面；调度器单列一个模块 `jobs.scheduler`。**

- 根包 `pkg/jobs` 是接口包与公共类型，不登记模块。它声明 `jobs.Queue`、`jobs.Handlers`、`jobs.Handler` 接口与 `jobs.Job`、`jobs.Task`、`jobs.Schedule`、`jobs.Status`、`jobs.Priority`、`jobs.Result`、`jobs.ProgressFn` 等类型及哨兵。提交方只依赖这个根包。
- `jobs.db` 排他交付 `(*jobs.Queue)(nil)` 与 `(*jobs.Handlers)(nil)`：队列与登记面由同一个模块提供，各是一份排他交付。它持作业表、执行循环、认领与退避。
- `jobs.scheduler` 单列一个模块，只 tick 并把 `jobs.Schedule` 声明展开成作业，不交付任何功能接口。它构造期必需 `(*jobs.Queue)(nil)`、`(*jobs.Handlers)(nil)` 与 `(*tenant.Catalog)(nil)`：入队经 `Queue`，`Start` 经 `Handlers.Registered` 校验声明类型已登记，每条声明按名册逐租户展开。
- 执行面与调度面各自独立纳入：一个只执行作业的部署纳入 `jobs.db` 而不纳入 `jobs.scheduler`，不起 tick；一个只产生周期作业的部署纳入 `jobs.scheduler`，只经队列入队。
- 调度面与执行面之间只经根包的 `jobs.Queue` 与 `jobs.Handlers` 接缝：`jobs.scheduler` 不 import `jobs.db`，`jobs.db` 不 import `jobs.scheduler`。
- 根包不登记模块，因此不提供任何默认后端；一个不写命令树、直接 `Run` 的宿主也要显式纳入 `jobs.db`（或为它预置实例）。

## 后果

提交方只依赖接口包，后端实现可选。执行与调度各自可单独纳入，一个部署按它要做的事选模块，不背它不需要的那一面。

**接受的代价：**

- 一个既执行作业又要周期作业的部署要同时纳入 `jobs.db` 与 `jobs.scheduler`，两个模块各有一份配置命名空间（`jobs.db`、`jobs.scheduler`）。
- 队列与登记面由同一模块交付，取用登记面即取用队列的实现方；一个想只登记 handler、由别处交付队列的部署做不到，队列与登记面绑在一起。
- 交付一份新后端要同时实现队列与登记面两面，排他性维护两份；`jobs.Queue` 与 `jobs.Handlers` 的接口形状对实现方都是不兼容变更面。
- 根包不登记模块，因此队列不会凭空出现；任何要用作业的装配都要显式纳入一个后端实现。

## 失效条件

若队列与登记面之间出现了独立的实现多态——同一个队列配另一个登记面，或反之——则「同一个后端的两面」这一判据不再成立，拆分的判断要重做。

若执行面与调度面在构造期依赖上不再可分（例如调度也需要读作业表），则单列调度器的意义下降。
