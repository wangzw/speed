# 配置承载启动期的值，运行期参数归设置

## 状态

已接受

## 背景

应用程序的参数按生效时机分成两类。一类必须在数据库可用之前、或在某项启动结构建立之前就位：数据库连接信息、路由挂在哪个端、静态产物的子树名、在数据库可用之前就要渲染拒绝应答的默认语言。另一类可以在进程运行期间改变，且改变应当立刻生效：限流阈值、功能开关、超时与预算。

用同一套机制承载两者，会迫使该机制同时满足"启动前可用"与"运行期可变"两个互斥的约束。

缺少判据时，两类参数的边界会随每次新增参数而漂移。

## 考虑过的选项

### 单一参数机制

主配置源承载全部参数，运行期可变的部分通过重新读取它来实现。

**否决**：运行期可变的参数需要按租户取值、需要变更审计、需要不重启生效，这些要求会把配置机制推向一个带存储、带通知、带版本的子系统；而启动期参数恰恰要求机制足够简单，在数据库可用之前就能工作。

### 两套机制，按判据划界

配置承载启动期的值，从文件或远程配置源读取；设置承载运行期参数，存放于数据库，由独立模块承载。

**采纳**，见决策。

## 决策

采纳：配置与设置分为两套机制，划界判据为：

**一个值属于配置，当且仅当它满足下列两条之一：(a) 它在数据库可用之前就被需要；(b) 它塑造一个启动结构，改变它就要求重启进程。其余的值属于设置，并在进程运行期间生效。一个值能在不重启的情况下生效时，它归设置。**

判据 (b) 的「启动结构」指进程在启动时一次性构造、此后按构造结果运行的东西：`Start` 里起的 ticker 及其间隔、执行协程池的规模与 `Stop` 的等待上限、构造时分配的缓存与并发信号量、路由挂在哪个端、嵌入产物的子树名。改变这些值使已建立的结构与配置不再对应，重启是让改动生效的唯一途径。

需要按租户或按运行时场景取不同值的值一律落在设置一侧，这是判据的推论而非另一条规则：设置存放于数据库，按租户取值要先读到租户，而读租户要数据库可用，这样的值因而不可能在数据库可用之前就被需要。它作为推论有用处——按租户取值比抽象地判断「是否需要重启」更容易在具体参数上判断，实践中先看它即可。

配置由 `pkg/config` 承载；设置由独立模块承载，依赖数据库模块，位于依赖图上层。模块对设置的依赖是一次普通的模块依赖，不使用任何特殊通道。

## 后果

判据是自举的：设置存放于数据库，则把数据库连接起来所需的一切必然是配置。边界不随新增参数漂移。

"把数据库连接起来所需"是判据 (a) 的下界而非全集：一个值不在这条下界之内，仍可能因塑造启动结构而落在配置一侧。判据问的是两件事——数据库可用之前是否被需要、改变是否要重启——够到任一条都归配置。

配置机制得以保持简单：单向、只读、无存储。

设置是运行期生效的一侧，也是两处都能承载时的选择：一个值只要能在不重启的情况下生效，就放在设置，使其可按租户取值、可审计、不必重启。

模块的配置结构体体量本身成为信号：它膨胀，说明其中大部分应当迁往设置；留下的成员应当各自能用启动结构或数据库可用之前的需要解释，解释不了的即是放错了地方。

限流阈值、功能开关均属于设置：它们都按租户取不同值，也都在数据库就绪之后才被需要。一段作为单个值的通知模板（一段字符串正文）同样落在设置一侧。

**第三种承载形态：值集合本身是运行期数据。** 有一类参数的值不是单个，而是一个在运行期增删的集合，声明的键集合表达不了它。厂商短信模板集是它的实例：模板名在运行期注册、停用、删除，每个名字下是语言到编号的映射与有序的参数表，而设置的键集合在装配期定死、容器不进设置（[ADR-settings-declaration-2026-09-21](adr-settings-declaration-2026-09-21.md)）。这类参数不进设置，由属主模块自带的存储承载——只读的那部分可来自配置，运行期增删的那部分落在模块自己的表里（[ADR-sms-capability-2026-10-13](adr-sms-capability-2026-10-13.md)）。这是本判据的一次细化：判据本身不变，它统辖的承载多出的是这一类集合型参数。

日志级别不在其列。它看似是运行期参数，但按判据归配置：进程一启动就要记日志，它在数据库可用之前就被需要，输出目标与级别也在启动时构造。它也不按租户取值，推论这一侧同样把它排除在设置之外。

**接受的代价：**

- 同一个模块可能同时需要配置与设置，其参数分散在两处，使用者需要知道去哪里改。
- 设置不可用时（数据库未就绪、查询失败），依赖设置的模块需要各自定义降级行为，这一负担落在模块而非机制上。
- 判据依赖具体设施作为分界线：一半依赖"数据库"这一设施，另一半依赖"启动结构"这一构造时刻，模块作者要先知道一个值在何处被读取才能判断它归哪边。
- 把一个值在配置与设置之间迁移是宿主可见的破坏性变更：配置迁到设置时，旧配置里的写法成为未知键，宿主随之启动失败；设置迁到配置时，旧设置行不再被声明，经设置存储写它被拒为未知键，运行期也不再读它，宿主要把值写进配置文件才生效。

## 失效条件

若设置改换存储，"数据库可用之前"这一半判据不再指向同一时刻，需要重新锚定到新的设施。

若出现一种机制，使启动结构能在不重启的情况下重建（例如运行期调整协程池规模，或更换 `Start` 起的 ticker），判据 (b) 覆盖的那批值不再满足「改变要重启」，它们随之按「能立即生效」迁往设置。
