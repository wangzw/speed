# 预置实例是已登记模块的实例，归属按实例认出或由模块名指定

## 状态

已接受

## 背景

宿主要在驱动开始之前预置自己生成的实例。配置读取面是其中之一：它由宿主在装配开始之前加载产出（[ADR-assembly-bootstrap-2026-09-20](adr-assembly-bootstrap-2026-09-20.md)），而模块在 `Prepare` 里就要按自己的配置判断能否启动（[ADR-module-enablement-2026-09-21](adr-module-enablement-2026-09-21.md)），那时驱动还没有构造任何模块的产物。不经命令树的执行发起驱动时，读取面由调用方自己预置（[ADR-drive-entry-2026-09-21](adr-drive-entry-2026-09-21.md)）。测试还要用替身顶替某个模块的产物。

注册表收下这类实例的途径是一条独立于模块机制的通道：`Supply(Token, instance)` 按功能标识收下一个已构造的实例。通道上的实例不属于任何模块：没有描述符，不表态，不参与消解，不出现在模块清单里，没有阶段回调，驱动的回滚不碰它，释放由提供它的一方负责。配置读取面走的就是这条通道，`pkg/config` 根包因此不登记模块。

这条通道靠下列专用规则与模块机制并存：

- 注册表另按功能类型存放通道上的实例与提供方的包路径，它们不进模块的实例表，也不进生命周期清单。
- `Resolve` 与 `ResolveAll` 各有一个先查通道的分支；依赖规划把通道持有的功能视为已满足，不为它排序。
- 同一功能标识收下两次、与已登记模块的 `Provides` 冲突、实例不满足该功能、驱动开始之后才调用，都在 `Supply` 处 panic。`Register` 一侧要对称地检查，否则先收实例、后登记模块的次序会漏过去，而手工搭建的注册表恰是这个次序。对称的检查维持着"通道与模块声明不会同时持有同一功能"，取用因此不需要另一条歧义规则。

这条通道是一处不经由模块机制进入注册表的入口：用它绕开模块机制是可能的，约束只能靠评审，机制本身拦不住。

模块交付哪些功能，已由描述符的 `Provides` 声明。注册表据此匹配取用的提供者，并在构造完成后断言每个声明的功能都已交付（[ADR-dependency-resolution-2026-09-13](adr-dependency-resolution-2026-09-13.md)）。

模块名与功能标识承担不同的事。功能标识指代功能，不指代某个特定实例（[ADR-capability-token-2026-09-13](adr-capability-token-2026-09-13.md)），未声明排他的功能可以有多个提供者并存（[ADR-dependency-resolution-2026-09-13](adr-dependency-resolution-2026-09-13.md)）。命令树按模块名纳入模块，写下的是实现名而不是功能名（[ADR-dependency-resolution-2026-09-13](adr-dependency-resolution-2026-09-13.md)）；各实现包导出模块名常量 `ModuleName` 与返回描述符的 `Module`。已登记的模块由 import 决定，不限于宿主自己写下的（[ADR-module-registration-2026-09-13](adr-module-registration-2026-09-13.md)），同一功能的多个实现同时被 import 是编译期的常态（[ADR-module-enablement-2026-09-21](adr-module-enablement-2026-09-21.md)）。

注册表为每个模块记录调用 `Register` 的包，重名冲突的报错据此指出双方的来处。进程级注册表的登记发生在各实现包自己的 `init` 里；手工搭建的注册表由调用方登记，记下的是调用方的包。产物类型与登记包的关系随打包而定：`kv.memory` 的产物是 `*store`，`store` 定义在 `pkg/kv/memory`，与登记它的包相同；`db.sqlite` 与 `db.postgres` 的产物都是 `*database`，`database` 定义在 `pkg/db`，两者各由自己的实现子包登记（[ADR-module-packaging-2026-09-22](adr-module-packaging-2026-09-22.md)）；`observability.otlp` 与 `observability.stdout` 的产物都是 `*Exporters`，`Exporters` 定义在 `pkg/observability`，而它是不登记模块的接口包（[ADR-observability-packaging-2026-09-22](adr-observability-packaging-2026-09-22.md)）。

## 考虑过的选项

### 保留独立于模块的通道

`Supply(Token, instance)` 连同背景所列的专用规则原样保留，读取面与测试替身继续占据一个功能标识而不属于任何模块。对称的检查让通道与模块声明从不持有同一功能，通道因而顶替不了任何已登记模块：已登记模块的表态只来自它自己的 `Prepare`，实例只来自它自己的 `New`。

**否决**：

- 实例如何进入注册表、如何被取用，要由两套机制并行回答：取用既看模块也看通道，依赖规划为通道持有的功能开特判，冲突在 `Supply` 与 `Register` 两侧各查一遍。
- 通道上的实例整个落在模块机制之外：没有描述符，`Requires`、`Resources` 与阶段回调无处声明，模块清单与启用结果的查询里没有它，驱动的回滚也不释放它。交付哪些功能、已构造的实例由谁释放，模块机制本来就有答案（`Provides` 与 [ADR-lifecycle-drive-2026-09-20](adr-lifecycle-drive-2026-09-20.md)）。被采纳的做法让预置实例留在模块机制之内，描述符、依赖校验与释放照旧适用；它为此放弃了本选项的那项性质：任何已登记模块都可被预置，其 `Prepare` 与 `New` 随之不执行，代价见后果。

### 指名预置：`Preset(name, instance)`

调用点总是写出模块名，注册表把实例记为那个模块的实例。名字取自登记该模块的包导出的名字常量，写法与命令树纳入模块相同。归属不靠推导：候选共用产物类型、手工登记、宿主自己包装的类型、不声明 `Provides` 的模块都能表达；import 图里新增一个同样被实例满足的模块，调用点也不受影响。

**否决**：名字在常见情形里重复陈述一个由实例就能确定的事实，强制每处都写，就把为认不出归属准备的入口变成了常态写法。实例满足的功能清单只对应一个已登记模块时，归属已经确定，例如宿主只 import 了一个键值后端时的键值实例；候选不止一个而产物类型定义在登记它的包里时，登记包也能确定归属，例如 `kv.memory` 的 `*store`。被采纳的做法保留同一个指名入口，只在功能清单与登记包给不出宿主要的那个模块时才需要写。

### 带功能标识：`Supply(Token, instance)`

调用点除实例外再给一个功能标识，注册表找到声明该功能的模块，把实例记为那个模块的实例。

**否决**：

- 作为消歧的手段，功能标识能分开的情形，模块名都能分开，反之不然。标识指代功能，同一功能可以有多个提供者：键值功能的各个后端都声明交付 `KV`，标识 `(*kv.KV)(nil)` 分不出实例属于哪一个，`db.sqlite` 与 `db.postgres` 同样分不出。被采纳的做法不必写名字，凭实例类型所在的包就认出 `kv.memory` 的产物；共用产物类型的那些后端，写模块名即可。只登记了一个提供者时标识能确定归属；实例不满足别的模块的功能清单时，不给名字的按实例认领同样能，满足时写模块名即可。
- 模块交付的功能已由 `Provides` 逐项声明，标识只是把其中一项在调用点再写一遍；模块交付多个功能时，实例仍要按 `Provides` 逐项核对。

### 描述符加可预置标记

描述符增加一个字段，声明本模块的实例允许由宿主预置；认领只在带标记的模块中进行，绕开 `Prepare` 的范围因此限于自行声明可预置的模块。

**否决**：

- 标记回答的是"这个模块允不允许被预置"，不回答"这个实例属于哪个模块"：认领仍须靠实例或名字，标记只在其上叠加一道准入限制。带标记的模块被预置时，它的 `Prepare` 照样不执行，绕开校验这件事没有消失，只是限定了范围。
- 描述符是被每一个模块依赖的稳定契约，加字段的代价高（[ADR-module-resources-2026-09-13](adr-module-resources-2026-09-13.md)）。标记由被预置模块的作者设置，而预置由宿主和别的包的测试发起：测试要顶替某个模块的产物，得先让那个模块的作者加上标记。

### 只按实例认领，不提供指名入口

`Supply(instance)`：归属只由实例满足的功能与实例类型所在的包认出，调用点不能给模块名。

**否决**：认不出归属的情形无从表达，而这些情形现成存在。`db.sqlite` 与 `db.postgres` 共用 `pkg/db` 的产物类型，`observability.otlp` 与 `observability.stdout` 共用 `pkg/observability` 的产物类型，定义它们的接口包不登记模块：同一功能的这些后端都被 import 时，它们的实例一个也预置不了。手工登记的候选，登记包是调用 `Register` 的包，与产物类型定义在哪里无关；宿主自己包装的类型不在任何候选的登记包里；不声明 `Provides` 的模块没有可比对的功能。注册表没有注销接口，补救只剩改变登记的内容：进程级注册表里不 import 另一个实现，或改用手工搭建的注册表。

### 传模块描述符

调用点传入该模块的描述符，例如 `Supply(instance, memory.Module())`，注册表取其中的名字。

**否决**：为取名字而构造一份描述符，效果与名字常量相同，各实现包都同时导出 `ModuleName` 与 `Module`。登记过的那份描述符才是权威，传入那份的其余字段无从使用，也无法与登记的那份比对：描述符含切片与函数字段，不可比较。

### 每个模块一个 Go 标记类型

每个模块定义一个标记类型并在描述符里声明它，`Supply` 收这个类型来指明模块，写错在编译期即被拦下。

**否决**：要新增一个描述符字段，并在模块名与功能标识之外再引入一类概念，每个模块都要改。编译期的拦截由导出的名字常量已经取得：调用点写 `ModuleName` 常量而不写字面量，拼错即编译失败，命令树纳入模块靠的是同一做法。

### 只交实例，可选地给出模块名：`Supply(instance, module ...string)`

调用点给实例，必要时再给一个模块名。不给名字时归属由实例认出，给了名字则以名字为准。

**采纳**，见决策。

## 决策

采纳：**预置实例是恰好一个已登记模块的实例。** 注册表以 `Supply(instance, module ...string)` 收下它，模块名可选，至多一个。

- **不给模块名，按实例认领。** 候选是声明了至少一项功能、且实例满足其 `Provides` 每一项功能的已登记模块，判据与构造后的交付断言相同。候选只有一个，就是它；不止一个时，取由实例类型所在的包登记的那一个，恰好一个就是它，实例类型所在的包指实例的动态类型去掉指针之后、那个命名类型的定义包。没有候选，或按登记包仍分不开，在 `Supply` 处 panic。
- **给了模块名，以名字为准。** 该模块须已登记，实例须满足它声明的每一项功能，不再按类型交叉核对。不声明 `Provides` 的模块也能这样被预置。
- **一个实例只对应一个模块**：一个模块至多一个预置实例，同一个对象不能预置给两个模块，是否同一个按引用身份判定。
- **预置实例代替所属模块的 `Prepare` 与 `New`**，效果等同于 `Prepare` 无条件表态 `StateEnabled`、`New` 返回这个实例。在注册表与驱动里，它与普通实例的差别以下列为限：
  - `Prepare` 与 `New` 不执行；表态固定为 `StateEnabled`，消解淘汰不了它，与别的提供者冲突时照普通规则消解。
  - 所属模块不看命令树是否纳入它，一律进入参与集；并入的只是它本身，不为它展开依赖闭包。
  - 实例自 `Supply` 起就存在，`Prepare` 阶段即可取用。
  - 实例自驱动开始即视为已构造：驱动无论在哪一步结束，都按模块的声明对它执行 `Stop` 与 `Close`。
- **其余照旧**，例如描述符、`Requires` 的校验与排序、依赖闭包展开到它时的规则、`Resources`、`Migrate` 到 `Close` 的阶段回调、构造后的交付断言、模块清单、启用结果与参与结果的查询。
- **先登记，后预置，都在驱动开始之前。** 归属在 `Supply` 被调用时按已登记的模块判定。

注册表没有独立于模块机制的预置通道。

## 后果

实例进入注册表只剩模块机制这一条路。背景所列的专用规则随独立通道一并取消：按功能类型存放实例的表、取用时先查通道的分支、依赖规划里的特判，以及 `Supply` 与 `Register` 之间对称的冲突检查。预置实例经所属模块的登记项进入注册表，描述符、`Requires`、`Resources` 与 `Migrate` 到 `Close` 的阶段回调不因预置而缺席，模块清单、启用结果与参与结果的查询都覆盖它。

常见情形不必写名字。同一功能的多个实现同时被 import 时，只要产物类型定义在登记它的实现包里，按登记包即可分开：宿主 import 了全部键值后端，`kv.memory` 产出的 `*store` 只有 `kv.memory` 由 `pkg/kv/memory` 登记，认领的就是它。按实例认不出宿主要的那个模块时，写上模块名即可表达。

配置读取面与其余实例一样属于一个已登记模块：`pkg/config` 根包登记一个只声明交付读取面的模块，命令树的执行把加载产出的读取面指名预置给它，名字是该包导出的模块名常量。配置包知道自己的模块名，指名之后归属不依赖按实例认领，手工搭建的注册表里另有交付读取面的模块时也不会认不出。不经命令树的执行、自行预置读取面的调用方不给名字也能在进程级注册表里认领成功：读取面的类型定义在 `pkg/config`，登记该模块的也正是 `pkg/config`。

预置实例自 `Supply` 起就存在，模块仍能在表态之前读到配置读取面。

驱动开始之后，预置实例与驱动构造的实例走同一条关闭路径：所属模块声明的 `Stop` 与 `Close` 由驱动对它执行，失败发生在 `Prepare` 时也不例外（[ADR-lifecycle-drive-2026-09-20](adr-lifecycle-drive-2026-09-20.md)）。

**接受的代价：**

- **仍有需要指名的情形。** 判据是按实例认不出宿主要的那个候选，例如：
  - 候选共用一个产物类型，而定义它的包不登记候选：`db.sqlite` 与 `db.postgres` 的产物都是 `*database`，`observability.otlp` 与 `observability.stdout` 的产物都是 `*Exporters`，`database` 与 `Exporters` 分别定义在 `pkg/db` 与 `pkg/observability`。同一功能的这些后端都被 import 时，预置其中任何一个都要写模块名。
  - 模块不由定义产物类型的包登记，且候选不止一个：手工搭建的注册表记下的登记包是调用 `Register` 的包，与产物类型定义在哪里无关。
  - 宿主自己包装的类型，且候选不止一个。
  - 不声明 `Provides` 的模块，只能指名预置。
- **按实例认领依赖一条打包惯例：产物类型定义在登记该模块的包里。** 候选不止一个而惯例对宿主要的那个候选不成立时：若实例类型所在的包没有登记任何候选，或登记了不止一个，`Supply` panic，不替宿主挑选；若该包恰好登记了另一个候选，实例认给那一个而不报错，宿主要的这个登记在别处的候选只有指名才分得开。
- **实例缺了宿主要的那个模块的某项功能时，不指名的认领可能不报错地归给另一个模块。** 候选须满足自己声明的每一项功能：宿主要的模块声明了多项功能而实例缺其中一项，它就不是候选；别的模块声明的功能被实例全部满足时，认领在它们之中进行，其中只有一个时实例归它，它随之进入参与集，表态固定为启用。近似候选只在没有候选时报出，缺的那一项因而不被报出。要让缺的功能被报出来，调用点就写上模块名：实例不满足所指模块的全部功能时，`Supply` 在调用处 panic 并指出缺哪一项。
- **不指名的调用点随 import 图变化。** 宿主的某个依赖新引入一个同样被实例满足的模块，调用点未改，`Supply` 就可能从认领成功变为 panic；新模块恰由实例类型所在的包登记、而原先认领的候选不由这个包登记时——定义该类型的包在新版本里多登记了一个模块即是——实例不报错地改认给新模块（[ADR-module-registration-2026-09-13](adr-module-registration-2026-09-13.md)）。无论哪种结局，补救都是给调用点写上模块名。
- **预置绕开所属模块 `Prepare` 与 `New` 中的一切，不只是校验。** 模块在那里读自己的配置、判断能否启动、设定自己持有的进程级状态、装配自己的产物，预置时都不发生：日志模块在 `Prepare` 里按配置设定引导链的级别，预置日志实例时它不设定，没有别的写者时引导链停在默认级别。注册表不检查实例是否合格、缺了哪一步：所属模块可以在自己的回调里拒收，其余由预置的一方负责。数据库模块即拒收：它在 `New` 里给句柄装上各模块声明的插件，不出自它的 `New` 的实例，句柄上没有它装上的租户过滤、语句审计这类插件，它在 `New` 之后的第一个回调 `Migrate` 里拒收这样的实例，返回错误，启动失败；宿主用它自己的 `New` 造出再预置的实例照常可用。拒收管不到的情形——在它之前的取用，以及出自它的 `New` 而插件与本次运行的启用集不一致的实例——插件在句柄上缺席或多出，没有任何一层报出（[ADR-db-scope-2026-10-08](adr-db-scope-2026-10-08.md)）。保留独立通道没有这一项代价：通道顶替不了任何已登记模块（见考虑过的选项）。
- **回调要容忍不是自家 `New` 产出的实例。** 所属模块从 `Migrate` 到 `Close` 的回调收到的，是满足其功能清单的任一实例，如何应对由模块自己负责，注册表不检查。略过外来实例的模块，它在回调里承担的那一份工作随之缺席，而它照样报在场：认证网关略过不是自己产物的实例，链上就没有认证层，启用结果与参与结果却都答网关在场（[ADR-authn-guarantees-2026-09-20](adr-authn-guarantees-2026-09-20.md)）；入口模块略过不是自己产物的实例，它的 `Stop` 不排空，那个实例放进来的在途请求不在入口先停的保护之内，其余模块照常收到 `Stop` 与 `Close`（[ADR-http-shutdown-2026-09-14](adr-http-shutdown-2026-09-14.md)）。应对也可以是拒收：数据库模块的 `Migrate` 拒收不是本模块产物的实例（见"预置绕开所属模块 `Prepare` 与 `New` 中的一切"一条），事件各实现的 `Start` 只接受自己的产物，预置的总线不是它时返回错误；推进到拒收那一阶段及更深的驱动因此失败。替身预置给这样的模块，只能用于浅于拒收那一阶段的驱动；更深的驱动要承接替身，就不用真模块，改为登记占位模块。
- **预置实例释放到哪一步，取决于驱动是否开始与所属模块的契约。** 驱动开始之后，驱动对预置实例执行所属模块声明的 `Stop` 与 `Close`；接管所取实例生命周期的取用方也照常释放它收取的预置实例，可观测性的装配器关停它收取的每个导出器即是。这些回调对不是本模块产物的实例做什么，由各模块自己决定：数据库模块的 `Close` 经 `Database` 关掉任何预置实例的句柄背后的连接池，而不少模块的回调只处理自己的产物，外来的实例原样留下。没有回调释放的部分仍由宿主释放；驱动没有开始时，全部由宿主释放。宿主在 `Execute` 之前预置的实例，`Execute` 只由命令行库应答了请求（帮助与补全即是）、或在发起驱动之前就因命令行、加载或校验失败而返回时，驱动没有开始，而 `Execute` 的返回值区分不了驱动有没有开始，宿主要另查参与结果。靠取用方释放的实例另有一个缺口：驱动在取用方收取它之前就结束时，没有任何一方释放它，宿主从外面也分辨不出它是否已被收取。宿主要对照所属模块与取用方的契约、并查明驱动是否开始，才不会重复释放，也不会漏释放。
- **预置一个接管别的模块实例的取用方，被它接管的实例就失去释放者。** 取用方在 `New` 里收取别的模块的实例并负责释放它们时，预置它就跳过了收取：其中由驱动构造的没有任何一方释放，预置的落回宿主释放。驱动对已构造实例的释放（[ADR-lifecycle-drive-2026-09-20](adr-lifecycle-drive-2026-09-20.md)）在这样的装配里不完整。可观测性的装配器即是：它被预置时，导出后端在同一次驱动里构造的导出器没有任何一方释放。
- **`Prepare` 阶段取得到的，构造之后不保证仍取得到。** `Prepare` 阶段存在的只有预置实例：非排他功能另有一个由驱动构造实例的提供者时，那时的单值取用只见到预置实例而成功，那个提供者在构造阶段建立实例之后，同一个取用得到 `ErrAmbiguousProvider`。
- **预置改变模块在参与集与消解里的位置。** 预置了实例的模块不看命令树就进入参与集，参与集不再全由命令树写出。并入的只是它本身：它 `Requires` 中必需的功能，提供者须已在参与集里，否则依赖解析判缺提供者。表态固定为启用：一个本会以 `StateAuto` 让位的默认实现被预置后不再让位，命令树同时点名同一排他功能的另一个表态启用的实现时，启动以排他冲突失败。
- **机制不限定谁来预置。** `Supply` 是注册表的公开方法，进程级注册表是包级变量：宿主 import 的某个包若在自己的 `init` 里对它预置，这个二进制无论执行哪条命令，被预置的模块都进入参与集，表态固定为启用，宿主的命令树上看不出它。预置只由宿主与测试在驱动之前发起，这一点只能靠评审维持，机制拦不住。
- **只因预置而参与的模块不在配置层的人机界面之内。** 命令行参数、帮助输出与必填判定按命令树决定的参与集，在驱动开始之前就已定下（[ADR-command-tree-2026-09-20](adr-command-tree-2026-09-20.md)）。命令树没有纳入的、预置了实例的模块，命令行上没有它的参数，帮助输出不列出，它的回调读自己那份配置时必填项缺值也不报错。
- **预置必须晚于登记。** 进程级注册表在 `init` 中登记，早于 `main` 里的预置；手工搭建的注册表不继承 `init` 期的登记，要先 `Register` 再 `Supply`。次序写反时，指名的调用在调用处以模块名未登记 panic；不指名的按调用那一刻已登记的模块认领，可能因没有候选或分不开而 panic，也可能被已登记的另一个候选认领而不报错，之后再登记目标模块也不纠正——要让写反的次序一定被报出来，调用点就写上模块名。手工搭建的注册表要预置读取面，须先登记 `config` 模块。
- **测试里没有真模块可顶替的功能，要登记一个只声明 `Provides` 的占位模块来承接替身。** 改用真模块，则它的 `Requires` 照常校验，其依赖也要在场，它的回调也照常对替身执行，其中拒收外来实例的会让驱动失败。
- **没有命令树的执行时，宿主要自己预置读取面。** `Run` 不加载配置，而 `config` 模块一经登记就在 `Run` 的参与集里，它没有 `New`，漏预置即启动失败（[ADR-drive-entry-2026-09-21](adr-drive-entry-2026-09-21.md)）。
- **一个对象承担多个模块的功能时，不能分别预置给它们。** 同一个对象只对应一个模块，这些功能须由一个模块在 `Provides` 中一并声明。"同一个对象"按引用身份判定，即动态类型与地址都相同，类型不同而地址相同的两个指针——结构体与它首个字段的指针即是——不算同一个。检查只覆盖指向非零大小类型的非 nil 指针、非 nil 映射与非 nil 通道，其余实例不作这项检查：值类型的实例每经一次传递就是一份副本，没有对象身份可言；切片与函数值可以共用底层的状态，按地址却分不出是否共用，同一底层数组上的两个切片首元素的地址可以不同，函数值按地址取到的是代码的位置，同一函数字面量生成的两个闭包各持一份状态，取到的地址可以相同；零大小类型的不同变量可以共用一个地址，两次 `&stub{}`（`stub` 为零大小类型）可能相等，按地址分不出是否同一个；值为 nil 的指针、映射与通道不指向任何对象，地址都是零，按动态类型与地址判定会把同一类型的任意两个判成同一个，而它们之间没有可共用的状态。代价落在覆盖之外：值类型、切片与函数值、零大小类型的实例分别预置给两个模块，机制不拦，它们共用同一份状态时——值里含有指向同一份状态的字段，切片共用底层数组，闭包捕获同一组变量——两个模块共用这份状态而注册表不知情；同一个零大小替身预置给两个模块同样不被拦下，分别构造的零大小替身则可以各自预置给不同模块。判据本身也漏过一种：经类型转换得到的、共用同一份底层状态而动态类型不同的指针、映射与通道，按动态类型与地址判定不算同一个，同样不被拦下。
- **驱动为预置了实例的模块保留专门的处理**：并入参与集、跳过 `Prepare` 并固定表态、跳过 `New`、关闭时补进构造序。这些处理落在驱动里，范围限于实例从何而来这一件事；注册表的实例表与取用不为预置另设规则。

## 失效条件

若实现普遍共用产物类型，或宿主普遍预置自己包装的类型，需要指名的预置成为多数，"常见情形不必写名字"的前提不再成立，模块名应改为必填。

若候选不止一个时的认领反复落在宿主不要的候选上——宿主要预置给某个候选而漏写了模块名，实例类型所在的包恰好登记了另一个候选，实例不报错地归了它——"要别的候选就指名"的前提在实践中不成立，按实例认领的判据需要收窄，例如候选不止一个时一律要求指名。

若绕开 `Prepare` 与 `New` 造成的故障反复出现在预置实例上，"由预置的一方负责"的前提不再成立，预置需要收窄到明确声明可被预置的模块。
