# 账户模型：全局账户、已验证标识、成员关系表、墓碑删除、无外键、UTC

## 背景

账户、标识、外部身份绑定、成员关系、口令凭据、服务密钥与失败退避的表由 `authn.account` 一个模块经 `pkg/db` 承载（[ADR-authn-scope](adr-authn-scope.md)、[ADR-authn-packaging](adr-authn-packaging.md)）。这些表的结构要同时满足下列事实。

**账户与租户的关系。** 一个人可以属于零到多个租户。登录时要跨租户列出账户的成员关系，请求期的成员判定读同一份数据。会话、令牌、审计行、角色绑定与事件都以账户标识指向账户（[ADR-authn-identity](adr-authn-identity.md)）；标识若可变或可复用，这些引用悬空，或者转移到另一个人名下。

**标识的证明。** 邮箱与手机号登记即作为账户的联系方式，是否作登录方式由持有人选择，验证只证明所有权（[ADR-authn-contact-and-login-ways](adr-authn-contact-and-login-ways.md)）；它们不作识别账户或建立外部身份绑定的键，企业预置账户按管理员断言渠道邮箱匹配的情形除外（[ADR-authn-external-binding](adr-authn-external-binding.md)）。邮箱与手机的唯一约束全局生效。库里若允许未经证明的标识行，攻击者可以先用受害者的邮箱建号并占住其唯一值，使受害者无法再用该地址登记或把它选作登录方式。外部提供方对「已验证」的口径不一致：GitHub 的 `/user`（[REF-github-rest-users](../references.md)）返回的邮箱不带验证状态，微信（[REF-wechat-website-login](../references.md)、[REF-wechat-oa-web-auth](../references.md)）没有邮箱，提供方的邮箱会被回收复用。迁移导入的账户来自旧系统，旧系统从未验证过它们的邮箱；管理员代建的账户则是管理员为某个人建的。

**成员关系与租户模块的约定。** 受租户约束的模型内嵌 `tenant.Model`：租户列进主键，其余索引以租户列打头，上下文里没有租户时语句被拒，跨租户的唯一途径是 `tenant.CrossTenant`，该途径不判权、只靠调用点自律（[ADR-tenant-scoping](adr-tenant-scoping.md)）。没有装载租户名册模块的命令里，受约束模型的插入因租户标识为空而失败。按账户反查「属于哪些租户」与约定要求的索引结构不合。`pkg/tenant` 位于 `pkg/authn` 之上，`tenant/resolve` 已经 import `pkg/authn` 根包，authn 的子包反向 import `pkg/tenant` 使两个目录互相依赖（[ADR-tenant-admission](adr-tenant-admission.md)）。已有的表不内嵌约定的先例是审计表（[ADR-audit-sink](adr-audit-sink.md)）。

**表之间与模块之间的完整性。** 每个模块只在自己的事务里写自己的表：`pkg/db` 没有跨模块传递事务句柄的通道，别的模块的表可能因模块未纳入而不存在。迁移的依赖序只在一次迁移收集之内成立。SQLite 上外键开关是否打开未经核实。

**删除与个人数据。** 邮箱、手机号与显示名是个人数据，删除账户要能抹除它们。GORM（[REF-gorm](../references.md)）的 `DeletedAt` 软删除保留行的全部内容，也不记录删除者（[ADR-db-plugin-scope](adr-db-plugin-scope.md)）。

**时间的存储。** GORM 的 `NowFunc` 默认取本地时间，`pkg/db` 没有覆盖它。SQLite 驱动把 `time.Time` 按其所在时区存成文本，比较是字符串比较。实测（`glebarez/go-sqlite` v1.21.2，[REF-glebarez-go-sqlite](../references.md)）：写入 `07:00-05:00`（即 12:00Z）之后，`WHERE at > 11:00Z` 命中 0 行。PostgreSQL 的 `TIMESTAMPTZ` 不受影响。

**加密列与盲索引。** `pkg/db` 的盲索引不替调用方规范化，一侧没规范化就查不到而不报错；换根密钥后每个已存摘要失效，要逐行重写；缺根密钥时 `BlindIndex` panic（[ADR-db-encryption](adr-db-encryption.md)）。

**同一模块的接口与实例。** 一个模块只有一个实例，`core.Resolve` 对它做类型断言，构造期逐个核对 `Provides` 声明的接口。同一模块交付的接口里出现同名而签名不同的方法，一个类型就无法同时实现它们。

**宿主与增长。** 宿主要给账户加自己的字段，而 authn 的表结构不能成为宿主的接口。会无界增长的表若无人清扫，表随运行时间一直变大。

## 考虑过的选项

### 账户标识用自增整数、邮箱或用户名

**否决**：自增整数暴露账户规模，也不能在多个副本上离线生成。邮箱与用户名可变、会被复用，唯一性要靠改名流程维持；会话、角色绑定与审计行里的旧引用在改名或复用之后指向别的人。

### 邮箱作外部身份的主键或自动合并键

**否决**：提供方的邮箱会被回收复用，各提供方的「已验证」口径不同，微信根本没有邮箱；以邮箱为键等于让预占劫持（[REF-pre-hijacked-accounts](../references.md)）成为一条合法路径。外部身份的键取（提供方，主体）。

### 允许未验证的邮箱标识存在，用 `verified_at` 区分

**否决**：只对已验证行唯一的部分唯一索引能缓解未验证行占住唯一值，缓解不了预占抢注：未验证的行仍在库里，每一条读取标识的路径都要记得过滤 `verified_at`，漏一处就把攻击者的行当作受害者邮箱的持有者。「没有待验证的行」让这条不变式由存储结构承担，不靠每处读取自觉。

### 管理员断言与导入来源的邮箱按已验证处理

**否决**：把断言渠道的邮箱视为已验证，等于让没有证明过地址的人获得证明的效果：该地址可被选作登录方式，在通知与匹配中按已验证地址对待。攻击者先在旧系统用受害者的邮箱注册并设口令，迁移之后该地址被当作已验证，而受害者无法凭自己对该地址的控制把它取回。管理员断言与导入来源只记录事实，不是邮箱所有权的证明。

### 成员关系嵌入 `tenant.Model`

**否决**：登录时枚举账户的全部租户只能走 `CrossTenant`，而该途径不判权；约定要求的主键与索引结构与按账户反查不合；没有租户名册模块的命令里，受约束模型的插入直接失败，账户存储因此依赖一个它不该依赖的模块。

### 成员关系放在授权模块

**否决**：授权缺席时「账户是否属于该租户」仍要有人回答，请求期的成员判定与登录时的租户枚举都不能以授权模块的存在为前提。授权模块读取成员关系时 import authn 根包，与 `tenant/resolve` 一致。

### 成员关系的方法沿用 `Get` 与 `Set`

**否决**：`authn.account` 交付的其他能力接口已占用 `Get` 与 `Set` 这两个名字，签名各不相同，一个实例无法同时实现它们。

### 手机与邮箱用加密列加盲索引

**否决**：盲索引不规范化，换根密钥后全体失效要逐行重写，缺密钥时 panic。标识是登录名，管理面还要按标识前缀做范围列出，摘要列做不了前缀范围。标识不是机密，机密是口令与因素密钥，用加密列保护标识换来的是这些运维负担。

### 物理删除，或 GORM 软删除

**否决**：物理删除让标识可以被复用，角色绑定与审计行里的引用随之悬空或转移。GORM 软删除保留行的全部内容，达不到抹除，也不记录删除者。

### 在表之间与跨模块建外键

**否决**：跨模块外键让迁移先后成为隐含契约，而依赖序只在一次迁移收集之内成立；别的模块的表可能不存在。SQLite 上外键开关是否打开未经核实，完整性不能押在它上面。墓碑行永久保留，外键对已抹除账户的「父行存在」检查照常通过，拦不住指向墓碑的成员关系写入，这一核对仍要由写入方做。规则一分为二（模块内有外键、跨模块没有）还会让每条完整性规则多一个要先判的前提。

### 沿用 GORM 与驱动的默认时间

**否决**：模型路径的 `CreatedAt` 与 `UpdatedAt` 取本地时间，SQLite 上非 UTC 的值让 `valid_after`、`locked_until`、`idle_expires_at` 一类的比较判错；判错的方向不可预期，可以偏向放行一个应当失效的会话。

### 账户表加 JSON 资料字段，或宿主模型内嵌账户模型

**否决**：JSON 资料字段把无界的个人信息放进安全关键表，authn 的表结构成了宿主的接口。宿主模型内嵌账户模型则让加密序列化器、审计捕获与租户插件按模型字段作用的范围不再自足，租户约定的主键结构也与账户全局唯一的约束并存不了。

### 由一个集中的清扫者回收各模块的增长表

**否决**：清扫要写别的模块的表，违反每个模块只写自己的表；清扫者所在的模块也不知道哪些表因模块未纳入而不存在。

### 全局账户，已验证标识，归 authn 的成员关系表，墓碑删除，无外键，一律 UTC

**采纳**，见决策。

## 决策

采纳：账户全局，库里只有已被证明的标识，成员关系表归 `authn.account` 且不嵌入租户约定，删除留墓碑，表之间不建外键，时间一律 UTC。表、列、接口与判定顺序写在设计文档 `design-authn-account`。

**账户。**

- 库里生成的账户标识 `AccountID` 是 UUIDv7（[REF-rfc9562](../references.md)）文本，由 `authn.account` 生成；宿主导入既有用户时可带入自己的标识，须满足 `ParseAccountID` 的格式且不以 `static.` 起头。两种来源的标识都不可变、不复用。UUIDv7 可在任一副本上离线生成，不暴露规模，生成的标识次序近似创建次序。
- 账户状态的零值视为停用：一个没有被显式启用的账户不能认证，与租户名册、判决零值取同一判据。
- 账户行带 `valid_after`：此刻之前签发的会话与令牌一律失效。停用与删除把它前移，重新启用不回退。清理没做完时，它是校验后端拒绝残留会话的底线（[ADR-authn-account-lifecycle](adr-authn-account-lifecycle.md)）。
- 运维口令表里的账户不进库，标识带 `static.` 前缀；库里生成的标识不带这个前缀，两个来源的标识不相撞（[ADR-authn-credential-dispatch](adr-authn-credential-dispatch.md)）。
- 账户停用与删除对全部租户生效；只在一个租户内下线一个人，用成员关系的暂停。

**标识。**

- 库里只有已被证明的标识：邮箱与手机标识写入时即带验证时刻与验证渠道 `verified_via`，没有待验证的行。
- 证明的强度由渠道决定。判据是该渠道本身让系统确认了对该标识的控制：系统自己完成了验证（如短信验证码），或提供方断言了已验证邮箱，属真实证明；管理员或导入方的陈述没有让系统确认任何控制，只是断言，只记录事实。验证渠道的取值是封闭集，逐项归类写在设计文档 `design-authn-account`；新增渠道须先按判据归类并修改该文档。
- 凡以邮箱所有权为前提的判断，只认真实证明的标识；断言的标识不参与。企业预置账户的匹配是唯一的例外：管理员预先建号并写下邮箱，IdP 断言同一已验证邮箱时直接进入该账户，这一匹配采信管理员断言渠道的邮箱（[ADR-authn-external-binding](adr-authn-external-binding.md)）。

**成员关系。**

- 成员关系表归 `authn.account`，不嵌入 `tenant.Model`，租户标识用 `tenant.ID` 的字符串形式，authn 不 import `pkg/tenant`。
- 每条语句显式写出租户列，`Memberships` 的实现独占这张表。成员关系与 IdP 的租户列由 authn 的代码显式过滤，租户插件不作用于它们。
- `Memberships` 的成员判定把零值（暂停）与查不到都视为非成员。
- 同一模块交付的各能力接口，方法名两两不相交，`Memberships` 的方法名因此避开同模块其他接口已占用的名字；新增能力接口先对同模块的其他接口查重名。方法名写在设计文档。

**删除。**

- 删除是终态：留墓碑行，抹除个人数据，通知。同一邮箱此后再注册得到新账户、新标识。停用与删除之后跨模块的清理分工见 [ADR-authn-account-lifecycle](adr-authn-account-lifecycle.md)。
- 邮箱与手机号规范化后明文存库；机密（口令哈希、因素种子、IdP 客户端密钥）不是明文。
- 宿主表里引用账户标识的行不由 authn 清理，宿主订阅 `authn.account.deleted`。

**表之间。**

- 所有 authn 表之间、与其他模块的表之间都不建外键。完整性由写入方在一个事务里显式清理与核对保证，例如成员关系的写入在账户不存在或已是墓碑时被拒。

**时间。**

- 所有写入的时间与作为参数绑定的时间，一律经 `internal/clock` 取，一律 `.UTC()`。模型路径的 `CreatedAt` 与 `UpdatedAt` 显式赋值，不靠 GORM 的 `NowFunc`。PostgreSQL 与 SQLite 适用同一条规则。

**宿主扩展用户字段。** 账户表不留自由字段。下列途径按分量由轻到重，是例举，不是封闭集；判据是不改 authn 的表结构：

- 账户属性集：条目数与大小有上限，会话载荷里来自 IdP 属性映射的键另有上限，数值写在设计文档；
- 宿主自有表，以 `AccountID` 为键，不建指向账户表的外键；
- `Provisioner`，首登开户之前改写拟创建的账户或拒绝开户；
- 生命周期事件。

**增长表的清扫。** 每张会无界增长的表有一个持有者，就是声明该表的模块，由它在 `Start` 里起有界协程清扫。各表的持有者、删什么与周期写在拥有该表的模块的设计文档里。

## 后果

账户标识的引用在账户的整个生命周期内稳定：停用、删除与重新注册都不会让一个旧引用指向另一个人。未经证明的标识不存在，预占抢注与抢占唯一约束在存储层没有入口。成员关系的读写不经租户插件，登录时的跨租户枚举不依赖 `CrossTenant`，授权缺席的装配里成员判定仍有答案。

**接受的代价：**

- **邮箱、手机号与显示名在库里是明文。** 库转储即泄露这些个人数据；盲索引与加密列不采用，保护靠库的访问控制与备份的保管。
- **没有外键，数据库不替写入方兜底。** 孤儿行靠写入方在自己的事务里清理，跨模块靠钩子与事件补偿；跨模块的抹除至少一次、非原子，崩溃窗口内的残留行不能用于认证，但抹除不保证（[ADR-authn-account-lifecycle](adr-authn-account-lifecycle.md)）。
- **成员关系表的租户隔离靠 authn 的代码，不靠插件。** 每条语句漏写租户列条件，就是一次跨租户的读写，且不报错；这张表只能经 `Memberships` 的实现访问。authn 不 import `pkg/tenant`，因此无从核对一个租户标识是否在册，租户准入由 `tenant.admission` 判（[ADR-tenant-admission](adr-tenant-admission.md)）。
- **断言的标识不是邮箱所有权的证明。** 迁移导入的用户（导入来源属断言）首次经社交或 SSO 登录时，不会因提供方声明的地址进入其账户，而须先用自己的登录方式登录再显式绑定；管理员为某人代建账户时，企业 SSO 的预置路径采信其邮箱，这是唯一的例外（[ADR-authn-external-binding](adr-authn-external-binding.md)）。
- **没有自助添加邮箱的路径。** 装配里没有邮件发送的通道，邮箱只能经 IdP 断言或管理员断言成为标识。
- **墓碑留下标识。** 审计行与授权的角色绑定里残留的是不指向任何个人数据的旧标识。`authn_impersonations` 的记录按「谁冒充过谁」保留，只含标识与冒充理由；冒充理由是管理员写的自由文本，可能含个人信息，是已知残留，保留期是宿主的合规策略。若法规要求连标识都不得留存，此决策不满足。
- **删除不可恢复。** 墓碑是终态，被删除的账户不能重新启用；同一个人再注册得到另一个账户。
- **一个没有被显式启用的账户不能认证。** 忘记设状态的创建路径得到一个无法登录的账户，失败方向是拒绝。
- **宿主要自己清理自己的表。** 宿主自有表以 `AccountID` 为键、没有外键，账户删除后其中的行由宿主订阅事件清理；订阅漏写则这些行残留。
- **接口命名受同模块重名约束。** `Memberships` 的方法名不如 `Get` 与 `Set` 对称，新增能力接口都要先查同模块的方法名。
- **每个时间值经 `internal/clock` 与 `.UTC()`，漏掉一处就是一处静默的比较错误。** 机制不拦截，靠失效条件中的 SQLite 时区测试。

## 失效条件

- **假设：SQLite 驱动按所在时区存时间文本、按字符串比较。** 这是实测所得（`glebarez/go-sqlite` v1.21.2），UTC 规则以它为据。守住它的测试：SQLite 夹具在 `TZ=America/New_York` 下用非 UTC 的 `time.Time` 写入，断言每个带时间比较的条件（会话有效性、退避锁定、刷新令牌空闲、断言去重清扫、挑战预算统计）结果仍然正确。驱动升级后行为改变，则这条规则的理由要重新比较；规则本身对 PostgreSQL 无害，不随之放宽。
- **假设：`pkg/db` 不覆盖 GORM 的 `NowFunc`。** 若它覆盖为 UTC，模型路径的显式赋值成为冗余，保留与否重新比较；对原生 SQL 路径绑定的时间，显式 `.UTC()` 仍然必要。
- **跨模块外键的否决不以 SQLite 外键开关为唯一理由。** 即便核实该开关恒开，迁移先后的隐含契约，以及墓碑行拦不住指向它的写入，仍然成立。
- **授权模块落地并要求自己持有成员关系**，或租户模块的约定放宽到可以不经 `CrossTenant` 按账户反查：成员关系归属与嵌入约定的比较要重做。
- **合规要求个人标识加密存放**：盲索引与加密列的比较要重做；`pkg/db` 的盲索引若自带规范化，并能在换根密钥时由模块自己重写，同样触发。
- **法规要求标识在抹除后也不得留存**：墓碑行保留标识的做法不满足，需要另议。
- **账户之外的数据（会话、因素、挑战）改由账户事务统一写入**，例如 `pkg/db` 提供跨模块传递事务句柄的通道：账户与它们的清理分工要重新比较。
