# 刷出落在关闭阶段，与入口排空的先后不作保证

## 状态

已接受

## 背景

一次驱动的关闭分两拍：`Stop` 停止接收新工作，`Close` 释放资源，两拍收到的 context 去掉取消、保留值。注册表不对停机施加超时，回调必须自己保证有界，而上界在上下文里表达不出来——它只能来自本模块自己的配置（见 [core](../design/modules/design-core.md) 的阶段一节、[ADR-observability-config-2026-09-22](adr-observability-config-2026-09-22.md)）。

关停会把上游 SDK 的批处理器与读数器里的在途数据刷出（见 [observability](../design/modules/design-observability.md) 的关停时的刷出）。刷出落在关闭路径的哪一拍，是本记录要定的。

关闭按逆构造序执行；构造次序按依赖定序，同一层就绪的模块取模块名字典序最小者（见 `pkg/core` 的 `planConstruction` 与 `(*Registry).shutdown`）。本模块与入口模块都不在对方的依赖闭包里，两者的相对次序由这一条决胜规则给出：本模块的模块名以 `observability` 开头（`observability.otel`，见 [observability](../design/modules/design-observability.md) 的模块名常量），入口实现的模块名以 `http` 开头（`http.stdmux`），构造时入口在前，关闭时本模块在前。

入口模块的排空从它的 `Stop` 起算、到它的 `Close` 结束，界由它自己的排空时限给出（见 [http](../design/modules/design-http.md) 的排空的界）。排空期间在途请求照常结束，照常产生跨度。

## 考虑过的选项

### 在停止阶段刷出

采纳它意味着 `Stop` 里就关停 provider。

**否决**：`Stop` 的职责是停止接受新工作，此时在途请求仍会结束、仍会产生跨度；在那一段把 provider 关停，这期间的跨度落在刷出之后，而关闭时已经没有东西可以接住它们。

### 让入口模块反过来依赖本模块

采纳它意味着入口模块的 `Requires` 里出现本模块的功能，关闭次序由这条依赖声明给出。

**否决**：那要求入口模块认识遥测，并把一个纯粹的后台命令也拖进一次它不需要的装配；顺序是命名规则的副产物，为它加一条反向依赖换来的不是顺序，而是一条本不该有的依赖边。

### 在关闭阶段不设上界，一直等到刷完

采纳它意味着 `Close` 无限等一个不肯结束的导出。

**否决**：注册表要求回调自身有界，而上界无处可来；没有第二个东西能在重启与停机路径上兜住一个不肯结束的关闭。

### 停止阶段无动作，关闭阶段以配置的上界依次关停两个 provider

采纳它意味着刷出落在关闭拍上，上界由 `shutdown-timeout` 给出，本模块与入口排空的相对位置不由本模块表达。

**采纳** — 见决策。

## 决策

采纳：**停止阶段无动作，关闭阶段以配置的上界依次关停两个 provider。** 本模块与入口模块的排空之间没有顺序保证；两者的先后由模块名的字典序决胜。

## 后果

**接受的代价：**

- **入口模块排空窗口的尾段不产生跨度。** 本模块的关停早于入口模块的在途排空结束，落在两者之间那一段的请求照常结束却不被导出（这条装配级性质见 [observability](../design/modules/design-observability.md) 的装配级性质）。这段窗口的长度取决于入口模块的排空耗时，本模块看不见它，配置也改不动它：把 `shutdown-timeout` 调长只延长刷出本身，不会把刷出挪到排空结束之后。
- **刷出超时后剩余的在途数据被丢弃，且不产生任何信号。** 这件事发生在 `Close` 内部，本模块不为它写日志行，也不报错；观测面缺口与「本来就没有数据」从外部看不出区别。
- **停机次序由模块名决定，改名会静默改变它。** 模块名是模块包导出的常量，宿主在命令树上写的是那个常量：改名会被编译期逐处拦住，次序却不受这层检查。两个名字都不是稳定性承诺的一部分，一次改名跨过字典序的分界，先后随之对调，没有一处会报。

## 失效条件

若同层模块的构造与关闭次序不再由模块名的字典序决定（例如注册表改为按显式声明的停机序），或本模块与入口模块之间出现一条依赖边，则把次序交给命名规则的判据不再成立，代价中「改名静默改变次序」那一条随之消失。
