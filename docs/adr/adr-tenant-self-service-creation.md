# 自助创建是公共模块，带上界与审计，不做人机验证

## 背景

平台管理面已有平台员工代开租户的入口。业务组织还需要一条无平台参与的创建路径：一个账户为自己的组织开一个空间。这条路径直接改变谁可以增加租户，因而必须回答三件事——创建逻辑住在哪里、一个账户能开多少、以及用什么代价换到这条路径。

创建逻辑此前写在示范宿主里。宿主实现了完整的判定、上界、锁与审计，但任何拷贝都要重写同一套逻辑，行为随拷贝漂移；创建是产品的租户能力，不是某个宿主的业务。

一个已验证的邮箱地址可以证明账户与地址的关系，但它不限制账户增加租户的次数。没有上界时，一个账户可以无限增加业务组织，名册与授权表随之增长。人机验证可以在入口处提高一次创建的成本，但它引入一个新的外部依赖与一套挑战状态，而这一轮没有可用的机制。

## 考虑过的选项

### 创建逻辑留在宿主

宿主继续实现 `POST /api/v1/orgs` 的判定、上界与审计。

**否决**：每一份宿主拷贝都要重写一遍同一套判定，行为随拷贝漂移；租户能力应当随 `pkg/` 交付，宿主只决定是否装配。

### 公共模块，无上界

把创建逻辑移进 `pkg/`，但不在账户维度设上界，依赖邮箱证明与审计发现滥用。

**否决**：已验证邮箱不限制创建次数；没有上界时，一个账户可以在一个小时内开出任意多的业务组织，名册与授权表的增长没有上限。审计记录事后可查，但不阻止增长。

### 公共模块，配上界、创建锁与审计，不做人机验证

把创建逻辑移进公共模块，按账户设活跃业务组织上界与每小时次数上界，用创建锁串行同一账户的并发请求，并为每次进入建立的尝试写强制审计行；人机验证留作后续开关。

**采纳**，见决策。

### 公共模块，配人机验证

在创建入口要求一份人机验证证明，再叠加账户维度的上界。

**否决**：这一轮没有可用的人机验证机制；引入它要新增挑战的签发、校验、一次性与过期状态，以及一个外部或自托管的验证器。上界、锁与审计已经把创建速率与持有量限在可审计的范围内，人机验证留作后续扩展，不在这一轮进入创建路径。

### 把创建限制在平台员工

只保留平台代开，不提供账户自助创建。

**否决**：产品需要账户在自己的命名空间里开组织，平台代开让平台成为每一次创建的必经环节；这同时把租户增长的上界交给平台员工的人工判断。

## 决策

采纳：业务组织的自助创建是公共模块 `pkg/tenant/selfcreate`，登记名与特性名 `org.create`，路由 `POST /api/v1/orgs` 挂在账户端；模块按固定次序判定并交给 `tenant.Provisioner`，创建者成为首任 `tenant-admin`，成员关系来源写 `initial`。

上界与保障：

- 调用方不得持有未证明的邮箱地址；没有邮箱地址的账户放行，服务账户按自己的规则拒绝。
- 一个账户最多持有五个活跃业务组织；计数只算有效成员关系、租户在册且非个人租户。
- 一个账户每小时最多创建三次；通过全部前置校验并进入 provisioner 的请求计一次，provisioner 失败也消耗。
- 同一账户的创建由一把三十秒的锁串行，并发请求只有一个进入 provisioner。
- 每次进入 provisioner 的尝试写一条强制审计行；provisioner 失败补一条关联的失败行。
- 这一轮不做人机验证。

两个数值上界是平台运行时设置：`org.create.max-organizations` 与 `org.create.max-per-hour`。声明的设置模式不设 `TenantFacing`，两个项不携带租户访问，因而只在平台层可读可写；租户设置面看不到它们，对它们的写入答 404。

开关 `org.create.enabled` 是静态配置，产品的缺省是打开，由宿主的默认文档写入；关闭时路由不挂、特性 `org.create` 缺席。

别名与用户名共用一个命名空间（[ADR-tenant-identifier](adr-tenant-identifier.md)）：别名按统一 slug 规则校验，拒绝用户名保留集里的名字，不得等于任何租户标识，并在 `tenants.alias` 的单列唯一约束上仲裁并发。

## 后果

- **宿主不再实现创建逻辑。** 宿主只装配模块、开关、配置与依赖；一份拷贝换掉业务域时，创建行为不随之重写。
- **账户可以增加租户，平台不是必经环节。** 名册与授权表的增长因此有一个账户维度的上界，而不是平台员工的人工判断。
- **多副本的上界依赖共享键值存储。** Redis、PostgreSQL、NATS 与 memcached 的键值实现让锁与计数跨副本可见；内存键值只在单副本内成立，部署必须写明这一前提，否则两个副本各自放行到上界。
- **计数限的是尝试，不是成功。** provisioner 失败也消耗一次，因而一个持续失败的账户不会无限重试；代价是一次失败会占用本小时的额度。
- **创建不做人机验证。** 上界与审计是这一轮的防滥用手段；入口的验证成本低于带人机验证的发送面。
- **别名不可复用。** 删除把租户写成墓碑，别名随行保留；同一个别名不能被另一个组织再次登记，这与标识不可复用同一条语义。
- **登记名与特性名同为 `org.create`。** 特性文档要求一个特性的首段等于声明它的模块名的首段，因此模块不能登记为 `tenant.selfcreate` 而同时声明 `org.create`；包路径仍按模块目录命名。

## 失效条件

若监管或产品要求创建入口必须有人机验证，或共享键值存储不再是部署的前提，则“不做人机验证”与“多副本上界”这两条要重新比较。

若一个账户的组织持有量需要按组织规模、计费或合规分层，则单一数值上界不再够用，上界的口径要重新裁定。
