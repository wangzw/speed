# 外部身份绑定、自动关联、首登开户与 JIT 并入的规则

## 状态

已接受

## 背景

账户是全局的，不属于任何一个租户，一个账户可以同时属于零到多个租户（[ADR-authn-accounts-2026-10-10](adr-authn-accounts-2026-10-10.md)）。登录方式除口令与短信之外，还有社交登录（Google、GitHub、微信）与企业 SSO（按租户配置的 OIDC 与 SAML 提供方）。这些方式在提供方处完成认证，交给 authn 的是一份外部身份断言：提供方、该提供方命名空间内的主体，以及可有可无的邮箱与「邮箱已验证」声明。登录引擎要把断言落到一个账户上：找到已绑定的账户、关联到已有账户、或开一个新账户。

下列事实限定了这一步的可选范围。

- 邮箱不是稳定的身份，各提供方对「已验证」的口径也不同，邮箱因此不作外部身份的键或自动合并的键；这一结论与理由由 [ADR-authn-accounts-2026-10-10](adr-authn-accounts-2026-10-10.md) 承载。Google 在部分账号上还会给出 `email_verified=false`。
- 企业 SSO 的提供方配置由租户管理员书写，其断言只对该租户的域有权威。一个租户的 IdP 管理员既能控制断言里的邮箱，也能控制主体。
- 账户全局，所以任何把已有账户并入某个提供方的动作，都把这个账户在其他租户里的访问也交给了该提供方的控制者。
- 库里的邮箱与手机标识都带验证渠道，只有真实证明渠道的标识能作并入依据，管理员断言与迁移导入渠道的标识不能；渠道的取值与判据见 [ADR-authn-accounts-2026-10-10](adr-authn-accounts-2026-10-10.md)。
- 邮件通道已在模块集合内，用户可在 authn 内以 `email-code` 自助证明邮箱所有权；邮箱标识不只经提供方断言或管理员断言进库，自助注册开户后的待验证窗口由 [ADR-authn-signup-2026-10-22](adr-authn-signup-2026-10-22.md) 决定。
- 租户成员关系归 authn 的成员关系表，登录成功本身不要求成员关系；成员关系的暂停与移除是管理员对「这个人还能不能进这个租户」的显式裁决。

假设（尚未核实，依赖它们的断言见失效条件）：微信在不同授权范围下是否下发 `unionid`、GitHub 能否把邮箱改成别人曾占用过的地址。决策不依赖 GitHub 能否把邮箱改成别人曾占用过的地址为真：邮箱不作键的理由由 ADR-authn-accounts-2026-10-10 承担，与它无关。

## 考虑过的选项

### 所有来源缺省自动并入已验证邮箱

不设开关，断言邮箱已验证且命中现有账户时一律并入。

**否决**：Google 与 GitHub 的邮箱回收风险与企业邮箱域的转手风险无法由 speed 一侧消除，提供方的「已验证」只在断言那一刻成立。缺省并入把这份风险强加给每一个部署，包括不需要这项便利的部署；风险只对愿意承担它的部署开放才成立。

### JIT 开户时并入同邮箱的现有账户（缺省开）

企业 SSO 的 JIT 提供方遇到邮箱已被现有账户占用时，直接并入。

**否决**：并入使该租户的 IdP 管理员，或已离职员工所在的 IdP，永久登录这个人在别的租户里的账户。域匹配只证明该邮箱属于该租户，不证明这个账户只与该租户有关。并入因此必须由提供方行显式选择，并限于只属于该租户、没有别的登录方式的账户。

### JIT 在每次登录时补建成员关系

不论绑定是否已存在，每次企业 SSO 登录都确保该租户的成员关系存在。

**否决**：管理员暂停或移除的成员在下一次 SSO 登录时被复活，租户管理员对成员关系的裁决被登录路径悄悄推翻。成员关系只应在建绑定的同一事务里新建，已有绑定的后续登录不读不写。

### 微信后来收到 `unionid` 时，对占用该 `unionid` 的另一个账户自动合并

补键时若 `unionid` 已绑定在别的账户上，把两个账户合并。

**否决**：两个账户各自带有会话、因素、口令与成员关系，没有任何证明它们是同一个人；自动合并把一方的全部登录事实交给另一方。冲突时以 `ErrBindingConflict` 失败，由管理员裁决。

### 自动并入成功后保留该账户既有的会话与口令

并入只增加一条绑定，其余不动。

**否决**：并入前的会话与口令不是由本次证明建立的，可能属于占位者；保留它们等于把账户连同攻击者的登录凭据一起交给新到场的登录者。并入必须撤销既有会话并删除口令凭据。

### 提供用户名加口令的自助注册

任何人可以用用户名与口令开户。

**否决**：没有邮件通道，自助注册没有验证渠道，产生的账户上没有任何可验证的标识；这类账户是垃圾账户与撞库的温床，也是预占抢注的原料。口令账户由管理面或宿主代码创建，或在社交与短信首登之后于账户设置里设口令。

该否决理由已被推翻：用户名加口令的自助注册已按 [ADR-authn-signup-2026-10-22](adr-authn-signup-2026-10-22.md) 采纳为注册即建号、开户后验证邮箱。

### 以（提供方，主体）为键；邮箱只作线索；并入与开户一律默认拒绝，放宽须显式

**采纳**，见决策。

## 决策

采纳：外部身份以（提供方，主体）为键；邮箱只作线索；自动关联、JIT 并入与首登开户各自缺省拒绝，放宽须显式选择并限定在最小范围；并入成功即撤销既有会话并删口令。规则的完整判定顺序、取值与错误映射见 authn 账户设计文档的外部身份绑定规则一节，企业 SSO 提供方行的字段见 authn 企业 SSO 设计文档，配置键见 authn 配置设计文档。

**键与主体。** 外部身份绑定的键是（提供方，主体）。各提供方的主体取法是封闭集：

- Google 取 `sub`。
- GitHub 取数字 `id`；`login` 会变，只作展示。
- 企业 OIDC 取 `sub`，命名空间是 `oidc:<IdP 标识>`。
- SAML 取 `NameID` 或提供方行映射指定的属性，命名空间是 `saml:<IdP 标识>`。
- 微信取 `unionid`；没有 `unionid` 时取 `wechat-openid:<appid>` 命名空间下的 `openid`。

**微信的补键。** 微信登录方法交出的主体取 `unionid`，没有则取 `openid` 的命名空间键，并把另一个键作为旧键别名一并交给引擎。已有以 `openid` 为键的绑定、而本次断言带来 `unionid` 时，没有账户占用该 `unionid` 就给同一账户补一条以 `unionid` 为键的绑定；已被别的账户占用则以 `ErrBindingConflict` 失败，不合并。

**邮箱只作线索。** 登录引擎不以邮箱选择账户。已有绑定的登录直接进入绑定的账户；断言里的邮箱变化不更新账户的邮箱标识，只更新绑定行里仅作展示的字段。

**社交登录无绑定时的自动关联。**

- `authn.account.auto-link` 是设置项，缺省 `never`，不关联，只有全局一档。改到 `verified-email` 是放宽方向：运行期改动写一行 Warn 并记 `authn.settings.relaxed`，启动时已是该值时写同一行 Warn。
- 缺省下仅当 `External.EmailVerified` 为真且该邮箱命中现有账户的邮箱标识时，应答 `link-required`，提示先用原方式登录再在账户设置里关联。提供方自称未验证的邮箱按没有邮箱线索处理。`link-required` 因此只对已被提供方证明拥有该邮箱的调用者给出，不构成对陌生人的枚举预言机。
- 开关设为 `verified-email` 时，自动关联要求同时满足全部条件：断言邮箱已验证；现有账户持有该邮箱的标识且标识的验证渠道是真实证明；账户为启用；该邮箱域不属于任何租户已验证的 SSO 域。微信没有邮箱，永不适用。管理员断言与迁移导入渠道的标识不算真实证明。
- 关联只改变第一因素，账户已登记的因素照常要求。

**企业 SSO 无绑定时。**

- 断言邮箱的域必须属于该提供方所属租户已验证的域，否则以 `ErrDomainMismatch` 失败。
- `provisioning` 为 `preprovisioned` 时，只匹配管理员预先建好且带该邮箱标识的账户，匹配不上即 `ErrNotProvisioned`；预置账户是管理员为这个人建的，管理员断言渠道的邮箱在此可用，迁移导入渠道的邮箱不可。
- `provisioning` 为 `jit` 时新建账户并建该租户的成员关系，成员关系来源记为 `jit:<提供方标识>`。缺省只新建、不并入：邮箱已被现有账户占用时应答 `link-required`，域匹配已由提供方的域所有权证明替代 `EmailVerified` 前提。
- 提供方行的 `merge_existing` 缺省假，创建提供方时显式选择。为真时，只并入同时满足下列全部条件的账户：邮箱标识是真实证明；全部成员关系都属于该租户；没有口令、手机、其他绑定与因素。账户可属多个租户，或有别的登录方式时，一律不并入。
- 成员关系只在建绑定的同一事务里新建。已有绑定的登录不读不写成员关系，所以被暂停或移除的成员不被复活；下线人员的处理是暂停成员关系，或在 IdP 侧停用。

**自动并入成功的副作用。** 自动关联与 `merge_existing` 并入成功时，引擎撤销该账户全部既有登录会话，并删除该账户的口令凭据，要求用户重设；本次登录建立的新会话在撤销之后创建。已登录用户经新鲜多因素显式关联不触发撤销会话与删口令。

**解绑与关联。** 解绑与显式关联要求新鲜的本地多因素，账户有因素时才要求；IdP 声明的多因素不算。解绑后账户必须至少剩一种可用登录方式，否则以 `ErrLastLoginMethod` 失败。成功后处理器撤销该账户除当前会话之外的登录会话。

**首登开户。**

- 社交与短信登录是否可首登开户由 `authn.account.signup` 决定。它是设置项，缺省 `closed`，设为 `open` 才开户；改到 `open` 是放宽方向，运行期改动写一行 Warn 并记 `authn.settings.relaxed`，启动时已是该值时写同一行 Warn。`closed` 时无绑定又无关联可走，统一应答 `login-failed`。
- 开户建启用的 `user` 账户，写绑定或手机标识，不建任何成员关系。账户能登录，访问任何租户资源得 404，成员关系由管理员或邀请授予。
- 提供方断言了已验证邮箱，且没有别的账户占用该邮箱时，同时写邮箱标识，验证渠道记为 `idp:<提供方标识>`；否则不写。微信与短信开户没有邮箱。显示名不作任何判定依据。
- 企业 SSO 的开户按提供方的 `provisioning` 执行，不受 `signup` 约束。
- 用户名加口令的自助注册经独立的匿名路由一次建号，邮箱在开户之后验证，其规则见 [ADR-authn-signup-2026-10-22](adr-authn-signup-2026-10-22.md)。

**并发。** 同一（提供方，主体）并发首登，由唯一约束裁决，失败方回读绑定后继续。

## 后果

外部身份的键由提供方保证稳定，邮箱回收、各提供方验证口径不一、预占抢注都不再能把一个人的账户交给另一个人。缺省部署里社交登录不并入任何账户、不开任何账户，企业 SSO 只新建不并入；每一项放宽是一个显式开关或提供方行上的显式选择，并带着限定的范围。一个租户的 IdP 对全局账户的权力止于该租户：它既不能并入属于别的租户的账户，也不能复活被管理员暂停的成员。`link-required` 只给已被提供方证明拥有邮箱的调用者，枚举面限定在这批人身上。

自动并入后，并入前的会话与口令都被清除，占位者在账户上预留的登录凭据不跨过并入存活。

规则的判定顺序与错误映射由设计文档承载；放宽开关的启动诊断、会话撤销与事件契约分别见 [ADR-authn-settings-and-secrets-2026-10-10](adr-authn-settings-and-secrets-2026-10-10.md)、[ADR-authn-account-lifecycle-2026-10-10](adr-authn-account-lifecycle-2026-10-10.md) 与 [ADR-authn-events-and-audit-2026-10-10](adr-authn-events-and-audit-2026-10-10.md)，企业 SSO 的域所有权证明与提供方行见 [ADR-authn-sso-2026-10-10](adr-authn-sso-2026-10-10.md)。

**接受的代价：**

- **已有账户的员工首次企业 SSO 登录得到 `link-required`。** 员工须先用原方式登录，再在账户设置里关联；租户 IdP 对跨租户全局账户的权限边界划在这里，登录的便利让位于它。
- **`auto-link` 开启时信任提供方的邮箱验证。** Google Workspace 管理员的操作、邮箱地址被回收后重新分配，都能让提供方对邮箱的断言与现实脱节；并入时的撤销会话与删口令只处理账户上已有的凭据，不处理断言本身的错误。
- **管理员写错预置账户的邮箱即错配。** `preprovisioned` 采信管理员断言渠道的邮箱，写错的邮箱把一个人的 SSO 登录匹配到另一个预置账户上；迁移导入的邮箱不经验证，由导入方负责标成迁移导入渠道。
- **并入使用户失去口令。** 自动并入后用户要重设口令；账户没有可作登录名的标识时（没有用户名也没有已验证邮箱），无法立刻设口令登录，要经管理员添加用户名或用别的方式登录。
- **`link-required` 对已被提供方证明拥有该邮箱的调用者暴露账户存在。** 这是有意接受的枚举面。
- **待验证账户在验证前受限。** 用户名加口令的自助注册得到的是可登录但邮箱尚未证明的账户；邀请他人、租户创建与变更、管理面人类写、授权与设置的写面、服务密钥创建与外部身份绑定在邮箱被证明之前都不可用，用户要先完成一次邮箱验证才能解除限制。没有装配邮件通道的部署保持注册关闭；接入真实邮件投递之后，注册带来的受限窗口才有稳定的自助解除路径。
- **成员关系不自愈。** 管理员暂停的成员，在 IdP 侧仍有效时也不会重新建立成员关系，恢复要管理员显式操作；下线人员要暂停成员关系，或在 IdP 侧停用，只做其一不能覆盖另一侧的登录路径。
- **微信 `unionid` 冲突要人工裁决。** 两个账户占用同一 `unionid` 时，引擎报 `ErrBindingConflict` 并停下，不提供自动合并的出口。

## 失效条件

下列假设尚未核实，依赖它们的断言以对应测试守住。

- **假设**：微信的网站应用扫码与公众号网页授权在各自的授权范围下，`unionid` 的下发条件与本决策的补键流程相符（先只有 `openid`、后来才有 `unionid`）。守住它的测试：对模拟的微信服务端驱动「先无 `unionid`、后带 `unionid`」的序列，断言同一账户补出 `unionid` 绑定；`unionid` 被别的账户占用时返回 `ErrBindingConflict` 且两个账户都不变。真实的下发条件需要真实应用凭据才能核实。
- **假设**：GitHub 可把邮箱改成他人曾占用的地址。决策不以它为真为前提，不需要测试守住；它为假时，邮箱不作键的理由仍由回收与口径差异承担。
- **假设**：并入、成员关系新建与绑定创建能在一个事务里完成，并在 PostgreSQL 与 SQLite 上以唯一约束裁决并发首登，不依赖 `RETURNING`。守住它的测试：并发首登同一（提供方，主体）两次，恰有一个账户与一条绑定，败者回读后登录同一账户。

下列行为各以测试守住，任何一条失败都说明规则被破坏。

- 管理员断言与迁移导入渠道的邮箱标识，在 `auto-link = verified-email` 与 `merge_existing = true` 下都不被并入。
- 自动并入成功之后，该账户并入前的会话经 `Sessions.Status` 判无效，口令凭据已删除，本次登录的新会话有效。
- 成员关系被暂停或移除的成员，经企业 SSO 再次登录后成员关系仍是暂停或不存在。
- `jit` 提供方遇到属于多个租户的账户、或带口令与其他绑定的账户时，即使 `merge_existing = true` 也一律不并入，该账户不被改动。
- 社交登录无绑定时，`link-required` 不在 `EmailVerified` 为假时出现，也不在没有邮箱线索时出现；企业 SSO 的 `link-required` 以域匹配为前提。

下列情形出现时，本决策需要重新评估。

- 部署方要求已有账户的员工首次企业 SSO 登录无需先用原方式登录。届时要给出不依赖邮箱断言的所有权证明——邮件通道已在模块集合内，邮箱确认即是一条现成的路径——并重估 JIT 并入的限定范围。
- 提供方的邮箱验证口径出现可检验的强保证（例如提供方对邮箱的回收与转手给出可校验的声明）。届时 `auto-link` 缺省值与按渠道限定并入的做法可以重估。
- 租户级的账户模型出现（账户不再全局）。届时「并入使 IdP 管理员触达别的租户」的前提消失，并入规则要整体重写。
