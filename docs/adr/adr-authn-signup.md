# 自助注册即建号，账户的邮箱只有已验证与未验证两种状态

## 背景

登录页必须提供用户名加口令的自助注册：提交用户名、口令与邮箱即得到账户，账户随后可以登录，邮箱的验证发生在开户之后（REQ-signup-003、REQ-signup-004、REQ-signup-005、REQ-signup-028）。手机号与邮箱的有效性不是开户的前提。

邮箱的验证状态是全平台唯一的一套判据，不是某一类账户的属性。管理员预置的账户、导入的账户与自助注册的账户在能力边界上必须一致（REQ-signup-023、REQ-signup-027）：同一个人换个入口被建出来，不能换一套放行规则，否则管理面与导入入口就是绕过验证的通道。这要求状态本身二值，即已验证、未验证，而不是在两者之间再放一个“管理员添加”。

决定要在下列既有约束内成立：

- **标识表只承载已写下的标识。** `authn_identifiers.verified_at` 非空，`verified_via` 非空，`UNIQUE (kind, value)`；每个账户至多一个 username 与一个 phone。`verified_via` 是写下这条标识的渠道，其中的 `admin`、`import-unverified` 与 `self` 只记录事实，不构成地址归属的证明。账户状态只有 disabled、active、deleted。
- **`Create` 只写标识，不写待验证行。** 邮箱与手机都要求一个合法的验证渠道，没有待验证的标识行。口令账户至少有一个登录名，登录名是用户名，或账户持有并已选作登录方式的已验证邮箱（[ADR-authn-login-identifier](adr-authn-login-identifier.md)、[ADR-authn-contact-and-login-ways](adr-authn-contact-and-login-ways.md)）；邮箱标识的证明渠道只决定它是否已证明，不决定它是否作登录方式。
- **会话只发给 active 账户。** 会话有效性判定读账户状态与 `valid_after`，没有 pending 账户的会话。
- **注册本身不发邮箱验证码。** 注册不写待验证的标识行，也不向提交的地址发信；自助添加邮箱经 `EmailCodeSender` 发码，验证记录挂在会话上。匿名口令重置另有一套挑战记录（邮箱以重置令牌为键，短信用 `authn_challenges` 行），那是找回口令的决定，不属于注册（[ADR-authn-mfa-recovery](adr-authn-mfa-recovery.md)）。
- **开户不建成员关系。** 新账户能登录，访问租户资源时按准入层的既有语义处理。
- **清理只针对自助注册。** 闲置账户的自动删除只挑 `signup_state = 1` 的自助注册账户；管理员经 `Create` 写的账户 `signup_state` 恒为 `0`，从不被这条清理选中。

需要接住的风险：只有用户名与口令的空账户、用户名与邮箱的枚举、批量注册、匿名邮箱轰炸、验证码猜测、以受害者邮箱预占账户的 pre-hijacking（[REF-pre-hijacked-accounts](../references.md)）。

## 考虑过的选项

### 短信首登开户、自助添加用户名、自助设口令的三步组合

注册由三个已有能力串起：短信首登开户、自助添加用户名、自助设口令。

**否决**：注册依赖手机号与短信通道，而产品要求的是用户名加口令的常规注册；登录页的注册入口不能以收短信为前提。

### 待验证账户，验证前不可登录

新增 pending 账户状态，注册后只能重发与校验验证码，验证通过后才发会话。

**否决**：会话层只认 active，验证前不可登录就需要为 pending 开一条会话特例，打穿账户状态与会话有效性的既有边界；用户也无法在登录状态完成改口令、登记多因素或补资料。用户名在验证前写入全局唯一标识，攻击者可在清理期限内置占名字。验证码本身也无处承载：没有会话就没有发起自助验证的主体。

### 只建号、按需验证

注册只写用户名与口令，不持久化验证目标；用户需要找回口令、邀请或创建租户时才添加并验证邮箱或手机。

**否决**：注册时填写的邮箱没有落点，`/auth/me` 无法表达“这个账户的邮箱尚未验证”；用“账户有没有已验证联系方式”派生信任会误伤种子管理员、社交登录账户与服务账户。

### 匿名邮箱验证码注册：先发码到地址，兑现后创建账户

注册请求先向邮箱发码，校验成功后再写账户。

**否决**：需要一套匿名调用方的邮箱挑战存储、按地址与来源的预算、抑制行与统一应答，与 `authn.sms` 对称；邮件投递从可选接口变成注册的前提；对第三方地址的邮件轰炸成为新的滥用途径。本条否决的是**注册流程**；匿名口令重置的验证码投递是另一条决定，不复用注册的建号路径（[ADR-authn-mfa-recovery](adr-authn-mfa-recovery.md)）。

### 登录流程内原子注册

在登录流程引擎里新增一个注册目的，手机号、验证码、用户名与口令在同一条流程里原子创建。

**否决**：流程引擎要新增开户路径，流程私有状态要持有口令摘要，`Proof` 与账户解析的契约随之改变；收益只是注册的原子性，而中途放弃留下的账户本来就是合法账户。

### 管理员预置与导入的邮箱算已验证，作为第三种状态

`admin` 与 `import-unverified` 渠道写下的邮箱视为“管理员添加（未经本人验证）”，既不算已验证，也不受未验证账户的限制。

**否决**：未由本人证明的地址不是证明，第三种状态是在二值的验证事实之上另加一个策略豁免。它让拦截可被绕开：任何能写一行 `admin` 邮箱标识的路径都直接放行；也要求每个门控、每个界面、每个错误码各自判断三种状态，其中“管理员添加”与“未验证”的差别只存在于判定者的解释里。产品要求的是要么验证、要么没验证，不保留第三状态。

### 管理员预置与导入的账户不适用本规则

只对自助注册的账户拦截未验证，管理员预置、导入与首登开户的账户一律放行。

**否决**：账户的来源不是验证事实。同一账户换个入口创建就换一套能力边界，管理面与导入入口因此成为绕过验证的通道；被预置的人从未证明过那个地址，而平台把管理权限按这个地址交给了他。产品要求管理员预置、导入与自助注册一视同仁。

### 没有邮箱的账户也拦截

把“没有任何邮箱”也视为未验证，直到账户添加并证明一个邮箱。

**否决**：没有邮箱就没有可验证的目标，拦截给不出验证入口，账户永远无法解除限制。手机首登、只绑微信的账户与宿主自建的服务类账户都是这种形态。

### 注册即建号、可立即登录、有邮箱而未验证受限

注册请求一次写入账户、用户名标识、口令凭据与待验证联系方式；账户立即可登录，验证在登录后完成；有邮箱而没有任何已验证邮箱的账户限制依赖可信标识的能力。

**采纳**，见决策。

## 决策

采纳：**自助注册经独立的匿名路由一次建号，账户立即可登录；账户的邮箱只有已验证与未验证两种状态；有邮箱而没有任何已验证邮箱的账户受限，邮箱被证明后解除。判定适用于所有用户账户，与账户的来源无关。**

- 注册路由是 `POST /api/v1/auth/register`，请求体要求用户名、口令与邮箱；一次事务写入 active 账户、`via=self` 的用户名标识、口令凭据与一条未证明的邮箱预留。注册不发送邮件，不建立会话，不写任何待验证的标识行。
- 判定是二值的：账户持有至少一条 `Verification.Proves()` 为真的邮箱标识即**已验证**；否则持有任何邮箱（任一渠道写下的邮箱标识，或一条未证明的邮箱预留）即**未验证**；没有任何邮箱即不适用本规则，不拦截。不存在“管理员添加（未经本人验证）”这类第三状态。
- 判定适用于每一个 `KindUser` 账户：自助注册、管理员经 `Create` 预置、导入、首登开户与企业 SSO 开户写出的账户一视同仁。`KindService` 没有可验证的邮箱，不适用本规则。
- `admin`、`import-unverified` 与 `self` 渠道写下的邮箱标识都视为有邮箱而未验证；未证明的邮箱预留同样是未验证账户的目标地址。两类目标的区别只在于前者已经是一条已登记的标识，后者不是；未证明的标识不能被选作登录方式。
- 未验证账户可以登录，除验证相关动作外受限；没有会话就没有承载验证码的主体，所以登录必须允许。验证入口是账户验证节与既有的自助邮箱验证码回路：向目标地址发码、兑现后写 `verified_via = email-code` 的邮箱标识。真实证明还包括 `idp:<提供方标识>`；`invite` 属于断言渠道，不构成证明。
- 管理员预置的邮箱经 `AccountAdmin.AddIdentifier` 的幂等证明转为 `email-code`：同一账户已经持有的邮箱标识由证明渠道就地提升，不新增第二行，也不以未证明渠道覆盖已证明的行。
- 验证前的限制范围是封闭集：允许登录、本人资料读写、改口令、多因素与通行密钥登记、添加并验证邮箱或手机、退出与撤销本人其他会话、接受他人发来的邀请；禁止邀请他人、租户创建与变更、管理面人类写、授权与设置的写入接口、服务密钥创建、外部身份绑定、冒充发起。短信验证手机不改变验证状态。
- 状态门控在身份确定之后，授权判定、强度与新鲜度判定以及业务逻辑之前执行；它只可能多拒绝，不可能放行，因此不构成越权。读取状态失败答 503，不按放行处理。
- 未证明的邮箱预留不是标识：它不是登录名，`Lookup`、口令登录名与外部身份的绑定判定都看不到它。
- 清理条件不变：只删 `signup_state = 1`、`signup_verified_at` 为空、没有任何真实证明邮箱且长期未登录的自助注册账户。管理员预置与导入账户的 `signup_state` 恒为 `0`，永不因未验证被清理。
- 注册开关 `authn.account.password-signup` 为设置项，缺省 `closed`，与既有 `authn.account.signup` 相互独立。
- 账户状态不新增取值；验证状态是账户上的独立事实，不进入会话、身份或访问令牌。
- 各条款的细节由账户、登录、用户档案、威胁、配置、前端与示范宿主的设计文档给出，本记录不重述。

## 后果

注册得到的是立即可登录的账户，邮箱验证是账户上的后续动作；标识表仍只承载已写下的标识，口令登录名与外部身份的绑定判定读取这些标识的方式不变。管理员预置与导入的账户与自助注册的账户共用同一套判定与同一个验证入口。

**接受的代价：**

- **用户名是否被占用以 409 暴露。** 匿名注册入口不依赖短信成本，占用探测的上界改由来源预算、全局预算与按用户名退避给出。
- **匿名注册是新的滥用途径。** 注册不发送消息，人机验证因此闸不到它；平台也不做行为风控与一次性邮箱识别。邮件轰炸在注册阶段被“不发任何邮件”挡住，账户登录后向任意未占用地址发码：人机验证打开时每次发码先核验证明，另受按地址、按账户与全局预算约束（[ADR-authn-human-verification](adr-authn-human-verification.md)）。
- **邮箱投递是解除限制的前提。** 没有装配邮件通道的部署保持注册关闭；管理员预置与导入的账户同样停在未验证，直到部署能投递验证码。运行期就是这种装配时，管理员自己也放行不了管理面。
- **管理员预置的账户首次登录即受限。** 预置时写的邮箱是管理员的断言，不是本人的证明。首次登录后必须在账户页的验证节向该邮箱发码并兑现，管理面才放行；预置账户在证明之前不能做管理面的人类写。这是预期行为，不是故障。
- **待验证账户会存在。** 长期不验证且从未有已验证联系方式的自助注册账户需要清理；清理是删除账户的破坏性动作，默认期限由设置给出。管理员预置与导入的账户不被这条清理选中，验证状态由本人证明或管理员处置（停用、删除、改写邮箱）结束。
- **手机验证不解除限制。** 手机可以作为登录方式或额外安全因素，但只有邮箱被证明才解除敏感能力限制。
- **删除最后一个已验证邮箱会让账户不再受限。** 删除之后账户可能一条邮箱也不剩，判定落到“没有邮箱”，不适用本规则。删除是对已验证地址的破坏性操作，受限能力不会因此获得任何它此前没有的资格；要在有邮箱的状态下重新受限，账户必须先添加一条邮箱。
- **未证明的邮箱标识不是登录方式。** 管理员或导入新写下的邮箱在 `authn_identifiers` 里，但这类新写入的未证明值不能被选作登录方式，也不能用于口令登录，账户仍受限；旧行为写下的邮箱标识按其写入方式继续工作（[ADR-authn-contact-and-login-ways](adr-authn-contact-and-login-ways.md)）。未证明的邮箱预留不是标识，也不是登录名。
- **注册与验证都不是会话的创建点。** 客户端注册后需要调用既有登录流程；自动登录失败时退回登录表单。
- **新增宿主可见的路由与公共接口。** 新路由、发现字段与账户创建参数进入发布对账。

## 失效条件

产品要求未验证账户不得登录，或要求管理员预置与导入的邮箱无需本人证明即算已验证，或要求没有邮箱的账户也必须受限，或要求匿名邮箱验证码先于账户存在，本决定的前提不再成立。
