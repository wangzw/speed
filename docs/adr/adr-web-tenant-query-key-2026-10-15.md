# 租户作用域的 query key 由框架提供工厂与逐出助手

## 状态

已接受

## 背景

多租户下，一个用户在某个租户下读到的数据不能出现在另一个租户的界面里：切换租户之后，前一个租户的缓存必须逐出，否则新租户的界面会显示旧租户的数据。

生成面刻意与租户无关。`@speed/api-sdk` 是 orval 生成的（`web/packages/api-sdk/src/index.ts`），它的 query key 是裸的 spec 路径，不带租户维度；`web/packages/api-sdk/AGENTS.md` 记下这条——生成代码里没有租户头、没有租户 query key，租户上下文只经访问令牌传递，`tenant_id` 只在认证片段的类型里出现。

今天的租户分域是消费者壳的纪律，不是框架能力：`web/packages/tenancy-ui/README.md` 把 `queryClient.removeQueries({ queryKey: ['tenant', oldId] })` 写成宿主在 `TenantSwitcher` 的 `onSwitched` 里的工作，`examples/reference-app/web/src/tenant-query-key.ts` 是宿主自己写的一份键形状加逐出。键形状与逐出时机因而会按宿主数各写一遍。

## 考虑过的选项

### 把租户维度放进 api-sdk 生成的 query key

**否决**：生成面必须保持与租户无关。做到这一条要么手改生成产物（破 `src/index.ts` 的 DO-NOT-EDIT 头），要么让 orval 持有一个它不认识、也无法在生成期取得的运行期维度。且生成的裸 spec 路径键是跨租户稳定的资源标识；把租户段塞进生成键会让每一处生成的 hook 都多背一个运行期维度，而多数操作与租户无关。

### 让每个宿主壳自定义键形状与逐出助手

**否决**：键形状与逐出时机是会出缺陷的地方——把键当成跨租户稳定、或漏逐某一个前缀，都会让上一个租户的数据留在新租户下。让每个宿主复制这套纪律，等于把这类缺陷按宿主数复制，而它们本可以定在一处。

### 由框架提供租户作用域的 query key 工厂与逐出助手，生成面保持租户无关

**采纳**，见决策。

## 决策

采纳：**租户作用域的 query key 由框架提供工厂与逐出助手，`api-sdk` 的生成面保持与 tenant 无关。**

- 工厂把租户标识作为最外层段拼在生成的裸 spec 键之上，一个租户下的全部读共用一个前缀。
- 逐出助手在租户切换提交后按该前缀逐出前一个租户的键。
- `@speed/api-sdk` 的生成面不变：query key 仍是裸 spec 路径，无租户头、无租户 query key；租户上下文仍只经访问令牌传递。
- 会话结束的整棵逐出（`web/packages/product-shell/src/bootstrap.tsx` 的 `bootstrapSpeedApp` 会话结束默认）与租户逐出并存：租户切换逐出租户段，会话结束逐出整棵缓存。

## 后果

宿主不再自定义键形状与逐出时机，一处定义；切换租户后旧租户的数据不再残留。生成面继续与租户无关。

**接受的代价：**

- **框架包背上一个与 react-query 键形状绑定的约定。** 键的最外层段保留给租户，业务自定义的键要服从这一约定；绕过它、自造一个顶层键，就失去逐出助手的覆盖，这类键只能靠会话结束的整棵逐出来兜底。
- **约定在类型系统里无强制。** 一个生成的裸键与一个租户前缀键类型相同，编译器不阻止一个裸键被直接用；纪律靠工厂的默认路径与代码审查守住。
- **逐出以租户段为界。** 一个在租户段之外缓存的键——身份域的行——逐出助手够不到；这类键的正确性是「租户切换逐出租户段」与「会话结束逐出整棵」合起来的结果，只看其中一条会漏。

## 失效条件

- 若 orval 或其继任者原生支持 query key 前缀或 transformer，工厂可以退回生成层，本决策要重新评估。
- 若租户上下文不再只经访问令牌传递——例如改为显式租户头——生成面与租户无关这一前提不再成立。
