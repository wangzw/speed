# 已提交写入的宣告在写入的事务里暂存，提交之后由中继发布

## 状态

已接受

## 背景

事件总线的发布独立于调用方的事务，投递承诺只到"总线接受了这次发布"为止（[ADR-event-delivery-2026-09-21](adr-event-delivery-2026-09-21.md)）。一个要宣告自己写入的发布方因此只有两个时机，两个都不成立：

- **提交之后发布**：总线拒收——连接断开、后端拒绝写入、总线正在停止——时写入已经提交，事件就此丢失，写入却留下。一笔成交写进了库，而只从它的事件得知成交的投影与对外回调永远不会知道。
- **提交之前发布**：总线接受之后事务仍可能回滚，订阅方收到一个从未发生的写入的宣告。

发布方自己补不上这个缺口。在提交之后重试，进程可能在重试之前退出；要让宣告活过进程，就得把它和写入存在一起，再写一个读它、发它、在多个副本之间分摊它的循环。这正是一项模块该给的能力，每个宿主各写一份只会各错各的。

总线已经为消费方准备好了重复到达的处置：事件带标识，要只处理一次的消费方按它去重（[ADR-event-delivery-2026-09-28](adr-event-delivery-2026-09-28.md)）。

## 考虑过的选项

### 维持现状，发布失败由发布方处置

**否决**：发布方能做的只有记日志或补偿。日志记下了丢失，补不回事件；补偿要发布方为每一种写入写一个反向操作，而补偿本身同样可能失败，失败时写入与宣告仍然不一致。

### 在事务里同步发布，总线拒收即让写入失败

写入与发布放在同一个事务闭包里，发布失败就回滚。

**否决**：仍然不同成同败。总线接受之后提交可能失败，事件宣告了一次没有发生的写入。它还把总线的一次故障变成写入的故障：总线不可用的整段时间里，每一个要宣告的写入都失败，而那些写入本身没有任何问题。

### 总线的 `Publish` 接受调用方的事务

`Bus` 增加一个带事务的发布方法，由实现把事件写进调用方的事务。

**否决**：进程内、Redis 与 NATS 实现无从在一个数据库事务里写入，只有 PostgreSQL 实现在总线与写入同库时做得到，一项跨实现的接口承诺于是只在一种部署下成立。`Bus` 的签名还会带上 `*gorm.DB`，事件根包被每一个发布方 import，GORM 随之进入每一个发布方的闭包（[ADR-event-scope-2026-09-21](adr-event-scope-2026-09-21.md)）。

### 两阶段提交

数据库与总线的后端共同参与一个分布式事务。

**否决**：各总线后端都不提供参与方的协议，`database/sql` 与 GORM 也没有协调者；部署因此被限定在支持它的后端组合上。

### 事务内暂存，提交之后由中继发布

事件写进调用方事务里的一张表，与写入一同提交或回滚；一个中继在提交之后读这张表，把事件交给总线，总线接受才删除那一行，拒收就留着再发。

**采纳**，见决策。

## 决策

采纳：**要与写入同成同败的事件，在写入的事务里暂存，提交之后由中继发布。**

- 暂存写在数据库功能交付的那个库里的一张表上，写在调用方的事务里、调用方的连接上。事务回滚，暂存随之消失；事务提交，暂存随之可见。
- 中继在提交之后把暂存的事件交给总线，总线接受才删除它，拒收就在延迟之后重发，一直到接受为止，不设上限，不转存别处。
- 事件携带暂存时的标识，每一次发布都是同一个值，消费方按它去重。
- 承诺是**至少一次**：事务提交了，事件至少被总线接受一次；事务回滚了，事件永不发布。
- 总线的发布保持原样，仍然独立于任何事务；暂存是另一项功能，由要它的发布方取用。

## 后果

一个写入与它的宣告成为一件事：订阅方要么在写入可见之后得知它，要么永远不会得知一个没有发生的写入。总线拒收只推迟宣告，不丢失它。

**接受的代价：**

- **至少一次而不是恰好一次。** 总线接受之后、删除那一行之前中继中断，删除失败，或者认领被别的中继接管，都让同一个事件再发一次。重复的来源多了一种，去重仍归消费方，而不去重的消费方会把它处理两次。
- **宣告晚于提交。** 暂存它的副本上是几十毫秒，那个副本上的暂存再密集也推迟不了读表；其余副本上至多一个读表间隔；总线拒收期间没有上界。依赖"发布返回时订阅者已处理完"的进程内总线用法不再成立：订阅者在中继的协程与上下文上运行，不在发布方的；收到的载荷是传输的形状，不是发布方的具体值。
- **每个宣告多一次写入。** 暂存是调用方事务里多出来的一行，中继每发一个事件还要删除它；服务所用的角色要有这张表的读写权限。
- **载荷以明文落库**，直到总线接受。凭据挡在载荷之外原本就是发布方的义务，暂存让违反它的后果从"经过总线"变成"存在库里"。
- **只能在交付的库上暂存。** 写入在另一个库上的发布方用不了它：那个库没有这张表，也没有中继读它。
- **每个副本都在读这张表**，没有事件时也按间隔读，这是没有提交通知的代价。

## 失效条件

若总线的实现普遍改为与业务数据同库、能在调用方的事务里写入，暂存表与中继就是多出来的一层，本记录应被取代。
