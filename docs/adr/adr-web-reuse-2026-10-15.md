# 现有前端原地复用，旧树改名保留

## 状态

已接受

## 背景

`web/` 下已有一批前端包，是早先实现的一部分：契约边界、分层与装配形态都已成形，但整棵树冻结于仓库自身的某次改动之后再未动过，且其 SDK 由早先实现的契约文件生成，与当下的后端模块不产生任何契约。同时后端一侧正在补齐一套可直接拷贝使用的产品骨架，它需要一个前端应用；那个应用要用到 `web/` 已交付的包。

摆在面前的是两条互斥的处置：把它们当作要保留的旧物丢开、另起一棵，或是在原地把它们接上新的契约来源继续演进。

## 考虑过的选项

### 另起一棵前端树，旧树删掉

**否决**：包的分层、契约边界与装配形态是已经付过代价的结论，另起一棵会把它们重推一遍；而旧树里可用的东西——设计令牌、i18n 协商链、组件族、传输运行时——都还在。删掉它们不是清理，是重做。

### 原地就地改造，不留旧树

**否决**：改造会整份重生成 SDK、改多个包的类型引用、移出若干不再对应的包，这是一段无法在中途安全回退的工作。没有一份完整的旧快照，一次错误的批量替换就没有参照可比。

### 旧树改名保留，新的 `web/` 从它拷出要用的包再改造

**采纳**，见决策。

## 决策

采纳：**`web/` 整体改名为 `web-legacy/` 并永久保留、纳入版本控制；新的 `web/` 从它拷出要留的包，再在新树里改造。**

- 旧的 `web/` 是**改名**而非复制出去：它留在仓库里，与仓库其它早先实现并列，照常进自检的扫描面，**不随改造消失**。
- 新的 `web/` 里那些包是**拷来的**，不是搬来的——搬走旧树就不成其为完整快照，回退没有参照。
- **契约来源换成新的后端产物**：SDK 由后端模块声明的 OpenAPI 片段合并后的文档生成，`orval.config.ts` 的输入随之改指；早先实现留下的那份契约文件与新的后端无关，不再被生成面读取。
- **不再对应的包移出**：后端不做计费，对应的前端包因此不在新树里。
- **前端门禁进 `make check`**：新增的前端腿（安装、静态检查、类型检查、测试、构建）由 `make check` 带上，与仓库其它门禁同一入口。

## 后果

前端包继续在原处演进，分层与契约边界的既有结论原样保留；后端契约成为 SDK 的唯一来源，生成面不再对着两份契约。

**接受的代价：**

- **仓库里多留一棵完整的前端树。** `web-legacy/` 与新的 `web/` 并存，二者只在包的内容上重合、在依赖协议与契约来源上不同；改名那一步在版本历史里是一大批文件的删除与新增，改名检测能配成对，但那仍然是很大的一笔。
- **旧树的存在会诱导误改。** 两棵树的包同名，改动必须确认落在新树；这靠目录区分，没有编译期保护。
- **门禁的覆盖面由此扩大到前端。** `make check` 从只跑 Go 模块变成还要装一次前端依赖并跑它的检查，单次用时上升，且前端工具链成为运行仓库门禁的前提。
- **不进持续集成的流水线。** 仓库的持续集成此前已被移除，前端腿只接进 `make check`，不恢复流水线；前端门禁因此只在本地与将来的流水线入口上生效。
- **被移出的包没有去处。** 它们的代码随旧树留在 `web-legacy/` 里，不再被任何应用消费。

## 失效条件

- 若新的后端契约与早先实现那份趋于一致，两棵树的包重新重合，保留旧树的价值随之下降。
- 若 `web-legacy/` 长期不再被任何人读取（例如新的契约与包已稳定演进过若干轮），它的存在只是在分摊新树的辨识成本，届时可以删。
