# 自助注册与首登开户在建号之前取得用户名，用户名须 URL 安全并排除保留用户名

## 背景

登录名是用户名或邮箱，口令登录按其中一个识别账户（REQ-signin-006）。用户名没有所有权可证，写入时按断言渠道记账，一步生效（[ADR-authn-selfservice-identifier](adr-authn-selfservice-identifier.md)）；带口令凭据的账户至少保留一个登录名（[ADR-authn-login-identifier](adr-authn-login-identifier.md)）。自助注册在开户时要求用户名（REQ-signup-004，[ADR-authn-signup](adr-authn-signup.md)）。

社交登录、短信验证码与企业 SSO 的即时开通都会在首次登录时开户（REQ-signup-017、REQ-signup-012、REQ-signin-022）。这些路径的开户结果必须包含一个可作口令登录名的用户名；账户没有用户名、也没有邮箱标识时无法设置口令（REQ-account-012），只能以手机或外部身份登录。

需要成立的条件：

- **开户即完整。** 账户在创建时就应当持有一个可作口令登录名的用户名；把用户名留到事后补，允许账户长期缺一个登录名。
- **取值可放进 URL 路径。** 用户名今天不出现在任何 URL 里；将来若把用户名放进路径段，字符集必须保证整段无需转义，编码不得成为取值的一部分。
- **不与系统面撞名。** 系统持有一批路径与名字（接口路径、控制台、静态资源、健康检查等）。账户取用这些名字时，将来用作路径或展示会与系统面混淆。
- **写入面不止一处。** 匿名口令注册、首登开户的用户名一步与账户面添加用户名写同一个值，规则必须在每一处一致。
- **存量账户继续工作。** 库中已有不带用户名的账户，它们仍以邮箱、手机或外部身份登录，账户面仍可补用户名。

## 考虑过的选项

### 自动生成用户名

新开户时由系统生成一个用户名，随机串或从邮箱派生，保证每个新账户都带一个，持有人之后可以改。

**否决**：用户名是登录名，持有人要用它登录；系统生成而持有人不知道的值仍要改一次才能用，换来多一次改名与多一次撞名。从邮箱派生的值复刻了邮箱的一部分，邮箱改名前后还会争同一个名字。命名权也从持有人手里移走。

### 先建号，再由完成设置页补用户名

首登开户先建没有用户名的账户，再用一次性提示与完成设置页催持有人补名，补名之前口令设置不可用。

**否决**：约束在建号时刻不成立，账户可以先于用户名存在，补名可以永远不发生。完成设置页与一次性提示因此要长期为「新账户还没有用户名」保留一条分支，判据与界面都多一个状态。

### 用户名可选

新账户可以没有用户名，用社交身份、短信或邮箱登录；用户名只在需要口令登录时补。

**否决**：用户名从账户必备的登录名降为可选装饰，口令登录名长期只剩邮箱；首登开户而账户没有邮箱时，口令登录无从建立。将来按用户名寻址一类的用途也没有全集可依赖。

### 建号之前取得用户名

自助注册、社交首登开户、短信首登开户与企业 JIT 首登开户在创建账户之前取得一个合法用户名，没有合法用户名就不建账户；用户名须 URL 安全并排除保留用户名；存量无用户名的账户不回溯补名。

**采纳**，见决策。

## 决策

采纳：**自助注册、社交、短信与企业 JIT 的首登开户、邀请受理、管理面预置与初始装配在创建账户之前都必须取得一个合法用户名；没有合法用户名就不建账户。用户名须 URL 安全，且不得落在保留用户名清单内。存量无用户名的账户不回溯补名；导入既有账户不受此限，它复原历史账户而不是开立新账户。**

- **建号前取得。** 自助注册在请求体里要求用户名（REQ-signup-004）。首登开户在判定「要开户」之后、写入账户之前索取用户名，用户名不合法时不开户。管理面预置在建账户的请求里要求用户名；导入路径可以不带，它写的是既有账户（REQ-account-060）。
- **取值规则。** 先 NFKC，再转小写；长度为 3 到 64 个字符，字符集为 `[a-z0-9._-]`；首字符为字母或数字；不得以静态凭据表的前缀（`static.`）起头；不得是 UUID 形状；全部账户内唯一。每一处写入用户名的路径都走同一个规范化与校验。
- **URL 安全是保证，不是寻址规则。** 规范化后的字符集是 RFC 3986 非保留字符的子集，把用户名作为 URL 路径的一段使用时不需要转义。用户名今天不出现在任何 URL 里，本决定不引入这种用法。
- **保留用户名清单。** 清单是内置缺省清单（`api`、`console`、`account`、`admin`、`system`、`login`、`logout`、`signin`、`signup`、`static`、`assets`、`health`、`ready`、`metrics`、`oauth`、`callback`、`well-known`、`www`、`root`）与部署经设置 `authn.account.reserved-usernames` 追加的集合的并集。写入用户名的每个入口都拒绝清单内的值；设置读取失败时内置清单仍然生效。
- **写入面一致。** 匿名口令注册、首登开户的用户名一步与账户面添加用户名适用同一套取值规则与同一份保留用户名清单（REQ-signup-004、REQ-account-008、REQ-account-038）。
- **拒绝的语义。** 保留用户名是取值不合法，与被其他账户占用是两种结果；两者不合并为同一种拒绝，界面与调用方分别呈现。
- **存量账户不回溯。** 没有用户名的账户保持现状：可以用邮箱、手机或外部身份登录，账户面仍可添加用户名（REQ-account-008、REQ-account-012、REQ-account-022、REQ-account-050）。系统不为其批量生成或补写用户名。
- 规范化函数、保留用户名清单的读取面与拒绝所用的错误码由账户、登录与配置的设计文档给出，本记录不重述。

## 后果

新开的账户在创建时即可作为口令登录名使用，首登开户与自助注册在这一点上一致；用户名的字符集保证它能作为 URL 路径的一段使用而不需要转义；保留用户名清单把系统路径与名字挡在账户名之外。存量无用户名的账户照常工作，系统不为它们批量补名。

**接受的代价：**

- **每一次会开户的首次登录多一步。** 社交、短信与企业 JIT 的首次登录在开户之前多出一个用户名输入；用户不填或填了不合法的值，本次登录不建账户。这是开户前取得用户名的代价。
- **存量账户长期没有用户名。** 新开的账户有用户名，旧账户可能没有。读账户资料的一方不能把「有用户名」当作新账户的判据；完成设置页、一次性提示与按登录名判定的能力边界都要同时容纳有用户名与没有用户名的账户。
- **新开户与旧账户的口令登录名边界不同。** 新开户的账户可以用用户名登录；旧账户在补名之前只能用邮箱、手机或外部身份，没有邮箱的旧账户无法设置口令（REQ-account-012）。
- **保留用户名清单要维护。** 内置清单是字面集合，新增一个系统路径或名字必须同时改内置清单与可能的部署追加集；部署遗漏一个名字，账户就可以占用它。清单不做同形字折叠：用户名只允许 `[a-z0-9._-]`，同形字在规范化阶段已被字符集拒绝。
- **保留用户名的拒绝要与占用冲突分开呈现。** 界面与 API 调用方要能区分「这个名字不能用作名称」与「这个名字已被占用」，文案与错误码各自成立。
- **寻址的前提收窄。** 用户名全局唯一；将来若以用户名作为路径段，改用户名会使旧路径失效。本决定只保证字符集安全，不承诺寻址稳定性。

## 失效条件

- 产品允许某个开户入口在不取得用户名的情况下建账户（例如完全由提供方或系统命名的账户），建号前取得的约束不再普遍成立。
- 保留用户名的内置清单无法覆盖新增的系统面，而部署又不维护追加集，字面清单的反混淆作用不成立；届时应改为按结构判定。
- 存量无用户名的账户全部迁移或删除，「不回溯」条款失去对象，规则可以收窄为「所有账户都有用户名」。
- 用户名被用作需要可回收或可改写的寻址键，与全局唯一的取值规则冲突时，取值规则要重新裁定。
