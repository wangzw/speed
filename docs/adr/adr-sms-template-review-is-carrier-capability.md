# 逐模板的厂商审核是载体的能力，不是能力的普遍不变量

## 背景

短信厂商对模板的处理分两类。阿里云（[REF-aliyun-sms](../references.md)）与腾讯云（[REF-tencent-cloud-sms](../references.md)）要求每一个模板都预先审核：发送时只能引用审核通过的编号，审核按语言分别给出，未过审的模板不能发送。AWS Pinpoint（[REF-aws-end-user-messaging-sms](../references.md)）的 `SendTextMessage` 直接收一条正文，厂商没有逐模板审核；Twilio 的 Content API（[REF-twilio-content-api](../references.md)）把正文登记成一个内容资源并返回 SID，同样没有逐模板审核。

此前的设计把「逐模板审核」当作能力的普遍不变量：每条运行期模板起于 `Pending`，每个语言各记一条审核状态，可发送的条件是该语言的状态为 `Approved`。这个不变量对没有逐模板审核的厂商不成立——它们要么被迫报告一个厂商从未给出的状态，要么在启动时就没有一条能通过的模板。

约束如下：

- 调用方必须能判断一条模板此刻可不可以发送。这个判断落在注册表的 `Resolve` 上，不落在厂商的错误应答上：一条注定失败的发送不该等到第一次调用才暴露。
- 本能力不得伪造厂商的状态。`Approved` 的含义是厂商审核通过；一个厂商没有审核，`Approved` 就是假的。`Unknown` 也不行，它的含义是这条审核存在而本进程不跟踪它，与「不存在审核」是两件事。
- 逐模板审核是载体的性质，不是消息的性质。同一个模板集挂到不同的载体上，审核的有无随之改变。
- 管理面必须能回答它挂的是哪一种载体，否则无法向运维解释为什么某条模板没有审核。

## 考虑过的选项

### 保持普遍审核，没有审核的厂商一律报告 `Approved`

让所有载体都把模板视为已过审，统一发送条件为 `Approved`。

**否决**：这伪造了厂商的状态。`Approved` 在阿里云与腾讯云上是一个真实的审核结论，一个从不审核的厂商得到同一个词之后，运维与调用方再也分不清「厂商审核过」与「厂商不审核」。日后某个厂商开始审核，也没有一个区分点可以把新状态表达出来。

### 保持普遍审核，没有审核的厂商让模板停在 `Pending`

维持单一状态机，没有审核的载体不推进状态。

**否决**：`Pending` 的含义是一条审核正在进行。把它用在一个根本没有审核的模板上，可发送条件永远不成立，载体在启动后一条也发不出去。要让它能发，只能特判载体种类，等于在没有名字的地方引入这个区分。

### 取消审核跟踪，模板一声明就发送

不记任何审核状态，注册表只做结构校验，发送结果由厂商的错误应答决定。

**否决**：阿里云与腾讯云的强制审核没有消失。取消跟踪不会让未过审的模板变成可发送，只会把失败从启动、装载与写入推迟到第一次发送，而那正是本能力的校验要提前的地方。一条在启动时就能读出的缺陷，不该等到生产流量里才发现。

### 载体声明是否逐模板审核，新增 `ApprovalNotRequired`

载体在 `CarrierModel.Review.PerTemplate` 里声明自己有没有逐模板审核；没有时模板的每个语言是 `ApprovalNotRequired`，可发送条件接受 `Approved` 与 `ApprovalNotRequired`。

**采纳**，见决策。

## 决策

采纳：**逐模板的厂商审核是载体的能力，由 `CarrierModel.Review.PerTemplate` 声明，不是能力的普遍不变量。**

- **两种载体。** `Review.PerTemplate` 为真的载体（阿里云、腾讯云）按语言跟踪审核，每个语言起于 `Pending`，可发送的条件是该语言 `Approved`。`Review.PerTemplate` 为假的载体（AWS、Twilio，[REF-twilio-messaging](../references.md)）不跟踪审核，运行期模板的每个语言是 `ApprovalNotRequired`，`Approval` 答 `ApprovalNotRequired`，`Offer` 不等待审核结果。
- **新增审核状态 `ApprovalNotRequired`。** 它表示厂商没有这条审核；`ApprovalUnknown` 表示这条审核存在而本进程不跟踪它。两者不可互相替代。
- **可发送的状态是 `Approved` 与 `ApprovalNotRequired`。** `Pending`、`Rejected`、`Withdrawn`、`Unknown` 仍然不可发送。
- **结构校验随载体收紧。** `Review.PerTemplate` 为真时每个语言必须带厂商编号——审核的对象就是编号；为假时不要求编号，正文足以让载体构造发送请求或在厂商侧创建内容资源。
- **管理面读到这份声明。** 载体路由报告 `CarrierModel`，运维据此知道当前载体是否有逐模板审核。

## 后果

一条模板在任何载体上都能得到「此刻可不可以发」的明确答案，而这个答案来自厂商真实的处理方式，不是一份所有厂商共用的近似。

**接受的代价：**

- **可发送条件变成两个取值。** 任何自行比对审核状态的调用方都必须同时接受 `Approved` 与 `ApprovalNotRequired`；只认 `Approved` 的调用方会在没有审核的载体上拒绝每一条模板。本能力内部的所有判定都按两个取值实现，但调用方写在自己一侧的检查不在本能力的控制范围内。
- **`ApprovalNotRequired` 与 `Unknown` 必须始终分开。** 把两者合并会让一条本进程不跟踪的审核被当作「不需要审核」而放行，正好放过了最需要拦下的情形。两者在词表、存储、视图与判定里各占一个取值。
- **没有审核的载体上，后台轮询没有可读的状态。** 轮询只读 `Pending`，`ApprovalNotRequired` 与 `Unknown` 都不轮询；运维不能把轮询当作「厂商尚未回复」的指示。
- **载体切换审核方式是一次宿主可见变更。** `Review.PerTemplate` 改变会改变模板所需的结构（是否必须带编号）与可发送条件，现有的模板行可能不再满足新载体的模型，启动时的结构校验会拒绝它们。
- **带审核的模板不能原样搬到不审核的载体上。** 编号属于原厂商，`carrier` 列把行按载体隔开；换载体需要重新声明模板，而不是改一个配置项。

## 失效条件

- 某个厂商在两种审核方式之间改换，使 `Review.PerTemplate` 不再是厂商的稳定性质。此时按载体声明的方式需要重新评估，可能要引入更细的能力描述。
- 出现一种既非逐模板审核、也非完全无审核的中间形态（例如按发送方身份审核、按用途审核）。此时 `PerTemplate` 这一个布尔值不足以表达，应重新设计审核能力的结构。
