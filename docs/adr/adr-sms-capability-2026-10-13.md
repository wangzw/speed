# 短信发送能力抽为顶层能力模块，载体不感知用途

## 状态

已接受

## 背景

短信的**发送**能力（载体接缝与阿里云、腾讯云适配）与短信的**验证码状态机**（挑战行、预算、尝试次数、校验、发送队列与指标）原在同一模块 `pkg/authn/sms` 里，作为认证树的子包。但「按模板把一条短信发出去」与认证无关，是一件通用基础能力，与 `pkg/kv`、`pkg/event` 同级。

约束如下：

- **国内厂商只收预先审核通过的签名与模板，不收自由文本**；模板按语言分别审核；位置参数厂商（腾讯云）还要求参数按审核时的次序给出。通用接口因此必须以模板为中心，把「模板」做成一等声明。
- **现状已经模板化**：`authn.SMS` 的字段是模板键加参数，不是自由文本。不通用之处只在：模板键的词表是认证的（`login`、`mfa`、`enroll`）、载体配置硬编码这组用途、语言常量取自认证根包、命名空间与整棵树挂在 `pkg/authn` 下。
- **Go 的 `internal` 规则**禁止 `pkg/sms/**` import `pkg/authn/internal/literal`，而两家载体都用它登记凭据的脱敏匹配器；它另被四个登录叶子共用。发送能力离开认证目录时，这个包必须上移到共享单元的位置。
- 认证侧的状态机、预算与队列不因发送能力外移而改变；去掉的只是发送方那一段。

## 考虑过的选项

### 只把发送接缝留在认证目录

保留 `authn.SMSSender` 与厂商适配在 `pkg/authn/sms` 之下，仅把实现整理一遍。

**否决**：任何要发通知的模块都得背上整套认证才能发一条短信。发送能力天然与 `pkg/kv`、`pkg/event` 同级，堵在认证目录里不会让「别的模块要发短信」这个需求消失，只会让它各自复制一份，或在认证之上再叠一层依赖。

### 只改名，不给模板声明

把 `authn.SMSSender` 整体挪到 `pkg/sms` 并改名，但保留自由文本式的消息形状（号码加已渲染的文本）。

**否决**：国内厂商不收自由文本，模板是这一类能力的强制形态。保留自由文本形状，要么让每个载体自己做模板映射与参数拼装，要么在调用方一侧重复同一份模板词表；模板的声明与校验因此分散到各个调用方，正是本改动要消掉的那份重复。模板必须是一等声明。

### 顶层能力加模板一等声明加消费方核对

新建顶层 `pkg/sms`，载体用一个 `map[string]TemplateSpec`（有序参数名表加语言到编号的映射）声明模板；载体只保证自己声明的集合自洽，覆盖某个消费方所需的组合由该消费方在启动期核对自己所需。

**采纳**，见决策。

### 消费方经 `core.Resources` 声明需求，载体在 `Prepare` 统一核对

消费方把自己所需的（模板，语言，参数）组合写成一份 `core.Resources` 声明，载体在 `Prepare` 阶段读全部声明并统一核对。

**否决**：`Registry.Resources` 返回全部已注册模块，含未纳入本次命令树的那些，载体要核对就得先按「在力」过滤一遍；这一层过滤是纯约定，没有编译期支持，漏过滤或过滤错了都只能靠测试发现。收益是核对早一个阶段（`Prepare` 早于 `New`），而 `New` 返回错误同样终止启动、同样早于服务，早一个阶段不抵这层额外的约定与过滤。核对因此留在唯一知道需求的一侧，用 `Sender.Declared()` 的只读视图逐个比对。

## 决策

采纳：**短信发送能力抽为顶层能力模块 `pkg/sms`，载体不感知用途；模板是一等声明；覆盖由消费方在启动期核对。**

- **能力归属。** `pkg/sms` 根包是接口包与工厂，不登记模块；它交付 `Sender`、`Message`、`Receipt` 与模板声明 `TemplateSpec`、`Declaration`、`Resolved`，哨兵 `ErrThrottled`、`ErrRejected`、`ErrUncertain`、`ErrInvalidConfig`。`sms.aliyun` 与 `sms.tencent` 各是一个载体叶子包，排他交付 `Sender`。`pkg/authn/sms` 退化为纯验证码状态机，经 `sms.Sender` 发送。
- **模板一等声明。** 载体以一个 `map[string]TemplateSpec` 声明它支持的模板；每个 `TemplateSpec` 是有序参数名表加语言到编号的映射。`Resolve` 把一条消息解成厂商编号与按声明次序铺开的参数值，四种落空都归调用方缺陷。载体只保证自己声明的集合自洽，覆盖闭集由消费方核对。
- **发送方接缝不感知用途与语言闭集。** `Message` 的模板名由调用方定义，语言是不透明非空串，空值一律拒绝。用途词表与语言闭集留在认证。
- **依赖方向。** `pkg/sms` 不 import `pkg/authn`；调用方（`pkg/authn/sms`）import `pkg/sms` 的根包。根包不 import 厂商 SDK，SDK 只落在绑定它的载体叶子包里。
- **`pkg/authn/internal/literal` 上移为 `pkg/internal/literal`。** 它被两个 SMS 载体与四个登录叶子共用，是共享单元，落在 `pkg/internal/` 下，不登记模块。上移是这次改动的必要前提，不只是整理。

## 后果

发送能力可被任何模块单独引入，不必背上整套认证。模板声明只有一处，载体与调用方都从它得到次序与编号；位置参数厂商与键参数厂商共用同一份声明。宿主可见面因此在几处改变。

**接受的代价：**

- **宿主可见的命名空间变更。** 厂商适配的模块名从 `authn.sms.aliyun`、`authn.sms.tencent` 变为 `sms.aliyun`、`sms.tencent`，配置命名空间随模块名改变。宿主的命令树与配置文件都要相应改写：命令树上点名的模块名与配置文件里的命名空间前缀都变了。
- **模板配置形态变更。** 载体配置里的 `templates` 从「把（用途，语言）映射到编号的平铺映射」变为「模板名 → 结构体（`params` 有序参数名表、`codes` 语言到编号映射）」的嵌套结构。`pkg/config` 把任何 map 判为一个容器叶子，整张 map 从主源取出后经解码器落进字段；值类型为结构体时嵌套 section 的键按 tag 落进字段，所以模板配置必须是嵌套的，不能是 `名: {zh-CN: 编号, params: [...]}` 的混合形式——混合形式要么只能落 `map[string]any` 绕过类型检查，要么在 `map[string]TemplateSpec` 下静默丢掉语言键。嵌套后类型错误在启动期即 `ErrTypeMismatch`。
- **认证根包的导出面收缩。** `authn.SMS`、`authn.SendReceipt`、`authn.SMSSender` 与 `authn.ErrSMSThrottled`、`ErrSMSRejected`、`ErrSMSUncertain` 从根包删除；三个发送哨兵改由 `pkg/sms` 定义，认证的工作池归类它们、不外露。认证根包保留 `SMSCodes` 与 `SendCode`，不再声明语言集或 `LocaleOf`：归一改在 `pkg/authn/sms`，其缺省语言取自共享的 `i18n.default-locale` 项（[ADR-i18n-language-set-2026-10-13](adr-i18n-language-set-2026-10-13.md)）。
- **`pkg/internal/literal` 的路径变更。** 引用它的包改 import 路径；该包自身的导出面不变。
- **认证侧的空值归一只有一处。** `pkg/sms` 把空 `Locale` 读作调用方缺陷；把空串填成缺省语言的归一留在 `pkg/authn/sms` 一处，缺省语言取自共享的 `i18n.default-locale` 项（[ADR-i18n-language-set-2026-10-13](adr-i18n-language-set-2026-10-13.md)）。消费方直接调 `sms.Sender` 时必须自己先归一。

## 失效条件

以下情形出现时，本决策需要重议：

- 若国内厂商开始接受自由文本，或模板不再是发送的强制形态，则「模板是一等声明」这一条的价值下降，接口可以重新按自由文本设计。
- 若出现一个消费方，它所需的模板集合在运行期才确定（例如由宿主的配置给出），则「消费方在 `New` 里用固定需求集核对」不再够用，覆盖核对需要迁到一个能拿到运行期需求的阶段。
- 若 `pkg/kv`、`pkg/event` 这类底层能力也被移入某个功能目录，则「发送能力与它们同级」这一判据的前提改变。
