# 每个用户账户在创建它的事务里拥有一个个人租户，个人租户是单人的受保护租户

## 背景

账户在开户之后必须能使用租户区，邮箱是否验证不阻止空间存在（REQ-tenancy-026、REQ-tenancy-028）。没有租户的账户让切换器、租户作用域与权限读取各多一档特殊处置。

需要成立的条件：

- 每个创建出来的用户账户都在一个租户中，不存在没有租户的用户账户这一状态。
- 个人租户与其它租户共用同一套租户、角色与绑定机制，管理员是同一种 `tenant-admin`（[ADR-tenant-administration](adr-tenant-administration.md)）。
- 个人租户只有一个成员，不能邀请他人加入。
- 服务账户是一种非交互的 API 客户端，由管理员授予租户访问，不拥有自己的组织。

决定要在下列既有约束内成立：

- **认证模块不依赖租户。** 账户存储的创建与删除各自是一个事务；租户行、成员关系与授权行归别的功能目录。认证根包不导入数据库句柄类型，事务签名住在叶包。
- **提交之后的钩子不承担账户固有数据。** `AccountLifecycle` 在账户事务提交之后运行，钩子失败时账户已在，它建立不了“与账户同时成立”这一性质。
- **租户名册的别名与账户的用户名共用一个 slug 命名空间。** 两者都落在 `tenants.alias` 的单列唯一约束上；一个 slug 只能属于一个租户的别名或标识。
- **运行期设置不塑造账户创建。** 账户是否存在、是否拥有空间，不由一个可被运营者关闭的开关决定。
- **多副本部署在名册快照刷新之前有一段窗口。** 另一个副本可能暂时读不到新租户行。

## 考虑过的选项

### 懒 ensure：进入租户区时建

账户创建后、首次进入租户区之前存在没有租户的账户。**否决**：「每个账户必须在一个租户中」在这段窗口内不成立，而这段窗口正是账户刚创建、最需要一致视图的时候。

### 订阅 `authn.account.created`，在事件里建租户

**否决**：该事件是尽力而为的提示，丢失就留下一个没有租户的账户，「每个创建出来的账户都在一个租户中」不能成为不变量；事件在账户创建之后异步到达，用户的第一批租户请求可能先于租户建立。

### 在 `Provisioner` 里于开户前建租户

**否决**：账户此时还不存在，成员关系与绑定无从写入，而且钩子只能改显示名与属性。

### 在账户创建事务内由认证模块直接写租户

认证模块在自己的事务里写租户行与绑定。**否决**：认证不依赖租户；跨模块事务把两个模块的写绑定在一个事务里，任一侧的失败都让另一个模块的写回滚，与模块边界的依赖方向相反。

### 账户创建提交后由宿主同步建租户，幂等 ensure 作补偿

**否决**：这是本记录取代的做法。提交与钩子之间账户已经存在而租户没有，补偿只在下一次调用时发生，而那次调用可能永远不来；把「账户拥有空间」交给一个宿主的可选步骤，使它成为部署配置的后果而不是产品的保证。一个第二宿主必须重写同一组写入、同一套幂等与同一个允许集。

### 由宿主模块承担，并保留一个关闭开关

**否决**：一个没有个人租户的用户账户不是一个合法的产品状态。开关要求每一条读路径多一档「没有空间」，并要求一条关闭期间开户的历史账户补齐路径；关闭后的账户与打开后的账户成为两种形状。缺省开启不是保证，运营者可以把它变成另一种产品。

### 由公共模块实现事务内的 seam

**采纳**，见决策。账户模块声明它需要的 seam，公共模块交付实现；每次写都走账户交出的同一个事务句柄，失败与账户一起回滚。

### 个人租户的别名取派生标识 `personal-<accountID>`

**否决**：个人组织在请求侧的名字会是一串内部标识。取用户名使个人组织以当事人的名字寻址，且用户名与别名已经共用同一个唯一命名空间；业务组织占用一个用户名时，同一用户名的账户创建在别名冲突处整体回滚，反之亦然。用户名空间保留 `personal-` 前缀，派生标识不会与用户名相撞。

## 决策

采纳：**每个用户账户在创建它的事务里拥有一个个人租户；租户由公共模块 `pkg/tenant/personal` 经 `provisioning.AccountProvisioning` 写入，删除在同一个事务里写墓碑。**

- **事务内建立。** 账户模块在写完账户行、标识与凭据之后、在创建事件入账之前调用 seam。seam 在同一个事务句柄上写租户行、创建者的成员关系、`tenant-admin` 角色、角色的授予与创建者的绑定；任一步失败使账户事务回滚，账户与空间要么都在，要么都不在。
- **别名的来源。** 个人租户的标识是 `personal-` 加账户标识；别名是账户的用户名。用户名缺席时以派生标识兜底，这是 seam 的防御性回退，不改变「用户账户有用户名」这一写入口的约束。
- **删除。** 账户删除事务在擦除账户自己的行之后调用 seam：清空账户在个人租户里的绑定、删除 `tenant-admin` 角色、把租户行写成墓碑。墓碑保留别名，用户名因此不复用。
- **提交之后的工作。** 名册快照重读、授权快照刷新与事件发布经 `provisioning.AfterCommit` 在提交之后运行，不在事务内运行。
- **生命周期与补偿。** `AccountLifecycle` 的创建、停用、启用与删除钩子仍由本模块实现，作为提交之后的补齐路径；账户事件投递时重跑同一组幂等钩子。它们不是账户固有数据的权威，权威是事务内的 seam。
- **没有开关。** 模块在装配中即在力，声明静态特性 `org.personal`；账户创建事务必须建立空间，不提供关闭分支，也不保留关闭期间开户的历史账户补齐。
- **服务账户不建。** 服务账户由管理员授予租户访问，两种 provisioning 方法都返回 nil。
- **补齐路由保留。** `POST /api/v1/orgs/personal` 仍挂在账户端，为一次丢失了事务写入或钩子的账户补齐同一组幂等写入；它不再按开关撤下。
- **允许集。** 个人租户的 `tenant-admin` 允许集不含成员管理动作；这是按租户种类声明的唯一一处差异，写在模块代码里，不从授权目录按种类推出。

## 后果

账户与租户的对应关系在账户存在的那一刻即成立，切换器与租户作用域的读取没有「账户没有租户」这一档。验证状态不改变空间是否存在，只限制可用能力（[ADR-authn-signup](adr-authn-signup.md)）。

**生命周期。** 个人租户与账户同一生命周期：账户停用时它随之停用，账户恢复时恢复；账户删除时，账户的绑定与角色在同一事务里清除或删除，租户行写成墓碑，标识与别名退役且不得重建；由业务模块持有的数据由各模块自行清除，审计记录保留。创建与删除都留审计。

**接受的代价：**

- **账户创建事务跨了模块边界。** 名册或授权的写失败会让整个账户创建回滚；这两个依赖因此成为账户创建的可用性前提。
- **用户名成为组织的对外名字。** 用户名与别名共用一个命名空间：一个业务组织不能使用现存用户名作别名，一个新用户名也不能等于现存业务组织的别名。用户名不再只是一个登录标识，它在请求路径、日志与审计行里作为个人组织的名字出现。
- **删除留下墓碑。** 每个删除的账户在名册里留下一个不可进入的行，标识与别名都不复用；名册随账户总量增长。
- **JIT 必须确定用户名。** 在 SSO JIT 总是提供用户名之前，兜底别名是派生标识，个人组织的名字不可读；这是过渡期的形态，不是长期名字。
- **多实例部署下有一个可见窗口。** 其它实例在名册快照刷新之前可能对新租户答 404，上界是名册的刷新周期；单实例部署没有这一窗口。
- **业务数据由业务模块清。** 平台只清自己持有的记录；宿主业务模块必须实现账户删除钩子，否则它在个人租户名下的数据会留下。
- **单人空间不能升级为团队。** 个人租户不能邀请成员，需要多人空间的账户必须使用另一个租户；产品若要求个人组织可升级，需要另立一条转换路径。
- **允许集因租户种类而异。** 进程启动之后新声明的租户级权限不会自动进入个人租户的 `tenant-admin`，模块必须在自己的允许集里显式加入。

## 失效条件

产品要求每个账户有多个个人租户、个人组织升级为团队租户，或需要账户在没有租户的状态下存在（例如预置但未启用的账户）。
