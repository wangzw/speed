# 每个账户创建即拥有一个个人租户，个人租户是单人的受保护租户

## 背景

账户在开户之后必须能使用租户区，邮箱是否验证不阻止空间存在（REQ-tenancy-026、REQ-tenancy-028）。没有租户的账户让切换器、租户作用域与权限读取各多一档特殊处置。

需要成立的条件：

- 每个创建出来的账户都在一个租户中，不存在没有租户的账户这一状态。
- 个人租户与其它租户共用同一套租户、角色与绑定机制，管理员是同一种 `tenant-admin`（[ADR-tenant-administration](adr-tenant-administration.md)）。
- 个人租户只有一个成员，不能邀请他人加入。

决定要在下列既有约束内成立：

- **租户是请求的路由事实，客户端没有读取本人成员关系的接口。** 租户记录只有标识、别名与状态，没有展示名。
- **授权的角色与绑定是按租户存的数据。** 迁移不种任何角色；租户区的 API 端有授权守卫，账户要在租户里持有带对象存储等权限的角色才能使用租户区。
- **认证模块不依赖租户。** 开户事件 `authn.account.created` 在提交之后尽力发布，不经发件箱；开户前的钩子 `Provisioner` 在账户存在之前调用，只能改显示名与属性。
- **认证模块的管理动作按判定域决策。** 成员管理、邀请、身份提供方管理与非成员放行在路径里的租户域内决策；冒充与客户端管理在平台域决策。
- **新租户在别的副本上要等名册快照刷新。**

## 考虑过的选项

### 懒 ensure：进入租户区时建

账户创建后、首次进入租户区之前存在没有租户的账户。**否决**：「每个账户必须在一个租户中」在这段窗口内不成立，而这段窗口正是账户刚创建、最需要一致视图的时候。

### 订阅 `authn.account.created`，在事件里建租户

**否决**：该事件不经发件箱，是尽力而为的提示，丢失就留下一个没有租户的账户，「每个创建出来的账户都在一个租户中」不能成为不变量；事件在账户创建之后异步到达，用户的第一批租户请求可能先于租户建立。

### 在 `Provisioner` 里于开户前建租户

**否决**：账户此时还不存在，成员关系与绑定无从写入，而且钩子只能改显示名与属性。

### 在账户创建事务内直接写租户

认证模块在自己的事务里写租户行与绑定。**否决**：认证不依赖租户；跨模块事务把两个模块的写绑定在一个事务里，任一侧的失败都让另一个模块的写回滚，与模块边界的依赖方向相反。

### 由 `pkg/` 提供「个人租户」能力模块

**否决**：个人租户是一类产品的策略，不是租户、认证或授权的原语。这样的模块要同时依赖三者，而认证不依赖租户，它只能放在它们之上；目前只有示范宿主一个需要，等第二个宿主出现再提升。

### 客户端在注册完成后创建租户，服务端不设守卫

**否决**：客户端的注册模式不跨重定向类渠道，也不可信；一个任何已认证调用方都能调用、没有守卫的建租户接口没有上界。

### 只给引导页与文案

**否决**：产品要求自动创建，引导页留下的仍是一个无法使用租户区的账户。

### 账户创建提交后由宿主同步建租户，幂等 ensure 作补偿

**采纳**，见决策。

## 决策

采纳：**每个账户创建事务提交后，宿主同步建立它的个人租户、成员关系与 `tenant-admin` 绑定；一个幂等的 ensure 作为补齐路径。**

- 个人租户由账户标识确定性派生，标识与别名都不取手机号、显示名或任何个人信息；别名是请求侧标识，不翻译。
- 建立动作属于示范宿主的一个模块，与通知接口的宿主侧授权同类；由宿主配置开关，缺省开启，部署可在配置里关闭。
- 账户创建的事务提交之后，宿主同步写入租户行、账户在该租户的成员关系与 `tenant-admin` 绑定。任一步失败时账户已存在而租户未建，由幂等的 ensure 重试补齐；ensure 也接受已认证调用方为自己补齐。
- 个人租户的 `tenant-admin` 允许集不含成员管理动作：个人租户不能邀请成员，也不接受其他账户加入。这是唯一一处按租户种类声明的允许集差异，由宿主声明，不由授权目录按租户种类推出。
- 个人租户不可停用、不可删除；账户不能移除自己在个人租户的成员关系与 `tenant-admin` 绑定。唯一成员与「`tenant-admin` 不能移除自己」共同保证后者。
- 运营者不以租户状态收回个人空间：账户停用是个人租户离开服务的唯一方式，恢复时随账户恢复。
- 不新增 `pkg/` 公共接口；各条款的细节由示范宿主的设计文档给出，本记录不重述。

## 后果

账户与租户的对应关系在账户存在的那一刻即成立，切换器与租户作用域的读取没有「账户没有租户」这一档。验证状态不改变空间是否存在，只限制可用能力（[ADR-authn-signup](adr-authn-signup.md)）。

**生命周期。** 个人租户与账户同一生命周期：账户停用时它随之停用，账户恢复时恢复；账户删除时，删除其成员关系与绑定，租户行保留为墓碑，标识退役且不得重建；由业务模块持有的数据由各模块自行清除，审计记录保留。创建与删除都留审计。

**接受的代价：**

- **创建路径多一步同步写。** 账户创建与租户建立跨两个模块，失败时存在没有租户的账户，直到重试成功；重试必须幂等，并能处理账户已删除这一档。
- **租户随账户增长。** 每个账户一个个人租户，总量随账户数；账户删除后租户行保留，名册里留下不可进入的已删除行。
- **验证状态不减少空间，只减少能力。** 未验证账户拥有个人租户，但邀请、组织创建与变更、外部身份绑定等能力仍不可用；验证提示与空间并存。
- **单人空间不能升级为团队。** 个人租户不能邀请成员，需要多人空间的账户必须使用另一个租户；产品若要求个人空间可升级，需要另立一条转换路径。
- **允许集因租户种类而异。** 进程启动之后新声明的租户级权限不会自动进入个人租户的 `tenant-admin`，宿主必须在自己的允许集里显式加入。
- **运营者失去收回手段。** 账户层面没有「停用空间但保留账户」的动作，收回个人空间只能停用或删除账户。
- **业务数据由业务模块清。** 平台只清自己持有的记录；宿主业务模块必须实现账户删除钩子，否则它在个人租户名下的数据会留下。
- **多实例部署下有一个可见窗口。** 其它实例在名册快照刷新之前可能对新租户答 404，上界是名册的刷新周期；单实例部署没有这一窗口。
- **租户标识含账户标识，名册读权限的持有者因此看得到每个个人租户的账户标识。** 这是可接受的信息暴露，只限持有租户管理权限的运营者。

## 失效条件

产品要求每个账户有多个个人租户、个人空间升级为团队租户，或需要账户在没有租户的状态下存在（例如预置但未启用的账户）。
