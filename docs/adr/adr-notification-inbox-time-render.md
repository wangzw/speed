# 站内信的时间由客户端按查看者的显示时区渲染

## 背景

全部界面约定按同一显示时区呈现时间，显示时区由账户设定、浏览器时区与 UTC 的三级链解析（[ADR-web-display-time-zone](adr-web-display-time-zone.md)）。站内信是存下来再读的文本：同一行可能在不同设备的显示时区下被打开，也可能在收件人改了时区之后仍留在收件箱里。服务端若在投递时把时间写成定格的文本，这个值不随查看者变化，读到的时刻与其余界面不一致。

邮件与短信不同：邮件是投递时定稿、收件人无法重渲染的产物；短信只把参数交给模板。两者的时间仍由服务端在投递时决定。

## 考虑过的选项

### 保持服务端按收件人时区定格

投递时按收件人存下的时区把时间写成文本，之后不再改写。

**否决**：旧消息不随查看者的显示时区变化，同一账户换设备或改偏好后，站内信与其余界面读到的时刻不一致；这正是不再让每个读者自行换算的那条约定所排除的。

### 服务端同时存格式化文本与原始时刻，客户端替换文本

正文里写格式化后的时刻，另把参数表交给客户端，由客户端找到文本中的时刻并替换。

**否决**：替换要按文本匹配一个随语言和布局变化的形状，正文措辞一改就失效，且无法区分正文里正常出现的同形文本。

### 客户端按结构化消息整体重渲染

服务端只存类型键与参数，正文由客户端从目录重新渲染。

**否决**：正文的目录条目归声明类型的业务模块，客户端没有这些目录；把全部文案下移到前端是把一次时间渲染的改动扩大成文案所有权的迁移。

### 服务端写时间标记，客户端从参数解析

服务端把每个时间段写成只带参数名的标记，客户端用消息的参数与显示时区解析。

**采纳**，见决策。

## 决策

采纳：站内信标题与正文的时间参数在服务端写标记，不写时刻。标记是私用区字符 U+E000、`time:`、参数名、U+E001，例如 `expires_at` 写成 U+E000 `time:expires_at` U+E001。参数名与派发参数的键一致。

客户端用消息的 `params` 与统一的显示时区入口解析每个标记，替换成按查看者显示时区与当前界面语言格式化的时刻。标记不带时刻、布局或时区，因此改显示时区或语言后，同一条旧消息重新渲染即变。参数缺失、`null`、布尔、对象、数组与空串替换成空串；字符串无法解析时原样显示；任何情况都不抛错，也不把标记字符留在页面上。

服务端在标记模式下把字符串参数里的两个私用区字符去掉，避免普通文本冒充标记。邮件与短信仍由服务端渲染，是本决定的例外。

## 后果

- 站内信的时间随查看者的显示时区与语言变化，与其余界面读到的时刻一致。
- 正文语言仍是投递时按收件人语言渲染的语言，只有时间按查看者当前界面语言格式化；用户切换语言后，两者可能不一致。
- 已写入的站内信行没有标记，按投递时的文本原样显示，不随查看者变化；不做回填。
- 宿主在收件箱之外直接渲染消息标题或正文时，必须调用同一解析函数，否则会看到私用区字符。
- 标记不携带格式档位，客户端统一用默认档；某个目录若需要只显示日期，当前标记表达不了。
- 没有浏览器的消费者无法解析标记，读到的是带私用区字符的文本。
- 邮件仍按收件人存下的时区在服务端定格，短信参数按 UTC 秒级字符串化；两者的实现不随之改变。

## 失效条件

- 站内信需要像邮件一样在投递时定格，例如时间本身要作为不可改写的审计证据：客户端渲染不再成立。
- 需要每条消息使用不同的时间格式档位：标记语法要扩展，届时重新权衡。
