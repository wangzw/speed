# 加密列按语句在所在引擎上实际读写的那一列认定

## 背景

序列化器只在 GORM（[REF-gorm](../references.md)）经模型字段读写一个值时运行。本模块在写入、查询与取结果集的回调链上补这个缺口：指明了模型的语句，要么加解密正确，要么拒绝并点名字段。补缺口的前提是认得出一条语句读写的是不是加密列，而这一列由两层共同决定。

第一层是 GORM 把列绑定到哪个字段。两个字段声明同一个列名时——嵌入结构体里有一个与模型自己的字段同列的字段，就是这样——GORM 把这一列绑定到其中一个：路径更短的那个，路径一样长时先声明的那个。经模型的插入按列写，每一列经绑定的字段写一次；默认值由数据库给出的字段另算，绑定与否，只要有一行给了它值就再写一次。经模型的更新同样只写绑定的字段，按值写入的更新还把写入的值设回调用方模型上绑定的那个字段。读出时，结果列扫进绑定的字段。没绑定到的字段，GORM 除上面那种默认值的情形外既不写也不读。

第二层是数据库把语句里的名字解析成哪一列。GORM 写模型的列、写它解析出的列名都加引号，解析不了的名字原样写进语句。两个引擎的解析规则不同：

- SQLite 比较标识符只折叠 ASCII 字母的大小写，带不带引号都如此。
- PostgreSQL 把不带引号的标识符的 ASCII 字母折成小写，带引号的按引号里的内容原样认，两者都只保留前 63 字节。

于是同一个模型在两个引擎上的列不一样多：列名只差大小写的两个字段，在 SQLite 上是同一列，在 PostgreSQL 上是两列。

## 考虑过的选项

### 只认 GORM 解析得到的名字

GORM 解析出加密字段的键与列才封装，其余原样放过。

**否决**：GORM 原样写进语句的名字由数据库解析。`Updates(map[string]any{"eMaIl": v})` 在 SQLite 上、原样写入的 `EMAIL` 在 PostgreSQL 上都落到加密列，值以明文存下，这一行此后经模型读不出来，写入却报告成功。

### 两个引擎共用最宽的一条规则，逐个声明的字段判断

去掉引号后不分大小写地等于某个加密列的列名，就认作那一列；模型上每一个声明了列名的字段都参与判断。

**否决**：在 PostgreSQL 上把另一列认作加密列。经模型的插入与更新被拒绝，而那条语句本来每一列只写一次；按那一列的名字写入的值被封装进一个不加密的列，此后经模型读出的是密文；PostgreSQL 截断后才与加密列同名的长名字反而认不出，值以明文存进加密列。逐个字段判断又把 GORM 不写的字段当成同一列的第二个值，嵌入结构体带来一个同列字段的模型从此插入不了；输掉列的加密字段则被当成封装的依据，按值写入的密文经模型那个不带标签的字段原样读回。

### 按所在引擎的规则与 GORM 的绑定判断，输掉列的加密字段不算数

一列是不是加密列，看 GORM 把它绑定到的那个字段带不带标签；输掉列的加密字段视同不存在。

**否决**：模型声明了这一列要加密，序列化器却从不运行，这一列以明文存下，没有任何信号——正是本模块要消除的静默失效形态，而且错在模型的声明上，调用点无从察觉。

### 按所在引擎的规则与 GORM 的绑定判断，输掉列的加密字段使那一列经模型的读写一律被拒绝

**采纳**，见决策。

## 决策

采纳：判断一条语句读写的是不是加密列，以这条语句在它所在的引擎上实际读写的那一列为准。

- 语句里的名字按语句所在引擎的标识符规则解析，与加密列的列名比较；列名就是字段声明的那个名字，因为 GORM 写模型的列总加引号。
- 经模型的写入只按 GORM 实际写出的字段判断。没写出的字段不算那一列的值。
- 加密字段输掉了它的列，GORM 把这一列绑定到一个不带标签的字段时，经这个模型写到或读到这一列的语句一律拒绝，并点名两个字段。

## 后果

封装与拒绝都落在数据库实际读写的那一列上：在 PostgreSQL 上只差大小写的两列各写各的，照常执行；在 SQLite 上它们是同一列，按一列判断。嵌入结构体带来的同列字段不再挡住经模型的写入。一个加密声明不起作用的模型在第一次读写那一列时就报出，报错指出 GORM 绑定的是哪个字段。

**接受的代价：**

- 同一个模型在两个引擎上的判断不同，在 PostgreSQL 上照常执行的写入换到 SQLite 上可能被拒绝。这是两个引擎本来就不同的地方，本模块照实反映，不抹平。
- 规则按引擎写在本模块里。新增一个方言，要同时给出它的标识符规则；没有给出规则的引擎，一个名字按两条规则中任一条与加密列相同，就认作加密列。
- 选择里写成表达式的一项仍按字面找列名，不解析 SQL，宁可判为读到加密列。
- 加密声明被遮住的模型，那一列经模型的读写全部不可用，要改模型的声明才用得了，只读那一列、而库里本来存的是明文的读法也在其内。
- PostgreSQL 截断到 63 字节的长列名，本模块认得出，GORM 却按截断后的名字交回结果列，扫不回声明全名的字段；这样的模型经 GORM 本来就读不回那一列。

## 失效条件

- GORM 改变同名列的绑定规则、写列名时加不加引号的做法，或按值更新之后写回模型的做法，这里的判断要随之重新对齐。
- PostgreSQL 在单字节编码的库上还会折叠 ASCII 之外的字母，编译时改过标识符长度上限的构建保留的字节数也不同；本模块按 UTF-8 编码、默认上限的库判断。部署到这两种库上时规则要改。
