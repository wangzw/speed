# 现有前端原地复用，旧树不保留

## 背景

`web/` 下已有一批前端包，是早先实现的一部分：契约边界、分层与装配形态都已成形。SDK 的来源换成新的后端契约，包在原地继续演进；需要裁定的是整棵旧树是否作为快照独立留在仓库里。

## 考虑过的选项

### 另起一棵前端树，旧树删掉

放弃现有包，按新的契约与装配形态重建一套。

**否决**：包的分层、契约边界与装配形态是已经付过代价的结论，另起一棵会把它们重推一遍；旧树里可用的东西——设计令牌、i18n 协商链、组件族、传输运行时——都还在。删掉它们不是清理，是重做。

### 旧树改名保留，新树从它拷出再改造

把现有 `web/` 整棵改名留在仓库里，新的 `web/` 从它拷出要用的包再改造。

**否决**：一份与 `web/` 包同名的完整副本让每次改动都要先判断落在哪棵树，目录区分是唯一的保护；快照的价值只在改造的过渡期，改造落地后它不再提供参照，只增加辨识成本与仓库体积。

### 原地就地改造，不留旧树

**采纳**，见决策。

## 决策

采纳：**`web/` 原地改造，不保留整棵旧树。**

- **契约来源换成新的后端产物**：SDK 由后端模块声明的 OpenAPI 片段合并后的文档生成，`orval.config.ts` 的输入随之改指；早先实现留下的契约文件与新的后端无关，不再被生成面读取。
- **不再对应的包移出**：后端不做计费，对应的前端包因此不在树里。
- **前端门禁进 `make check`**：安装、静态检查、类型检查、测试、构建由 `make check` 带上，与仓库其它门禁同一入口。
- **回退参照是版本历史**：改造的每一步是一个可检出的提交，不靠仓库里的一棵并行快照。

## 后果

前端包在原处演进，分层与契约边界的既有结论原样保留；后端契约成为 SDK 的唯一来源，生成面不再对着两份契约。

**接受的代价：**

- **没有并行的旧树可对照。** 大规模批量替换只能以 git 历史为参照；一次跨多个包的重构若需要并排比较，要在工作树之外自行取一份旧提交。
- **被移出的包没有去处。** 后端不做计费，对应的前端包随之删除，不再被任何应用消费。
- **门禁的覆盖面由此扩大到前端。** `make check` 从只跑 Go 模块变成还要装一次前端依赖并跑它的检查，单次用时上升，前端工具链成为运行仓库门禁的前提。
- **不进持续集成的流水线。** 仓库的持续集成此前已被移除，前端腿只接进 `make check`，不恢复流水线；前端门禁因此只在本地与将来的流水线入口上生效。

## 失效条件

- 若一次改造的规模大到需要并排比较两棵树，且 git 历史不足以承担参照，本决定需要重新裁定。
- 若前端不再由本仓库的 `make check` 承载（例如迁到独立的流水线），前端门禁进 `make check` 这一条不再成立。
