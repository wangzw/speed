# 投递承诺取所有实现都能满足的下界

## 状态

已接受

## 背景

事件总线的实现在投递机制上不同。进程内实现可以在发布方的协程上直接调用每一个订阅者，于是它知道每一个订阅者的处理结果。经传输投递的实现不能：它把事件交给传输后即返回，落在别的副本上的订阅者由传输自己的读取协程调用，那时发布方的调用早已返回，没有一处能把结果交还给它。

旧实现把这个差异写进了接口文档：`Publish` 的错误取决于那个处理函数跑在谁的协程上，接口不承诺它的含义。诚实，但调用方读不出可以依赖什么——同一个发布调用在两条装配下行为不同，而判据是实现的内部结构。

## 考虑过的选项

### 接口不承诺，错误语义由实现决定

**否决**：调用方写不出确定的代码。把订阅者的失败当作自己的失败来处理，代码在进程内实现下正确、在经传输的实现下静默失效；反过来，忽略 `Publish` 的错误，在进程内实现下丢掉了唯一的失败信号。调用方要写对，必须先知道当前装配用了哪个实现，而那正是接口应当屏蔽的。

### 承诺最强语义：同步、必达、订阅者失败回传

**否决**：跨副本的投递在物理上做不到同步回传，任何一个经传输投递的实现都无法满足。一个做不到的承诺比没有承诺更坏：调用方会据此写出在单进程下通过、在分布式部署下静默错误的代码，而分布式部署正是需要承诺的场景。

### 承诺一个所有实现都能满足的下界，更强的性质由实现自己声明

**采纳**，见决策。

## 决策

采纳：**接口承诺一个下界，下界之内是确定的，下界之外是实现自己的性质，调用方不得依赖。**

下界由以下各条构成：

- `Publish` 返回 nil 表示这次发布已被总线接受。它不表示任何订阅者已收到，也不表示任何订阅者已处理完成。
- `Publish` 返回非 nil 表示这次发布没有被总线接受，且失败发生在交给总线的那一步——载荷不可序列化、连接不可用、总线已关闭。它不表示某个订阅者处理失败。
- 订阅者处理的失败不回传给发布方。一个订阅者失败不阻止同一事件的其余订阅者被调用。

**实现可以更强，且必须在自己的文档里写明强在哪。** 进程内实现在发布方的协程上依次调用每一个订阅者，所以 `Publish` 返回时它们都已处理完毕；调用方不得依赖这一点，因为经传输投递的实现做不到。

**订阅者的失败在任何实现里都不回传**，知道结果的进程内实现也不例外。它本可以把结果汇进返回值，但没有：那会让 `Publish` 的错误同时意味着两件事——事件没有被接受，或者事件已被接受而某个订阅者处理失败——而第二条会把调用方引向重发一个已经投递过的事件。下界的全部价值是让这个错误只意味着一件事。

**本模块不承诺投递次数与顺序。** 跨副本恰好一次、按发布顺序投递，都是实现与其后端的事，接口层面不做规定。需要顺序的场景由调用方在载荷里携带序号自行处理。

## 后果

调用方可以确定地写代码：`Publish` 的错误只关于交给总线这一步，与订阅者无关。

需要知道订阅者处理结果的调用方必须自己建一条回执通路——由订阅方在载荷指定的位置回写，或者由调用方订阅一个结果事件。本模块不提供这条通路。

**接受的代价：**

- 订阅者的失败没有一条回到发布方的途径，任何实现都没有。需要知道的调用方要自己建一条：由订阅方按约定回写结果，或者发布一个结果事件。本模块不提供这条通路。
- 不承诺投递保证意味着"事件丢了"不是一个可以判定的问题。调用方察觉不到，本模块也报不出来。
- 订阅者的失败只有各实现自己记录，格式与去处各不相同，没有统一的一处可以查询。

## 失效条件

若出现一种部署形态，其中所有实现都能满足更强的语义（例如全部经同一个具备同步确认能力的后端投递），下界可以上移，本记录随之被取代。

若订阅者失败的可见性被证明是普遍需求，而不是每个调用方各自处理的问题，则需要在接口上增加一条回执通路，那会改变 `Publish` 的签名与每一个实现。
