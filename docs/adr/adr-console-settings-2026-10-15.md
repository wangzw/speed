# 运行期设置的管理面由框架提供一个按层判定的模块

## 状态

已接受

## 背景

设置能力带的是接缝与实现：它交付读写面 `settings.Store` 与三级回落，不提供配套的 HTTP 管理面。它的立场是写面的调用点是宿主自己的代码或它写出的管理命令，写入面的访问控制由宿主负责（[ADR-settings-scope-2026-09-21](adr-settings-scope-2026-09-21.md)）。一个想要管理面的宿主得自己写——项目的评估宿主就写了一遍：列设置、按租户或全局写、删，同一组路由与同一套判定在宿主里各写一遍。

一面设置管理面要处理的事，都与设置业务无关，却每个宿主都会重复：

- **谁可以问，按层分。** 设置的读写落在两层：全局层与某个租户的层。全局层的写是平台操作，在保留的平台域里持角色；租户层的写落到那个租户，在它的域里判定（[ADR-authz-model-2026-10-12](adr-authz-model-2026-10-12.md)）。
- **每次写留痕。** 改一项设置是平台或租户的写操作，要有一行在动作之前落下、写不进就不做的审计。
- **敏感项的值不外泄。** 设置模块对敏感项的默认值与变更事件遮蔽值，却照常把值交给 `List` 与 `Get`；把它们交给客户端之前要遮住（[ADR-settings-declaration-2026-09-29](adr-settings-declaration-2026-09-29.md)）。

这些落在一处还是散在每个宿主里，是本记录要定的。

## 考虑过的选项

### 管理面留给宿主自建

宿主自己写路由，自己按层判定，自己写审计前置与敏感遮蔽。

**否决**：同一组路由、同一套判定与同一条审计前置会在每个宿主里重复一遍，重复的每一份都可能判错域、漏掉审计或漏遮敏感值，而这些错都是安全形态的——判错域让一个租户的授权伸到平台的层，漏掉审计让一次写不留痕，漏遮敏感值让凭据随响应出去。把安全形态的判定留给每个宿主各写一遍，正是这份重复要消掉的东西；评估宿主里那份手写面就是这份重复的证据。

### 把管理面放进设置能力本身

把路由直接挂进 `pkg/settings`。

**否决**：`pkg/settings` 根包同时是接口包与实现，自身不做授权判定，依赖的是数据库、事件与配置几个功能标识。路由落在这里，会让它 import `pkg/authz`、`pkg/audit`、`pkg/http`，并把一面 HTTP 表面挂进一个不认识 HTTP 的能力。设置能力的立场不变：它交的是接缝，不是 HTTP 面。

### 把两层合并成一个权限点，判定都在平台域

读用一个权限点、写用一个权限点，平台管全部层，域名一律取保留的平台域。

**否决**：租户层的设置是那个租户的数据，不是平台资产。把它的判定放在平台域，会让「能管平台」等同「能管任意租户的层」，一个租户对自己的层没有任何授权位置；租户层的读写是租户域里的一次判定，不是平台域里的一次。

### 一个独立的管理面模块，判定按层分

新建管理面模块 `settings.admin`，宿主按需纳入；路由在中间件的声明表里登记为开放，handler 经 `authz.guard` 在 handler 内按层判定，每次写强制档审计，敏感项由本模块遮蔽。

**采纳**，见决策。

## 决策

采纳：**运行期设置的管理面由框架提供一个独立的模块 `settings.admin`，判定按层分。**

- **归属。** 管理面是 `settings.admin` 模块，挂在固定基路径 `/api/v1/settings/admin`，宿主把它写进命令树即挂上，不写即不挂。它不交付任何功能接口，每条路由的动作是一次 `settings.Store` 调用，模块自己不持数据、不持规则。设置能力本身的立场不变：它仍不做授权判定。
- **权限点按层分。** 读用 `settings.read`、写用 `settings.write`，由授权能力为设置能力承载（`pkg/authz/permissions.go`），本模块不另声明目录与翻译。全局层的一次读写是平台操作，在保留的平台域 `authz.PlatformDomain` 判定；租户层的一次读写落到该租户，在它的域 `authz.Domain(id)` 判定。层由查询串 `layer` 点名，租户由查询串 `tenant` 点名。
- **审计在动作之前。** 每次写在调设置模块之前落一行强制档审计，写不进即 503 且动作不执行；设置模块拒绝写时再尽力落一行 `failed` 行。
- **敏感项由本模块遮蔽。** `Declared` 不带敏感项的默认值，`List` 与 `Get` 却照常交出值；本模块按 `DeclaredItem.Sensitive` 在响应视图里把敏感项的值遮住。
- **租户标识的取值域就地复述。** 查询串里的租户标识是外部输入，而 `settings.ForTenant` 对越出取值域的标识当场 panic；本模块在拼层选之前把它挡在租户标识的取值域外，判据复述而不 import 租户能力。

## 后果

框架有了设置的运维面：一个想要管理面的宿主纳入 `settings.admin` 即可，不必重写这组路由、这套按层判定与这条审计前置。设置的读写语义仍只在设置模块一处定义，管理面只是它的一个调用方。

**接受的代价：**

- **一个宿主可见的新面。** 新模块名 `settings.admin`、新配置键 `settings.admin.endpoints`（必填、只收具体端名）、新的一组路由、新的一组查询串与新的 `Problem.Type` 前缀 `urn:speed:settings:`。这些都是宿主可见面。
- **管理面把一整套依赖带进设置能力目录的一个叶子。** `settings.admin` import `pkg/authz`、`pkg/authn`、`pkg/audit`、`pkg/http`，是设置能力目录里唯一这样做的一层。它可撤掉，设置根包不因它背上这些依赖，但一个纳入它的宿主的依赖闭合里就有了这套东西。
- **租户层的读写按租户的域判定。** 一个在某租户获 `settings.write` 的调用方可以经本模块改那个租户的层。这是刻意的——租户层是那个租户的数据——但它也意味着这面「管理面」同时是一条租户自助的写路径。
- **平台域的授予是写全局层的前提。** 部署要在平台域为角色备好 `settings.write`，否则改全局层对所有调用方都答 403。
- **遮蔽是本模块自己的一步。** 设置模块对敏感项遮蔽的是默认值与变更事件，值本身照常交给 `List` 与 `Get`；漏遮不报错，凭据随响应出去，所以这一步落在管理面而不是设置模块。

## 失效条件

以下情形出现时，本决策需要重议：

- **若设置能力自己长出一面 HTTP 管理面**，本模块不再必要，判定的位置与遮蔽的责任随之收回设置能力。
- **若权限模型把设置拆成更多权限点**（例如按命名空间分权，或把「读全局」与「读租户」拆开），本模块「读一写一、按层分域」的形状要重议。
- **若租户标识的取值域不再能就地复述**（例如标识的合法性取决于名册内容而非字符形态），本模块复述判据这一步要改为一次显式的查名册。
