# 宿主可为平台命名空间补整套语言，注册期全覆盖规则不变

## 状态

已接受

## 背景

web 包库的每个命名空间随包发布 `zh-CN` 与 `en-US` 两份资源。宿主创建实例时钉住受支持语言集，`registerNamespace` 要求每个受支持语言都有 bundle、所有 bundle 键集一致、复数族覆盖每个语言可选的计数类别；缺一个语言即拒绝注册。平台错误文案包同样只随包发布这两种语言。

产品从 `starters/demo` 拷出骨架后可能支持第三种语言。按原有边界，新增一种语言要触及包内默认集、MUI 映射、夹具、复数族覆盖与测试，是一次平台级改动；宿主既改不了包源码，也无法为一种语言等一次平台发布。

全覆盖规则本身不能放宽：缺语言的命名空间会让该语言用户看到裸键，而跨语言回落会让界面混用两种语言，两者都破坏「缺键绝不静默回落到另一种语言」的既有保证。

## 考虑过的选项

### 维持「新增语言是平台级改动」

每种语言都要由平台包自己发布。

**否决**：宿主的产品语言集是宿主的事实，平台无法预知；一种语言要被所有包同时发布，宿主才能上线，这与「拷出骨架后按版本区间消费包」的复用方式冲突。

### 放宽注册期的语言覆盖，缺语言的命名空间回落到默认语言

宿主只补它关心的命名空间，其余命名空间缺语言时用默认语言渲染。

**否决**：这正是缺键纪律禁止的跨语言回落。界面会在同一个页面上混用两种语言，而注册期的缺口校验——整套语言或整键缺失在启动时即报错——也随之失效。

### 宿主在注册时补齐整套语言

注册面接受宿主提供的整语言 bundle，走同一条校验路径；每个命名空间覆盖全部受支持语言的规则不变。

**采纳**，见决策。

## 决策

采纳：宿主可以为平台命名空间补整套语言。宿主提供的 bundle 进入与包内资源完全相同的注册校验：语言必须在实例的受支持集内、必须携带与已发布 bundle 相同的键集、复数族必须覆盖该语言可选的计数类别、叶子必须为非空字符串。任何一项不满足，注册在落地前抛错。

「每个命名空间必须覆盖每个受支持语言」的规则不变，改变的只是 bundle 的来源：它可以是平台随包发布的，也可以是宿主在注册时提供的。平台错误文案包以同样的方式扩展：它导出自己发布的两份资源，并在注册入口接受宿主补的整语言 bundle。

资源键因此成为兼容面的一部分：新增叶子是兼容的；删除或改名不兼容，因为宿主的覆盖或补语言按旧键集书写，升级后会指不到目标。注册前的资源覆盖工具对「改写一个不存在的叶子」抛错，让这类升级在启动时暴露，而不是静默多出一个键。

## 后果

宿主可以不改包源码就上线第三种语言，覆盖范围限于实例受支持集内的命名空间；平台包不必为宿主的产品语言发版，也不必知道它们是哪些。

`design-web-i18n.md` 扩展点里「新增一种语言是平台级改动」的表述不再成立，由本记录取代；注册期的覆盖、键集与复数校验保持不变。

**接受的代价：**

- 宿主补的语言由宿主自己维护：平台包后续新增的键会要求宿主同步更新补语言 bundle，否则该命名空间的注册失败。这是有意的早失败，代价是宿主必须跟随平台包的资源变更。
- 键集一致规则连同复数覆盖规则一起保留：一种语言的计数类别若超出已发布 bundle 携带的复数形，宿主无法只补语言——那些形要在每个语言的 bundle 里都出现，仍属平台发版。宿主补语言适用于计数类别不超出既有复数族的语言，以及没有复数族的命名空间（平台错误文案包即属后者）。
- 宿主补的语言不在 `muiLocaleFor` 的映射里：MUI 自身的组件文案不会随该语言本地化，宿主需要按 ui-kit 的本地化接缝自行供给，或接受 MUI 文案落到默认语言。
- 平台包不能假定自己发布的两三种语言就是全集：读取可用语言、渲染语言选择面必须走实例的受支持集，而不是包内常量。

## 失效条件

- 平台包的资源出现无法以整语言方式表达的形态（例如某份 bundle 依赖包内运行期计算而非静态叶子）：宿主的整语言 bundle 无法与它对齐，补语言要重新设计。
- 出现一种宿主必须支持、但计数类别超出既有复数族的语言，而平台又不愿为它发版：本记录把这类语言留给平台发版的前提不再成立，需要另立机制。
