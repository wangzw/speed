# 条件里以表名限定各列的整键元组按上下文填租户那一半，多对多关联的连接表按所连模型写进它的租户列判定

## 背景

隔离插件按来源识别受约束模型，按结构体主键寻址的更新与删除由插件把主键里租户那一半填成上下文的标识（[ADR-tenant-isolation](adr-tenant-isolation.md)）。宿主据此按标识的其余部分寻址一行，租户那一半留给插件。

GORM 的关联模式（`Association` 的 `Find`、`Count`、`Append`、`Replace`、`Delete`、`Clear`）不经这条路。它在任何回调之前就把属主与所给记录的整个键读出来，写进语句的条件，形状总是一个对键的各列取 `IN` 的元组，各列以它寻址的表的表名限定，每条记录一组。宿主留空的租户那一半因而作为空标识写进条件，标识拒绝以空值被绑定，语句以"上下文里没有租户"失败，而上下文明明带着租户。同一个按键寻址，在模型自己的删除上可用，在关联的删除上不可用。

调用方自己也在租户列上写条件：map、结构体、`clause.Eq` 写成租户列上的等值，列表取值与 `clause.IN` 写成那一列上的 `IN`。这些条件与关联模式写下的键落在同一个 WHERE 里，插件看到的只是表达式，看不到是谁写的。

多对多关联还要经过一张连接表。GORM 给没有 `SetupJoinTable` 点名模型的关联自己构造一个连接表模型，那个模型不内嵌任何东西；`SetupJoinTable` 点名的模型也可以不内嵌约定。这样的连接表在插件看来是全局表：没有租户条件，也不拒绝没有租户的语句，一次在没有租户的上下文里对别的租户的属主做的 `Clear` 删掉了那个租户的关联行。连接表的内容是租户的数据——哪个商机关联了哪些联系人——而它的行只经关联模式写入与删除。

关联模式的 `Find` 与 `Count` 读的是另一侧的模型，连接表经 FROM 子句按表名联接进来：ON 把连接表的列与另一侧的键列相等，并以一个 `IN` 带上属主的键。这条读里没有连接表的模型，也没有属主的模型、schema 或关联，插件能看到的只有 ON 里的条件；GORM 的 schema 缓存不导出，从表名找不回声明它的关联。

## 考虑过的选项

### 写明哪些关联写法要先加载记录，报错点名真正的原因

宿主在调用关联模式之前把属主与目标记录读出来，租户那一半因而是读出的值；关联模式遇到空的租户那一半时，错误文本改为说明要加载记录。

**否决**：同一个按键寻址在普通的写上可用、在关联语句上不可用，宿主要记住两套规矩，而宿主的规则要求租户那一半留给插件。`Delete` 的目标同样按键给出，每删一条关联先读一次它所指的记录。读出来的记录在别处不需要，这次读只为绕过一个插件填得了的空。

### 在 GORM 把键写进条件之前替它填结构体

插件在关联模式读取键之前把属主与记录的租户那一半填上，与按结构体主键寻址的写同样处理。

**否决**：`Association` 是 `*gorm.DB` 上的方法，读键发生在它自己的代码里，早于任何回调链；插件没有更早的挂点，模型的钩子也不在那里被调用。

### 条件里所有空的标识类型取值一律填成上下文的标识

不看它写在哪一列上，条件里凡是空的 `tenant.ID` 都替换成上下文的标识。

**否决**：一个以标识类型声明、却不是租户列的列——例如一行记录它指向的另一个租户——上的条件会被改写成另一个意思；写语句还要据它拒绝写了别的租户的键，那会把合法的语句拒掉。关联模式写键时列名是确定的，填的只该是写在那条语句自己的租户列上的那一段。

### 语句自己租户列上的等值与 `IN`，空的一律填成上下文的标识

按列判断：写在这条语句自己租户列上的等值、`IN` 与元组，租户那一位是空的就填。

**否决**：调用方自己写在租户列上的条件与关联模式写下的键同形，按列填就是改写调用方的条件。取值意外为空的 `Where(map[string]any{"tenant_id": x})` 本来一行也碰不到——空串匹配不到任何一行，标识类型的空值在绑定时被拒绝——填上之后读出整个租户的行，删除与更新作用于整个租户的每一行。插件只拒绝除它自己的条件之外没有条件的写，调用方这条被改写的条件照 GORM 的口径算作条件，拦不下来。

### 对一整个键的元组都当作关联模式写的键，不看各列怎么限定

**否决**：调用方按列名或以当前表占位符写出的整键元组也会被填，一条取值意外为空的条件从碰不到任何行变成碰到上下文租户里的那一行，还是改写了调用方的条件。判据取"各列以所寻址的表的表名限定"这个形状，不是因为能从元组看出是谁写的——分不出（见决策）——而是关联模式写键时总写成这个形状，调用方常用的写法都产不出它；不看各列怎么限定，就把那些写法的条件一并改写了。

### 调用方在租户列上写了空值的写语句一律拒绝

不填，也不照原样执行：写语句的条件在租户列上写了空值的，拒绝。

**否决**：照原样判定时这条语句本来碰不到任何行，拒绝它换不来隔离上的任何东西，只让一条合法的语句失败；读语句还得另立一套不同的规矩。条件照原样判定已经守住了"不扩大"。

### 连接表一律按它自己的模型认，要求它内嵌约定

与任何模型一样，连接表内嵌了约定才受约束，宿主为每个多对多关联用 `SetupJoinTable` 点名一个内嵌约定的连接表模型。

**否决**：GORM 自己构造的连接表模型不内嵌任何东西，漏写一次 `SetupJoinTable` 的关联静默成为全局表，正是要挡的那一类。按表名联接连接表的读看不到它的模型，只看得到键，同一张表在两处的判据因而不一致：连接表模型内嵌了约定、而两侧的键把租户写在另一列上时，它自己的语句按一列加条件，联接它的读按另一列。

### 连接表当全局表放行，写进非保证

插件不认连接表，宿主自己守住它。

**否决**：连接表的行是租户的数据，而写它、删它、预加载时读它的语句都经过插件，插件认得出它是哪个关联的连接表；认得出却放行，等于把一个查得出的缺陷交给评审，证据里一次没有租户的 `Clear` 已经删掉了别的租户的关联行。

### GORM 默认构造的两个租户列都加条件、都填列

两个受约束模型之间不写 `joinForeignKey` 与 `joinReferences` 时，连接表里每一侧各有一个租户列；两列都按上下文加条件、填列、核对。

**否决**：插件的每一档——填列、核对、主键里租户那一半、条件——都按一个租户列设计，两列要处处各做一遍。更要紧的是一行关联写得下两个租户，库里没有约束让两列相等，要靠插件在每一条语句上维持，漏一处就是一行跨租户的关联；让两侧的键把租户写进同一列，这种行从 schema 上就不存在。

### 取不出一个租户列的连接表另立一个哨兵

**否决**：它与内嵌了约定却取不出一个租户列的模型同类，经它的语句到不了任何一个租户，`ErrNoTenantInContext` 已经承担这一类（[ADR-tenant-isolation](adr-tenant-isolation.md)）。修复在关联的声明上，错误文本点名连接表、关联与缘由即可。

### 按表名联接的读一律当成以 SQL 文本写出的联接

FROM 子句里按表名写出的联接与 `Joins("JOIN ...")` 同类，被联接的那一侧不加条件，写进非保证。

**否决**：关联模式的 `Find` 与 `Count` 正是这种形状，放行它们，连接表的读路径就是全局的。ON 是 GORM 按关联的键写出的条件，插件读得出其中连接表的哪一列带着租户。

### ON 看不出租户的那一格写进非保证

受约束的属主只以键的其余部分参与、另一侧是全局模型时，ON 里既没有标识类型的取值，也没有与受约束模型租户列的相等；这条读当作判定不了，写进非保证。属主以一个不是标识类型的字段接管租户列时，ON 里属主键的租户那一半是个普通取值，同样看不出。

**否决**：连接表里的行不论怎么写进去——绕过插件写的，或连接表曾被当作全局表时写下的——经这条读在任何上下文里都读得到，双胞胎属主共用键的其余部分时，一个租户读到另一个租户的关联行。判定不了的读就是一条全局路径。

### 按表名在 GORM 已解析的 schema 里找出以它为连接表的关联

读语句上只有表名，插件去 GORM 的 schema 缓存里找以这张表为连接表的多对多关联，再照连接表自己的判据判定。

**否决**：GORM 不导出它的 schema 缓存，要读就得经 `unsafe` 伸进未导出的字段；缓存里的 schema 在解析完成之前就已登记，读它的关系与 GORM 的写并发。GORM 一次改名就让这条判定静默失效，而静默失效的方向正是全局读。

### ON 看不出租户的按表名联接一律拒绝

**否决**：两个全局模型之间的多对多关联走的是同一种读，ON 里同样看不出租户。一律拒绝就是本模块去拒绝不受约束模型的语句，而不受约束的模型不受本模块影响。

### 按键写进它的租户所在的列认定连接表的租户列，条件里以表名限定各列的整键元组补上租户那一半，读判定不了的关联拒绝它的属主

读的那一刻认不出，就在认得出的地方拒绝：声明这种关联的是属主，属主的每一条语句都经过插件。

**采纳**，见决策。

## 决策

采纳：条件里以表名限定各列的整键元组，租户那一半按上下文填——判据是形状，不是谁写的；调用方自己写在租户列上的其余条件照原样判定、从不改写；多对多关联的连接表按所连受约束模型的键把租户写进哪一列来认定租户列，取不出一个租户列的连接表一律拒绝；受约束模型声明的多对多关联，读判定不了的，拒绝这个模型，属主不出现在语句里的那条读除外。

- **条件里的整键元组。** 受约束模型的语句在上下文带租户时，条件里对这条语句自己的表的一整个键的各列取 `IN` 的元组——各列以这张表的表名限定，键指模型的主键，或一个关联在这张表上绑定某一侧键的那组列——租户那一位是空的、其余部分写了值的，填成上下文的标识；其余部分全空的元组什么也不指，不填。**这个形状是关联模式写键的唯一形状，元组是谁写的分不出，判据是形状。** 条件本身原样保留，同一条语句再次执行时按新的上下文重新填。
- **调用方的条件照原样判定。** 租户列上的其他条件——等值、只对这一列的 `IN`、不是整个键或不以表名限定各列的元组，写在 NOT、OR 与分组里也一样——都是调用方的，从不填：空值留作空值，语句碰到的是那条条件照原样选中的行，标识类型的空值在绑定时被拒绝。除插件自己的条件之外没有条件的写，照 GORM 的口径拒绝，调用方写在租户列上的条件照 GORM 的口径算作条件。
- **别的租户。** 条件在这条语句自己的租户列上写了别的租户的：写语句以 `ErrExplicitTenantMismatch` 拒绝，与按结构体主键寻址的写相同；读语句照原样，读不到任何行。
- **连接表的租户列按来源认。** 一个多对多关联里受约束的一侧以含租户列的键参与关联时，它的租户写进连接表的某一列，那一列就是连接表的租户列，不论连接表的模型是谁构造的、内不内嵌约定。受约束的一侧只以键的其余部分参与关联时，它不往连接表里写租户，读写它的行的语句由它自己的模型加条件。连接表的每一条语句照受约束模型的规矩加条件、填列与核对。
- **三种声明取不出一个租户列，经这样的连接表的每一条语句都被拒绝**，不论上下文，配 `ErrNoTenantInContext`：至少一侧受约束而没有一侧往连接表里写租户；两侧把租户写进两列；连接表的模型内嵌了约定，落在另一列上。
- **按表名联接连接表的读，从 ON 里认它的租户列。** ON 在被联接表的某一列上绑定了标识类型的取值（属主键里租户那一半），或把那一列与这条读自己的租户列相等，那一列即是租户列：插件填上键里空的租户那一半，并在 ON 里加上那一列等于上下文标识的条件，这条读因而与受约束模型的读一样要求上下文里有租户。ON 显示被联接的表把租户放在两列上，或受约束的这一侧只按键的其余部分与一张看不出租户列的表联接，那条读被拒绝，理由与连接表自己的那三种相同。
- **读判定不了的关联拒绝它的属主。** 受约束模型声明的多对多关联，另一侧是全局模型时，属主键里租户那一半是 ON 里唯一能说明这条读属于哪个租户的东西。两种声明让它缺席：属主只以键的其余部分参与关联；属主的租户列绑在一个不是标识类型的字段上。这样的模型经它的每一条语句都被拒绝，不论上下文，配 `ErrNoTenantInContext`，错误文本点名关联、连接表与缘由。**属主不出现在语句里的那条读够不着这个拒绝**：关联模式的 `Find` 与 `Count` 把连接表按表名联接进另一侧的读，语句里没有属主，插件没有可以据以判定或拒绝的东西；这条读是后果里的非保证。

## 后果

宿主按标识的其余部分寻址关联的属主与目标，与寻址普通的写一样，不必先读出记录。两个受约束模型之间的多对多关联，用 `joinForeignKey` 与 `joinReferences` 把两侧键里的租户那一半写进同一列，连接表模型可以由 GORM 构造，也可以是宿主点名的、不内嵌约定的模型。

**接受的代价：**

- **GORM 默认的多对多写法在两个受约束模型之间被拒绝。** 不写那两个标签时，连接表每一侧各有一个租户列，经它的每一条语句都失败，第一条语句上就摆出修复。
- **外键含租户列的一对多、一对一与属于关系，解除关联被拒绝。** GORM 把记录从属主上取下的做法是把外键的每一列写成 NULL，租户列在其中，这条更新把租户列写空，在租户之下以 `ErrExplicitTenantMismatch` 失败。要解除就用 `Unscoped` 的关联删除（删掉那一行），或自己写更新只置空外键的其余列。
- **只把属主的租户写进连接表的关联，跨租户读时另一侧按键的其余部分匹配。** 一行关联属于属主的租户，在租户之下它指的是那个租户里的行；跨租户的读不加条件，另一侧每一个持有那个键的租户的行都被读到。
- **调用方写在租户列上的空值照原样判定。** 以字符串写的，读写都碰不到任何行，不报错；以标识类型写的，绑定时被拒绝。取值意外为空的写因而是一次什么也没做的写，而不是作用于整个租户的写。
- **读判定不了的关联让它的属主整个不可用。** 受约束模型与全局模型之间只以键的其余部分参与的多对多关联，或租户列绑在不是标识类型的字段上的受约束模型与全局模型之间的多对多关联，声明它的模型的每一条语句都失败，模型自己的增删改查也在内，而不只是那个关联；第一条语句上就摆出修复。
- **属主不经任何语句时，那条读仍判定不了。** 关联模式的 `Find` 与 `Count` 把连接表按表名联接进另一侧的读，属主的键写在 ON 里，语句里没有属主的模型、schema 或关联——属主按键构造还是从表里读出、上下文带不带租户都一样：拒绝落在属主上，而属主不出现在语句里；插件手里只有联接的表名与 ON，认不出这张表是连接表，没有可以据以拒绝的东西（见否决）。只以键的其余部分参与的，这条读读到连接表里每个租户的关联行；那张连接表自己的语句一律被拒绝，这些行是绕过插件写进去的，或连接表曾被当作全局表时写下的。租户列绑在不是标识类型的字段上的，连接表照常带着租户、经插件照常写入，属主键里那个字段的取值决定读到哪个租户的关联行，一个写着别的租户的属主因而读到那个租户的关联行。这一条写进非保证。
- **判据读 GORM 写出的条件形状，不读是谁写的。** 条件里的键认的是对一整个键的各列取 `IN`、各列以表名限定的元组，这是关联模式写键的唯一形状，调用方常用的写法——map、结构体、按列名的 `clause.IN`——都产不出它；调用方亲手写出一模一样的元组，照键处理，填上的租户那一半只让它指向那个键在上下文租户里的行。按表名联接的读认的是 ON 里标识类型的取值与列之间的等值。
- **关联模式写在这张表上、却不在主键或它能找到的关联上的键，不填。** 能找到的关联是模型 schema 上的关联——它自己声明的，以及 GORM 为指向它的一对一、一对多写回的那一条——和以它为连接表的多对多关联。经嵌入结构体声明的一对一与一对多指向它时，GORM 不写回；别的模型按非主键的列属于它时，那组列只在声明方的 schema 上。这样的键租户那一半留作空值，绑定时被拒绝，失败方向是拒绝。
- **每一条语句多走一遍 schema 上的关系**，看它的模型是不是某个多对多关联的连接表；经受约束模型的语句另把它声明的多对多关联走一遍；每一条带 FROM 联接的读另把 ON 走一遍；条件里出现租户列上的元组时，另把模型的关联走一遍求它的键。

## 失效条件

若 GORM 的关联模式改为在回调之后才把键写进条件，或为它提供一个早于读键的挂点，条件里的填补可以换成在结构体上填，与按结构体主键寻址的写合成一处。

若 GORM 在按表名联接连接表的读上带出连接表的 schema 或声明它的关联，从 ON 里认租户列的那一步可以换成与连接表自己的语句同一个判据，读判定不了的那两种声明随之可判：拒绝可以从属主收回到那条读上，属主不经任何语句的那条读也随之被拒绝。

若 GORM 的关联模式改为以别的形状写键——不再以表名限定各列，或不再写成元组——或调用方的某个常用写法开始产出以表名限定、对整个键的元组，"只填以表名限定的整键元组"的判据要跟着改，否则前者让关联语句失败，后者让调用方的条件被改写。
