# 实时推送每副本一个 Hub，行先提交、事件后发，Hub 只值延迟

## 背景

站内信收件箱的实时推送要求：收件人已连接时，新增的消息必须送达该连接，收件人无需手动刷新（REQ-notifications-013）。

约束如下：

- **推送是延迟优化，不是正确性依赖。** 收件箱是持久表，一条消息写进去之后，使用方打开页面就能读到它；推送只决定它多快被看到。
- **多副本部署下，一次写与一条连接可能不在同一个副本上。** 写发生在处理投递的那个副本，连接可能落在另一个副本。
- **本仓没有跨副本的发布订阅扩展点。** `pkg/event` 的 `Bus` 是进程内的发布订阅，没有引入 Pub/Sub 中间件（[ADR-event-scope](adr-event-scope.md)）。
- **推送没有收件箱之外的状态。** 它不可被退订、不可被重试、不可被持久化；推送丢失与推送尚未到达，在使用方那一侧不可区分，而尚未到达的那一条可由回读收件箱补齐。
- **订阅按（租户，收件人）作用域。** 一条连接只接收发给它所属收件人的推送（REQ-notifications-013）。

## 考虑过的选项

### 跨副本的推送总线

引入一个 Pub/Sub 中间件（例如 Redis Pub/Sub）把一次收件箱写广播到所有副本，每个副本把消息推给它自己持有的连接。

**否决**：要引入 Pub/Sub 中间件，增加一个部署组件与一份运维负担；而漏一次推送只值一次延迟——使用方打开页面就能回读那一行，不值得为一个延迟优化背上一个中间件。

### 把推送当作投递的一条渠道

推送与 `in_app`、`email`、`sms` 并列，成为投递流水线的一条渠道，按（收件人，类型）可退订、可被队列重试、进 `notification_sends` 账。

**否决**：推送没有持久收件箱之外的状态，它不能被退订，也不能被重试——重试一条已经送不到任何连接的推送没有意义，因为目标连接可能早已不在。把它做成渠道会要求它有一条可持久化的失败与重试语义，而它没有；把它记进结果账还会把「此刻无人在线」记成一次投递失败。

### 长轮询替代 SSE

客户端发起一次请求，服务端挂起到有新消息或超时，客户端收到后立即再发起一次。

**否决**：每次取新消息都要一次请求往返，空闲时也要占着一条连接与一份挂起的预算；延迟上界与连接开销都高于一条持续复用、服务端主动推送的连接。

### 每副本一个 Hub，订阅收件箱创建事件，行先提交事件后发

**采纳**，见决策。

## 决策

采纳：**实时推送每副本一个 Hub，靠订阅收件箱创建事件驱动；收件箱行先提交、事件后发；Hub 只值延迟。**

- **每副本一个 Hub。** 没有跨副本的 Hub，没有 Pub/Sub 扩展点；每个副本各自持有一个进程内的 Hub，服务落在本副本上的连接。
- **订阅收件箱创建事件。** Hub 订阅 `notification.inbox.created`，载荷含 `message_id`、`tenant_id`、`recipient_user_id`、`type_key`。收件箱是这条事件的唯一发布方：写这一行的 `Write` 发布它，投递流水线不发布。
- **行先提交、事件后发。** 收件箱行先落库并提交，收件箱在写行提交之后才发事件。因此一次送不到任何人的通告什么都不丢——使用方可以回读那一行；Hub 唯一的价值是延迟。
- **`Publish` 永不阻塞、永不报错。** 每连接一个深度 64 的缓冲，慢消费者丢自己的帧、不拖累其他连接；匹配在进缓冲之前做，使整个平台的流量挤不掉某个合法客户端自己的缓冲。
- **消息 channel 永不 close。** `Close` 只置一个 per-connection 的 done 并注销订阅，因为一次与 close 竞争的发送会把并发 Hub 打 panic。
- **路由 `GET /stream`。** 用 `http.Flusher`（沿 `Unwrap()` 逐层找），设 `Content-Type: text/event-stream`，按（租户，收件人）作用域订阅 Hub，事件帧形如 `event: message\ndata: {…}\n\n`。

## 后果

推送的到达不改变收件箱的内容：推送到与不到，收件箱的行都在那里。Hub 缺席不影响收件箱的正确性，只影响它被看到的快慢。

**接受的代价：**

- **一次推送只送到写那行的副本上连接的客户端。** 写发生在 A 副本、连接落在 B 副本时，客户端收不到这次推送，要等它下次读收件箱。
- **Hub 是进程内的，副本重启即丢全部订阅。** 客户端要重连，重连之前它收不到推送；这段时间里的消息靠回读收件箱补齐。
- **慢消费者丢帧，不重投。** 它丢的帧只能靠回读收件箱补齐，Hub 不为此保留状态。
- **推送不能承载只在推送里携带的信息。** 事件载荷里的字段是提示，收件箱行才是真相；一个只在推送里给出的字段，一次漏推之后就永久丢失。

## 失效条件

以下情形出现时，本决策需要重议：

- 若出现一类要求「所有在线副本上的客户端都即时收到」的推送，且回读补不齐（例如在线状态一类的信号），则「每副本一个 Hub、漏一次推送只值一次延迟」这条要重议。
- 若部署已经引入一个 Pub/Sub 中间件，则「为推送引入中间件不划算」这条代价的前提改变。
