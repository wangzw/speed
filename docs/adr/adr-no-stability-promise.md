# 早期阶段不做稳定性承诺，破坏性改动仍逐次标注

## 背景

项目处于早期阶段，尚未发布稳定版本。模块、包的公开面与外部接口仍在形成，没有需要保护的外部消费者。为公开面承诺向后兼容，会把每一次形状调整都变成兼容垫片，而早期没有任何一方依赖这些形状。

约束是另一件事：一次改动仍要让读者判断它是否影响自己的代码。提交的 `!` 与 `BREAKING CHANGE` footer 承担这一判断，它们描述的是当次改动，不是对未来兼容的承诺。

## 考虑过的选项

### 为每个公开面保留兼容承诺

模块文档为公开面写下兼容承诺段，发布之后按承诺维持兼容。

**否决**：早期没有外部消费者依赖这些形状，承诺换来的是把未定形的设计冻结。每次形状调整都要按兼容流程处置，而调整本身正是早期设计的常态。

### 不再标注改动是否破坏性

既然不做稳定性承诺，改动也不再区分兼容与不兼容。

**否决**：读者无法判断一次改动是否影响自己的代码。破坏性标注描述的是当次改动，删除它不会减少承诺，只会减少信息。

### 不做稳定性承诺，保留逐次破坏性标注

设计文档只陈述当前的接口面与接口语义；每次改动仍按破坏性标注。

**采纳**，见决策。

## 决策

采纳：**项目早期不做稳定性承诺。** **不做稳定性承诺，不等于不标注破坏性。**

- 设计文档不设稳定性承诺段。模块的外部接口契约陈述当前的接口面、接口语义与变更分类，不陈述「以后兼容」。
- 每一次改动仍标注是否破坏性：提交的 `!` 与 `BREAKING CHANGE` footer。这条标注描述当次改动，不是对未来兼容的承诺。
- 破坏性的判据按改动所在的语言与面给出：Go 按签名与方法集，TypeScript 按源码语义，配置按键的路径与取值域，数据表按读取方直接依赖的列与键。

## 后果

模块与包的公开面可以随设计调整而变；设计文档只陈述当前形状与当次改动的影响。

宿主、其他模块与包的使用者不能假定跨版本兼容。前端包以锁定版本组发布，使用方按锁定的版本工作。

破坏性改动仍可追溯：提交的 `!` 与 `BREAKING CHANGE` footer 记录的是当次改动。

**接受的代价：**

- 早期出现外部消费者时，他们得不到兼容保证，只能锁定版本或跟随升级。
- 设计文档的接口面段不给出「这条以后不会变」的承诺，读者要自己判断升级风险。

## 失效条件

- 项目发布第一个稳定版本并出现需要保护的外部消费者时，需要一条新记录确立承诺的范围与期限。
