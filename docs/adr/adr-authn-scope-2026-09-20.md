# 认证与路由豁免同属一个发布单元，权限另立

## 状态

已接受

## 背景

已落地的文档里，把「调用方是谁、可不可以做这件事」这一类判定推给别处的有以下各处，每一处给承接方起的名字都不一样。

入口模块不决定哪些路由免于认证，把路由的准入策略推给实现准入的那个模块，并规定它以中间件的形式接入。

中间件的排序以「认证」作为可被指向的功能：按身份分支的层声明自己位于认证之后，否则它分支所依据的身份尚未确定（[ADR-http-middleware-2026-09-14](adr-http-middleware-2026-09-14.md)）。同一条记录载明，约束指向的功能在链上无人代表时该约束消失，声明它的那一层照常运行而位置不再受任何约束；在有模块交付认证之前，这条约束在任何一次装配里都没有落点。

数据库模块不对物理删除设门槛，把「谁可以物理删除」判为权限问题，推给「认识操作者的那一层」；它同样不提供审计，理由是那要知道操作者是谁，而操作者身份产生于依赖图上层（[ADR-db-scope-2026-09-14](adr-db-scope-2026-09-14.md)）。

准入、认证、认识操作者的那一层——这些名字之间没有一处文档划过等号，也没有一处说明承接它们的是一个发布单元还是几个。

判定凭据对应哪一个主体，与判定这个主体能不能做这件事，所需的输入不同。认定身份要的是凭据与一份主体的来源；裁定权限还要资源、动作与一份策略，而资源与动作是应用自己的领域概念，策略的模型形态同样由应用决定——角色、属性与能力列表都是其中一种。

入口模块不认识任何具体功能，新增一种横切机制不修改它；中间件的登记面不带登记方身份，它无从知道调用它的是谁（[ADR-http-middleware-2026-09-14](adr-http-middleware-2026-09-14.md)）。它也不提供路由级中间件：登记的层作用于该端的全部路由，只对一部分路由生效的层由那些路由的 handler 自己包，或者分到另一个监听端，而监听端是一个具名的监听地址（[ADR-http-endpoints-2026-09-14](adr-http-endpoints-2026-09-14.md)）。

发布单元按功能划分，是版本与发布的粒度；把一种能力升格为独立的发布单元需要举证，成立条件是它有独立的发布节奏，或者消费者会脱离它所属的发布单元单独取用它（[ADR-module-packaging-2026-09-13](adr-module-packaging-2026-09-13.md)）。

## 考虑过的选项

### 认证、路由豁免与权限同属一个发布单元

一个发布单元交付从凭据到「这个请求可不可以继续」的整条判定，中间件在一层里既判定主体，也判定该主体可否继续。

**否决**：权限的判定要认识资源与动作，而这两者是应用自己的领域概念；策略的模型形态也由应用决定，合并进来等于替每个宿主选定一种，并让只需要认证的宿主一并承受它的约定与输入项。两者的输入来源与变更节奏都不同，而发布单元是版本与发布的粒度（[ADR-module-packaging-2026-09-13](adr-module-packaging-2026-09-13.md)），合并会让策略模型的每一次演进都推动认证的版本。

### 认证独立，路由豁免归入口模块

入口模块在登记路由时接受一个「这条不需要认证」的标注，或者提供查询面，让作出认证判决的那一层问出当前请求匹配到哪条模式、那条模式上有什么标注。

**否决**：「这条路由不需要认证」是一个认证概念，落进登记面就要求入口模块认识认证，而它不认识任何具体功能，新增一种横切机制不修改它（[ADR-http-middleware-2026-09-14](adr-http-middleware-2026-09-14.md)）。登记面不带登记方身份，它也无从判断提出标注的与作出判决的是不是同一方。该选项要加出的查询面只有一个取用方，代价却落在被每一个登记路由的模块依赖的那个发布单元上。

### 认证与路由豁免各成一个发布单元

豁免表由一个独立的发布单元承载，作出认证判决的那一层在判决之前向它查询。

**否决**：豁免表只有一个读取方，就是作出认证判决的那一层，两者之间不存在第二条取用关系；为这一条通路要发明一个跨发布单元的功能接口，而跨发布单元的接口变更需要版本联动（[ADR-module-packaging-2026-09-13](adr-module-packaging-2026-09-13.md)）。升格所需的举证不成立：豁免没有独立于认证的发布节奏，也没有脱离认证单独取用它的消费者。拆开还多出一种失败形态——豁免登记可以在没有任何一层作出认证判决的进程里成功完成，登记方拿到的信号与生效时完全一样。

### 不设豁免机制，免认证的路由分到另一个监听端

沿用入口模块对「只对一部分路由生效的层」给出的既有答案，把不需要认证的路由挪到另一个不挂认证的监听端。

**否决**：监听端是一个具名的监听地址（[ADR-http-endpoints-2026-09-14](adr-http-endpoints-2026-09-14.md)），挪端就是改地址。登录与令牌签发这类路由要与被保护的路由在同一个地址上对外，它们的地址是 API 的形状，不是装配的自由度。

### 认证与路由豁免同属一个发布单元，权限另立

**采纳**，见决策。

## 决策

采纳：`pkg/authn` 交付认证——判定请求所携带的凭据对应哪一个主体——以及路由豁免，即哪些路由不需要这一判定。权限模型另立，由别的发布单元承载。

**判据是判定所需的输入**：只需要凭据与主体来源的归 `pkg/authn`；还需要资源、动作与策略的归权限模型。

`pkg/authn` 从不写 403。它的收口穷尽于拒绝、故障与自身失败，各自对应的状态码见 [ADR-authn-verdict-2026-09-20](adr-authn-verdict-2026-09-20.md)。通过认证的请求继续沿链向内，是否还有一层拦它不由 `pkg/authn` 决定，它也不知道有没有那一层。

豁免的来源限于代码登记，`pkg/authn` 不提供配置式的豁免清单。命令行是配置的最外覆盖层（[ADR-config-source-2026-09-13](adr-config-source-2026-09-13.md)），做成输入项即意味着一条命令行参数能改变哪些路径不需要认证。

## 后果

推让有了同一个承接方，用词随之收敛为「认证」与「权限」：入口模块推让的是认证，数据库推让的是权限。

「位于认证之后」这条中间件约束有了落点。在此之前它指向的功能在任何一次装配里都无人代表，约束静默消失而声明它的那一层照常运行（[ADR-http-middleware-2026-09-14](adr-http-middleware-2026-09-14.md)）。

只需要认证的宿主不承受权限模型的约定与输入项，权限模型的演进也不推动 `pkg/authn` 的版本。

豁免与认证判决同属一个发布单元，两者的登记时机、冻结时机与匹配语义在一个版本里一起变更，不需要跨发布单元协调。

**接受的代价：**

- 装配了认证而没有装配权限模型的进程里，凡通过认证的主体都能到达每一条不豁免的路由。`pkg/authn` 不写 403，也不知道链上有没有人写；未被本次命令纳入的模块不进启动诊断，架构文档已写明这一点，理由是诊断要写的原因——表态禁用，或消解落选——在一个连表态都没有的模块身上无从写起。缺一个权限模型因而不产生任何主动信号——按名查询答得出它未被纳入，但那要宿主自己去问。
- 认证与权限之间的接缝只由 `pkg/authn` 一侧定义。身份的形状与主体的键在权限模型落地之前就已固定，权限模型届时若要求另一种形状，改的是一个已经发布的接口包。
- 豁免的匹配语义由 `pkg/authn` 自持一份，与入口模块实际使用的路由引擎是两份各自维护的事实。同一条模式在两者之间判断不一致时，不一致不在任何一处显形：豁免多匹配一条，那条路由不再需要认证；少匹配一条，那条本该免认证的路由要求认证。这是不改动入口模块换来的代价。
- 豁免与作出判决的那一层一同在场或一同缺席：那一层不在本次命令的参与集里时，豁免登记整体不发生，而缺席时的净效果是放行不是拒绝（[ADR-authn-guarantees-2026-09-20](adr-authn-guarantees-2026-09-20.md)）。合一把两者绑在同一个发布单元里，没有改变这一点。
- 豁免只来自代码：改一条豁免要改代码并重新发布，运维面没有可用的开关。
- 归属的判据落在输入上，而新出现的判定未必一眼看得出落在哪边。一种判定先按认证实现、后来才发现它要读一份策略，改归属就是一次跨发布单元的搬迁。

## 失效条件

若出现一种不经 HTTP 的入口同样需要认证与豁免，则「哪些路由免于认证」这一形态不再覆盖它——豁免以 HTTP 的路由模式表达，而那种入口没有路由模式——`pkg/authn` 的交付面需要重新裁定。
