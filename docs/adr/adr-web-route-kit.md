# route-kit 按宿主给出的特性在场判定收窄注册面，特性缺席的页面与未登记路径同走 `fallback`

## 背景

特性缺席的页面，前端一律 404：导航里不出现，直接访问其链接得到与不存在的路径相同的 404。

`@speed/route-kit` 是前端的路由与导航层。产品经声明式注册面登记页面；选中态、链接构造、深链接解析与未命中回退由它一处承担；路径与权限之间的关系不由它建立，声明里的权限码只是被携带的数据（[ADR-web-route-seam](adr-web-route-seam.md)）。它不 import 任何同族前端包。

宿主手里的特性态有读取中、读取失败、就绪之分（[ADR-web-feature-state](adr-web-feature-state.md)）。读取失败时，门控的页面要渲染可重试的错误，同时门控的导航项要隐藏，不门控的页面照常可用。

控制台的短信页对特性缺席另有逐页的处理：读取答 404 时渲染「该面只在配置了短信服务商的部署上挂载」的说明。权限目录取可用集，前端把它当作持有集，所以本进程未运行的模块的页面在权限守卫处被放行，落到后端的 404 或这类说明分支。

layout-kit 的 `RouteGuard` 在命中页面的框架里渲染，状态取值是封闭集合 `RouteGuardStatus`。

## 考虑过的选项

### 宿主过滤注册表后再交给 `RouteProvider`

**否决**：读取失败时页面要渲染错误、导航项要隐藏，过滤只能在「留」与「删」之间选一个，表达不了这个组合；每个宿主还要另写一套等待态。

### auth-core 在装配入口加全局等待门

特性态就绪之前整个应用等待。

**否决**：一处读取失败就让整个应用不可用，不门控的页面也被拖住。

### `RouteGuard` 加一个特性缺席状态

**否决**：守卫在命中页面的框架里渲染，选中态与外框都与未登记路径不同，用户分辨得出来；还要改封闭集 `RouteGuardStatus`。

### 逐页判断特性缺席

每个页面在读取答 404 时自行渲染特性缺席的说明，例如控制台短信页的 `isSurfaceAbsent` 分支。

**否决**：页面先被导航列出、被匹配、发出请求，后端答 404 之后才知道特性缺席；渲染的是页面自己的说明，与未登记路径的 404 不同；每个页面各写一遍。

### `route-kit` 按宿主给出的特性在场判定，收窄可渲染视图、可导航的声明

**采纳**，见决策。

## 决策

采纳：**`route-kit` 按宿主给出的特性在场判定，从注册表里收窄出可导航、可渲染视图的声明；特性缺席的页面与未登记路径走同一个 `fallback`。**

- `RouteDeclaration` 可带 `requires`：一组特性名，其中全部特性在场时这条声明才可渲染视图、可导航。它与 `permission` 一样是纯数据。
- 宿主经 `RouteProvider` 给出 `presence`（`RoutePresence`：读取中、读取失败，或就绪并带一个按特性名答该特性是否在场的函数），连同读取中与读取失败时各自的视图。表里只要有一条声明带 `requires`，`presence`、读取中视图、读取失败视图缺任何一项即抛错；不带 `requires` 的表不需要这几项，匹配与导航只按注册表进行。
- 匹配在全表上做。未命中渲染 `fallback`；命中不门控的声明渲染视图；命中门控声明时，就绪且全部特性在场渲染视图，就绪且有特性缺席渲染 `fallback`——与未命中同一分支，读取中与读取失败渲染各自的视图。
- 导航与选中态只在收窄后的声明集合（`presentDeclarations` 的结果）上推导：特性缺席的声明，以及读取中、读取失败时的全部门控声明，不出现在导航里，也不会被选中。
- `useMatch` 返回收窄后集合上的精确命中，不做前缀继承；`useHasRoute` 答一条路径是否精确命中其中某条声明，入口控件据此跟随目标页。
- `route-kit` 不取回特性集合，也不认识任何特性名。

**与 [ADR-web-route-seam](adr-web-route-seam.md) 并存。** 那条记录的决策「路径与权限之间的关系不由 `route-kit` 建立」仍然成立：特性在场不是授权，`permission` 仍只是被携带的数据，`route-kit` 不据权限拦路由，也不据权限过滤导航。本记录裁定的是那条记录没有覆盖的另一件事——按特性在场收窄注册面。

## 后果

「特性缺席」与「路径不存在」由同一个分支、同一个 `fallback` 渲染，404 的一致由结构保证，不靠各页面自律；宿主为控制台侧栏复用同一个 `presentDeclarations`，收窄后的声明交给控制台壳。存在性与授权分属不同的层，宿主的组合次序是先存在性、后权限。

**接受的代价：**

- `route-kit` 在注册表之外多一份输入，宿主要提供特性在场判定以及读取中、读取失败时的视图。导出带 `requires` 的页面声明的包（如 console-ui），对拿不出特性态的宿主不再可用：`RouteProvider` 拒绝没有 `presence` 的门控表。
- 读取中时门控导航项不出现，就绪后才出现：导航在就绪时增长，不会先显示后隐藏，但读取期间导航不完整。
- 404 完全在客户端渲染：合一拓扑下，不落在 `/` 以外任何认领前缀之下、末段不带扩展名的深链接在 HTTP 层得到入口文档与 200，状态码区分不了特性缺席与特性在场，这一点与未登记路径相同。
- `requires` 里写错的名字与特性缺席表现相同，只能靠名字对齐检查拦下（[ADR-feature-vocabulary](adr-feature-vocabulary.md)）。

## 失效条件

- 产品需要对特性缺席的页面给出与 404 不同的呈现（例如按租户套餐提示「当前套餐不含此页」），「与未登记路径同走 `fallback`」要重审。
- 存在性改由每个页面在匹配之后逐页求值，而不是宿主一次给出的集合，`RoutePresence` 这一输入形态不再成立。
