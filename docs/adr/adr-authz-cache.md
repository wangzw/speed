# 策略常驻进程内不可变快照，事件失效、周期重载兜底

## 背景

授权判定落在每个受保护请求的路径上：中间件对每条命中路由的请求做一次判定，处理函数内的判定 API 也在请求内。策略的读取因此远多于写入，判定路径的代价按请求数计。

策略是共享的权威数据：全部副本读同一份策略，一次写入发生在某个副本上，其效果要到达其余副本。事件总线是现成的跨副本通道，它的投递承诺有明确的下界——`Publish` 返回成功只表示事件被总线接受，不承诺投递次数与顺序（[ADR-event-delivery](adr-event-delivery.md)）。

判定的失败语义把存储放到了代价很高的一侧：引擎或存储不可用时判定答 503，不答 403（见设计文档 design-authz 的错误与失败语义）。判定路径若每一步都依赖存储在线，一次存储抖动即让全部受保护请求失败。

判定是排他的布尔问句（[ADR-authn-decision-seam](adr-authn-decision-seam.md) 的 `Decider` 接口），结果由一个闭集的动作到（资源，动作）的翻译给出；判定不需要在请求期读写策略之外的可变状态。

键值模块交付的是原语，不承载缓存语义（[ADR-kv-scope](adr-kv-scope.md)），把判定缓存放进键值需要本模块自己维护失效。设置模块已经立起同样的先例——内存快照读取、事件广播加速、周期刷新兜底（[ADR-settings-propagation](adr-settings-propagation.md)）。策略与设置的区别在于：策略是授权本身的权威数据，快照是整份策略的不可变替换，而不是按键的取值。

## 考虑过的选项

### 每次判定读存储

判定不持有进程内策略，每次从存储读取规则再匹配。

**否决**：判定在每个受保护请求的路径上，把它退化成每请求一次（或多次）数据库往返；策略的读远多于写，这正是快照要消掉的负载。存储的短暂不可用随之变成每一条受保护请求的失败。

### 不持有进程内模型

进程内不保留任何策略模型，连匹配也在判定时现场装载。

**否决**：与「每次判定读存储」同一后果——把一次内存匹配退化成 IO，且每次装载多出一次解析。进程内没有任何可服务判定的状态，一次存储抖动直接落到整个端点。

### 判定结果缓存放键值，跨副本共享

把已判定的结果（主体与查询到布尔值）放键值，多副本共享一份。

**否决**：策略本身是共享的权威数据，副本各自持有的策略快照已经能被事件失效；在它之上再叠一层跨副本的判定缓存，等于为同一份权威数据维护两层失效——策略变更要同时失效快照与键值里的判定，两层之间任何不一致都表现为已撤销的授权仍被放行。命中缓存还要一次键值往返，与进程内匹配相比没有省下代价。

### 进程内不可变快照，事件失效、周期重载兜底

**采纳**，见决策。

## 决策

采纳：策略在启动时全量装载为进程内不可变快照，以原子指针替换；请求期只读快照，不查库。

**装载与读取。** `pkg/authz/policy` 的启动阶段全量装载全部租户的策略成一份不可变快照，判定只读这份快照，进程内不发起查询。装载有超时上界，超时即启动失败，取值见设计文档 design-authz 的配置项。

**写路径的次序。** 写库成功（提交）之后，本进程重装快照并原子替换指针，再发 `authz.policy.changed`。发布失败不回滚写入、不改变写入的返回值（与设置的发布失败处置同一条，[ADR-settings-propagation](adr-settings-propagation.md)）；发布失败记日志，其余副本由重载跟进。

**跨副本失效。** 其余副本在 `authz.policy.changed` 投递到本副本时重新装载；投递尽力而为，可丢、顺序不保证。

**兜底。** 没有事件总线的装配以周期重载兜底，是否开启与间隔是该模块的配置项，取值与默认见设计文档 design-authz 的配置项。它归配置，因为它设定 `Start` 建立的 ticker，改值要重启；周期性重载因此不依赖设置存储，一个只有数据库、没有事件总线也没有设置存储的装配可以直接配置它。刷新关闭时，跨副本生效只依赖事件。

**快照整体替换。** 每次写入后重装整份快照并原子替换指针，而不是增量改动内存模型——整份替换天然幂等，读侧无锁，多条重载路径（写入重载、事件重载、周期重载）替换的是同一份快照。

装载跨租户读取、薄 adapter 如何读写、表如何定义，在 [ADR-authz-store](adr-authz-store.md) 与设计文档 design-authz 里，不在本记录重述。

## 后果

判定是内存操作：受保护请求的判定不产生数据库负载；策略的读取远多于写入，同步进快照的负载与请求量无关。

存储的短暂不可用不落在判定路径上：已有快照的判定照常作答，跨副本的收敛推迟到事件恢复或下一个重载周期。

**接受的代价：**

- **撤销有一个生效窗口。** 一次写入在发起它的副本上立即换指针，其余副本要等事件投递或下一个重载周期，窗口上界是两者中先到的那个。事件可丢、不保证顺序（[ADR-event-delivery](adr-event-delivery.md)），读到旧策略期间的判定按旧策略执行；对零容忍的撤销，快照形态给不出零窗口。
- **发布失败只有日志。** 写入方看不到「其余副本还没收到」，本模块不重发；周期重载是它的兜底，刷新关闭的装配没有这一层兜底，只能等下一次变更的事件或重启。
- **整份快照的装载成本随策略规模增长。** 每次写入重装全量策略，启动装载也有一次同样的成本；启动装载必须在超时上界内完成，策略规模触及这条上界即启动失败。
- **没有事件总线的装配只有周期重载这一条跨副本路径。** 跨副本的生效窗口等于一个重载周期；周期重载未开启时，其余副本读到旧策略直到下一次变更事件。
- **多条重载路径并存，各自的失败处置都要成立。** 写入重载、事件重载与周期重载都在替换同一份快照，重载失败保留旧快照并记日志；重载的幂等由整份替换天然给出，不靠各路径自己维护。
- **从设置迁到配置是宿主可见的迁移。** `refresh-interval` 曾经是设置项。升级后旧设置表里的行不再被声明：经设置存储写它被拒为未知键，运行期也不再读它，宿主要把非零间隔写进配置文件，周期重载才按它生效。

## 失效条件

- 若事件总线的投递承诺上移到至少一次且有序，「周期重载兜底」的权重需要重新比较（[ADR-event-delivery](adr-event-delivery.md) 记有同一条件的失效情形）。
- 若出现一类策略变更，读到旧值的后果不可接受（授权撤销的零容忍），快照形态给不出零窗口，那类变更需要另找承载，本记录不预设它是什么。
- 若策略规模增长到「全量装载」不能在启动超时内完成，或每次写入重装整份快照的成本不可接受，快照的粒度与装载方式需要重新裁定。
