# Designer

> 共享的角色分工、Issue 状态机、结构化评论格式见 [../SKILL.md](../SKILL.md)。本文件只记录 Designer 专属的规则。

## 职责范围

两项工作，运行方式不同：

1. **交互式设计**：与人类在人类自己的**本地独立分支/worktree** 中协同产出设计文档，不在 Action 中运行。这是整个系统里唯一强制的人类介入点。设计文档本身的格式规范由另一个独立 skill 负责，不在本 skill 范围内。
   - 常见做法是这一步发生在主题 Issue 创建之前（此时还没有 Issue，不受 Scheduler 调度），设计收敛后人类通知 Scheduler，Scheduler 才新建主题 Issue，直接从 `phase:planning` 起步。
   - 也允许 Issue 已经先存在（`phase:design`）、设计还没做完的情况——不强制约定先后顺序，Scheduler 只看设计文档当下是否就绪来决定 phase。
2. **规划**：把设计文档转成实施计划（plan），自主迭代收敛。由 Scheduler 派发，在 Action 中运行，此时 Issue 已存在。

## 执行流程：交互式设计（模式一）

不是 `workflow_dispatch` 触发的，是人类在自己的本地分支/worktree 里直接调用 `coding-flow designer`（或等价入口）发起的常规交互会话：

1. 了解需求来源（新功能、bug report 里牵出的设计缺陷、审查发现需要重新设计的问题），读现有代码库找可复用的模式，而不是凭空设计。
2. 与人类来回讨论方案、取舍，产出设计文档（格式由另一个独立 skill 规定，本 skill 不介入）。用下面这份引导性 checklist 确保关键决策点都被问到、不是走个过场：
   - **问题定义**：解决的是什么问题？不做这件事会怎样？（避免为了做而做）
   - **范围边界**：这次要覆盖哪些场景，明确排除哪些（排除的写下来，不是留白）？
   - **现有模式**：代码库里有没有类似问题已经解决过的模式可以直接复用/参考，而不是另起一套？
   - **备选方案**：除了当前方案，还考虑过哪些？为什么放弃——这是后续「判断能否自主处理设计变更」时区分"技术正确性问题"和"方案取舍问题"的关键依据，取舍理由写清楚了，后面 agent 才能判断哪些改动会推翻这个理由。
   - **失败模式**：这个方案在什么情况下会失败/不适用？谁来处理这些情况？
   - **对外接口**：这次改动会不会影响到其它模块依赖的接口/契约？影响范围写清楚，供后续「跨主体问题」判定用。
   - **验证方式**：怎么判断这个方案做对了（对应后续 plan 阶段"可独立验证"的验收标准雏形）？
   - **遗留问题**：还有没有讨论中悬而未决、故意推迟到实施阶段再定的点？如果有，显式写进文档而不是让它悄悄消失。
3. 设计文档写完后，**内置对抗性审查（见下）先过一遍**——不要等到进了 `phase:planning` 才被 Designer 的规划模式发现问题，能在这一步先自查的就先自查。
4. 收敛后，人类决定何时通知 Scheduler；Scheduler 依当前 Issue 是否已存在、设计文档是否已就绪，决定新建 Issue（正文按 [../templates/issue-body.md](../templates/issue-body.md) 填写）还是把已有 Issue 切到 `phase:planning`（见 SKILL.md「Issue 与设计文档的先后顺序不强制约定」）。

## 执行流程：规划（模式二）

由 Scheduler 通过 `workflow_dispatch` 触发，接收 `issue_number`、`phase` 两个 input，在 Action 中运行。整个流程写成 Claude Code Workflow 脚本（见 SKILL.md「非交互式任务一律用 Claude Code 的动态 Workflow 工具实现」）：

1. **拉取上下文**：`gh issue view <issue_number>` 取 Issue 正文（设计文档/前情）和最新一条结构化评论；若已有 plan 的本地副本（`.claude/plan/<issue_number>.md`）就在其基础上迭代，否则新建。
2. **生成/迭代 plan**：按 [../templates/plan.md](../templates/plan.md) 的结构产出——把设计文档拆成任务清单，每项要满足「可独立验证」——写清楚验收标准（怎么判断这一项做完了），而不是笼统的一句话描述；标注任务间的顺序/依赖；边界情况和遗留问题按模板要求显式写出，不能留空当作已经考虑过。
3. **对抗性审查（Workflow: produce → verify）**：
   - `agent()`：自查 plan 是否完整覆盖设计文档范围、边界情况（错误处理、并发、迁移等）是否遗漏。
   - `agent()`（独立 fork）：只拿设计文档 + plan，逐条验证每个任务是否真的可独立验证、顺序是否合理，标出不成立的部分。
   - `pipeline()` 串联两步。
4. **收敛判定**：
   - 有 CONFIRMED 问题且是 plan 自身的措辞/遗漏 → 直接修 plan，回到步骤 2 重新走一遍审查。
   - 问题指向设计层面（前提假设错了、需求理解有偏差）→ 走「判断能否自主处理设计变更」。
   - 全部通过 → 转 `phase:implementation`，结构化评论 `action: advance`。
5. **产出**：把最终 plan 写回 Issue，本地副本用完即弃；按 SKILL.md 格式追加结构化评论。

## 内置对抗性审查

### 审设计文档

关注：完整性（是否覆盖需求点）、自洽性（方案内部是否矛盾）、可实现性（与现有代码库/技术栈是否兼容，是否有过度设计）、是否有遗留未决问题。

**produce 步骤 prompt：**
```
审查这份设计文档（{{design_doc_path}}），对照最初的需求描述（{{requirement}}）。

只关注这几个维度：
1. 完整性——需求里提到的场景/约束，有没有在设计里找不到对应处理方式的。
2. 自洽性——文档内部前后是否矛盾（比如前面说用方案 A，后面某个细节又假设了方案 B 才成立）。
3. 可实现性——方案是否要求现有代码库/技术栈里不存在的能力；有没有为了这个需求引入明显过重的新组件/新依赖（过度设计）。
4. 遗留问题——文档里有没有写了"待定""TODO"却没有后续说明的地方。

每个问题给出：文档里的具体位置（章节/段落）、问题描述、为什么这会在后续规划/实施阶段变成障碍。
```

**verify 步骤 prompt（独立 fork，只传设计文档 + 需求描述 + 问题清单，不传上一步的推理过程）：**
```
下面是对一份设计文档提出的问题清单，做对抗性验证。

对每一条：
1. 重新独立读一遍设计文档相关章节，判断问题是否真实存在。
2. 如果存在，说明具体会在哪个后续环节（规划还是实施）暴露出来。
3. 标记 CONFIRMED 或 NOT_REAL，附理由。

拿不准的标 NOT_REAL，不要因为"听起来有道理"就放行没有具体依据的问题。
```

### 审 plan

关注：每个任务是否可独立验证、是否完整覆盖设计文档范围、任务顺序/依赖是否合理、是否遗漏边界情况（错误处理、并发、迁移等）。

**produce 步骤 prompt：**
```
审查这份实施计划（{{plan_path}}），对照设计文档（{{design_doc_path}}）。

只关注这几个维度：
1. 可独立验证——每个任务项是否写清楚了验收标准，还是只有一句笼统描述（"实现 XX 功能"这种不合格，要能回答"怎么判断这一项做完了"）。
2. 覆盖度——设计文档里的需求点/约束，有没有任务项漏掉了对应的实现。
3. 顺序/依赖——任务项之间的先后顺序是否合理，有没有 B 任务依赖 A 任务的产出却被排在了 A 前面。
4. 边界情况——错误处理、并发、数据迁移这类容易被规划阶段忽略的场景，plan 里有没有体现。

每个问题给出：对应的任务项编号、问题描述、如果不修复会在实施阶段导致什么后果。
```

**verify 步骤 prompt（独立 fork，只传设计文档 + plan + 问题清单）：**
```
下面是对一份实施计划提出的问题清单，做对抗性验证。

对每一条：
1. 重新独立对照设计文档和 plan，判断问题是否真实存在。
2. 如果存在，判断这是"plan 自身可以直接修"的问题，还是"设计文档的前提假设本身有问题"——后者需要特别标注，因为处理路径不同（见「判断能否自主处理设计变更」）。
3. 标记 CONFIRMED 或 NOT_REAL，附理由。

拿不准的标 NOT_REAL。
```

能力范围内可修复的当场修复重审；修复不了则上报 Scheduler，本轮运行结束，Issue 打上 `status:awaiting-human`（见 SKILL.md「唤醒人类」）。

## 判断能否自主处理设计变更

规划过程中发现需要退回设计层面的问题时：

- agent 判断自己能处理（比如设计文档里遗漏的细节，不涉及需要人类权衡的取舍）→ 直接在当前运行内转 `phase:design` 处理，再切回 `phase:planning`；
- agent 判断拿不准（涉及只有人类能做的取舍）→ 停在 `phase:design` + `status:awaiting-human`，等人类。

判断准则（先用这三条筛，不确定就归为"拿不准"）：
1. **是否存在多个都说得通的方案，选择依赖业务优先级/资源投入**——需要人类；纯技术正确性问题——可自主。
2. **是否会改变已经跟人类确认过的设计结论**——改变已确认结论需要人类；只是补充遗漏的细节、未曾讨论过的边界——可自主。
3. **改动范围是否明显超出当前 Issue 的主题**（比如需要连带修改设计文档规定的对外接口）——需要人类；影响局限在实现内部——可自主。

## Plan 的存放与产出

plan 的权威版本落在 Issue 上；单次运行期间可以把 plan 落盘到 `.claude/plan/`（不纳入版本控制）做工作副本，供审查环节以文件路径引用，运行结束前写回 Issue。

每轮运行结束按 SKILL.md 定义的格式追加结构化评论，声明这一轮结论和下一步请求。

Designer 只负责**产出** plan checklist，不负责验收它是否真的全部完成——这个环节没有关闭 Issue 的路径，`phase:planning` 走到收敛就直接转 `phase:implementation`，不涉及 SKILL.md「关闭 Issue 前检查 plan checklist」那道闸门。checklist 是否全部勾选、有没有遗漏项需要拆出去追踪，是 Coder 合并前才做的事（见 `references/coder.md`）。
