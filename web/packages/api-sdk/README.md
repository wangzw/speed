# @speed/api-sdk

The spec-first typed surface of speed APIs for the frontend -- the
generated frontend half of the API-contract discipline. Operation
functions, TanStack Query
hooks and response models are generated by orval from the merged
platform document (`contracts/api.json`, the OpenAPI fragments the
platform modules declare, merged by the demo host's `gen` command), and
every HTTP call they make is routed through
`@speed/api-client` (the one package allowed to touch HTTP, enforced by
the `speed/no-direct-http` ESLint rule).

## All-generated discipline

`src/` holds two generated files plus the package's one hand-written
binding:

- `src/index.ts` -- orval output over the merged document, stamped with
  a DO-NOT-EDIT header from `web/orval.config.ts`. The header carries
  the pinned orval version, so tool drift between the generator and the
  committed artifact shows up as a diff in the header itself.
- `src/features.ts` -- output of `web/scripts/feature-names.mjs` from
  `contracts/features.json` (the demo host's `gen --features` output),
  stamped with its own DO-NOT-EDIT header. Exported as the
  `@speed/api-sdk/features` subpath.
- `src/runtime.ts` -- the package's only hand-written source file,
  exported as the `@speed/api-sdk/runtime` subpath. It exists because
  generated code must not know how a host wires its HTTP transport.

Never hand-edit a generated file, and never add another hand-written
file inside `src/` to bridge generation gaps: tooling problems belong
to tooling (see the fixup below), not to shipped source.

## Regenerating

One command from `web/` regenerates both generated files:

```sh
cd web
pnpm api:gen
```

`web/package.json`'s `api:gen` runs `web/scripts/feature-names.mjs` to
write `src/features.ts` from `contracts/features.json` first, then runs
orval over `contracts/api.json` and the nodenext fixup, so one command
refreshes both files. orval is pinned to 8.17.0 and never enters the
workspace lockfile -- it is fetched on demand through `pnpm dlx` -- and
every caller runs this same command, so neither generated file drifts
from the other or from the pinned generator. A version bump must land in
`orval.config.ts`'s comment and `web/package.json`'s script together.

### Why the fixup script

orval emits mutator imports without a file extension -- one line per
mutator: `import { speedRequest } from './runtime';`, plus a second line
for each per-operation override (`import { speedRequestCredentialless }
from './runtime';` for the authn refresh operation) -- specifiers
TypeScript accepts under bundler resolution but rejects under nodenext
(TS2835), where this package's build runs.
`web/scripts/orval-nodenext-fixup.mjs` deterministically rewrites every
such import to the explicit `'./runtime.js'` form after each
regeneration and exits non-zero when orval's emission changes or drops
them; the package's nodenext build then rejects any committed import the
script did not rewrite. Regeneration and the fixup are manual steps -- no
CI job reruns them -- so run `pnpm api:gen` whenever `contracts/api.json` or
`contracts/features.json` changes. Config paths in `orval.config.ts` are
relative to the config file's directory (`web/`).

## How generated code calls HTTP

Generated functions call the mutator `speedRequest` (imported from
`src/runtime.ts`) with one axios-shaped options object; a per-operation
override in `web/orval.config.ts` switches the session-refresh
operation to the `speedRequestCredentialless` mutator, which declares
the request credential-less (`omitAccessToken`) so it carries no
Authorization header and never reads the host's token store -- the
refresh request authenticates with the refresh token in its body, and
its 401 must stay terminal under `@speed/api-client`'s bearer-only
refresh rule rather than re-entering the refresh path. `runtime.ts`
adapts that call to the `@speed/api-client` request function the host
bound once at bootstrap:

```ts
import { bindRequestFn } from '@speed/api-sdk/runtime'
import { createClient } from '@speed/api-client'

bindRequestFn(
  createClient({ baseUrl: window.location.origin, accessTokenStore: ... }),
)
```

`baseUrl` is the origin alone when the client binds this generated
surface: every generated operation path already carries its own
`/api/v1`, and the client appends paths verbatim. A hand-written layer
that uses `@speed/api-client` directly may instead keep an API prefix in
`baseUrl` and pass prefix-less paths -- the two conventions belong to
different callers of the same client.

Transport concerns (base URL, access-token store, refresh, retry,
timeout, reporter, the language and tenant headers) are entirely the
host's `createClient` configuration; generated code carries none of
them (the tenant the transport announces as `X-Tenant` included), and
generated query keys are plain path strings
without a tenant prefix -- tenant query-key namespacing is a
consumer-shell discipline.

## Generated surface (the merged document)

orval input is the merged `contracts/api.json` -- the demo host's `gen`
command merging the OpenAPI fragments the platform modules declare (each
module's `http.Spec` resource, through `pkg/ops/openapi.Merge`). orval
runs over that merged document, so a platform fragment only reaches this
package by entering the merge, and every platform module with an HTTP
fragment is a merge member. A consuming app's own fragments are members
too, but their operations carry the application-owner tag `gen` writes
from the declaring module's Go package, and `web/orval.config.ts` excludes
that tag through orval's `input.filters`; the app generates its own SDK
over the unfiltered document through a second orval configuration that
lives with the app (the starter's self-service organization creation is
the app fragment that exercises that leg).
Platform
membership, in the same per-operation shape:

- `useAuthnLoginWithPassword` -- `useMutation` hook;
  `authnLoginWithPassword(body)` function; the authn group covers the
  full session lifecycle (login channels, logout, tenant switch,
  refresh, registration, code sending, `/me`, session listing and
  revocation, MFA and social sign-in) and exists because
  `@speed/auth-core` consumes it (see Status below): a spec change
  whose regenerated surface outgrows auth-core's calls fails that
  package's typecheck.
- Every other platform fragment group follows the same shape --
  notification, billing, org, storage, sharing, pki, admin,
  integration and ai-gateway each export their module's hooks, plain
  functions, types and error envelopes.
- Error typing is per-module (`NotesError`-shaped `{code, params}`
  envelopes -- codes resolve to bilingual user-facing text in the
  consuming package's own catalogs; no i18n resources ship here).
- `./runtime` subpath: `bindRequestFn`, the `speedRequest` mutator and
  the per-operation `speedRequestCredentialless` mutator. The app-owned
  SDK's own seam re-exports this subpath, so one `bindRequestFn` call
  at bootstrap serves both generated surfaces.
- `./features` subpath: `FeatureNameRegistry`, `FeatureName` and
  `FEATURE_NAMES`, generated by `web/scripts/feature-names.mjs` from
  `contracts/features.json` (the demo host's `gen --features` output).
  The generator registers the platform-owned names only: an application
  declares its own names through a module augmentation of the same
  registry, which its own build writes (the demo's is
  `starters/demo/web/src/app-api/features.ts`). Frontend code that writes
  a feature name (a route's `requires`, a control's gate) takes
  `FeatureName`, so a misspelled name fails to compile; `FEATURE_NAMES`
  is the run-time membership list of the platform names.

The peer family (`react` + `@tanstack/react-query` v5) exists so hosts
share one `QueryClient`/`QueryClientProvider`; the package itself never
creates one.

## Consumption status

Compile consumption is live in-workspace, and `starters/demo/web` binds
this surface at runtime.

- **Compile-consumed in-workspace.** `@speed/auth-core` type-checks
  against the generated authn surface, and its unit suite drives the
  session operations through a scripted `RequestFn` bound with
  `bindRequestFn` -- the same seam a host's real client binds.
  `@speed/account-ui` is the second in-workspace compile consumer and
  the first to render generated hooks into a component tree, and
  `@speed/admin-ui` consumes the generated admin operations. The
  merged document is covered by the same
  regeneration-and-comparison step.
- **Runtime consumption.** `starters/demo/web` binds this surface at
  runtime: its app-entry assembly (`@speed/product-shell/bootstrap`'s
  `bootstrapSpeedApp`) binds one real `@speed/api-client` client through
  this package's `bindRequestFn` seam, and the app's admin area drives
  the generated operations through the composed tree. Release-time
  packaging of the published SDK (generated from the merged `api.json`,
  versioned alongside the doc site) is not shipped -- release-machinery
  work.

## Development

From this directory (`web/packages/api-sdk/`), or workspace-wide from
`web/` with `pnpm -r`:

```sh
pnpm lint        # eslint; generated src/ must pass, incl. speed/no-direct-http
pnpm typecheck   # strict, bundler resolution against sibling sources
pnpm test        # vitest (jsdom); colocated tests exercise generated hooks
pnpm build       # tsc nodenext build; pre-builds @speed/api-client for its dist types
```

Tests live one-per-source-file next to what they test
(`src/runtime.test.ts`, `src/index.test.ts`) and never touch a network.
