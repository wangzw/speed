# pkg/objectstore

The object-storage capability: an object's bytes, together with its metadata,
land in the system once and are thereafter read, listed and deleted by
identifier. The root package is the interface package — it carries the
capability's seams, the common types and the backend factory, and registers no
module.

An object is written in three steps. **Declaration** validates what the caller
states, reserves an identifier and an internal key, and lands a `pending` row
open for upload. **Upload** stores the bytes through the byte seam and moves the
row to `uploaded`. **Completion** moves the row to `completed`, after which the
object can be read. The bytes live behind one seam, the metadata and lifecycle
behind another; each is held by the party that owns it.

## The two seams

- **`Store`** is the byte seam — `Name`, `Put`, `Open`, `Delete`. An object's
  bytes move through it and nowhere else. The internal key that addresses them
  is generated by the metadata module; this seam promises nothing about its
  syntax, and an implementation only maps it to wherever its own backend keeps
  bytes.
- **`Objects`** is the metadata and lifecycle seam — `Create`, `Upload`,
  `Complete`, `Get`, `OpenContent`, `List`, `Delete`. It is delivered
  exclusively by the metadata module, and its methods carry the lifecycle rules:
  what a state allows, what an upload window closes, and how a list pages.

`Object` is one object's view, `Declaration` is what a caller states before any
byte arrives, `ListQuery` narrows and pages a list, and `State` is the closed set
`pending` / `uploaded` / `completed` / `deleted`. The declared values a caller
gave and the observed values recorded at upload are kept apart in the table, and
the view hands out the observed side.

The root package also declares the audit action type names — `EventObjectCreated`,
`EventObjectCompleted` and `EventObjectDeleted`. An audit action is not a
resource: this package declares the names and publishes nothing. The host emits
the event at the irreversible point a name describes, and the audit module names
the type it watches through its own configuration.

## The two backends

`fs` and `s3` are the implementations of the byte seam, each a module of its own:

- **`objectstore.fs`** keeps bytes under a local directory. Its dependencies are
  the standard library and this root package, so an assembly that uses only a
  local directory carries no object-storage SDK. Its bytes are visible only to
  the process that can reach that directory: a multi-replica assembly that shares
  one set of bytes needs `s3`.
- **`objectstore.s3`** keeps bytes in an S3-compatible object store and binds its
  own SDK, which lands in that subpackage alone.

Both deliver `(*Store)(nil)` **exclusively**: one process has exactly one answer
to where bytes land, so a host names exactly one of them on the command tree and
two at once fail in resolution. The metadata module requires `(*Store)(nil)`
non-optionally, so an assembly that installs no backend fails at startup.

## What the capability does not do

- **Content re-verification, sanitization and thumbnail derivation are deferred
  on purpose, not left out.** The capability records the byte count and SHA-256
  it observes at upload and refuses an upload whose byte count differs from the
  declaration, but it does not recompute a declared checksum against the bytes,
  does not parse or re-encode a format, does not scan for anything, and does not
  derive a thumbnail or any other projection from an object's bytes. Completion
  only moves the row into a usable state.
- **It makes no authorization decision.** It declares its permission points and
  the permission each of its routes needs; the decision is made by the entry
  module's middleware against the route declarations.
- **It does not interpret an object's content or purpose.** `Object.MIME` is an
  opaque value. `Declaration.Name` is the caller's label: it is optional, it is
  normalized once by the metadata module before it is stored, and it
  identifies nothing — it is not unique and no lookup reads it.
- **It does not queue or retry.** One upload and one read are synchronous calls
  that return once the backend has answered; a backend that is unreachable fails
  that call.
- **It does not write audit rows.** It declares the action type names and points
  no dependency at the audit module.

The internal key never leaves the capability. It is not in any API response, not
in any error text and not in any log line; changing its syntax is an internal
change that no caller can observe.

## How a backend contributes

A backend subpackage fixes its namespace, states its stance and its credentials,
and registers the module this package builds from its `Spec`.

```go
func init() { core.ProcessRegistry.Register(Module()) }

func Module() core.Module {
	prototype := Config{}
	return objectstore.NewModule(objectstore.Spec[Config]{
		ModuleName:      ModuleName,   // "objectstore.fs"
		ConfigNamespace: ModuleName,   // where this backend's items are mounted
		Config:          &prototype,   // the prototype, carrying the defaults
		Items:           items,        // the declared input items
		Stance:          stance,       // how the exclusive claim yields, or what is missing
		Secrets:         secrets,      // the credential strings to redact, or nil
		Open:            open,         // builds the Store
	})
}
```

**A backend registers its secrets before it binds any logger.** `Spec.Secrets`
returns the credential strings to register as literal redaction matchers, and the
factory registers them through `pkg/internal/literal` before it calls
`Spec.Open`, which is where a backend would bind an attribute to a `Named`
logger. The register lives one level up at `pkg/internal/literal`, not here,
because a backend's credentials and the login leaves that use the same register
must not each carry their own copy. A backend whose credentials come only from
configuration returns what it decoded; a backend with no credential leaves the
hook nil.

## Boundaries

- **The root package registers no module and imports no object-storage SDK.** It
  imports `pkg/config` for reading a backend's values, `pkg/core` for the
  registry, `pkg/internal/literal` for the redaction register, and `pkg/log` for
  the optional logging capability. A backend's SDK is bound by the subpackage
  that deploys on it, so it is never in what a host compiles by importing the
  root package. `deps_test.go` holds the root package's non-test dependency face
  to no object-storage SDK and to no upper-layer feature directory.
- **Bytes are addressed by an internal key the metadata module generates.** The
  key's syntax is this capability's private convention, and an implementation
  maps it to a relative path or an object key of its own; the mapping never
  enters the seam and never appears in an answer.
- **`Store`, `Objects`, `State`, `Object`, `Declaration` and `ListQuery` are the
  contract with a caller**, as are the sentinels. Adding a method, changing a
  signature or renaming a field is incompatible for the backends that implement
  the seam and the callers that take it up.

## Running it

From the repository root, over every module in the workspace:

```
make build
make test
make test-race
make lint
make check
```

`make check` is what CI runs. On this capability alone:

```
go -C pkg build ./objectstore/...
go -C pkg test ./objectstore/...
go -C pkg test -race ./objectstore/...
env -C pkg golangci-lint run ./objectstore/...
```

Run `golangci-lint` from inside `pkg`: handed an absolute path from outside the
module it prints zero issues without loading the packages.
