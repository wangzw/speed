# pkg/authn/mfa/totp

The TOTP second factor of the authentication capability: the one factor kind whose
code is generated by the user's own authenticator app from a seed this module
holds. It delivers `authn.Factor` for the kind `totp`, without claiming the
capability, so the kinds stand side by side and the multi-factor module takes them
all.

The orchestration is not here. Registration, the failure back-off, the audit row
and the event belong to `authn.mfa`, which drives this factor through the root
package's `Factor` interface. What this module does is generate a seed, seal it,
hand back the otpauth address once, and check a code against the seed with the
replay protection the library's own validation does not give. It reads the time
through a source a test replaces, and it never logs.

## Where the authority is

- What this module is and why it is shaped this way: the `TOTP` section of
  [`docs/design/modules/design-authn-mfa.md`](../../../../docs/design/modules/design-authn-mfa.md).
  The table it owns (`authn_totp_secrets`) and the `Factor` seam it answers are in
  that document too.
- The decisions behind it: the factor seam and the single composition of the level
  ([`adr-authn-mfa-2026-10-10.md`](../../../../docs/adr/adr-authn-mfa-2026-10-10.md)) —
  in particular that TOTP verification does not use the library's boolean
  validation, and that the replay counter lives in the database and is judged by a
  conditional write — and where that state is placed and why
  ([`adr-authn-state-placement-2026-10-10.md`](../../../../docs/adr/adr-authn-state-placement-2026-10-10.md)).
- The one input item, its default and its domain:
  [`docs/design/modules/design-authn-config.md`](../../../../docs/design/modules/design-authn-config.md)
  (`authn.mfa.totp.issuer`, defaulting to the host name of the gateway's public
  address). The `authn.mfa.verifications` instrument this factor's outcomes are
  counted under is the multi-factor module's, reported there and not here.
- The API itself: the godoc in this package. Read `factor.Enroll`'s comment before
  changing the two steps of a registration, and `factor.Verify`'s before changing
  the replay judgement.

This file states only what neither of those states: the boundaries a change here
must not cross, and how to run it.

## Boundaries

- **The seed is a secret and it stays inside this module.** It is written into an
  encrypted column (`secret`, `serializer:encrypted`) and read back through the
  model, so the database module seals it on the way in and opens it on the way out
  (`register.go`, `seedRow`). It is never written to a log line, an error text, an
  event or a metric. The `otpauth://` address carries the seed, so it is answered
  once by the first registration step and read back nowhere: the confirmation step
  answers with the record and no payload
  (`TestARealRegistryRegistersAndVerifiesATOTPFactor`,
  `TestVerifyRefusesAForgedCode` does not leak it either). `Verify` and `Remove`
  never return it.
- **The kind is `totp`, delivered without claiming it, and the module requires
  the database and the multi-factor module.** The factor kinds stand side by side,
  so the provision is not exclusive; the multi-factor module drives this one and a
  command that takes this factor without it fails at resolution, because a factor
  without its orchestrator can check nothing
  (`TestTheDescriptorNamesWhatItDeliversAndRequires`). The pending row's
  identifier, which is what this factor keys its seed by, arrives in the context
  the multi-factor module set; a call that finds none registers nothing
  (`factor.Enroll`, `mfa.PendingFactor`).
- **A registration writes the seed then requires a valid code.** The first step
  generates a 20-byte secret with the convention every authenticator app follows
  (SHA-1, six digits, a thirty-second step), writes it sealed and answers the
  otpauth address. The confirmation step, told apart by the marker left in the
  factor's private bytes, requires the code of that seed and, on a match, answers
  `StepEnrolled`, which is what the multi-factor module activates the row on. A
  code that does not match leaves the row pending
  (`factor.Enroll`, `TestARealRegistryRegistersAndVerifiesATOTPFactor`,
  `TestEnrollmentGeneratesAConventionalSeed` pins the generated secret's length
  and the recorded algorithm, digit count and step).
- **Verification accepts the current step and one either side, and nothing
  wider.** The window is fixed at one step and is not a setting; the library's
  `Validate` is not used, because it answers only whether some step matched and
  reports none of them. The comparison is constant time, and every candidate step
  is generated before the first match is honoured, so the time before a match does
  not depend on which step matched (`code.go` `match`,
  `TestVerifyAcceptsOneStepEitherSide`, `TestVerifyRefusesACodeTwoStepsOut`). A
  code built for another algorithm, another digit count or another step does not
  match (`TestVerifyRefusesACodeBuiltWithOtherParameters`,
  `TestVerifyRefusesAForgedCode`).
- **The replay judgement is a conditional write, not a read.** The matched
  counter must be above the stored one, and the write is
  `UPDATE authn_totp_secrets SET last_counter = ? WHERE factor_id = ? AND last_counter < ?`:
  one row affected is a pass, zero is `ErrReplay`. Two attempts that present one
  code both read a lower stored value, and the write lets exactly one through
  (`factor.Verify`, `register.advance`,
  `TestTwoConcurrentVerificationsOfOneCodeLeaveExactlyOneTheWinner`,
  `TestVerifyRefusesTheSameCodeTwiceAsAReplay`).
- **A factor that is not active, or whose seed is gone, is `ErrFactorNotEnrolled`
  and never an outage or a pass.** The zero status is pending, and a pending row
  is never used to verify; a read that fails is an outage the multi-factor module
  answers 503, not a refusal
  (`TestVerifyRefusesAFactorThatIsNotActive`,
  `TestVerifyRefusesAFactorWhoseSeedIsGone`).
- **A challenge sends nothing.** A TOTP is made by the client's own app, so
  `Challenge` answers a prompt for a code and reports no sends
  (`TestChallengeAsksForACodeAndSendsNothing`).
- **Remove is idempotent.** It deletes the seed and never touches the row that
  names the factor, which belongs to the multi-factor module; deleting a seed that
  is already gone is not an error (`TestRemoveIsIdempotent`).
- **Start probes the table and round-trips the encrypted column.** A missing seed
  table ends the startup with `ErrNotMigrated`; a write and a read that cannot be
  sealed and opened, which is a deployment with no usable root key, ends it with
  `ErrNoEncryptionKey`
  (`TestStartRefusesWhenTheSeedTableIsMissing`,
  `TestStartRefusesWithoutAUsableEncryptionKey`).
- **The step of a code is fixed, and the period column records it.** The design
  fixes the step at thirty seconds, so generation uses that constant; the
  `algorithm`, `digits` and `period` columns the design's table requires record
  what the seed was generated with, and generation reads the first two of them
  (`code.go` `validateOpts`).

## Running it

From the repository root, over every module in the workspace:

```
make build
make test
make test-race
make lint
make check
```

`make check` is what CI runs. On this module alone:

```
go -C pkg build ./authn/mfa/totp/...
go -C pkg vet ./authn/mfa/totp/...
go -C pkg test ./authn/mfa/totp/...
go -C pkg test -race ./authn/mfa/totp/...
env -C pkg golangci-lint run ./authn/mfa/totp/...
```

Run `golangci-lint` from inside `pkg`: handed an absolute path from outside the
module it prints zero issues without loading the packages.

`helpers_test.go` builds the factor over a real database handle
(`pkg/internal/dbtest`) with the encryption key set and a fixed clock, and holds
the helpers that read a step apart. `factor_test.go` covers the code matching, the
replay judgement and the idempotent removal over that rig; the concurrency case
runs on a handle held to one connection, so what decides the winner is the
conditional write and not the engine's write lock. `assembly_test.go` drives a
real registry through the descriptor and the real multi-factor module with
stand-in modules for the exclusive capabilities, which is what holds the startup
checks and the registration-and-verification path end to end. `config_test.go`
covers the issuer default off the public address.
